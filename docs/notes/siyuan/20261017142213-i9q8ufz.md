认证只说明身份，授权决定权限。除此之外，浏览器跨域、反向代理、请求 ID 和安全响应头也属于同一个边界层：它们决定哪些请求能进来、请求如何被追踪，以及响应能暴露什么。

## 401 与 403

- `401 Unauthorized`​：没有提供凭证，或凭证无效。通常带 ​`WWW-Authenticate`。
- `403 Forbidden`：身份有效，但没有权限。

```python
def require_admin(user: CurrentUser) -> User:
    if not user.is_admin:
        raise HTTPException(status_code=403, detail="需要管理员权限")
    return user


AdminUser = Annotated[User, Depends(require_admin)]
```

不要把“未登录”写成 403，也不要把“权限不足”写成 401；客户端和监控系统会据此做出不同反应。

## 角色之外：作用域

角色适合粗粒度权限，OAuth2 scope 适合按操作授权：

```python
oauth2_scheme = OAuth2PasswordBearer(
    tokenUrl="/api/v1/auth/token",
    scopes={"tasks:read": "读取任务", "tasks:write": "创建和修改任务"},
)


@router.post("/tasks")
def create_task(
    user: Annotated[User, Security(oauth2_scheme, scopes=["tasks:write"])],
) -> dict:
    ...
```

令牌需要在 ​`scope`​ 声明里包含对应作用域；​`Security`​ 会检查。scope 不是万能的，真正的资源级权限仍要在查询里限制 ​`owner_id`。不要只依赖前端隐藏按钮。

## CORS

浏览器跨域请求需要服务端明确允许：

```python
from fastapi.middleware.cors import CORSMiddleware

app.add_middleware(
    CORSMiddleware,
    allow_origins=settings.cors_origins,
    allow_credentials=True,
    allow_methods=["GET", "POST", "PATCH", "DELETE"],
    allow_headers=["Authorization", "Content-Type", "X-Request-ID"],
)
```

- `allow_origins=["*"]`​ 与 ​`allow_credentials=True` 不能同时使用；浏览器会拒绝。
- 生产环境列出具体域名，不要用正则匹配任意子域。
- CORS 只限制浏览器读取响应，不阻止非浏览器客户端；真正的权限仍在服务端。
- 预检请求由中间件处理，业务路由不会收到 ​`OPTIONS`。

## 中间件

中间件适合处理所有请求共享的横切逻辑：

```python
from uuid import uuid4

from fastapi import Request


@app.middleware("http")
async def request_id(request: Request, call_next):
    request_id = request.headers.get("X-Request-ID") or uuid4().hex
    request.state.request_id = request_id
    response = await call_next(request)
    response.headers["X-Request-ID"] = request_id
    return response
```

常见中间件：

- `TrustedHostMiddleware`​：限制 ​`Host` 头，防止主机头攻击。
- `GZipMiddleware`：压缩响应，注意不要压缩已经压缩的图片。
- 安全响应头：​`X-Content-Type-Options`​、​`Content-Security-Policy`​、​`Strict-Transport-Security`。
- 请求 ID、耗时、访问日志。
- 限流：通常放在反向代理或 Redis，不在应用进程内做单机计数。

中间件顺序会影响行为。Starlette 中后添加的中间件更靠外层；认证、日志和 CORS 的顺序要结合部署验证，不要凭记忆。

## Cookie 认证与 CSRF

如果令牌放在 Cookie 中，浏览器会自动携带，必须防 CSRF：

- `SameSite=Lax`​ 或 ​`Strict`​，跨站表单场景谨慎使用 ​`None`。
- 写操作要求自定义头或 CSRF token。
- `HttpOnly`​ 防 XSS 读取，​`Secure` 只走 HTTPS。
- 登出时清除 Cookie，并考虑服务端撤销令牌。

纯 Bearer Token 的 API 不依赖 Cookie，CSRF 风险较低，但令牌一旦泄漏就等同于密码。

## 反向代理边界

生产环境通常在 Nginx、Caddy 或云负载均衡后面运行 Uvicorn：

- 只信任来自代理的 ​`X-Forwarded-For`​，配置 ​`--forwarded-allow-ips`。
- 由代理终止 TLS，应用内不要假设 ​`request.url.scheme`​ 一定是 ​`https`。
- 设置请求体上限、超时和连接数，避免应用被慢请求拖垮。
- 代理和应用的请求 ID 要能串起来，日志里使用同一个字段。

## 练习

1. 实现 ​`require_owner` 依赖，确保任务属于当前用户。
2. 为管理员接口加 scope 检查。
3. 配置只允许 ​`https://app.example.com` 的 CORS，并用浏览器验证。
4. 写一个中间件，记录方法、路径、状态码和耗时，但不记录请求体。
