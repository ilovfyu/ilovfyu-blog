> 一句话总结：3.14 是语言层真正「动刀」的版本——模板字符串 t-string、注解延迟求值、标准库支持多解释器、Zstandard 进标准库；同时自由线程摆脱「实验」标签，正式获得官方支持。

## 版本速览

|项目|内容|
| ------------| -----------------------------------------------------------|
|发布时间|2025 年 10 月 7 日|
|上一个版本|3.13|
|维护节奏|常规修复约 2 年，之后继续做安全修复|
|核心主题|t-string、注解延迟求值、多解释器、Zstandard、自由线程转正|
|升级成本|中等偏高，注解和进程启动方式的变化可能影响已有代码|

如果说 3.13 主要是「手感升级」，那 3.14 是「能力升级」：语言层拿到了新语法，标准库拿到了新并发模型和新的压缩格式，解释器层面则完成了自由线程的第一阶段目标。

## 1. 模板字符串 t-string：给字符串加一份「说明书」（PEP 750）

f-string 很方便，但它的问题是：**拼接在当场就发生了**，你拿到的只是一根最终的 `str`，没法知道哪一段是用户输入、哪一段是模板自带的。这给安全处理（HTML 转义、SQL 参数化）留下隐患。

t-string 用 `t` 前缀，语法和 f-string 一样：

```python
name = "Ada"
tpl = t"你好，{name}！"
print(type(tpl))   # <class 'string.templatelib.Template'>
```

它得到的不是字符串，而是一个 `Template` 对象：静态文本和插值被分开保存，可以逐段处理：

```python
from string.templatelib import Interpolation

def upper_interpolations(template):
    parts = []
    for part in template:
        if isinstance(part, Interpolation):
            parts.append(str(part.value).upper())
        else:
            parts.append(part)
    return "".join(parts)

name = "ada"
print(upper_interpolations(t"你好，{name}！"))   # 你好，ADA！
```

插值部分的 `Interpolation` 对象带着 `.value`（求值结果）、`.expression`（原始表达式文本）、`.conversion`（`!r` 之类的转换）、`.format_spec`（格式说明），所以你可以自己决定怎么落字。

**典型用途是做转义**。比如写一个给用户输入转义的 HTML 函数：

```python
from html import escape
from string.templatelib import Interpolation

def html(template):
    out = []
    for part in template:
        if isinstance(part, Interpolation):
            out.append(escape(str(part.value)))   # 只转义插值
        else:
            out.append(part)                     # 静态片段原样保留
    return "".join(out)

user = "<script>alert(1)</script>"
print(html(t"<p>{user}</p>"))
# <p>&lt;script&gt;alert(1)&lt;/script&gt;</p>
```

注意这里转义的是**插值部分**，模板里的 `<p>` 保持原样。同一套思路可以做 SQL 参数绑定、安全的 shell 命令拼装、结构化日志。

> 一句话记忆：f-string 给你「拼好的结果」，t-string 给你「拼之前的零件」。

## 2. 注解延迟求值：写类型不用再加引号（PEP 649 / PEP 749）

以前函数注解在定义时立刻求值，于是：

- 想写前向引用（引用还没定义的类），得加引号 `"MyClass"`。
- 复杂的注解会拖慢模块导入。
- 想在运行时读取注解，行为和预期经常对不上。

3.14 改成**用到时才求值**：

```python
def parse(
    data: str,
    cls: type[Result] = Result,   # Result 在后面才定义，也不需要引号
) -> Result:
    ...
```

注解被存进专门的「注解函数」（`__annotate__`），默认不执行。要检查注解时，用新模块 `annotationlib`：

```python
from annotationlib import get_annotations, Format

def func(arg: Undefined) -> None: ...

get_annotations(func, format=Format.VALUE)       # 求值，名字不存在会 NameError
get_annotations(func, format=Format.FORWARDREF)  # 未定义的名字变成 ForwardRef
get_annotations(func, format=Format.STRING)      # 统一变成字符串
```

三种格式分别对应三种使用场景：

|格式|得到什么|适合谁|
| ------| --------------------------| ------------------------------------|
|`VALUE`|真正的运行时对象|需要真实类型的框架|
|`FORWARDREF`|未定义的名字用占位符表示|文档生成、序列化|
|`STRING`|注解的字符串形式|不需要导入依赖、不触发副作用的场景|

开启方式也不复杂：如果你想保留旧行为（注解按字符串处理），继续 `from __future__ import annotations` 就行。框架作者需要注意：`typing.get_type_hints()`、`inspect.get_annotations()` 在 3.14 的行为也跟着这条链路走。

## 3. 多解释器进入标准库：同一个进程里开多个「沙盒」（PEP 734）

CPython 早就能在同一个进程里跑多个互相隔离的解释器，但过去只有 C API 能用。3.14 把它带进了标准库：`concurrent.interpreters`。

```python
from concurrent import interpreters

interp = interpreters.create()

# 在子解释器里执行一段代码
interp.exec('print("hello from another interpreter")')

# 或者调用一个函数，拿到返回值
def add(a, b):
    return a + b

result = interp.call(add, 1, 2)
print(result)   # 3
```

两个解释器之间用 `Queue` 通信，而不是共享变量：

```python
from concurrent import interpreters

interp = interpreters.create()
queue = interpreters.create_queue()

def worker(q):
    q.put("来自子解释器的消息")

t = interp.call_in_thread(worker, queue)
print(queue.get())
t.join()
```

它和已有方案的差别值得记住：

|方案|内存|并行|共享数据|启动成本|
| -----------| --------------------| -------------| ------------------------| --------------|
|线程 `threading`|共享|受 GIL 限制|随意共享|最低|
|进程 `multiprocessing`|独立|真正并行|需要序列化传递|较高|
|多解释器|同一进程、互相隔离|真正并行|只能通过队列等机制传递|介于两者之间|

可以粗略理解成：**进程级的隔离，线程级的轻量**。

限制也要清楚：

- 解释器启动还不够快，每个解释器会多占一些内存。
- 真正能共享的数据很有限（基本只剩 `memoryview` 和队列）。
- 很多第三方 C 扩展还不兼容多解释器（标准库里的扩展已经兼容）。
- 跨解释器传对象默认走 pickle，可变对象不会「同步」。

对绝大多数业务代码来说，3.14 还不到「必须用」的程度；但当你要在同进程里跑互不信任的插件、或者想把 CPU 密集任务并行化又不想负担进程开销时，它是个新选项。

## 4. Zstandard 进标准库：压缩比和速度都更好（PEP 784）

Zstandard（zstd）这几年在日志、数据管道里很流行：压缩比接近 gzip 的高级设置，速度却快得多。3.14 新增 `compression.zstd`：

```python
from compression import zstd

data = b"hello zstd " * 1000
packed = zstd.compress(data, level=3)

with zstd.open("demo.zst", "wb", level=3) as f:
    f.write(data)

with zstd.open("demo.zst", "rb") as f:
    print(f.read() == data)   # True
```

需要更细的控制时，用 `ZstdCompressor` / `ZstdDecompressor` 做流式压缩解压，或者用 `compression.zstd.ZstdFile` 包住已经打开的文件对象。

> 迁移提示：`gzip`、`bz2`、`lzma` 都还在，不需要急着改；新项目选 zstd，通常能同时省 CPU 和磁盘。

## 5. 自由线程正式支持（PEP 779），JIT 覆盖面扩大

3.13 的自由线程还标着「实验」，3.14 正式变成**官方支持的构建**（PEP 779）。实现层面的临时方案被替换成长期方案，C API 完成，专门化自适应解释器也在自由线程构建里启用了。

- 二进制仍然单独提供，通常叫 `python3.14t`。
- 单线程代码的性能损失降到约 **5%–10%** （具体看平台和编译器），比 3.13 明显改善。
- 默认构建**仍然带 GIL**。想用自由线程，要显式选择那个构建版本。

同时，实验性 JIT 从 Linux 扩展到 Windows 和 macOS 的官方二进制，不再需要自己编译才能试。

## 6. 解释器内部：尾调用解释器、增量式回收

这两项都不改变代码写法，但值得了解，因为它们解释了「为什么这个版本快一点」。

- **尾调用解释器**：把「一个大 switch 分发所有字节码」改成「每个操作码一个小 C 函数之间尾调用」。在 Clang 19 及更新的编译器上，pyperformance 基准大约快 **3%–5%** 。它是可选项，需要 `--with-tail-call-interp` 编译。
- **增量式垃圾回收**：3.14 引入了增量式 GC，把回收工作拆成小步，减少长时间停顿。不过因为生产环境反馈了显著的内存压力，**从 3.14.5 起又改回 3.13 的分代式回收**。所以「3.14 用增量 GC」这句话只对 3.14.0–3.14.4 成立。

## 7. 语法与内置函数的小改动

### `except` 可以不带括号（PEP 758）

多个异常类型、又不用 `as` 时，括号可以省掉：

```python
try:
    connect()
except TimeoutError, ConnectionRefusedError:
    print("网络没连上")
```

### `finally` 里的跳转会被警告（PEP 765）

在 `finally` 里写 `return`、`break`、`continue`，会吞掉异常或提前结束循环，长期是 bug 温床。3.14 起编译器会发 `SyntaxWarning`；将来可能变成错误。

```python
def f():
    try:
        return 1
    finally:
        return 2   # 现在会警告：这会把返回值改成 2
```

### 其他顺手的变化

- `-O` 模式下也会检查更多语法错误，例如 `assert await 1`、向 `__debug__` 赋值。
- `map()` 支持 `strict=True`，可迭代对象长度不一致时直接报错，和 `zip(strict=True)` 一致。
- 新增 `float.from_number()`、`complex.from_number()`，把数值明确转成浮点/复数。
- `bytes.fromhex()`、`bytearray.fromhex()` 可以直接吃 `bytes` 参数，不用先解码成 `str`。
- `int()` 不再调用 `__trunc__()`，自定义类型想支持 `int()` 必须实现 `__int__()` 或 `__index__()`。
- 三参数 `pow()` 现在会尝试 `__rpow__()`。
- 格式化浮点数时，小数部分也能用下划线或逗号做千分位分隔。
- `super` 对象可以复制和 pickle 了。
- 新增 `uuid.uuid6()`、`uuid.uuid7()`、`uuid.uuid8()`（RFC 9562）。其中 uuid7 因为自带时间戳、可直接排序，很适合做数据库主键。
- `python -c` 的代码会自动缩进，粘贴多行片段更省事。

## 8. 调试、观测与并发安全

### 安全地给运行中的进程「加调试器」（PEP 768）

3.14 提供了零开销的外部调试接口 `sys.remote_exec()`：把一段脚本送进目标进程，在下一个安全执行点运行。不需要重启，也不改代码：

```python
import sys

sys.remote_exec(1234, "/path/to/inspect.py")
```

出于安全考虑，它可以用 `PYTHON_DISABLE_REMOTE_DEBUG` 环境变量、`-X disable-remote-debug` 选项或构建时的 `--without-remote-debug` 关闭。

### asyncio 可以被「看一眼」了

新增命令行，直接查看某个进程里正在跑的任务：

```bash
python -m asyncio ps 12345       # 任务列表、协程栈、谁在等谁
python -m asyncio pstree 12345  # 用树形展示等待关系
```

排查「协程卡住了」这类问题，比翻日志快得多。

### 并发安全的警告控制

`warnings.catch_warnings()` 现在可以基于上下文变量生效。它的开关是 `-X context_aware_warnings`，在自由线程构建里默认打开，在多线程/异步场景下警告过滤终于可预测了。

### 导入耗时看得更细

`-X importtime=2` 会把「从缓存加载」的模块也标出来，排查启动慢时不再看到一堆 0 毫秒的误导信息。

## 9. 发布方式与平台支持

- **Emscripten 成为官方支持平台**（第 3 层级），浏览器里跑 Python 有了正式入口。
- **提供 Android 二进制发布包**。
- **PGP 签名退役**（PEP 761）：官方发布包改用 Sigstore 签名与证明，验证方式需要更新。
- **新增** **`build-details.json`**（PEP 739）：安装包里带上构建信息，不用启动解释器就能查到构建参数，对打包、交叉编译、启动器都有用。

## 10. 一个容易被忽略的坑：多进程默认启动方式变了

在 macOS 以外的 Unix 平台上，`multiprocessing` 和 `ProcessPoolExecutor` 的默认启动方法从 `fork` 改成了 `forkserver`。

影响在于：

- 依赖 `fork` 复制父进程内存的代码，行为会变。
- 某些「父进程里定义的对象」不再能自动被子进程看到，需要能 pickle。
- 使用可变全局变量共享状态的写法会失效。

如果暂时不想改，可以显式指定：

```python
import multiprocessing as mp

ctx = mp.get_context("fork")
```

升级时如果遇到 `NameError`、pickle 报错，先检查这一条。

## 升级检查清单

从 3.13 升到 3.14 之前：

1. 跑测试，重点看 `multiprocessing` / `ProcessPoolExecutor` 相关用例（默认启动方法变了）。
2. 检查依赖注解的代码：ORM、数据校验、依赖注入框架，确认它们支持 3.14 的延迟注解。
3. 搜一下 `finally` 里的 `return` / `break` / `continue`，提前修掉。
4. 检查是否有依赖 `int()` 调 `__trunc__()`、`NotImplemented` 布尔上下文的老代码。
5. 日志、备份脚本可以考虑换用 `compression.zstd`，但先验证目标机器上的 Python 版本。
6. 如果发布流程里用 PGP 校验官方包，改成 Sigstore 校验。
7. 想上自由线程构建的，先确认关键 C 扩展是否提供了 `cpython-314t` 的 wheel。

## 小结

3.14 的重点可以浓缩成四句话：

- **写字符串更安全**：t-string 把「模板」和「值」分开。
- **写类型更省心**：注解延迟求值，前向引用不用再套引号。
- **跑并发多了选择**：多解释器带来进程级隔离、线程级开销。
- **底层继续提速**：自由线程转正、JIT 扩平台、尾调用解释器可选用。
