`Base.metadata.create_all()` 只能把当前模型变成表，不能表达“从旧版本升级到新版本”。一旦有真实数据，就需要迁移文件：每次结构变更都有唯一版本、可审查的 SQL 和可回滚的步骤。

## 初始化 Alembic

```bash
python -m pip install "alembic==1.20.0"
alembic init migrations
```

生成的文件：

```text
alembic.ini
migrations/
├── env.py
├── script.py.mako
└── versions/
```

`alembic.ini`​ 里的 ​`sqlalchemy.url` 可以写本地开发地址，但生产环境应从配置或环境变量读取，不要提交真实密码。

## 让 env.py 认识模型

```python
from logging.config import fileConfig
from pathlib import Path
import sys

from alembic import context
from sqlalchemy import engine_from_config, pool

sys.path.insert(0, str(Path(__file__).resolve().parents[1]))

from app.db import Base
from app import models  # noqa: F401  确保模型被导入

config = context.config
if config.config_file_name is not None:
    fileConfig(config.config_file_name)

target_metadata = Base.metadata


def run_migrations_offline() -> None:
    context.configure(
        url=config.get_main_option("sqlalchemy.url"),
        target_metadata=target_metadata,
        literal_binds=True,
        dialect_opts={"paramstyle": "named"},
    )
    with context.begin_transaction():
        context.run_migrations()


def run_migrations_online() -> None:
    connectable = engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    with connectable.connect() as connection:
        context.configure(
            connection=connection,
            target_metadata=target_metadata,
            render_as_batch=connection.dialect.name == "sqlite",
        )
        with context.begin_transaction():
            context.run_migrations()


if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()
```

`render_as_batch=True`​ 用于 SQLite：它不支持完整的 ​`ALTER TABLE`，Alembic 会用“建新表、复制数据、换名”的方式完成修改。PostgreSQL 不需要这个选项。

## 生成与审查

```bash
alembic revision --autogenerate -m "create users and tasks"
alembic upgrade head
```

自动生成只是起点。必须打开 ​`migrations/versions/*.py` 检查：

- 表、列、索引、外键是否和模型一致。
- 是否误删了列或表。
- 是否有需要回填的数据。
- 降级函数 ​`downgrade()` 是否能安全执行。

迁移文件应提交到版本库，并与代码一起发布。

## 命名约定

数据库约束名不稳定会让后续迁移难以定位。给 ​`MetaData` 加统一命名：

```python
from sqlalchemy import MetaData
from sqlalchemy.orm import DeclarativeBase


class Base(DeclarativeBase):
    metadata = MetaData(
        naming_convention={
            "ix": "ix_%(column_0_label)s",
            "uq": "uq_%(table_name)s_%(column_0_name)s",
            "ck": "ck_%(table_name)s_%(constraint_name)s",
            "fk": "fk_%(table_name)s_%(column_0_name)s_%(referred_table_name)s",
            "pk": "pk_%(table_name)s",
        }
    )
```

## 异步项目的迁移

异步 SQLAlchemy 项目可以用异步模板：

```bash
alembic init -t async migrations
```

`env.py`​ 会使用 ​`async_engine_from_config`​ 和 ​`run_sync`。迁移命令仍然是同步执行，只是内部通过异步连接运行。若团队更熟悉同步迁移，也可以单独维护同步数据库 URL，只用于 Alembic。

## 生产流程

1. 部署前先备份数据库。
2. 在应用启动前执行 ​`alembic upgrade head`，作为独立任务或 init container。
3. 只运行一个迁移进程；不要每个 worker 启动时都执行。
4. 大表变更拆成多步，避免长时间锁表。
5. 准备回滚方案，但不要假设 ​`downgrade()` 一定能恢复数据。
6. 数据迁移和应用代码变更分开提交，便于定位。

不要在应用启动时自动 ​`create_all()` 或自动迁移。启动失败、并发执行和权限问题都会让部署变得更难排查。

## 验证

```bash
alembic current
alembic history
alembic upgrade head
alembic downgrade -1
alembic upgrade head
```

本地验证过：自动生成的迁移创建了 ​`users`​、​`tasks`​、索引和 ​`alembic_version`​ 表；​`upgrade head`​ 后表存在，​`downgrade -1` 能撤销。生产环境还要在真实数据库副本上演练。

## 练习

1. 给 ​`Task`​ 增加 ​`priority` 列，生成并审查迁移。
2. 加一个唯一约束，确认命名约定生效。
3. 写一个只做数据回填的迁移。
4. 解释为什么迁移不应放在 ​`lifespan` 里。
