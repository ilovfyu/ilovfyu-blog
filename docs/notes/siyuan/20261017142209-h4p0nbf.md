上一章的模型只够演示路由。真实接口需要区分“创建时允许提交什么”“更新时允许改什么”“返回给客户端什么”，并把约束写进模型，让校验发生在进入业务逻辑之前。

## 三个模型，一条边界

```python
from datetime import datetime, timezone

from pydantic import BaseModel, ConfigDict, Field, field_validator


class TaskCreate(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)

    title: str = Field(min_length=1, max_length=200)
    description: str | None = Field(default=None, max_length=2000)
    done: bool = False

    @field_validator("title")
    @classmethod
    def title_not_blank(cls, value: str) -> str:
        if not value.strip():
            raise ValueError("标题不能全是空白字符")
        return value


class TaskUpdate(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)

    title: str | None = Field(default=None, min_length=1, max_length=200)
    description: str | None = Field(default=None, max_length=2000)
    done: bool | None = None


class TaskPublic(BaseModel):
    model_config = ConfigDict(from_attributes=True)

    id: int
    title: str
    description: str | None
    done: bool
    created_at: datetime
    updated_at: datetime
```

`TaskCreate`​ 描述创建请求，​`TaskUpdate`​ 描述 PATCH 请求，​`TaskPublic` 描述响应。三者分开，才能避免“客户端可以提交 id”或“响应泄漏内部字段”这类问题。

## 约束先于业务

`Field(min_length=1, max_length=200)`​ 会在请求进入处理函数前执行；​`extra="forbid"`​ 会拒绝未声明字段，避免客户端悄悄传入 ​`owner_id`​、​`is_admin`​ 之类的字段；​`str_strip_whitespace=True` 会先去掉首尾空白，再做长度校验。

字段级规则用 ​`field_validator`​。多个字段之间的规则用 ​`model_validator(mode="after")`，例如拒绝一个什么字段都没提供的 PATCH 请求：

```python
from pydantic import model_validator


class TaskUpdate(BaseModel):
    model_config = ConfigDict(extra="forbid")
    title: str | None = Field(default=None, min_length=1, max_length=200)
    done: bool | None = None

    @model_validator(mode="after")
    def at_least_one_field(self) -> "TaskUpdate":
        if not self.model_fields_set:
            raise ValueError("至少提供一个要更新的字段")
        return self
```

校验器只做与数据本身有关的判断。需要查数据库的规则，例如“标题在同一用户下唯一”，应放到业务层或数据库约束里，而不是在模型里访问会话。

## 让响应模型过滤字段

在路由上声明 ​`response_model=TaskPublic`，FastAPI 会用这个模型序列化返回值：

- 返回值里多出的字段不会出现在响应中。
- 类型会被再次校验，避免业务层返回了错误结构。
- OpenAPI 会记录响应 schema。

配合 ​`from_attributes=True`，可以直接返回 SQLAlchemy 对象，Pydantic 会按属性读取，而不要求先转成字典。后续接入数据库时不需要再手写序列化函数。

## PATCH 与 exclude_unset

更新接口要区分“没传这个字段”和“显式传了 null”。用 ​`model_dump(exclude_unset=True)`：

```python
@app.patch("/tasks/{task_id}", response_model=TaskPublic)
def update_task(task_id: int, payload: TaskUpdate) -> TaskPublic:
    task = tasks[task_id]
    changes = payload.model_dump(exclude_unset=True)
    if "title" in changes and changes["title"] is None:
        raise HTTPException(status_code=422, detail="title 不能设为 null")
    for key, value in changes.items():
        setattr(task, key, value)
    task.updated_at = datetime.now(timezone.utc)
    return task
```

如果使用 ​`exclude_none=True`​，客户端就无法把 ​`description`​ 清空；如果直接遍历 ​`payload.__dict__`​，未传字段会被默认值覆盖。​`exclude_unset` 才是 PATCH 的语义。

## 默认 422 的结构

模型校验失败时，FastAPI 返回 422，响应体大致如下：

```json
{
  "detail": [
    {
      "type": "string_too_short",
      "loc": ["body", "title"],
      "msg": "String should have at least 1 character",
      "input": ""
    }
  ]
}
```

`loc`​ 表示出错位置，​`type`​ 是机器可读的错误类型，​`msg` 是面向人的说明。第 5 章会把这份结构统一成项目自己的错误契约。

## 从 Pydantic 1 迁移时的对应关系

|Pydantic 1|Pydantic 2|
| ------------| ------------|
|`class Config`|`model_config = ConfigDict(...)`|
|`.dict()`|`.model_dump()`|
|`.json()`|`.model_dump_json()`|
|`@validator`|`@field_validator`|
|`@root_validator`|`@model_validator`|
|`orm_mode = True`|`from_attributes=True`|
|`parse_obj()`|`model_validate()`|

新项目直接用 Pydantic 2 写法。第三方库如果仍依赖 Pydantic 1，升级前要确认兼容性，不要在同一进程里混用两套模型基类。

## 练习

1. 给 ​`TaskCreate`​ 增加 ​`priority`​，只允许 ​`low`​、​`normal`​、​`high`。
2. 给 ​`TaskUpdate`​ 增加 ​`due_at`，并拒绝过去的时间。
3. 创建响应模型 ​`TaskSummary`​，只包含 ​`id`​、​`title`​、​`done`。
4. 故意提交 ​`{"title": "ok", "is_admin": true}`​，确认 ​`extra="forbid"` 返回 422。
