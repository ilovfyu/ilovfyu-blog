配置散落在代码里，环境一换就会出错。​`pydantic-settings`​ 把环境变量、​`.env` 文件和类型校验集中到一个对象，并在应用启动时尽早失败。

## 配置对象

```python
from functools import lru_cache
from typing import Annotated

from pydantic import SecretStr, field_validator, model_validator
from pydantic_settings import BaseSettings, NoDecode, SettingsConfigDict


class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",
        env_prefix="APP_",
        extra="ignore",
        case_sensitive=False,
    )

    name: str = "Task API"
    environment: str = "dev"
    database_url: str = "sqlite:///./tasks.db"
    secret_key: SecretStr = SecretStr("dev-only-change-me-please-32bytes")
    access_token_expire_minutes: int = 60
    cors_origins: Annotated[list[str], NoDecode] = ["http://localhost:5173"]

    @field_validator("cors_origins", mode="before")
    @classmethod
    def split_origins(cls, value: object) -> object:
        if isinstance(value, str):
            return [item.strip() for item in value.split(",") if item.strip()]
        return value

    @model_validator(mode="after")
    def production_requires_real_secret(self) -> "Settings":
        if self.environment == "prod" and self.secret_key.get_secret_value().startswith("dev-"):
            raise ValueError("生产环境必须通过 APP_SECRET_KEY 提供真实密钥")
        return self


@lru_cache
def get_settings() -> Settings:
    return Settings()
```

环境变量名会加上 ​`APP_` 前缀：

```bash
export APP_ENVIRONMENT=prod
export APP_DATABASE_URL='postgresql+psycopg://user:pass@db:5432/taskdb'
export APP_CORS_ORIGINS='https://app.example.com,https://admin.example.com'
export APP_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_urlsafe(32))')"
```

`SecretStr`​ 在日志和 ​`repr`​ 中显示为 ​`**********`​，需要真实值时显式调用 ​`get_secret_value()`。这能减少误打印，但不能替代“不要记录配置”的纪律。

## 为什么用 NoDecode

Pydantic Settings 默认把复杂类型的环境变量当 JSON 解析。​`APP_CORS_ORIGINS=a,b`​ 会先尝试 JSON 解码并失败，根本到不了 ​`field_validator`​。​`NoDecode` 让原始字符串直接传入校验器，再手动拆成列表。

如果你更喜欢 JSON 格式，可以写成：

```bash
export APP_CORS_ORIGINS='["https://app.example.com","https://admin.example.com"]'
```

两种方式都可以，但要在 ​`.env.example` 和部署文档里写清楚，避免运维猜格式。

## 配置的注入方式

- 应用工厂：​`create_app(settings)`，测试可以传入隔离配置。
- 请求依赖：​`request.app.state.settings`，避免全局缓存与环境不一致。
- 业务函数：通过参数接收需要的配置，不要在深层函数里调用 ​`get_settings()`。

不要在每个模块顶层执行 ​`settings = Settings()`。那会让 import 顺序影响配置来源，也会让测试无法替换。

## .env 与密钥管理

`.env`​ 只用于本地开发，必须加入 ​`.gitignore`​。提交一个 ​`.env.example`，只写变量名和示例值：

```dotenv
APP_ENVIRONMENT=dev
APP_DATABASE_URL=sqlite:///./tasks.db
APP_SECRET_KEY=change-me
APP_CORS_ORIGINS=http://localhost:5173
```

生产环境使用平台提供的密钥管理：容器 Secret、Kubernetes Secret、云厂商 Secrets Manager。不要把密钥写进 Docker 镜像、前端 bundle 或 CI 日志。

## 配置项清单

|变量|用途|生产建议|
| ------| ----------------| ------------------------------|
|`APP_ENVIRONMENT`|环境标识|`prod`​ / ​`staging`|
|`APP_DATABASE_URL`|数据库连接|使用密钥注入，不在仓库中|
|`APP_SECRET_KEY`|JWT 签名|至少 32 字节随机值，定期轮换|
|`APP_CORS_ORIGINS`|允许的前端来源|明确域名，不用 ​`*`|
|`APP_ACCESS_TOKEN_EXPIRE_MINUTES`|令牌有效期|15～60 分钟，配合刷新令牌|

## 启动时失败

配置错误应该在启动阶段暴露，而不是等第一个请求：

- 数据库 URL 无法解析。
- 生产环境仍使用默认密钥。
- CORS 配置为空或包含非法来源。
- 令牌有效期不是正数。

`model_validator`​ 和字段约束能在创建 ​`Settings` 时完成这些检查。部署平台看到启动失败，会停止滚动发布，比运行到一半才发现更安全。

## 练习

1. 增加 ​`APP_LOG_LEVEL`​，只允许 ​`DEBUG`​、​`INFO`​、​`WARNING`​、​`ERROR`。
2. 增加 ​`APP_DOCS_ENABLED`​，生产环境关闭 ​`/docs`。
3. 用 ​`Settings(_env_file=None)`​ 在测试里完全禁用 ​`.env`。
4. 解释 ​`SecretStr` 能防住什么、不能防住什么。
