# 从 Demo 到生产：构建可靠 RAG 系统的六个层次

RAG 的 Demo 往往只有三步：切分文档、向量检索、把结果交给模型。上线后，真正的问题通常不是模型“不会回答”，而是文档过期、权限串库、召回了相似但不相关的段落，或者答案无法解释。可靠 RAG 应被看成一条可观测的数据链路，而不是一个向量数据库加提示词的函数。

## 六个层次

### 1. 数据源与知识生命周期

先定义哪些系统是事实来源，并为每份文档保存来源、版本、更新时间、租户和访问控制信息。增量同步必须支持新增、更新和删除；只追加不删除会让系统持续引用已失效内容。同步任务应可重试、可幂等，并记录失败项。

### 2. 解析与切分

切分的目标不是让块大小相等，而是让每个块表达一个完整事实。优先利用标题、段落、列表和表格边界，保留父标题作为元数据。重叠只能缓解边界损失，不能替代结构化解析。对代码、配置和数字表格要使用不同的解析规则，并保留原文定位信息。

### 3. 索引与检索

向量检索擅长语义相似，关键词检索擅长精确匹配，生产系统通常需要混合召回，再用元数据过滤租户、权限和文档版本。查询改写、过滤条件和候选数量都应记录。重排可以提升候选顺序，但不能补救索引中根本没有召回的证据。

### 4. 上下文组装与生成

把候选按来源去重、按相关性排序，并在进入模型前限制总 token 数。提示词要明确：答案只能依据给定证据；证据不足时说明不知道；引用应指向文档和段落，而不是生成一个看似真实的链接。组装逻辑应与模型调用分离，便于单独测试。

### 5. 评测与可观测性

不要只看最终答案。分别评测检索的相关性、证据覆盖、引用准确性、拒答正确性和端到端答案质量。每次请求至少关联一个 trace，记录查询、过滤条件、候选文档 ID、提示词版本、模型版本、延迟、token 用量和错误。这样才能区分“没有找到”和“找到但模型用错了”。

### 6. 安全与运行治理

权限过滤必须在检索层执行，生成前再做一次防御性校验；不能把用户可见的文档 ID 当作授权依据。文档内容也可能包含提示词注入，模型应把它当作不可信数据。为索引、切分规则、提示词和模型建立版本，支持灰度、回滚、超时、限流和人工升级。

一个最小的请求编排可以把关键边界显式写出来：

```ts
type Request = { tenantId: string; userId: string; question: string };

async function answer(request: Request) {
  const query = await rewriteQuery(request.question);
  const hits = await search(query, {
    mode: "hybrid",
    topK: 20,
    filter: { tenantId: request.tenantId, userId: request.userId },
  });
  const context = assembleContext(hits, { maxTokens: 6000 });

  if (context.length === 0) return "没有找到足够的依据。";
  return generate({
    question: request.question,
    context,
    instruction: "仅依据证据回答，并为每个关键结论附上来源。",
  });
}
```

## 上线前清单

- 能否定位每个答案使用的文档版本和段落？
- 文档更新、删除、权限变化是否会进入索引？
- 是否有无答案、越权、旧版本和跨租户的测试样本？
- 检索失败、模型超时和额度耗尽时，用户是否得到可理解的降级结果？
- 提示词、索引和模型变更能否比较、灰度并回滚？

## 总结

生产 RAG 的核心是证据链治理：从可追溯的数据开始，经由结构化切分、受控检索和有边界的生成，最后用评测与观测闭环。模型只是其中一层。把六层分别定义责任、接口和失败处理，系统才会从“偶尔答对”变成“出错可查、行为可控”。
