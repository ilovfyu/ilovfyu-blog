# 不靠感觉调 Prompt：建立可重复的评测集

Prompt 调优最容易陷入一个循环：挑几条问题手动试，看到答案变好就上线，随后真实输入暴露新的退化。人的直觉适合发现问题，不适合证明改动没有伤害其他场景。可重复评测的目标不是给模型一个绝对分数，而是让每次 Prompt、模型或检索变更都能在同一组问题上比较。

## 评测集先定义“好”

一条样本至少包含稳定的输入、任务类型、参考答案或事实、评价标准和可选的禁止行为。例如客服摘要不能只要求“写得好”，还应规定不得添加原文没有的承诺、必须保留日期和金额。标准要拆成可观察的断言，避免把风格偏好伪装成事实正确性。

样本来源应覆盖真实分布和边界分布：常见请求、歧义表达、空输入、超长输入、越权问题、无资料问题和历史上出现过的故障。按任务类型、语言、长度和风险等级分层，测试集固定不参与调 Prompt；新增线上错误进入回归集，并记录来源与脱敏规则。

## 选择合适的评估器

能用程序判断的优先用程序：JSON Schema、枚举值、必填字段、引用是否存在，以及数值计算都不应交给模型裁判。事实型任务可用参考答案或断言比对；开放式回答再使用模型评审，但必须提供明确 rubric、评分范围和“证据不足时拒答”的规则。高风险样本应保留人工复核，并定期抽查模型评审与人工判断的一致性。

评测结果不要只报平均分。按切片查看通过率、错误类型、拒答是否恰当、延迟和成本；对两个版本使用完全相同的输入、模型参数、工具返回和检索快照。模型服务具有随机性时，应记录随机种子（若接口支持），并保存原始输出，避免只留下一个不可追溯的汇总数字。

## 一个最小评测框架

把 Prompt 版本和运行依赖作为输入，把每条样本的输出与判定作为产物。评估器返回结构化原因，失败时先定位是指令冲突、上下文缺失还是输出解析失败。

```ts
type Case = {
  id: string;
  input: string;
  rubric: string[];
  expected?: string;
};

async function evaluate(cases: Case[], promptVersion: string) {
  const results = [];
  for (const item of cases) {
    const output = await callModel({
      promptVersion,
      input: item.input,
      temperature: 0,
    });
    const checks = await Promise.all(
      item.rubric.map((rule) => checkRule({ rule, input: item.input, output }))
    );
    results.push({ id: item.id, output, checks });
  }
  return results;
}
```

在持续集成中，可以把评测分为快速门禁和完整回归。门禁关注关键安全规则、结构化输出和已修复案例；完整回归用于分析所有切片。阈值必须与业务风险对应，并允许人工批准有意的行为变化，而不是为了过门禁而修改样本。

## 实践清单

- 是否有固定测试集、回归集和明确的样本版本？
- 每个质量标准能否转成断言、规则或可复核的 rubric？
- 是否冻结模型、工具、检索资料和参数，保存完整原始输出？
- 是否按场景切片分析，并区分事实错误、格式错误和安全错误？
- Prompt 变更是否必须附评测结果、失败样本和人工复核结论？

## 总结

评测集是 Prompt 工程的实验记录。先把“好答案”拆成可检查的标准，再固定输入和依赖，最后用分层结果指导修改。这样调 Prompt 不再依赖一次顺眼的对话，而成为可以重复、比较和回归的软件工程过程。
