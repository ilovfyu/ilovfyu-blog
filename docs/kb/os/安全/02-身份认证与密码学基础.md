::: abstract 本章定位
认证回答"**你凭什么说你是你**"，密码学回答"**数据怎么在传输和存储中不被偷看、篡改、冒充**"。本篇覆盖 Ch17 Security 中的认证与加密部分：认证三要素、盐+哈希存密码、对称/非对称加密、哈希与 MAC、数字签名与证书，以及 openssl / LUKS / TLS 的实际应用。
:::

安全的第一道防线是"确认你是谁"（Authentication），第二道才是"你进来后能干什么"（Authorization，见 [保护机制与访问控制](/kb/os/安全/01-保护机制与访问控制/)）。而密码学是让认证与加密"在数学上可靠"的底层工具。本篇概念多但彼此串联紧密：**哈希解决完整性，对称加密解决效率，非对称加密解决密钥分发，签名解决身份**。

## 1. 认证三要素（Authentication Factors）

认证就是证明身份，可依据三类凭证，称为**三要素**：

| 要素 | 英文 | 含义 | 例子 | 弱点 |
|---|---|---|---|---|
| **你知道的** | Something you know | 知识 | 密码、PIN、安全问题 | 会被钓鱼、撞库、被偷看 |
| **你拥有的** | Something you have | 持有物 | 手机验证码、USB Key、门禁卡、TOTP 令牌 | 会被盗取/伪造，会丢失 |
| **你是什么** | Something you are | 生物特征 | 指纹、人脸、虹膜、声纹 | 不可撤销，泄露即永久失效 |

::: warning 生物特征与密码的根本区别
密码泄露可以改，**指纹泄露没法"换指纹"**。因此生物特征不应作为唯一的认证手段，也不该在不可信环境（明文）传输，通常只作为"第二个因子"。
:::

**多因素认证（MFA / 2FA）**：组合两个**不同类别**的要素。如"密码（你知道）+ 手机验证码（你有）"。MFA 的价值在于：攻击者必须同时攻破两个不同通道，钓鱼密码 + 窃取验证码同时成功的概率大幅下降。

::: tip 判断 MFA 是否合格
两个密码/两个验证码只是"双因子"但**不是多因素**——因为同一类别。必须跨类别（知识+持有 或 知识+生物）才算真正的 MFA。
:::

## 2. 密码存储：盐（Salt）+ 哈希（Hash）

### 2.1 为什么不能存明文

数据库一旦泄露，明文密码直接裸奔，撞库攻击（用其他站点泄露的密码试你）立刻生效。所以密码必须**单向变换后**存储。

### 2.2 只存哈希为什么也不够

直接 `store = sha256(password)` 有三个致命问题：

1. **彩虹表（Rainbow Table）**：预计算海量常见密码的哈希，反查即得明文。
2. **相同密码产生相同哈希**：Alice 和 Bob 都用 `123456`，哈希相同，一次破解俩。
3. **速度**：SHA-256 太快（每秒可算数十亿次），暴力破解成本低。

### 2.3 加盐（Salt）解决

**盐 = 每个用户独享的随机值**，存入时拼接：`hash(salt + password)`。

```
注册：salt = random()             # 每个用户不同
      store: {salt, hash(salt+password)}
登录：读取 salt，再算 hash(salt+password) 比对
```

- 每个用户哈希不同 → 彩虹表整表失效。
- 相同密码生成不同哈希 → 无法批量破解，一个密码一个算。
- 现代标准更进一步用**慢哈希**（故意算得慢）：`bcrypt`、`argon2`、`scrypt`，每次计算耗时数百毫秒，暴力破解成本指数上升。

### 2.4 Linux 的 shadow 文件

```bash
$ sudo cat /etc/shadow
alice:$6$rO3Y0cXs$aR4...hash...:18765:0:99999:7:::
        │     │      │
        │     │      └ 加盐哈希后的密码（$6$ = SHA-512 算法标识）
        │     └ 盐
        └ 用户名
```

`/etc/shadow` 只有 root 可读，而 `/etc/passwd` 所有用户可读（存账号信息但不存密码）——这就是"把密码隔离在高权限文件"的权限设计。

## 3. 加密基础（对称加密）

### 3.1 目标

加密把明文变成密文，**只有持有密钥的人能还原**。加密解决机密性（confidentiality），哈希解决完整性——两者不混。

### 3.2 对称加密：AES / DES

**同一个密钥既加密又解密**（key 必须保密，双方共享）。

| 算法 | 密钥长度 | 分组 | 状态 |
|---|---|---|---|
| DES | 56 bit | 64 bit | 已淘汰，56 位可被暴力破解 |
| 3DES | 112/168 bit | 64 bit | 过渡方案，速度慢 |
| **AES** | 128/192/256 bit | 128 bit | 现代标准，全球最广泛使用 |
| ChaCha20 | 256 bit | 流式 | 现代流密码，移动端/协议常用（TLS 1.3 备选） |

::: important 加密 ≠ 哈希
加密可逆（有密钥就能还原），哈希不可逆（单向）。加密存密码没意义（密钥一旦泄露全裸奔），哈希存数据没法校验篡改。
:::

### 3.3 流密码 vs 分组密码

| 类型 | 原理 | 特点 | 例子 |
|---|---|---|---|
| **分组密码（Block Cipher）** | 把明文切成固定大小的块（如 128 bit）逐块加密 | 需要填充（padding）；相同明文块→相同密文块，需配合工作模式 | AES、DES |
| **流密码（Stream Cipher）** | 用密钥生成密钥流，与明文逐位异或 | 可逐字节加密、无填充、速度快；密钥流重用会致命 | ChaCha20、RC4（已破） |

分组密码的工作模式（mode）值得一提：

- **ECB**：每块独立加密，相同明文块得到相同密文块——会泄露模式（比如企鹅图片变成马赛克），**别用**。
- **CBC**：每块先与前一块密文异或再加密，需 IV（初始化向量），块间有依赖。
- **GCM**：认证加密模式（AEAD），一次同时提供加密 + 完整性校验，现代首选（TLS 1.3 用 AES-GCM）。

### 3.4 密钥交换（Key Exchange）

对称加密最大的问题：**双方怎么安全地共享同一个密钥？** 直接传密钥会被窃听。两种方案：

1. **Diffie–Hellman（DH）密钥交换**：双方在不暴露密钥的情况下协商出共享密钥（依赖离散对数难题）。经典握手见下。
2. **非对称加密交换**：用对方的公钥加密会话密钥传过去（TLS 的做法）。

```
Diffie–Hellman 流程（简化）：
  共同公开：素数 p、底数 g
  Alice 选私密 a，发 A = g^a mod p
  Bob   选私密 b，发 B = g^b mod p
  Alice 算 K = B^a mod p = g^(ab) mod p
  Bob   算 K = A^b mod p = g^(ab) mod p   ← 双方得到相同密钥 K
  窃听者只知道 A、B、p、g，无法推出 a、b（离散对数难题）
```

::: warning DH 的经典漏洞
传统 DH 本身**不认证身份**——中间人可以和 Alice 交换一个密钥、和 Bob 交换另一个密钥，两边都以为在和对方说话。因此真实 TLS 里 DH 必须配合证书/签名认证端点身份（见 6 节）。
:::

## 4. 非对称加密（公钥密码学）

### 4.1 概念

**加密和解密用不同的密钥**：公钥（public，公开分发）+ 私钥（private，秘密保存）。两者数学关联但无法互相推出。

| 用途 | 用什么加密 | 用什么解密 | 解决的问题 |
|---|---|---|---|
| 机密性 | 接收者的公钥 | 接收者的私钥 | 只有接收者能读 |
| 数字签名 | 发送者的私钥 | 发送者的公钥 | 只有发送者能产生，防抵赖 |

### 4.2 主要算法

| 算法 | 数学基础 | 密钥长度（推荐） | 特点 |
|---|---|---|---|
| **RSA** | 大整数分解 | 2048/3072 bit | 最经典，加密/签名通用 |
| **ECC**（椭圆曲线） | 椭圆曲线离散对数 | 256 bit ≈ RSA 3072 强度 | 同安全强度下密钥更短、更快，移动端/现代 TLS 首选 |
| ECDSA | 椭圆曲线签名 | 同上 | 签名专用 |
| Ed25519 | Edwards 曲线 | 256 bit | 现代 SSH 密钥推荐 |

::: tip 密钥长度对比记忆
**同为 ~128 bit 安全强度：RSA 需 3072 bit，ECC 只需 256 bit**。这就是为什么现代系统（TLS、SSH、区块链）都转向 ECC——短、快、省电。
:::

### 4.3 一个公钥能派两个用场

```
机密性（别人发给我）：
  Bob ──用 Alice 的公钥加密──► 密文 ──用 Alice 的私钥解密──► Alice

签名（我发给别人）：
  Alice ──用 Alice 的私钥签名──► 签名 ──用 Alice 的公钥验证──► Bob
```

## 5. 哈希、消息认证码与数字签名

### 5.1 哈希（Hash）与 SHA 族

哈希函数把任意长数据映射为固定长度摘要，三个性质：**单向**（不可逆）、**抗碰撞**（很难找到不同输入同摘要）、**雪崩效应**（改一个比特，摘要面目全非）。

| 算法 | 输出长度 | 状态 |
|---|---|---|
| MD5 | 128 bit | 已破（碰撞成本极低），只能用来查重 |
| SHA-1 | 160 bit | 已破，2017 年 SHAttered 碰撞 |
| SHA-256 | 256 bit | 安全，当前标准 |
| SHA-3 | 可变 | Keccak 算法，新一代标准 |

哈希只解决"数据被改没改"（完整性），**不解决"数据是不是来自正确的人"**——任何人都能算同一份数据的哈希。

### 5.2 消息认证码 MAC（Message Authentication Code）

在哈希基础上加**共享密钥**：`MAC = f(key, message)`。接收者用同样的密钥重算比对。

- 保证**完整性 + 数据来源认证**（双方共享密钥，第三方没密钥算不出正确 MAC）。
- 例：HMAC（Hash-based MAC，如 `HMAC-SHA256`）。
- 注意：MAC 用共享对称密钥，所以只能证明"来自共享密钥的持有者"，**不能防抵赖**——双方都有密钥，无法向第三方证明是谁发的。

### 5.3 数字签名（Digital Signature）

签名 = **用发送者私钥"加密"（签名）哈希值**。接收者用发送者公钥验证。

- 提供完整性（哈希）**+ 认证（只有私钥持有者能签）** + **不可否认性（non-repudiation，第三方用公钥能验证，发送者无法抵赖）**。
- 是 MAC 的"非对称升级版"：MAC 用对称密钥（双方都有，可抵赖），签名用私钥（仅一方持有，不可抵赖）。

```
MAC：   双方共享对称密钥 K → HMAC(msg, K)         只能验完整性+共享方认证
签名：  发送者私钥 → sign(hash(msg)) → 公钥验证     完整性+认证+防抵赖
```

### 5.4 数字证书与 PKI

**数字证书** = 把"公钥 + 身份信息"用受信任的**证书颁发机构（CA）**的私钥签名。

```
TLS 中的证书链：
  CA 根证书（系统预装，信任锚）
    └── 签名 ──► 网站证书（含 www.example.com 的公钥 + 域名）
  浏览器验证：用 CA 公钥验证网站证书的签名 → 信任网站公钥 → 建立安全连接
```

- **X.509**：标准证书格式。
- 解决"如何安全获得对方公钥"的引导问题（Trust On First Use 的替代方案）。
- 自签名证书用于内部测试（浏览器会报警），生产环境必须由受信 CA 签发。

## 6. 加密在系统中的应用

### 6.1 传输加密：TLS 简化流程

TLS（HTTPS 的底层协议）是"非对称 + 对称"混合加密的教科书：

```
① 客户端 → 服务器：ClientHello（支持的算法）
② 服务器 → 客户端：ServerHello（选定算法）+ 证书（含公钥）
③ 客户端验证证书（CA 签名、域名、有效期）
④ 客户端 → 服务器：用服务器公钥加密"预主密钥（pre-master）"
⑤ 双方由预主密钥派生对称会话密钥（AES-GCM）
⑥ 之后所有数据用对称加密 + MAC 保护（快）
   非对称只用来做"一次性的安全密钥交换 + 认证端点"
```

::: important 为什么混合加密
非对称加密安全但慢（RSA 慢 AES 数百上千倍）。**用非对称做握手交换会话密钥（一次），用对称加密实际数据（持续）**——既安全又高效。
:::

### 6.2 磁盘与文件加密

| 层次 | 技术 | 说明 |
|---|---|---|
| 整盘加密 | **LUKS**（cryptsetup） | 加密整块分区/磁盘，开机输入口令解锁 |
| 文件系统加密 | fscrypt / eCryptfs | 按目录/文件加密（如 ext4 的 fscrypt） |
| 应用层加密 | GPG 加密文件 | 按文件手动加密，适合文档传递 |

LUKS 的工作方式：主密钥由磁盘存储、用用户口令派生密钥加密后存放，改口令只需重加密"口令-密钥包装"，不需重加密整盘数据。

### 6.3 openssl 命令示例

```bash
# 哈希与 HMAC
echo -n "hello" | sha256sum                        # 完整性地校验
echo -n "hello" | openssl dgst -sha256 -hmac "k"   # HMAC：带密钥的校验

# 对称加密（AES-256-CBC）
echo -n "secret" | openssl enc -aes-256-cbc -salt -pbkdf2 -pass pass:yourkey
openssl enc -aes-256-cbc -d -pbkdf2 -pass pass:yourkey   # 解密 -d

# 非对称：生成 RSA 密钥对
openssl genrsa -out key.pem 2048
openssl rsa -in key.pem -pubout -out pub.pem

# 用公钥加密文件、私钥解密（验证公钥体系）
openssl pkeyutl -encrypt -pubin -inkey pub.pem -in file -out enc.bin
openssl pkeyutl -decrypt -inkey key.pem -in enc.bin -out file

# 生成自签名证书（用于本地测试）
openssl req -x509 -newkey rsa:2048 -keyout server.key -out server.crt -days 365 -nodes
```

```bash
# LUKS 磁盘加密（root 权限）
sudo cryptsetup luksFormat /dev/sdX            # 会清空该分区！
sudo cryptsetup open /dev/sdX myluks           # 映射为 /dev/mapper/myluks
sudo mkfs.ext4 /dev/mapper/myluks
sudo mount /dev/mapper/myluks /mnt/encrypted
sudo cryptsetup luksClose myluks               # 卸载并关闭
```

::: warning 加盐别手软、密码别复用
加盐与 `-pbkdf2`（把口令拉伸成密钥）缺一不可，否则弱口令照样被暴力破解；所有加密的口令最终强度都取决于人类记忆的密码——"密码管理器 + 强随机口令"是现代加密安全的真正底座。
:::

## 本章小结

1. **认证三要素**：你知道的 / 你拥有的 / 你是什么；跨类别组合才是真 MFA。
2. **密码存储**：盐 + 慢哈希（bcrypt/argon2），杜绝彩虹表与批量破解；shadow 文件高权限隔离。
3. **对称加密（AES）** 快但需共享密钥，靠 DH/非对称交换密钥；流密码 vs 分组密码、CBC vs GCM 各就各位。
4. **非对称加密（RSA/ECC）**：公钥加密=机密性，私钥签名=身份+防抵赖；ECC 同强度更短更快。
5. **哈希→完整性，MAC→完整性+共享方认证，签名→完整性+认证+防抵赖**，证书链解决"信谁的公钥"。
6. **落地**：TLS 混合加密、LUKS 整盘加密、openssl 一套命令走遍全部流程。

## 自测题

1. **认证三要素是什么？为什么"密码+短信验证码"算多因素？**
   > 你知道的+你拥有的+你是什么。密码属知识、短信验证码属持有物，跨了两个类别，故为真正的 2FA。

2. **为什么密码存储要加盐？不加盐的两个具体风险是什么？**
   > 盐使每个用户哈希唯一，彩虹表失效、相同密码不再同哈希。不加盐会遭彩虹表反查和批量碰撞。

3. **对称加密 vs 非对称加密各自的痛点是什么？**
   > 对称快但密钥分发难（要共享密钥）；非对称无密钥分发问题但慢。实际用非对称握手换会话密钥、对称加密数据（TLS 模式）。

4. **哈希、MAC、数字签名三者分别保证什么？**
   > 哈希=完整性；MAC=完整性+共享密钥方认证（对称，可抵赖）；签名=完整性+认证+不可否认（私钥，不可抵赖）。

5. **分组加密 ECB 模式为什么危险？**
   > 相同明文块产生相同密文块，暴露明文模式；应改用 CBC（加 IV）或 GCM（认证加密）。

6. **DH 密钥交换缺少什么安全属性？容易被什么攻击利用？**
   > 缺少端点认证，可被中间人同时与双方交换不同密钥而冒充；因此要配合证书/签名。

7. **为什么说"生物特征不可作为唯一认证手段"？**
   > 生物特征不可撤销，一旦泄露无法更换，且易被收集复制（照片指纹等），应作第二因子配合密码。

8. **TLS 握手里非对称加密只做了一次，为什么这就足够？**
   > 因为目的只是安全交换会话密钥 + 认证服务器；之后的批量数据传输由派生的对称密钥完成，兼顾安全与性能。
