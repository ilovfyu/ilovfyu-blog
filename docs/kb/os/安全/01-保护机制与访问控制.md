::: abstract 本章定位
保护（Protection）回答操作系统最基础的安全问题：**系统里这么多主体（用户/进程），如何防止他们越权访问客体（文件/内存/设备）？** 核心思想是访问矩阵（Access Matrix），它抽象了从 Linux 权限位到数据库 GRANT 再到 Kubernetes RBAC 的一切授权模型。本篇对应教材 Ch16 Protection。
:::

很多人把"保护"和"安全"混为一谈。记住一句区分的话：**保护关心"合法的用户之间谁不能碰谁的东西"，安全关心"恶意的攻击者怎么进来"。** 保护是操作系统对内部资源的"交通规则"，安全是对外部入侵的"边防战争"。本篇讲交通规则，下一篇讲边防。

## 1. 保护目标

操作系统要保护资源不被"非授权的访问"使用，核心三元组是信息安全的三支柱：

| 目标 | 英文 | 含义 | 违反后果举例 |
|---|---|---|---|
| 完整性 | Integrity | 数据不能被非授权修改 | 篡改 /etc/passwd 添加一个 root 账号 |
| 可用性 | Availability | 数据/服务在需要时可用 | DoS 攻击让 Web 服务瘫痪 |
| 机密性 | Confidentiality | 数据只能被授权者读取 | 窃取数据库中的用户密码 |

::: tip 三支柱的关系
三者的权重因场景而异：银行系统最看重完整性，医疗记录最看重机密性，电商网站最看重可用性。安全设计的第一步就是想清楚"这个系统最怕丢什么"。
:::

保护机制要满足的更高层原则：
- **最少特权（Least Privilege）**：每个主体只拥有完成任务所需的最小权限集。
- **多样性（Diversity）**：防御机制不应千篇一律，否则一种攻击手段通杀（纵深防御的一部分）。
- **经济（Economy of Mechanism）**：机制应小而简单、易于验证——越复杂的权限系统越容易出 bug。
- **失败安全（Fail-Safe Defaults）**：默认拒绝访问，显式授予才算授权。

## 2. 保护域（Protection Domain）

**域（Domain）是"权限的集合"**：一个域定义了一组 `<object, operation>` 对，表示"在该域内的进程可以对这些客体做这些操作"。

关键理解：

- **进程与域的关系**：进程在某个域中运行，可以**静态**绑定（进程始终在一个域），也可以**动态**切换（通过 `enter` 操作切换域）。
- **域切换的意义**：系统调用就是域切换的典型实例——用户态进程通过系统调用进入内核域，获得访问内核数据结构与硬件的权限，完成后返回用户域。这天然实现了"内核是高权限域，用户是低权限域"的隔离。
- **进程即域**：Unix 的双状态模型（用户态/内核态）就是一种两域模型。每个用户也是一个"域"，同一用户的所有进程共享该用户的权限。
- **域的最小化**：成熟系统会把权限拆成很多小域。例如 Web 服务器有一个主进程 + 多个 worker 进程，worker 只拥有处理请求所需的最小权限，即使被攻破也不能破坏整个系统。

```
      用户域 A                    用户域 B                 内核域（最高特权）
 ┌─────────────────┐      ┌─────────────────┐      ┌─────────────────────────┐
 │ 读 /home/alice   │      │ 读 /home/bob    │      │ 访问硬件 / 内核内存      │
 │ 读 /tmp/app.cfg │      │ 写 /var/log/app │      │ 创建进程 / 网络收发       │
 └─────────────────┘      └─────────────────┘      └─────────────────────────┘
        ▲  进程 P1 在域 A           ▲  进程 P2 在域 B         ▲  syscall 切换进入
```

::: important 域的本质
域 = 权限集合 + 可切换。现代容器（namespace + cgroup）、沙箱、虚拟机全部是"域"思想的不同实现。理解域，你就理解了容器安全的第一步——把每个服务的权限域切小。
:::

## 3. 访问矩阵（Access Matrix）

**访问矩阵**是保护模型的统一框架：行是**主体（Subject）**——用户或进程；列是**客体（Object）**——文件、设备、进程、内存段；单元格填**权限（Rights）**，如 read / write / execute / search。

```
                     客体 ──────────────►
  主体 |    File1   |   File2   |    Printer  |   Process P1
 ──────┼───────────┼───────────┼────────────┼──────────────
 alice |   r w      |   r        |    print   |   r
 bob   |   r        |   r w x    |    --      |   send
 root  |   r w x    |   r w x    |    print   |   r w
```

访问矩阵的三个关键扩展概念：

1. **copy（复制权）**：`copy` 允许主体把某个权限复制给其他主体——权位可以"蔓延"。
2. **owner（属主权）**：拥有 owner 权的主体可以授予/撤销矩阵中该列的权限。
3. **控制权（Control）**：某个域可以切换另一个域（`switch`），或删除另一个域中的权限。这是动态域切换的机制来源。

::: warning copy 与 owner 的隐患
copy 会让权限失控扩散（Alice 复制给 Bob，Bob 复制给 Charlie…）。现代系统默认不提供 copy 权，权限只由 owner 或管理员授予，杜绝"权限传染病"。
:::

## 4. 访问矩阵的实现：ACL vs Capability

矩阵是理论，实现时需要压缩存储——因为绝大多数单元格是空的。两种经典压缩方式：

### 4.1 ACL（Access Control List，基于列）

**每个客体挂一张"权限表"**，列出哪些主体可以对该客体做什么。检查顺序：**客体被访问时，在它的 ACL 里查当前主体**。

Linux 的 `ls -l` 就是最朴素的 ACL（只能列 owner/group/other 三类）；`setfacl` 可以给任意指定用户/组单独授权。

```
File: /etc/passwd
Owner: root
ACL:  alice:rw, bob:r, root:rwx, other:---
```

### 4.2 Capability List（能力列表，基于行）

**每个主体持有一串"门票"**，每张票写明了"凭此票可对某客体做某事"。检查顺序：**主体访问客体时，出示自己的 capability，检查票上是否含该操作**。

Capability 的经典形象是"凭证 / 门禁卡"：持有者出示即可进入，无需查任何中央列表。

```
进程 P1 的 Capability List:
  (File1, read)
  (File2, read)
  (Printer, print)
  (kernel, syscall_enter)
```

### 4.3 撤销权限的差异（面试重点）

| 维度 | ACL（客体中心） | Capability（主体中心） |
|---|---|---|
| 信息存储位置 | 存在客体上 | 存在主体手里 |
| 权限检查时机 | 每次访问时查客体上的列表 | 访问时出示票证 |
| **撤销一个主体的权限** | **改客体上的 ACL 即可，立即全局生效** | **必须回收该主体持有的所有票**，困难 |
| **撤销所有主体对某客体的权限** | 删掉该客体的 ACL 条目即可 | 必须逐个通知所有持票者 |
| 典型例子 | Linux setfacl、Windows NTFS 权限 | L4 微内核、Seccomp 白名单、Kerberos ticket |
| 是否便于授权 | 授权在客体侧统一管理 | 授权在主体侧发放 |
| 撤销的实现技巧 | 无 | 引入"间接层"（如对象的 capability 都指向同一个 version 号，改版本即撤销） |

::: important 记住一句话
**ACL 管"这个文件谁能碰"（客体视角），Capability 管"这个进程能碰什么"（主体视角）**。撤销权限 ACL 容易、Capability 难，这是两者最本质的差异，面试 90% 会问。
:::

### 4.4 现代系统里两者都在用

- **ACL 代表**：Linux 传统权限位 + `setfacl` 扩展、Windows 文件权限。
- **Capability 代表**：Linux **capabilities**（给单个可执行文件授予如 `CAP_NET_RAW`，而不是整个 setuid root）、Docker 的 `--cap-drop`、Seccomp 的系统调用白名单、Kerberos 票据、OAuth2 access token。

## 5. Linux 权限模型

### 5.1 传统 rwx 权限位

每个文件/目录有三组权限，对应三类主体：

```
   [文件类型]  [owner]  [group]  [other]
       d      rwx      r-x      r-x
       目录   主    组     其他
```

| 字符 | 含义 |
|---|---|
| 首字符 | `-` 普通文件，`d` 目录，`l` 符号链接，`b` 块设备，`c` 字符设备 |
| r | 读。对文件=读内容；对目录=可列出目录条目（`ls`） |
| w | 写。对文件=改内容；对目录=可增/删/改名目录内的条目 |
| x | 执行。对文件=可运行；对目录=可进入（`cd`）——目录的 x 决定"能否穿越" |

### 5.2 特殊权限位

| 权限 | 符号（ls -l） | 含义 | 例子 |
|---|---|---|---|
| **setuid** | `s` 在 owner 位（`-rwsr-xr-x`） | 执行时以**文件属主**的身份运行 | `/usr/bin/passwd` 以 root 运行才能写 /etc/shadow |
| **setgid** | `s` 在 group 位（`-rwxr-sr-x`） | 执行时以**文件属组**身份运行；对目录=新文件继承属组 | `/usr/bin/wall`、团队共享目录 |
| **sticky bit** | `t` 在 other 位（`drwxrwxrwt`） | 目录里**只有文件主或 root 能删除**自己的文件 | `/tmp` |

::: warning setuid 是双刃剑
setuid 让普通用户能以 root 身份运行程序，等于"特权提升通道"。历史上大量漏洞（如 sudo、passwd）都因 setuid 程序写得不安全被利用。**现代最佳实践：用 Linux capabilities 替代 setuid**，只授所需的最小能力，而不是整个 root。
:::

```
$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 59976   # 注意 owner 位是 's'：setuid
$ ls -ld /tmp
drwxrwxrwt   # 注意末尾 't'：sticky bit，谁也删不了别人的临时文件
```

### 5.3 权限检查顺序

Linux 权限检查的精确语义（很多人搞错）：**按顺序匹配 owner → group → other，命中即止，不再累加**。

- 进程是文件 owner → 只看 owner 权限位。
- 不是 owner 但属于文件 group → 只看 group 权限位。
- 都不是 → 看 other。

所以如果 owner 是 `r--`、group 是 `rw-`，一个属于 group 的用户**不能**因为"owner 能读"而获得读写——它按 group 匹配，只有 `rw-`。**权限位之间是"或"的关系存在于同一类别内，三类之间是"短路"的关系。**

## 6. MAC 与 DAC 简述

### 6.1 DAC（Discretionary Access Control，自主访问控制）

**客体属主可以自行决定谁能访问自己的客体**。"自主"体现在：Alice 的文件的访问权由 Alice 自己说了算，她可以授权给别人。Linux 传统 rwx、Windows ACL 都是 DAC。

- 优点：灵活、简单。
- 缺点：**容易被提权扩散**——Alice 授权给 Bob，Bob 再授权给 Mallory；且恶意程序可以用"Alice 的名义"授权自己。

### 6.2 MAC（Mandatory Access Control，强制访问控制）

**系统策略凌驾于属主意志之上**。即使你是文件属主，也不能违反系统既定策略。典型实现：

- **SELinux**（内核内嵌，基于标签 + 策略）：每个进程和文件都有安全上下文标签，只有策略允许的主体-客体组合才能交互。
- **AppArmor**（按程序路径限制）：给每个程序写一个配置文件，规定它能访问哪些文件、网络等。
- **BLP 模型**（Bell–LaPadula）：著名的多级安全模型，规则是"**不上读、不下写**"——低密级不能读高密级，高密级不能写低密级，专为军事机密设计。

| 维度 | DAC | MAC |
|---|---|---|
| 谁能授权 | 客体属主 | 系统/管理员策略 |
| 属主能否违背策略 | 能 | 不能 |
| 典型场景 | 日常文件共享 | 军事、金融、容器加固（SELinux/AppArmor） |
| 防护目标 | 防止越权访问 | 防止提权扩散、约束被攻破的程序 |

::: tip 理解 MAC 的一个比喻
DAC 像"你的抽屉你自己管，想给谁钥匙就给谁"；MAC 像"办公室规定机密文件只能放保险柜，就算你是文件主人也不能把它带出大楼"。Docker 里 `--security-opt seccomp`、K8s 的 Pod Security 都是把 MAC 思想落到容器。
:::

## 7. Protection 与 Security 的区别

| 维度 | Protection（保护） | Security（安全） |
|---|---|---|
| 对象 | 内部合法主体之间的访问控制 | 外部/恶意主体的入侵对抗 |
| 问题 | "Alice 能读 Bob 的文件吗" | "黑客能不能拿到 root" |
| 手段 | 访问矩阵、ACL、域 | 认证、加密、防火墙、入侵检测、审计 |
| 性质 | 规则设计（静态） | 攻防博弈（动态） |
| 教材章节 | Ch16 | Ch17 |

两者互补：**Security 的第一步是"确认你是谁"（认证），Protection 的职责是"确认了你是谁之后你能干什么"（授权）**。认证失效，保护机制就会被冒充者绕过。

## 本章小结

保护机制的核心是把"谁能对什么做什么"这个二维关系显式化：

1. **域** = 权限的集合，进程在域中运行，通过域切换实现权限隔离。
2. **访问矩阵** = 主体 × 客体 → 权限的统一模型，理论上的完美形态。
3. **ACL（列实现）** 与 **Capability（行实现）** 是矩阵的两种压缩存储，撤销权限 ACL 易、Capability 难。
4. **Linux** 用 rwx + owner/group/other + setuid/setgid/sticky bit 实现了 DAC；SELinux/AppArmor 实现 MAC。
5. **保护（合法用户间隔离）≠ 安全（对抗恶意主体）**，但授权模型是两者共享的地基。

## 自测题

1. **保护的三个目标（CIA）各是什么？举一个违背的例子。**
   > 完整性=防篡改、可用性=可用、机密性=防窃读。例如：攻击者修改 /etc/passwd 添加 root 账号违背完整性。

2. **什么是保护域？系统调用和域切换有什么关系？**
   > 域是一组 `(客体, 权限)` 对构成的权限集合。进程通过系统调用从用户域切到内核域获得硬件访问权限，syscall 就是一次受控的域切换。

3. **画一个访问矩阵并说明 copy、owner 权的含义。**
   > 行主体列客体填权限。copy 允许复制权限给他人；owner 允许授予/撤销某列的权限。

4. **ACL 与 Capability 撤销权限的差异是什么？**
   > ACL 存在客体上，改一处全局生效；Capability 存在各主体手中，需要逐张回收票证，撤销困难，通常用版本号/间接层解决。

5. **Linux 权限检查顺序为什么是"命中即止"？**
   > 按 owner→group→other 依次匹配，先匹配到哪类就只看那类权限，三类之间不叠加，避免权限意外膨胀。

6. **setuid 和 sticky bit 各解决什么问题？**
   > setuid 让普通用户以属主身份运行程序（如 passwd 写 shadow）；sticky bit 让共享目录里只有文件主能删自己的文件（如 /tmp）。

7. **DAC 与 MAC 的本质区别是什么？**
   > DAC 由属主自主授权、可随意扩散；MAC 由系统策略强制，属主也不能违背，用于对抗提权扩散。

8. **为什么说"ACL 是客体中心、Capability 是主体中心"？**
   > ACL 挂在每个客体上列"谁能访问我"；Capability 握在主体手里写"我能访问谁"。
