::: abstract 本章定位
前几篇讲了授权、认证、威胁与恶意软件，本篇收拢成一套**可落地的防御体系**：安全策略与最小权限、纵深防御、Linux 内核安全机制（capabilities / SELinux / AppArmor / seccomp / namespaces）、审计（auditd）、完整性校验（AIDE）、系统加固清单与安全事件响应流程。对应教材 Ch17 Security 的防御部分。
:::

防御不是"装个杀毒软件"，而是一整套系统工程：**策略定规矩（最小权限）→ 架构设防线（纵深防御）→ 内核给机制（LSM/seccomp）→ 审计留证据（auditd）→ 校验防篡改（AIDE）→ 出事有流程（事件响应）**。本篇结束，你应该能照着一张清单去加固一台 Linux 服务器。

## 1. 安全策略设计与最小权限原则

### 1.1 安全策略（Security Policy）

安全策略 = 明确定义"允许谁、对什么、做什么"。它是所有技术手段的"宪法"。

- **身份策略**：密码强度、MFA 要求、账号生命周期。
- **访问策略**：谁能访问哪些资源（对接 [保护机制与访问控制](/kb/os/安全/01-保护机制与访问控制/) 的访问矩阵）。
- **审计策略**：什么操作必须留痕、日志保留多久。
- **应急策略**：发生入侵后怎么处置。

### 1.2 最小权限原则（Least Privilege）

**每个主体（用户/进程/服务）只获得完成任务所必需的最小权限**，并用"默认拒绝、按需授予"实现。

落地要点：

| 场景 | 最小权限做法 |
|---|---|
| 应用进程 | 不用 root 跑服务，用专用低权限用户 + capabilities |
| 数据库 | 应用账号只拥有 `SELECT/INSERT/UPDATE/DELETE`，不给 DDL/`FILE` |
| 文件 | 服务只读自己需要读的目录，写日志只写日志文件 |
| 网络 | 防火墙只开放业务必需端口 |
| 权限提升 | sudo 白名单命令级授权，不授 `sudo ALL` |

::: tip 最小权限 + 审计 = 可问责
最小权限缩小攻击面，审计把"谁干了什么"记下来。二者配合才能做到**出事能定位到人**。这也是 [恶意软件与网络攻击](/kb/os/安全/04-恶意软件与网络攻击/) 末尾原则的落地执行。
:::

## 2. 纵深防御（Defense in Depth）

**纵深防御**：不依赖单层防线，而是在物理、网络、主机、应用、数据多个层面叠加独立防御，即使某一层被突破，攻击者也过不了下一层。

```
                    ┌──────────────────────────────────┐
   攻击者 ──► 物理安全（机房/门禁）
              │
              ▼
        网络层：防火墙 + IDS/IPS + 分段隔离（DMZ）
              │
              ▼
        主机层：最小权限账号 + SELinux/AppArmor + 补丁 + HIDS
              │
              ▼
        应用层：输入校验 + 认证授权 + WAF + 代码审计
              │
              ▼
        数据层：加密存储（LUKS）+ 备份 + 完整性校验（AIDE）
              │
              ▼
        管理闭环：auditd 审计 + 日志中心 + 事件响应 + 恢复演练
                    └──────────────────────────────────┘
```

::: important 纵深防御的关键是"独立性"
若各层共用同一个漏洞或同一个管理员口令，纵深就退化成单层。**各层用不同的机制、不同的密钥、不同的供应商**，才能避免"一锅端"。
:::

## 3. Linux 内核安全机制

### 3.1 Linux Capabilities（能力机制）

传统 `setuid root` 把**所有** root 特权一次性给程序；**capabilities** 把 root 特权拆成几十个"能力位"，可按需授予。

| 能力 | 用途 | 对应特权 |
|---|---|---|
| `CAP_NET_RAW` | 允许使用原始套接字 | ping / 抓包需要 |
| `CAP_NET_BIND_SERVICE` | 绑定 1024 以下端口 | Web 服务器需要 |
| `CAP_DAC_OVERRIDE` | 绕过文件权限检查 | 接近 root 的全部文件权力 |
| `CAP_SYS_ADMIN` | 各类系统管理操作 | **高危**，容器逃逸常涉及 |
| `CAP_CHOWN` / `CAP_FOWNER` | 改属主 / 绕过属主检查 | 文件管理 |

```bash
# 查看 / 设置 / 删除能力位
getcap /usr/bin/ping            # 输出：cap_net_raw=ep（effective+permitted）
sudo setcap cap_net_raw=ep /tmp/myping
sudo setcap -r /tmp/myping      # 移除
```

::: warning 不要对程序滥用 setcap
给 Web 程序加 `CAP_DAC_OVERRIDE` 等于又给了半个 root。**只授业务必需的最小能力**，生产环境应通过 systemd `AmbientCapabilities=` 管理。
:::

### 3.2 SELinux 与 AppArmor（强制访问控制 MAC）

让 Linux 从"属主说了算"的 DAC 升级为"系统策略说了算"的 MAC（见 [保护机制与访问控制](/kb/os/安全/01-保护机制与访问控制/) 第 6 节）。

| 维度 | SELinux | AppArmor |
|---|---|---|
| 内核机制 | LSM，标签（label）+ 类型强制 | LSM，按程序路径绑定 profile |
| 标识对象 | 每个进程/文件都有安全上下文（如 `system_u:object_r:httpd_t`） | 以**路径**描述（如 `/usr/sbin/apache2`） |
| 配置复杂度 | 高（策略语言复杂） | 低（文本 profile，易上手） |
| 典型发行版 | RHEL / Fedora / CentOS | Ubuntu / Debian / SUSE |
| 失败模式 | 违反策略 = 拒绝（deny） | 违反 profile = 拒绝 |
| 适用 | 服务器、高安全要求环境 | 桌面、云主机、容器（Docker 常用 AppArmor） |

```bash
# SELinux 常用
getenforce                          # Enforcing / Permissive / Disabled
sudo semanage fcontext -l | head    # 查看默认文件标签
sudo setenforce 0                   # 临时改 Permissive（排障用，别长期开着）

# AppArmor 常用
sudo aa-status                      # 列出已加载 profile 与状态
sudo apparmor_parser -r /etc/apparmor.d/usr.sbin.nginx   # 重新加载
```

### 3.3 Seccomp（系统调用过滤）

**Seccomp** 拦截进程发起的**系统调用**，只放行白名单里的调用。即使程序被攻破，攻击者也调不了 `open`/`execve`/`socket` 等危险系统调用——攻击面被压缩到极小。

```bash
# Docker 默认给容器装 seccomp profile（只放行必要 syscall）
docker run --security-opt seccomp=default.json nginx
# 查看容器使用的 seccomp profile
docker inspect &lt;container&gt; --format '{{.HostConfig.SecurityOpt}}'
```

### 3.4 Namespaces（命名空间）

**Namespaces** 让每个容器"以为自己是系统里唯一的进程"，实现资源视角隔离：PID namespace（看不到宿主进程）、Network namespace（独立网卡/IP）、Mount namespace（独立挂载视图）、User namespace（容器内 root ≠ 宿主 root）等。

::: tip 容器安全的组合拳
**namespaces（视角隔离）+ cgroups（资源限制）+ capabilities（降权）+ seccomp（系统调用过滤）+ AppArmor/SELinux（MAC 约束）** = 一个完整的多层容器沙箱。这也是 [Linux 安全](/kb/os/Linux/06-Linux安全权限与审计/) 实操篇要展开的内容。
:::

## 4. 审计：auditd

### 4.1 审计的价值

审计（Audit）解决"**出了事，谁在什么时候对什么做了什么**"。内核的 auditd 子系统把所有安全相关的系统调用行为记录到日志，是取证与合规（等保、ISO 27001）的必需品。

### 4.2 配置示例

```bash
# 1. 安装并启动
sudo apt install auditd
sudo systemctl enable --now auditd

# 2. 监控文件（wa = 写 + 属性变更）
sudo auditctl -w /etc/passwd -p wa -k passwd_watch
sudo auditctl -w /etc/shadow -p wa -k shadow_watch

# 3. 监控系统调用（如 execve，记录谁执行了什么程序）
sudo auditctl -a always,exit -F arch=b64 -S execve -k exec_trace

# 4. 查看规则
sudo auditctl -l

# 5. 检索审计记录
sudo ausearch -k passwd_watch          # 按 key 查
sudo ausearch -ts today -k exec_trace  # 今天所有命令执行记录
sudo tail -f /var/log/audit/audit.log
```

持久化：把 `auditctl -w` 规则写进 `/etc/audit/rules.d/audit.rules`，否则重启丢失。

### 4.3 一条审计记录长什么样

```
type=SYSCALL msg=audit(1680000000.123:456):
  arch=c000003e syscall=59(execve) success=yes exit=0
  a0=0x7ffd... a1=... a2=... a3=...
  ppid=1234 pid=5678 auid=1000 uid=0 gid=0
  comm="bash" exe="/usr/bin/bash"
  key="exec_trace"
```

解读关键字段：`auid`=登录身份（即使程序 setuid 成 root，仍能追溯到是哪个用户干的）、`syscall=execve`=动作、`comm/exe`=执行的程序、`key`=你打的标签。

::: important auid 为什么重要
恶意程序可能 setuid 成 root，但 **auid（audit user id）在登录时固定，无法被提权伪造**——审计因此能穿透提权，追到"最终用户"。这是审计与普通日志的本质差别。
:::

## 5. 完整性校验：AIDE / Tripwire

恶意软件（尤其 Rootkit）会**改文件而不留痕迹**，因此需要**完整性校验**：预先建立文件哈希基线，定期重算比对，发现被改就报警。

| 工具 | 原理 |
|---|---|
| **Tripwire** | 经典主机完整性工具，首次建基线数据库 |
| **AIDE**（Advanced Intrusion Detection Environment） | Tripwire 的现代轻量替代，配置简单 |

```bash
# AIDE 初始化与检查
sudo apt install aide
sudo aideinit                      # 生成基线数据库 /var/lib/aide/aide.db
sudo mv /var/lib/aide/aide.db.new /var/lib/aide/aide.db
sudo aide.wrapper --check          # 检查：报告新增/删除/修改的文件
# 策略配置 /etc/aide/aide.conf 可指定监控哪些目录、忽略哪些（如 /var/log 会持续变化）
```

::: tip 基线也要保护
AIDE 的基线数据库若被攻击者改写就失效了。**把基线放到只读介质/离线存储**，并配合 `auditd` 监视数据库文件本身——这正是纵深防御的体现。
:::

## 6. 系统加固清单（Checklist）

一份 Linux 服务器最小加固 SOP：

| 类别 | 动作 | 命令/说明 |
|---|---|---|
| **账号与认证** | 禁用 root 远程登录、强制密钥认证 | `PermitRootLogin no`、`PasswordAuthentication no`（sshd_config） |
| **最小权限** | 服务用专用低权限用户、sudo 白名单 | `useradd -r -s /sbin/nologin app`；visudo 命令级授权 |
| **关闭端口** | 只开业务端口，其余默认拒绝 | `ss -tlnp` 审计 + 防火墙默认 DROP |
| **补丁更新** | 及时更新内核与应用 | `sudo apt upgrade`；关注 CVE 公告 |
| **SSH 加固** | 禁用空密码、限制允许用户、限登录次数 | `AllowUsers alice`、`MaxAuthTries 3` |
| **内核安全** | SELinux/AppArmor 开启 enforcing、模块签名 | `getenforce`、`module.sig_enforce` |
| **服务最小化** | 卸载/禁用无用服务 | `systemctl list-units --type=service` 排查 |
| **文件系统** | 关键目录只读挂载（`/usr` `-o ro`）、`/tmp` noexec | fstab 加 `noexec,nosuid,nodev` |
| **审计与监控** | auditd 规则、AIDE 基线、日志外送 | 见第 4、5 节 |
| **备份** | 定期离线备份 + 恢复演练 | 防勒索软件的最终保险 |

```bash
# sshd 关键加固（/etc/ssh/sshd_config）
PermitRootLogin no
PasswordAuthentication no
PubkeyAuthentication yes
MaxAuthTries 3
AllowUsers alice bob
```

::: warning 加固顺序
加固前先备份与规划变更窗口；每改一项都验证服务仍正常（改完 sshd 先 `sshd -t` 语法检查再重启），避免把自己锁在门外。**安全与可用性需要平衡。**
:::

## 7. 安全事件响应流程（Incident Response）

即使防住了大部分攻击，也要假定"**一定会发生**"——事件响应流程决定损失上限。通用六阶段（NIST SP 800-61）：

| 阶段 | 动作 | 产出 |
|---|---|---|
| 1. 准备（Preparation） | 应急预案、工具、联系表、备份 | 响应手册 |
| 2. 检测与分析（Detection & Analysis） | 从 auditd/IDS/日志发现异常，确定影响范围 | 事件定级 |
| 3. 遏制（Containment） | 断网、隔离主机、冻结证据、改口令 | 阻止扩散 |
| 4. 根除（Eradication） | 查杀恶意代码、修复漏洞、重装受影响系统 | 干净环境 |
| 5. 恢复（Recovery） | 从备份恢复服务、验证业务正常 | 服务恢复 |
| 6. 复盘（Lessons Learned） | 分析根因、补策略、更新流程与培训 | 改进报告 |

::: tip 取证第一原则：先取证后处置
遏制前**先保留原始证据**（内存镜像、磁盘镜像、日志副本），用只读方式复制，避免破坏证据链。审计日志此时就是最关键的证据来源。
:::

## 本章小结

1. **策略先行**：最小权限 + 默认拒绝 + 白名单，是所有技术手段的指导思想。
2. **纵深防御**：物理/网络/主机/应用/数据/管理六层独立防线，单点突破不致命。
3. **内核机制**：capabilities 拆分 root 特权、SELinux/AppArmor 实现 MAC、seccomp 过滤系统调用、namespaces 隔离视图——四者叠加构成容器安全的地基。
4. **审计闭环**：auditd 记录"谁何时对什么做了什么"，`auid` 穿透提权；AIDE 用哈希基线发现篡改。
5. **加固清单 + 事件响应**：从"怎么防"落到"怎么加固"与"出事怎么办"，安全运营形成闭环。

## 自测题

1. **最小权限原则在"服务运行"上的具体做法？**
   > 服务不用 root 运行，用专用低权限用户 + 最小 capabilities（如只给 `CAP_NET_BIND_SERVICE`），文件权限只授予所需目录。

2. **纵深防御为什么要求各层"独立"？**
   > 若各层共用同一个口令或同一漏洞，突破一层等于突破全部；独立机制、独立密钥、独立供应商才能保证单点失效不连带。

3. **SELinux 与 AppArmor 最本质的差异是什么？**
   > SELinux 基于标签的强制访问控制（全系统策略，复杂强大）；AppArmor 基于程序路径的 profile（简单易用）；二者都是 MAC。

4. **seccomp 限制什么？为什么容器需要它？**
   > 限制进程可用的系统调用（白名单）。即使容器内程序被攻破，也无法调用危险 syscall 攻击宿主内核，压缩攻击面。

5. **auditd 里的 auid 有什么独特价值？**
   > auid 在登录时确定且不可被提权伪造，能穿透 setuid/提权，把审计记录追溯到最初的登录用户。

6. **AIDE 的原理是什么？基线为什么不能放在被监控的磁盘上？**
   > 先建立文件哈希基线、定期比对找差异；基线若被攻击者改写则校验失效，应放只读/离线介质。

7. **SSH 加固至少要列哪三条？**
   > `PermitRootLogin no`、`PasswordAuthentication no`（强制密钥）、`AllowUsers` 限制可登录用户。

8. **事件响应六阶段中，"先取证后遏制"为什么重要？**
   > 遏制动作（杀进程、断网）可能破坏内存与日志证据，先保留只读镜像/日志副本才能完整还原攻击链条并支持后续追责。
