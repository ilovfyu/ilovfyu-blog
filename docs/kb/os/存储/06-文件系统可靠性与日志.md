::: abstract 本章定位
前几章假设系统一直正常运行，本章处理"崩溃了会怎样"。断电/崩溃会在元数据与数据之间造成不一致，日志（journaling）通过"先记账、后落盘"保证可恢复；日志结构文件系统与写时复制文件系统从设计上规避覆盖写风险；最后讲 fsck、SSD 的 TRIM 与磨损，以及 NFS。对应教材 Ch15 File-System Internals（含 C.7 等 Linux/可靠性内容）。
:::

## 1. 一致性问题

### 1.1 崩溃为什么会导致不一致

一次文件写操作涉及多个磁盘写：更新 inode（大小）、更新数据块、更新目录项、更新空闲位图。这些**不是原子的**，崩溃可能发生在任意两步之间：

```text
场景：创建文件并写入内容
步骤：① 分配数据块（改块位图）
      ② 写数据到数据块
      ③ 更新 inode（大小/指针）
      ④ 在目录添加目录项

崩溃点：
  在 ① 与 ② 之间 → 位图说"已用"但数据没写，块被白占
  在 ② 与 ③ 之间 → 数据在磁盘但 inode 不知道（文件为空/旧大小）
  在 ③ 与 ④ 之间 → inode 存在但目录无记录（孤儿 inode）
```

::: important 两种不一致
- **元数据不一致**：位图/inode/目录项互相矛盾（结构损坏）。
- **数据与元数据不一致**：元数据说文件有 N 字节，实际数据块没写全（内容损坏）。
日志文件系统主要保证**元数据一致性**与崩溃后可恢复，数据是否一致取决于日志模式（见 §3）。
:::

### 1.2 破坏数据块的假设

为保证可恢复，文件系统通常假设**单扇区/单块写是原子的**（要么完整写要么没写），并依赖断电保护（写缓存电池/掉电保护）。现代 SSD 的"掉电后仍丢页"问题要靠设备级 power-loss protection 解决。

## 2. 经典解法：fsck 一致性检查

传统做法是**启动时扫描检查**（`fsck`）：检查并修复位图、inode、目录项间的不一致。

```bash
# fsck 只能对未挂载的文件系统运行
sudo fsck /dev/sdb1
sudo fsck -f /dev/sdb1   # 强制检查
```

::: warning fsck 的缺点
- 全盘扫描**耗时**（TB 级盘可能数十分钟），服务器停机代价大。
- 只能修复**元数据**不一致，无法恢复没写全的**数据**。
- 自动化修复可能误删"看起来损坏"但实际有效的数据。
:::

**这就是日志文件系统存在的理由**：与其崩溃后全盘扫描，不如平时记录"将要做什么"，崩溃后只重放或撤销最近的少量操作，几秒内恢复。

## 3. 日志/日记文件系统（journaling）

### 3.1 原理：先记账、后落盘

ext3/ext4 在磁盘上划一块**日志区（journal）**。一次修改先写日志（记录"我要改 inode X、位图 Y"），日志落盘后再真正修改数据区：

```text
写操作流程（ordered 模式）:
  ① 把修改的元数据描述 写入 journal（日志落盘，有 CRC）
  ② 把数据块写到数据区
  ③ journal 提交（commit）标记
  ④ 把元数据真正写入磁盘对应位置
  ⑤ 日志可被覆盖（checkpoint）

崩溃恢复:
  看 journal 有无未完成的提交
  有 → 用日志里的描述**重做（redo）**或丢弃
  无 → 数据区一致，直接继续
```

::: tip 类比记账
就像饭店先记"客人点了菜"再上菜：崩了也能知道该补哪些菜或该退哪些菜，不用把整个厨房盘点一遍。
:::

### 3.2 ext3/ext4 的三种提交模式（高频考点）

| 模式 | 日志记录内容 | 数据安全性 | 性能 | 适用 |
|---|---|---|---|---|
| **writeback** | 仅元数据 | 最差（崩溃后**数据可能已损坏**，元数据可能引用坏数据） | 最快 | 性能优先、容忍数据丢失 |
| **ordered** | 仅元数据，但**数据先落盘再提交日志** | 较好（元数据一致，且提交时数据已落盘，不会引用半截数据） | 中 | **ext4 默认**，大多数业务 |
| **data** | 元数据 + 数据都写日志 | 最好（数据与元数据都完整） | 最慢（双倍写入） | 关键数据、小文件 |

::: important 三种模式的核心区别
- **writeback**：先记元数据，数据随意写 → 快但可能数据损坏。
- **ordered**：把数据写盘排在"提交日志"之前 → 保证"日志说文件有 100 字节时，100 字节已在盘上"，既不双写又能避免数据损坏。
- **data**：数据也进日志 → 双写开销大，但数据恢复最完整。
:::

```bash
# 查看/修改日志模式
tune2fs -l /dev/sdb1 | grep -i journal   # 看默认模式
sudo tune2fs -o journal_data_writeback /dev/sdb1   # 改为 writeback
# mount 选项也可指定: mount -o data=ordered /dev/sdb1 /mnt
```

### 3.3 journaling 的代价

- 写操作多一次"写日志"步骤 → 少量写性能开销（ordered 下小文件写尤其明显）。
- 日志区占磁盘空间（ext4 默认约 128 MB 或动态）。
- 日志只在"正常提交"时护体；**磁盘本身损坏、固件 bug** 不在其保护范围。

## 4. 日志结构文件系统（LFS）

**Log-Structured File System**（Ousterhout, 1991）：把磁盘当**连续日志**，所有修改（数据+元数据）都**顺序追加**到日志末尾，定期压实（segment cleaner）。

```text
传统 FS:  文件块随意散布，频繁原地改写 → 随机写 + 碎片
LFS:      所有写顺序追加 → 天然顺序 IO，随机写变顺序写
         ┌──────────────────────────────┐
         │ 新增写  →→→→→→→→ 尾部追加    │
         └──────────────────────────────┘
          定期垃圾回收，把"活的"数据压实搬到尾部
```

::: tip LFS 的动机与命运
80 年代磁盘随机写慢、顺序写快，LFS 把随机写变成顺序写。但后来日志/日志结构的思想被现代文件系统吸收：ext4 的日志、SSD 的"追加式"固件（FTL 层把随机写变顺序写）都继承了这个理念。纯 LFS 因垃圾回收开销与碎片未普及，其思想却影响深远。
:::

## 5. 写时复制文件系统（COW）

**Copy-On-Write（COW，写时复制）**：修改数据时**不覆盖旧块**，而是写一份到新块，更新指针指向新块。旧版本保留，天然支持快照与一致性。

```text
修改文件前:
  [inode] ─→ 块A(版本1)
修改后 (COW):
  [inode] ─→ 块B(版本2)   ← 新的
             块A(版本1)     ← 旧数据仍在，快照可引用
```

| 文件系统 | 特点 |
|---|---|
| ZFS | 存储池+校验和+快照+RAID-Z，COW 保证"永远不会破坏已有数据" |
| Btrfs | 子卷+快照+校验和+压缩，COW 默认开启，支持在线缩容 |

::: important COW 为什么可靠
崩溃时旧数据块仍完整（没被覆盖），恢复只需丢弃"未完成的写"即可，**不需要 journal 重放**——这就是 ZFS/Btrfs 号称"崩溃一致性"的底气。代价：频繁修改会放大写量、产生更多碎片，需定期碎片整理（btrfs）或依赖 SSD。
:::

## 6. SSD 的 TRIM 与磨损

### 6.1 TRIM 是什么

删除文件后，文件系统只知道"这些块空闲了"，但 SSD 固件不知道（它以为数据还在）。若不做 TRIM，SSD 会保留这些"僵尸页"，垃圾回收时会误判、浪费写与寿命。

**TRIM（discard）**：文件系统主动告诉 SSD"这些 LBA 已删除"，SSD 立即把对应页标记为可回收。

```bash
# 查看是否开启 discard
cat /sys/block/sda/queue/discard_max_bytes
# 手动 TRIM
sudo fstrim -av
# 挂载时实时 discard（ssd 下可用）
sudo mount -o discard /dev/sdb1 /mnt
```

::: warning 不 TRIM 会怎样
- 删除后写新数据要先"擦掉"旧数据所在的块 → **写放大**、速度变慢。
- 空闲块不足时 GC 被迫搬移更多数据 → 寿命缩短。
对写敏感的工作负载，开启 TRIM 能显著改善随机写性能与寿命（结合 [磁盘结构与大容量存储](/kb/os/存储/01-磁盘结构与大容量存储/) 的磨损均衡）。
:::

### 6.2 磨损均衡与寿命

- 闪存每单元有擦写次数上限（P/E 数，SLC 万级、TLC 千级）。
- SSD 固件做**磨损均衡**：把写均匀分散到所有块，避免"热点块"提前报废。
- 文件系统层面配合：开启 TRIM、避免小随机写、控制写放大。

## 7. 网络文件系统（NFS）

**NFS（Network File System）** 把远程文件系统挂载到本地目录树，客户端像访问本地文件一样访问远程文件。

```bash
# 服务端导出
echo "/srv/data *(rw,sync,no_subtree_check)" > /etc/exports
sudo exportfs -a; sudo systemctl restart nfs-server

# 客户端挂载
sudo mount -t nfs4 server:/srv/data /mnt/nfs
```

| 概念 | 说明 |
|---|---|
| 状态 | 早期 NFS 无状态（每个请求独立，崩溃恢复简单）；v4 引入状态化与会话 |
| 一致性 | 客户端有缓存，多客户端并发写可能读到旧数据（cache coherence 弱） |
| 安全 | v4 支持 Kerberos 等；传统 NFS 依赖主机信任 |
| 位置透明 | 文件在网络上的位置对用户透明，挂载点接入本地树 |

::: tip NFS 与分布式文件系统
NFS 是"共享导出"型（SAN/NAS 思路），一台服务器导出、多客户端挂载；分布式文件系统（如 HDFS、Ceph）是"多服务器协同"型。面试区分：**NFS = 网络化单文件系统；分布式 FS = 多机横向扩展**。
:::

## 8. 本章小结

- 崩溃导致元数据/数据不一致，本质是**多步磁盘写不原子**。
- fsck 全盘扫描修复元数据，但慢且救不了数据；日志 FS 用"先记账再落盘"换快速恢复。
- journaling 三种模式：writeback（快但可能数据坏）、ordered（数据先落盘，默认）、data（双写最安全）。
- LFS 把随机写变顺序写，思想被现代 FS/SSD 固件继承。
- COW（ZFS/Btrfs）不覆盖旧块，崩溃天然一致，代价是写放大。
- SSD 需要 TRIM 及时告知删除、磨损均衡延长寿命。
- NFS 把远程 FS 挂进本地树，是无状态/有状态演进的经典案例。

## 9. 自测题

1. 一次"创建文件"为什么可能崩溃后不一致？举例两个崩溃点。
   <details><summary>答案</summary>
   涉及位图、数据块、inode、目录项多步写。如：更新了 inode 但目录项未写（孤儿文件，无法通过路径找到）；位图标记已用但数据未写（块被白白占用）。
   </details>

2. 为什么 fsck 不适合现代大磁盘？
   <details><summary>答案</summary>
   全盘扫描耗时长（停机久），且只能修复元数据不一致、无法恢复数据损坏。因此现代 FS 用日志把恢复时间降到几秒。
   </details>

3. journaling 三种模式的区别？ext4 默认是哪种？
   <details><summary>答案</summary>
   writeback 只记元数据（最快但数据可能坏）；ordered 记元数据但先落盘数据再提交日志（默认，数据一致性较好）；data 数据也进日志（最安全、双写慢）。
   </details>

4. 为什么说 ordered 模式能避免"日志说文件有 100 字节但实际数据没写"？
   <details><summary>答案</summary>
   ordered 保证**在提交日志之前**把数据块写盘，所以一旦日志记录了大小，对应的数据已经落在盘上，不会出现元数据指向未写数据。
   </details>

5. 日志文件系统的"日志区"崩溃后是怎么用的？
   <details><summary>答案</summary>
   启动时检查日志，若有未完成的提交则**重做**（redo）其中记录的操作，使元数据一致；完成后日志可覆盖（checkpoint），避免全盘扫描。
   </details>

6. LFS 的核心思想是什么？它为什么没取代传统 FS？
   <details><summary>答案</summary>
   把随机写变顺序写（所有更新追加到日志尾）。因垃圾回收（segment cleaner）开销与碎片管理复杂未普及，但其思想被日志 FS 和 SSD 固件继承。
   </details>

7. ZFS/Btrfs 为什么声称"崩溃一致性"？代价是什么？
   <details><summary>答案</summary>
   COW 不覆盖旧块，崩溃时旧版本仍完整，恢复只需丢弃未完成的写，无需 journal 重放。代价是写放大、碎片多、需定期整理。
   </details>

8. 不开启 TRIM，SSD 会怎样？如何手动触发 TRIM？
   <details><summary>答案</summary>
   已删数据仍被 SSD 认为"活着"，GC 无法回收 → 写放大、随机写变慢、寿命缩短。用 `fstrim -av` 手动，或 `mount -o discard` 实时。
   </details>

9. NFS 客户端缓存可能导致什么问题？
   <details><summary>答案</summary>
   多客户端并发读写同一文件时，各客户端缓存可能不一致（读到旧数据），即弱缓存一致性。NFS v4 通过状态化与会话改进，但仍不如本地 FS 强一致。
   </details>
