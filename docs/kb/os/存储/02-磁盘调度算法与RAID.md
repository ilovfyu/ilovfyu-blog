::: abstract 本章定位
磁盘访问 99% 的时间花在寻道与旋转上。磁盘调度算法通过安排请求的**服务顺序**来最小化磁头总移动距离（寻道距离），从而降低平均响应时间。本章给出 FCFS / SSTF / SCAN / C-SCAN / LOOK / C-LOOK 六个算法的完整手算例题，回答"SSD 还需要调度吗"，并介绍 Linux 的 IO scheduler。对应教材 Ch11（磁盘调度）与 Ch14（RAID）。
:::

## 1. 磁盘调度的目标与评价指标

### 1.1 为什么需要调度

磁盘一次随机访问约 8–10 ms，其中寻道 + 旋转占 99%+（见 [磁盘结构与大容量存储](/kb/os/存储/01-磁盘结构与大容量存储/)）。当多个请求在队列中等候时，服务顺序直接决定总寻道距离。调度的目标：

- **最小化总寻道距离**（主要指标）
- **最小化平均响应时间 / 平均等待时间**
- 尽量**公平**，避免某个请求被无限期饿死

::: important 用"电梯"想问题
磁盘调度器就像大楼电梯：磁头沿一个方向移动，沿途捎带顺路的请求，到头再掉头。电梯不会为"正在上升时按了下行键的人"立刻掉头——磁头也一样。
:::

### 1.2 手算例题的统一前提

下面所有算法共用同一组数据，方便对比：

- 磁道编号范围：0 – 199
- 请求队列（到达顺序）：**98, 183, 37, 122, 14, 124, 65, 67**
- 磁头当前位置：**53**
- 对于 SCAN/C-SCAN/LOOK/C-LOOK，假设**初始移动方向为磁道号变小（朝 0）**

::: warning 计算结果依赖初始方向
教材中 SCAN/C-SCAN 的起始方向可能不同（有的朝大磁道、有的朝小磁道），数值会变。解题时必须**先说明方向**。本文统一按"朝 0 移动"计算，方向一致才可横向比较。
:::

## 2. 六种调度算法详解

### 2.1 FCFS（First-Come-First-Served，先来先服务）

按请求到达顺序依次服务，最简单、最公平，但没有优化。

```
磁头在 53
队列顺序: 98, 183, 37, 122, 14, 124, 65, 67

移动距离:
 53→98  = 45
 98→183 = 85
183→37  = 146
 37→122 = 85
122→14  = 108
 14→124 = 110
124→65  = 59
 65→67  = 2
────────────────────
总寻道距离 = 45+85+146+85+108+110+59+2 = 640
```

```text
0     14   37   53 65 67    98        122 124              183    199
|──────|────|────|──|──|────|─────────|───|───|──────────────|──────|
       ←─────────→ 磁头移动路径（来回大幅摆动，走了很多冤枉路）
```

::: warning 最坏情况
FCFS 在队列两端来回跳（如 183→37→122→14），寻道距离很大。它**不做任何优化**，通常只作为对照基线。
:::

### 2.2 SSTF（Shortest Seek Time First，最短寻道时间优先）

每次从当前位置选择**寻道距离最短**的请求。类似 CPU 调度的 SJF，是贪心策略。

```
磁头在 53

第1步: 到 53 最近的请求是 65（距离12）→ 65
第2步: 最近是 67（距离2）      → 67
第3步: 最近是 37（距离30）     → 37
第4步: 最近是 14（距离23）     → 14
第5步: 最近是 98（距离84）     → 98
第6步: 最近是 122（距离24）    → 122
第7步: 最近是 124（距离2）     → 124
第8步: 剩 183（距离59）        → 183

服务顺序: 65, 67, 37, 14, 98, 122, 124, 183
移动距离: 12+2+30+23+84+24+2+59 = 236
总寻道距离 = 236
```

::: warning SSTF 的饥饿问题
贪心导致"磁头总在小范围内打转"：若不断有小距离请求到达，远处（如 183）的请求可能被无限期推迟。它不是最优解（局部最优≠全局最优），但实践中很高效。
:::

### 2.3 SCAN（电梯算法 / Elevator）

磁头沿一个方向移动，途中服务所有顺路请求，**到头（0 或 199）再掉头**。保证每个请求等待有限，消除饥饿。

```
磁头在 53，初始向 0 移动，服务到 0 后掉头向 199：

向 0 方向: 37(16), 14(23)  → 到达 0
掉头向 199: 65, 67, 98, 122, 124, 183

服务顺序: 37, 14, 0, 65, 67, 98, 122, 124, 183
移动距离:
 53→37  = 16
 37→14  = 23
 14→0   = 14
  0→65  = 65
 65→67  = 2
 67→98  = 31
 98→122 = 24
122→124 = 2
124→183 = 59
────────────────────
总寻道距离 = 16+23+14+65+2+31+24+2+59 = 236
```

```text
0(53→)  14 37   65 67     98      122 124       183  199
|───────|───|────|──|─────|───────|───|───|───────|────|
  →→→→→   →→ →→ →→ →→ →→ →→   →→  →→   →→→   →→   →
```

### 2.4 C-SCAN（Circular SCAN，循环扫描）

只在**一个方向**提供服务，到头后**快速回到起点**再继续同向服务。避免 SCAN 中磁头"刚服务完一边又要服务另一边"时，远离的新请求等待过长。

```
磁头在 53，只向 0 方向服务，到 0 后直接跳到 199 再向 0 服务：

向 0 方向: 37, 14, 0（到终点）
跳到 199（这段不计请求，算总移动距离）
向 0 方向: 183, 124, 122, 98, 67, 65

服务顺序: 37, 14, 0, 183, 124, 122, 98, 67, 65
移动距离:
 53→37  = 16
 37→14  = 23
 14→0   = 14
  0→199 = 199 （快速返回，无请求）
199→183 = 16
183→124 = 59
124→122 = 2
122→98  = 24
 98→67  = 31
 67→65  = 2
────────────────────
总寻道距离 = 16+23+14+199+16+59+2+24+31+2 = 386
```

::: tip 与 SCAN 的对比
同样数据下 SCAN = 236，C-SCAN = 386。C-SCAN 因为"快速回程"多了 199+183 段，总距离更大，但**最坏等待时间更均匀**：请求只会等待"一圈"，不会在掉头点附近被反复推迟。
:::

### 2.5 LOOK（先看再走）

SCAN 的改进：磁头**不必走到磁道两端**，只走到当前方向最后一个请求就掉头。

```
磁头在 53，初始向 0 方向：
向 0 方向: 37, 14（14 是该方向最后一个请求，不用走到 0）
掉头向 199: 65, 67, 98, 122, 124, 183

服务顺序: 37, 14, 65, 67, 98, 122, 124, 183
移动距离:
 53→37  = 16
 37→14  = 23
 14→65  = 51
 65→67  = 2
 67→98  = 31
 98→122 = 24
122→124 = 2
124→183 = 59
────────────────────
总寻道距离 = 16+23+51+2+31+24+2+59 = 208
```

### 2.6 C-LOOK（Circular LOOK）

C-SCAN 的改进：只在一个方向服务，且**只在最后一个请求处折返**到另一端最后一个请求。

```
磁头在 53，只向 0 方向：
向 0 方向: 37, 14（该方向最后一个请求）
跳到最大请求 183（不是 199）
向 0 方向: 124, 122, 98, 67, 65

服务顺序: 37, 14, 183, 124, 122, 98, 67, 65
移动距离:
 53→37  = 16
 37→14  = 23
 14→183 = 169 （折返）
183→124 = 59
124→122 = 2
122→98  = 24
 98→67  = 31
 67→65  = 2
────────────────────
总寻道距离 = 16+23+169+59+2+24+31+2 = 326
```

## 3. 六种算法对比

| 算法 | 优化思路 | 服务顺序（本例题） | 总寻道距离 | 饥饿 | 公平性 | 适用 |
|---|---|---|---|---|---|---|
| FCFS | 无 | 98,183,37,122,14,124,65,67 | **640** | 无 | 最公平 | 对照基线 |
| SSTF | 每次取最近 | 65,67,37,14,98,122,124,183 | **236** | 有 | 差 | 请求均匀的小系统 |
| SCAN | 单向往返 | 37,14,0,65,67,98,122,124,183 | **236** | 无 | 较好 | 通用磁盘 |
| C-SCAN | 单向循环 | 37,14,0,183,124,122,98,67,65 | **386** | 无 | 等待最均匀 | 高负载、重负载 |
| LOOK | SCAN+不走到头 | 37,14,65,67,98,122,124,183 | **208** | 无 | 好 | 现代默认思想 |
| C-LOOK | C-SCAN+不走到头 | 37,14,183,124,122,98,67,65 | **326** | 无 | 等待均匀 | 高负载 |

::: important 结论与记忆
- **总距离**：FCFS(640) > C-SCAN(386) > C-LOOK(326) > SSTF=SCAN(236) > LOOK(208)。
- 本例题里 SSTF 和 SCAN 恰好相等（236），属巧合。
- LOOK 系列因为"不空走磁道两端"，通常寻道距离最小；C-SCAN/C-LOOK 多付"折返"代价，换最坏等待更均匀。
- 面试口诀：**SCAN 到头、LOOK 不到头、C- 只去不回**。
:::

## 4. SSD 需要磁盘调度吗

::: important 核心结论：SSD 不需要寻道，传统调度算法失去意义
SSD 任意地址访问时间相同（约 0.05–0.2 ms，见 [磁盘结构与大容量存储](/kb/os/存储/01-磁盘结构与大容量存储/)），SCAN 等面向"减少磁头移动"的算法优化目标不存在。现代内核为 SSD 默认使用 `none`（直接透传，把排序交给 NVMe 控制器）或 `mq-deadline`（保序防饿死）。
:::

SSD 真正需要的是：

| SSD 特有机制 | 作用 |
|---|---|
| **磨损均衡（wear leveling）** | 让所有闪存块的擦写次数接近，避免个别块过早报废 |
| **垃圾回收（GC）** | 后台把分散的"活页"搬走、整块擦除，腾出空闲块 |
| **TRIM / discard** | 操作系统主动告诉 SSD 哪些块已删除，让 GC 提前清理（见 [文件系统可靠性与日志](/kb/os/存储/06-文件系统可靠性与日志/)） |
| **写放大控制** | 减少"读-改-写"触发的多余写，延长寿命、提升随机写性能 |

::: tip 面向 SSD 的调度其实是"队列深度"管理
NVMe SSD 性能吃**队列深度（QD）**：并发请求越多越能掩盖延迟。`blk-mq`（多队列）框架把请求直接分发到各核队列，配 `none` 调度让设备自己合并与重排，这就是现代 SSD 高性能的原因（详见 [IO 性能优化](/kb/os/IO/05-IO路径与性能优化/)）。
:::

## 5. Linux 的 IO Scheduler

### 5.1 查看与切换

```bash
# 查看当前块设备支持的调度器及当前使用哪个（方括号内）
cat /sys/block/sda/queue/scheduler

# 切换（临时，重启失效）
echo mq-deadline > /sys/block/sda/queue/scheduler

# 永久生效：grub 内核参数或 udev 规则
```

### 5.2 常见调度器

| 调度器 | 全称/来源 | 适用 | 特点 |
|---|---|---|---|
| `none` | 无调度（NVMe 默认） | SSD/NVMe | 直接透传给设备，靠设备自身队列，无排序开销 |
| `mq-deadline` | Multi-Queue Deadline | HDD 默认 | 按截止时间保证请求不被饿死，兼顾顺序批量，现代内核替代 deadline |
| `deadline` | Deadline（旧） | 老 HDD | 每个请求设截止时间，读写各一队列，防饿死 |
| `bfq` | Budget Fair Queuing | 桌面/交互 | 按进程公平分配 IO 带宽，交互应用延迟低 |
| `kyber` | Kyber | 云/延迟敏感 | 基于延迟感知，动态调整队列深度 |
| `cfq` | Completely Fair Queuing（已移除） | 旧内核 | 按进程分配时间片，公平但吞吐一般，4.x 后废弃 |

::: warning CFQ 为什么被淘汰
CFQ 让每个进程"轮转"使用磁盘，公平但对吞吐有损，且在 blk-mq 时代单队列设计无法扩展。内核 5.x 移除了 CFQ，被 mq-deadline / bfq / kyber 取代。面试若问"Linux IO 调度器"：默认是 **mq-deadline（HDD）** 与 **none（SSD）**。
:::

## 6. 本章小结

- 磁盘调度以**最小化寻道距离**为目标，因为随机访问瓶颈在寻道+旋转。
- FCFS 不优化（640）、SSTF 贪心会饿（236）、SCAN/C-SCAN 电梯式最公平（236/386）、LOOK/C-LOOK 是"不到头"改进（208/326）。
- C-SCAN/C-LOOK 多付折返距离，换**最坏等待时间均匀**。
- SSD 无寻道，调度算法退位，磨损均衡 + TRIM + 多队列才是重点。
- Linux 默认：HDD 用 `mq-deadline`，SSD/NVMe 用 `none`；CFQ 已废弃。

## 7. 自测题

1. **手算**：请求队列 {53, 65, 98, 183, 37, 122, 14, 124, 65, 67} 中，磁头初始在 53。用 SSTF 求服务顺序与总寻道距离。（提示：注意请求里有两个 65？本题用标准教材请求 {98,183,37,122,14,124,65,67}）
   <details><summary>答案</summary>
   采用标准队列 {98,183,37,122,14,124,65,67}，磁头 53，方向无关（SSTF 只看距离）。顺序：65,67,37,14,98,122,124,183；总距离 = 12+2+30+23+84+24+2+59 = **236**。
   </details>

2. **手算**：同一队列，磁头在 53，初始朝大磁道（199）方向，求 SCAN 的服务顺序与总寻道距离。
   <details><summary>答案</summary>
   先朝 199：65,67,98,122,124,183（到 199 掉头），再朝 0：37,14,0。顺序：65,67,98,122,124,183,37,14,0。距离 = 12+2+31+24+2+59+16 + (199→37=162) + 23 + 14 = **345**。注意方向不同结果与文内例题（236）不同。
   </details>

3. **手算**：同一队列，C-LOOK 初始朝 0 方向，求服务顺序与总寻道距离。
   <details><summary>答案</summary>
   朝 0：37,14；折返到最大请求 183；朝 0：124,122,98,67,65。顺序：37,14,183,124,122,98,67,65。距离 = 16+23+169+59+2+24+31+2 = **326**。
   </details>

4. SSTF 与 SCAN 在本例题总距离同为 236，为什么实践中更推荐 SCAN 类？
   <details><summary>答案</summary>
   SSTF 是贪心，短距离请求不断插入会饿死远处请求；SCAN 固定方向、到端折返，保证每个请求在一个方向扫描内必被服务，等待时间有上界。
   </details>

5. C-SCAN 比 SCAN 总距离大，为什么还要用它？
   <details><summary>答案</summary>
   单向循环使各位置的**最坏等待时间更均匀**。SCAN 在掉头处两端的位置等待时间差别大；C-SCAN 统一为"一圈"，负载重时更可预测。
   </details>

6. SSD 为什么默认用 `none` 调度器？"磨损均衡"和"磁盘调度"是一回事吗？
   <details><summary>答案</summary>
   SSD 无寻道，排序无意义，交给设备自身多队列处理。磨损均衡是 SSD 固件把写分散到各闪存块延长寿命，与磁头寻道调度**无关**，分属不同层。
   </details>

7. Linux 现在 HDD 和 SSD 各默认用什么调度器？CFQ 去哪了？
   <details><summary>答案</summary>
   HDD 默认 `mq-deadline`，SSD/NVMe 默认 `none`。CFQ 因吞吐损失与无法适配 blk-mq 被移除，被 mq-deadline / bfq / kyber 取代。
   </details>

8. 如何用命令查看并临时修改某块盘的调度器？
   <details><summary>答案</summary>
   `cat /sys/block/sda/queue/scheduler` 查看；`echo mq-deadline > /sys/block/sda/queue/scheduler` 临时切换（需 root）。
   </details>
