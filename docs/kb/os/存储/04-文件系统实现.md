::: abstract 本章定位
上一章讲"文件对用户长什么样"，本章深入"文件在磁盘上怎么落地"：文件系统五层结构、inode 的元数据与间接指针（含最大文件大小计算）、目录项存储、空闲空间管理、四种文件分配方式对比，以及 Linux ext4 的磁盘布局。对应教材 Ch14 File-System Implementation。
:::

## 1. 文件系统分层

一次 `read()` 从应用层到磁盘，经过五层：

```text
┌───────────────────────────────────────────┐
│ 应用层 (read/write 系统调用)               │
├───────────────────────────────────────────┤
│ 逻辑文件系统 (logical file system)        │ 目录、文件控制块(FCB/inode)、
│                                          │ 保护、安全
├───────────────────────────────────────────┤
│ 文件组织模块 (file-organization module)   │ 把逻辑块转成物理块，
│                                          │ 空闲空间管理
├───────────────────────────────────────────┤
│ 基本文件系统 (basic file system)          │ 发通用命令给设备驱动，
│                                          │ 管理缓冲/缓存
├───────────────────────────────────────────┤
│ IO 控制层 (I/O control)                  │ 设备驱动 + 中断 + 控制器
│                                          │ （见 IO 系列）
└───────────────────────────────────────────┘
        ↓ 最终落到磁盘块（见磁盘结构）
```

| 层 | 职责 | 对应概念 |
|---|---|---|
| 应用层 | 系统调用接口 | open/read/write/close |
| 逻辑文件系统 | 管理目录与元数据，维护文件控制块（FCB） | inode、目录、权限 |
| 文件组织模块 | 逻辑块号 → 物理块号，分配策略 | 连续/链接/索引/FAT、位图 |
| 基本文件系统 | 与设备驱动交互，缓冲数据 | buffer cache、read-ahead |
| IO 控制层 | 真正驱动硬件 | 设备驱动、中断、DMA |

::: tip 理解要点
用户看到的是"文件 + 偏移"，逻辑文件系统把它变成"inode + 逻辑块号"，文件组织模块把逻辑块号映射成"物理块号"，最后基本文件系统 + IO 控制层把物理块送到磁盘。**每一步都是一次"翻译"**。
:::

## 2. inode 结构

### 2.1 inode 里有什么

**inode（index node）** 是文件控制块，存文件元数据与数据块指针，**不含文件名**：

| inode 字段 | 说明 |
|---|---|
| 类型与权限 | 文件/目录/链接、rwx |
| 属主 UID / 组 GID | 权限判定 |
| 大小、块数 | 文件逻辑大小与占用块数 |
| 时间戳 | atime / mtime / ctime |
| 链接计数 | 有多少个目录项引用它 |
| **数据块指针** | 直接指针 + 间接指针（见下） |

### 2.2 直接与间接指针（Unix 经典模式）

```text
inode（示意）
┌──────────────────────────────┐
│ 元数据 (权限/时间/大小/计数)  │
│ 数据块指针:                  │
│   direct[0]  ───────────────→ │ 数据块 0
│   direct[1]  ───────────────→ │ 数据块 1
│   ...
│   direct[11] ──────────────→  │ 数据块 11
│   single indirect ──→ [指针块]→ 数据块 12..1027
│   double indirect ──→ [指针块]→ [指针块]→ 更多数据块
│   triple indirect ──→ ...     → 更多更多数据块
└──────────────────────────────┘
```

- **直接指针**：直接指向数据块（通常 12 个）。
- **单间接（single indirect）**：一个指针指向一个**指针块**，指针块里每个条目又指向一个数据块。
- **双间接（double indirect）**：指针指向"存指针块的块"，两级扩展。
- **三间接（triple indirect）**：三级扩展，支持超大规模文件。

::: important 最大文件大小计算（高频考点）
设块大小 4096 B（4 KB），块地址（指针）4 B，则每个指针块可容纳 `4096/4 = 1024` 个指针。


:::```
> 直接指针 12 个           →  12 个块
> 单间接                 →  1024 个块
> 双间接                 →  1024 × 1024 = 1,048,576 个块
> 三间接                 →  1024 × 1024 × 1024 = 1,073,741,824 个块
>
> 总块数 = 12 + 1024 + 1,048,576 + 1,073,741,824
>        = 1,074,791,436 个块
>
> 最大文件大小 = 1,074,791,436 × 4096 B
>             ≈ 4.40 × 10^12 B
>             ≈ 4.0 TiB（4 TB）
> ```
>
> 口算技巧：三间接占绝对主导，`1024³ × 4096 = 2³⁰ × 2¹² = 2⁴² B = 4 TiB`。所以 **4 KB 块 + 4 B 指针 → 最大约 4 TiB**。

::: tip 换个参数再算一次
若块大小仍 4096 B，指针改为 8 B，则每指针块 512 个指针，三间接 = 512³ = 134,217,728 块，最大文件 ≈ 134,217,728 × 4096 ≈ 0.5 TiB。**块越小、指针越宽，最大文件越小**。
:::

### 2.3 为什么用间接指针

- 小文件（< 48 KB，12×4 KB）**只需直接指针**，inode 一次读完，高效。
- 大文件靠间接指针**按需分配**，稀疏文件不浪费空间。
- 代价：访问越靠后的块，需要越多的指针块读取（多一次 IO）。

::: tip 在 Linux 上观察

:::```bash
> # ext4 默认使用 extent（连续的区间）而非经典间接指针，但仍可看 inode 数据
> stat -c '%s bytes' bigfile
> filefrag -v bigfile    # 显示文件的 extent 分布
> df -i                  # 查看 inode 使用率
> ```

## 3. 目录项存储

目录本身也是文件，其内容是一系列目录项。经典做法是"定长目录项"，现代（ext4）用"文件名+inode 号"的哈希树或简单线性表：

```text
目录文件内容（ext4 线性示意）:
┌──────────┬─────────┬──────────────┐
│ inode 号 │ 文件名长度 │ 文件名      │
├──────────┼─────────┼──────────────┤
│  5234    │   5     │  hosts       │
│  5236    │   6     │  passwd      │
│  5237    │   7     │  subdir      │
└──────────┴─────────┴──────────────┘
```

- 目录项 = 文件名 → inode 号的映射，不含文件内容。
- 路径解析逐级查目录项（见 [文件系统接口与目录结构](/kb/os/存储/03-文件系统接口与目录结构/)）。
- 现代 FS 用 **dentry cache** 缓存已解析过的目录项，加速路径查找。

## 4. 空闲空间管理

磁盘空闲块怎么记录？三种经典方法：

| 方法 | 原理 | 优点 | 缺点 |
|---|---|---|---|
| 位图（bitmap） | 每个块 1 bit，1=已用 0=空闲 | 查找连续块快、内存小（磁盘大小的 1/块大小 的位） | 维护成本，超大数据集位图也大 |
| 链表（free list） | 空闲块互相链接，头指针存超级块 | 实现简单 | 逐个遍历慢，链表本身占块 |
| 组（grouping） | 第一个空闲块存一批其他空闲块号 | 比链表快 | 管理稍复杂 |

::: tip 位图大小估算（常考）
磁盘 1 TB，块大小 4 KB，则总块数 = 1 TB / 4 KB = 2³⁰ / 2¹² = 2¹⁸ 个块 = 262,144 块。位图需要 262,144 bit = 32 KB。**1 TB 磁盘的位图只要 32 KB**，很小，所以位图最常用。
:::

::: warning ext4 的实际做法
ext4 在每个块组里放**块位图 + inode 位图**（见下节），分散管理、便于按组分配，避免全局位图的争用。
:::

## 5. 文件分配方式

文件的数据块如何分布在磁盘上？四种经典方案：

| 方案 | 原理 | 随机访问 | 顺序访问 | 碎片 | 扩容 | 场景 |
|---|---|---|---|---|---|---|
| 连续分配 | 文件占连续块，目录存起始块+长度 | O(1) 最好 | 最好 | 外部碎片严重 | 难 | 老系统、ISO 光盘 |
| 链接分配 | 每块末尾存下一块指针，目录存首块 | 差（要遍历） | 好 | 无外部碎片 | 易 | 顺序访问场景 |
| FAT（文件分配表） | 指针集中放内存/磁盘一张表 | 较好（查表 O(1)） | 好 | 少 | 易 | 老 Windows FAT |
| 索引分配 | 索引块集中存所有块指针（同 inode 间接指针） | 好 | 好 | 无 | 易 | **现代 FS（Unix/ext4/NTFS）** |

```text
连续分配:
 文件A: [块3][块4][块5][块6]    起始=3, 长度=4
 删除 A 后块 3-6 空闲但不连续 → 外部碎片

链接分配:
 文件B: 块10 →(指向)块22 →(指向)块47
 每块尾 4B 存下一块地址，随机访问要顺着链走

索引分配:
 inode ─→ 索引块 [指向块8][指向块19][指向块33]...
```

::: important 现代文件系统 = 索引分配 + 连续分配（extent）
纯索引分配每个块一个指针，条目多、随机访问要查表。现代 FS（ext4/NTFS）改用 **extent**：把**连续的块范围**记成一个区间（起始块 + 长度），文件大块连续时一个指针就能覆盖很多块，兼顾随机与顺序，还减少碎片。


:::```bash
> filefrag -v bigfile   # 看 extent 数，越多碎片越多
> ```

## 6. Linux ext4 布局

### 6.1 磁盘分区结构

```text
┌─────────┬──────────────┬───────────────────────────────┐
│ 引导块   │ 超级块         │ 块组 (block group) × N         │
│ boot block│ superblock  │                               │
└─────────┴──────────────┴───────────────────────────────┘
                                    │
               ┌────────────────────┼────────────────────┐
               ▼                    ▼                    ▼
         ┌────────────────────────────────────────────────┐
         │ 组描述符  │ 块位图 │ inode位图 │ inode表 │ 数据块 │
         │ group     │ block  │ inode     │ inode   │ data  │
         │ desc      │ bitmap │ bitmap    │ table   │ blocks│
         └────────────────────────────────────────────────┘
         每块组内部结构（块组 = 磁盘被切分的固定大小单位）
```

| 组件 | 作用 |
|---|---|
| 引导块 | 存放引导程序（bootloader） |
| 超级块 superblock | 全局信息：块大小、inode 数、块组数、FS 状态、挂载次数等 |
| 组描述符 | 记录每个块组的位图/inode 表位置 |
| 块位图 / inode 位图 | 该块组内块与 inode 的占用情况 |
| inode 表 | 该块组的 inode 数组（每个 inode 一个文件） |
| 数据块 | 存放文件内容 |

### 6.2 关键点

::: important 超级块备份
超级块极重要（丢了 FS 就废了），ext4 在**多个块组**存有备份。主超级块损坏时可用备份恢复。`dumpe2fs` 可查看这些结构。


:::```bash
> sudo dumpe2fs /dev/sdb1 | head -50   # 查看超级块、块组信息
> sudo dumpe2fs /dev/sdb1 | grep -i block
> ```

::: tip inode 与块的关系
- 块组内 inode 表大小固定，所以 **inode 数量有上限** → 小文件极多时 inode 用光（`df -i` 100%），即使还有空间也建不了文件。
- 新建文件 = 分配一个 inode（写 inode 位图）+ 分配数据块（写块位图）+ 填目录项。
:::

## 7. 本章小结

- 文件系统五层：应用 → 逻辑 FS → 文件组织模块 → 基本 FS → IO 控制，每层一次翻译。
- inode 存元数据 + 数据块指针（12 直接 + 单/双/三间接）。
- **最大文件大小**：4 KB 块 + 4 B 指针 ≈ 4 TiB；核心是 `(12+1024+1024²+1024³)×4KB`。
- 目录项 = 文件名 → inode 号；路径解析逐级查目录。
- 空闲空间：位图（1 TB 磁盘仅 32 KB）最常用，ext4 分块组管理。
- 分配方式：连续/链接/FAT/索引对比；现代 FS 用索引 + extent。
- ext4 布局：引导块、超级块、块组（组描述符、双位图、inode 表、数据块），超级块有备份。

## 8. 自测题

1. **计算**：块大小 4096 B、块地址 8 B，12 个直接指针 + 单/双/三间接，求最大文件大小。
   <details><summary>答案</summary>
   每指针块 4096/8 = 512 个指针。总块数 = 12 + 512 + 512² + 512³ = 12 + 512 + 262,144 + 134,217,728 = 134,480,396。最大大小 = 134,480,396 × 4096 ≈ 5.51 × 10¹¹ B ≈ 0.5 TiB。
   </details>

2. **计算**：块大小 1024 B、块地址 4 B，求单间接能支持的最大文件大小（无直接与多级）。
   <details><summary>答案</summary>
   每指针块 1024/4 = 256 个指针 → 单间接最多 256 块 × 1024 B = 262,144 B = **256 KB**。
   </details>

3. inode 为什么不含文件名？目录项存什么？
   <details><summary>答案</summary>
   文件名属于"组织关系"，存在目录项里（文件名 → inode 号）。好处是重命名不改 inode、硬链接共享 inode、目录结构与文件内容解耦。
   </details>

4. 连续分配、链接分配、索引分配的随机访问性能如何？
   <details><summary>答案</summary>
   连续 O(1)（起始块+偏移）；链接 O(n)（要沿链遍历）；索引 O(1)（查索引块直接定位）。因此现代 FS 用索引 + extent。
   </details>

5. 1 TiB 磁盘、4 KB 块，空闲空间位图占多大？
   <details><summary>答案</summary>
   块数 = 2⁴⁰/2¹² = 2²⁸ 个块 = 268,435,456 块；位图 = 268,435,456 bit = 32 MiB。约 32 MiB（口算：2²⁸ 位 /8 = 2²⁵ B = 32 MiB）。
   </details>

6. `df -i` 100% 但 `df -h` 显示有空间，是什么情况？
   <details><summary>答案</summary>
   inode 已用完。文件系统 inode 数在格式化时定死（ext4 默认每约 16 KB 一个 inode），海量小文件会先耗尽 inode，导致无法新建文件，即使数据块仍有空闲。
   </details>

7. ext4 的"块组"由哪些部分组成？超级块为什么有备份？
   <details><summary>答案</summary>
   组描述符、块位图、inode 位图、inode 表、数据块。超级块记录全局结构，损坏会导致 FS 无法挂载，因此多处备份以提高可靠性。
   </details>

8. 现代 ext4 为什么用 extent 而不是纯索引分配？
   <details><summary>答案</summary>
   extent 把连续块范围记录为一个区间（起始+长度），大文件只需少量区间即可覆盖，减少索引块数量、降低寻址开销与碎片，兼顾随机与顺序访问。
   </details>
