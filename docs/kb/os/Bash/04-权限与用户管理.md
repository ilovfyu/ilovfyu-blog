::: abstract 本章定位
聚焦账户与权限命令实操：useradd/usermod/group 管用户，逐列读懂 /etc/passwd 与 /etc/shadow，chmod/chown/umask 控制权限，setuid/sudo/ACL/setcap 精细授权，最后用 ls -l 逐位读法 + find 排查权限故障。机制原理见 [Linux 安全实操](/kb/os/Linux/06-Linux安全权限与审计/)，本笔记只补命令全集与操作细节。
:::

Linux 里一切皆文件，访问文件靠的就是"uid/gid + rwx 权限位"。本篇把这些命令讲透：**能创建和删除用户、能看懂账号数据库、能精确控制每个文件谁能读谁能跑、能提权又不留后门、出了问题能一眼定位**。学习路线总览见 [Bash命令学习路线总览](/kb/os/Bash/00-Bash命令学习路线总览/)，基础命令见 [核心命令与文件操作](/kb/os/Bash/01-核心命令与文件操作/)。

## 1. 用户与组管理

### 1.1 useradd：创建用户

```bash
useradd -m -s /bin/bash -G docker,sudo -u 1050 -d /home/dev alice
grep alice /etc/passwd /etc/group
# → /etc/passwd:alice:x:1050:1050::/home/dev:/bin/bash
# → /etc/group:docker:x:999:alice  /etc/group:sudo:x:1001:alice
```
参数逐个解读：

| 参数 | 含义 | 不写会怎样 |
|---|---|---|
| `-m` | 创建家目录 `/home/alice`（并复制 `/etc/skel` 模板文件） | 很多发行版默认不建家目录，用户登录无 HOME |
| `-s` | 指定登录 shell | 用 `/etc/default/useradd` 里的默认 shell（常为 sh） |
| `-G` | 附加组（逗号分隔，可多个） | 只有主组，没有 sudo/docker 等组权限 |
| `-g` | 指定已有主组 | 是否自动创建同名组由发行版的 `USERGROUPS_ENAB`/工具默认值决定 |
| `-u` | 指定 UID（普通用户通常从 `UID_MIN` 开始） | 按 `/etc/login.defs` 的范围分配下一个未用 UID |
| `-d` | 指定家目录路径；配合 `-m` 时在该路径创建目录 | 默认 `/home/用户名` |

::: tip useradd vs adduser
`useradd` 是底层命令，`adduser` 是 Debian/Ubuntu 上的交互式封装：它会**自动**建家目录、设密码、问全名。写脚本用 useradd，手动建号可以用 adduser。
:::

### 1.2 usermod：改用户属性

```bash
usermod -aG docker alice       # 把 alice 追加进 docker 组（-a 必须配合 -G！）
usermod -s /bin/zsh alice      # 换 shell
usermod -d /data/home/alice alice   # 改家目录字段（锁定/解锁用 passwd -l/-u）
```
::: warning 忘了 -a 的后果
`usermod -G docker alice`（无 -a）会**把 alice 从所有其他组里踢掉**，只留 docker 和主组。凡是"追加进组"，一律写 `-aG`。
:::

### 1.3 userdel / groupadd / groupdel / groupmod

```bash
userdel alice                  # 删用户，保留家目录和邮件
userdel -r alice               # 连家目录、邮件 spool 一起删（-r 慎用）
groupadd -g 1051 devteam       # 建组并指定 GID
groupadd --system svc          # 按发行版的 SYS_GID_MIN/SYS_GID_MAX 范围建系统组
groupmod -n team devteam       # 组改名：devteam → team
groupdel team                  # 删组（组被某个用户设为主组时会报错）
gpasswd -a alice team          # 把 alice 加入组 team（gpasswd -d 移出）
```
预期输出片段：
```
gpasswd: user 'alice' is already a member of 'team'
```
解读：`groupdel` 遇到"还有用户以它为组"会拒绝；先改那些用户的主组（`usermod -g other alice`）再删。新建用户的默认 shell/UID 范围等由 `/etc/login.defs` 控制。

### 1.4 id / groups / getent：查询身份与 NSS 数据

```bash
id alice
groups alice
getent passwd alice
getent group docker
getent hosts example.com
getent services ssh
```
预期输出：
```
uid=1050(alice) gid=1050(alice) groups=1050(alice),999(docker),1001(sudo)
alice : alice docker sudo
alice:x:1050:1050:Alice Zhang:/home/alice:/bin/bash
docker:x:999:alice
93.184.216.34  example.com
ssh                   22/tcp
```
解读：`id` 的输出拆成三块——**uid**（真实用户 ID）、**gid**（主组）、**groups**（主组 + 所有附加组）。`groups alice` 查询目录服务中的组关系；不带用户名的 `groups` 才显示**当前进程**持有的组列表，刚执行 `usermod -aG` 后两者可能暂时不同。

`getent &lt;database&gt; [key]` 通过 **NSS（Name Service Switch）** 查询系统认可的数据源，比直接读 `/etc/*` 更完整：

| 数据库 | 常用查询 | 输出解读与用途 |
|---|---|---|
| `passwd` | `getent passwd alice`、`getent passwd 1050` | 用户名或 UID → 7 字段账户记录 |
| `group` | `getent group docker`、`getent group 999` | 组名或 GID → 4 字段组记录 |
| `hosts` | `getent hosts example.com` | 按 NSS 顺序解析主机名；可能返回 IPv6，需逐行读取 |
| `services` | `getent services ssh`、`getent services 22` | 服务名或端口号 → `名称 端口/协议`，数据通常来自 `/etc/services` |

常用参数有 `-s service`（临时限定后端，如 `getent -s files passwd alice`）和 `-i`（部分数据库关闭 IDN 编码）。某些 libc/发行版不支持这些 GNU 选项；脚本应先以退出码判断：找到为 0，未知数据库或未找到为非 0，不要依赖本地化错误文本。

### 1.5 `/etc/nsswitch.conf` 与 NSS 查询顺序

```bash
grep -E '^(passwd|group|hosts|services):' /etc/nsswitch.conf
# passwd:         files systemd sss
# group:          files systemd sss
# hosts:          files dns myhostname
# services:       db files
getent -s files passwd alice     # 若实现支持 -s，只查本地 /etc/passwd
```

逐行格式是 `数据库: 后端1 后端2 ...`。`files` 读 `/etc/passwd`、`/etc/group`、`/etc/hosts` 等本地文件；`dns` 查 DNS；`sss`/`ldap`/`winbind` 接企业目录；`systemd` 可提供动态用户和本机名解析。方括号动作（如 `[NOTFOUND=return]`）会改变“失败后是否继续下一个后端”。

::: warning 不要把“本地没有”当成“用户不存在”
LDAP/SSSD 环境中，`grep alice /etc/passwd` 没结果不代表 alice 不存在，应以 `getent passwd alice` 为准。错误调整 NSS 顺序可能导致登录变慢、DNS 失效，甚至所有目录账户无法登录；改 `/etc/nsswitch.conf` 前保留 root 会话，并用 `getent` 分库验证。
:::

### 1.6 groups / newgrp / gpasswd / groupmems：组成员操作

```bash
groups                            # 当前 shell 实际持有的组
groups alice                      # 查询 alice 的组关系
newgrp docker                     # 在新子 shell 中把主有效组切为 docker
newgrp - docker                   # 同时按登录方式重建环境（实现存在细节差异）
gpasswd -a alice devteam          # 追加成员
gpasswd -d alice devteam          # 删除成员
sudo gpasswd -M alice,bob devteam # 替换完整成员列表，慎用
```

`newgrp` 成功后通常没有提示，用 `id` 可看到 `gid=... (docker)`；输入 `exit` 返回原 shell。已是成员时一般不需密码；不是成员时可能要求 `/etc/gshadow` 中的**组密码**。共享组密码难审计且会扩散，现代系统应由管理员维护成员，不要用 `gpasswd &lt;group&gt;` 给多人共享口令。

`gpasswd` 常用参数：`-a/-d` 增删单个成员，`-M` **整体覆盖**成员列表，`-A` 指定组管理员，`-r` 删除组密码。它修改 `/etc/group` 与 `/etc/gshadow`，应检查退出码并再用 `getent group devteam` 验证。

```bash
sudo groupmems -g devteam -l          # 列出成员
sudo groupmems -g devteam -a alice    # 添加
sudo groupmems -g devteam -d alice    # 删除
sudo groupmems -g devteam -p          # 清空全部成员，危险
```

`groupmems` 来自 shadow-utils，RHEL/Rocky 常见；Debian/Ubuntu 可能未安装或不提供，优先使用跨发行版更常见的 `gpasswd`/`usermod`。`-p` 是 purge，不是“打印”；批量操作前先 `-l` 留存现状。以上命令只改账户数据库，**不会回写已登录进程的 supplementary groups**，需重新登录或显式使用 `newgrp`。

### 1.7 passwd / chage / chpasswd：密码与过期策略

```bash
passwd                     # 自己改密码（会要求先输入旧密码）
sudo passwd alice          # root 帮别人设密码
sudo passwd -l alice       # 锁账号（shadow 中密码前加 !）
sudo passwd -u alice       # 解锁
passwd -S alice            # 查看账号密码状态 → alice L 08/10/2026 0 99999 7 -1
```
解读：shadow-utils 的 `passwd -S` 通常输出 **7 个字段**：用户名、状态（`L`=锁定，`P`=有可用密码，`NP`=无密码）、最近改密日期、最短天数、最长天数、警告天数、密码失效宽限天数。日期格式和字段细节会随发行版变化，自动化优先读 `/etc/shadow`/`chage -l` 的结构化字段，而不是硬切本地化文本。

加锁的实质通常是往 `/etc/shadow` 哈希前加 `!`，它只禁止**密码认证**：SSH 公钥、现有会话、cron 或其他认证后端仍可能可用。要停用人员账户，应结合 `chage -E 0`、终止会话、撤销密钥/token 和禁用相关服务，而不是只做 `passwd -l`。

```bash
chage -l alice             # 查看全部过期策略
chage -M 90 alice          # 密码最长 90 天
chage -d 0 alice           # 强制下次登录改密（天数为 0）
chage -E 2026-12-31 alice  # 账号到期
```
预期输出片段：
```
Last password change                              : Aug 10, 2026
Password expires                                  : Nov 08, 2026
Minimum number of days between password change    : 0
Maximum number of days between password change    : 90
```
解读：`chage -d 0` 常用于"给新用户一个临时密码，要求首次登录必须改"——临时员工/外包账号的标准做法。

批量设置密码用 `chpasswd`，它从标准输入读取 `用户:密码`：

```bash
printf '%s\n' 'alice:临时密码' 'bob:另一临时密码' | sudo chpasswd
# 成功通常无输出；随后核验状态并强制首次登录改密
passwd -S alice
sudo chage -d 0 alice

sudo chpasswd -e < hashes.txt   # 输入已加密哈希：alice:$y$...，不是明文
```

常用参数：`-e` 表示输入第二列已经是 crypt 哈希，`-c METHOD` 在部分 shadow-utils 版本选择加密方法，`-R CHROOT_DIR` 面向离线根目录。发行版对 `-c/-R` 支持不同，先查本机 `chpasswd --help`。不要把明文密码写进 shell 历史、进程参数或长期文件；从权限为 600 的临时输入读取并立即销毁，生产环境优先使用密钥或受控密码管理系统。

### 1.8 whoami / who / w / loginctl

```bash
whoami && who && w   # 当前 effective 用户 / 谁登录了系统 / 谁在干什么
```
预期输出：
```
zhang
zhang    pts/0    2026-08-10 09:30 (192.168.1.5)
```
解读：`whoami` 打印的是 **effective uid**（su/sudo 之后会变），`who`/`w` 从 utmp 数据库读取登录会话。排查"谁登录过、谁还在挂机"用这三个命令。

systemd 系统再用 `loginctl` 看 logind 当前掌握的 seat/session/user：

```bash
loginctl list-sessions                 # SESSION UID USER SEAT TTY STATE IDLE SINCE
loginctl session-status 3              # 会话 3 的用户、TTY、来源与进程树
loginctl show-user alice -p State -p Sessions -p Linger
sudo loginctl terminate-session 3      # 结束一个会话，先确认编号
sudo loginctl kill-user alice           # 向该用户全部会话发送信号，影响更大
sudo loginctl enable-linger alice       # 允许用户服务在登出后继续运行
```

输出中 `active/online/closing` 是会话状态，`Linger=yes` 表示用户登出后 `user@UID.service` 仍可运行。`loginctl` 只显示 systemd-logind 管理的**当前状态**，不是历史审计；容器、非 systemd、精简 WSL 中可能无 logind。`terminate-session`/`kill-user` 会中断作业并可能造成数据丢失，先用 `session-status` 和 `ps` 核实。

### 1.9 last / lastb / lastlog：登录历史

```bash
last -n 10 -F                         # /var/log/wtmp：最近 10 次登录，显示完整时间
last -x -n 10 reboot shutdown           # 加入 reboot/shutdown 等系统事件
last -i alice                         # alice 的来源显示为数字 IP（实现支持时）
sudo lastb -n 10                      # /var/log/btmp：失败登录，通常仅 root 可读
lastlog -u alice                      # 每个用户最近一次登录
lastlog -b 90                         # 超过 90 天未登录的账户
```

典型输出与解读：

```text
alice  pts/1  203.0.113.8  Mon Aug 10 09:10:02 2026 - 10:02:11  (00:52)
reboot  system boot  6.8.0  Mon Aug 10 08:55:00 2026 - still running
```

依次是用户、TTY、来源、起止时间和时长；`still logged in` 只表示 wtmp 中没有对应 logout，不保证连接仍存活。`last` 读轮转后的历史可用 `last -f /var/log/wtmp.1`；`lastb` 依赖 btmp，文件不存在或 PAM/sshd 未写入时结果不完整；`lastlog` 是稀疏数据库，不能用表面文件大小估算占用。部分新发行版逐步提供 `lastlog2`，最小系统也可能不装这些工具。历史文件可被 root 修改，严格取证应结合远程日志和 auditd。

### 1.10 faillock / pam_tally2：失败计数与解锁

```bash
sudo faillock --user alice             # 查看 alice 的失败记录
sudo faillock --user alice --reset     # 清零，成功通常无输出
sudo faillock --reset                  # 清所有用户，影响大，慎用

sudo pam_tally2 --user alice           # 老系统查看
sudo pam_tally2 --user alice --reset   # 老系统清零
```

`faillock` 是 Linux-PAM 的 `pam_faillock` 前端，RHEL 8/9、Fedora 与较新的 PAM 栈常见；策略通常在 `/etc/security/faillock.conf`，是否真正生效取决于 PAM 配置。输出含用户名、失败时间、来源与 `V/S/I` 状态；“无输出”通常表示无记录，不等于策略已启用。

`pam_tally2` 对应旧 `pam_tally2.so`，已废弃并从较新的 Linux-PAM 移除；RHEL 7/老 Ubuntu 教程里仍常见。两者数据库格式不同，不能混用，也不要手工删计数文件。Debian/Ubuntu 是否默认启用失败锁定随版本和 PAM 配置而异，先用 `grep -R 'pam_faillock\|pam_tally2' /etc/pam.d /etc/security` 核实。解锁前应确认是误锁还是暴力破解，并结合 `lastb`、SSH 日志和来源 IP 调查。

### 1.11 vipw / vigr / pwck / grpck：安全编辑与一致性检查

```bash
sudo vipw                  # 加锁编辑 /etc/passwd
sudo vipw -s               # 编辑 /etc/shadow
sudo vigr                  # 编辑 /etc/group
sudo vigr -s               # 编辑 /etc/gshadow
sudo pwck -r               # 只读检查 passwd/shadow
sudo grpck -r              # 只读检查 group/gshadow
```

`vipw`/`vigr` 会锁定账户数据库并调用 `$VISUAL`/`$EDITOR`，避免与 `useradd` 等并发写坏文件；部分实现保存 `.OLD` 备份。优先用 `usermod`/`gpasswd` 等结构化命令，只有修复异常字段时才直接编辑。

`pwck` 检查字段数、用户名唯一性、UID/GID、家目录和 shell 等；`grpck` 检查组字段、成员名和 GID。`-r` 是 read-only，只报告不修改；交互修复模式可能询问是否删除坏行，必须先备份四个数据库并保持救援 root 会话。LDAP/SSSD 条目不在本地文件中，`pwck/grpck` 也不会校验远端目录。

## 2. /etc/passwd 与 /etc/shadow

### 2.1 /etc/passwd：七字段

```
alice:x:1050:1050:Alice Zhang:/home/dev:/bin/bash
```

| 字段 | 示例 | 含义 |
|---|---|---|
| 1 用户名 | alice | 登录名 |
| 2 密码占位 | x | 早期存哈希，现在固定 `x` 表示"哈希在 /etc/shadow" |
| 3 UID | 1050 | 用户 ID（0=root；系统/普通用户范围由 `/etc/login.defs` 和发行版约定决定） |
| 4 GID | 1050 | 主组 ID |
| 5 GECOS | Alice Zhang | 备注（全名/电话，可空） |
| 6 家目录 | /home/dev | 登录后的 $HOME |
| 7 shell | /bin/bash | 登录 shell；`/sbin/nologin` 表示禁止交互登录 |

::: important 为什么密码单独放 /etc/shadow？
`/etc/passwd` 所有程序都要读（`ls -l` 要查属主名），所以必须任何人可读——那就不能放哈希。于是密码哈希挪到只有 root 能读的 `/etc/shadow`，`/etc/passwd` 第二字段固定留 `x`。这就是"读写最频繁的文件最小化暴露"的经典设计。
:::

### 2.2 /etc/shadow：九字段与密码哈希

```
alice:$6$rXs9zV3m$Km0lDn9k...哈希串...:19744:0:90:7:30:20500:
```

| 字段 | 含义 |
|---|---|
| 1 用户名 | 与 passwd 对应 |
| 2 密码哈希 | `$算法$盐$哈希`，见下表；`!` 或 `*` 前缀 = 锁定/不可登录 |
| 3 上次改密日 | 距 1970-01-01 的天数 |
| 4 最短天数 | 两次改密最小间隔（0=随时可改） |
| 5 最长天数 | 密码有效期（99999≈永不） |
| 6 警告天数 | 过期前多少天开始警告 |
| 7 密码失效期 | 密码过期多少天后禁用账户；不是普通的“继续登录宽限” |
| 8 账号过期日 | 距 1970-01-01 的天数，空=不过期 |
| 9 保留字段 | 留空 |

密码哈希格式 `$type$salt$hash`：

| 前缀 | 算法 | 备注 |
|---|---|---|
| `$1$` | md5crypt | 计算太快、抗破解能力弱，已不推荐 |
| `$5$` | SHA-256 | 一般 |
| `$6$` | SHA-512 | 最常用（老发行版） |
| `$y$` | yescrypt | 新版 Debian/Ubuntu 默认 |
| `$2b$` | bcrypt | BSD 系常见 |

解读：**salt（盐）通常随机生成，每个密码记录应不同**，它作为口令哈希算法的输入，并与算法标识、计算结果一起编码保存。同一个密码两次设置会得到不同记录——这正是 [认证加密](/kb/os/安全/02-身份认证与密码学基础/) 里“加盐抗预计算表”思想的落地。登录校验是取出算法参数和盐重新计算比对，而不是反解哈希；盐不需要保密，也不能弥补弱口令或过快算法。

### 2.3 /etc/group 与 uid/gid 概念

`docker:x:999:alice` 四字段 = 组名、组密码占位（x）、GID、成员列表（逗号分隔，主组用户不写在这）。

::: note uid 只认数字
内核判断"谁是谁"只认 **uid/gid 数字**，用户名只是给人看的映射。两个用户都设成 1050，在系统眼里就是同一个人。所以**备份归档、nfs 共享要保留数字 uid**，否则换个环境权限全乱。查看映射：`getent passwd 0`、`getent group 0`。
:::

## 3. 文件权限操作

### 3.1 chmod：符号模式 vs 数字模式

```bash
chmod u+x script.sh        # 属主加执行位
chmod g-w,o-r data.txt     # 组去掉写、其他去掉读
chmod a+r report.md        # 所有人加读（a=ugo）
chmod -R g+r docs/         # 递归给目录下全部文件加组读
```
符号模式语法：`who`（u/g/o/a）+ `operator`（+/‑/=）+ `perm`（r/w/x/X/s/t）。其中大写 `X` 只在"目标是目录或已有执行位"时才生效，常用语递归给脚本目录加执行。

数字模式：r=4、w=2、x=1，三组依次相加：

| 八进制 | 二进制 | 权限 | 八进制 | 二进制 | 权限 |
|---|---|---|---|---|---|
| 7 | 111 | rwx | 3 | 011 | -wx |
| 6 | 110 | rw- | 2 | 010 | -w- |
| 5 | 101 | r-x | 1 | 001 | --x |
| 4 | 100 | r-- | 0 | 000 | --- |

```bash
chmod 754 file.sh   # 属主 7=rwx，组 5=r-x，其他 4=r--
chmod 644 file.txt  # 属主 rw-，组 r--，其他 r--
chmod 600 secret    # 属主 rw-，其余全无
```
**速记**：r=4、w=2、x=1，想给谁就加谁。`644`（rw-r--r--）是普通文件默认，`755`（rwxr-xr-x）是脚本/目录默认。改成同符号模式哪种更好记？看场景——写脚本/批量处理用数字，临时给某类用户加一个位用符号。

### 3.2 chown / chgrp：改属主属组

```bash
chown alice file.txt            # 只改属主
chown alice:devteam file.txt    # 同时改属主和属组
chown :devteam file.txt         # 只改属组（等价 chgrp devteam）
chown 1000:1000 data/ -R        # 递归 + 用数字 UID
chgrp -R devteam /srv/app/      # 递归改属组
```
预期输出：`-rw-r--r-- 1 alice devteam 0 Aug 10 10:00 file.txt`
::: warning 只有 root 能改属主
普通用户只能改自己文件的**组**（且只能改成自己所在的组）；改**属主**（chown）必须 root。这是防止"把文件栽赃给别人"的保护。
:::

### 3.3 umask：默认权限面具

```bash
umask            # 022
umask -S         # u=rwx,g=rx,o=rx
touch f1 && ls -l f1    # -rw-r--r-- (644)
mkdir d1 && ls -ld d1   # drwxr-xr-x (755)
```
预期输出：`0022`、`u=rwx,g=rx,o=rx`。计算规则：**文件请求权限通常从 0666、目录从 0777 开始，再清除 umask 中置位的权限**（即 `mode & ~umask`），不是一般意义的十进制或八进制算术减法。

| umask | 新文件 | 新目录 | 适用 |
|---|---|---|---|
| 022 | 644 | 755 | 默认 |
| 027 | 640 | 750 | 组内可读、其他不可读 |
| 077 | 600 | 700 | 完全私有（密钥、证书） |
| 002 | 664 | 775 | 团队协作共享 |

```bash
umask 077            # 临时改（仅当前 shell 会话）
umask 022            # 用完改回来
# 永久：写 /etc/profile、/etc/profile.d/*.sh（所有用户）或 ~/.bashrc（个人）
```
::: tip umask 优先于 chmod
新文件一出生权限就由 umask 定好，比"建完再 chmod"少一个出错窗口。服务器建议 `umask 027`。注意 `umask 077` 之后 `cat` 创建的重定向文件同样是 600。
:::

### 3.4 目录 vs 文件的权限语义

| 权限 | 对**文件**的含义 | 对**目录**的含义 |
|---|---|---|
| r | 读内容 | 列出目录里的**文件名**（ls） |
| w | 写内容 | 创建/删除/改名目录内的条目 |
| x | 执行（脚本/二进制） | 进入目录、访问内部文件（cd、按路径读取） |

关键推论：
- **目录的 r 必须配 x 才有用**：`r` 无 `x`，能 `ls` 出文件名，但打不开任何内容；`x` 无 `r`，能进目录、按已知路径访问文件，但列不出名字。
- 对文件做任何操作，需要路径上**每一层目录**的 x 权限。`/home/alice/secret.txt` 即使文件是 777，只要 `/home/alice` 没有 x，其他人照样进不去。
- 删除文件的权限看**目录**的 w，不看文件自己的权限——文件权限只约束"改内容"，"删文件"是目录的事。这正是 sticky bit 要补救的漏洞（见 4.4）。

### 3.5 `namei -l`：逐层检查路径权限

```bash
namei -l /home/alice/project/report.txt
namei -om /srv/app/current/bin/server   # -o 属主/组，-m 权限位
namei -lx /etc/ssh/sshd_config          # 长格式，并把挂载点目录标为 D
```

预期输出片段：

```text
f: /home/alice/project/report.txt
drwxr-xr-x root  root  /
drwxr-xr-x root  root  home
drwx------ alice alice alice
drwxr-x--- alice dev   project
-rw-r----- alice dev   report.txt
```

`d`/`-`/`l` 表示目录、普通文件和符号链接，首行 `f:` 表示正在解析的路径；从左到右就是内核解析路径时逐层经过的对象。上例中，即使 `report.txt` 对组可读，只要调用者不是 alice 且 `/home/alice` 没有组/其他 `x`，仍会得到 `EACCES`。`-l` 等价于长格式组合（mode、owner、垂直对齐），`-m` 只显示 mode，`-o` 显示 owner/group，`-x` 标记挂载点，`-n` 才是“不跟随符号链接”。它只检查路径组件的 DAC 展示，不替代 ACL、SELinux/AppArmor 或挂载选项检查。

## 4. setuid / setgid / sticky bit

### 4.1 三种特殊位

| 特殊位 | chmod 写法 | 数字写法 | 作用 |
|---|---|---|---|
| setuid | `chmod u+s file` | `chmod 4755 file` | 运行时 effective uid = 文件属主 |
| setgid | `chmod g+s dir` | `chmod 2755 dir` | 目录下新建文件自动继承目录的组 |
| sticky | `chmod +t dir` | `chmod 1777 dir` | 共享目录只能删自己的文件 |

setuid 的关键：**passwd**。看它的权限：
```bash
ls -l /usr/bin/passwd
# -rwsr-xr-x  属主位 s = setuid
```
普通用户执行 passwd 时进程 effective uid 临时变成 root，才能写 `/etc/shadow` 改自己密码——这解释了"普通用户为什么能改只给 root 写的文件"。完整原理见 [Linux 安全实操](/kb/os/Linux/06-Linux安全权限与审计/)，这里只讲操作与排查。

### 4.2 ls -l 显示与大小写

```bash
chmod u+s file_suid    && ls -l file_suid
chmod g+s file_sgid    && ls -l file_sgid
chmod +t dir_sticky    && ls -ld dir_sticky
```
预期输出：
```
-rwsr-xr-x   # u 位 s（有 x）
-rwxr-Sr-x   # g 位 S（无 x，大写=对应执行位没开）
drwxrwxrwt   # t 位 t（有 x）
```
规则：**小写 s/t = 特殊位 + 执行位同时存在；大写 S/T = 只有特殊位、没执行位**（此时特殊位基本无效，且是不常见/可疑状态）。`find / -perm -4000 -type f` 可列出全系统 setuid 文件。

### 4.3 setuid 实验与安全风险

```bash
# 虚拟机/测试机上练习
sudo cp /bin/cat /usr/local/bin/mysuid && sudo chmod u+s /usr/local/bin/mysuid
ls -l /usr/local/bin/mysuid     # -rwsr-xr-x；切普通用户执行，mysuid /etc/shadow 能读（原 cat 不能）
sudo rm /usr/local/bin/mysuid   # 用完立即删除实验文件
```
::: warning setuid 是最高危权限
一个 setuid root 程序被攻破 = 攻击者直接拿到 root。镜像/打包/上线前用 `find / -perm -4000 -type f` 审计一遍；能用 `setcap`（7.2）或 sudo 白名单替代就绝不裸用 setuid。原则见 [访问控制](/kb/os/安全/01-保护机制与访问控制/)。
:::

### 4.4 /tmp 的 sticky bit

```bash
ls -ld /tmp
# drwxrwxrwt  任何人可写 + sticky（末尾 t）
```
`/tmp` 允许所有用户写入，但 sticky bit 保证**只有文件属主能删除/改名自己的文件**，避免"我删你、你删我"的临时文件战争。排查"为什么 `/tmp` 里删不掉别人的文件"答案就在这里。

## 5. sudo

### 5.1 sudoers 与 visudo

```bash
sudo visudo        # 编辑 /etc/sudoers，语法错误会拒绝保存（语法检查保护）
```
::: warning 永远不要直接 vim /etc/sudoers
语法写错会直接导致**所有 sudo 失效、谁也提不了权**。visudo 保存前做语法检查，还能 `:e` 退出重来。大型环境把自定义规则放 `/etc/sudoers.d/` 下独立文件（visudo 会自动 include），更方便管理。
:::

### 5.2 规则语法

```
user host=(runas) commands     # user 可为单个用户名或 %组名
```
典型行：
```
zhang   ALL=(ALL:ALL) ALL                                  # 完整提权
alice   ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx   # 免密执行单条命令
bob     ALL=(devops) /usr/bin/systemctl                    # 只能以 devops 身份执行
%ops    ALL=(ALL) /usr/bin/systemctl, /usr/sbin/useradd    # 组授权，命令白名单
```
逐段解读（以第 3 行为例）：

| 段 | 含义 |
|---|---|
| `bob` | 谁能用 sudo（用户或 `%组`） |
| `ALL` | 从哪些主机来（一般就 ALL） |
| `(devops)` | 可以切换成哪个用户/组执行（runas） |
| `/usr/bin/systemctl` | 允许执行的命令（绝对路径白名单） |
| `NOPASSWD:` | 免密；不写则首次 sudo 要输**自己**密码 |

::: tip 权限可累积，标签受匹配顺序影响
同一用户可从多条 User_Spec/Cmnd_Spec 获得命令权限，但 `NOPASSWD`/`PASSWD` 等 tag 会在命令列表中继承，后续匹配规则可能改变同一命令的认证结果，不能靠“写在前面就覆盖”判断。修改后用 `visudo -c` 做语法检查，并以 `sudo -l` 查看最终授权。
:::

### 5.3 常用参数

```bash
sudo -l                 # 列出我可执行哪些 sudo 命令
sudo -u alice id        # 以 alice 身份执行单条命令（不切 shell）
sudo -i                 # 完全 root 登录 shell（环境也切成 root 的）
sudo -s                 # 以目标用户运行当前 SHELL；环境仍受 sudoers 策略过滤
sudo systemctl restart nginx   # 最常用：临时提权执行一条命令
```
预期输出（sudo -l）：
```
User zhang may run the following commands on this host:
    (ALL : ALL) ALL
```
解读：`-i` 模拟目标用户登录并设置其 HOME、SHELL、USER、LOGNAME、PATH 等；`-s` 使用调用者的 `$SHELL`（或 passwd shell），但环境仍由 `env_reset`、`env_keep`、`secure_path` 等 sudoers 策略过滤。不要假设 `sudo -s` 会原样保留 HOME/环境，实际值用 `sudo -V`、`sudo -l` 和 `env` 核验。

### 5.4 sudo 与 root 的区别、日志、sudo !!

| 维度 | `su -` | `sudo command` |
|---|---|---|
| 密码 | 目标用户密码（切 root 时通常是 root 密码） | 默认验证调用者密码，也可配置 NOPASSWD/其他认证 |
| 权限 | 一次全给 root | 按白名单给单条命令 |
| 审计 | PAM/syslog 常记录切换事件，shell 内部命令通常不逐条记录 | 记录 sudo 启动的命令；shell 里的后续子命令需 I/O logging/auditd 才完整 |
| 适用 | 系统运维终端 | 日常授权、给他人最小提权 |

```bash
sudo !!                  # 用 sudo 重跑上一条命令（!! 是上条命令的别名）
sudo cat /var/log/auth.log | grep -i sudo     # Debian/Ubuntu sudo 日志
sudo grep -i sudo /var/log/secure             # RHEL/CentOS sudo 日志
journalctl _COMM=sudo                        # systemd 日志里筛 sudo
```
预期输出片段（auth.log）：`Aug 10 09:40:11 host sudo: zhang : TTY=pts/0 ; COMMAND=/usr/bin/systemctl restart nginx`
解读：sudo 通常记录“谁、何时、以谁身份启动了哪条命令”，日志可能在 `/var/log/auth.log`、`/var/log/secure`、journal 或远端日志。它不会天然看见 `sudo sh` 之后 shell 内的每个子命令，也可能因日志配置/轮转/主机失陷而不完整；高要求环境应启用 sudo I/O logging、auditd 和远程集中日志。与共享 root 密码相比，按人授权的 sudo 仍更利于最小权限和追责。

## 6. ACL：扩展权限

rwx 只能按"属主/组/其他"三类授权。想"只给 alice 一个人 rw、其他人一律没有"？标准权限做不到，用 ACL。原理见 [Linux 安全实操](/kb/os/Linux/06-Linux安全权限与审计/)。

### 6.1 getfacl / setfacl

```bash
setfacl -m u:alice:rw  report.txt     # 给 alice 加 rw
setfacl -m g:devteam:r report.txt     # 给 devteam 组加 r
getfacl report.txt
```
预期输出：
```
user::rw-
user:alice:rw-          # 命名用户项：alice 特有
group::r--
mask::rw-               # mask = 除属主与 other 外所有授权的上限
other::r--
```
参数速查：

| 参数 | 作用 |
|---|---|
| `-m` | 添加/修改条目 |
| `-x` | 删除某条目（`-x u:alice`） |
| `-b` | 清空全部 ACL |
| `-R` | 递归 |
| `-d` | 设置默认 ACL（目录用） |

### 6.2 默认 ACL 与 mask

```bash
setfacl -m d:u:alice:rwx project/    # 目录默认 ACL：其下新文件自动继承
```
mask 是**硬上限**：设了 `mask::r--`，alice 就算写了 `rwx`，实际也最多只拿到 `r`。`setfacl -m m::rx` 可整体收紧。想验证真实权限：`getfacl` 看 `effective:` 注释行。

### 6.3 ACL 与 chmod 的交互

- 文件带 ACL 时，`ls -l` 权限位末尾多一个 **`+`**（`-rw-rw-r--+`）。
- 文件存在扩展 ACL 时，`chmod` 的组权限位对应 ACL 的 `mask::`（而非简单等同 `group::`），因此会改变命名用户/组和 owning group 的有效上限；“先 setfacl 又 chmod，alice 权限缩水”通常是 mask 被收紧。属主/other 位仍对应 `user::`/`other::`。
- 彻底回到普通权限：`setfacl -b file`（`+` 消失）。

```bash
setfacl -R -m u:alice:rwx /srv/share/   # 递归给整个目录树授权（大目录慎用）
```
::: tip 什么时候用 ACL
共享目录"给张三一个人写、其他组只读"；web 服务器"给 php-fpm 用户写日志、管理员只读"。这都比"把权限放开到组"精准得多。
:::

## 7. 特殊场景

### 7.1 chroot：限制文件系统视图

```bash
sudo mkdir -p /newroot/{bin,lib,lib64}
sudo cp /bin/bash /newroot/bin/
ldd /bin/bash            # 找出依赖的动态库，逐个 cp 进 /newroot/lib/x86_64-linux-gnu/
sudo chroot /newroot /bin/bash    # 进入监狱：ls / 只剩 /newroot 里的文件
```
解读：chroot 改变进程看到的文件系统根，配合 chroot 内**没有 suid、没有可写目录**，可做一个简易隔离环境。它不隔离网络、进程、内核（root 可逃逸），是"早期版容器"的雏形，对应能力 `cap_sys_chroot`，见 [安全机制](/kb/os/Linux/14-Linux安全机制内核原理/)。

### 7.2 setcap：把 root 拆成单项能力

setuid 一次性把整个 root 给出去；capabilities 只给"干那件事的最小能力"：

```bash
sudo setcap cap_net_bind_service+ep ./myserver   # 让普通用户能绑 80 端口
getcap ./myserver                                # 查看文件能力
sudo setcap -r ./myserver                        # 移除
```
预期输出：
```
./myserver = cap_net_bind_service+ep
```
解读：`+ep` = effective + permitted。容器安全里常配 `--cap-drop=ALL --cap-add=cap_net_raw`，本质一样——只给需要的单项能力。有了它，很多本要 setuid root 的场景可以收敛，原理和危险能力清单（如 `cap_sys_admin`）详见 [Linux 安全实操](/kb/os/Linux/06-Linux安全权限与审计/)。

### 7.3 `runuser` / `setpriv`：非交互降权与精确清权

```bash
sudo runuser -u app -- id                 # root 直接以 app 执行一条命令
sudo runuser -u app --preserve-environment -- /opt/app/bin/server
sudo runuser -l app -c 'printf "%s\\n" "$HOME:$PATH"'  # 登录环境（实现支持 -c）

setpriv --reuid=app --regid=app --init-groups -- /opt/app/bin/server
setpriv --dump                              # 查看当前进程可调整的身份/能力状态
sudo setpriv --reuid=app --regid=app --init-groups \
  --inh-caps=-all --bounding-set=-all -- /opt/app/bin/server
```

`runuser` 是 util-linux 提供的 root 专用 `su` 变体：不要求目标账户密码，但仍使用独立的 PAM 配置处理 account/session 等步骤，不应拿来给普通用户互相切换；适合 root 脚本一次性以服务账户运行程序。`-u` 指定用户，`-g`/`-G` 可指定组，`-l`/`-c` 分别模拟登录环境和执行命令；不要随意使用 `--preserve-environment`，它可能把不可信的 `PATH`、代理、动态库变量带入目标上下文。systemd 服务长期降权优先用 unit 的 `User=`/`Group=` 与加固选项。

`setpriv` 直接修改 exec 前后的 real/effective/saved UID/GID、supplementary groups、capability bounding/inheritable sets、`no_new_privs`（`--no-new-privs`）和 securebits。它不是容器，也不会隔离文件系统、网络、PID 或内核；`--reuid`/`--regid` 只改身份，`--init-groups` 才会按目标用户初始化附加组。`--bounding-set=-all` 是不可逆地收窄当前进程及后代可获得的能力，参数顺序和可用选项随 util-linux 版本变化，先在非生产进程上用 `setpriv --dump` 验证。

### 7.4 su vs sudo 对比

```bash
su - alice         # 换用户 + 登录 shell（干净的 HOME/PATH，输 alice 的密码）
sudo -u alice cmd  # 以 alice 身份执行一条命令，不用知道 alice 密码
```

| 命令 | 要谁的密码 | 给什么权限 | 默认是否审计 |
|---|---|---|---|
| `su` | 目标用户的密码 | 整个 shell | 否 |
| `su -` | 目标用户的密码 | 整个 shell + 登录环境 | 否 |
| `sudo -u u cmd` | 自己的密码 | 单条命令（白名单内） | 是 |

### 7.5 切换用户与权限丢失问题

- **组不刷新**：`usermod -aG docker alice` 之后，alice **已登录的会话看不到新组**——必须重新登录或 `newgrp docker`，否则 `docker` 命令仍报权限拒绝。`id alice` 能显示新组，但**当前进程**的 groups 不会变。
- **umask/HOME 差异**：sudo 是否保留 umask、如何设置 HOME 由 sudo 版本和 sudoers（如 `umask`、`umask_override`、`always_set_home`、`set_home`）决定；`sudo -i`/`su -` 更接近目标用户登录环境。不能靠记忆猜，直接用 `umask; printf '%s\n' "$HOME"` 对比。
- **双用户写同一文件**：属主不同 + umask 不同，常出现"一个能写一个不能"，优先用共享组 + `setgid` 目录（4.1）解决。

## 8. 权限排查实战

### 8.1 "文件在，却报 No such file or directory"

现象：`ls -l` 明明看到 `run.sh`，执行却报 `No such file or directory`。按优先级排查：

```bash
head -1 run.sh                # ① 看 shebang：#! /bin/bash 的解释器在不在
command -v bash               # ② 解释器是否存在
cat -A run.sh | head -1       # ③ 行尾有没有 ^M$（Windows 传的 CRLF）？
file run.sh                   # ④ 架构对不对（x86 程序在 arm 机器上也会这样报）
ls -ld /home /home/alice      # ⑤ 路径上每层目录有没有执行位
```
| 原因 | 现象 | 修法 |
|---|---|---|
| 缺执行位 | 报 **Permission denied**（不是这个错误） | `chmod +x` |
| shebang 解释器不存在 | No such file | 改 shebang 或补解释器 |
| CRLF 行尾（`#!/bin/bash\r`） | No such file（找的是 `bash\r`） | `sed -i 's/\r$//' run.sh` |
| 架构/动态库不匹配 | No such file | 用正确架构的二进制 |

::: important 把"权限"和"存在性"分开
缺执行位 → Permission denied；文件/解释器真不存在或找不对 → No such file or directory。报错措辞帮你区分"有权限问题"还是"路径问题"。
:::

### 8.2 Permission denied 排查路径

```bash
ls -l target                  # ① 看权限串：属主/组/其他 rwx 够不够
id                            # ② 我是谁？我在哪些组？effective uid 是啥？
namei -l "$(readlink -f target)" # ③ 路径每层是否都有 x（目标存在时）
getfacl target                # ④ 有没有 ACL（ls 末尾有 + 就要查）
lsattr target                 # ⑤ immutable/append-only 等文件系统标志
getenforce                    # ⑥ SELinux：Enforcing 时查 ausearch -m avc
sudo dmesg | grep -i apparmor # ⑦ AppArmor 拦截（Ubuntu 系）
```
排查顺序的口诀：**属主 → 属组 → 其他 → 路径逐层 x → ACL（+号）→ 文件属性 → MAC（SELinux/AppArmor）**。云主机上"服务起不来、日志又正常"不应直接归因于 MAC，先用 `namei -l`、`getfacl` 和日志验证。

### 8.3 ls -l 权限位逐位读法总表

```
-rwxr-xr--+ 1 alice devteam 4096 Aug 10 10:00 file
  ││└┬┘└┬┘└┬┘ │
  ││ │  │  └──其他 r--         7 8 9 位
  ││ │  └─────组 r-x           4 5 6 位
  ││ └────────属主 rwx          1 2 3 位
  │└──────────特殊位：s/setuid、s/setgid、t/sticky（大小写见表）
  └───────────文件类型：-普通 d目录 l软链 b块设备 c字符设备 p管道
```
第 1、4、7 位的 s/S/t/T 特例（以属主位为例，组/其他同理）：

| 显示 | 含义 | 对应数字位 |
|---|---|---|
| `s` | setuid + 有 x | 4+1（4755 中的 4） |
| `S` | setuid 但**无 x**（异常） | 4 而已 |
| `t` | sticky + 有 x（/tmp） | 1 |
| `T` | sticky 但无 x（异常） | 1 而已 |

其它尾缀：`+` = 有 ACL，`.` = 有 SELinux 上下文（`ls -Z` 看标签）。数字三连读法：`-rwxr-xr--` = `(7)(5)(4)`。

### 8.4 find 与权限组合

```bash
find / -perm -4000 -type f 2>/dev/null        # 全系统 setuid 文件（-4000 = 命中 setuid 位）
find / -perm -2000 -type f                    # setgid 文件
find / -perm -0002 -type f 2>/dev/null        # 对"其他"可写的文件（安全审计常查）
find / -perm /022                             # 属组或其他任一写位命中（/ 表示任一命中）
find /srv -type f -perm -o+w -exec chmod o-w {} \;   # 找出并收回其他可写
```
::: note -perm 三种写法
`-mode` = 必须**全部**命中；`/mode` = **任一**位命中；`mode`（不带符号）= 必须**精确等于**。审计"危险文件"用 `-`，找"只要有一个危险位"用 `/`。
:::

文件还有扩展属性和文件系统标志：`getfattr/setfattr` 适合查看/设置 xattr，`getcap/setcap` 适合 file capabilities；`lsattr/chattr` 则检查/修改 ext2/3/4 等文件系统 flags（如 `i` immutable、`a` append-only）。本篇不重复展开，分别交叉阅读 [文件系统实操](/kb/os/Linux/03-Linux文件系统与磁盘实操/) 的 `lsattr/chattr` 章节与 [Linux 安全实操](/kb/os/Linux/06-Linux安全权限与审计/) 的 ACL、capabilities、auditd 章节。

审计关键文件变更可直接跳转：[安全防御与审计](/kb/os/安全/05-安全防御与审计/)（`auditctl` 定规则，`ausearch` 查明细，`aureport` 出报告）。`auditctl` 运行时规则重启会丢，生产环境应写 `/etc/audit/rules.d/*.rules` 并由 auditd 加载。

## 9. 本章小结

- 用户三件套：`useradd -m -s -G` 建号、`usermod -aG` 加组（**别忘 -a**）、`userdel -r` 清理；身份用 `id` 看 uid/gid/groups。
- 目录服务查询：`getent passwd/group/hosts/services` 遵循 `/etc/nsswitch.conf` 的 NSS 顺序；`groups` 看当前组，`newgrp` 仅在新 shell 刷新组身份；`gpasswd` 管成员，`groupmems` 仅在部分 shadow-utils 发行版可用。
- 账户校验与历史：`vipw/vigr` 防并发编辑，`pwck/grpck` 查本地数据库一致性；`last/lastb/lastlog` 查登录记录，`faillock` 是新 PAM 失败锁定工具，`pam_tally2` 主要是旧栈兼容命令。
- 账号数据库：`/etc/passwd` 7 字段（哈希放 shadow）、`/etc/shadow` 9 字段（`$算法$盐$哈希`），加盐抗彩虹表呼应 [认证加密](/kb/os/安全/02-身份认证与密码学基础/)。
- 权限：`chmod` 数字（r=4/w=2/x=1）/符号（u/g/o + +-/=）两套写法；`chown` 只有 root 能改属主；`umask` 决定新文件初始权限；目录要 r+x 才完整可用。
- 特殊位：`u+s`/`g+s`/`+t` 数字写 4/2/1；小写 s/t 有 x、大写 S/T 无 x；setuid 是最危险的提权，定期 `find / -perm -4000` 审计。
- `sudo` 是"自己密码 + 白名单 + 全审计"，优于裸 root；规则在 visudo 写 `user host=(runas) commands`，日志在 auth.log / secure。
- `runuser` 适合 root 启动服务账户命令，`setpriv` 可同时收窄 UID/GID、附加组和 capabilities，但二者都不是完整沙箱；`loginctl` 管理 systemd 会话，`namei -l` 逐层定位路径权限。
- 标准 rwx 不够用上 **ACL**（setfacl，注意 mask 与 chmod 的联动）；setuid 太粗用 **capabilities**。
- 排查口诀：属主 → 组 → 其他 → 路径逐层 x → ACL(+) → 文件属性 → SELinux；"No such file" 多查 shebang/CRLF，缺执行位才报 Permission denied。

## 10. 动手实验

1. **创建用户并授权**：`useradd -m -s /bin/bash -G sudo,docker alice`，`sudo passwd alice` 设密码，`id alice` 看组；再 `usermod -aG dev alice` 追加，对比不加 `-a` 的后果（别在生产机上试踢组）。
2. **chmod 数字转换练习**：写 8 个目标（如 `rwxr-x---`、`r-x--x--x`、`-rwxrwxr-x`），先在纸上转八进制，再用 `chmod` + `ls -l` 验证；补做 `chmod 1777`、`chmod 4755` 观察 ls 显示。
3. **setuid 实验**（虚拟机）：复制 `/bin/cat` 为 `/usr/local/bin/mysuid` 并 `chmod u+s`，切普通用户读 `/etc/shadow` 成功、原 cat 失败；演示后 `rm` 删除并 `find / -perm -4000` 复核。
4. **sudo 配置**：visudo 里给一个测试用户加 `NOPASSWD: /usr/bin/systemctl restart nginx`，用 `sudo -l` 验证；再执行并去 `/var/log/auth.log`（或 `/var/log/secure`）找到对应审计记录。
5. **ACL 授权**：建 `report.txt`，`setfacl -m u:alice:rw` 后用 alice/bob 两种身份验证读写差异，观察 `ls -l` 的 `+`；再 `chmod 600` 一次看 mask 如何吞掉 alice 的权限，最后 `setfacl -b` 清理。
6. **SELinux/权限检查**：`getenforce` 看状态；`find /tmp -perm /022 -type f` 找出可被他人写的文件；对一个只有 `r--` 的目录 `cd`，确认报 Permission denied，再 `chmod u+x` 观察行为变化。
7. **NSS 与路径排查**：分别执行 `getent passwd "$USER"`、`getent group "$(id -gn)"`、`getent hosts example.com`、`getent services ssh`；在测试目录用 `namei -l` 对比路径中某一级去掉 `x` 前后的报错。
8. **账户校验与登录失败**（测试机）：`vipw -s`/`vigr -s` 只查看后退出，运行 `pwck -r`/`grpck -r`；再用错误密码制造一次记录，用 `lastb -n 5`、`faillock --user "$USER"` 检查，确认后 `faillock --user "$USER" --reset`。
9. **降权执行**：用 `sudo runuser -u nobody -- id` 和 `setpriv --reuid=nobody --regid=nobody --init-groups -- id` 对比 UID/GID/组；用 `setpriv --dump` 记录当前能力，切勿把 `--preserve-environment` 用于不可信命令。

## 11. 自测题

1. **`useradd alice` 之后为什么用户可能没有家目录？** 不带 `-m` 时多数发行版只写入 `/etc/passwd` 字段不建目录，且默认 shell 可能不是 bash；加 `-m -s /bin/bash` 更符合预期。
2. **`usermod -G docker alice` 和 `-aG docker alice` 差别在哪？** 前者把 alice 从所有其他附加组移除只剩 docker，后者只追加；`-G` 必须配 `-a` 才是"追加"语义。
3. **`/etc/passwd` 第 2 字段为什么是 `x`？** 哈希被移到 `/etc/shadow`（只有 root 可读），passwd 里放占位符 `x`，避免任何用户可读的哈希被离线破解。
4. **`chmod 4755` 与 `chmod 0755` 的差别？** 高位的 4 是 setuid；`4755` 运行时会临时获得属主身份（如 passwd），`0755` 没有特殊位。
5. **为什么普通用户 `passwd` 能改密码？** passwd 是 setuid root 程序，执行时 effective uid 变 root，从而可写 `/etc/shadow`；这是 setuid 的经典正面案例。
6. **`/tmp` 权限 `drwxrwxrwt` 里最后一个 `t` 的意义？** sticky bit：所有用户可写但只能删自己属主的文件，防止互相删临时文件。
7. **`umask 022` 下 `touch f` 和 `mkdir d` 分别得到什么权限？为什么？** 常见请求 mode 下文件 0644、目录 0755；计算是 `0666 & ~0022`、`0777 & ~0022`，本质为清除掩码位，不是普通减法。
8. **对一个目录只有 `r--` 权限，`ls` 能看到文件却 `cat file` 报 Permission denied，为什么？** 目录 r 只允许列名字，访问文件内容需要目录的 x 执行权；无 x 时路径遍历被拒。
9. **`getent passwd alice` 为什么比 `grep alice /etc/passwd` 更可靠？** `getent` 经过 NSS，除了本地 files 还可查 SSSD/LDAP/NIS 等账户源；`grep` 只看本地文本且可能误匹配用户名或 GECOS 字段。
10. **`usermod -aG docker alice` 后当前终端为什么仍没有 docker 组？** supplementary groups 在进程创建时继承；重新登录，或在确认安全边界后用 `newgrp docker` 创建新 shell。
11. **`faillock` 和 `pam_tally2` 能互相替代吗？** 不能直接替代；前者对应较新的 `pam_faillock`，后者对应旧 `pam_tally2`，配置模块、数据库和发行版支持不同，先检查 PAM 栈。
12. **`runuser`、`sudo -u`、`setpriv` 如何选？** 需要 sudoers 授权和审计用 `sudo -u`；root 脚本切服务账户用 `runuser`；需要明确收窄组/能力且不要求认证时用 `setpriv`，但它不是完整隔离。
13. **文件是 0644，为什么仍然打不开？** 用 `namei -l` 查每一级父目录的 `x`，再用 `getfacl` 查 ACL、`lsattr` 查 immutable 等文件属性，并检查 SELinux/AppArmor。
