::: abstract 本章定位
讲透软件从哪来、怎么装、怎么卸、坏了怎么修：Debian 系 apt/dpkg、RHEL 系 dnf/yum/rpm 两条主线的完整命令链，加上源码编译、AppImage/Snap/Flatpak、update-alternatives 与 ldconfig。目标：拿到一台服务器就能判断"这软件用哪种方式装、装到哪、坏了怎么排"。
:::

软件安装是运维的第一课：装错体系、装坏依赖、锁文件卡死、软件源失效，每类坑后面都有清晰路径。本篇把 Debian 系（apt/dpkg）与 RHEL 系（dnf/rpm）两条主线平行对照着讲，命令真实可运行，排查方法论见 [排查方法论](/kb/os/问题排查/00-系统问题排查方法论/)，底层机制见 [Linux 实操](/kb/os/Linux/00-Linux实操学习路线/)。学习路线总览见 [Bash命令学习路线总览](/kb/os/Bash/00-Bash命令学习路线总览/)，装完软件要管服务则见 [服务管理与定时任务](/kb/os/Bash/12-服务管理与定时任务/)。

## 1. 包管理概念

### 1.1 什么是"包"（Package）

一个**软件包（package）**就是把"编译好的二进制程序 + 配置文件 + 文档 + 元数据"打包成一个文件。以 `.deb` 为例，`dpkg-deb -I` 能看到它的元数据：

```bash
dpkg-deb -I vim_8.2.3995-1ubuntu2_amd64.deb
# →  Package: vim
# →  Version: 8.2.3995-1ubuntu2
# →  Architecture: amd64
# →  Depends: vim-common, vim-runtime, libacl1, libc6 ...
```

::: note 包 = 二进制 + 元数据
`.deb` 使用 ar 容器；RPM 有自己的头和签名区，payload 通常是压缩后的 cpio 归档。里面是编译好的二进制、默认配置、man 文档，外加包名/版本/依赖/架构等元数据。dpkg/rpm 负责落盘，依赖求解主要由 apt/dnf/zypper 等前端完成。
:::

| 元数据字段 | 含义 | 排查用途 |
|---|---|---|
| `Package` | 包名（软件唯一标识） | `apt install vim` 用的就是这个 |
| `Version` | 版本号，`上游版本号-打包修订号` | 判断软件新旧、是否可回退 |
| `Architecture` | 架构（amd64/arm64/i386） | "安装失败 arch 不符"看这里 |
| `Depends` | 依赖包列表（可带版本约束） | 依赖损坏排查看这里 |
| `Conflicts` | 冲突包（装了它就不能共存） | 包冲突报错查这里 |

### 1.2 依赖管理：装一个包带起一串

包不是孤立的。`vim` 依赖 `libc6`，`libc6` 又依赖别的……包管理器根据 `Depends` 字段**递归解析依赖树**，自动把缺的包一起装上。三个常见词：

- **依赖（Depends）**：必须装上，缺了程序跑不起来。
- **冲突（Conflicts）**：与某包不能共存（常因文件名覆盖或库冲突）。
- **推荐（Recommends）**：多数发行版默认安装，可用 `--no-install-recommends` 关闭（生产/容器镜像常用，减少攻击面与磁盘）。

### 1.3 软件源（Repository）概念

软件源 = 发布包的**仓库服务器**。`apt update` 时客户端拉取仓库的**索引**（所有可用包的名称/版本/依赖清单），`apt install` 时再从仓库下载真正的包文件，并用源签名（GPG key）校验包没被篡改。

### 1.4 两大体系总览：.deb vs .rpm

| | Debian/Ubuntu 系 | RHEL/Rocky/Alma 系 |
|---|---|---|
| 包文件格式 | `.deb` | `.rpm` |
| 底层包工具 | `dpkg` | `rpm` |
| 前端包管理器 | `apt`（老：`apt-get`） | `dnf`（老：`yum`） |
| 软件源配置 | `/etc/apt/sources.list`、`.d` 目录 | `/etc/yum.repos.d/*.repo` |
| 常见发行版 | Debian、Ubuntu | CentOS、Rocky、Alma、Fedora |

::: warning 两份生态不通用
`.deb` 不能直接装到 RHEL 上，`.rpm` 也不能装到 Debian 上（除非用 alien 转换，但依赖库可能对不上）。先确认系统是哪系：`cat /etc/os-release`。
:::

### 1.5 root 权限需求

绝大多数包管理操作要写 `/usr/bin`、`/var/lib/dpkg` 等 root 所有目录，必须提权；查询与下载类则普通用户即可：

```bash
sudo apt install nginx              # 装到系统目录，必须 sudo
apt search nginx && apt show nginx  # 查询，不需要 root
apt download nginx                  # 仅下载到当前目录，不需要 root
```

源码编译到 `--prefix=$HOME` 也不需 root；`dpkg -l`/`-L`/`-S`/`-s` 查询同样免 sudo。**安装/删除/更新一律 `sudo`**。

## 2. Debian 系 apt

### 2.1 apt 常用操作

```bash
sudo apt update               # ① 从软件源拉取最新索引（必先做）
sudo apt upgrade              # ② 升级所有已装包
sudo apt full-upgrade         # ③ 升级并处理依赖变化（可能装/卸包）
sudo apt install nginx htop   # ④ 安装（可一次装多个）
sudo apt remove nginx         # ⑤ 卸载（保留配置文件）
sudo apt purge nginx          # ⑥ 卸载并删除配置文件
sudo apt autoremove           # ⑦ 清理无人再依赖的包
apt search "python3.*http"    # ⑧ 按名称/描述搜索
apt show nginx                # ⑨ 查看包详细信息
```

预期输出片段：

```
$ sudo apt update
Hit:1 http://archive.ubuntu.com/ubuntu jammy InRelease
All packages are up to date.

$ apt show nginx
Version: 1.18.0-6ubuntu14.4
Depends: libc6, libpcre3, zlib1g, ...
```

解读：`update` 只刷新**索引**（不升级任何软件），`upgrade` 才动软件；长期不 `update` 直接 `install`，会因索引过期装到旧版本或报 "Unable to locate package"。

### 2.2 apt 与 apt-get 的关系与差异

`apt-get` 是传统命令，`apt` 是 16.04+ 提供的**面向交互用户的整合前端**（进度条、彩色）。两者底层同一套机制，可混用：

| 场景 | apt-get | apt |
|---|---|---|
| 安装 | `apt-get install` | `apt install` |
| 升级 | `apt-get upgrade` | `apt upgrade` |
| 搜索/查看 | `apt-cache search`/`show` | `apt search`/`show` |
| 已装列表 | `dpkg -l` | `apt list --installed` |

::: note 脚本里用 apt-get
脚本中请用 `apt-get` 并加 `-y`、`-q`，避免交互提示挂住 CI；交互终端用 `apt` 体验更好。
:::

### 2.3 apt list 与缓存清理

```bash
apt list --installed | grep nginx    # 列出已装包并过滤
apt list --upgradable                # 有哪些包可升级
sudo apt clean                       # 清空 /var/cache/apt/archives 里的 .deb 缓存
```

解读：`apt list --installed` 输出形如 `vim/xenial,now 2:8.0.1453-1ubuntu1 amd64 [installed]`，末尾 `[installed]` 标注状态；缓存目录会在升级后堆积 `.deb`，`apt clean` 可腾出磁盘空间（排查磁盘满的常见操作）。

### 2.4 `apt-cache` / `apt policy`：看索引、候选版本与优先级

`apt-cache` 是面向脚本和诊断的索引查询工具，不会修改系统；`apt show/search` 更适合交互查看。

```bash
apt-cache policy nginx
apt-cache madison nginx                  # 各源可见的版本表（实现/源支持时）
apt-cache depends --recurse --no-recommends nginx
apt-cache rdepends --installed nginx      # 已安装包中谁依赖 nginx
apt-cache show nginx | grep -E '^(Package|Version|Depends|Description)'
```

预期输出片段：

```text
nginx:
  Installed: 1.24.0-2ubuntu7
  Candidate: 1.24.0-2ubuntu7.1
  Version table:
 *** 1.24.0-2ubuntu7.1 500
        500 http://archive.ubuntu.com/ubuntu noble-updates/main amd64 Packages
     1.24.0-2ubuntu7 100
        100 /var/lib/dpkg/status
```

`Installed` 是当前已装版本，`Candidate` 是按 APT pinning 选出的默认安装版本；左侧 `***` 标记已安装项，数字是优先级。`madison` 便于确认目标版本是否仍在索引中；`depends` 是正向依赖树，`rdepends` 是反向依赖，递归输出可能很大。`apt-cache` 读本地索引，索引未更新时结论可能过期。

```bash
apt policy nginx                           # apt 的简洁候选版本查询
grep -R . /etc/apt/preferences /etc/apt/preferences.d/ 2>/dev/null
```

`apt policy` 也会显示源和 pin 优先级。不要只看版本号，Debian 版本还包含 epoch、上游版本和 Debian revision；比较时交给 APT，不要用普通字符串排序。

### 2.5 `apt-mark hold/unhold`：控制自动升级

```bash
sudo apt-mark hold nginx                 # 将包标记为 hold
apt-mark showhold                        # 查看所有 hold 包
sudo apt-mark unhold nginx               # 解除 hold
apt-mark manual nginx                    # 标记为手动安装，避免 autoremove
apt-mark auto libfoo1                    # 标记为自动依赖
```

成功通常输出 `nginx set on hold` / `nginx was already not hold`；`apt-mark showhold` 只列包名。hold 会影响 `apt upgrade`/依赖解析，但管理员显式指定版本或某些强制操作仍可能改变它；长时间 hold 会积累安全更新，必须记录原因、版本和复查日期。它不是冻结文件，也不是安全补丁策略的替代品。

### 2.6 软件源配置与换源

配置文件层级：

| 路径 | 作用 |
|---|---|
| `/etc/apt/sources.list` | 主源文件（经典格式） |
| `/etc/apt/sources.list.d/*.list` | 追加源（docker、vscode 装完自己放这里） |
| `/etc/apt/keyrings/*.gpg` | 第三方源专用 keyring，配合源条目的 `signed-by=`（推荐） |
| `/etc/apt/trusted.gpg.d/*.gpg` | 全局信任 keyring；信任范围过大，不宜放无关第三方 key |

看当前源：`cat /etc/apt/sources.list`，输出如 `deb http://archive.ubuntu.com/ubuntu/ jammy main restricted universe multiverse`。逐列解读 `deb http://mirrors.aliyun.com/ubuntu/ jammy main`：`deb`（二进制包）vs `deb-src`（源码包）；URL 源地址；`jammy` 发行版代号（对应 Ubuntu 22.04）；`main` 官方免费、`restricted` 专有驱动、`universe` 社区维护、`multiverse` 含版权受限软件。

**换源**三步（Ubuntu 换阿里云镜像）：

```bash
sudo cp /etc/apt/sources.list /etc/apt/sources.list.bak   # ① 备份
sudo sed -i 's|archive.ubuntu.com|mirrors.aliyun.com|g' /etc/apt/sources.list  # ② 替换域名
sudo apt update                                           # ③ 换源后必须 update
```

添加 Ubuntu PPA 时可用 `add-apt-repository`：

```bash
sudo add-apt-repository ppa:deadsnakes/ppa
sudo apt update
sudo add-apt-repository --remove ppa:deadsnakes/ppa
sudo add-apt-repository 'deb [arch=amd64 signed-by=/etc/apt/keyrings/vendor.gpg] https://repo.example stable main'
```

它会写入 `/etc/apt/sources.list.d/`，PPA 还可能导入签名密钥；`--remove` 删除对应源配置。Ubuntu/Debian 的 PPA 生态不同，Debian 通常直接写 `deb` 源；服务器上不要为了一个小工具盲目添加个人 PPA，先确认发行版代号、架构、维护者和密钥来源。第三方源推荐使用专用 `/etc/apt/keyrings/vendor.gpg` 配合 `signed-by=` 限定信任范围，不要把任意公钥放入全局 trusted keyring；`apt-key` 已废弃。

### 2.7 apt-file：查文件属于哪个包

`apt install` 常报 "E: Unable to locate package" 或二进制找不着，用 `apt-file` 反查：

```bash
sudo apt install apt-file          # 先装工具本身
sudo apt-file update               # 更新文件索引（体积大，须 sudo）
apt-file search /usr/bin/ffprobe   # 查 ffprobe 属于哪个包
# →  ffmpeg: /usr/bin/ffprobe
```

解读：`apt-file search <文件>` 输出 `包名: 完整路径`。Ubuntu 也提供在线版 `packages.ubuntu.com`；Debian 用 `packages.debian.org`。二进制被删、被换路径时的反查利器。

### 2.8 apt 与 dpkg 的关系：前端与后端

- **dpkg** 是**底层**工具：只会"这一个包装到系统里"，不理解依赖、不知道软件源在哪。`dpkg -i x.deb` 缺依赖会直接失败。
- **apt** 是**上层前端**：负责解析依赖、连接软件源、自动补齐缺失的包，最终调 dpkg 落盘。

所以 `apt` 的报错往往带出 `dpkg: error processing package ...` 的字眼——那是后端出错了，修 dpkg 状态直接用 dpkg（见第 3 节）。

### 2.9 包签名、GPG 与离线下载

APT 的安全链至少包括：仓库发布的 `InRelease`/`Release.gpg` 签名、仓库元数据中记录的包校验和、下载 `.deb` 后的校验。不要把“`sha256sum` 一致”误当成“来自可信发布者”；摘要文件本身也必须来自可信签名链。

```bash
apt download nginx                         # 当前目录下载，不安装、不需 root
sudo apt-get --download-only --reinstall install nginx
apt-get indextargets                        # 查看 APT 需要的索引目标
sha256sum nginx_*.deb
dpkg-deb -I nginx_*.deb | grep -E '^( Package| Version| Architecture| Depends)'
```

`apt download` 只取得目标包，通常不会自动把依赖全部下载；`--download-only` 让 APT 按依赖解析但不解包安装，下载位置受 APT 配置影响。完全离线前，应在同版本、同架构且索引已更新的联网机执行：

```bash
mkdir -p /tmp/deb-cache && cd /tmp/deb-cache
apt-get download nginx nginx-common
apt-rdepends nginx | awk '/^[A-Za-z0-9][A-Za-z0-9+.-]*$/' | xargs -r apt download
sha256sum *.deb > SHA256SUMS
# 传输 deb + 可信来源的源签名/校验资料；离线机上先校验，再：
sudo apt install ./*.deb
```

`apt-rdepends` 是额外工具，输出包含版本关系和 `Depends`/`Recommends` 细节，简单 `xargs` 示例仍需人工检查虚拟包、`:any`、源版本和架构；更稳妥的是为离线环境制作内部镜像或使用 `apt-offline`。离线机的 `apt install ./*.deb` 仍可能提示缺依赖，先用 `dpkg-deb -I`、`apt-cache policy` 和目标系统架构核对，不要用 `--force-depends` 硬装。

上游直接发布 tarball/AppImage 时，用 detached signature 校验发布者：

```bash
gpg --show-keys --with-fingerprint publisher.asc   # 先经独立可信渠道核对完整指纹
gpg --import publisher.asc
gpg --verify app-1.2.3.tar.gz.asc app-1.2.3.tar.gz
# gpg: Good signature from "Example Release Key ..."
sha256sum app-1.2.3.tar.gz                           # 可再与签名清单比对
```

`Good signature` 只表示签名与**已导入的那把公钥**匹配；若公钥和软件都从同一个被劫持页面下载，验证仍可能“成功”。必须通过发行版 keyring、项目官网的独立渠道或管理员配置核对完整 fingerprint，并关注密钥撤销/过期。APT 通常签的是仓库 Release 元数据，再用其中的摘要保护 `.deb`，并不要求每个 `.deb` 都自带 OpenPGP 签名。

## 3. dpkg

### 3.1 主要参数

| 参数 | 含义 | 示例 |
|---|---|---|
| `-i` | 安装本地 .deb 文件 | `sudo dpkg -i vim.deb` |
| `-r` | 卸载（remove，留配置） | `sudo dpkg -r vim` |
| `-P` | 彻底卸载（purge，删配置） | `sudo dpkg -P vim` |
| `-l` | 列出已装包（可带模式） | `dpkg -l \| grep nginx` |
| `-L` | 列出某包安装的全部文件 | `dpkg -L nginx` |
| `-S` | 查某个文件属于哪个包 | `dpkg -S /etc/nginx/nginx.conf` |
| `-s` | 查看包的状态/详细信息 | `dpkg -s nginx` |
| `-c` | 查看 .deb 包里的文件清单（不安装） | `dpkg -c x.deb` |

预期输出：

```
$ dpkg -i vim_8.2_amd64.deb
Unpacking vim (8.2.3995-1ubuntu2) over (8.1) ...
Setting up vim (8.2.3995-1ubuntu2) ...

$ dpkg -S /usr/bin/ffprobe
ffmpeg: /usr/bin/ffprobe

$ dpkg -c python3_3.10.deb
-rwxr-xr-x root/root     12345 2022-01-01 00:00 ./usr/bin/python3.10
```

解读：`-l` 第一列是状态码（`ii`=正常已装，`rc`=已卸但留配置，`un`=未装，详见 3.3）；`-S` 反查"文件→包"，`-L` 正查"包→文件"；`-c` 在**安装前**预览包会往系统放哪些文件，装陌生 .deb 前必查。

### 3.2 dpkg -i 依赖问题的处理

`dpkg -i` 不懂依赖，直接装缺依赖的包会失败：

```bash
sudo dpkg -i xxx.deb
# →  dpkg: dependency problems prevent configuration of xxx:
# →   xxx depends on libfoo1 (>= 2.0); however:
# →    Package libfoo1 is not installed.
```

解决套路（两选一）：`sudo apt -f install` 让 apt 补装缺失的依赖并修复（最常见）；或 `sudo apt install ./xxx.deb` 直接用 apt 装本地 deb，自动解析依赖。

::: tip 装本地 deb 优先用 `apt install ./pkg.deb`
它会像装仓库包一样自动拉依赖，比裸 `dpkg -i` + `apt -f install` 两步省事。命令里的 `./` 不能省，否则 apt 会去源里找名为 `pkg.deb` 的包。
:::

### 3.3 dpkg 状态：rc 残留态与 -P 清理

```bash
dpkg -l | grep ^rc           # 找出已卸载但留着配置文件的包
# →  rc  nginx  1.18.0-6ubuntu14.4  amd64  high performance web server
sudo dpkg -P nginx           # 彻底清理（删配置文件）
```

解读：第一列两位状态码，第二位固定 `i` 表示"安装意图"，第一位表示实际状态：`ii` 装好、`rc` 已删但配置残留、`un` 未安装、`iU` 解包未配置（升级中断）。批量清理：`dpkg -l | awk '/^rc/ {print $2}' | xargs sudo dpkg -P`。

### 3.4 与 apt 的联动

```bash
sudo dpkg --configure -a      # 修复"解包/升级中断"的包（常见于断电、apt 被杀）
dpkg -l | grep ^iU            # 找出解包未配置的包
```

规律：**apt 报 dpkg 的错，先用 `dpkg --configure -a` 修 dpkg，再用 `apt -f install` 补依赖**。这个先后顺序在排障实战（第 8 节）会反复出现。

### 3.5 `dpkg-query`：脚本化读取包数据库

```bash
dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\n' nginx
dpkg-query -W -f='${binary:Package}\t${db:Status-Status}\n'
dpkg-query -S /usr/bin/ssh
dpkg-query -L nginx
```

预期输出：

```text
nginx:amd64	1.24.0-2ubuntu7.1	amd64
nginx:amd64	installed
openssh-client:amd64	/usr/bin/ssh
```

`-W/--show` 查询包，`-S/--search` 按文件反查，`-L/--listfiles` 列安装文件，`-f/--showformat` 用 `${binary:Package}`、`${Version}`、`${Architecture}`、`${db:Status-Status}` 等变量生成稳定字段。相比解析 `dpkg -l` 的表格，`dpkg-query -W -f` 更适合脚本；`dpkg-query -W` 对不存在的包返回非零，脚本需检查退出码。只读查询一般不需 root。

### 3.6 `debsums`：Debian 文件摘要核验

```bash
sudo apt install debsums
debsums -c nginx                    # 把摘要变化的文件列到 stdout
debsums -s nginx                    # 静默正常项，只报告错误
debsums -a nginx                    # 包含配置文件（通常默认跳过配置）
debsums -e nginx                    # 只查配置文件
sudo debsums -ca                    # 全部已安装包，包含配置文件
debsums -l                           # 列出没有 md5 清单的包
```

典型输出：`/usr/sbin/nginx FAILED`、`debsums: missing file /usr/share/...`；没有输出不代表系统干净，只表示已记录 md5 的文件没有发现差异。`-c` 列变化，`-s` 只报告错误，`-a` 包含配置文件，`-e` 仅配置文件，`-l` 列无清单包；`-m FILE` 是从指定 md5 清单读取，并不是“列缺失文件”。不是所有包都附带 md5sums，`debsums` 会跳过无清单项目。配置被管理员修改通常是预期的，程序文件变更更值得调查；重新安装前先留存现场和哈希，别把取证证据覆盖掉。RPM 系统对应 `rpm -V`，不是 `debsums`。

## 4. RHEL 系 yum/dnf

### 4.1 dnf 常用操作

dnf（Dandified Yum）是 RHEL 8+/Fedora 的默认包管理器，是 yum 的下一代重写：

```bash
sudo dnf update                       # 升级所有包（也做索引同步）
sudo dnf install nginx htop           # 安装（可多个）
sudo dnf remove nginx                 # 卸载
sudo dnf search "http server"         # 搜索（匹配名称/描述）
sudo dnf info nginx                   # 查看包详细信息
sudo dnf list installed               # 列出已装包
sudo dnf repolist                     # 列出已启用软件源
sudo dnf provides /usr/bin/ffprobe    # 反查文件属于哪个包
```

预期输出片段：

```
$ sudo dnf install nginx
Dependencies resolved.
Installing:
 nginx     x86_64 1:1.20.1-14.el9   appstream    537 k
Installing dependencies:
 libunistring x86_64 0.9.10-15.el9  baseos      512 k
Is this ok [y/N]:
```

解读：dnf 和 apt 一样会先展示依赖解析结果再询问；`dnf repolist` 输出 `id / name / 启用数`，确认源状态。搜索/信息/列表是只读操作，多数情况不需 sudo。

### 4.2 软件源：/etc/yum.repos.d/

RHEL 系的源是一个个 `.repo` 文件：

```bash
cat /etc/yum.repos.d/rocky.repo
# →  [rocky]              ← 源 ID（唯一，dnf repolist 第一列）
# →  baseurl=http://mirror.rocky/.../baseos ← 包服务器地址
# →  enabled=1  gpgcheck=1  gpgkey=file:///etc/pki/rpm-gpg/RPM-GPG-KEY-rockyofficial
sudo dnf install epel-release     # 装 EPEL 源（Extra Packages for Enterprise Linux）
```

| 关注点 | 说明 |
|---|---|
| RHEL 订阅 | RHEL 本体源需订阅（subscription-manager）；CentOS/Rocky/Alma 免费无需订阅 |
| EPEL | Fedora 社区维护的"免费附加源"，大量常用软件（htop、tmux）都在 EPEL |

### 4.3 dnf vs yum

| 维度 | yum | dnf |
|---|---|---|
| 时代 | RHEL 7/CentOS 7 | RHEL 8+/Fedora（默认） |
| 实现 | Python 2 老架构 | 基于 libsolv 重写，依赖解析更快 |
| 回滚能力 | 弱 | `dnf history undo` 支持 |

::: note 兼容技巧
RHEL 8 上 `yum` 是指向 `dnf` 的软链接，写脚本用 `dnf` 兼容新旧；遇到只有 yum 语法的老教程，多半命令照搬也能跑。
:::

### 4.4 dnf provides 与 dnf history

```bash
sudo dnf provides /usr/bin/ffprobe   # 反查哪个包提供该文件
# →  ffmpeg-free-4.4.4-7.el9.x86_64 : Compatibility version...
sudo dnf history                     # 列出事务 ID、时间、操作、包数
sudo dnf history undo 7              # 回滚第 7 次事务
```

::: tip dnf history 是"后悔药"
升级把服务搞挂后，`dnf history undo <事务ID>` 会尝试反向执行那次包事务，比手工逐包找版本方便；但旧包已从仓库移除、模块流变化或 scriptlet 已改业务数据时，回滚可能失败或不能恢复应用数据。执行前先看 `dnf history info &lt;ID&gt;` 和备份，deb 系则用 `apt install pkg=旧版本` 明确回退。
:::

### 4.5 `dnf module`：RHEL 模块流

RHEL 8/9、Rocky/Alma 的 AppStream 可让同一个软件提供多个生命周期不同的 stream：

```bash
dnf module list nodejs
dnf module info nodejs:20
sudo dnf module enable nodejs:20
sudo dnf module install nodejs:20/common
sudo dnf module reset nodejs
sudo dnf module disable nodejs
```

典型输出：

```text
Name    Stream  Profiles          Summary
nodejs  18 [d]  common [d], dev  Javascript runtime
nodejs  20 [e]  common [d], dev  Javascript runtime
```

`[d]` 是默认 stream/profile，`[e]` 是已启用。`list/info` 查询，`enable stream` 只选流不一定安装包，`install stream/profile` 选流并安装 profile，`reset` 回到初始状态，`disable` 禁止该模块提供内容。切换 stream 可能涉及 `distro-sync`、卸包或应用数据迁移，不要在生产库上直接改。Fedora 已逐步退出 Modularity，较新 Fedora 上可能无 `dnf module` 数据；此命令主要面向企业 RPM 发行版的 AppStream。

### 4.6 `dnf repoquery` / `repoquery`：仓库元数据查询

```bash
dnf repoquery nginx                         # 所有匹配 NEVRA
dnf repoquery --installed nginx             # 仅已安装
dnf repoquery --available --latest-limit 1 nginx
dnf repoquery --requires --resolve nginx     # 依赖能力及提供包
dnf repoquery --whatrequires 'libssl.so.3()(64bit)'
dnf repoquery -l nginx                       # 包文件列表，不必安装
```

输出如 `nginx-1:1.24.0-2.el9.x86_64`，依次包含 name、epoch、version、release、arch（NEVRA）；`--requires --resolve` 会把能力映射为候选包，可能返回多个提供者。DNF4 常需安装 `dnf-plugins-core` 才有完整插件命令；DNF5 的选项布局有变化，以 `dnf repoquery --help` 为准。

RHEL/CentOS 7 的 `yum-utils` 提供独立 `repoquery`：

```bash
repoquery --requires --resolve nginx
repoquery --whatprovides '/usr/bin/ffprobe'
repoquery -l nginx
```

独立 `repoquery` 读 yum 仓库元数据，语法与 `dnf repoquery` 高度相似但并非完全一致；脚本不要仅因命令同名就假设参数通用。

### 4.7 `yumdownloader` / `dnf download`：只下载与离线准备

```bash
sudo dnf install dnf-plugins-core
dnf download --destdir /tmp/rpms nginx
dnf download --resolve --alldeps --destdir /tmp/rpms nginx
dnf download --source nginx                 # 需要启用源码仓库

sudo yum install yum-utils                  # RHEL/CentOS 7
yumdownloader --destdir=/tmp/rpms nginx
yumdownloader --resolve --destdir=/tmp/rpms nginx
yumdownloader --urls nginx                  # 只打印下载 URL
```

成功会显示 `nginx-...rpm 100%` 并把文件写入目标目录。`--resolve` 下载解析到的依赖；`--alldeps` 让 DNF 即使本机已安装也下载依赖，更适合准备另一台离线机。依赖集合必须以**目标机相同发行版、版本、架构、模块流和仓库状态**解析，否则离线安装仍会失败。传输后先 `rpmkeys --checksig /tmp/rpms/*.rpm`，再在离线机使用 `sudo dnf install /tmp/rpms/*.rpm`；不要用 `rpm --nodeps` 绕过依赖。

## 5. rpm

### 5.1 主要参数

rpm 是 RHEL 系**底层**包工具，与 dnf 的关系 = dpkg 与 apt 的关系（dnf 是前端，rpm 是后端）。日常装删用 dnf，**查询与校验**（`rpm -qa`/`-qf`/`-V`）直接调 rpm 更顺手：

| 参数 | 含义 | 示例 |
|---|---|---|
| `-ivh` | 安装本地 .rpm（i=install v=显示过程 h=进度条） | `sudo rpm -ivh nginx.rpm` |
| `-e` | 卸载 | `sudo rpm -e nginx` |
| `-qa` | 列出所有已装包 | `rpm -qa \| grep nginx` |
| `-ql` | 列出包安装的文件 | `rpm -ql nginx` |
| `-qf` | 反查文件属于哪个包 | `rpm -qf /etc/nginx/nginx.conf` |
| `-qi` | 查看包详细信息 | `rpm -qi nginx` |
| `-q --scripts` | 查看包安装/卸载脚本 | `rpm -q --scripts nginx` |
| `-V` | 校验已装文件是否被改过 | `rpm -V nginx` |

预期输出：

```
$ rpm -ivh nginx.rpm
   1:nginx-1.20.1-14.el9              ################################# [100%]

$ rpm -qf /etc/nginx/nginx.conf
nginx-1.20.1-14.el9.x86_64

$ rpm -q --scripts nginx
postinstall scriptlet (using /bin/sh):
  # 创建用户、写日志目录、启动服务等
```

解读：`rpm -qa` 输出格式是 `名称-版本-发行版.架构`；`-qf` 反查文件来源（对应 dpkg -S）；`-q --scripts` 显示安装后自动运行的脚本，安装前可预判副作用。

### 5.2 rpm -V 校验

```bash
rpm -V nginx                # 校验 nginx 装的文件是否被改动
# →  S.5....T.  c /etc/nginx/nginx.conf   ← c 标记配置文件，改动属正常
rpm -Vf /usr/sbin/sshd      # 校验某个文件属于的包
```

::: warning 校验字符的读法
九列依次表示 S(大小)、M(模式/权限)、5(摘要)、D(设备号)、L(符号链接)、U(属主)、G(属组)、T(mtime)、P(capabilities)。`.` 表示没变；后面的 `c` 表示配置文件——配置文件变化常有合理原因，**程序文件变化更可疑，但两者都要结合变更记录判断**。
:::

### 5.3 `rpm2cpio` + `cpio`：不安装就检查 RPM 内容

```bash
rpm2cpio nginx.rpm | cpio -t                 # 只列文件清单
mkdir /tmp/rpm-root
rpm2cpio nginx.rpm | (cd /tmp/rpm-root && cpio -idmv --no-absolute-filenames)
rpm -qp --scripts nginx.rpm                   # 安装前审查 scriptlet
rpm -qip nginx.rpm                            # 包元数据
```

`rpm2cpio` 将 RPM payload 转为 cpio 流；`cpio -t` 只列目录，`-i` 解包，`-d` 建目录，`-m` 保留时间，`-v` 显示路径。输出如 `./usr/sbin/nginx`、`./etc/nginx/nginx.conf`，末尾 `12345 blocks` 是处理的数据块数，不是文件数。

::: warning 在专用目录解包不可信 RPM
不要在 `/` 或工作树根目录执行 `cpio -id`，否则可覆盖同名文件。现代 GNU cpio 默认会拒绝绝对路径和 `..`，仍应使用空目录、普通用户和 `--no-absolute-filenames`；解包只取 payload，不会执行 RPM scriptlet，但后续打开解析器可利用的文件仍需隔离。
:::

### 5.4 RPM 签名、导入密钥与完整性

```bash
rpmkeys --checksig --verbose nginx.rpm
# nginx.rpm: digests signatures OK
rpm -Kv nginx.rpm                            # 常见兼容写法
rpm -qa 'gpg-pubkey*'                        # 已导入的 RPM 公钥
rpm -qi gpg-pubkey-&lt;id&gt;-&lt;buildtime&gt;          # 查看指纹/来源信息
sudo rpm --import /etc/pki/rpm-gpg/RPM-GPG-KEY-redhat-release
rpm -V nginx                                  # 安装后与 RPM 数据库元数据比对
```

`OK` 只说明签名可由**当前 keyring 中某把密钥**验证，还要从发行版可信渠道核对完整指纹；不要根据下载包旁边同站点提供的未知 key 就直接信任。`rpm -V` 验证安装后文件的摘要、权限、属主等，和签名解决的问题不同：前者查“落盘后是否变化”，后者查“包是否由可信密钥签发”。旧 RPM 可能使用 SHA-1 等弱算法并在新系统被策略拒绝，正确做法是换受支持的新包，不是关闭 crypto policy。

## 6. openSUSE 与 Arch Linux

### 6.1 `zypper`：openSUSE/SLES

```bash
sudo zypper refresh                       # 刷新仓库元数据
zypper repos -u                            # 仓库 ID、启用状态、优先级、URL
zypper search -s nginx                     # 搜索并显示版本/仓库
zypper info nginx
sudo zypper install nginx
sudo zypper remove nginx
sudo zypper update                         # 常规包更新
sudo zypper dup                            # distribution upgrade，可能切换厂商/降级，慎用
zypper what-provides /usr/sbin/nginx
sudo zypper addrepo -f -p 90 URL alias
sudo zypper removerepo alias
sudo zypper addlock nginx && zypper locks
sudo zypper removelock nginx
```

`search` 输出状态列：`i` 表示已安装，`i+` 表示用户显式安装，`v` 表示另一个版本；`repos -u` 的较小 priority 数字优先级更高。`dup` 用于 Tumbleweed 快照或发行版升级，不等于普通 `update`，会按目标仓库做 vendor/依赖同步；远程生产机先 `zypper dup --dry-run` 审查事务。SLES 仓库还受 SCC/订阅注册控制。

### 6.2 `pacman`：Arch/Manjaro 基础实用链

```bash
sudo pacman -Syu                         # 同步数据库并完整升级
pacman -Ss nginx                         # 远端搜索
pacman -Si nginx                         # 远端包信息
pacman -Qi nginx                         # 已安装包信息
sudo pacman -S nginx                     # 安装/重装
sudo pacman -Rns nginx                   # 删除、无用依赖和配置备份记录，先审查列表
pacman -Ql nginx                         # 包 → 文件
pacman -Qo /usr/bin/ssh                  # 文件 → 已装包
pacman -F /usr/bin/ffprobe               # 仓库文件数据库反查（首次先 pacman -Fy）
pacman -Qkk nginx                        # 检查已装文件存在性/元数据，不是内容哈希全检
pacman -Qdt                              # 孤儿依赖
```

`-S` 同步仓库，`-Q` 查本地数据库，`-R` 删除，组合短选项需逐字理解。Arch 是滚动发行版，**不支持 partial upgrades**：不要长期只运行 `pacman -Sy` 后单装包，因为本地索引与已装库可能错配；标准升级用 `pacman -Syu`。签名由 pacman-key keyring 与仓库数据库保证，遇到签名错误先校时钟、更新 `archlinux-keyring` 并查官方公告，不要使用 `SigLevel = Never`。

## 7. 源码编译安装

### 7.1 configure / make / make install 三步骤

当软件源里没有、或想要最新版/定制编译参数时，就用源码安装：

```bash
wget https://example.com/app-1.2.3.tar.gz
tar xzf app-1.2.3.tar.gz && cd app-1.2.3
./configure --prefix=/usr/local     # ① 检查环境 + 生成 Makefile
make -j$(nproc)                     # ② 编译（-j 并行，nproc 取 CPU 核数）
sudo make install                   # ③ 安装到 /usr/local（写系统目录才要 sudo）
```

三步各干什么：`./configure` 探测编译器/库/头文件并生成 `Makefile`（失败报 `checking for ... not found`）；`make` 真正编译出二进制（缺头文件报 `error: 'X' undeclared`）；`make install` 把产物复制到目标路径（忘 sudo 报 `Permission denied`）。

::: note 没 configure 怎么办
有的项目使用 CMake/Meson，有的直接提供 Makefile。先看 `README`、`CMakeLists.txt`、`meson.build` 等构建入口和项目声明的最低工具版本，不要硬套三步骤。
:::

### 7.2 ./configure --prefix= 与依赖检查

`--prefix` 指定安装路径（默认 `/usr/local`）：`--prefix=/usr/local/app` 装指定目录、`--prefix=$HOME/apps` 装用户目录（不需 sudo）、`--prefix=/opt/app` 装 /opt（隔离应用常见选择）。`configure` 主要干两件事：**探测依赖** 和 **生成 Makefile**。常见失败与对策：

```bash
./configure
# →  checking for gcc... not found
sudo apt install build-essential        # deb 系补 gcc/g++/make 全套
# →  checking for libpcre2... not found
sudo apt install libpcre2-dev           # 缺头文件 → 装 -dev 开发包
```

::: important 缺"开发包"是最高频坑
运行时缺库报 `libfoo.so not found`（装 `libfoo1` 即可）；编译时缺的是**头文件和链接库**，要装 `libfoo-dev`（RHEL 系是 `libfoo-devel`）。
:::

### 7.3 `cmake` / `ninja`：现代 out-of-source 构建

```bash
cmake -S . -B build -G Ninja \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_INSTALL_PREFIX=/opt/myapp
cmake --build build --parallel "$(nproc)"
ctest --test-dir build --output-on-failure
sudo cmake --install build

ninja -C build -n                    # dry-run：只显示会执行什么
ninja -C build -v                    # 显示完整编译/链接命令
ninja -C build -j 4                  # 限制并行度
```

配置成功会出现 `-- Configuring done`、`-- Generating done` 和 `Build files have been written to: .../build`；Ninja 成功输出 `[N/N] Linking ...`。`-S/-B` 把源码与构建产物分开，删 `build/` 即可干净重配；`-G Ninja` 需要安装 `ninja-build`（Debian/RHEL 包名通常如此，Arch/openSUSE 常为 `ninja`）。`cmake --build`/`--install` 是跨生成器接口，脚本比直接写 `ninja` 更通用。

不要用 sudo 配置或编译，否则 build 树会混入 root 属主；只在安装前缀确实需要时对 `cmake --install` 提权。`CMAKE_BUILD_TYPE` 对 Ninja/Unix Makefiles 这类 single-config 生成器有效，多配置生成器需在 build/install 时用 `--config Release`。安装陌生项目之前先看 `cmake --install build --prefix /tmp/stage` 或使用 `DESTDIR` 做 staging，审查将写入的文件。

### 7.4 `pkg-config`：查询头文件与链接参数

```bash
pkg-config --modversion openssl
pkg-config --cflags --libs openssl
pkg-config --variable=pc_path pkg-config
PKG_CONFIG_PATH=/opt/myapp/lib/pkgconfig pkg-config --cflags --libs mylib
pkg-config --exists 'openssl >= 3.0' && echo compatible
```

典型输出：`-I/usr/include/openssl -lssl -lcrypto`；`--modversion` 输出 `.pc` 元数据声明的版本。`pkg-config` 不安装包，也不验证库 ABI，只读取搜索路径中的 `.pc` 文件并展开 `Cflags/Libs/Requires`；报 `Package foo was not found` 时应安装开发包并检查 `.pc` 的目录，而不是盲目加 `-I/-L`。

`PKG_CONFIG_PATH` 是在默认路径前追加，交叉编译通常用 `PKG_CONFIG_LIBDIR`/`PKG_CONFIG_SYSROOT_DIR` 隔离目标 sysroot。不要把不可信可写目录永久加入全局搜索路径，否则构建可能链接攻击者伪造的参数或库。

### 7.5 make -j 与 make uninstall 的坑

```bash
make -j$(nproc)                # nproc 是 CPU 核数，多核并行编译快数倍
```

::: warning make uninstall 不保证存在
很多项目**根本没有写 uninstall 规则**，`make uninstall` 只清 `make install` 记录过的文件，不保证清配置/日志/用户。编译安装前想清楚怎么卸载，或用 7.7 的 `checkinstall` 做成包。
:::

### 7.6 /usr/local 与 PATH 问题

源码默认装到 `/usr/local`，二进制在 `/usr/local/bin`。多数发行版 PATH 已含它，但最小化系统不一定：

```bash
which app          # 找不到？先看 PATH
echo $PATH         # /usr/local/bin 在不在里面？
echo 'export PATH="$PATH:/usr/local/app/bin"' >> ~/.bashrc   # 永久加（重开 shell 生效）
```

::: tip 装到 /opt 还是 /usr/local
隔离/自包含应用推荐 `/opt/<应用名>`（不污染系统目录，删除时 `rm -rf /opt/app` 即卸载），但必须手动把 bin 加进 PATH；装 `/usr/local` 则多数发行版默认在 PATH 里。
:::

### 7.7 checkinstall 制作包

把编译好的程序打包成系统包，享受包管理的卸载/升级：

```bash
sudo apt install checkinstall
./configure && make                    # 先 configure + make（别 make install）
sudo checkinstall                      # 交互式问包名/版本，自动替代 make install
```

解读：checkinstall 拦截 `make install` 复制文件的动作，生成 `.deb`/`.rpm` 并注册进包数据库——之后就能 `sudo apt remove myapp` 像普通包一样卸载。

### 7.8 编译 vs 包管理选型表

| 场景 | 推荐方式 | 理由 |
|---|---|---|
| 系统自带的老版本够用 | 包管理器 | 安全补丁自动跟随、卸载干净 |
| 要特定新版本/上游特性 | 官方 .deb/.rpm 或 ppa/源 | 依旧走依赖管理 |
| 最新开发版/魔改编译参数 | 源码编译 | 只有源码满足 |
| 大量自编译软件要管理 | checkinstall 打包 | 有包管理的卸载能力 |
| 纯 GUI 工具（Chrome/VSCode） | 官方安装包/AppImage | 自带依赖，不污染系统 |

## 8. 其他安装方式

### 8.1 AppImage / Snap / Flatpak：分发与隔离差异

三者都主打"自带依赖、免安装、不污染系统"，适合桌面应用：

| | AppImage | Snap | Flatpak |
|---|---|---|---|
| 形态 | 单个可执行文件，chmod +x 即用 | snapd 守护进程 + squashfs 快照 | OSTree 应用 + runtime + 沙箱 |
| 隔离 | 默认无强制沙箱 | strict 有隔离，classic 基本绕过隔离 | bubblewrap 沙箱，权限由 manifest/override 决定 |

```bash
./app.AppImage                    # 直接运行（先 chmod +x）
file app.AppImage && sha256sum app.AppImage

snap find code
snap info code                     # 发布者、channels、版本、confinement
sudo snap install code --channel=stable
snap list && snap connections code
sudo snap refresh code --channel=stable
sudo snap revert code              # 回退到保留的上一 revision
sudo snap remove --purge code

flatpak remote-add --if-not-exists flathub https://flathub.org/repo/flathub.flatpakrepo
flatpak search vim
flatpak install flathub org.vim.Vim
flatpak run org.vim.Vim
flatpak info --show-permissions org.vim.Vim
flatpak list --app && flatpak update
flatpak uninstall --delete-data org.vim.Vim
flatpak uninstall --unused          # 清理无人使用的 runtime
```

Snap 的 channel 通常写成 `track/risk/branch`（如 `latest/stable`）；`classic` 包安装时需显式 `--classic`，意味着它拥有接近传统包的主机访问能力。`snap connections` 的 `Plug/Slot` 能看接口是否连接，`snap changes`/`snap tasks &lt;ID&gt;` 用于排查卡住的事务。Snap 依赖 systemd/snapd，部分发行版默认不提供；自动 refresh 是其设计的一部分，长期 hold 仅应作为维护窗口而非永久冻结。

Flatpak 可按系统或 `--user` 安装；应用 ID（如 `org.vim.Vim`）比显示名可靠。`info --show-permissions` 展示 socket、device、filesystem 等静态权限，但运行中通过 portal 授权的数据也需结合 `flatpak permission-show`/桌面设置审查；可用 `flatpak override --show APPID` 查看本地覆盖。沙箱不等于可信，第三方 remote 和 broad filesystem/device 权限仍可能暴露数据。

离线 Snap 可在联网机执行 `snap download &lt;name&gt;` 获得 `.snap` 和 `.assert`，离线机先 `sudo snap ack <file.assert>` 再 `sudo snap install <file.snap>`；缺少 assertion 时的 `--dangerous` 会绕过签名验证，不应作为常规安装方式。Flatpak 应准备包含 runtime 的本地 OSTree 仓库、USB sideload repo 或签名 bundle，再由离线机 `flatpak install`；只复制应用目录会漏 runtime/元数据。大规模离线环境更适合维护受信任的内部 mirror。

### 8.2 pip / npm 的 -g 全局安装

Python/Node 的包管理器也能全局装可执行工具，但会污染系统环境：

```bash
sudo pip install httpie           # 装到系统 Python（/usr/local/bin/httpie）——慎用
npm install -g nodemon            # -g = 全局，装到全局 node_modules
```

::: warning pip 全局安装会污染系统 Python
系统 Python 由 apt 管理，混用 pip 全局装可能搞乱依赖。优先用 venv/uv/poetry 建虚拟环境；npm 同理，能本地装别全局装，需要 -g 时可考虑 `pip install --user`。
:::

### 8.3 ccache：编译缓存

```bash
sudo apt install ccache
make CC="ccache gcc" -j$(nproc)    # 或 export CC="ccache gcc"
```

解读：ccache 按"源文件哈希 + 编译参数"缓存编译产物，重复编译直接命中，二次编译快一个数量级；第一次编译无加速。

### 8.4 update-alternatives：多版本切换

多个 `python3`、多个 `java` 共存时，用 alternatives 管理"默认用哪个"：

```bash
update-alternatives --list python3                # 看有哪些可选
update-alternatives --config python3              # 交互式切换（输编号）
sudo update-alternatives --install /usr/bin/java java /opt/jdk17/bin/java 100
```

解读：`--install` 把"候选"注册进组（优先级数字大默认优先），可用 `--slave` 连带 javac 等符号链接；`--config` 交互切换。RHEL 系对应 `alternatives`。多版本 Python/JDK/Go 共存的标准解法。

### 8.5 ldconfig：动态库缓存与链接维护

编译安装把 .so 放进非标准目录后，运行时报 `error while loading shared libraries: libxxx.so`：

```bash
ldconfig -p | grep libxxx             # ① -p 只打印缓存，无需 sudo
echo '/opt/app/lib' | sudo tee /etc/ld.so.conf.d/app.conf   # ② 写持久配置
sudo ldconfig                          # ③ 刷新缓存
ldd /opt/app/bin/app | grep libxxx     # ④ 验证链接结果
sudo ldconfig -v                       # verbose：显示扫描目录与建立的 SONAME 链接
sudo ldconfig -n /opt/app/lib          # 只处理指定目录，不重建全局缓存
```

解读：`ldconfig` 根据 `/etc/ld.so.conf`、其 include 文件和受信任默认目录更新 `/etc/ld.so.cache`，并按库的 SONAME 维护链接（典型为 `libfoo.so.1 -> libfoo.so.1.2`）。动态装载器也会按 RPATH/RUNPATH、`LD_LIBRARY_PATH` 和默认目录搜索，所以“库在但找不到”不一定只因缓存；用 `readelf -d` 检查 `NEEDED/RPATH/RUNPATH`，对可信程序再用 `ldd` 看最终解析。

不要把普通用户可写目录加入 `/etc/ld.so.conf.d/`，攻击者可放同名 `.so` 劫持高权限程序；不要手工把无 SONAME 约束的任意文件软链为系统库。`-n` 只处理命令行目录且隐含不重建缓存，发行版参数细节以本机 man page 为准。对不可信 ELF 不直接执行 `ldd`，风险和静态替代方法见 [二进制与安全审计命令](/kb/os/Bash/16-二进制与安全审计命令/)。

## 9. 排障实战

### 9.1 依赖损坏：apt --fix-broken 与 dpkg --configure -a

现象：`apt install` 报一堆 `unmet dependencies` 或 `dpkg was interrupted`。标准修复流程：

```bash
sudo dpkg --configure -a        # ① 先修复中断的包（优先做）
sudo apt --fix-broken install   # ② 再补装缺失依赖/修复损坏
```

::: important 顺序很重要
先 `dpkg --configure -a`（后端），再 `apt -f install`（前端补依赖）。反过来可能装不上还反复报同样的错。修完 `dpkg -l | grep ^..d` 复查。
:::

### 9.2 包冲突

`apt install` 报 `a conflicts with b`：先 `sudo apt remove b && sudo apt install a` 手动卸冲突方，用 `dpkg -l | grep -E '^(ii|rc).*(a|b)'` 看真实状态（rpm 系用 `rpm -qa | grep`）。冲突常因两个包装同一路径文件、或提供同一库。解决原则：**删一个留一个**，别强装（`--force-overwrite` 是最后的危险手段，可能把包数据库搞脏）。

### 9.3 锁文件：/var/lib/dpkg/lock

现象：`E: Could not get lock /var/lib/dpkg/lock-frontend - open (11: Resource temporarily unavailable)`——另一个 apt/dpkg 进程还在跑（常见：后台无人值守升级、另开终端、CI 卡死）。

```bash
sudo lsof /var/lib/dpkg/lock-frontend      # ① 谁锁着它
sudo fuser -v /var/lib/dpkg/lock-frontend  # ② 交叉确认 PID，不终止进程
systemctl status apt-daily.service apt-daily-upgrade.service  # ③ 是否后台更新
sudo dpkg --configure -a                   # ④ 确认原进程结束后修复中断事务
```

::: warning 别上来就删锁
apt/dpkg 使用的是内核维护的文件锁；持锁进程退出后锁会自动释放，通常不存在需要 `rm` 的“陈旧锁”。直接删除 lock 文件既不能安全终止持锁进程，还可能让后续工具在不同 inode 上并发写数据库。先识别进程并等待；只有确认进程卡死、评估事务阶段并有恢复方案后才发送 TERM，随后运行 `dpkg --configure -a`/`apt -f install`。RHEL 系同样应让 dnf/rpm 正常结束，不要手删其状态文件。
:::

### 9.4 软件源报错：404 与公钥过期

现象 1：`apt update` 报 404 Not Found——源里某个路径已失效（常见于版本 EOL 后旧源被下线）：

```bash
grep -r . /etc/apt/sources.list.d/   # 找残留的失效源
sudo rm /etc/apt/sources.list.d/xxx.list   # 移除失效源（或改归档源 old-releases.ubuntu.com）
sudo apt update                      # 再更新
```

现象 2：`NO_PUBKEY 1234567890ABCDEF` / `key is expired`——公钥缺失或过期。旧教程常给出 `apt-key adv --recv-keys`，它会扩大全局信任且已废弃，不应继续照抄。

::: note apt-key 已废弃
Debian 11+/Ubuntu 22.04+ 弃用 `apt-key`。标准做法是从发行方可信渠道取得 key，核对完整 fingerprint，把专用 keyring 安装到 `/etc/apt/keyrings/vendor.gpg`，并在对应源条目写 `signed-by=/etc/apt/keyrings/vendor.gpg`。不要盲信第三方安装脚本，也不要把 key 放进全局 `trusted.gpg.d`；看到 NO_PUBKEY 先核对源官网、发行版代号与密钥轮换公告。
:::

### 9.5 "command not found" 但包已装

现象：`apt list --installed | grep nginx` 显示装了，`nginx` 却报 command not found：

```bash
dpkg -L nginx | grep /bin/        # ① 包装的文件到底在哪
ls -l /usr/sbin/nginx             # ② 实际路径（nginx 在 sbin 而非 bin！）
echo $PATH                        # ③ 你的 PATH 含 /usr/sbin 吗？
```

| 原因 | 解释 | 修法 |
|---|---|---|
| 二进制在 /usr/sbin | 普通用户 PATH 常不含 sbin | `sudo nginx` 或加 PATH |
| 软链/目录未建 | 包装了但链接没生成 | `sudo apt install --reinstall` |
| 动态库缺失 | 二进制在，运行时缺 .so（见 8.5） | 可信程序可用 `ldd "$(command -v app)"`，不可信 ELF 用 `readelf -d` |
| 用户态工具 | 装在 $HOME（pip --user 等） | 加到 PATH 或 source 对应 rc |

::: tip 三步定责
`apt list --installed | grep 名`（装了没）→ `dpkg -L 名 | grep -E 'bin/名$'`（装到哪）→ `echo $PATH`（找得到不）。三步走完基本都能定位。
:::

### 9.6 版本回退

deb 系指定版本安装：`sudo apt install nginx=1.18.0-6ubuntu14.4`（先 `apt-cache policy nginx` 看 Installed/Candidate）；`sudo apt-mark hold nginx` 锁定版本防误升级。rpm 系（配合 dnf history 更佳）：`sudo dnf downgrade nginx-1.20.1-14.el9`，或直接 `sudo dnf install nginx-1.20.1-14.el9`。

### 9.7 卸载残留清理

```bash
dpkg -l | grep ^rc                          # deb：残留配置的包
dpkg -l | awk '/^rc/ {print $2}' | xargs sudo dpkg -P   # 批量清
sudo apt autoremove --purge                 # 顺手清无人用的依赖（带配置）
dnf autoremove                              # rpm：清孤儿依赖
find / \( -name "*nginx*" -o -name "nginx.*" \) 2>/dev/null | grep -v /proc   # 通用：文件残留
```

联动 [排查方法论](/kb/os/问题排查/00-系统问题排查方法论/)：凡是"装了软件不对、坏了、卸不干净"，都按它的通用流程走——**现象 → 复现 → 缩小范围 → 验证**，上面每一节都是可复现的"缩小范围"步骤。

## 10. 本章小结

- **生态识别**：`.deb` 用 apt/dpkg，`.rpm` 用 dnf/rpm，openSUSE 用 zypper，Arch 用 pacman；先读 `/etc/os-release`，滚动发行版尤其不能做 partial upgrade。
- **Debian 查询与控制**：`apt-cache`/`apt policy` 看候选和来源，`apt-mark hold/unhold` 控制升级，`dpkg-query -W -f` 给脚本稳定字段，`apt-file` 查未安装包文件，`debsums` 查已安装文件变化。
- **RPM 查询与分发**：`dnf module` 选择 AppStream 流，`dnf repoquery`/旧 `repoquery` 查依赖与文件，`dnf download`/`yumdownloader` 准备离线包，`rpm2cpio | cpio` 在空目录预览 payload，`rpmkeys --checksig` 验证签名，`rpm -V` 查落盘变化。
- **源与签名**：APT 第三方 key 用专用 `/etc/apt/keyrings` + `signed-by=`；GPG/RPM `Good signature` 只有在完整 fingerprint 已从独立可信渠道核对后才有身份意义，哈希不能替代发布者认证。
- **构建链**：Autotools 用 configure/make，CMake 推荐 `-S/-B` out-of-source，Ninja 用 `-C/-n/-v/-j`，`pkg-config` 查询 `.pc` 中的 cflags/libs；只在安装系统前缀时提权。
- **桌面分发**：AppImage 默认不强制沙箱；Snap 要看 channel/confinement/connections；Flatpak 要看 remote/runtime/permissions。离线 Snap 需要 assertion，Flatpak 需要包含 runtime 的受信任 bundle/仓库。
- **动态库**：`ldconfig -p` 只读缓存，`ldconfig` 刷新并维护 SONAME 链；不可信 ELF 静态用 `readelf -d`，不要直接 `ldd`。
- **排障纪律**：APT 锁先找持锁进程并等待，绝不靠删锁解锁；中断事务先 `dpkg --configure -a` 再 `apt -f install`；“已装但找不到”按包状态 → 文件路径 → PATH/动态库逐层查。

## 11. 动手实验

1. **apt 全流程**：`apt search "web server"` → `sudo apt install nginx` → `apt show nginx | grep -E 'Depends|Size'` → `apt list --installed | grep nginx` → `sudo apt remove nginx`，再用 `dpkg -l | grep ^rc` 验证残留并 `sudo dpkg -P nginx` 清干净。
2. **dpkg 正反查询**：对 `/usr/bin` 下几个文件 `dpkg -S` 反查来源包，再对结果包 `dpkg -L` 正查装到哪些路径，两两对照。
3. **apt-file 反查**：`sudo apt install apt-file && sudo apt-file update`，再 `apt-file search /usr/bin/dpkg`、`apt-file search libssl.so`，体会"文件→包"检索。
4. **源码编译小程序**：`sudo apt install build-essential`，编译 GNU hello：`./configure --prefix=$HOME/apps/hello && make -j$(nproc) && make install`，运行 `$HOME/apps/hello/bin/hello` 并把该 bin 加进 PATH。
5. **update-alternatives 切换**：`update-alternatives --list python3` 看候选；有多个则 `--config` 交互切换，只有一个就用 `--install` 注册自建软链作第二候选再切换，最后切回。
6. **软件源故障模拟**（虚拟机）：备份 `sources.list` 后写入不存在的域名，`sudo apt update` 观察报错，再恢复备份重试，理解 `update` 失败的恢复路径。
7. **版本与 hold**：用 `apt-cache policy`/`apt policy` 记录 Installed、Candidate、source priority；对无关测试包执行 `apt-mark hold`、`showhold`、`unhold`，确认状态变化并立即解除。
8. **包数据库和完整性**：用 `dpkg-query -W -f='${binary:Package}\t${Version}\t${db:Status-Status}\n'` 导出三列；选一个系统包运行 `debsums -c`（Debian）或 `rpm -V`（RPM），解释“无输出”和配置文件变化的含义。
9. **无安装解包**：下载一个小型 `.deb`/`.rpm`，先验签或核对可信摘要，再用 `dpkg-deb -c` 或 `rpm2cpio | cpio -t` 看清单；只在 `/tmp` 空目录解包，审查 scriptlet/maintainer scripts，不安装。
10. **CMake + Ninja**：准备一个最小 `CMakeLists.txt` 项目，执行 `cmake -S . -B build -G Ninja`、`cmake --build build`、`ctest --test-dir build`；用 `ninja -C build -n/-v` 对比 dry-run 与完整命令，并用 `pkg-config --cflags --libs` 查询一个开发库。
11. **跨发行版对照**：在可用容器/虚拟机中任选 zypper 或 pacman，完成“搜索 → 信息 → 文件归属 → 只下载/缓存查看”；Arch 只运行 `pacman -Syu` 的完整升级流程，不单独执行 `pacman -Sy`。
12. **Snap/Flatpak 权限**（桌面测试机）：分别查看 `snap info/connections` 与 `flatpak info --show-permissions`，记录 channel、confinement、filesystem/socket/device 权限；不安装未知发布者包。

## 12. 自测题

1. **`apt update` 和 `apt upgrade` 的区别？** update 只拉索引不装不卸，upgrade 才升级软件；索引过期时 install 可能找不到新包、装到旧版本。
2. **`apt remove` 与 `apt purge` 的区别？** remove 保留 `/etc` 配置；purge 连配置一起删。清 `rc` 残留用 `dpkg -P`。
3. **apt 和 dpkg 的分工？** dpkg 只负责单个 .deb 装卸，不懂依赖、不碰软件源；apt 负责连源、解析依赖、自动补装，最终调 dpkg 落盘。
4. **`dpkg -S` 与 `dpkg -L` 各干什么？** `-S 文件路径` 反查文件属于哪个包（从文件找包）；`-L 包名` 正查包装了哪些文件（从包找文件）。
5. **`rc` 状态是什么？如何清理？** 包已卸载但配置残留（rc = removed but config-files remain）。`sudo dpkg -P <包名>` 单独清，或 `dpkg -l | awk '/^rc/ {print $2}' | xargs sudo dpkg -P` 批量清。
6. **dnf 相比旧 yum 的优势（举两点）？** 基于 libsolv 的依赖解析与更清晰的事务历史；支持 `dnf history info/undo`。RHEL 8+ 的 `yum` 通常是 DNF 兼容入口，但回滚仍依赖旧包可用，不能恢复应用数据。
7. **`./configure` 报 `checking for libssl... not found` 怎么处理？** 编译缺的是开发包：deb 系 `sudo apt install libssl-dev`，rpm 系 `sudo dnf install openssl-devel`，不是装运行时库。
8. **编译装完运行报 `cannot open shared object file` 如何排查？** 先用 `readelf -d` 看直接 `NEEDED/RPATH/RUNPATH`，对可信程序再用 `ldd` 看最终解析，核对架构和库路径；确认目录受信任后才加入 `ld.so.conf.d` 并运行 `ldconfig`。
9. **`apt-cache policy` 与 `apt-mark hold` 分别解决什么问题？** 前者解释 Installed/Candidate/源优先级，后者阻止常规升级选中该包；hold 过久会漏安全更新，需要原因和复查日期。
10. **`dpkg-query` 为什么比解析 `dpkg -l` 更适合脚本？** `-W -f` 可明确输出字段与分隔符，不依赖给人看的列宽、本地化标题和截断格式。
11. **`dnf module enable X:Y` 与 `dnf module install X:Y/profile` 有何区别？** enable 选择 stream 但不一定装包；install 同时选择 stream 并按 profile 安装。切 stream 前要评估依赖和数据迁移。
12. **`rpmkeys --checksig`、`rpm -V`、`sha256sum` 各证明什么？** `checksig` 验证包签名与已信任 key，`rpm -V` 对比已安装文件与本地 RPM 数据库，`sha256sum` 只证明内容与给定摘要一致；三者都依赖可信 key/数据库/清单。
13. **为什么离线下载必须在与目标机匹配的环境解析依赖？** 发行版版本、架构、仓库、模块流和已装包会改变依赖集合；`--resolve` 在错误环境下载的包可能缺失或 ABI 不兼容。
14. **Snap 的 `--dangerous` 与 Flatpak 的宽泛 filesystem 权限风险是什么？** 前者跳过 assertion 验证，后者可能把主机敏感数据暴露给应用；沙箱存在不等于来源可信或权限最小。
