上篇教会你"卡住用 strace、热点用 perf、看栈用 gdb"。本篇把这三件工具**加满**，再补上另外三个：`ltrace` 看库函数、`bpftrace` 一行脚本追踪内核、`valgrind` 找内存 bug。一句话定位：**strace 问"内核入口"、ltrace 问"库内部"、gdb 问"程序现场"、perf 问"时间去哪了"、bpftrace 问"内核事件"、valgrind 问"内存坏了没"**。

## 1. strace 深入

上篇已讲过 `strace -p` 挂进程、`-c` 统计、`-e trace=` 过滤。本篇展开全部进阶参数与三板斧用法。

### 1.1 参数全解

```bash
strace -f -tt -T -s 128 -o /tmp/tr.log -yy -e trace=network ./myprog
```

| 参数 | 作用 | 说明 |
|---|---|---|
| `-e trace=%file` | 只跟踪文件类调用 | 现版本集合名：`%file`/`%network`/`%process`/`%signal`/`%desc`/`%memory`；不带 `%` 的旧写法仍常见但已弃用 |
| `-e trace=read,write` | 精确到具体调用 | 用逗号列出多个，或用 `read,write` |
| `-c` | 统计每类调用的次数/耗时 | 结束时输出汇总表，最常用于找"调用最多的调用" |
| `-f` | 跟随 fork/exec 的子进程 | 不跟则多进程程序只见父进程 |
| `-ff` | 每个进程一个输出文件 | 配合 `-o /tmp/tr.log` 生成 `tr.log.&lt;pid&gt;` |
| `-tt` | 微秒级时间戳 | 比 `-t` 精确到微秒，用于量两个调用之间间隔 |
| `-T` | 每次调用耗时 | 行尾输出 `<0.000123>` 形式耗时 |
| `-o file` | 输出到文件 | 避免与程序自身输出混淆 |
| `-p PID` | 附加到运行中进程 | 需权限，Ctrl+C 结束并输出统计（若带 `-c`） |
| `-yy` | 显示 fd 完整信息 | 把 fd 展开为 `/path/file`、`socket:[3]` 等 |
| `-s 128` | 字符串显示长度 | 默认 32 字符，改大看完整路径/参数 |
| `-e inject=...` | 系统调用注入 | 注入延迟/错误码，模拟故障 |

### 1.1.1 现版本常用过滤与调用栈选项

```bash
sudo strace -k -f -e trace=futex,epoll_wait -p "$PID"       # 每次 syscall 后打印用户栈
sudo strace -P /var/lib/myapp -e trace=%file -p "$PID"       # 只看访问该路径的调用
sudo strace -Z -e trace=%file -p "$PID"                      # 只输出失败的 syscall
sudo strace -kk --stack-trace-frame-limit=12 -p "$PID"       # 栈 + 源码信息，需 DWARF
```

输出片段：

```text
epoll_wait(3, [], 128, 30000) = 0 <0.300123>
 > /usr/lib/libevent-2.1.so.7(event_base_loop+0x...) [0x...]
 > ./myapp(handle_connection+0x42) [0x...]

openat(AT_FDCWD, "/var/lib/myapp/state", O_RDONLY) = -1 ENOENT (No such file or directory)
```

参数与解读：

- `-k` 在系统调用后附加用户态栈，适合回答"是谁调用了这个 syscall"；`-kk` 还请求源码/行号，目标程序和库需要可用的调试信息。
- `-P path`/`--trace-path=path` 只跟踪访问指定路径的系统调用，适合大程序中追一个配置、日志或数据文件；多个路径可重复指定。
- `-Z`/`--failed-only` 只输出返回错误的系统调用，和 `-z` 成功调用过滤相反。它不是 SELinux 选项；SELinux 上下文使用 `--secontext`。
- `--stack-trace-frame-limit=N` 限制每次 syscall 的栈帧数，防止输出爆炸；结合 `-e trace=` 缩小事件集合。

场景与风险：`-k/-kk` 每次系统调用都要取栈，开销和输出会明显高于普通过滤；`-P` 只按路径过滤，不能证明程序没有访问其他路径；`-Z` 会丢掉成功调用，适合找错误但不适合复原完整时序。生产现场优先 `-P` + 小型 syscall 集合 + 短时窗口，敏感路径和参数可能包含密钥、用户数据，输出文件要按权限保存。

### 1.2 三个典型用法

**用法一：跟踪所有系统调用找瓶颈**

```bash
sudo strace -c -f -p $(pgrep -f myworker | head -1)
```
跑 10 秒后 Ctrl+C，预期输出：
```
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 48.72    0.831218        8302       100          0 futex
 30.15    0.514432        5144       100          0 read
 12.08    0.206123        2061       100          0 write
  9.05    0.154321        1543       100          0 nanosleep
------ ----------- ----------- --------- --------- ----------------
100.00    1.705094                  400         0 total
```
解读：`% time` 是该类调用占总耗时比例，`usecs/call` 单次平均耗时。`futex` 占 48% 说明大量时间在等锁；`read` 单次 5ms 像在等 IO。**先看百分比列，再抓单次耗时异常大的那类。**

**用法二：统计失败的系统调用**

```bash
strace -e trace=openat,open,connect -f ./app 2>&1 | grep -E '= -1' | head
```
预期输出：
```
openat(AT_FDCWD, "/etc/nonexist.conf", O_RDONLY) = -1 ENOENT (No such file or directory)
connect(3, {sa_family=AF_INET, sin_port=htons(3306), ...}, 16) = -1 ECONNREFUSED
```
解读：`= -1` 后面跟着错误码。统计 `strace -c -e trace=openat ./app` 的 `errors` 列也能看失败次数。**"能打开的文件全打开了吗？连上的端口都连上了吗？"答案全在这。**

**用法三：定位阻塞点**

```bash
sudo strace -tt -T -p $(pgrep myworker) -e trace=read,write,select,poll,epoll_wait,futex
```
预期输出：
```
16:22:10.001234 read(7,  ...)           = -1 EAGAIN
16:22:10.001250 epoll_wait(3, [], 128, 30000) = 1  <0.300123>
16:22:10.301500 read(7,  "HTTP/1.1", ...) = 8   <0.000011>
```
解读：`epoll_wait` 花了 300ms（`<0.300123>`）在等事件，然后 `read` 立刻返回——**耗时在"等"，不在"读"**。进程卡住时先看哪个调用 `usecs/call` 最大或 `-T` 耗时最长，就知道它睡在哪。

::: tip `-e inject` 故障注入
生产没法重现故障时，可以用注入制造故障：`strace -e inject=write:error=EIO:when=2 ./app` 让第 2 次 `write` 返回 `EIO`，`strace -e inject=read:delay_enter=2s ./app` 让每次 `read` 慢 2 秒。这是**验证程序容错逻辑**的利器，不用改一行代码。
:::

### 1.3 strace 的局限

| 局限 | 说明 |
|---|---|
| 只看系统调用 | 看不到库内部逻辑（`malloc` 内部怎么管理堆？要看 ltrace/gdb/源码） |
| ptrace 开销巨大 | 每次调用入口+出口各停一次，**拖慢目标 10~100 倍**，高并发/高频调用场景不可用 |
| 只能看本进程 | 内核内部、其他进程的事件看不到（上 bpftrace） |
| 样本会变形 | 被跟踪的行为不是正常行为——慢 50 倍的进程，时序/竞争行为都会变 |

::: warning 生产纪律
上篇已警告过：`strace -p` 慎用于生产。正确的顺序是：先用 `perf`/`pidstat` 这类低成本工具缩小范围，**必须用 strace 时，限定 `-e trace=` 集合、记下时间、尽快断开**。
:::

## 2. ltrace：动态库调用追踪

`ltrace` 追踪的是**动态库函数**（`malloc`/`strlen`/`pthread_mutex_lock`），比 strace 高一层——它拦截的是用户态的 PLT/GOT 跳转。

```bash
ltrace -e malloc+free ls /tmp 2>&1 | tail -8
```
预期输出：
```
ls(1, ["/tmp"], 0x10)       = 0
malloc(4096)                = 0x55f6e1c2c010
malloc(1024)                = 0x55f6e1c2e020
free(0x55f6e1c2e020)        = &lt;void&gt;
malloc(8192)                = 0x55f6e1c31000
free(0x55f6e1c2c010)        = &lt;void&gt;
```
解读：每行是"函数(参数) = 返回值"。`-e malloc+free` 只追堆分配/释放；`+` 表示取并集（也可 `-e all`）。看到 malloc 与 free 成对是好事，**一直 malloc 不见 free 就是泄漏嫌疑**。

| 参数 | 作用 |
|---|---|
| `-e expr` | 过滤库函数，如 `-e malloc+free`、`-e printf*` |
| `-c` | 统计每个库函数调用次数与耗时（同 strace） |
| `-p PID` | 附加到运行进程 |
| `-f` | 跟随子进程 |
| `-o file` | 输出到文件 |

```bash
ltrace -c -p $(pgrep myservice)   # 跑几秒 Ctrl+C
```
预期输出：
```
% time     seconds  usecs/call     calls      function
------ ----------- ----------- --------- --------------------
 52.17    0.412310       4123       100   memcpy
 20.55    0.162400       1624       100   malloc
 12.30    0.097210        972       100   strncpy
```

### 2.1 三者分工对比

| 维度 | strace | ltrace | gdb |
|---|---|---|---|
| 观察层 | 系统调用（内核入口） | 动态库函数（用户态） | 任意行/函数/变量/内存 |
| 是否需要源码 | 否 | 否（但需符号） | 是（有符号才好看） |
| 典型问题 | 卡在哪个 syscall、fd 泄露 | 库调用失衡、malloc/free 不配对 | 崩溃现场、变量值、逻辑错误 |
| 开销 | 极大（ptrace） | 大（也是 ptrace） | 停在断点无持续开销，但运行慢 |
| 适合场景 | 阻塞/IO/文件问题 | 业务逻辑与内存分配 | 交互式深度调试 |
| 反向 | 一层层往里：strace → ltrace → gdb，**越往里开销越大、看得越细** |

## 3. gdb 基础与进阶

上篇讲了 `gdb -p` 附加看栈。本篇把交互式调试的核心命令串成一条主线：**启动 → 断点 → 运行 → 看现场 → 改状态 → 内存 → 多线程**。

### 3.1 启动三种方式

```bash
gdb ./prog                 # 1. 调试未运行的程序
gdb ./prog core            # 2. 调试 core dump（崩溃现场回放）
sudo gdb -p 1234           # 3. 附加到运行中的进程
```

### 3.2 断点：核心命令

```
(gdb) break main                        # 在函数入口断
(gdb) break src/foo.c:42                # 在源文件行号断
(gdb) break func if x > 5               # 条件断点
(gdb) condition 1 x == 0                # 给 1 号断点加条件
(gdb) ignore 1 5                        # 跳过 1 号断点前 5 次命中
(gdb) info breakpoints                  # 列出所有断点
(gdb) delete 1                          # 删除 1 号断点
```

::: tip 条件断点 vs ignore
循环跑 1000 万次、只在 `i == 9999999` 时停下，两种写法：
`break loop if i == 9999999` 或 `break loop` + `ignore 1 9999999`。
`condition` 每次命中都要**求值条件**（慢），`ignore` 是纯计数（快）。追求性能用 `ignore`。
:::

### 3.3 看现场

```
(gdb) run                  # 或 r，运行到第一个断点
(gdb) bt                   # backtrace：完整调用栈
(gdb) frame 2              # 切到 2 号栈帧
(gdb) info locals          # 当前函数所有局部变量
(gdb) info args            # 当前函数参数
(gdb) print x              # 或 p x，打印变量
(gdb) p/x 0x1234           # 按十六进制打印
(gdb) list                 # 显示当前行附近源码（需带调试符号编译）
```

预期输出示例（一个段错误现场）：
```
(gdb) bt
#0  0x00007f1e4a12d4e7 in __strlen_avx2 () from /lib/x86_64-linux-gnu/libc.so.6
#1  0x0000555555555170 in do_greet (name=0x0) at greet.c:15
#2  0x00005555555551a4 in main () at greet.c:28
```
解读：`#0` 是最深栈帧，`do_greet` 在 `greet.c:15` 调用了 `strlen`，而 `name=0x0`——**传了空指针**。崩溃排查的标准读法：从 `#1` 以下看业务代码，`#0` 是"压垮骆驼的最后一根稻草"。

### 3.4 单步与修改变量

```
(gdb) step                 # 或 s：单步进入函数
(gdb) next                 # 或 n：单步跳过函数
(gdb) stepi                # 单条汇编指令
(gdb) continue             # 或 c：继续运行
(gdb) set var x = 42       # 运行时改变量（调试利器！）
(gdb) call foo()           # 直接调用函数
(gdb) watch x              # 监视变量，值一变就停下
(gdb) watch *(int*)0x7fff   # 也可以监视内存地址
```

::: important 先编译出调试符号
gdb 好不好用全看符号：`gcc -g -O0 -o prog prog.c`。`-g` 生成调试信息，`-O0` 关闭优化（优化会重排代码、删变量，导致"行对不上、变量看不到"）。生产优化后的二进制 `-O2` 也可以调，但看到的变量可能不是源码那个值——调生产前要知道这一点。
:::

### 3.5 看内存：x 命令与堆

```
(gdb) x/16bx buf           # 看 buf 前 16 个字节（b=字节）
(gdb) x/8wx 0x7ffc1234     # 8 个 4 字节 word，十六进制
(gdb) x/20s str            # 20 个字符串
(gdb) p buf                # 打印指针
(gdb) p *head              # 解引用指针看结构体
(gdb) p *(struct node*)0x1234  # 把地址强转成结构体看字段
```
配合堆检查：
```
(gdb) info proc mappings   # 进程虚拟内存映射（哪些段可读/可写）
(gdb) p malloc_info         # glibc 堆信息
```
`x` 命令格式 `x/Nfu`：`N` 数量、`f` 格式（`x` 十六进制/`d` 十进制/`c` 字符/`s` 字符串）、`u` 单位（`b` 字节/`h` 半字/`w` 字/`g` 8 字节）。**看到乱码前的 `0x00` 或越界的 `0xcc`（MSVC）/`0xab`（glibc freed 内存），就找到了内存 bug 的物证。**

### 3.6 多线程调试

```
(gdb) info threads                 # 列出所有线程
(gdb) thread 3                     # 切到 3 号线程
(gdb) thread apply all bt          # 所有线程都打印调用栈（死锁排查神器）
(gdb) set scheduler-locking on     # 单步时只跑当前线程（否则别的线程会动）
```
预期输出（一个死锁现场）：
```
(gdb) thread apply all bt
Thread 2 (Thread 0x7f1e3bffd700 (LWP 3120)):
#0  0x00007f1e4a1d2d5d in __futex_abstimed_wait_common ... in pthread_mutex_lock ()
#1  ... worker_main () at worker.c:41
Thread 1 (Thread 0x7f1e4a7ff740 (LWP 3119)):
#0  ... in pthread_mutex_lock ()
#1  ... main () at main.c:66
```
解读：两个线程都卡在 `pthread_mutex_lock`——线程 1 等线程 2 的锁、线程 2 等线程 1 的锁，**互相等，就是死锁**。配合 `frame 1` + `info locals` 看它们各自持有哪个锁。

### 3.7 脚本化与远程调试

```bash
gdb -batch -x cmds.txt ./prog
gdb -batch -ex "b foo" -ex "run" -ex "bt" -ex "p var" ./prog
```
`-batch` 非交互执行，`-ex` 一条命令一执行——**适合 CI、适合对 100 个 core 文件批量跑 `bt` 提取崩溃栈**：

```bash
for core in /crash/*.core; do
  gdb -batch -ex "bt" ./app "$core" 2>/dev/null | head -5
done
```

远程调试（现场进程不便停、或目标机没有调试工具时）：
```bash
# 目标机：起 gdbserver，监听端口让 gdb 连
gdbserver :1234 ./prog
gdbserver --attach :1234 5123
# 调试机：
gdb ./prog
(gdb) target remote 10.0.0.5:1234
```

::: tip 崩溃优先看 dmesg/告警日志
core dump 要 `ulimit -c unlimited` 才生成，systemd 下默认可能被 journald 接管。gdb 调试前先 `dmesg | grep segfault`，能看到崩溃瞬间的地址与指令指针，比盲开 gdb 快得多。
:::

### 3.8 coredumpctl：systemd 管理的 core 现场

```bash
coredumpctl list myservice                    # 列出该程序的 core
coredumpctl info 5123                         # PID、信号、命令行、存储位置、摘要栈
coredumpctl -o /tmp/myservice.core dump 5123  # 导出 core 文件
coredumpctl debug myservice                   # 调用 gdb 调试最近一次匹配的 core
coredumpctl list --since '1 hour ago'         # 按时间缩小事故窗口
```

输出片段：

```text
TIME                         PID  UID  GID SIG  COREFILE  EXE
Tue 2026-08-11 09:20:03     5123 1001 1001 SEGV present  /usr/local/bin/myservice

Signal: 11 (SEGV)
Command Line: /usr/local/bin/myservice --worker
Storage: /var/lib/systemd/coredump/core.myservice....zst (present)
```

解读：`list` 是索引，`info` 读取 journal 元数据并可能带简要栈，`dump` 把压缩或 journal 中的 core 导出给 gdb，`debug` 默认启动 gdb。`COREFILE=present` 表示当前用户可访问完整 core；`journal`、`truncated`、`missing` 分别表示存于 journal、被截断或文件已不在。程序没有被信号终止、`ulimit -c` 为 0、systemd-coredump 未启用时，列表可能为空。

场景与风险：先保存二进制、调试符号、core 对应的版本和 `coredumpctl info`，再分析；同名程序若已升级，拿错 ELF 会得到错误的栈。core 可能包含密码、请求内容和密钥，导出文件按敏感生产数据管理；磁盘配额、`ProcessSizeMax`/`ExternalSizeMax` 等 coredump 配置也会导致 core 被截断或不保存。

### 3.9 addr2line、eu-stack 与 pstack：把地址还原成栈

```bash
addr2line -e ./myservice -f -C 0x401234       # 函数名 + 源码行，-C 还原 C++
eu-stack -p 5123 -e /usr/local/bin/myservice  # elfutils，读取运行中进程栈
pstack 5123                                   # 常见兼容命令，打印线程栈
```

输出片段：

```text
handle_request
/build/myservice/src/http.c:87

TID 5123:
 #0  0x00007f... in epoll_wait ()
 #1  0x000000... in event_loop at event.c:42
```

解读：`addr2line` 用 ELF 的 DWARF 调试信息把指令地址映射到函数和文件行；`-f` 打印函数名，`-C` 对 C++ 符号做 demangle。`eu-stack` 是 elfutils 工具，通常比临时启动 gdb 更适合快速抓一份栈；`pstack` 在不同发行版上可能是脚本、gdb 包装器或未安装，先用 `command -v` 确认。

PIE/共享库地址要先换算为模块内偏移：从 core 的 gdb `info proc mappings`、`info files` 或 `/proc/PID/maps` 找到模块加载基址，再用正确 ELF 和相对地址解析；直接把 ASLR 后的绝对地址喂给 `addr2line` 常得到 `??:0`。调试符号必须与二进制构建版本匹配，strip 后需要单独的 debuginfo 文件。二进制布局、符号和调试节见 [二进制与安全审计命令](/kb/os/Bash/16-二进制与安全审计命令/)。

### 3.10 trace-cmd 与 ftrace：tracefs 的内核事件轨迹

```bash
mount | grep tracefs || sudo mount -t tracefs nodev /sys/kernel/tracing
sudo trace-cmd record -e sched_switch -e sched_wakeup -- sleep 10
trace-cmd report trace.dat                       # record 默认写当前目录的 trace.dat

TRACE=/sys/kernel/tracing
echo 0 | sudo tee "$TRACE"/tracing_on
echo 1 | sudo tee "$TRACE"/events/sched/sched_switch/enable
echo 1 | sudo tee "$TRACE"/tracing_on
sudo cat "$TRACE"/trace_pipe
echo 0 | sudo tee "$TRACE"/tracing_on
echo 0 | sudo tee "$TRACE"/events/sched/sched_switch/enable
```

输出片段：

```text
           <...>-5123  [002] ....  120.100: sched_switch: prev_comm=myservice prev_pid=5123 ==> next_comm=swapper/2 next_pid=0
```

解读：tracefs 提供内核事件、缓冲区和开关；ftrace 是内核内置的追踪框架，`events/sched/*` 是稳定的 tracepoint 入口。`trace-cmd record` 负责选择事件、采集并在当前目录写入 `trace.dat`，`trace-cmd report trace.dat` 将其解码；适合复盘调度切换、唤醒、IRQ、block IO 等时序问题。需要的事件可先列出：`ls "$TRACE"/events/sched` 或 `trace-cmd list -e`。

场景与风险：tracefs 需要 root/相应 capability，缓冲区过小会丢事件，事件过多会让输出和内核开销迅速增长；先清理旧 filter、限定事件和采集窗口。直接写 `/sys/kernel/tracing` 会改变全机可见的追踪状态，结束实验必须关闭 `tracing_on` 并恢复 enable/filter；不要在生产开启 function_graph 这类高频追踪器而不设边界。

### 3.11 SysRq：内核无响应时的最后观测入口

```bash
cat /proc/sys/kernel/sysrq                    # 查看允许的 SysRq 范围
sudo sh -c 'echo w > /proc/sysrq-trigger'     # 阻塞任务/不可中断睡眠栈
sudo sh -c 'echo t > /proc/sysrq-trigger'     # 全部任务栈
sudo sh -c 'echo l > /proc/sysrq-trigger'     # 所有 CPU 的 backtrace
```

输出片段（通常进入内核日志）：

```text
INFO: task myservice:5123 blocked for more than 120 seconds.
Call Trace:
 __schedule+0x...
 io_schedule+0x...
```

解读：`/proc/sysrq-trigger` 直接调用 Magic SysRq 功能，`w` 主要打印 D 状态阻塞任务，`t` 打印任务栈，`l` 打印各 CPU backtrace；随后用 `dmesg` 或 `journalctl -k` 读取。键盘上的 `Alt+SysRq+w/t/l` 是同一机制的物理按键入口，前提是发行版和内核允许。

场景与风险：SysRq 是机器级动作，输出可能包含敏感路径和参数；`c` 会触发 kernel panic，`b` 会立即重启，绝不能作为普通调试命令。生产先确认变更窗口、串口/远程控制台和日志接收链路，再只使用观测型字母；`kernel.sysrq` 的策略由发行版定义，`0` 通常表示禁用，具体位掩码以当前内核文档为准。

### 3.12 perf probe：给函数临时加动态探针

```bash
sudo perf probe -x ./myservice 'handle_request'       # 按用户函数建 uprobe
sudo perf probe -x ./myservice --list                 # 查看已注册探针
sudo perf record -e probe_myservice:handle_request -p "$PID" -- sleep 10
sudo perf script | head -20                          # 查看命中样本
sudo perf probe --del='probe_myservice:handle_request' # 删除用户态探针
```

输出片段：

```text
Added new event:
  probe_myservice:handle_request (on handle_request in ./myservice)
myservice 5123 [002] ...: handle_request: (0x401230)
```

解读：`perf probe` 根据符号或源码位置创建临时 kprobe/uprobes 事件；`-x ELF` 明确探测用户程序，`--list` 检查注册结果，随后用 `perf record -e probe_*` 采集命中。需要变量值时可用带调试信息的源码位置，但参数语法随内核、perf 和 DWARF 支持变化，先 `perf probe --help`、`perf probe -x app --line 'file.c:42'` 验证；脚本中可显式写 `--add='event=function'`、`--del='event'`，减少短选项歧义。

场景与风险：探针会在每次命中路径运行，热函数上可能有明显开销；高频函数不要直接全量打印，使用 `perf record`/计数器或增加过滤，把采集窗口压到秒级。删除探针后再确认 `perf probe --list`，避免留下全机可见的动态事件。

### 3.13 BCC 常用命令：execsnoop / opensnoop / biolatency / tcpconnect

```bash
sudo execsnoop -T                         # bcc-tools：谁 exec 了什么，带时间
sudo opensnoop -T -p "$PID"              # 指定进程打开了哪些路径
sudo biolatency -m 1 5                     # block IO 延迟直方图，按毫秒；1 秒 5 次
sudo tcpconnect -t                         # 新建 TCP 连接，带时间戳
```

输出片段：

```text
TIME     PID    PPID  COMM              ARGS
09:30:02 5123   5000  myservice         /usr/bin/curl https://api.example

MILLISECONDS        : COUNT     DISTRIBUTION
0 -> 1              : 124       |************************|
8 -> 16             : 12        |***                     |

PID    COMM      IP SADDR             DADDR            DPORT
5123   myservice 4  10.0.0.5          10.0.0.8         443
```

解读：`execsnoop` 观察进程生命周期和短命命令，`opensnoop` 观察文件打开失败/热点路径，`biolatency` 给出块 IO 延迟分布，`tcpconnect` 观察主动建立的 TCP 连接。它们对应 07 篇的 `pidstat`/`iostat` 初筛：BCC 告诉你发生了什么事件，`pidstat`/`ps` 告诉你任务当前资源画像。`execsnoop` 的 `-P` 按父 PID 过滤，`opensnoop` 的 `-p` 按目标 PID 过滤，`tcpconnect` 的 `-p` 也按目标 PID 过滤；不同发行版脚本参数先用 `-h` 核对。

场景与风险：命令名和安装路径随发行版不同，常见位置是 `/usr/share/bcc/tools/`，也可能需要 `python3-bpfcc`/`bcc-tools` 包；先 `command -v execsnoop` 或 `ls /usr/share/bcc/tools`。这些工具需要 root/CAP_BPF 等权限，`execsnoop`/`opensnoop` 在高事件量机器上会产生大量输出，先加 `-p`/`-P`/`-x` 等过滤并限时；不要把命令参数和路径原样送到公共日志。

### 3.14 Sanitizers：编译期抓内存与并发错误

```bash
gcc -g -O1 -fno-omit-frame-pointer \
  -fsanitize=address,undefined -o app_asan app.c
./app_asan

gcc -g -O1 -fno-omit-frame-pointer -fsanitize=thread \
  -o app_tsan app.c -pthread
./app_tsan
```

输出片段：

```text
==5123==ERROR: AddressSanitizer: heap-use-after-free on address 0x...
    #0 0x... in read_item app.c:42
SUMMARY: AddressSanitizer: heap-use-after-free app.c:42

WARNING: ThreadSanitizer: data race
  Write of size 4 at app.c:18 by thread T1
  Previous read of size 4 at app.c:22 by thread T2
```

解读：ASan 发现越界、use-after-free、double free 等地址错误，UBSan 发现有符号溢出、非法移位、类型等未定义行为；TSan 检测数据竞争和部分锁使用问题。它们要求重新编译并尽可能保留调试信息，错误报告自带调用栈，适合 CI、测试和最小复现。

场景与风险：ASan/UBSan 的运行成本通常远低于 Valgrind，但 ASan 会显著增加内存占用；TSan 常有数倍时间和内存开销，且不是所有平台/第三方库都支持。不要把 sanitizer 构建直接当生产二进制，先在测试流量、回放数据或灰度环境验证；`ASAN_OPTIONS`/`UBSAN_OPTIONS` 的日志文件路径也可能暴露请求数据。

### 3.15 rr：录制并重放非确定性故障

```bash
rr record ./myservice --config test.yml       # 非默认工具，录制一次运行
rr replay                                     # 重放，进入 gdb 风格调试
(rr) reverse-continue
(rr) reverse-step
rr replay -a -x 'bt'                          # 批量执行 gdb 命令（版本支持时）
```

输出片段：

```text
rr: Saving execution to trace directory `/home/zhang/.local/share/rr/myservice-12'
(rr) reverse-continue
```

解读：`rr` 记录系统调用、信号和必要的非确定性输入，之后重放同一执行历史，可以反向继续/单步，特别适合偶发数据竞争、错误状态被后续覆盖、只发生一次的崩溃。它不是默认安装工具，主要面向 Linux x86 等受支持平台，运行环境、硬件性能计数器和 ptrace 权限会影响可用性。

场景与风险：录制会增加时间、磁盘和 IO，trace 目录可能包含敏感输入；不能把 rr 录制当生产长期采集。先在测试或一次性现场短时录制，并把 trace 和对应二进制/符号绑定保存，版本不一致会让重放失真。

### 3.16 heaptrack：堆分配增长分析

```bash
heaptrack ./myservice --config test.yml       # 非默认工具，录制堆分配
heaptrack_print heaptrack.myservice.*.gz | head -40
heaptrack --pid "$PID"                        # 部分版本支持附加到运行进程
```

输出片段：

```text
MOST CALLS TO ALLOCATION FUNCTIONS
  42.1%  allocate_request  http.c:87
  18.7%  parse_json        parser.c:42
PEAK MEMORY CONSUMPTION
  512.0 MiB at 00:02.31
```

解读：heaptrack 记录 malloc/new 等堆分配的调用栈和生命周期，报告累计分配次数、峰值内存和可能未释放的路径；它比只看 RSS 更接近"谁在分配"。先用 `pidstat -r`/`pmap -x` 确认是进程内存增长，再用 heaptrack 对最小复现做归因。

场景与风险：记录每次分配会有明显 CPU、内存和磁盘开销，输出文件也可能很大；附加运行中的进程会改变时序，且不同版本对 `--pid` 支持不同。不要在高 QPS 生产服务直接全量启用，优先测试环境或限流回放。

## 4. perf 深入

上篇讲了 `perf top` 实时热点与 `perf record/report` 基本用法。本篇上采样频率、事件分类、火焰图和权限。

### 4.1 record/report 进阶

```bash
sudo perf record -F 99 -g -p $(pgrep -f myservice) -o /tmp/perf.data -- sleep 30
sudo perf report --stdio --sort=sym | head -30
```
| 参数 | 作用 |
|---|---|
| `-F 99` | 每秒采样 99 次（香农采样，默认可能很高；99 对系统负担小） |
| `-g` | 记录调用栈（火焰图数据源） |
| `-p PID` | 指定进程；`-a` 全系统 |
| `-o file` | 输出文件；`-- sleep 30` 只采 30 秒 |
| `--stdio` | 非交互输出（脚本友好）；`--sort=sym` 按符号排序 |
| `--call-graph dwarf` | 采样用户态完整栈（默认 fp 在某些库会断栈） |

```bash
sudo perf top -p $(pgrep myservice)   # 实时看单进程热点
sudo perf top -a --sort=cpu           # 全系统按 CPU 核分
```

### 4.2 perf stat：计数器

```bash
perf stat ./myprog
perf stat -e cycles,instructions,cache-misses,cache-references ./myprog
perf stat -e dTLB-loads,dTLB-load-misses ./myprog
```
预期输出：
```
 Performance counter stats for './myprog':
            124,712,340      cycles                    # 3.103 GHz
             86,201,451      instructions              # 0.69  insn per cycle
              3,412,988      cache-misses              # 5.2% of all cache refs
             65,401,000      cache-references
       0.040189305 seconds time elapsed
```
读法：`insn per cycle`（IPC）< 0.5 说明 CPU 在**等**（内存/锁/分支），> 1 说明在**算**；`cache-misses` 比例高说明内存访问局部性差。

### 4.3 常用事件分类

| 事件 | 含义 | 高代表什么 |
|---|---|---|
| `cycles` | CPU 时钟周期 | 总消耗（时间=周期×频率） |
| `instructions` | 执行指令数 | 计算量；配合 cycles 算 IPC |
| `cache-misses` | 末级缓存缺失 | 内存带宽吃紧、局部性差 |
| `branch-misses` | 分支预测失败 | 乱序流水线停顿 |
| `cpu-migrations` | 跨核迁移 | 被调度踢来踢去，cache 全废 |
| `context-switches` | 上下文切换 | 线程数/调度问题 |
| `dTLB-load-misses` | 数据页表缓存缺失 | 地址离散/页大小不当 |

### 4.4 调度与锁事件

```bash
sudo perf sched record -- sleep 5
sudo perf sched latency            # 各任务的调度延迟分布
sudo perf sched timehist           # 每个任务何时跑/何时被抢
sudo perf lock record -- sleep 5   # 记录锁事件
sudo perf lock report              # 锁竞争排行榜（谁持锁最久、等锁最多）
sudo perf trace -- sleep 2         # 轻量 strace 替代（只采样 syscall）
```
`perf sched` 回答"**谁抢了谁的 CPU**"，`perf lock` 回答"**锁是热点吗、谁把持不放**"——对应 [崩溃排查](/kb/os/问题排查/05-并发与异常排查/) 的锁竞争场景。

### 4.5 火焰图生成

火焰图把 `perf` 采样到的调用栈画成**横条=栈帧、宽=占比、叠成山**的图，一眼看出热点与调用路径。

```bash
sudo perf record -F 99 -g -- sleep 30          # 1. 采样
perf script > /tmp/perf.script                  # 2. 导出文本
# 用 FlameGraph 工具（github.com/brendangregg/FlameGraph）：
/opt/FlameGraph/stackcollapse-perf.pl /tmp/perf.script > /tmp/out.folded
/opt/FlameGraph/flamegraph.pl /tmp/out.folded > /tmp/out.svg
open /tmp/out.svg                                # 浏览器打开
```
读法口诀：**山尖是"此刻在跑什么"，山腰是"谁调用来的"，山底是入口。最宽的那条"山脊"就是主热点路径**，双击可放大某条调用链。

### 4.6 权限与实时性

| 问题 | 说明 |
|---|---|
| `perf_event_paranoid` | `cat /proc/sys/kernel/perf_event_paranoid`：2=非特权只能用户态、1=内核态也开、-1=全开；采样自己进程多要求 `<=2`，采样内核/他进程要 root |
| 采样开销 | `-F 99` 约 1% CPU 开销，可接受；`-g` 高频率在真实高频服务上会有可观开销，先低频率试 |
| 干扰 | perf 中断可能让 **RT 实时任务被抢占延迟**，实时系统（`SCHED_FIFO`）上用 perf 要谨慎，别给实时线程采样 |
| 降采样 | 大量短命进程（`-a` 全系统）会漏采短任务，关注的是热点占比而非绝对值 |

::: important `-F 99` 为什么不选 100
100 会与系统每秒的节拍（`timer`/HZ=1000）及采样同步，产生**周期共振**（每次都采到同一点，样本失真）。99 是 Brendon Gregg 推荐的质数采样频率，避免与任何固定周期对齐。
:::

## 5. bpftrace 与 eBPF

### 5.1 是什么

eBPF（extended Berkeley Packet Filter）是内核提供的一种安全可编程追踪框架：内核里运行经过验证的字节码，把程序挂到事件/函数上，**不用改内核、不用重启、不以 ptrace 停住目标进程**。`bpftrace` 是它的命令行封装——**一门"探针语言"，一行脚本查一个内核真相**。它通常比 strace 低开销，但不是零开销；探针命中频率、聚合方式和输出量仍决定实际成本。

```bash
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { printf("%s %s\n", comm, str(args->filename)); }'
```
每一行探针脚本结构：`探针 { 动作 }`。上面这句打印"每个进程打开文件的事件"——就是 `opensnoop` 的原型。

### 5.2 常用探针

| 探针类型 | 语法 | 挂载点 | 开销 |
|---|---|---|---|
| tracepoint | `tracepoint:syscalls:sys_enter_read` | 内核**已埋点**的静态位置 | 极低，生产首选 |
| kprobe | `kprobe:do_sys_openat2` | 任意内核函数入口（动态插桩） | 较低 |
| kretprobe | `kretprobe:do_sys_openat2` | 内核函数返回 | 较低 |
| uprobe | `uprobe:/usr/bin/myapp:myfunc` | 用户程序函数（需符号） | 较低 |

**能用 tracepoint 就别用 kprobe**：tracepoint 是内核作者维护的稳定接口，`kprobe` 跟着内核函数名走，内核升级函数名变了脚本就废了。

### 5.3 基本语法

```bash
sudo bpftrace -e 'BEGIN { printf("start\n"); }  END { printf("done\n"); }'
sudo bpftrace -e 'kprobe:vfs_read { @bytes = hist(arg2); }'   # 直方图
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @opens[str(args->filename)] = count(); }'
```
| 语法 | 作用 |
|---|---|
| `BEGIN`/`END` | 脚本开始/结束时执行一次 |
| `$var` 单美元符 | 临时变量，探针内有效 |
| `@map` 全局映射 | 跨探针累计，可当统计表/直方图 |
| `str()`/`comm`/`pid`/`uid` | 转换字符串、进程名、pid、uid |
| `hist(x)` | 生成对数刻度直方图（延迟/大小分布） |
| `count()`/`sum(x)`/`avg(x)`/`max(x)` | 聚合函数 |
| `printf` | 打印（格式符同 C） |

### 5.4 现成脚本（bpftrace 工具）

装好 bpftrace 后，`/usr/share/bpftrace/tools/` 里有几十个现成脚本，**别自己造轮子**：

```bash
sudo /usr/share/bpftrace/tools/opensnoop.bt      # 谁打开了什么文件
sudo /usr/share/bpftrace/tools/biolatency.bt     # 磁盘 IO 延迟直方图
sudo /usr/share/bpftrace/tools/execsnoop.bt      # 谁执行了什么命令
sudo /usr/share/bpftrace/tools/runqlat.bt        # 进程排队等待 CPU 的延迟
sudo /usr/share/bpftrace/tools/statssnoop.bt     # 谁改了文件状态
```

### 5.5 真实示例

**示例一：opensnoop 看谁打开文件**（怀疑有进程在疯狂读写某个目录）
```bash
sudo /usr/share/bpftrace/tools/opensnoop.bt 2>/dev/null | head -15
```
预期输出：
```
PID    COMM               FD ERR PATH
12345  myservice          13   0 /etc/app/config.yml
12345  myservice          14   0 /var/log/app.log
22222  logrotate           4   0 /var/log/app.log
22222  logrotate          -1   2 /var/log/other.log
```
解读：`myservice` 每次请求都打开 `config.yml`（应缓存却没缓存）；`logrotate` 对 `/var/log/other.log` 返回 `ERR 2`（ENOENT，文件已被轮转走）。**打开频率高到可疑的文件路径，就是热点与 bug 的入口。**

**示例二：biolatency 看 IO 延迟直方图**（怀疑磁盘慢）
```bash
sudo /usr/share/bpftrace/tools/biolatency.bt 2>/dev/null   # 跑 10 秒自动结束
```
预期输出：
```
Tracing block device I/O... Hit Ctrl-C to end.
     usecs               : count     distribution
         4 -> 8          : 1        |                                        |
         8 -> 16         : 4        |                                        |
        16 -> 32         : 18       |*                                       |
        32 -> 64         : 240      |*******************                     |
        64 -> 128        : 512      |****************************************|
       128 -> 256        : 68       |*****                                   |
       256 -> 512        : 12       |                                        |
```
解读：横轴是延迟区间（对数刻度）、`count` 是数量、`distribution` 可视化。峰值落在 64~128us，但**右尾拖到 512us 的 12 次**——"大部分快，偶尔巨慢"就是 IO 排队/磁盘抖动特征。对应 [IO 排查](/kb/os/问题排查/04-磁盘与IO瓶颈排查/)。

### 5.6 选型对比

| 维度 | perf | strace | bpftrace |
|---|---|---|---|
| 数据来源 | 采样（随机瞬间） | 系统调用序列（全量） | 事件/函数探针 |
| 开销 | 低 | 高（ptrace） | 极低（eBPF） |
| 生产可用 | 是 | 谨慎 | 是 |
| 能看到 | CPU 时间占比 | 每个 syscall | 任意内核/用户事件+参数 |
| 学习曲线 | 中 | 低 | 中高 |
| 典型问题 | 热点/火焰图 | 阻塞点/文件/网络 | 谁干了什么、分布统计 |

::: tip BCC 工具链
`bpftrace` 之外还有 Python 的 BCC 库（bcc/tools/ 下同样有 opensnoop、biolatency 等，功能更全、支持输出 CSV/JSON）。用 Python 写复杂 eBPF 程序走 BCC，一行脚本走 bpftrace，**生产日常排查先试 bpftrace 现成脚本**。
:::

## 6. valgrind：内存检测与剖析

### 6.1 memcheck：内存四大 bug 全捉

`valgrind` 是一个"虚拟机"：程序跑在它模拟的 CPU 上，每条内存读写都被检查。

```bash
gcc -g -O0 -o prog prog.c
valgrind --leak-check=full --show-leak-kinds=all ./prog
```
| 检测项 | 表现 | 典型报告 |
|---|---|---|
| 越界访问 | `Invalid read/write of size 4` | 数组越界、`strcpy` 超长 |
| 使用未初始化值 | `Conditional jump depends on uninitialised value` | 忘初始化变量 |
| 双重释放/非法释放 | `Invalid free()` | 同一指针 free 两次 |
| 内存泄漏 | `definitely lost / still reachable` | malloc 后没 free |

预期输出（`--leak-check=full`）：
```
==3210== Invalid write of size 4
==3210==    at 0x1091A2: main (prog.c:12)
==3210==    Address 0x4a2a040 is 0 bytes after a block of size 10 alloc'd
==3210==    at 0x4845D68: malloc (in .../vgpreload_memcheck)
==3210==    by 0x10917E: main (prog.c:10)
==3210== 
==3210== HEAP SUMMARY:
==3210==     in use at exit: 8 bytes in 1 blocks
==3210== LEAK SUMMARY:
==3210==    definitely lost: 8 bytes in 1 blocks
```
读法：先看 `Invalid ...` 的**行号**（`prog.c:12` 在写、`prog.c:10` 分配），"Address ... 0 bytes after a block" 意思是**写到了刚分配块末尾之外**；再看 `LEAK SUMMARY` 的 `definitely lost`（程序退出时还没释放且无指针可达）。

### 6.2 callgrind：性能剖析（谁在吃时间）

```bash
valgrind --tool=callgrind ./prog
callgrind_annotate callgrind.out.* | head -30
```
预期输出：
```
Ir         file:function
--------   ------------------------------------
5,218,422  ???:main
4,132,951  ???:compute_hash
1,200,010  ???:strlen
```
解读：`Ir`（instruction references）= 该函数累计执行的指令数。**不要用 callgrind 找 IO/锁瓶颈**——它只统计 CPU 指令，等 IO 的时间不计数。

### 6.3 massif：堆内存快照

```bash
valgrind --tool=massif ./prog
ms_print massif.out.* | head -60
```
输出一张"堆用量随时间"的 ASCII 图：内存**什么时候涨上去、涨到多大、峰值在哪个分配点**。配合 `--max-snapshots=50 --peak-inaccuracy=1` 看峰值处的调用栈，定位"内存为什么越用越多"。

### 6.4 慢与适用场景

::: warning valgrind 减速 10~50 倍
程序在模拟 CPU 上跑，还要逐条检查内存，**典型减速 10~50 倍**。大程序、真实负载跑不动；必须用**最小可复现用例**（减小数据量、缩短路径）。同类的 `-fsanitize=address`（编译期插桩）只慢 2 倍，是快速替代；valgrind 优势是不需要重编译、能查泄漏。
:::

| 工具 | 原理 | 减速 | 能查 | 适合 |
|---|---|---|---|---|
| valgrind memcheck | 虚拟机逐条检查 | 10~50x | 越界/未初始化/泄漏/重复释放 | 老二进制、无法重编译 |
| `-fsanitize=address` | 编译期插桩 | 2x | 越界/释放后使用 | 自己源码，快速 CI |
| `-fsanitize=leak` | 插桩 | 2x | 泄漏 | 自己源码，查泄漏 |
| `malloc_info`/`mtrace` | glibc 内置 | 低 | 堆分配统计 | 轻量排查 |
| `gdb` 手动 | 调试器 | — | 现场分析 | 已经崩了，看现场 |

## 7. 动态追踪选型总表

| 工具 | 解决什么问题 | 何时用 | 看到什么 | 权限 |
|---|---|---|---|---|
| `strace` | "进程卡在哪个系统调用？" | 阻塞/文件/网络问题，先在测试环境 | 系统调用序列+参数+返回值 | ptrace（同用户/root） |
| `ltrace` | "库函数调用平衡吗？malloc 配不配对？" | 怀疑库层逻辑、内存分配 | 动态库函数调用 | ptrace |
| `gdb` | "崩溃现场/变量值/死锁在哪？" | 有 core、能复现、需要交互 | 内存、栈、变量、寄存器 | ptrace |
| `perf` | "CPU 时间去哪了？" | CPU 高、无 CPU 时（采空闲） | 采样热点+调用链+计数器 | `perf_event_paranoid`/root |
| `bpftrace` | "内核/谁干了什么？延迟分布？" | 生产、低频、想低成本观测 | 任意事件+参数+统计 | root/CAP_BPF（`CAP_SYS_ADMIN`） |
| `coredumpctl`/`addr2line`/`eu-stack` | "core 对应哪个函数和行？" | 崩溃、SIGSEGV、服务重启 | core 元数据、符号、线程栈 | journal/core/符号文件权限 |
| `trace-cmd`/ftrace | "内核事件的时序是什么？" | 调度、唤醒、IRQ、block IO | tracepoint 事件时间线 | tracefs/root |
| BCC `execsnoop`/`opensnoop`/`biolatency`/`tcpconnect` | "谁执行、打开、发 IO、建连接？" | 生产低频事件定位 | 事件明细、延迟直方图、连接目标 | root/CAP_BPF |
| ASan/UBSan/TSan | "源码哪里有内存/未定义行为/竞态？" | CI、测试、最小复现 | 带源码行号的错误报告 | 需要重新编译 |
| `rr`/`heaptrack` | "偶发执行能否重放？堆是谁分配的？" | 非默认工具，测试或短时现场 | 可逆执行、分配调用栈 | ptrace/文件/调试符号 |

**选择逻辑一句话：先确定问题类型（阻塞/崩溃/CPU/内存），再选对应工具，从低成本向高成本升级：`perf/bpftrace`（低开销）→ `strace`（中，谨慎）→ `gdb`（重，停进程）。**

::: warning 权限与生产纪律
- `strace`/`ltrace`/`gdb` 走 **ptrace**：需要是同一用户，跨用户要 root；`kernel.yama.ptrace_scope=1` 时同用户也限制。
- `perf` 采样内核事件、`bpftrace` 挂内核探针：需要 **root** 或 `CAP_PERFMON`/`CAP_BPF`（老内核是 `CAP_SYS_ADMIN`）。
- **生产三条红线**：① 绝不整机 `strace -f -a`；② perf 用 `-F 99` 低频率限时；③ bpftrace 选现成脚本、先看 README 确认开销再挂。
:::

### 7.1 生产环境开销分级

| 等级 | 工具/用法 | 典型成本 | 生产策略 |
|---|---|---|---|
| L0 极低 | `nstat`、`ss -s`、`pidstat`、`perf stat` 短命令、eBPF tracepoint + `count/hist` | 主要是读取计数器或在内核聚合，通常低于 1% 量级，但依赖事件频率 | 可作为常规巡检；仍要限制输出、确认权限和采样窗口 |
| L1 低 | `perf record -F 49/99`、`bpftrace`/BCC 的单事件脚本、`trace-cmd` 少量 tracepoint | 采样中断、BPF map 和 ring buffer 有开销；高频事件/打印会放大成本 | 可短时生产使用，优先 PID/端口/cgroup 过滤，先记录开始/结束时间 |
| L2 中 | `perf -g`、`perf probe`、ftrace 事件、`trace-cmd` 多事件、`strace -P/-Z/-e trace=...` | 栈回溯、动态探针或 ptrace 会改变时序；`strace` 可能使高频 syscall 明显变慢 | 只在低峰短时使用；先在同版本压测环境验证，输出按敏感数据保存 |
| L3 高 | `strace -f` 全量、`strace -k/-kk`、`ltrace`、`gdb -p`/断点、`heaptrack`、`rr record` | 可能暂停线程、逐调用拦截、记录大量数据，破坏竞争和延迟现场 | 默认不直接用于高 QPS 生产；需要审批、限时、限 PID，并准备回滚/脱离方案 |
| L4 极高 | `valgrind`、TSan/ASan 测试构建、SysRq `c/b`、ftrace function_graph 全量 | 10~50 倍减速、数倍内存，或直接 panic/重启 | 仅隔离环境、故障演练或明确授权的单机现场；`SysRq c/b` 不属于普通调试 |

生产升级路径：先看 [监控篇](/kb/os/Bash/07-系统监控与性能命令/) 的 `pidstat`/`vmstat`/`iostat`，再用 L0/L1 缩小资源与 PID；仍需解释代码时从 L2 的限定追踪开始，L3/L4 只用于可复现、可回滚、已批准的诊断窗口。"eBPF 低开销"不等于"零风险"，事件频率、栈深度、字符串输出和 map/ringbuf 内存都要纳入预算。

## 8. 综合实战

### 8.1 实战一：服务偶发崩溃（core + gdb）

**症状**：`myservice` 每天凌晨随机段错误（segfault），日志无异常。
**思路**：段错误 = 非法内存访问。步骤：开 core → 复现 → `gdb` 看栈 → 读源码 → 修复。

```bash
ulimit -c unlimited                     # 1. 允许生成 core
# 复现后：systemd 默认 core 在 journald/var/crash，找到 core 文件
coredumpctl list                        # systemd 查 core 列表
coredumpctl info myservice              # 看 pid/时间/哪个二进制
```
```bash
gdb /usr/bin/myservice /var/crash/core.myservice -batch -ex bt
```
预期输出：
```
[New LWP 5123]
Core was generated by `/usr/bin/myservice --mode=worker'.
Program terminated with signal SIGSEGV, Segmentation fault.
#0  0x00007f4c2a55d4e7 in __strlen_avx2 () from libc.so.6
#1  0x0000555b1c401234 in parse_token (buf=0x0) at parser.c:42
#2  0x0000555b1c401567 in handle_line (line=...) at parser.c:88
#3  0x0000555b1c401abc in main_loop () at parser.c:150
```
解读：`#1` 的 `parse_token (buf=0x0)`——`buf` 是空指针，还拿去 `strlen`。回到源码 `parser.c:42`：
```c
size_t len = strlen(buf);   // 42 行：buf 可能为 NULL
```
修复：调用处 `handle_line` 里 `line` 为空就 return 才传给 `parse_token`。改法：入口判空 + 指针初始化。
```bash
# 验证：修完重新编译跑 24 小时压测，coredumpctl 不再增长
coredumpctl list | wc -l      # 应停在修复前的数量
```
**方法论**：偶发崩溃先 `ulimit -c unlimited` 保 core → `gdb -batch -ex bt` 提取崩溃栈 → 认 `#1` 以下业务函数 → 对照源码找"为什么是空指针"。更系统的流程见 [崩溃排查](/kb/os/问题排查/05-并发与异常排查/)。

### 8.2 实战二：CPU 热点（perf 火焰图）

**症状**：`myservice` 常驻 CPU 60%，load 居高不下，`top` 只看到 CPU 使用率高，不知道在干什么。

```bash
sudo perf record -F 99 -g -p $(pgrep -f myservice) -- sleep 30
perf script > /tmp/perf.script
/opt/FlameGraph/stackcollapse-perf.pl /tmp/perf.script > /tmp/out.folded
/opt/FlameGraph/flamegraph.pl /tmp/out.folded > /tmp/myservice.svg
```
火焰图读法（配图）：
```
main_loop ── parse_request ── json_parse ── strtod     (最宽山脊，80%)
                          └─ regex_compile              (小尖，偶发)
```
解读：最宽的山脊是 `json_parse → strtod`——**每个请求都解析 JSON 里的浮点数**，`strtod` 是 CPU 大户。进一步 `perf stat -e branch-misses ./bench` 确认分支预测正常后，优化方向明确：改用整数毫秒代替浮点、缓存解析结果。对应 [CPU 排查](/kb/os/问题排查/02-CPU性能问题排查/) 的完整流程。

::: tip 没有 CPU 也怕——off-CPU 采样
CPU 空闲但有延迟，火焰图是"空"的（时间不在 CPU 上）。此时换 `offcputime`（BCC：`/usr/share/bcc/tools/offcputime -K`）统计**线程离开 CPU 等在哪**，得到"阻塞时间火焰图"。CPU 忙→CPU 火焰图；CPU 闲→off-CPU 火焰图。
:::

### 8.3 实战三：IO 慢（biolatency）

**症状**：接口偶尔慢几百毫秒，`iostat` 看 `await` 平均不高，但 P99 差。

```bash
sudo /usr/share/bpftrace/tools/biolatency.bt 2>/dev/null   # 挂 60 秒抓全部盘 IO
```
预期输出：
```
     usecs               : count     distribution
        32 -> 64         : 812      |*****************************           |
        64 -> 128        : 1240     |****************************************|
       128 -> 256        : 98       |***                                     |
       256 -> 512        : 21       |                                        |
         512 -> 1024     : 3        |                                        |
         1024 -> 2048    : 2        |#                                       |
```
解读：平均延迟 ~70us 很健康，但**尾部有 2 次 1~2ms**——和接口 P99 慢对齐。这 2 次可能是：磁盘排队（IO 调度器在等）、同盘有 `fsync`/垃圾回收、或页面回收触发的同步写。再叠加：
```bash
sudo /usr/share/bpftrace/tools/biosnoop.bt 2>/dev/null   # 看哪次 IO 最慢、谁发的
```
定位到是**周期性备份任务的 `fsync` 大包写**抢占了正常流量。对应 [IO 排查](/kb/os/问题排查/04-磁盘与IO瓶颈排查/)：先分布（biolatency）→ 再单笔（biosnoop）→ 定位元凶 → 错峰或限流。

**三条排查线合并成一张表**：

| 问题 | 入口工具 | 深挖工具 | 输出 |
|---|---|---|---|
| 偶发崩溃 | `dmesg` + core | `gdb bt` | 崩溃函数+行号 |
| CPU 高 | `perf record -F 99 -g` | 火焰图/`perf stat` | 热点函数占比 |
| IO 慢 | `biolatency.bt` | `biosnoop.bt` + `iostat` | 延迟分布+元凶进程 |

## 本章小结

本章已经从六件工具扩展成一条"**从内核入口到内存内部**"的完整光谱：`strace`（系统调用序列、`-k/-P/-Z` 现版本过滤）→ `ltrace`（库调用）→ `gdb`/`coredumpctl`/`addr2line`/`eu-stack`（程序现场与符号）→ `perf`/`perf probe`（采样、计数器、动态探针、火焰图）→ `trace-cmd`/ftrace/SysRq（内核时序和卡死现场）→ `bpftrace` 与 BCC（事件探针和现成工具）→ sanitizer/`rr`/heaptrack/Valgrind（内存、并发、录制重放和堆分配）。心法：**先低成本后高成本**（监控篇 `pidstat`/`perf`/BPF → 限定 `strace` → gdb/heaptrack → Valgrind/TSan/rr）；崩溃看 core 对应的业务帧、CPU 看火焰图最宽山脊、IO 看直方图右尾、内存看 `Invalid`/ASan 行号与 PSS/RSS 趋势。生产分级见 7.1：L0/L1 可限时常规使用，L2 需要缩小事件，L3/L4 只在批准的复现窗口使用。全程回顾从 [总览](/kb/os/Bash/00-Bash命令学习路线总览/) 出发，监控基础见 [系统监控](/kb/os/Bash/07-系统监控与性能命令/)，符号与 ELF 见 [二进制与安全审计命令](/kb/os/Bash/16-二进制与安全审计命令/)。

## 动手实验

1. **gdb 调试小 C 程序**：写 `int main(){ char *s=NULL; printf("%s\n", s); }` 编译 `gcc -g -O0 -o t t.c`，`gdb ./t` 里 `run` 看到段错误，`bt` + `p s` 确认空指针，再用 `set var` 把 `s` 改成字符串继续跑——体会"改状态再运行"。
2. **strace -e trace=%file 看 ls**：`strace -e trace=%file -o /tmp/ls.tr ls /etc`，打开文件数一数 `openat` 出现了多少次、都打开哪些路径；再加 `-yy` 对比 fd 显示差异。
3. **perf stat 自测**：写个循环算 `sqrt` 一万次的小程序，`perf stat ./prog` 看 `IPC`；再 `perf stat -e cache-misses,instructions ./prog`，解释为什么 cache-misses 高或低。
4. **perf 火焰图自己生成**：`sudo perf record -F 99 -g -- sleep 5` 再 `perf script`，若能装 FlameGraph 就生成 SVG 并找出最宽函数；没有工具就 `perf report --stdio` 看前 10 个符号。
5. **bpftrace 现成脚本**：开一个终端跑 `sudo /usr/share/bpftrace/tools/opensnoop.bt`，另一个终端执行 `ls`/`cat`，观察每次打开文件的调用；再跑 `biolatency.bt` 同时 `dd if=/dev/sda of=/dev/null bs=4k count=10000` 看直方图形态。
6. **valgrind 泄漏检测**：写 `int main(){ malloc(100); return 0; }` 编译后 `valgrind --leak-check=full ./leak`，读出 `LEAK SUMMARY` 的 `definitely lost`；再故意越界写 `p[100]`，观察 `Invalid write` 报告与行号。
7. **core 与地址还原**：在测试二进制中执行 `ulimit -c unlimited; kill -SEGV $$` 或运行会崩溃的最小程序，用 `coredumpctl list/info` 找现场；用 `coredumpctl -o /tmp/test.core dump PID` 导出，再用 `gdb -batch -ex bt`、`addr2line -e binary -f -C OFFSET` 对照调试符号。
8. **strace 现版本过滤**：对会访问临时目录的程序运行 `strace -P /tmp -e trace=%file -Z -o /tmp/failed.tr ./prog`，检查只留下失败的路径调用；对小程序再试 `strace -k -e trace=futex ./prog`，比较栈信息和开销。不要对大服务使用全量 `-f -k`。
9. **tracefs 调度时序**：在测试 Linux 上执行 `sudo trace-cmd record -e sched_switch -e sched_wakeup -- sleep 5`，用 `trace-cmd report trace.dat` 找唤醒与切换；手工启用一个 ftrace event 后必须关闭 `tracing_on` 和 event enable。
10. **BCC 四件套**：安装 `bcc-tools` 后分别运行 `sudo execsnoop -T -P $$`、`sudo opensnoop -T -p $$`、`sudo biolatency -m 1 5`、`sudo tcpconnect -t -p $$`；另一个终端执行短命命令、读文件、制造临时 IO 和访问本地端口，记录 PID/路径/延迟/连接目标。
11. **Sanitizer 与 heaptrack**：对同一个越界或 data race 小程序分别用 `-fsanitize=address,undefined`、`-fsanitize=thread` 编译；再用 `heaptrack ./prog` 和 `heaptrack_print` 查看分配热点。比较错误定位能力、运行时间和内存占用，不把 instrumented 二进制当生产版本。
12. **rr 录制重放**：安装非默认 `rr` 后执行 `rr record ./prog`，用 `rr replay` 进入调试，尝试 `reverse-continue` 回到错误发生前；保存 trace 与精确二进制，实验结束清理 trace 目录。

## 自测题

1. **strace 的 `-c` 和 `-T` 分别回答什么问题？** `-c` 统计每类系统调用的次数/总耗时占比（"调用太多"的问题）；`-T` 看单次调用的耗时（"某次调用太慢"的问题）。
2. **`strace -e trace=%file ls /etc` 与 `strace ls /etc` 的区别？** 前者只跟踪文件类系统调用（openat/newfstatat 等），输出量小、聚焦文件；后者跟踪全部调用，量大、信号/内存调用混在一起。`%file` 是现版本推荐的集合名，旧的不带 `%` 写法仍常见但已弃用。
3. **gdb 里 `bt` 看到 `#0` 是 libc 的 `strlen`，说明崩溃在哪一层？怎么往下找业务原因？** 崩溃发生在库函数内部，但原因通常在更浅的帧：切 `frame 1` 看业务函数传了什么参数（如 `buf=0x0`），对照源码定位。
4. **`condition` 断点与 `ignore` 断点哪个更快？为什么？** `ignore` 更快：它是纯计数器，不反复求值；`condition` 每次命中都要计算条件表达式，循环量巨大时有开销。
5. **perf 的 `-F 99` 为什么是 99 而不是 100？** 100 会与系统 1ms 节拍周期共振，采样点对齐导致样本失真；99 是质数频率，避开所有固定周期。
6. **火焰图最宽的"山脊"和最高的"山尖"分别告诉我们什么？** 最宽山脊是累计占用 CPU 最多的调用路径（优化目标）；山尖是此刻正在执行的叶子函数（具体的指令热点）。
7. **为什么生产上优先 bpftrace 而不是 strace？** bpftrace 走 eBPF 探针，每次事件只在探针点执行一小段字节码，开销远低于 strace 的 ptrace（每次系统调用入口+出口全停），且只采样、不改程序行为。
8. **valgrind 报告 `Invalid write of size 4 ... 0 bytes after a block of size 10` 怎么解读？** 往一个 10 字节的堆块**末尾之外**写了 4 字节（越界），堆块在报告下方的 `alloc'd` 处分配（看行号定位分配点），配合函数栈行号找越界写入语句。
9. **`coredumpctl list`、`info`、`dump`、`debug` 分别做什么？** `list` 列索引，`info` 看元数据/摘要栈，`dump` 导出 core，`debug` 默认调用 gdb。导出的 core 必须和同一构建版本的 ELF、debuginfo 配套。
10. **为什么 `addr2line` 对 PIE 的绝对地址常返回 `??:0`？** ASLR 使模块加载基址变化，`addr2line` 需要 ELF 内的相对地址；先从 mappings 找基址并做地址换算，同时确认调试符号没有丢失。
11. **`strace -P`、`-Z`、`-k` 各自回答什么问题？** `-P` 限定访问路径，`-Z` 只看失败 syscall，`-k` 在 syscall 后打印用户栈；`-kk` 还请求源码信息。它们都应和小的 `-e trace=` 集合、短时间窗口配合。
12. **ftrace/trace-cmd、perf、BCC 的边界是什么？** ftrace/trace-cmd 适合内核事件时序，perf 适合采样和硬件计数器，BCC 适合用 eBPF 对事件做过滤/聚合；三者都比 ptrace 全量拦截更适合先做低成本观测，但高频探针仍会有开销。
13. **ASan/UBSan/TSan 分别抓什么？** ASan 抓越界、use-after-free 等地址错误，UBSan 抓多类未定义行为，TSan 抓数据竞争和部分同步问题；它们需要重新编译，TSan 的时间/内存成本通常高于 ASan。
14. **为什么 rr、heaptrack、Valgrind 不应直接挂到高 QPS 生产服务？** rr 要记录可重放输入，heaptrack 要记录分配事件，Valgrind 逐条模拟内存访问；它们会改变时序、产生大量敏感数据或显著减速，应放在测试、回放或批准的短时现场。
