::: abstract 本章定位
本篇是 Bash 系列的"最后一公里"：把本地命令延伸到远程主机。`ssh` 建立安全通道，`scp`/`sftp` 传文件，`rsync` 做增量同步，`tmux`/`screen` 解决"断线任务丢"的痛点。重点在**密钥认证原理**与**rsync 增量机制**两块硬核内容。前置是 [网络篇](/kb/os/Bash/06-网络命令/) 的连接层知识，安全加固见 [SSH 加固](/kb/os/Linux/06-Linux安全权限与审计/)，排障思路呼应 [排查方法论](/kb/os/问题排查/00-系统问题排查方法论/)。硬件、网络参数与工具选型分别交叉到 [内核模块硬件与系统参数命令](/kb/os/Bash/17-内核模块硬件与系统参数命令/) 和 [现代高效命令行工具](/kb/os/Bash/20-现代高效命令行工具/)。
:::

## 1. SSH 基础

### 1.1 `ssh`：建立安全连接

```bash
ssh user@192.168.1.100      # 常规连接，默认 22 端口
ssh -p 2222 user@host       # 指定端口（服务器改过端口时）
ssh -i ~/.ssh/id_ed25519 user@host   # 指定私钥
ssh -v user@host            # 调试模式，打印握手全过程
```

预期输出（`-v` 时追加）：
```
debug1: Reading configuration data /etc/ssh/ssh_config
debug1: Connecting to host port 22.
debug1: Server host key: ssh-ed25519 SHA256:fW...
debug1: Authentication succeeded (publickey).
Last login: Mon Aug 10 09:12:33 2026 from 192.168.1.1
```

解读：
- 语法是 `ssh [选项] [user@]host`，不写 `user` 时默认用本地当前用户名。
- `-p` 指远端 sshd 监听的端口，SSH 官方默认 22；`-i` 指定私钥文件，优先级高于默认路径。
- `-v`（verbose）打印三个阶段的日志：**配置加载 → TCP/握手 → 认证**，连不上时先 `-v` 再看报错。
- 首次连接会提示 `The authenticity of host ... can't be established.`，输入 `yes` 后指纹写入 `~/.ssh/known_hosts`。

::: tip 连不上三板斧
1. `ssh -v` 看到底卡在"网络""host key"还是"认证"；2. 检查端口：`-p` 不写就按 22 连，服务器改端口必报 `Connection refused`；3. 检查目标主机防火墙（呼应 [网络实操](/kb/os/Linux/05-Linux网络与系统调用实操/) 的 `ss -ltnp`）。这是 [排查方法论](/kb/os/问题排查/00-系统问题排查方法论/) 里的"分层定位"。
:::

### 1.2 `~/.ssh/config`：别老写长命令

```bash
mkdir -p ~/.ssh && chmod 700 ~/.ssh
cat >> ~/.ssh/config <<'EOF'
Host webprod
    HostName 192.168.1.100
    User deploy
    IdentityFile ~/.ssh/id_ed25519
    Port 2222

Host db*  *.internal
    User admin
EOF
```

配置写好后的用法：
```bash
ssh webprod        # 等价于 ssh -p 2222 deploy@192.168.1.100 -i ~/.ssh/id_ed25519
scp a.log webprod:/tmp/    # config 对 scp/rsync 同样生效
```

| 配置项 | 作用 | 示例 |
| --- | --- | --- |
| `Host` | 别名，可含通配符 `*`/`?` | `Host webprod`、`Host db*` |
| `HostName` | 真实主机名/IP | `HostName 192.168.1.100` |
| `User` | 登录用户名 | `User deploy` |
| `IdentityFile` | 私钥路径 | `IdentityFile ~/.ssh/id_ed25519` |
| `Port` | 连接端口 | `Port 2222` |

解读：SSH 客户端可能匹配多个 `Host` 段，但**每个参数通常采用第一次获得的值**，所以具体主机段应放在宽泛的 `Host *` 之前，通用默认值放在后面。用 `ssh -G` 查看最终值，不要只靠目测推断。用户 config 建议权限 `600`，目录权限 `700`；权限/属主不安全时 OpenSSH 会拒绝使用。

### 1.3 密钥认证原理：公钥锁、私钥钥匙

```bash
ssh-keygen -t ed25519 -b 256 -C "zhang@work" -f ~/.ssh/id_ed25519
```

预期输出：
```
Generating public/private ed25519 key pair.
Enter passphrase (empty for no passphrase):
Your identification has been saved in /home/zhang/.ssh/id_ed25519
Your public key has been saved in /home/zhang/.ssh/id_ed25519.pub
```

| 参数 | 含义 | 说明 |
| --- | --- | --- |
| `-t` | 算法类型 | `ed25519`（推荐）/ `rsa` / `ecdsa` |
| `-b` | 密钥长度 | RSA 至少 `3072`；ed25519 固定 256 可省略 |
| `-C` | 注释 | 通常写"谁在用这把钥匙"，进 `.pub` 文件尾部 |
| `-f` | 输出路径 | 默认 `~/.ssh/id_ed25519` |

解读：
- 生成的是一对钥匙：`id_ed25519`（**私钥，留本地，永不出机器**）和 `id_ed25519.pub`（**公钥，可公开，放到服务器的 `authorized_keys`**）。
- 认证时服务器用公钥发起"签名挑战"，客户端用私钥签名应答。私钥被锁在本地，即使服务器被黑，攻击者也拿不到能冒充你的私钥——这就是"**私钥在本地、公钥在服务器**"的信任模型。
- passphrase 是可选的二次保护：就算私钥文件被偷，没有口令也解不开。安全细节见 [SSH 加固](/kb/os/Linux/06-Linux安全权限与审计/)。

::: note 裸公钥与 SSH certificate
最常见的 `authorized_keys` 是逐把登记的裸公钥信任；OpenSSH 也原生支持由 SSH CA 签发的短期 user/host certificate，适合大量主机集中管理。它不是 X.509/HTTPS 证书体系，签发与信任配置见 1.9 节。服务器身份的传统信任锚仍是 `known_hosts` 中的 host key，也可改为信任 host CA。
:::

### 1.4 `ssh-copy-id`：一键部署公钥

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub user@host
```

预期输出：
```
/usr/bin/ssh-copy-id: INFO: Source of key(s) to be installed: ".../id_ed25519.pub"
user@host's password:
Number of key(s) added: 1
```

解读：工具本质是把本地公钥**追加**到远端 `~/.ssh/authorized_keys` 并设好权限。第一次部署时还需要密码，此后就能免密登录。没有 `ssh-copy-id` 时手写等价命令：

```bash
cat ~/.ssh/id_ed25519.pub | ssh user@host 'mkdir -p ~/.ssh && chmod 700 ~/.ssh && cat >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys'
```

### 1.5 权限要求：太"开放"会被拒绝

```bash
ls -ld ~/.ssh ~/.ssh/authorized_keys
# drwx------ 2 deploy deploy 4096 ... .ssh
# -rw------- 1 deploy deploy 123 ... authorized_keys
```

| 路径 | 权限 | 原因 |
| --- | --- | --- |
| `~/.ssh` | `700` | 目录可被他人写/读会导致密钥文件被替换 |
| `~/.ssh/authorized_keys` | `600` | 只允许属主读写 |
| 私钥文件 | `600` | 泄漏即等于交出登录权 |

解读：OpenSSH 对关键文件权限极其敏感。如果看到 `Bad owner or permissions on /home/user/.ssh` 或 `Permissions 0644 for 'key' are too open`，就是权限过宽。修复：`chmod 700 ~/.ssh && chmod 600 ~/.ssh/*`。这是 [SSH 加固](/kb/os/Linux/06-Linux安全权限与审计/) 的最小权限原则在本章的落地。

### 1.6 `known_hosts` 与 host key

```bash
cat ~/.ssh/known_hosts
# 192.168.1.100 ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA...
ssh-keygen -F 192.168.1.100      # 查某台主机的指纹
ssh-keygen -R 192.168.1.100      # 删除某台主机记录（服务器重装后必用）
```

解读：`known_hosts` 存的是**服务器身份**（host key 指纹），用来防止中间人冒充。服务器重装系统后 host key 变了，再连接会报 `REMOTE HOST IDENTIFICATION HAS CHANGED`，此时用 `ssh-keygen -R` 清掉旧记录即可——**不要**在看到该警告时盲选 yes，要先确认服务器确实是你以为的那台。

### 1.7 `ssh-agent` / `ssh-add`：缓存解密后的密钥能力

给私钥设置 passphrase 后，不必每次连接都重复输入，可以让 `ssh-agent` 在当前登录会话里提供签名服务：

```bash
eval "$(ssh-agent -s)"                  # 当前 shell 启动 agent 并导出环境变量
ssh-add -t 8h ~/.ssh/id_ed25519         # 加载私钥，8 小时后自动移除
ssh-add -l                              # 列出已加载密钥的指纹
ssh-add -L                              # 输出已加载公钥
ssh-add -d ~/.ssh/id_ed25519            # 移除指定密钥
ssh-add -D                              # 移除 agent 中全部密钥
```

预期输出片段：

```text
Agent pid 23145
Identity added: /home/zhang/.ssh/id_ed25519 (zhang@work)
256 SHA256:AbCd... zhang@work (ED25519)
```

解读：agent 不把私钥复制到远端，而是通过 `$SSH_AUTH_SOCK` 接收签名请求；`-t 8h` 限制驻留时间，`ssh-add -c` 还可要求每次使用前确认，但桌面确认程序的支持因环境而异。桌面 Linux、macOS、systemd user session 可能已启动 agent，先用 `ssh-add -l` 检查，避免套娃式启动多个 agent。

::: warning agent forwarding 扩大信任边界
`ssh -A`/`ForwardAgent yes` 把签名 socket 转发给远端。远端 root 或已入侵进程虽读不到私钥文件，却可能在连接期间借你的 agent 登录其他主机。默认保持 `ForwardAgent no`，跳板优先用 `ProxyJump`；确需转发时只给受信主机、给密钥加 `-t`/`-c`，用完 `ssh-add -D`。
:::

### 1.8 `ssh-keyscan`、指纹核验与 `ssh -G`

```bash
ssh-keyscan -T 5 -t ed25519,rsa host.example.com
ssh-keyscan -p 2222 -H host.example.com >> ~/.ssh/known_hosts
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub     # 在服务器控制台取真实指纹
ssh -G webprod | less                               # 展开最终客户端配置，不发起连接
ssh -G webprod | grep -E '^(hostname|user|port|identityfile|proxyjump) '
```

预期输出片段：

```text
host.example.com ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA...
hostname 192.168.1.100
user deploy
port 2222
identityfile ~/.ssh/id_ed25519
```

参数与解读：`ssh-keyscan` 的 `-T` 是超时秒数，`-t` 限 host key 类型，`-p` 指端口，`-H` 对输出中的主机名做哈希；适合自动收集 key 和生成候选清单。`ssh -G` 只展开 `~/.ssh/config`、`Include`、通配段及命令行选项，正适合排查“为什么用了错误用户/密钥/跳板”。

::: warning keyscan 只收集，不验证
`ssh-keyscan` 不认证对端，直接把网络返回值追加到 `known_hosts` 仍可能固化中间人 key。应通过云控制台、带外终端、资产平台或管理员提供的独立渠道比对 `ssh-keygen -lf` 指纹。`StrictHostKeyChecking=no` 也不应成为生产自动化的默认值。
:::

### 1.9 SSH certificate / CA 简介

规模化环境可让 CA 签用户公钥，服务端只信 CA，不再给每台机器逐条维护所有人的 `authorized_keys`：

```bash
# CA 管理机：CA 私钥应离线/受控保存，不放到普通登录服务器
ssh-keygen -t ed25519 -f user_ca -C 'SSH User CA'

# 给 alice 的公钥签一张 8 小时证书；-I 是审计标识，-n 是允许登录的 principal
ssh-keygen -s user_ca -I alice-20260810 -n alice -V +8h ~/.ssh/id_ed25519.pub

# 检查生成的证书字段、有效期、principal 和 CA 指纹
ssh-keygen -L -f ~/.ssh/id_ed25519-cert.pub
```

预期输出片段：

```text
Type: ssh-ed25519-cert-v01@openssh.com user certificate
Signing CA: ED25519 SHA256:CaFingerprint...
Key ID: "alice-20260810"
Valid: from 2026-08-10T09:00:00 to 2026-08-10T17:00:00
Principals:
        alice
```

服务端把 `user_ca.pub` 放到只允许 root 修改的位置，并在 `sshd_config` 配置：

```text
TrustedUserCAKeys /etc/ssh/user_ca.pub
```

客户端通常把 `id_ed25519-cert.pub` 与私钥放在同目录，OpenSSH 会自动发现；也可在 config 中显式设置 `CertificateFile`。host certificate 则反过来：服务器 host key 由 host CA 签名，客户端在 `known_hosts` 用 `@cert-authority` 信任该 CA，从而避免逐主机登记 host key。

::: important CA 安全与吊销
CA 私钥泄漏意味着可伪造整个信任域，必须离线保存、最小化签发权限并记录 `Key ID`。生产证书应短有效期、principal 最小化；紧急撤销可用 `RevokedKeys`/KRL（`ssh-keygen -k/-u`）。OpenSSH certificate 不是公网 X.509，发行版较老时先确认 `sshd -T` 与 `man sshd_config` 支持相应指令。
:::

## 2. SSH 高级

### 2.1 远程执行命令

```bash
ssh user@host 'hostname; uptime; df -h /'   # 一次性执行多条
ssh user@host 'cat /var/log/nginx/access.log | tail -5'
ssh user@host 'systemctl is-active nginx'
```

解读：`ssh host 'cmd'` 不在本地开交互 shell，把命令串交给远端执行并返回结果。注意引号：本地 shell 会先展开变量，想传 `$HOME` 给远端就**必须用单引号**包住整串命令。

::: warning 远程 sudo 要加 `-t`
`ssh host 'sudo systemctl restart nginx'` 会报 `sudo: no tty present and no askpass program specified`。因为 sudo 需要交互式 tty 要密码，而 `ssh 'cmd'` 默认不分配 tty。解决：`ssh -t host 'sudo systemctl restart nginx'`，`-t` 强制分配伪终端。
:::

### 2.2 代理跳转 `ProxyJump`

```bash
# 通过跳板机 bastion 登录内网目标机（目标机不暴露公网）
ssh -J user@bastion.example.com webuser@10.0.0.5
```

解读：`-J`（ProxyJump）把连接交给跳板机转发，链路上每一跳都用 SSH 加密，且支持链式 `user@host1,user@host2`。也可写进 config：

```bash
Host inner
    HostName 10.0.0.5
    User webuser
    ProxyJump user@bastion.example.com
```

### 2.3 端口转发：SSH 是加密的隧道

```bash
ssh -L 8080:127.0.0.1:3306 user@host   # 本地转发：本机8080 → 远端127.0.0.1:3306
ssh -R 9000:127.0.0.1:80 user@host     # 远程转发：远端9000 → 本机80
ssh -D 1080 user@host                  # 动态转发：本机1080做 SOCKS5 代理
```

| 类型 | 参数 | 流向 | 典型场景 |
| --- | --- | --- | --- |
| 本地转发 | `-L` | 本机端口 → 远端目标 | 本机浏览器连内网数据库/管理台 |
| 远程转发 | `-R` | 远端端口 → 本机目标 | 把内网服务暴露给远端访问 |
| 动态转发 | `-D` | 本机 SOCKS 代理 | 全流量走代理，当梯子用 |

解读：隧道建立后，访问 `localhost:8080` 的数据会被加密送到远端，再由远端转发到 `127.0.0.1:3306`。全程不暴露明文，比直连安全。`-N` 表示"只建隧道不执行命令"，配合 `-f` 放后台使用。

### 2.4 KeepAlive 与连接复用

```bash
ssh -o ServerAliveInterval=60 -o ServerAliveCountMax=3 user@host
# 60秒发一次心跳，3次无响应才判定断开，告别"挂一会就断"
ssh -o ControlMaster=auto -o ControlPath=/tmp/ssh-%r@%h:%p user@host
# 首个连接建立后，后续连接复用同一条 TCP，秒连
```

解读：`ServerAliveInterval` 解决 NAT/防火墙把空闲连接杀掉的问题；`ControlMaster=auto` 让同一目标主机的多次 `ssh`/`scp`/`rsync` 共享连接，省掉重复握手。以上可写进 config 全局生效。

### 2.5 排查："改了端口就连不上"

- 现象：原本 `ssh host` 正常，管理员把 sshd 端口改成 2222 后本地仍用 22，报 `Connection refused`。
- 思路（呼应 [排查方法论](/kb/os/问题排查/00-系统问题排查方法论/) 的分层定位）：
  1. `ssh -v -p 2222 user@host` 看连接阶段；`nc -vz host 2222` 确认端口通不通（`nc` 见 [网络篇](/kb/os/Bash/06-网络命令/)）。
  2. 通但认证失败 → 查密钥与 config；不通 → 查防火墙（`firewall-cmd`/`ufw`）与 SELinux 是否放行新端口。
  3. 确认 `sshd` 真的在监听：`ss -ltnp | grep 2222`（该命令见 [监控篇](/kb/os/Bash/07-系统监控与性能命令/)）。
- 教训：所有参数只要有一个没同步（config 的 Port、防火墙规则、`-p`），表现就是"连不上"，**先加 `-v` 分层，别瞎猜**。

### 2.6 远程变更防锁死流程

修改 `sshd_config`、监听地址/端口、路由或防火墙时，严格按以下顺序执行：

1. **保留现有会话**：不要退出当前 SSH；另开一个终端准备测试，确认云控制台/串口/KVM 等带外入口可用。
2. **记录回滚材料**：备份 SSH 与防火墙配置，记录当前来源 `echo "$SSH_CONNECTION"`、监听 `ss -ltnp`、路由和当前规则；准备明确的恢复命令。
3. **先验证配置**：`sudo sshd -t` 做语法检查，`sudo sshd -T | grep -E '^(port|listenaddress|passwordauthentication|pubkeyauthentication)'` 看服务端最终值；客户端用 `ssh -G 别名` 检查目标参数。
4. **先加后删**：先放行新端口/新来源，保留旧 SSH 规则；涉及 SELinux 的 RHEL 系还要检查端口标签。只 `reload` sshd，避免无必要的 `restart`。
5. **服务端验证**：`ss -ltnp | grep sshd` 确认真正在新端口监听，再从第二个终端发起一条**全新连接**并执行 `id`/`sudo -v`。
6. **最后收口**：新连接验证成功后才移除旧端口/旧规则；再次重连验证，并把运行时防火墙规则持久化。失败时保持旧会话，立刻回滚，不要继续叠加修改。

改 sshd 时的定时回滚（脱离当前会话执行，断线也会生效）：

```bash
# 备份并安排 10 分钟后自动恢复 sshd 配置
sudo cp /etc/ssh/sshd_config /root/sshd_config.rollback
sudo systemd-run --on-active=10min --unit=sshd-rollback /bin/sh -c \
  'cp /root/sshd_config.rollback /etc/ssh/sshd_config && sshd -t && systemctl reload sshd'

# 改配置 → 语法校验 → 只 reload，不 restart
sudo sshd -t
sudo sshd -T | grep -E '^(port|listenaddress|permitrootlogin|passwordauthentication|pubkeyauthentication) '
sudo systemctl reload sshd

# 从第二个终端建立全新连接（禁用连接复用，避免复用旧 TCP 假装成功）
ssh -o ControlMaster=no -o ControlPath=none -o ProxyCommand=none -p <新端口> user@host 'id; sudo -n true'

# 验证通过后取消回滚
sudo systemctl list-timers sshd-rollback.timer
sudo systemctl stop sshd-rollback.timer
```

解读：`systemd-run --on-active` 把恢复动作交给 systemd，即使 SSH 断开也会按时执行，比 `sleep 600 && cp ...` 挂在当前 shell 可靠。回滚脚本里先 `sshd -t` 再 reload，避免恢复的是一份坏配置。`sshd -T` 打印服务端最终生效值，比 `grep` 配置文件准确，因为 `Include`、`Match` 和默认值都会影响结果。`reload` 不会踢掉已建立会话，`restart` 在部分配置下更容易造成失联，所以优先 reload。防火墙侧的 `--timeout`、`iptables-apply -t` 与原子加载流程见 [防火墙与网络安全命令](/kb/os/Bash/15-防火墙与网络安全命令/)。

没有 systemd 时的替代：`echo 'cp /root/sshd_config.rollback /etc/ssh/sshd_config && systemctl reload sshd' | sudo at now + 10 minutes`（需 `at` 包与 `atd` 服务），或 `sudo setsid sh -c 'sleep 600; ...' </dev/null >/dev/null 2>&1 &` 让任务脱离终端会话组。

::: warning 现有连接不断不等于规则正确
conntrack 可能继续放行已建立的 SSH 会话，所以“当前终端还能敲命令”不能证明新连接可用。**必须显式禁用连接复用**验证：`ControlMaster=auto` 环境下 `ssh` 会复用现有 master 连接，即使新端口/新规则完全不通也能进入 shell，这是最常见的假阳性。同时确认带外入口（云控制台 VNC、串口、KVM）当前真的能登录，而不只是"应该有"。防火墙工具的保命规则、超时回滚与原子加载流程见 [防火墙与网络安全命令](/kb/os/Bash/15-防火墙与网络安全命令/)。
:::

### 2.7 `autossh`：自动重建 SSH 隧道

`autossh` 不是 OpenSSH 自带命令，需安装同名 `autossh` 包。它监视 ssh 子进程并在连接失效后重启，适合长期反向隧道或运维通道：

```bash
AUTOSSH_GATETIME=0 autossh -M 0 -N \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
  -R 127.0.0.1:9000:127.0.0.1:22 tunnel@bastion.example.com
```

预期日志片段（前台或 systemd journal）：

```text
starting ssh (count 1)
ssh child pid is 18422
```

参数与解读：`-M 0` 关闭 autossh 自己的监控端口，依赖 OpenSSH keepalive 检测失效；`-N` 不执行远端命令；`ExitOnForwardFailure=yes` 让端口绑定失败立即退出，由 autossh 重试；`AUTOSSH_GATETIME=0` 让首次失败也持续重启。`-R 127.0.0.1:...` 只让跳板机本机访问该端口，若改成公网监听还受 sshd `GatewayPorts` 和防火墙约束。

::: warning 生产应交给 systemd
不要把 autossh 私钥做成无约束的通用登录钥匙。使用专用账号和 `authorized_keys` 限制（如禁 PTY/agent/X11，按需限制转发目的），在 systemd 中设置 `Restart=always`、环境和日志；建立反向入口前还要获得授权并记录资产归属。
:::

### 2.8 `mosh`：高延迟、漫游网络上的交互终端

`mosh` 非默认安装，客户端和服务端都需安装 `mosh` 包。它先用 SSH 做认证并启动服务端，交互数据再走 UDP，能在 Wi-Fi/移动网络切换 IP 后恢复：

```bash
mosh user@host
mosh --ssh='ssh -p 2222' user@host
mosh --server='mosh-server new -p 60001' user@host
```

预期输出通常直接进入远端 shell；调试时服务端会给出类似：

```text
MOSH CONNECT 60001 key-material
```

解读：`--ssh` 只影响启动阶段的 SSH 参数；会话数据默认使用 UDP 60000-61000，固定 `-p 60001` 可把防火墙收窄到单端口。mosh 对高延迟输入有本地回显，网络恢复后自动续接，适合移动办公。

::: note mosh 不是 SSH 的完整替代
它不提供 SSH 的 `-L/-R/-D`、agent/X11 forwarding，也不适合非交互命令/文件传输；UDP 被企业网或 NAT 拦截时会失败。认证仍依赖 SSH，UDP 流量由 mosh 自身加密；服务端 locale 必须兼容 UTF-8。长期任务仍放在 tmux 中，mosh 只解决传输层漫游。
:::

## 3. scp：基于 SSH 的文件复制

```bash
scp local.txt user@host:/home/user/          # 上传到远端目录
scp user@host:/var/log/app.log ./            # 下载到本地
scp -r ./config/ user@host:/etc/myapp/       # -r 递归整个目录
scp -P 2222 -i ~/.ssh/id_ed25519 big.bin user@host:/data/
scp -O legacy@old-host:/path/old.tar ./       # 强制旧 SCP 协议，仅兼容老服务器
```

| 参数 | 作用 | 说明 |
| --- | --- | --- |
| `-r` | 递归复制目录 | 不加 `-r` 复制目录会报错 |
| `-P` | 指定远端端口 | **大写 P**，与 `ssh -p` 小写相反，历史遗留坑 |
| `-i` | 指定私钥 | 同 `ssh -i` |
| `-C` | 压缩传输 | 文本文件省带宽，已压缩文件反而更慢 |
| `-O` | 强制 legacy SCP 协议 | 仅兼容旧服务端/依赖 shell 通配语义时使用 |

解读：`scp` 语法与 `cp` 相同，只是 `远端路径` 写作 `user@host:path`。`:` 前后要分清：冒号左边是主机、右边是远端路径，**路径是相对远端用户家目录的**。数据全程走 SSH 加密通道，安全无需额外配置。

::: note OpenSSH 新版的协议差异
OpenSSH 9.0 起 `scp` 默认使用 **SFTP 协议**，安全语义更清晰，也不依赖远端 shell 展开路径；`-O` 才退回旧 SCP/RCP 协议。旧协议会让远端 shell 解释通配符和特殊字符，服务端路径检查也更脆弱，因此只在老服务器不支持 SFTP 或旧脚本确实依赖该行为时临时使用，并对路径完整引用。`scp -T` 会关闭严格文件名检查，不是常规兼容开关。
:::

| 对比项 | `scp` | `rsync` |
| --- | --- | --- |
| 传输方式 | 全量复制 | 增量（只传差异块） |
| 断点续传 | 不支持 | `--partial` 支持 |
| 保留属性 | `-p` 手动 | `-a` 默认全套 |
| 两端一致性 | 不做校验 | 边传边校验 |
| 场景 | 单次少量文件 | 反复同步/大文件/备份 |

::: warning 大文件传输注意
`scp` 一次性全量复制，大文件中断就得重来。传几个 GB 以上的文件优先 `rsync -P`；另外大文件别开 `-C` 压缩（CPU 白烧且可能更慢），本地网速慢可改用 `rsync --bwlimit` 限速。
:::

## 4. sftp：交互式安全传输

```bash
sftp user@host        # 进入交互式 shell，提示符变为 sftp>
```

交互式命令示例：
```
sftp> ls -l                    # 列远端目录
sftp> cd /var/www              # 切换远端目录
sftp> lcd /tmp                 # 切换本地目录（l 前缀=本地）
sftp> put local.txt ./         # 上传
sftp> get remote.log ./        # 下载
sftp> get -r data/ ./          # -r 递归下载目录
sftp> mget *.log               # 批量下载
sftp> exit                     # 退出（或 bye / Ctrl+D）
```

批量脚本（`man sftp` 支持 `-b` 批处理）：
```bash
cat > /tmp/upload.sftp <<'EOF'
lcd /tmp
put report.txt /home/user/uploads/
get /var/log/app.log ./app.log
bye
EOF
sftp -b /tmp/upload.sftp user@host
```

预期输出片段：

```text
sftp> lcd /tmp
sftp> put report.txt /home/user/uploads/
Uploading report.txt to /home/user/uploads/report.txt
sftp> get /var/log/app.log ./app.log
```

解读：`-b file` 从批处理文件读取命令，遇到 `get`/`put`/`rename` 等失败默认中止并返回非零，适合 CI；命令前加 `-` 可忽略该条失败，前加 `@` 可禁止回显。批处理应使用密钥或其他非交互认证，并可加 `-oBatchMode=yes` 保证密码提示不会挂住任务。不要把密码写进 batch 文件。

| 场景 | 推荐工具 | 理由 |
| --- | --- | --- |
| 单次传几个小文件 | `scp` | 一条命令，不用交互 |
| 想在远端浏览目录再取文件 | `sftp` | 交互式 `ls`/`cd`，还能断点续传 |
| 大文件/反复同步/备份 | `rsync` | 增量 + 断点 + 校验 |
| 传输几百 GB 且要带宽控制 | `rsync --bwlimit` | 限速避免挤占生产带宽 |

## 5. rsync 核心：增量同步之王

### 5.1 本地同步与尾部斜杠语义

```bash
rsync -av /path/src/  /path/dst/     # 同步目录内容
rsync -av /path/src   /path/dst/     # 把 src 整个目录放进 dst
```

| 写法 | 结果 | 记忆法 |
| --- | --- | --- |
| `src/ dst/` | 复制 src 的**内容**到 dst | 有斜杠=只取内部 |
| `src dst/` | 复制 **src 目录本身**（成 dst/src/） | 无斜杠=连目录带 |
| `src/ dst` | 同第一行，dst 不存在则新建 | 目标斜杠不影响语义 |

预期输出（`-v` 文件清单后跟汇总）：
```
sending incremental file list
config/app.ini
config/db.yaml
index.html
          sent 2,048 bytes  received 231 bytes  4,558.00 bytes/sec
```

解读：斜杠差异是 rsync 最经典的坑。`rsync -av /data/ /backup/` 把 data 的内容合并进 backup；漏了斜杠会在 backup 下生成 `/backup/data/`。目标目录不要求为空，rsync 只"补齐差异"。

### 5.2 关键参数

```bash
rsync -avzP --delete /data/ user@host:/backup/
rsync -av --exclude='*.tmp' --exclude='cache/' /data/ /backup/
rsync -av --bwlimit=2000 /data/ user@host:/backup/   # 限速 2MB/s
rsync -avn /data/ /backup/                          # -n 干跑，只预览不真传
rsync -avx /data/ /backup/                          # -x 不跨越文件系统挂载点
rsync -avni --delete /data/ /backup/                 # -i/--itemize-changes 解释每项为何变化
rsync -av --checksum /data/ /backup/                 # 忽略 size+mtime 快速判断，读取内容校验
rsync -av --partial-dir=.rsync-partial /data/ user@host:/backup/
```

| 参数 | 作用 | 说明 |
| --- | --- | --- |
| `-a` | 归档模式 | 递归 + 保留权限/属主/时间戳/软链等，**日常必加** |
| `-v` | 显示明细 | verbose，看传输清单 |
| `-z` | 传输压缩 | 文本类收益大，已压缩媒体反而负优化 |
| `-P` | 进度 + 断点续传 | `--partial --progress` 的合体，传输中断后能续 |
| `-n` | 干跑 | dry-run，配合 `-v` 先看会动哪些文件 |
| `-x` | 不跨界 | 不同挂载点不递归，防把挂载盘整个拷走 |
| `--delete` | 删除目标端多余文件 | 镜像同步关键，**慎用**，见下方警告 |
| `--exclude` | 排除 | 支持通配与路径，可多次指定 |
| `--bwlimit` | 限速 | 单位 KB/s，别把生产带宽吃满 |
| `-i` / `--itemize-changes` | 输出变化码 | 审计新增、更新、属性变化和删除原因 |
| `-c` / `--checksum` | 按内容判断是否变化 | 两端读取所有文件，I/O 与 CPU 成本高 |
| `--partial-dir=DIR` | 集中保存未完成文件 | 重跑可复用，避免半成品混在目标根目录 |
| `--link-dest=DIR` | 未变化文件硬链接到基线 | 创建节省空间的多版本快照 |

::: warning `--delete` 是双刃剑
目标端任何源端没有的文件都会被删。备份场景常用"源 → 备份"单向，安全；但如果命令写反（方向错），灾难性删除会发生在源端。务必先用 `rsync -avn --delete` 干跑看清单，确认无误再真传。
:::

`--itemize-changes` 输出示例：

```text
>f.st...... config/app.ini
cd+++++++++ uploads/
*deleting   cache/old.bin
```

解读：`>` 表示文件发往接收端，`f` 是普通文件，`s`/`t` 表示大小/mtime 改变，`+++++++++` 表示新建，`*deleting` 表示目标删除。和 `-n` 组合可形成变更审计清单。`--checksum` 只改变“文件是否需要更新”的快速判断，传输时仍使用 rsync 校验机制；它会把两端所有候选文件读一遍，机械盘或海量文件场景可能比传输本身还慢。

### 5.3 远程同步：两种通道

```bash
# 方式一：ssh 通道（默认，推荐）
rsync -avz /data/ user@host:/backup/
# 方式二：rsync 守护进程协议
rsync -avz rsync://backup.example.com/data/ /local/
rsync -avz --port=873 /data/ rsync://backup.example.com/dest/
```

解读：rsync 默认走 SSH 认证与加密，语法与 `scp` 一致，config 里的别名同样生效。`rsync://` 走 rsync 专用守护进程（端口 873），需要在服务器配置 `/etc/rsyncd.conf`，适合服务端集中管理、只暴露指定模块的场合；数据默认不加密，公网慎用。`rsync -e 'ssh -p 2222'` 可给 SSH 通道传额外参数。

最小 rsync daemon 只读模块：

```ini
# /etc/rsyncd.conf
uid = nobody
gid = nogroup
use chroot = yes
max connections = 4
log file = /var/log/rsyncd.log

[releases]
    path = /srv/rsync/releases
    comment = Published releases
    read only = yes
    hosts allow = 10.0.0.0/24
    hosts deny = *
```

```bash
sudo rsync --daemon --no-detach --config=/etc/rsyncd.conf   # 前台验证；生产交给 systemd
rsync rsync://server/                                      # 列模块
rsync -av rsync://server/releases/ /srv/releases/
```

预期输出片段：

```text
releases       Published releases
receiving incremental file list
app-v2.4.0.tar.zst
```

解读：客户端双冒号语法 `server::releases` 与 `rsync://server/releases` 等价；模块名不是任意服务器路径。daemon 能做模块级只读、来源和连接数限制，但其传统 challenge-response 认证和数据流**都不是加密通道**，跨不可信网络应套 VPN/stunnel，或直接使用 SSH 模式。`gid` 在 RHEL 系可能用 `nobody` 而非 Debian 的 `nogroup`，服务单元及配置路径也应以发行版包为准。

### 5.4 增量同步原理：为什么 rsync 快

- **两端先比"元数据"**：大小 + mtime 相同 → 跳过；不同 → 只处理该文件，而不是整个目录重传。
- **文件级增量 = 只传变化文件**：这是大多数场景 90% 的速度来源。
- **块级增量（两端都有 rsync 时）**：接收端按文件大小选择块长并生成弱滚动校验 + 强校验，发送端滑动匹配，**只传目标文件缺失的字面数据和块引用**再重组。强校验算法由双方版本协商，不要把实现固定理解成 MD5；`rsync --version`/`--debug=NSTR` 可看协商能力。
- **配合硬链接快照**：`--link-dest` 让完全未变化的**文件**与上一版共用 inode，变化文件才占新空间；它不是“按块硬链接”。修改快照中的硬链接文件会影响共享 inode，归档目录应只读管理。

::: tip 记忆口诀
全量比较用 `diff`，同步补差用 `rsync`。rsync 是"聪明的 diff + 校验的 cp"：先看元数据省目录扫描，再看块哈希省文件传输。
:::

### 5.5 rsync 与 cp/scp 的对比

| 对比项 | `cp` | `scp` | `rsync -a` |
| --- | --- | --- | --- |
| 作用范围 | 本地 | 本↔远 | 本地/远↔远 |
| 增量 | 无 | 无 | 有 |
| 断点续传 | 无 | 无 | 有（`-P`） |
| 跳过未变化文件 | 无 | 无 | 有 |
| 保留权限/时间 | 部分 | 需 `-p` | 默认全套 |
| 加密通道 | 无 | 有 | 有（ssh 通道） |
| 限速/排除 | 无 | 无 | `--bwlimit`/`--exclude` |

::: note rsync 只能有一个远程端点
`rsync` 支持本地到远端或远端到本地，但不能像某些 `scp` 用法那样让两个端点都写成 `host:path`。远端到远端应登录其中一端执行 rsync，或在受控主机上分两段同步。
:::

### 5.6 同步技巧

```bash
# 备份：源到归档，加时间戳，保留增量
rsync -avP --delete /data/ /backup/current/ \
  && rsync -a /backup/current/ /backup/$(date +%Y%m%d)/

# 镜像：两端完全一致（先干跑再执行）
rsync -avn --delete /src/ /dst/
rsync -av --delete /src/ /dst/

# 保留软链接（-a 已含 --links），不跟随指向
rsync -av --links /opt/app/ user@host:/opt/app/

# 只同步指定模式
rsync -av --include='*/' --include='*.conf' --exclude='*' /etc/ /backup/etc/
```

`--link-dest` 日快照示例：

```bash
rsync -ani --delete --link-dest=../2026-08-09 \
  /data/ /backup/2026-08-10/              # 正式运行前先干跑
rsync -a --delete --link-dest=../2026-08-09 \
  /data/ /backup/2026-08-10/
```

解读：`--link-dest` 相对路径以**目标目录**为基准，所以 `../2026-08-09` 指前一天快照；源文件与基线属性/内容满足条件时在新目录创建硬链接。硬链接不能跨文件系统；基线不存在或选项路径算错时仍会完成同步，但退化为占更多空间的普通复制。快照目录应禁止业务写入，并用 `find ... -links +1`/`stat` 验证 inode 复用。

### 5.7 `rclone`：非默认的云存储同步工具

`rclone` 面向 S3、Google Drive、OneDrive、WebDAV 等对象/云存储，不是 rsync 的默认替代。多数发行版可安装 `rclone` 包，但官方版本迭代更快，生产应固定来源和版本并校验发布签名。

```bash
rclone config                              # 交互创建 remote，凭据写入配置
rclone listremotes                         # 列出 remote 名称，不打印 secret
rclone lsd cloud:                          # 列云端顶层目录/bucket
rclone copy ./reports/ cloud:backup/reports/ --progress
rclone sync ./reports/ cloud:backup/reports/ --dry-run --combined=-
rclone sync ./reports/ cloud:backup/reports/ --combined=-
rclone check ./reports/ cloud:backup/reports/ --one-way
```

预期输出片段：

```text
= report-01.pdf
+ report-02.pdf
- old-report.pdf
Transferred:       12.428 MiB / 12.428 MiB, 100%
Checks:                 42 / 42, 100%
```

解读：路径格式为 `remote:path`；`copy` 复制新增/变化对象而不删除目标多余项，`sync` 让目标镜像源并可能删除目标，必须先 `--dry-run`；`--combined=-` 用 `=` 相同、`-` 仅目标、`+` 仅源、`*` 内容不同、`!` 错误生成变化报告，概念类似但不等于 rsync `--itemize-changes`。`check` 比较两端，具体能否用哈希取决于后端是否提供兼容 checksum，某些对象存储的 ETag 不是文件 MD5。

::: warning 凭据与云端删除
`rclone.conf` 常含 refresh token/access key，默认路径可用 `rclone config file` 查看，应权限 `600`、使用系统 secret 管理或 `rclone config password` 加密，日志也不要开到泄露 header/token 的级别。云端最终一致性、版本控制和 API 限流因后端而异；关键同步开启 bucket versioning/保留策略，先 dry-run，再小范围执行。高级替代工具工作流见 [现代高效命令行工具](/kb/os/Bash/20-现代高效命令行工具/)。
:::

### 5.8 `sshfs`：按需挂载远端目录

`sshfs` 基于 FUSE/SFTP，把远端目录挂成本地文件系统。Linux 安装 `sshfs`（依赖 FUSE 3 的环境使用 `fusermount3`）；macOS 通常需额外安装 macFUSE 与兼容 sshfs 实现。

```bash
mkdir -p ~/mnt/project
sshfs user@host:/srv/project ~/mnt/project \
  -o IdentityFile="$HOME/.ssh/id_ed25519" \
  -o reconnect,ServerAliveInterval=15,ServerAliveCountMax=3
mount | grep sshfs
fusermount3 -u ~/mnt/project               # Linux；旧 FUSE 可能是 fusermount -u
# umount ~/mnt/project                     # macOS/BSD 常用
```

预期挂载信息片段：

```text
user@host:/srv/project on /home/zhang/mnt/project type fuse.sshfs (rw,nosuid,nodev,relatime,user_id=1000)
```

解读：`reconnect` 尝试断线重连，keepalive 缩短失效检测；权限仍同时受远端账号和本地 FUSE 映射约束。sshfs 适合交互浏览和轻量编辑，不适合数据库、锁语义敏感程序、海量小文件构建或高吞吐同步，这些场景用 rsync/rclone 或原生网络文件系统。

::: warning 挂载卡住时先停止使用者
断网后访问挂载点的进程可能阻塞。先让编辑器/任务离开目录，再正常卸载；`fusermount3 -uz` 是 lazy unmount，只在正常卸载失败且理解影响时使用。`allow_other` 会扩大本机可访问用户范围，还要求 `/etc/fuse.conf` 启用，不要为了省事默认添加。
:::

## 6. tmux：断线不丢任务的终端复用

### 6.1 为什么需要

```bash
ssh host
rsync -avP /big/ /backup/   # 假设要跑 3 小时
# 网络一断 → ssh 断开 → rsync 被杀 → 白干
```

解读：SSH 会话断开会把前台进程一并带走（收到 SIGHUP）。tmux 把终端会话挪到**服务器上独立运行**，本地断开只是"看不见"，进程继续跑；重新连上后 `tmux attach` 就能回到原样。远程部署、长任务、多窗口并行是它的主战场。

### 6.2 会话管理

```bash
tmux new -s deploy          # 新建会话并命名 deploy
tmux ls                     # 列出所有会话（别名 tmux list-sessions）
tmux attach -t deploy       # 重新附加到会话（-t 指定名）
tmux detach                 # 暂时离开：Ctrl+b 再按 d
tmux kill-session -t deploy # 结束会话（进程随之终止）
tmux new -d -s sync         # 后台新建会话，不进入
tmux kill-server            # 结束所有会话
```

| 命令 | 作用 |
| --- | --- |
| `tmux new -s NAME` | 新建命名会话 |
| `tmux ls` / `-ls` | 列出会话（`attached` 表示有人挂着） |
| `tmux attach -t NAME` | 重新进入会话 |
| `tmux detach`（Ctrl+b d） | 离开但会话继续跑 |
| `tmux kill-session -t NAME` | 杀死会话 |

### 6.3 窗口与窗格

```bash
# 窗口（window）：会话里可开多个独立"标签页"
tmux new-window -n log      # 新开窗口并命名 log
# 窗格（pane）：同一窗口内分屏
```

| 快捷键（先按 Ctrl+b 前缀） | 功能 |
| --- | --- |
| `Ctrl+b` `%` | 左右分屏 |
| `Ctrl+b` `"` | 上下分屏 |
| `Ctrl+b` 方向键 | 在窗格间移动光标 |
| `Ctrl+b` `z` | 当前窗格全屏/还原 |
| `Ctrl+b` `c` | 新开窗口 |
| `Ctrl+b` `n` / `p` | 下一个/上一个窗口 |
| `Ctrl+b` `d` | 分离（detach） |
| `Ctrl+b` `?` | 查看全部快捷键 |

::: note 前缀键
tmux 的指令都以 `Ctrl+b` 开头——先按 `Ctrl+b` 松开，再按后面的键。如果屏幕没反应，多半是前缀没按对或按在了终端软件自己拦截了快捷键上。
:::

### 6.4 复制粘贴与滚动

```bash
# 进入复制模式：Ctrl+b [（滚动/选择用方向键或 PgUp/PgDn）
# 开始选择：Space；复制选中：Enter；粘贴：Ctrl+b ]
```

解读：`Ctrl+b [` 进入 copy-mode，此时可以自由滚动屏幕看历史输出（默认回滚被禁用）；选中后按 Enter 复制，`Ctrl+b ]` 粘贴。鼠标模式可开启：`tmux set -g mouse on`（配置进 `~/.tmux.conf` 永久生效）。

### 6.5 退出与恢复

```bash
exit          # 或 Ctrl+d，关闭当前窗格/窗口
tmux attach   # 之后随时回来，进程都还在
```

解读：tmux 的黄金用法 = `ssh` 连上 → `tmux new -s job` 开长任务 → `Ctrl+b d` 分离 → 关电脑走人 → 下次 `ssh` 回来 `tmux attach` 继续。所谓"tmuxinator"（或 `tmuxp`）是把这套"命名会话 + 分屏布局"写成 YAML 配置一键还原的进阶工具，多服务器巡检场景常用。

### 6.6 `~/.tmux.conf` 与同步窗格

一份克制的基础配置：

```tmux
# ~/.tmux.conf
set -g mouse on
set -g history-limit 100000
set -g base-index 1
set -g renumber-windows on
setw -g pane-base-index 1
setw -g mode-keys vi
bind r source-file ~/.tmux.conf \; display-message 'tmux config reloaded'
```

```bash
tmux source-file ~/.tmux.conf              # 当前 server 重载配置
tmux show-options -g                       # 查看 server/global 选项
tmux show-window-options -g                # 查看 window 默认选项
```

同步当前窗口的所有窗格：

```bash
tmux set-window-option synchronize-panes on
tmux set-window-option synchronize-panes off
```

交互式等价操作是 `Ctrl+b :` 后输入 `setw synchronize-panes on`；开启后当前窗格键入的字符会广播到该窗口所有 pane，状态栏可自定义显示开关状态。

::: warning 广播前先做无害探针
同步窗格适合多机同时执行 `hostname`、`uptime` 和只读检查，但一条错误的 `rm`/防火墙命令也会同时破坏所有主机。先确认每个 pane 的主机名、用户、工作目录和 sudo 状态，先广播 `printf '%s %s\n' "$(hostname)" "$PWD"`，变更命令先 dry-run；执行后立刻关闭 `synchronize-panes`。
:::

## 7. screen：tmux 的老前辈

```bash
screen -S build             # 新建命名会话
screen -ls                  # 列出会话
screen -r build             # 重新附加
screen -d build             # 把别的终端挂着的那份踢掉
Ctrl+a d                    # 分离（screen 的前缀是 Ctrl+a）
```

| 对比项 | `screen` | `tmux` |
| --- | --- | --- |
| 年龄 | 1987，发行版几乎必装 | 2007，功能更现代 |
| 前缀键 | `Ctrl+a` | `Ctrl+b` |
| 分屏布局 | 较笨拙 | 灵活、支持嵌套窗格 |
| 脚本化/配置 | 一般 | 强，配合 tmuxinator |
| 适用 | 服务器上"有就能用" | 长期工作流、多窗格编排 |

解读：两者都能"分离会话、后台保活"，但 tmux 布局管理和脚本化更好。老机器或最小化系统可能只有 screen，`screen -r` 接任意一个会话来 `-ls` 看到的 ID 也一样能恢复。**选型原则：个人新项目用 tmux，通用服务器应急用 screen**。

## 8. 远程操作综合实战：本地代码同步 + 重启服务

```bash
# 1) 干跑：确认要动哪些文件（排除本地无关目录）
rsync -avzn --delete --exclude='node_modules/' --exclude='.git/' ./app/ deploy@webprod:/opt/app/

# 2) 真正同步（限速避免挤占带宽，-P 支持断点续传）
rsync -avzP --delete --exclude='node_modules/' --exclude='.git/' ./app/ deploy@webprod:/opt/app/

# 3) 远端重启服务（-t 给 sudo 分配 tty）
ssh -t webprod 'sudo systemctl restart myapp && sudo systemctl status myapp --no-pager'
```

完整链路解读：
- 第 1 步 `-n` 干跑零风险，先确认 `--delete` 不会误删远端文件。
- 第 2 步真实同步：增量 + 断点 + 排除，本地开发机可以随时 Ctrl+C，重跑续传。
- 第 3 步 `-t` 解决 sudo 无 tty 的问题，`&&` 保证 restart 成功才看状态；`--no-pager` 避免 `systemctl` 卡在分页器里。
- 若第 2 步中途断网：重跑第 2 步即可续传；若担心服务状态，可把第 3 步放进 tmux 会话里挂机。

断点续传技巧：
```bash
rsync -avzP /big-file.bin user@host:/data/   # 中断后原样重跑即可续传
rsync -avz --append /big-file.bin user@host:/data/   # 仅追加模式，适合只增长的日志
```

多机批量操作：
```bash
# for + ssh：逐台执行同一命令（注意失败继续）
for h in web1 web2 web3; do ssh "$h" 'uptime'; done
# 更正规的批量工具（免密 + 并行；按发行版可能叫 pssh/parallel-ssh）：
parallel-ssh -h hosts.txt -P 'hostname && uptime'
pssh -h hosts.txt -P 'hostname && uptime'
# 输出 host 与结果但不改变远端：
parallel-ssh -h hosts.txt -i -P 'ss -ltn | grep -E ":(22|443) " || true'
# 更完整的配置管理生态：
# ansible all -m ping   （见 [[../Linux/01 Linux进程与调度实操|运维自动化]] 生态）
```

预期输出片段：

```text
[1] 10.0.0.11:22 OK (stdout)
10.0.0.11: uptime
[2] 10.0.0.12:22 OK (stdout)
```

解读：`-h hosts.txt` 从主机清单读取，`-P` 把 stdout/stderr 打印出来，`-i` 把每台结果交错收集；不同实现的选项细节略有差异，先执行 `parallel-ssh --help`。Debian/Ubuntu 常见包为 `pssh`，也可能从 PyPI 安装 `parallel-ssh`；它们都通常要求 SSH key、config 和 known_hosts 已准备好。

::: warning 并发操作的边界
`parallel-ssh` 只是并发执行器，不提供幂等、变更审批、分批发布或自动回滚。对生产主机先用只读命令，再按 canary/批次执行；防火墙、路由和 sshd 变更必须保留带外入口与当前 SSH 会话。
:::

### 8.1 `sshpass`：密码自动化的风险边界

`sshpass` 不是 OpenSSH 默认组件，通常来自同名包。它通过密码模拟交互，适合极少数无法立即迁移密钥的临时导入，不应作为长期自动化方案：

```bash
sshpass -d 3 ssh -o StrictHostKeyChecking=accept-new user@host 'hostname' 3<<<"$TEMP_PASSWORD"
sshpass -f /run/user/1000/sshpass.secret scp file user@host:/tmp/
```

预期行为：命令成功时只返回远端 `hostname`/scp 进度；密码不会出现在 `ps` 参数列表中（`-d 3` 是从文件描述符读取）。

解读：避免 `sshpass -p 'password'`，因为密码可能出现在 shell history、进程列表、审计日志和 CI 日志；`-e` 读取 `SSHPASS` 也会把秘密放进环境，仍可能泄露。临时文件应由当前用户创建、权限 `600`、使用后立即删除，CI 优先用 secret store。迁移路线是一次性 `ssh-copy-id`/控制台安装公钥，之后关闭密码登录并移除 sshpass。

同步安全要点：
- **权限**：同步到远端后属主/权限可能被源端覆盖，先 `rsync -avn` 看 `-a` 会不会把不该变的权限改了；生产目录用 `--chown` 与 `--chmod` 显式指定。
- **软链接**：`-a` 默认保留软链不跟随（等价 `--links`），需要"把链接指向的内容也拷走"时才用 `-L`（follow）。方向别搞反，`-L` 会把链目标内容复制成普通文件。
- **加密**：公网同步一定走 SSH 通道；`rsync://` 守护进程模式默认明文，别传敏感数据。

## 本章小结

1. `ssh` 是远程操作的地基：`-p`/`-i`/`-v` 管连接细节，`~/.ssh/config` 把长命令收敛成别名。
2. 密钥认证核心是**公钥放服务器，私钥永驻本地**；`ssh-agent` 缓存签名能力，`ssh-keyscan` 只收集不验证，`ssh -G` 展开客户端配置。大规模环境可用短期 SSH certificate + CA，CA 私钥必须重点保护。
3. 高级连接包括 `-J` 跳板、`-L/-R/-D` 隧道、`autossh` 自动重连与 `mosh` 漫游；远程变更必须保留旧会话/带外入口，通过第二条新 SSH 验证后再收口。
3.1 防锁死三件套：`systemd-run --on-active`（或 `at`）安排定时回滚 → `sshd -t`/`sshd -T` 校验后只 `reload` → 用 `ssh -o ControlMaster=no -o ControlPath=none` 建立**真正的新连接**验证，通过后才 `systemctl stop` 掉回滚计时器。
4. 传输选型：小文件 `scp`，OpenSSH 9+ 默认 SFTP、仅兼容旧服务端时用 `-O`；交互/批处理用 `sftp -b`；反复同步和快照用 `rsync`。
5. rsync 高级审计与恢复使用 `--itemize-changes`、`--checksum`、`--partial-dir`、`--link-dest`；daemon 模式默认明文，公网优先 SSH。云对象存储使用非默认 `rclone`，先 dry-run 并保护凭据。
6. `sshfs` 适合轻量浏览而非数据库/重负载，`parallel-ssh` 只负责并发而不保证幂等，`sshpass` 仅限临时迁移且禁止命令行明文密码。
7. `tmux` 用 `Ctrl+b d` 分离、`attach` 恢复，`synchronize-panes` 可广播多机命令也会放大误操作；广播前核验主机/目录，执行后立即关闭。
8. SSH keepalive、网络与内核参数继续参考 [内核模块硬件与系统参数命令](/kb/os/Bash/17-内核模块硬件与系统参数命令/)；`rclone`、终端与其他增强工具见 [现代高效命令行工具](/kb/os/Bash/20-现代高效命令行工具/)。

## 动手实验

1. `ssh-keygen -t ed25519 -C "lab"` 生成密钥，用 `ssh-copy-id` 把公钥部署到你的测试机（或本地 `ssh localhost`），验证免密登录，并检查 `.ssh` 与 `authorized_keys` 权限。
2. 在 `~/.ssh/config` 里给测试机写一个 `Host` 别名（含 `Port`/`User`/`IdentityFile`），然后 `ssh 别名` 验证，再用 `ssh 别名 'hostname; date'` 试远程命令。
3. 搭一条端口转发：`ssh -L 8080:localhost:80 别名`，用 `curl -I http://localhost:8080` 访问远端 Web 服务，再用 `-v` 观察握手日志。
4. 建目录 `/tmp/src` 放几个文件，分别执行 `rsync -av /tmp/src/ /tmp/dst1/` 与 `rsync -av /tmp/src /tmp/dst2/`，用 `tree` 对比两处结构，验证尾部斜杠语义。
5. 修改 `/tmp/src` 中一个文件后重跑 `rsync -avn /tmp/src/ /tmp/dst1/`，观察只列出变化文件；再跑 `rsync -avn --delete`，体会干跑的价值。
6. `tmux new -s lab` 后用 `Ctrl+b %` 左右分屏、`Ctrl+b "` 上下分屏，在左右窗格分别跑 `top` 和 `ping`，`Ctrl+b d` 分离后 `tmux ls`、`tmux attach -t lab` 恢复。
7. 用 `tmux` 包裹一次"`rsync -P` 传输 + `ssh -t` 重启服务"的完整命令链，中途按 `Ctrl+C` 中断 rsync 再重跑，体验断点续传。
8. **agent 与最终配置**：给实验私钥设置 passphrase，执行 `ssh-add -t 10m`、`ssh-add -l`；再用 `ssh -G <别名>` 检查 hostname/user/port/identityfile。实验后 `ssh-add -d`，不要开启全局 agent forwarding。
9. **host key 独立核验**：用 `ssh-keyscan` 收集测试机 ed25519 key，在测试机控制台执行 `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`，比较指纹后才加入临时 known_hosts。
10. **rsync 审计与快照**：建立 yesterday/today 两个目标，先 `rsync -ani --delete --link-dest=../yesterday`，再正式同步；用 `stat` 对比未变化文件 inode，用 `--partial-dir` 中断/恢复一个大文件。
11. **SFTP 与 rclone 干跑**：编写不含密码的 `sftp -b` 文件上传测试文件；若已配置测试云 remote，执行 `rclone sync ... --dry-run --combined=-`，不得直接对生产 bucket 运行 sync。
12. **tmux 广播保护**：两个 pane 分别进入不同测试目录，开启 `synchronize-panes`，只广播 `hostname; pwd`，随后立即关闭；解释为什么防火墙、删除和 sudo 命令不宜广播。
13. **定时回滚演练**（虚拟机）：备份 `sshd_config`，用 `systemd-run --on-active=3min` 安排恢复任务，把 `Port` 改成一个**防火墙未放行**的端口并 reload，故意让自己连不上；等计时器到点后确认能重新登录，再解释为什么必须 `sshd -t` 校验回滚文件。
14. **连接复用假阳性**：先用 `ControlMaster=auto` 建立会话，再把 sshd 换到未放行端口，验证旧 master 仍能"登录"；改用 `ssh -o ControlMaster=no -o ControlPath=none` 后失败。说明为什么验证必须禁用复用。

<details><summary>参考答案</summary>

1. 历史遗留：`ssh` 用 `-p`（小写）指定端口，`scp`/`sftp` 沿用老式工具习惯用 `-P`（大写）。`rsync -e 'ssh -p 2222'` 内部仍走 `ssh -p`。
2. 公钥放在服务器的 `~/.ssh/authorized_keys`；私钥文件被偷且无 passphrase 时，攻击者可直接登录所有放了对应公钥的主机——所以建议给私钥设 passphrase 并保管好。
3. 一个主机可匹配多个 `Host` 段，但每个参数通常取第一次获得的值；具体主机段放前面，宽泛 `Host *` 默认值放后面，并用 `ssh -G` 验证最终结果。
4. `src/ dst/` 只把 src 的**内容**同步进 dst；`src dst/` 会把 src **目录本身**放进 dst（结果 `dst/src/`）。斜杠只影响源端。
5. sudo 需要交互式 tty，而 `ssh host 'cmd'` 默认不分配 tty；加 `-t` 强制分配伪终端即可。
6. `--delete` 让目标端与源端完全一致，删除目标端多余的、源端不存在的文件。风险是命令方向写反会删源端；安全做法是先 `rsync -avn --delete` 干跑确认清单。
7. 左右分屏 `Ctrl+b %`；分离 `Ctrl+b d`；重新附加 `tmux attach -t &lt;name&gt;`。分离只是本地"看不见"，远端 tmux 进程与其中命令继续运行。
8. 服务器重装后 host key 变了，与 `known_hosts` 里的旧指纹不符。确认服务器确实是目标机器后，用 `ssh-keygen -R 主机名/IP` 删除旧记录再重连；不要盲目 yes。
9. `ssh-keyscan` 只记录网络对端声称的 key，中间人也能返回自己的 key；必须通过控制台/资产平台等独立通道比对指纹。`ssh -G` 不连接服务器，只展开 config/Include/通配与命令行后的最终客户端参数。
10. `--checksum` 读取两端内容判断变化，可靠但 I/O/CPU 高；`--partial-dir` 集中保留未完成文件供重跑复用；`--link-dest` 让未变化文件与基线快照硬链接，省空间但要求同一文件系统且归档不能被修改。
11. OpenSSH 9.0 起 scp 默认走 SFTP；仅当旧服务端不支持 SFTP，或遗留脚本确实依赖远端 shell 通配语义时临时用 `-O`，并严格引用路径。
12. `sshpass -p` 会把密码暴露给 history/进程/日志；agent forwarding 会让受控远端在会话期间借用本地签名能力。长期自动化应使用受限密钥/证书，ProxyJump 优于 agent forwarding。
13. 已建立 SSH 可能被 conntrack 继续放行，不能证明新认证/端口/规则正确；保留旧会话和带外入口，从第二终端完整重连成功后才能移除旧规则并持久化。
14. `sleep` 挂在当前 shell 里，SSH 断开后进程可能随会话被 SIGHUP 带走，恰好在最需要回滚时失效；`systemd-run --on-active` 生成瞬时 timer/service，归属 systemd，与终端生命周期无关，还能用 `systemctl list-timers`/`stop` 查询和取消。
15. `ControlMaster=auto` 会复用已有 master 连接，新端口/新规则即使完全不通也能进入 shell，形成假阳性；显式关闭复用才会真正走一次 TCP 握手、认证和防火墙判定。
16. `reload` 让 sshd 重读配置但不影响已建立会话，配置有问题时旧会话还能救场；`restart` 更容易造成失联。`sshd -T` 输出的是把默认值、`Include` 和匹配块都展开后的**最终生效值**，而配置文件里可能有被覆盖或未生效的行。
</details>
