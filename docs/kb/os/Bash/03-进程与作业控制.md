上一篇 [Linux 进程实操](/kb/os/Linux/01-Linux进程与调度实操/) 已用 `ps`/`top`/`kill` 建立起"进程状态机"的直觉。本篇换一个角度：不深究内核状态，而是**把命令当工具箱**——ps 的三套语法、top 的交互键、完整的信号语义、以及终端下的前台/后台作业控制（`&`/`jobs`/`fg`/`bg`/`nohup`/`setsid`）。学完你该能回答：怎么优雅停一个进程？怎么让程序关掉终端也不死？怎么批量管理一堆进程？

命令视角的进程管理 = **看清（ps/top/htop/pstree）→ 发指令（kill/信号）→ 调度（nice/renice/chrt）→ 防干扰（作业控制/守护进程）**。本文是 [Bash命令学习路线总览](/kb/os/Bash/00-Bash命令学习路线总览/) 的第 3 篇，涉及的系统监控拓展见 [系统监控与性能命令](/kb/os/Bash/07-系统监控与性能命令/)。

## 1. ps：三种语法，一套事实

`ps` 的历史包袱决定了它有三套兼容语法，同一套进程数据，三张不同的脸。

### 1.1 BSD 风格：`ps aux`

```bash
ps aux
```
预期输出片段：
```
USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
root         1  0.0  0.1 166468 13292 ?        Ss   20:15   0:03 systemd
zhang    2150  0.0  0.0  20364  1288 pts/1    S    21:10   0:00 sleep 300
zhang    2180  0.0  0.0 226344  3908 pts/1    R+   21:15   0:00 ps aux
```
解读：
- `aux` 三个字母不是选项：`a` 显示所有终端的进程，`u` 用面向用户格式显示，`x` 包含无终端（`?`）的守护进程。**`ps aux` 里要写裸的 `aux`（无 `-`），这才是 BSD 风格**。
- 列多、有人性化的 `%CPU`/`%MEM`/`START`，适合人眼扫。注意 `ps aux | grep` 会抓到 grep 自己（经典困扰），下面有解法。

### 1.2 SysV 风格：`ps -ef`

```bash
ps -ef
```
预期输出片段：
```
UID          PID    PPID  C STIME TTY          TIME CMD
root           1       0  0 20:15 ?        00:00:03 /sbin/init
zhang       2150    1499  0 21:10 pts/1    00:00:00 sleep 300
```
解读：`-e` 所有进程 + `-f` 完整格式。列更少、机器友好（`C` 是 CPU 占用、`STIME` 是启动时刻）。**脚本解析进程列表优先用 `-ef`，列位置稳定**。

### 1.3 三套风格对比

| 风格 | 写法 | 关键列 | 适用场景 |
|---|---|---|---|
| BSD | `ps aux` | USER/PID/%CPU/%MEM/VSZ/RSS/STAT/START | 人肉排查，看内存 CPU 直观 |
| SysV | `ps -ef` | UID/PID/PPID/C/STIME | 脚本解析、找父子关系 |
| GNU | `ps -eo ... --sort` | **完全自定义** | 输出指定列、排序、管道处理 |

### 1.4 GNU 风格：自定义列 + 排序

::: tip 一台机器上，`ps aux`、`ps -ef`、`ps -eo` 得到的是**同一批进程**，只是换滤镜。遇到"两种 ps 输出不一样"的疑问，答案通常是：BSD 与 SysV 解析方式不同，或某列的定义不同，数据源都是 `/proc`。
:::

```bash
ps -eo pid,ppid,%cpu,%mem,stat,cmd --sort=-%cpu | head -10
```
预期输出片段：
```
    PID   PPID %CPU %MEM STAT CMD
   1120      1  2.3  3.8 Ssl  mysqld --datadir=/var/lib/mysql
   1499      1  0.0  0.1 Ss   /usr/lib/systemd/systemd --user
   2182   1499  0.0  0.0 R+   ps -eo pid,ppid,%cpu,%mem,stat,cmd --sort=-%cpu
```
解读：
- `-e` = 所有进程，`-o 列名,列名,...` = 指定列；列名就是 1.2 表里那些字段的关键词（`cmd` 完整命令行、`comm` 仅名字）。
- `--sort=-%cpu` 按 CPU 降序，`--sort=pid` 升序——**这是"CPU 最高进程"问题的标准答案**。换列名就是一张定制报表：`ps -eo pid,etime,stat,cmd --sort=etime` 看最长寿的进程。

### 1.5 STAT 字母全解（本篇补全版）

| 主字母 | 含义 | 与 [Linux 进程实操](/kb/os/Linux/01-Linux进程与调度实操/) 的对应 |
|---|---|---|
| `R` | running/runnable，正在跑或等 CPU | running/ready |
| `S` | 可中断睡眠（等终端/网络/sleep） | waiting（最常见） |
| `D` | 不可中断睡眠（等磁盘 IO） | 杀不掉，`kill` 无效 |
| `T` | stopped，被 `Ctrl+Z` 或 `SIGSTOP` 暂停 | 挂起态 |
| `t` | 被调试器（gdb）跟踪停止 | — |
| `Z` | 僵尸：已 exit、父进程未 wait | terminated 未回收 |
| `I` | idle，内核空闲线程 | — |
| `X` | dead，理论上存在、几乎见不到 | — |

| 附加修饰符 | 含义 |
|---|---|
| `+` | 属于**前台进程组**（挂在你终端前的进程） |
| `s` | session leader（会话首进程，通常是登录 shell） |
| `l` | 多线程进程 |
| `<` | 高优先级（nice 为负） |
| `N` | 低优先级（nice 为正） |
| `L` | 有页面锁定在内存（mlock） |

::: important 组合读法
`Ss` = 会话首进程 + 睡眠（登录 shell 的典型状态）；`S+` = 前台 + 睡眠（你正在跑的命令）；`Ssl` = 会话首 + 多线程 + 睡眠（mysqld 这种守护进程）。两字母/三字母是"主状态 + 属性"，`ps` 把它们拼在一格。
:::

### 1.6 `ps -L`：看线程

```bash
ps -L -p 1120
```
预期输出片段：
```
  PID   LWP TTY          TIME CMD
 1120  1120 ?        00:00:01 mysqld
 1120  1121 ?        00:00:00 mysqld
 1120  1122 ?        00:00:31 mysqld
```
解读：`-L` 把进程的每个线程拆成一行。**LWP = light-weight process（线程号）**，主线程的 LWP 等于 PID。线程与进程的内核关系见 [进程内核](/kb/os/Linux/08-Linux进程与线程内核原理/)。想只看线程数：`ps -o nlwp -p PID`。

### 1.7 `ps -eo wchan`：进程睡在哪

```bash
ps -eo pid,stat,wchan:30,comm | grep -v '^ *PID' | sort -k2 | head
```
预期输出片段：
```
    1 Ss  do_wait                           systemd
    523 Ss  do_select                        sshd
   1499 Ss  wait_for_completion_killable     systemd --user
```
解读：`wchan` 是**内核等待函数名**——进程睡眠时停在哪个内核函数。`do_wait` = 在等子进程，`do_select` = 在等 IO 就绪。这是调试"卡在哪"的第一手线索：状态是 `D` 就看 wchan 是不是 IO 等待。普通用户看别进程可能显示 `?`（无权限读取）。

### 1.8 `ps -o pri,ni,rtprio`：三种优先级

```bash
ps -o pid,pri,ni,rtprio,comm -p 1120
```
预期输出片段：
```
    PID   PRI  NI RTPRIO COMMAND
   1120    20   0      - mysqld
```
解读：
- `PRI`：内核当前优先级。普通进程用 CFS 动态优先级（默认 20 = nice 0），数字越大越靠后。
- `NI`：nice 值（-20~19），用户可调的"谦让系数"，见第 7.2 节。
- `RTPRIO`：实时优先级（1~99），**只有实时调度策略的进程才非 `-`**。看到非 `-` 说明该进程用了 SCHED_FIFO/RR，见第 7.3 节。

## 2. top：动态监控三键一屏

`top` 是交互式进程管理器，刷新间隙会更新排序。先记住四个键：**P/M/T 排序、1 看核、H 看线程、q 退出**。

### 2.1 交互键速查

| 按键 | 作用 |
|---|---|
| `P` | 按 %CPU 降序（默认） |
| `M` | 按 %MEM（RES）降序 |
| `T` | 按 TIME+（累计 CPU 时间）降序 |
| `1` | 展开/收起每个 CPU 核的统计 |
| `H` | 切换"线程模式"，把每个线程当一行 |
| `k` | 输入 PID 发信号（默认 TERM），最实用 |
| `r` | 输入 PID 改 nice 值 |
| `c` | 切换完整命令行 / 短名 |
| `t`/`m` | 切换 CPU / 内存条形图 |
| `x`/`b` | 高亮排序列 / 加粗当前行 |
| `q` | 退出 |

### 2.2 进程行字段

```
    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
   1120 mysql     20   0 1875432 305432  11812 S   2.3   3.8   0:31.22 mysqld
```

| 字段 | 含义 |
|---|---|
| `PR` | 内核优先级（20 = nice 0 的普通进程） |
| `NI` | nice 值 |
| `VIRT` | 虚拟内存总量（含未驻留/未分配），常虚高，别被吓到 |
| `RES` | 常驻物理内存（真正占的 RAM） |
| `SHR` | 共享内存（库文件等可与其他进程共用） |
| `%CPU` | **最近刷新间隔内的 CPU 使用率**，单核最多 100%，多线程可超 100% |
| `%MEM` | RES / 总物理内存 |
| `TIME+` | **累计 CPU 时间**，和 `%CPU` 是两回事：`%CPU` 是速度，`TIME+` 是总量 |
| `COMMAND` | 命令名/完整命令行 |

### 2.3 头部两行：load average 与 %Cpu(s)

```
top - 21:15:03 up 1 day,  3:12,  2 users,  load average: 0.52, 0.43, 0.40
Tasks: 168 total,   2 running, 165 sleeping,   0 stopped,   1 zombie
%Cpu(s):  5.3 us,  1.8 sy,  0.0 ni, 92.3 id,  0.4 wa,  0.0 hi,  0.1 si,  0.0 st
```
- **load average**：过去 1、5、15 分钟"正在运行 + 等待运行 + 不可中断"的进程平均数。判断：持续大于核数 = 排队了；`1 < 5` 说明负载在下降。**load 高 ≠ CPU 忙**，`wa`（等磁盘）同样推高它——这条在 [CPU 排查](/kb/os/问题排查/02-CPU性能问题排查/) 里会反复用。
- **%Cpu(s)**：us 用户态 / sy 内核态 / ni nice 进程 / id 空闲 / wa 等 IO / hi/si 硬软中断 / st 被虚拟机偷走的时间。

::: warning Tasks 行的 `zombie`
`1 zombie` 表示当前有僵尸进程。出现僵尸不致命（只占 PCB 和 PID），但**长期挂着的父进程会持续产僵尸**，累积下去才是问题。处理见 8.4 节。
:::

### 2.4 top 的非交互模式

```bash
top -b -n1 -o %CPU | head -15        # 批处理拍一张快照，按 CPU 排好
top -b -n2 -d 3 | tail -40           # 隔 3 秒拍两张，避免第一张偏小
top -p 1120 -p 1499                  # 只看指定 PID
top -H -p 1120                       # 只看某进程的每个线程（排查线程卡死）
```
解读：`-b` 批处理（不占终端），`-n1` 只刷一轮，配合管道/脚本抓拍；`-o %CPU` 直接按列排序，省去进交互按 `P`；`-p` 限定 PID，`-H` 看线程，`-d` 刷新间隔秒数。

## 3. htop：可视化加强版 top

```bash
htop
```
与 top 的核心差异：

| 维度 | top | htop |
|---|---|---|
| 界面 | 文本密集，信息密度高 | 彩色、可鼠标点选、有进程树 |
| 颜色 | 单色 | **红=内核态、绿=用户态、蓝=nice 进程**；内存条里金黄色=缓存 |
| 树形 | 无 | **F5 切换进程树视图**（能看到父子关系） |
| 杀进程 | `k` + 输 PID | **F9** 弹出信号菜单，方向键选中直接发 |
| 排序 | `P/M/T` | F6 选排序列 |

::: tip htop 的实用键
F3 搜索（按名字）、F6 排序、F8 nice 调整、F9 发信号、F10 退出。htop 顶部把 CPU/内存画成彩色条，**红条多 = 内核忙（系统调用/锁），绿条多 = 用户程序在算**。
:::

## 4. 信号与 kill：给进程"发指令"

`kill` 的名字有迷惑性：它不是"杀"，而是"发送一个信号"。信号是内核与进程之间最小的控制单元，其内核实现与信号挂起/投递机制见 [进程内核](/kb/os/Linux/08-Linux进程与线程内核原理/)。

### 4.1 信号清单

```bash
kill -l
```
预期输出（Linux x86_64 片段）：
```
 1) SIGHUP       2) SIGINT       3) SIGQUIT      4) SIGILL       5) SIGTRAP
 6) SIGABRT      7) SIGBUS       8) SIGFPE       9) SIGKILL     10) SIGUSR1
11) SIGSEGV     12) SIGUSR2     13) SIGPIPE     14) SIGALRM     15) SIGTERM
16) SIGSTKFLT   17) SIGCHLD     18) SIGCONT     19) SIGSTOP     20) SIGTSTP
...
```
Linux 上还有 32~64 号实时信号（`SIGRTMIN..SIGRTMAX`），用于自定义用途。

### 4.2 核心信号语义表

| 信号 | 编号 | 默认行为 | 可否捕获 | 触发场景 |
|---|---|---|---|---|
| `SIGHUP` | 1 | 终止进程 | 可 | 终端挂断；守护进程常把它当"重载配置"信号 |
| `SIGINT` | 2 | 终止 | 可 | 键盘 `Ctrl+C` |
| `SIGQUIT` | 3 | 终止 + **core dump** | 可 | 键盘 `Ctrl+\` |
| `SIGKILL` | 9 | 立即终止 | **不可** | 进程无响应时最后手段 |
| `SIGTERM` | 15 | 优雅终止 | 可 | **`kill` 的默认信号**，先给清理机会 |
| `SIGSTOP` | 19 | 暂停进程 | **不可** | `kill -STOP`，等效 `Ctrl+Z` |
| `SIGCONT` | 18 | 继续运行 | 可 | 恢复被 STOP 的进程 |
| `SIGCHLD` | 17 | 忽略 | 可 | 子进程状态变化时发给父进程（回收僵尸的时机） |
| `SIGPIPE` | 13 | 终止 | 可 | 写一个没人读的管道（如 `head` 提前退出） |
| `SIGUSR1/2` | 10/12 | 终止 | 可 | 用户自定义，用于让程序做特定动作 |

::: important SIGTERM vs SIGKILL
先 `kill PID`（TERM，程序可以保存数据、关连接、写日志）；5 秒后还不死再 `kill -9`。**`-9` 没有清理机会**，可能留下脏数据、未写回的缓存、临时文件。多数应用会把 SIGHUP 用于"热重载配置"（nginx 的 `reload` 本质就是发 HUP）。
:::

### 4.3 kill / killall / pkill：三种"指名道姓"

```bash
sleep 300 &                # 后台起一个,输出 [1] 2150
kill 2150                  # ① 按 PID 发 SIGTERM
killall sleep              # ② 按"进程名"杀，干掉所有名为 sleep 的
pkill -f "python app.py"   # ③ 按"完整命令行"匹配（-f）
pkill -9 -u www-data       #    按用户杀，-9 强杀
```

| 命令 | 匹配目标 | 例子 | 风险 |
|---|---|---|---|
| `kill PID` | 精确 PID | `kill 2150` | 低，最精确 |
| `killall NAME` | **进程名**（comm，15 字符截断） | `killall chrome` | 同名全杀，`killall python` 误伤所有 python 脚本 |
| `pkill 模式` | 进程名正则 | `pkill -x sleep` | 中 |
| `pkill -f 模式` | **完整命令行正则** | `pkill -f "python app.py"` | 高，模式太宽会误杀 |

::: warning 先确认再动手
批量杀之前先用 `pgrep -f 模式`（只打印 PID，不杀）确认匹配名单。**`pkill -f` 能匹配到包含你这条命令行在内的进程**——`pgrep -f` 也同理，注意不要匹配到自身。
:::

### 4.4 信号送达后，程序怎么响应

进程收到可捕获信号后的行为链：**内核把信号挂到进程上 → 进程回到用户态时先执行信号处理函数 → 执行完继续原流程**。所以：

- 对 SIGTERM：程序可能"等一下"——正在写文件、等 IO 时，信号要等它回用户态才能处理（尤其是 `D` 状态进程，信号排队但杀不掉）；`kill` 因此**不保证立刻生效**。
- 对 SIGKILL：内核直接终止，**根本不给用户态处理的机会**，不依赖程序配合。
- 进程可以 `signal()`/`sigaction()` 注册处理器：重载配置（HUP）、忽略信号、自杀前清理。

## 5. 前台后台作业控制

终端里的"作业"（job）概念：**一次命令行启动的所有进程**（含管道、子进程）构成一个**进程组**，组长的 PID 就是组号。作业控制就是把"进程组"这个单元挂到终端前后台。

### 5.1 `&`：放后台跑

```bash
sleep 300 &
# [1] 2150          ← [1] 是作业号(Job ID)，2150 是进程组组长 PID
echo hello          # 前台命令不受影响，立即返回
```
解读：`&` 让命令进入后台，shell 立刻提示符。但注意：**后台作业仍连在终端上**，若它读取终端通常会收到 `SIGTTIN` 而停住；`Ctrl+C` 只发给当前**前台进程组**，不会同时中断后台作业。要完全脱开，见第 6 节。

### 5.2 `Ctrl+Z`：挂起（不是退出）

```bash
sleep 300
^Z
# [1]+  Stopped                 sleep 300
```
解读：`Ctrl+Z` 给前台进程组发 `SIGTSTP`（终端停止信号），进程进入 `T` 状态停着。**进程还在内存里，随时能继续**。

### 5.3 jobs / fg / bg

```bash
sleep 100 &      # [1] 2150
sleep 200 &      # [2] 2151
jobs -l
# [1]- 2150 Running                 sleep 100
# [2]+ 2151 Running                 sleep 200
bg %2            # 把作业 2 放后台继续（它本来就后台,一般用不上）
fg %1            # 把作业 1 调到前台,占据终端直到结束
```

| 命令 | 作用 |
|---|---|
| `jobs` | 列出当前 shell 的后台作业；`-l` 显示 PID，`+` 是当前作业 |
| `%1` / `%2` | 按**作业号**引用，注意和 PID 是两套编号 |
| `fg %1` | 把作业调到前台，shell 等它跑完 |
| `bg %1` | 让**被挂起（Stopped）的作业**在后台继续跑 |
| `%sleep` | 用命令前缀引用作业（`%sleep` 匹配名为 sleep 的作业） |

::: tip Ctrl+Z + bg = 手动"最小化"
前台跑着个大任务（如编译）时：`Ctrl+Z` 挂起 → `bg` 放后台 → 继续干别的。这比重新 `&` 优雅，因为它不中断任务。
:::

### 5.4 `Ctrl+C` 中断 vs `Ctrl+\` 退出

| 按键 | 信号 | 效果 |
|---|---|---|
| `Ctrl+C` | `SIGINT`（2） | 请求中断，程序可捕获（vim 里就有自己的 Ctrl+C 逻辑） |
| `Ctrl+\` | `SIGQUIT`（3） | 强制退出并生成 **core dump**（核心转储），用于崩溃现场分析 |

```bash
sleep 300        # 按 Ctrl+C
^C               # 进程退出
sleep 300        # 按 Ctrl+\
^\Quit (core dumped) sleep
```
`core dumped` 会把进程内存镜像写到 `core` 文件（或交给 systemd-coredump），配合 gdb 分析崩溃点。日常排错基本只用 `Ctrl+C`。

### 5.5 作业 ≠ 进程：两个编号体系

```
job = 一个进程组(可能是多个进程)   job id: [1] [2] ...
  └─ 组内第一个进程 = 组长          pid: 2150
```
- `Ctrl+C`/`Ctrl+Z` 发给**整个前台进程组**，不是单个进程。`kill -TERM -2150`（负 PID）就是"按进程组发信号"。
- `&`/`fg`/`bg`/`jobs` 是 shell 提供的**作业级**操作；`ps`/`kill` 是**进程级**操作。`jobs -l` 帮你把两套编号对起来。

### 5.6 disown：从 shell 的作业表里"除名"

```bash
sleep 300 &
disown %1          # 从作业表移除,shell 退出时不会管它
disown -h %1       # 只取消 SIGHUP 继承,但仍留在作业表里
```
解读：默认情况下 shell 退出会给作业发 `SIGHUP` 带走它们。`disown` 让 shell 不再惦记这个作业——**但进程仍连着你的终端**，终端关闭后失去控制终端的行为仍可能异常。要彻底脱离，看下一节。

## 6. 守护进程与脱离终端

目标：**关掉终端，程序照跑**。难点有三：① shell 退出时发 SIGHUP；② 失去控制终端后读终端报错；③ stdout/stderr 无处可写。按脱离程度从弱到强排列：

| 手段 | 忽略 SIGHUP | 脱离控制终端 | 重定向输出 |
|---|---|---|---|
| `nohup cmd &` | ✅ | ❌ | ✅（默认写 nohup.out） |
| `cmd & disown` | ✅ | ❌ | ❌ 需要手动 |
| `(cmd &)` | ✅（子 shell 退出不通知） | ✅（无控制终端） | ❌ 需要手动 |
| `setsid cmd` | ✅ | ✅（新会话，无终端） | ❌ 需要手动 |
| `systemd-run` | ✅（由 systemd 托管） | ✅ | ✅（journal） |

### 6.1 nohup：忽略 SIGHUP

```bash
nohup ./my_server > server.log 2>&1 &
```
- `nohup` 让进程忽略 `SIGHUP`：**关掉终端、甚至退出登录，进程都不死**。若没手动重定向，stdout/stderr 会写进当前目录 `nohup.out`。
- 注意：它只是不响应 HUP，**进程仍持有原终端作为控制终端**，读 stdin 的行为仍可能异常。

::: tip nohup 的"断电测试"
后台 `nohup ./job.sh &` 后直接关闭整个终端窗口（而不是 Ctrl+C），再重开终端 `ps` 看它还在。这比 `kill -HUP` 更贴近真实挂断场景。
:::

### 6.2 setsid：开新会话，彻底脱钩

```bash
setsid ./my_server </dev/null >/dev/null 2>&1 &
```
解读：`setsid` 让进程成为**新会话的会话首进程**——没有控制终端，自然收不到终端信号，也不会因为终端关闭而死。相比 nohup，它是更彻底、更接近"守护进程"的做法。实现层面对应 `setsid()` 系统调用，进程组/会话模型见 [进程内核](/kb/os/Linux/08-Linux进程与线程内核原理/)。

### 6.3 三者的正确姿势

```bash
# 稳妥组合：nohup + 重定向 + &
nohup ./app > app.log 2>&1 &
# 简洁组合：& + disown
./app > app.log 2>&1 & disown
# 最彻底：setsid + 重定向
setsid ./app </dev/null > app.log 2>&1 &
```
::: warning 三个坑
① 日志不重定向 → 进程写终端报 "No such device or address"，很多程序直接崩；② 输入不重定向（`</dev/null`）→ 后台进程读终端会停顿或收到 SIGTTIN 被挂起；③ `nohup`/`setsid` 对**已经通过 fork 脱离的守护进程**是多余的（它们早就 `setsid()` 过了）。
:::

### 6.4 `(cmd &)`：子 shell 一走了之

```bash
(sleep 300 &)
ps -o pid,ppid,stat,comm -C sleep
```
解读：`(...)` 起一个子 shell，子 shell 把 `sleep` 放后台后自己立刻退出——`sleep` 成了孤儿，被 init/systemd 收养，shell 退出时也不会给它发 SIGHUP。**相当于一次性 disown**，比 `& disown` 少打几个字，但没有 shell 作业号可用。

### 6.5 systemd-run：把进程交给 systemd 托管

```bash
systemd-run --unit=myapp --property=Restart=on-failure ./my_server
systemd-run --user --unit=myapp-user ./my_server    # 用户级会话
systemctl --user status myapp                        # 查看状态
systemctl --user stop myapp                          # 停止
```
解读：现代 Linux 的推荐做法——不手动 nohup/setsid，而是**把进程注册成 systemd 单元**，由 systemd 管理生命周期：自动重启、开机启动、集中日志（`journalctl -u myapp`）。相比裸 `nohup`，可维护性高一个量级。

### 6.6 日志重定向速查

```bash
./cmd > log 2>&1 &        # 标准输出+错误都进 log（最常用）
./cmd >> log 2>&1 &       # 追加而不是覆盖
./cmd >/dev/null 2>&1 &   # 全丢弃,只要它活着
```
- `> log` 只重定向 stdout；`2>&1` 把 stderr 也并入 stdout 的落点。顺序不能反：`2>&1 > log` 会把 stderr 留在终端；`&` 放行末，让整条命令后台化。

## 7. 进程树与优先级

### 7.1 pstree：一眼看清父系

```bash
pstree -p -u zhang
```
预期输出片段：
```
systemd(1)───sshd(523)───sshd(1501)───bash(1500,zhang)───sleep(2150)
```
- `-p` 显示 PID，`-u` 显示 UID 变化点（`bash(1500,zhang)` 表示切换了用户）。`{名字}` 表示线程。
- 排查"哪个进程是我起的 / 谁衍生出来的"最直观；结合 8.4 找僵尸的父进程。
### 7.2 nice / renice：调"谦让系数"

nice 值范围 **-20 ~ 19**，数字越小越抢占 CPU，默认 0。

```bash
nice -n 10 ./heavy_task &      # 启动时给低优先级(更谦让)
sudo nice -n -10 ./heavy_task & # 负数=高优先级,需要 root
sleep 300 &
renice 5 -p $!                  # 对已运行的 PID 调整
ps -o pid,ni,pri,stat,comm -p $!
```
预期输出片段：
```
    PID  NI PRI STAT COMMAND
   2160   5  25 S    sleep
```
解读：`renice 5` 后 `NI=5`、内核 `PRI` 从 20 变 25（数字大 = 靠后调度）。调度的具体影响见 [调度器原理](/kb/os/Linux/09-Linux调度器原理/)。

::: important 为什么调低 nice 要 root？
nice 为负 = 抢占更多 CPU，如果人人可调，就能把自己进程抬到第一饿死别人。所以**调大（更谦让）任何人可以，调小（更霸道）需要 root（CAP_SYS_NICE）**。普通用户 `renice -n -5` 会报 "Operation not permitted"。
:::

### 7.3 chrt：实时调度策略

```bash
chrt -l          # 列出调度策略
```
预期输出：
```
SCHED_OTHER  0   CFS,默认完全公平调度
SCHED_FIFO   1   FIFO,先到先做,直到让出或被更高优先级抢占
SCHED_RR     2   轮转,带时间片
```
```bash
chrt -p 1120     # 查看某进程当前策略与优先级
chrt -f 99 -p 1120   # 设为 FIFO 99(需要 root)
```
解读：实时策略让进程**不受 CFS 公平性的约束**，FIFO/RR 的实时优先级 1~99 直接决定顺序。内核 RT 线程（如 `ps` 里 PRI 为负、RTPRIO 非 `-` 的）都用它。乱设实时优先级可能饿死普通进程——生产环境别乱动，原理见 [调度器原理](/kb/os/Linux/09-Linux调度器原理/)。

### 7.4 资源限制：ulimit 与 prlimit

资源限制分为 soft limit（当前生效值）和 hard limit（上限）。shell 内建的 `ulimit` 影响当前 shell 及之后启动的子进程；`prlimit` 读取或修改指定 PID 的限制，也可以带限制启动一个命令。

```bash
PID=1120                         # 以下示例替换成目标 PID
ulimit -a                         # 当前 shell 的全部限制
ulimit -n                         # soft NOFILE：打开文件描述符数
ulimit -S -c 0; ulimit -H -c     # core 文件 soft/hard 上限
prlimit --pid "$PID"             # 读取指定进程的全部限制
prlimit --pid "$PID" --nofile   # 只看 NOFILE 的 soft/hard
prlimit --nofile=1024:4096 ./app # 以限制启动 app
```

输出片段：

```text
RESOURCE   DESCRIPTION                         SOFT      HARD UNITS
NOFILE     max number of open files            1024      4096 files
CORE       max size of core files                 0 unlimited bytes
```

解读：`ulimit -n` 的单个数字只是当前 shell 的 soft 值；`prlimit` 同时展示边界，`1024:4096` 表示 soft=1024、hard=4096，`unlimited` 表示无穷上限。soft 不能超过 hard；调高 hard limit 或修改别人的进程通常需要 root/CAP_SYS_RESOURCE。

场景与风险：

- `Too many open files`：先 `prlimit --pid PID --nofile`，再用 `lsof -p PID` 看是否句柄泄漏；不要只把上限无限调大掩盖泄漏。
- 没有 core：检查 `ulimit -c`/`prlimit --core`，systemd 服务还要看服务单元和 `coredumpctl`，见 [调试与追踪工具](/kb/os/Bash/13-调试与追踪工具/)。
- `ulimit` 只作用于 shell 进程树，不等于 cgroup 的 CPU/内存/PID 配额；systemd、容器和服务管理器可能再次施加边界。

### 7.5 地址空间、文件和 /proc 现场

```bash
pmap -x "$PID"                         # -x 扩展映射：Kbytes/RSS/Dirty
lsof -p "$PID"                         # 该 PID 的文件、库、管道、socket
sudo lsof -nP -p "$PID" -a -d 0,1,2    # 不解析名字，只看标准 IO fd
fuser -v /var/lib/myapp/data.db          # 谁正在使用文件
fuser -v -n tcp 8080                     # 谁占用本机 TCP 8080
```

输出片段：

```text
Address           Kbytes     RSS   Dirty Mode  Mapping
0000555555400000      132     128       0 r-x-- app
00007f1e40000000   24576   18432    1024 rw--- [ anon ]
----------------  ------  ------  ------
total kB          196812   84200    4096

mysqld  1120 mysql  13u  IPv4  ... TCP 127.0.0.1:3306 (LISTEN)
/var/lib/myapp/data.db: 1120
```

解读：`pmap -x` 按映射拆出虚拟地址空间，`RSS` 是当前驻留物理页，`Dirty` 是脏页；匿名映射持续增大时再查堆和线程栈。`lsof -p` 把 PID 关联到实际文件/网络对象，`fuser` 反过来从文件、挂载点或端口找 PID。`lsof` 的 `13u` 表示 fd 13 以读写方式打开；`fuser` 默认把 PID 输出到 stdout、说明文字输出到 stderr。

场景与风险：文件被占用无法卸载时用 `fuser -vm MOUNTPOINT` 先列名单；确认后才考虑 `fuser -km`，因为它可能一次终止文件系统上的大量进程。`lsof`/`fuser` 跨用户、跨 mount namespace 查看常需要 root，权限不足时结果可能不完整。

进程的 `/proc` 现场：

```bash
readlink /proc/"$PID"/exe           # 实际可执行文件；需要规范化路径时再加 -f
cat /proc/"$PID"/{status,limits,cmdline,environ,stack}
tr '\0' ' ' < /proc/"$PID"/cmdline; printf '\n'
tr '\0' '\n' < /proc/"$PID"/environ
sudo cat /proc/"$PID"/stack
```

输出片段：

```text
Name:   myapp
State:  S (sleeping)
Threads:        8
VmRSS:      84200 kB
voluntary_ctxt_switches:        1204
nonvoluntary_ctxt_switches:      18
```

解读：`status` 有状态、线程数、VmRSS、上下文切换和 capability；`limits` 是内核实际看到的限制；`cmdline` 是 NUL 分隔的 argv；`environ` 是 NUL 分隔的环境变量；`stack` 是内核等待栈，常用于判断 D/S 状态睡在哪。`readlink /proc/PID/exe` 比只看 `comm` 更能识别被替换或从临时目录执行的二进制。

场景与风险：直接 `cat` `cmdline`/`environ` 可能把多项挤在一起，应该用 `tr '\0'` 还原；环境变量可能含 token、密码等秘密，不能直接写入公开日志。读取别的用户的 `environ`/`stack` 可能被权限、Yama 或内核配置拒绝；进程退出后 `/proc/PID` 会立即消失，取证要先保存结果。

### 7.6 CPU 亲和性、IO 优先级与调度边界

```bash
taskset -pc "$PID"                    # 查看 PID 的 CPU affinity
taskset -cp 0-3 "$PID"                 # 限定到 CPU 0~3
taskset -c 0-3 ./worker                 # 启动时限制 CPU
ionice -p "$PID"                       # 查看 IO class/priority
ionice -c 3 -p "$PID"                  # idle class，只在无人用盘时运行
ionice -c 2 -n 7 -p "$PID"             # best-effort class，低优先级
schedtool -v "$PID"                    # 可选工具，查看策略/优先级/affinity
sudo schedtool -B -a 0,1 "$PID"        # 可选：batch + CPU 0/1
```

输出片段：

```text
pid 1120's current affinity list: 0-7
1120: policy SCHED_OTHER, prio 0, nice 0
```

解读：`taskset` 控制能在哪些逻辑 CPU 上运行；`ionice` 控制块 IO 调度类，实际效果取决于内核、文件系统和 IO 调度器；`schedtool` 是发行版通常不默认安装的可选工具，提供 `SCHED_BATCH`、FIFO/RR 等策略的统一查询/设置。普通 CFS 任务通常先用已有的 `nice`/`renice`，实时策略仍用 `chrt`。

场景与风险：`renice` 只改变 CFS 的权重，不能给普通进程实时保证；`chrt` 改变调度类，`SCHED_FIFO`/`SCHED_RR` 的实时优先级与 nice 不可直接比较。亲和性过窄会让一个核满载而全机仍有空闲；IO 优先级不能改变已经进入页缓存的写回时机；实时选项可能饿死普通任务，甚至让 shell 失去运行机会。修改前保存原值，限定 PID 和测试窗口，并确认 cgroup/cpuset 没有覆盖你的设置。

### 7.7 namespace：容器进程的另一张进程表

```bash
lsns -p "$PID"                          # 目标进程持有的 namespace
readlink /proc/"$PID"/ns/{pid,mnt,net,uts,user,cgroup}
sudo nsenter -t "$PID" -m -u -i -n -p -- ps -ef
unshare --user --map-root-user --pid --mount-proc --fork sh
```

输出片段：

```text
        NS TYPE  NPROCS PID USER COMMAND
4026531836 pid       42   1 root /sbin/init
4026532901 net        18 1120 app  /usr/bin/app
```

解读：`lsns` 的 namespace ID 本质上是 `/proc/PID/ns/*` 的 inode；同一个 inode 表示进程共享同一 namespace。`nsenter -t PID` 进入目标的 mount/network/PID 等视图后再执行 `ps`，适合从宿主机检查容器内部；`unshare` 创建隔离的 namespace，`--mount-proc` 是 PID namespace 中获得正确 `/proc` 视图的关键。

场景与风险：宿主机看到的 PID 和容器内 PID 可能不同；`nsenter -n` 后网络命令看到的是容器网络栈，`-m` 后挂载操作可能影响目标 namespace 内的服务。`unshare` 的 user namespace 不是完整容器安全边界，实验应使用临时目录、非生产主机，并确认权限和 mount propagation。

## 8. 进程命令组合实战

### 8.1 找出 CPU 占用最高的进程

```bash
ps -eo pid,%cpu,%mem,comm --sort=-%cpu | head -6
top -b -n1 -o %CPU | head -12
watch -n 2 'ps -eo pid,%cpu,comm --sort=-%cpu | head -5'   # 持续盯
```
配合 [调度疑难](/kb/os/问题排查/07-进程与调度异常疑难/) 判断是计算密集还是自旋锁。

### 8.2 批量杀：先看名单再动手

```bash
pgrep -af "build_worker"          # 先看会匹配到谁(带命令行)
pkill -f "build_worker"           # 确认无误再杀(默认 SIGTERM)
pgrep -af "build_worker" && echo "还有残留"   # 复查
pkill -9 -f "build_worker"        # 残留才用 -9
```
::: warning `-f` 匹配的是整个命令行
`pgrep -f build` 会同时匹配到 `build_worker` 和 **`pgrep -f build` 自己那条命令行**（含 `build` 字样）。脚本里要么用 `pgrep -x` 精确名字，要么在模式里排除 `pgrep`。
:::

### 8.3 按关键字定位并查看线程

```bash
pgrep -f my_server                # 找 PID
top -H -p $(pgrep -f my_server | head -1)   # 看这个进程的每个线程
```
场景：怀疑某进程有线程卡死——`top -H -p PID` 里某线程 `%CPU` 持续 100% 而进程整体不高，往往是**单线程自旋/死循环**。

### 8.4 僵尸进程处理

```bash
ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^Z/ {print}'
```
预期输出片段：
```
   2156   2154 Z    bash
```
处理流程：
1. 记录僵尸 PID（2156）与父进程 PPID（2154），确认父进程是谁：`ps -o pid,stat,cmd -p 2154`。
2. 处理父进程：它若已死，僵尸会被 init 收养回收；它若活着，让它 `wait()`（重启该服务）或 `kill 2154`，由 systemd 收养回收。
3. 处理完确认：`ps -o pid,stat,cmd -p 2156` 应显示进程已不存在。
> 僵尸只占 PCB 和 PID，**kill -9 杀不掉僵尸**（它已经死了），只能处理它的父进程。反复产僵尸的父进程才是病根，详见 [调度疑难](/kb/os/问题排查/07-进程与调度异常疑难/)。父进程常驻且必收子的正确姿势是注册 `SIGCHLD` 处理器调用 `wait()`。

### 8.5 ps 与 pgrep 的配合

| 工具 | 特点 | 用法 |
|---|---|---|
| `ps -C sleep` | 按进程名（comm）过滤 | `ps -o pid,stat -C sleep` |
| `pgrep sleep` | 只输出 PID，可 `-x` 精确名、`-P` 按父 PID、`-f` 按命令行 | `pgrep -x sshd` |
| `pgrep -P 2150` | 列出某 PID 的所有子进程 | 找父进程的子进程树 |

```bash
pgrep -x sleep                    # 精确匹配名为 sleep 的进程(排除 sleep3 之类)
pgrep -P 1 -a                     # PID 1 的直接子进程(带命令行)
ps -o pid,ppid,stat,comm -p $(pgrep -x sleep)
```

### 8.6 pidstat：按 PID 取证的完整资源画像

`pidstat` 属于 `sysstat`，在"找进程"的视角下补上了 `ps/top` 的缺口：它报告**采样间隔内的变化速率**，而不是只给一个累计快照。`-p PID` 用于查某个进程，`-p ALL` 用于明确请求所有任务；系统资源总览和历史趋势见 [系统监控与性能命令](/kb/os/Bash/07-系统监控与性能命令/)，本节聚焦某个 PID 为什么吃 CPU、内存、IO 或频繁切换。

```bash
PID=1120
pidstat -u -p "$PID" 1 3       # CPU
pidstat -r -p "$PID" 1 3       # 缺页与 VSZ/RSS
pidstat -d -p "$PID" 1 3       # 进程发起的磁盘 IO
pidstat -w -p "$PID" 1 3       # 上下文切换
pidstat -t -p "$PID" 1 3       # 该进程的线程
pidstat -u -p ALL 1 3           # 明确列出全系统任务，找 CPU 活跃者
```

预期输出片段（`-u -p PID`）：

```text
09:30:01 UID       PID   %usr %system  %guest   %wait   %CPU  CPU  Command
09:30:02 1001     1120    4.10    0.60    0.00    0.00   4.70    2  mysqld
```

参数和列含义：

| 视角 | 命令与输出列 | 如何解读 |
|---|---|---|
| CPU | `pidstat -u -p PID 1 5`；`%usr` 用户态，`%system` 内核态，`%guest` 虚拟机时间，`%wait` 等待运行，`%CPU` 合计，`CPU` 当前运行的逻辑核 | `%usr` 高是应用在算，`%system` 高要查系统调用/锁/内核路径，`%wait` 高说明它想运行但在排队。多线程进程的 `%CPU` 在未使用 `-I` 时可能超过 100% |
| 内存 | `pidstat -r -p PID 1 5`；`minflt/s` 次缺页，`majflt/s` 主缺页，`VSZ` 虚拟内存，`RSS` 常驻内存，`%MEM` 占物理内存比例 | 次缺页不一定访问磁盘，主缺页通常需要从磁盘调页；RSS 持续上涨比 VSZ 更像实际内存压力。把它和 [系统监控与性能命令](/kb/os/Bash/07-系统监控与性能命令/) 的 `free`/`sar -r` 一起看，避免把单进程增长误判成全局 OOM |
| IO | `pidstat -d -p PID 1 5`；`kB_rd/s` 读盘速率，`kB_wr/s` 写盘速率，`kB_ccwr/s` 取消的脏页写回，`iodelay` 块 IO/换入等待 | 这是任务造成或归因到任务的 IO，不是设备最终完成量；页缓存可能让进程写得很快而设备稍后才忙。设备延迟仍需 `iostat -x`/`biolatency` |
| 切换 | `pidstat -w -p PID 1 5`；`cswch/s` 自愿切换，`nvcswch/s` 非自愿切换 | 自愿切换高常见于等待锁、IO、条件变量；非自愿切换高说明时间片耗尽或被抢占。切换高并不等于 bug，要与 `%CPU`、`runq`、业务延迟对齐 |
| 线程 | `pidstat -t -u -p PID 1 5`；输出增加 `TGID`（线程组/进程 PID）和 `TID`（线程 ID） | 某个 TID 持续 `%CPU` 高，可能是单线程死循环；多个线程都在 `futex` 等待，才更像锁竞争。用 [调试与追踪工具](/kb/os/Bash/13-调试与追踪工具/) 的 `perf`/`strace -f` 深挖 |
| 全局筛选 | `pidstat -u/-r/-d/-w -p ALL 1 3`；`-p ALL` 选择全部任务，`1` 为采样间隔，`3` 为报告次数 | 适合从所有任务中筛出活跃者，再把 PID 带回本节的 `-p PID`。输出很多、短命任务可能一闪而过；资源总览优先在 07 篇使用 `vmstat`/`mpstat`/`iostat` |

预期输出片段（其他视角）：

```text
# pidstat -r -p 1120 1 1
UID       PID  minflt/s  majflt/s       VSZ       RSS   %MEM  Command
1001     1120      8.00      0.00   1875432    305432    3.8  mysqld

# pidstat -d -p 1120 1 1
UID       PID   kB_rd/s   kB_wr/s kB_ccwr/s iodelay  Command
1001     1120    120.00     40.00       0.00        2  mysqld

# pidstat -w -p 1120 1 1
UID       PID   cswch/s nvcswch/s  Command
1001     1120     84.00      3.00  mysqld

# pidstat -t -u -p 1120 1 1
UID      TGID       TID   %usr %system  %guest   %wait   %CPU  CPU  Command
1001     1120      1120    1.10    0.20    0.00    0.00   1.30    2  mysqld
1001     1120      1122    8.90    0.10    0.00    0.00   9.00    3  mysqld
```

第一条报告通常是自系统启动以来的平均统计，短间隔判断看第二条及以后；使用 `-l` 可显示完整命令行，使用 `-I` 可在 SMP 上按逻辑 CPU 总数归一化 CPU 百分比。`pidstat -p ALL` 的"全量"仍受 `/proc` 权限、容器 PID namespace 和任务生命周期影响，不能替代 cgroup 级别的配额监控。

场景与风险：

- CPU 高：先 `pidstat -u -p ALL 1 5` 找 PID，再 `pidstat -u -t -p PID 1 5` 找线程，最后用 `perf record -p PID` 看函数热点。
- 内存增长：用 `pidstat -r -p PID 5` 观察 RSS/主缺页趋势，再用 `pmap -x PID` 和 [调试与追踪工具](/kb/os/Bash/13-调试与追踪工具/) 的 heaptrack/ASan 工具链分辨映射增长还是堆泄漏。
- IO 抖动：用 `pidstat -d -p ALL 1 5` 找发起 IO 的任务，再回到 07 篇的 `iostat -x` 看设备 `await`；不要因为某进程 `%CPU` 高就直接杀掉，它可能只是 IO 瓶颈的受害者。
- 生产中优先短时、限定 PID、低频采样；`-p ALL` 会放大输出与解析成本，`-t -p ALL` 还会按线程扩张行数。敏感信息不要把 `-l` 输出直接写入公开日志。

### 8.7 查进程工具链：命中、确认、取证、再操作

把"找进程"拆成四步：先用 `pgrep` 命中候选，再用 `ps`/`pstree` 确认父子关系，随后用 `watch` 或 `pidstat` 观察变化，最后才执行 `pkill`/`kill`。这条链能减少把同名服务或自己的查询命令误当目标的概率。

```bash
pgrep -af 'python.*worker.py'                 # -a 带命令行，-f 匹配完整命令行
pgrep -P 2150 -a                              # -P 按父 PID 找直接子进程
pstree -aps 2150                              # 从 PID 向上显示祖先
watch -n 2 -d 'ps -eo pid,ppid,stat,pcpu,pmem,cmd --sort=-pcpu | head -12'
pkill -TERM -x worker                         # -x 精确匹配 comm，默认 TERM
```

输出片段与解读：

```text
2150 /usr/bin/python3 /srv/worker.py --queue high
systemd(1)---sshd(523)---bash(1500)---worker(2150)---worker(2152)
```

`pgrep -af` 的 PID 行是候选名单，`pstree` 说明谁启动了谁，`watch -d` 用反色突出两次快照间变化。确认后才用 `pkill`；`pkill -f` 是完整命令行正则，匹配范围最宽，脚本中应优先 `pgrep -af` 复核并使用 `-x`、`-u`、`-P` 等限制条件。`watch` 只是在重复执行命令，命令本身若有副作用或输出过大就不适合放进去。

## 9. 本章小结

- **ps 三套语法**：BSD `aux`（人看）、SysV `-ef`（脚本）、GNU `-eo ... --sort`（自定义报表）；STAT 主字母 + 修饰符 = 完整状态机快照，`ps -L`/`wchan`/`pri,ni,rtprio` 分别看线程、睡眠点、三级优先级。
- **top 四键打天下**：P/M/T 排序、1 看核、H 看线程、q 退出；`-b -n1` 抓拍、`-p` 盯单进程、`-o` 预排序。load average 是"1/5/15 分钟排队数"，要结合 `wa` 判断是不是磁盘撑的。
- **kill 是发信号不是杀**：SIGTERM 优雅、SIGKILL 强杀（不可捕获）、STOP/CONT 暂停/恢复；`kill`/`killall`/`pkill(-f)` 三种匹配粒度，批量动手前先用 `pgrep` 复核。
- **作业控制**：`&` 后台、`Ctrl+Z` 挂起、`jobs/fg/bg` 用作业号 `%1` 操作、`Ctrl+C`=SIGINT、`Ctrl+\`=SIGQUIT+core；作业是一个进程组，信号按组投递。
- **脱离终端三件套**：`nohup` 忽略 HUP、`setsid` 开新会话彻底脱钩、`systemd-run` 交给 systemd 托管；无论哪种都别忘了 `> log 2>&1`。
- **优先级与调度**：nice（-20~19）调谦让系数，调负需 root；`chrt` 上实时策略动它有饿死别人的风险。
- **PID 取证链**：`pgrep`/`pkill` 负责候选与操作，`pstree`/`watch` 负责关系和变化，`pidstat` 的 `-u/-r/-d/-w/-t` 分别看 CPU、内存、IO、切换和线程；资源总览从 `-p ALL` 开始，单进程解释回本篇 8.6。
- **进程现场**：`prlimit`/`ulimit` 看 soft/hard 资源边界，`pmap -x` 看映射，`lsof -p`/`fuser` 看句柄和占用，`/proc/PID` 提供状态、限制、命令行、环境、等待栈和真实 exe 路径。
- **隔离与调度边界**：`taskset`/`ionice`/`schedtool`/`chrt` 会改变调度条件；`lsns`/`nsenter`/`unshare` 解释容器中 PID、挂载和网络视图为何不同。变更前记录原值，生产优先只读观察。

## 10. 动手实验

1. **制造并管理后台作业**：`sleep 100 & sleep 200 &`，用 `jobs -l` 看作业号与 PID，`fg %2` 拉回来，`Ctrl+C` 结束它，`ps` 确认进程消失。
2. **Ctrl+Z / fg / bg 三连**：前台 `sleep 300`，`Ctrl+Z` 挂起，`ps -o stat,comm -C sleep` 看到 `T`；`bg` 放后台，看 STAT 回 `S`；最后 `fg` 拿回前台 `Ctrl+C`。
3. **nohup 断电测试**：`nohup sh -c 'for i in $(seq 1 60); do echo tick $i; sleep 1; done' > /tmp/nohup.log 2>&1 &`，**直接关闭终端窗口**，重开终端 `ps` 找 `seq`/`sh` 还在，`tail /tmp/nohup.log` 看它一直写——这就是"关终端程序不死"。
4. **kill 不同信号对比**：`sleep 300` 在后台，依次 `kill -STOP`（看 `ps` 变 `T`）、`kill -CONT`（回 `S`）、`kill`（TERM 退出）、再起一个 `kill -9`（无痕迹退出）；用 `watch -n1 'ps -o stat,comm -C sleep'` 全程观察。
5. **用 ps+kill 模拟守护进程管理**：`setsid sh -c 'echo $$ > /tmp/daemon.pid; while true; do date >> /tmp/daemon.log; sleep 2; done' </dev/null >/dev/null 2>&1 &`；`cat /tmp/daemon.pid` 拿 PID，关终端后回来 `ps -p PID` 还在；用 `pkill -f daemon.log`（或按 PID）停掉它，模拟一个"自己管理的守护进程"。
6. **僵尸制作**：跑 Linux/01 的 `zombie.sh`，用 `ps -eo pid,ppid,stat,cmd | awk '$3~/^Z/'` 看到 `Z`，`kill` 父进程后观察僵尸消失——对比 Linux/01 的 kill 父进程实验，本篇用 `awk` 过滤更省事。
7. **pidstat 进程画像**：启动 `yes > /dev/null &`、`dd if=/dev/zero of=/tmp/pidstat-test bs=1M count=256` 和一个多线程程序；先用 `pidstat -u/-r/-d/-w -p ALL 1 5` 找 PID，再用 `pidstat -t -u -p PID 1 5` 识别线程。实验结束用 `kill`、`rm` 清理。
8. **/proc 与句柄取证**：对一个长时间运行的 `sleep 300` 或测试服务记录 `readlink -f /proc/PID/exe`、`cat /proc/PID/status`、`pmap -x PID`、`lsof -p PID`；打开一个临时文件后用 `fuser -v file` 反向确认。不要把 `environ` 输出到共享终端。
9. **资源限制与调度实验**：运行 `prlimit --nofile=64:128 sh -c 'ulimit -n; sleep 30'`，对比 `ulimit -n`；再用 `taskset -pc PID`、`ionice -p PID`、`renice 10 -p PID` 记录变更前后。不要在实验机外设置 FIFO/RR。
10. **namespace 观察**：运行 `unshare --user --map-root-user --pid --mount-proc --fork sh`，在内部和外部各执行 `ps -ef`、`readlink /proc/self/ns/pid`；退出后用 `lsns` 确认临时 namespace 消失。需要进入真实容器时只读使用 `nsenter`。

## 11. 自测题

1. **`ps aux` 和 `ps -ef` 的 `a`/`-e` 有什么区别？为什么说它们显示的是同一批进程？** `a` 是 BSD 语法"所有终端"，`-e` 是 SysV 语法"所有进程"；加上 `x` 后两者都覆盖全部进程，数据都来自 `/proc`，只是列格式不同。
2. **一个进程 STAT 是 `Ssl`，分别代表什么？** `S` 可中断睡眠（在等 IO/输入）；`s` 是会话首进程；`l` 是多线程。典型如 mysqld。
3. **`kill`、`killall`、`pkill -f` 的匹配对象各是什么？** PID；进程名（comm，15 字符内）；完整命令行正则。`-f` 最灵活也最危险，先 `pgrep -f` 复核。
4. **`SIGTERM` 和 `SIGKILL` 的行为差异是什么？为什么说先 TERM 后 KILL？** TERM 可被捕获，进程能清理退出；KILL 不可捕获，直接由内核终止、无清理机会。先 TERM 给机会，超时再 KILL 兜底，避免脏数据。
5. **`Ctrl+Z` 之后进程是什么状态？怎么让它继续？** 进程收到 SIGTSTP 进入 `T`（stopped），`fg %N` 拉回前台或 `bg %N` 放后台继续（后者会收到 SIGCONT）。
6. **`nohup`、`& disown`、`setsid` 三者的差别是什么？** nohup 只忽略 SIGHUP；`& disown` 是"shell 退出不通知"，但进程仍持有控制终端；setsid 开新会话、无控制终端，脱离最彻底。三者都要配合重定向避免读/写终端。
7. **为什么普通用户 `renice -n -5` 会被拒绝？** 负 nice 代表抢占更多 CPU，属于特权操作（CAP_SYS_NICE/root），防止普通用户饿死其他进程。
8. **为什么 `kill -9` 杀不掉僵尸进程？那要怎么办？** 僵尸已经死了（terminated 但未回收），kill 对它无效；必须处理它的父进程——让父进程 `wait()`/重启，或直接结束父进程让 systemd 收养回收。
9. **03 篇和 07 篇的 `pidstat` 如何分工？** 07 用 `-p ALL` 做资源总览和 PID 初筛；03 用 `-p PID` 解释单进程与线程的列，并继续到 `/proc`、`pmap`、`lsof` 和调试篇。
10. **`pidstat -r` 的 `VSZ`、`RSS`、`minflt/s`、`majflt/s` 怎么读？** VSZ 是虚拟地址空间，RSS 是当前驻留物理内存；minor fault 不必从磁盘取页，major fault 通常需要磁盘 IO。RSS/major fault 的持续趋势比一次值更有意义。
11. **为什么 `ulimit -n` 和 `prlimit --pid PID --nofile` 可能不同？** `ulimit` 只显示当前 shell 的限制；`prlimit` 读取目标 PID，子进程可能继承后又被服务管理器、容器或程序修改。还要分别看 soft 与 hard。
12. **`lsof -p`、`fuser`、`readlink /proc/PID/exe` 分别从哪一侧找进程？** `lsof -p` 从 PID 展开它持有的 fd/文件/socket；`fuser` 从文件、挂载点或端口反查 PID；`readlink` 从 PID 反查真实可执行文件路径。
13. **为什么不能随便用 `chrt -f 99` 或 `schedtool -F`？** FIFO/RR 属于实时调度类，可能长期占用 CPU，使普通任务、ssh shell 甚至 watchdog 无法运行；nice 只改变 CFS 权重，二者边界不同。
