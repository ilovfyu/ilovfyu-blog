## 1. systemd 基础概念

systemd 把所有"要被管理的东西"统一抽象成 **Unit（单元）**：给系统下定义——这个程序是什么、怎么启动、依赖谁、何时启动。unit 按功能分类型，文件后缀即类型。

### 1.1 Unit 类型表

| 类型 | 后缀 | 管什么 | 典型例子 |
|---|---|---|---|
| `service` | `.service` | 一个守护进程/服务 | `nginx.service` `ssh.service` |
| `socket` | `.socket` | 监听端口/套接字，按需拉起服务 | `systemd-journald.socket`（有人连接才启动对应服务） |
| `target` | `.target` | 一组 unit 的"集合点/里程碑"（不跑代码，只分组） | `multi-user.target` `reboot.target` |
| `timer` | `.timer` | 定时触发对应 service（systemd 版 cron） | `systemd-tmpfiles-clean.timer` |
| `mount`/`automount` | `.mount` | 挂载点/按需挂载 | `boot-efi.mount` |
| `path` | `.path` | 监控目录/文件变化触发服务 | `incoming.path`（自定义） |
| `slice` | `.slice` | cgroup 资源分组容器 | `system.slice` `user-1000.slice` |

::: tip 记法
后缀就是类型，省略后缀时 systemd 按类型搜索补齐（`systemctl start ssh` 会找到 `ssh.service`）。
:::

### 1.2 Unit 文件位置与优先级

```bash
systemctl show nginx -p FragmentPath   # 打印 nginx.service 实际生效的文件路径
```
预期输出片段：`FragmentPath=/etc/systemd/system/nginx.service`（被管理员覆盖时在此目录）。

| 目录 | 谁放的 | 优先级 | 说明 |
|---|---|---|---|
| `/usr/lib/systemd/system/` | 软件包安装的**厂商默认** | 低 | 升级包会覆盖，别手改 |
| `/run/systemd/system/` | 运行时临时生成（generator/`--runtime`） | 中 | 重启即失 |
| `/etc/systemd/system/` | **管理员自定义/覆盖** | **最高** | 同名文件会"盖掉" `/usr/lib` 里的默认定义 |

优先级高者胜。"改包自带 unit"的正确姿势：复制到 `/etc/systemd/system/` 再改，或写 drop-in（`/etc/systemd/system/xxx.service.d/override.conf`，见 3.4）。

### 1.3 Unit 依赖：Requires / Wants / After / Before

```bash
systemctl list-dependencies nginx
```
预期输出：unit 依赖树（这就是"开机先起谁、再起谁"的来源）。

| 指令 | 强度 | 含义 | 典型用法 |
|---|---|---|---|
| `Requires=` | **硬依赖** | 依赖的 unit 启动失败，本 unit 也失败/被停止 | 数据库挂了，应用就别假装活着 |
| `Wants=` | 软依赖 | 尽量拉起依赖，失败也不影响自己 | 启动时顺手开个辅助服务 |
| `After=` | **顺序**（只排序不依赖） | 自己在这两个 unit **之后**启动 | `After=network.target` 联网后再起 |
| `Before=` | 顺序 | 自己在前 | 很少用，反过来的 After |

::: important After 不是依赖，Requires 不是顺序
`After=` 只规定**先后**，不规定"非得有它"；`Requires=`/`Wants=` 只规定**依赖**，不规定先后。要"等它起完再起我"，必须 `Requires/Wants` + `After` **双写**——新手最常见的 unit 坑。
:::

### 1.4 Target 与 Runlevel 对照

```bash
systemctl get-default    # 看开机默认进入哪个 target
```
预期输出：`multi-user.target`。target 是 SysV 时代 runlevel 的进化版：不是 7 个数字，而是任意多个**语义化集合点**，且可以同时激活多个。

| SysV runlevel | systemd target | 含义 |
|---|---|---|
| 0 | `poweroff.target` | 关机 |
| 1 / S | `rescue.target` | 单用户救援模式（最小系统） |
| 2、3、4 | `multi-user.target` | 多用户命令行（默认几乎都是这个） |
| 5 | `graphical.target` | 图形界面（= multi-user + display manager） |
| 6 | `reboot.target` | 重启 |
| — | `default.target` | 软链接，指向开机默认进入的 target |

切换：`systemctl isolate multi-user.target`（切运行级）、`systemctl set-default graphical.target`（改默认）。

### 1.5 daemon-reload 时机

```bash
systemctl daemon-reload
```
systemd 启动时读 unit 文件并**缓存在内存里**，之后你新建/删除/修改了 unit 文件它不知道。所以：

| 场景 | 要执行 |
|---|---|
| 新建/删除 unit 文件、改 unit 文件内容 | `systemctl daemon-reload` |
| 只改了 unit 对应**程序自己的配置**（如 nginx.conf） | 不需要，用 `systemctl reload nginx` |
| enable/disable（会自动 reload，见 2.3） | 不用手动 |

::: warning 改完 unit 不 daemon-reload 的后果
直接 `systemctl restart xxx` 用的还是**旧内存定义**，改动"不生效"且不报错。
:::

## 2. systemctl 服务操作

systemctl 是 systemd 的总控制台：启停、开机自启、查状态、看依赖、改配置，全在它身上。

### 2.1 start / stop / restart / reload

```bash
sudo systemctl restart nginx     # start / stop / restart / reload 四个子命令同理
```
预期输出：成功时**无输出**（退出码 0）。无输出 = 命令成功，这是 systemd 的设计哲学。

解读：`start` 激活（已激活会报 already active）；`stop` 停止（程序不响应 SIGTERM 就按 TimeoutStopSec 强杀）；`restart` = stop + start，常用来让新配置生效；`reload` 只发 SIGHUP **不中断连接**（不是每个服务都支持，看有没有 `ExecReload=`）。

### 2.2 status：状态输出全解读

```bash
systemctl status nginx
```
预期输出（以 nginx 为例）：
```
● nginx.service - A high performance web server and a reverse proxy server
   Loaded: loaded (/usr/lib/systemd/system/nginx.service; enabled; preset: enabled)
   Active: active (running) since Mon 2026-08-10 09:12:03 CST; 2h 3min ago
 Main PID: 1234 (nginx)
   CGroup: /system.slice/nginx.service
           └─1234 "nginx: master process"
```

| 字段 | 含义 | 关键值 |
|---|---|---|
| `Loaded:` | unit 文件加载与开机自启状态 | `loaded`/`not-found`/`masked` + `enabled`/`disabled` |
| `Active:` | 高层激活状态（泛化的 SUB） | `active (running)`/`inactive (dead)`/`failed`/`activating` |
| `Sub:` | 低层细粒度状态（随类型而变） | service 常见 `running`/`exited`/`dead`/`failed` |
| `Main PID:` | 主进程 PID | 数字 |
| `Tasks:` / `Memory:` | 该 unit cgroup 内进程数/内存占用 | 呼应 [系统监控与性能命令](/kb/os/Bash/07-系统监控与性能命令/) |
| `CGroup:` | 这个 unit 装进哪个 cgroup、哪些进程在册 | cgroup v2 树，见 [cgroup](/kb/os/Linux/09-Linux调度器原理/) |

::: important status 排障口诀
看 `Active:` 是否 `failed` → 看 `Loaded:` 是否 `not-found`/`masked` → 看 `CGroup:` 进程树 → 看末尾 journal；完整日志在 journalctl（第 4 节）。
:::

### 2.3 enable / disable：开机自启

```bash
sudo systemctl enable nginx
sudo systemctl disable nginx
```
预期输出：
```
Created symlink /etc/systemd/system/multi-user.target.wants/nginx.service → /usr/lib/systemd/system/nginx.service
```
解读：
- `enable` 的本质是**在 `.target.wants/` 目录建软链接**，把 unit 挂进 `multi-user.target` 的依赖网；`disable` 删链接。`enable` 不 start、`disable` 不 stop——一步到位用 `--now`。
- `is-enabled` 查状态：`enabled`/`disabled`/`static`（无 [Install] 段、跟别的 unit 走）/`masked`/`indirect`。
- enable/disable 会自动做一次 daemon-reload，不用手动。

### 2.4 mask / unmask：彻底禁用

```bash
sudo systemctl mask docker.socket
sudo systemctl unmask docker.socket
```
预期输出：`Created symlink /etc/systemd/system/docker.socket → /dev/null`。
解读：`mask` 把 unit 软链到 **/dev/null**，`start`/`enable` 全部拒绝，比 `disable` 更强（disable 仍可手动 start）。`--now` 可顺带 stop，用于"彻底关掉某功能又不想卸载"。

### 2.5 is-active / list-units / --failed

预期输出片段：`is-active` 打印 `active`（退出码 0）、`is-enabled` 打印 `enabled`；`list-units` 输出 `UNIT LOAD ACTIVE SUB DESCRIPTION` 表。

| 命令 | 干什么 | 退出码 |
|---|---|---|
| `is-active unit` | 只输出 `active`/`inactive`/`failed` | 0=有激活 1=没有 |
| `is-enabled unit` | 只输出 enablement 状态 | 0=enabled |
| `list-units` | 列出**已加载**的 unit（默认只看激活/失败） | — |
| `list-units --all` | 加进 inactive 的 | — |
| `list-units --failed` | 只看失败的 | — |
| `list-unit-files` | 列磁盘上所有 unit 文件 + enable 状态 | — |

::: tip 脚本友好
`is-active`/`is-enabled` 给机器读（值固定 + 退出码）；`status`/`list-units` 给人读。写脚本判状态用前者。
:::

### 2.6 从 PID 反查服务与 unit 文件

```bash
systemctl status 1234         # 1234 是某个进程的 PID，status 直接接受 PID
systemctl whoami 1234         # 新版 systemd（≥254）直接输出该 PID 所属 unit
systemctl cat nginx.service   # 打印 unit 文件全文（fragment + drop-ins）
```
预期输出片段：`status &lt;PID&gt;` 显示所属 unit 与 CGroup；`whoami` 输出 `nginx.service`；`cat` 打印 `[Unit]`/`[Service]`/`[Install]` 全文。

解读：怀疑某个进程"不正常"先定位它归谁管，再 `systemctl cat` 看它怎么定义、限制了什么。顺带：`systemctl kill &lt;unit&gt;` 能按 unit **整组发信号**（呼应 1.2 的 cgroup 管理）。

### 2.7 systemd-run：临时交给 systemd 托管

不值得为一次性任务写永久 unit 时，可以用 `systemd-run` 生成 transient unit。它比裸后台进程多了 cgroup、journal、退出状态和生命周期管理：

```bash
sudo systemd-run --unit=demo-date --wait --collect --pipe /usr/bin/date
```

预期输出片段：

```
Running as unit: demo-date.service
Mon 2026-08-10 09:30:00 CST
```

`--wait` 等待命令结束并返回其退出状态，`--collect` 结束后清理 transient unit；需要保留 unit 便于 `status`/`journalctl` 查询时，去掉 `--collect`，或使用 `--remain-after-exit`。常驻或临时定时任务也可直接创建：

```bash
sudo systemd-run --unit=report-now --property=RuntimeMaxSec=10s \
  --property=Nice=10 --property=IOSchedulingClass=best-effort \
  --property=IOSchedulingPriority=7 /usr/local/bin/report.sh
sudo systemd-run --unit=report-hourly --on-calendar=hourly /usr/local/bin/report.sh
systemctl list-timers --all | grep report-hourly
```

预期输出片段：`Running as unit: report-now.service`；日历任务会生成类似 `report-hourly.timer` 的 transient timer。`--property` 可把一次任务放进 systemd 的资源控制和日志体系；`--user` 可创建当前用户的 user unit。需要长期维护、依赖和明确配置时，仍应写普通 `.service`/`.timer` 文件。

### 2.8 loginctl / hostnamectl：会话与主机身份

`loginctl` 管 systemd-logind 的用户、登录会话和 user manager：

```bash
loginctl list-users
loginctl list-sessions
loginctl show-session "$XDG_SESSION_ID" -p Name -p Type -p Remote -p State
loginctl user-status zhang
sudo loginctl enable-linger zhang       # 用户未登录时也启动其 user manager
sudo loginctl disable-linger zhang
```

预期输出片段：

```
SESSION  UID USER   SEAT  TTY
2        1000 zhang  seat0 tty2
Name=zhang
Type=tty
State=active
```

`enable-linger` 适合用户级 timer 或长期 user service，但会让该用户的 user manager 在未登录时也持续运行；`terminate-session`/`terminate-user` 会结束会话或该用户的进程，先确认对象再执行：

```bash
sudo loginctl terminate-session 2
sudo loginctl terminate-user zhang
```

主机身份使用 `hostnamectl`：

```bash
hostnamectl status
sudo hostnamectl set-hostname app01.example.com
hostnamectl --static
```

预期输出片段：`Static hostname: app01.example.com`、`Operating System: ...`、`Kernel: ...`。`hostnamectl set-hostname` 会持久化静态主机名，DNS 解析仍要检查 `/etc/hosts`、DNS 或云平台配置。

::: note 与时间、终端环境的交叉提示
`localectl status`/`set-locale LANG=...` 管 locale、键盘布局；`timedatectl status`/`set-timezone Asia/Shanghai` 管时区、NTP 和 RTC。这里仅提示它们与服务日志时区、用户会话的关系，完整命令见未来的 [时间终端与环境管理命令](/kb/os/Bash/19-时间终端与环境管理命令/)；硬件时钟和内核参数的关联见未来的 [内核模块硬件与系统参数命令](/kb/os/Bash/17-内核模块硬件与系统参数命令/)。
:::

### 2.9 service / chkconfig：旧 SysV 兼容层

在仍带有 SysV init 脚本的系统上，`service` 是统一的启停入口；systemd 系统通常把它兼容转发给 `systemctl`：

```bash
sudo service nginx status
sudo service nginx restart
```

预期输出仍会显示 `active (running)` 或服务自己的状态文本。`service` 适合兼容旧脚本，不适合替代 `systemctl daemon-reload`、drop-in、依赖和 journal 排障。

RHEL/CentOS 旧环境常见 `chkconfig` 管开机级别：

```bash
sudo chkconfig --list nginx       # 查看 SysV 各 runlevel 开关
sudo chkconfig nginx on           # 启用旧脚本的开机项
sudo chkconfig nginx off          # 禁用旧脚本的开机项
sudo chkconfig --add nginx        # 把带 chkconfig 头的脚本加入管理
```

预期输出片段：`nginx 0:off 1:off 2:on 3:on 4:on 5:on 6:off`。现代 systemd 主机可能没有 `chkconfig`，或它只影响 `/etc/init.d/` 脚本；原生 unit 用 `systemctl enable/disable`，不要混用两套开机配置。

## 3. 编写 Unit 文件

unit 文件是 INI 风格：`[段名]` + `键=值`，注释 `#`/`;`。service 文件三段式：`[Unit]` 描述与依赖、`[Service]` 怎么跑、`[Install]` 怎么自启。

### 3.1 三段式结构

```ini
[Unit]
Description=My python app
After=network.target          # 顺序：网络就绪之后
Wants=postgresql.service      # 软依赖：尽量起 postgresql

[Service]
Type=simple
ExecStart=/usr/local/bin/myapp --config /etc/myapp.conf
User=myapp
Restart=on-failure
```
::: note 第三段 [Install]
`WantedBy=multi-user.target` 决定 `enable` 时挂到哪个 target，示例见 3.5。
:::

| 段 | 管什么 | 常用键 |
|---|---|---|
| `[Unit]` | 描述、依赖、顺序 | `Description=` `Requires=` `Wants=` `After=` `Before=` `Conflicts=` |
| `[Service]` | 进程怎么启动/停止/重启/受限 | `Type=` `ExecStart=` `ExecStartPre=` `ExecStop=` `User=` `WorkingDirectory=` `Environment=` `Restart=` `RestartSec=` `StandardOutput=` |
| `[Install]` | enable 时挂到哪个 target | `WantedBy=` `RequiredBy=` `Also=` |

::: important ExecStart 用绝对路径
`ExecStart=` 的值 systemd 只做**极简单解析**（不做 shell 展开！不支持 `$VAR`、`~`、`<`、`>`）。所以：路径写绝对路径；要管道/重定向/变量时，把逻辑外包给脚本——`ExecStart=/usr/local/bin/run.sh`。
:::

### 3.2 Type 四兄弟对比

| `Type=` | systemd 判定"启动成功"的时机 | 典型适用 |
|---|---|---|
| `simple`（默认） | `ExecStart` 的进程被 fork 起来就算成功，立即进入 active | 前台型进程（nginx master、node app） |
| `exec` | `exec()` 真正执行成功才算 | 比 simple 严格，简单进程的推荐 |
| `forking` | **父进程 fork 出守护进程后退出生效** | 传统 daemon（sshd、mysqld 老版），配 `PIDFile=` |
| `oneshot` | 命令跑完一次就退出，进程不算"长驻" | 一次性初始化任务、脚本作业，配 `RemainAfterExit=yes` |
| `notify` | 进程通过 `sd_notify()` 主动汇报 READY | 支持 sd_notify 的服务（nginx、很多 DB） |

解读：`oneshot` 配 `RemainAfterExit=yes` 时进程退出 unit 也显示 `active (exited)`——适合"跑一次配置"；`forking` 忘写 `PIDFile=` 时 systemd 找不到主进程就 `failed`。

### 3.3 日志输出：StandardOutput

| 值 | 效果 |
|---|---|
| `journal`（默认） | 输出被 journald 收集，进 journal |
| `null` | 丢弃 |
| `file:/path` | 直接追加写入指定文件 |
| `syslog` | 走传统 syslog 接口 |

默认情况下进程 stdout/stderr 都被 journald 接管（2.2 里 `status` 末尾那几行日志就是它）。用 `file:` 时小心磁盘与轮转。

### 3.4 改完怎么生效 + drop-in

```bash
sudo systemctl daemon-reload      # ① 先让 systemd 重读（必须！）
sudo systemctl restart myapp      # ② 再重启应用配置
```
解读：顺序铁律。忘记 `daemon-reload` 是最常见的"改了不生效"根因（见 1.5）。

更推荐 **drop-in**（不动厂商默认文件）：
```bash
sudo systemctl edit nginx          # 编辑 /etc/systemd/system/nginx.service.d/override.conf
sudo systemctl edit --full nginx   # 编辑整个 unit 文件
```
drop-in 只写要覆盖的键，数组型键（多个 `Environment=`）自动合并——"给厂商 unit 打补丁"的最安全姿势。

### 3.5 完整示例：写一个自定义服务

**场景**：把一个每秒写一条时间戳的 Python 脚本托管成服务 `mytime.service`。

第一步，脚本 `/opt/mytime/ticker.py`（先手动跑通，再交给 systemd）：
```python
import time
while True:
    print(time.ctime(), flush=True)   # 每秒打一行时间戳
    time.sleep(1)
```

第二步，unit 文件 `/etc/systemd/system/mytime.service`：
```ini
[Unit]
Description=Ticker demo service
[Service]
Type=simple
User=myapp
ExecStart=/usr/bin/python3 /opt/mytime/ticker.py
Restart=on-failure
RestartSec=3

[Install]
WantedBy=multi-user.target
```

第三步，生效并验证：
```bash
sudo chown -R myapp:myapp /opt/mytime
sudo systemctl daemon-reload && sudo systemctl enable --now mytime
systemctl status mytime          # Active: active (running)
journalctl -u mytime -f          # 实时看 tick 日志（第 4 节）
```

### 3.6 systemd-analyze verify：加载前验证 Unit

修改 unit 后，先检查语法、未知键、路径和依赖提示，再 reload：

```bash
sudo systemd-analyze verify /etc/systemd/system/mytime.service
sudo systemd-analyze verify /etc/systemd/system/backup.timer
sudo systemctl daemon-reload
sudo systemctl restart mytime
```

预期输出：验证通过时通常无输出；错误时会指出文件、行号和原因，例如 `Unknown lvalue 'Execstar' in section 'Service'`。`verify` 能抓语法和常见配置问题，但不会证明程序业务逻辑正确，仍要用 `systemctl status` 与 `journalctl` 运行验证。

Unit override 的实际文件放在 `/etc/systemd/system/&lt;unit&gt;.d/override.conf`，只写需要覆盖的键：

```bash
sudo systemctl edit mytime.service
sudo systemctl show mytime.service -p FragmentPath -p DropInPaths
sudo systemctl revert mytime.service       # 删除该 unit 的本地 override，谨慎执行
```

编辑器中可写：

```ini
[Service]
Restart=on-failure
RestartSec=5s
```

`systemctl edit --runtime mytime.service` 只写 `/run`、重启失效，适合临时验证；`systemctl edit --full` 会复制并编辑完整 unit，升级维护成本更高。改完 drop-in 一样要 `daemon-reload`，然后用 `systemctl cat` 确认 fragment 和 drop-in 的合并结果。

### 3.7 socket activation / path unit：按需触发

**socket activation** 让 systemd 先监听端口，连接到来时再拉起服务；服务程序必须支持 systemd socket activation，或使用相应的 fd 继承方式，不能在同一端口再次自行 bind：

```ini
# /etc/systemd/system/hello.socket
[Unit]
Description=Hello socket
[Socket]
ListenStream=127.0.0.1:9090
[Install]
WantedBy=sockets.target
```

```ini
# /etc/systemd/system/hello.service
[Unit]
Description=Hello socket service
Requires=hello.socket
After=hello.socket
[Service]
ExecStart=/usr/local/bin/hello-server
```

启用和检查：

```bash
sudo systemd-analyze verify /etc/systemd/system/hello.socket /etc/systemd/system/hello.service
sudo systemctl daemon-reload
sudo systemctl enable --now hello.socket
systemctl status hello.socket
ss -ltn 'sport = :9090'
```

预期输出片段：`Active: active (listening)`、`LISTEN ... 127.0.0.1:9090 ...`；尚未有连接时 `hello.service` 可以仍是 inactive，收到连接后才被激活。

**path unit** 监控文件或目录变化，并触发同名 service，适合“目录出现文件就处理”：

```ini
# /etc/systemd/system/incoming.path
[Path]
DirectoryNotEmpty=/var/spool/myapp/incoming
Unit=incoming.service
[Install]
WantedBy=paths.target
```

```ini
# /etc/systemd/system/incoming.service
[Service]
Type=oneshot
ExecStart=/usr/local/bin/process-incoming.sh
```

```bash
sudo systemd-analyze verify /etc/systemd/system/incoming.path /etc/systemd/system/incoming.service
sudo systemctl daemon-reload
sudo systemctl enable --now incoming.path
sudo install -d -m 0750 /var/spool/myapp/incoming
touch /var/spool/myapp/incoming/one.txt
journalctl -u incoming.service -n 20
```

预期输出：`incoming.service` 被激活并记录处理结果。`DirectoryNotEmpty=` 适合“目录非空就处理”，`PathChanged=` 关注路径变化，`PathModified=` 关注文件内容写入；高频写入可能反复触发，脚本应具备幂等性并自行处理并发。

## 4. journalctl 日志查询

journal 是 systemd 的**结构化二进制日志**（由 `systemd-journald` 收集），和传统 `/var/log/*.log` 文本日志并存。`journalctl` 是它的查询器。

### 4.1 基本查询组合

```bash
journalctl -b                 # 本次启动（不带选项=全部日志；-b -1 上一次启动）
journalctl -u nginx.service   # 只查某个 unit
journalctl -p err             # 只查 err 及以上级别
journalctl -n 50              # 最后 50 条（tail 效果）
journalctl -f                 # 实时跟踪（tail -f 效果）
journalctl -x                 # 附上 man 页等解释（新手指南）
journalctl -o json-pretty     # 结构化 JSON 输出，机器可解析
```
预期输出片段：`Aug 10 09:12:03 host nginx[1233]: start worker processes`。
| 选项 | 含义 |
|---|---|
| `-b [n]` | 第 n 次启动（默认本次；负数往前数） |
| `-u &lt;unit&gt;` | 按 unit 过滤，`-u nginx` 即可（自动补后缀） |
| `-p &lt;level&gt;` | 按优先级过滤：`emerg` `alert` `crit` `err` `warning` `notice` `info` `debug`，**含该级及以上** |
| `-n N` / `-f` | 尾部 N 条 / 实时跟踪 |
| `-x` | 输出时附加帮助/解释文本（配合 -u 最友好） |
| `-o json-pretty` | 结构化 JSON，机器可解析 |

```bash
journalctl -o json-pretty -u nginx -n 3 | head -20
```
预期输出片段：
```
{ "__REALTIME_TIMESTAMP" : "1786525923123456",
  "MESSAGE" : "start worker processes",
  "_PID" : "1234",
  "_UNIT" : "nginx.service" }
```
解读：journal 每条记录都带**结构化字段**（`_PID`、`_UNIT`、`_COMM`、`_HOSTNAME`、`MESSAGE`…），`-o json-pretty` 全量吐出——比 `grep 文本` 强在能按字段精确过滤。

### 4.2 按时间 / 按进程 / 按字段过滤

```bash
journalctl --since "1 hour ago" --until now      # 按时间窗口（绝对/相对时间均可）
journalctl _PID=1234 _COMM=nginx                 # 按字段过滤，多条件 = AND
```
解读：
- `--since/--until` 接受绝对或相对时间（`"10 min ago"`、`"yesterday"`、`today`）。
- 字段过滤：`journalctl _PID=xxx`、`_SYSTEMD_UNIT=xxx`、`_HOSTNAME=xxx` 直接组合多条件 = **AND**——把结构化字段当 grep 列用，就是 journal 相对文本日志的杀手锏。

### 4.3 journal 大小与清理

```bash
journalctl --vacuum-size=100M      # 删到占用 ≤100M
journalctl --vacuum-time=7d        # 只留最近 7 天（--disk-usage 查占用）
```
预期输出：`Archived and inactive journals are taking up 812.3M.` → `Vacuuming done, freed 712.3M of archived journals on disk.`

| 配置 | 位置 | 作用 |
|---|---|---|
| `SystemMaxUse=` | `/etc/systemd/journald.conf` | journal 上限（默认约为分区 10%），到顶自动轮转 |
| `SystemKeepFree=` | 同上 | 给系统预留的空间底线 |
| `Compress=` | 同上 | 是否压缩（默认 `yes`） |

解读：journal 存于 `/var/log/journal/`（开启持久化后），**也是日志，会撑磁盘**——要有上限/清理策略。`--vacuum-*` 是删除操作，会影响历史排障能力，删之前想清楚。

### 4.4 journal 与 /var/log 的关系

| | journal（`/var/log/journal/`） | 传统文本日志（`/var/log/*.log`） |
|---|---|---|
| 格式 | 二进制 + 结构化字段 | 纯文本 |
| 收集者 | `systemd-journald` | 应用/服务自己写 |
| 查询 | `journalctl` 按字段/时间/unit 过滤 | `grep` 文本 |
| 保留 | 默认近期，受 SystemMaxUse 限制 | 取决于轮转配置（logrotate） |
| 关系 | **很多系统服务的日志只进 journal** | nginx/mysql 自己写的应用日志另有一套 |

::: note 一句话
`status` 末尾的日志、`journalctl` 查的日志，和 `/var/log/nginx/access.log` 是**两套东西**：前者是系统级 journal，后者是应用级文本。排障先看 journal（管服务起没起），再看应用日志（管业务错误）。
:::

### 4.5 journalctl 高级查询与写入日志

启动次数、内核消息和正则检索是服务排障中很常用的三种过滤方式：

```bash
journalctl --list-boots                    # 列出本机保存的启动记录
journalctl -b 0 -k                         # 本次启动的内核消息（-k = --dmesg）
journalctl -b -1 -k                        # 上一次启动的内核消息
journalctl -g 'timeout|failed' -u nginx    # -g 是 --grep，按 MESSAGE 正则过滤
journalctl --grep='I/O error' --since today
```

预期输出片段：

```
 -1  7e...  Sun 2026-08-09 08:10:02 CST—Mon 2026-08-10 08:55:01 CST
  0  9a...  Mon 2026-08-10 08:55:20 CST—now
Aug 10 09:01:03 host kernel: nvme nvme0: I/O error
```

`--list-boots` 的编号可传给 `-b`；`-k` 过滤内核日志；`-g/--grep` 是对 `MESSAGE` 内容的正则过滤，不是任意字段查询。权限不足时加 `sudo`，并留意不同 systemd 版本对 `--grep` 的支持。

向 journal/syslog 写入测试事件用 `logger`：

```bash
logger -t backup-check -p user.notice 'backup preflight passed'
journalctl -t backup-check -n 1
```

预期输出：`backup-check[1234]: backup preflight passed`。`-t` 设置 tag，`-p` 设置 facility.priority；它适合 shell、cron 和应用写一条结构化入口。用 `systemd-cat` 包装命令，可以把 stdout/stderr 作为 journal 日志收集：

```bash
systemd-cat -t backup --priority=info -- /usr/local/bin/backup.sh
printf '%s\n' 'manual checkpoint' | systemd-cat -t backup
journalctl -t backup -n 10
```

预期输出片段：`backup[1234]: manual checkpoint`。`systemd-cat` 不会替脚本处理失败重试或轮转，长期任务仍建议用 service/timer；跨发行版的日志设施、时间戳和终端环境见 [时间终端与环境管理命令](/kb/os/Bash/19-时间终端与环境管理命令/)。

### 4.6 logrotate：文本日志轮转与调试

传统应用日志通常由 `logrotate` 按配置轮转，与 journal 的 vacuum 是两套机制。一个安全的应用配置示例：

```conf
# /etc/logrotate.d/myapp
/var/log/myapp/*.log {
    daily
    rotate 7
    missingok
    notifempty
    compress
    delaycompress
    create 0640 myapp adm
    sharedscripts
    postrotate
        /usr/bin/systemctl reload myapp.service >/dev/null 2>&1 || true
    endscript
}
```

检查和执行：

```bash
sudo logrotate -d /etc/logrotate.conf       # debug：模拟，不修改日志和状态文件
sudo logrotate -d -v /etc/logrotate.conf    # verbose：查看匹配、跳过和轮转原因
sudo logrotate -f /etc/logrotate.conf       # force：立即轮转，生产前先确认配置
cat /var/lib/logrotate/status               # 上次轮转状态（路径因发行版略异）
```

预期输出片段：`considering log /var/log/myapp/app.log`、`log does not need rotating`；`-f` 后会看到重命名、压缩或 `postrotate` 执行记录。优先使用服务支持的 reload + `create`；`copytruncate` 不需要通知服务但复制期间可能丢日志，只有无法 reload 的程序才考虑。不要用 `-f` 代替日常调度，也不要把 `-d` 误认为会执行轮转。

## 5. cron 传统定时

cron 是最经典的定时任务工具：守护进程 `crond` 每分钟扫一次调度表，到点按用户身份执行命令。

### 5.1 crontab -e / -l / -r

```bash
crontab -e            # 编辑当前用户的 cron 表（默认编辑器）
crontab -l            # 列出当前用户的 cron 表
crontab -r            # 删除当前用户的 cron 表（不带提示，慎用）
sudo crontab -e -u otheruser   # 编辑指定用户的表
```
解读：`crontab -e` 编辑"该用户的调度表"（存于 `/var/spool/cron/`，各发行版路径略异），**语法错误保存时会被检查**；普通用户只能管自己的，root 可管所有人。

### 5.2 五字段格式与取值范围

格式：`分 时 日 月 周 命令`，如 `30 2 * * * /usr/local/bin/backup.sh`（每天 02:30 备份）。
| 字段 | 含义 | 取值范围 |
|---|---|---|
| 1 | 分钟 | 0–59 |
| 2 | 小时 | 0–23 |
| 3 | 日（月份中的第几天） | 1–31 |
| 4 | 月 | 1–12（或 `jan`–`dec`） |
| 5 | 周（星期几） | 0–7（**0 和 7 都表示周日**，或 `sun`–`sat`） |
| 6 | 要执行的命令 | 任何 shell 命令 |

::: warning 日/周是 OR 不是 AND
第 3、5 字段都填了非 `*` 时**满足任一即执行**：`0 0 1 * 1` 是"每月 1 号 **或** 每周一"，不是"1 号且周一"。
:::

### 5.3 特殊符号

| 符号 | 含义 | 例子 |
|---|---|---|
| `*` | 该字段任意值 | `* * * * *` = 每分钟 |
| `*/n` | 步进 | `*/15 * * * *` = 每 15 分钟 |
| `a-b` | 区间 | `9-18` = 9 到 18 点 |
| `a,b,c` | 列表 | `0,30` = 0 分和 30 分 |
| `@reboot` | 开机时 | `@reboot /usr/local/bin/start.sh` |
| `@daily`/`@midnight` | 每天 0:0 | 等价 `0 0 * * *` |
| `@hourly` | 每小时 0 分 | `0 * * * *` |

`crontab -e` 新增一行即生效，例如 `5 * * * * /usr/local/bin/cleanup.sh >/dev/null 2>&1`（每小时第 5 分钟跑清理）。

### 5.4 环境变量与系统级 cron

```bash
cat /etc/crontab        # 系统级 cron 表；/etc/cron.d/ 是系统级分片
```
预期输出片段：`SHELL=/bin/bash`、`PATH=/sbin:/bin:/usr/sbin:/usr/bin`、`MAILTO=root`，命令行形如 `* * * * * root cleanup.sh`（多了用户字段）。
解读：
- 用户 crontab 里**默认环境极简**：`PATH` 只有 `/usr/bin:/bin`、无你的别名/环境变量、工作目录是家目录。可在表头自声明 `PATH=...`、`MAILTO=you@example.com`（任务输出默认邮件发它）、`SHELL=/bin/bash`。
- `/etc/crontab` 与 `/etc/cron.d/` 是**系统级**（管理员用），命令**前多一个"用户"字段**：`* * * * * root 命令`。
- 任务有 stdout/stderr 时 cron 默认**发邮件**；不想收就 `>/dev/null 2>&1` 或重定向到日志文件。

### 5.5 cron 常见坑

| 坑 | 现象 | 对策 |
|---|---|---|
| 环境变量不全 | 脚本用到 `PATH` 外的命令报 not found | 脚本顶部 `set -a; source /etc/profile` 或写全路径 |
| 相对路径 | 脚本 `cd x` 找不到目录 | 一律绝对路径，`cd /opt/proj && ./run.sh` |
| 时间不一致 | "我 15 点提交怎么没跑" | cron 用系统时区；服务器漂 UTC 就比你本地差 8 小时 |
| 周/日 OR 陷阱 | 每月 1 号+周一理解错 | 见 5.2 的 warning |

```bash
tail -f /var/log/cron     # 或 grep cron /var/log/syslog：看 crond 实际执行记录
```
解读：`/var/log/cron`（部分发行版在 `/var/log/syslog`）记录每次调度命中——**定位"到底跑没跑"的第一现场**。

### 5.6 run-parts / anacron：系统目录任务与错过补跑

`run-parts` 按目录中的合法文件名依次执行脚本，系统的 `/etc/cron.daily`、`/etc/cron.weekly` 等目录经常由它调用：

```bash
run-parts --test /etc/cron.daily        # 只列出将执行的脚本，不执行
sudo run-parts --report /etc/cron.daily # 执行并报告脚本名/错误
```

预期输出（`--test`）：`/etc/cron.daily/logrotate`、`/etc/cron.daily/apt-compat`。文件名含点号等字符时，某些发行版的 `run-parts` 会跳过它；先用 `--test` 确认，手工执行目录前要确认不会重复触发备份、清理等生产任务。

`anacron` 面向“每天/每周/每月至少执行一次”的任务：机器关机错过时间后，在开机时按延迟补跑。配置文件通常是 `/etc/anacrontab`：

```bash
cat /etc/anacrontab
sudo anacron -T -t /etc/anacrontab       # 检查语法，不执行任务
echo 'date >> /tmp/batch-low-load.log' | batch
```

预期配置片段：

```
1       5       cron.daily      run-parts --report /etc/cron.daily
7       10      cron.weekly     run-parts --report /etc/cron.weekly
```

字段是“间隔天数、延迟分钟、任务标识、命令”；任务标识用于 `/var/spool/anacron/` 的时间戳判断。`batch` 是 `atd` 提供的低负载一次性任务队列，提交后可用 `atq` 查看、`atrm JOB` 删除；`anacron` 的 `-d`/`-n`/`-f` 会改变调度行为，线上调试前先读 man 和确认不会立即重复执行系统任务。

### 5.7 定时任务的 CPU/IO 资源控制

cron/anacron 只负责“何时启动”，不会自动降低任务优先级。对备份、压缩等可让路任务，可以在命令前加 `nice` 和 `ionice`：

```cron
30 2 * * * /usr/bin/nice -n 10 /usr/bin/ionice -c2 -n7 /usr/local/bin/backup.sh >>/var/log/backup.log 2>&1
```

含义：`nice -n 10` 让任务降低 CPU 调度优先级，`ionice -c2 -n7` 使用 best-effort IO 类的低优先级 7；也可用 `ionice -c3` 让任务只在没有其他 IO 时运行。任务仍可能占满磁盘带宽，建议同时限制并发、输出量和运行时长。systemd timer 则可在 service 的 `[Service]` 段使用 `Nice=`、`IOSchedulingClass=`、`IOSchedulingPriority=` 或 cgroup 的 `CPUWeight=`/`IOWeight=`。

## 6. at 一次性任务

cron 管"周期任务"，at 管"一次性、到点跑一次"的任务。守护进程是 `atd`。

### 6.1 交互式与管道式

```bash
at 23:00                              # 交互模式：输命令后 Ctrl+D 提交
echo '/usr/local/bin/backup.sh' | at now + 5 minutes   # 管道式，脚本化最常用
```
预期输出：`job 12 at Sat Aug 20 23:00:00 2026`。
解读：at 的时间语法很灵活：`now + 5 minutes`、`now + 2 hours`、`tomorrow 09:00`、`noon`、`teatime`（16:00）、`midnight`。提交后返回 **job 编号**，用它管理。

### 6.2 atq / atrm / batch

```bash
atq                # 列出排队任务（at -l）
atrm 12            # 删除 12 号任务（at -d 12）
batch              # 系统负载低于某阈值时才执行（旧式）
```
预期输出：`atq` 输出 `任务号 / 时间 / 队列字母(a) / 用户`，如 `4 Sat Aug 20 23:00:00 2026 a zhang`。

解读：`atrm` 按任务号删除；`batch` 相当于"负载允许时跑"的 at。现代 at 还可用 `at -l`/`at -q` 管理队列。

### 6.3 at vs cron

| 维度 | cron | at |
|---|---|---|
| 重复性 | 周期重复 | 一次性 |
| 配置方式 | crontab 表 | 交互/管道提交 |
| 管理命令 | `crontab -e/-l/-r` | `atq`/`atrm` |
| 典型场景 | 每天备份、定时清理 | 晚上临时维护、延迟重启服务 |

::: tip 现在少用 at，但要认识它
一次性任务现在更常见的是 `systemd-run --on-calendar "..."`（临时 timer）或 sleep+后台（[进程与作业控制](/kb/os/Bash/03-进程与作业控制/)），但 at 语法简单、无文件残留，脚本里临时"晚点执行"仍很顺手。
:::

### 6.4 systemd-inhibit：维护期间阻止关机/休眠

备份、升级或刷写固件期间，可以让一个命令持有 logind inhibitor lock：

```bash
systemd-inhibit --list
sudo systemd-inhibit --what=shutdown:sleep \
  --who=backup --why='backup in progress' --mode=block \
  -- /usr/local/bin/backup.sh
```

预期输出片段：

```
WHAT       WHO     WHY                MODE
shutdown   backup  backup in progress  block
```

命令结束后锁自动释放。`--mode=block` 阻塞对应操作，`--mode=delay` 只允许短暂延迟；它不是权限绕过，也不应包住无限期服务。长时间备份仍需要监控失败路径，否则可能让维护人员误以为“系统无法关机”。

### 6.5 shutdown / reboot / poweroff / halt / wall

关机前先广播维护窗口，再使用带明确时间和动作的命令：

```bash
echo 'System maintenance starts in 5 minutes.' | wall
sudo shutdown -h +5 'maintenance window'
sudo shutdown -c 'maintenance cancelled'
sudo shutdown -r now 'reboot after kernel update'
sudo systemctl reboot
sudo systemctl poweroff
sudo systemctl halt
```

预期输出片段：`Broadcast message from root@host ... The system is going down for poweroff in 5 minutes!`。`shutdown -h` 计划关机，`-r` 计划重启，`-c` 取消待执行计划；`reboot`/`poweroff`/`halt` 是传统命令，在 systemd 系统通常转发到对应 target。`halt` 是否切断电源依赖实现和参数，要求明确断电时用 `poweroff`。这些命令需要相应权限，且可能中断 SSH、写盘和正在运行的任务；执行前查看 `systemd-inhibit --list`、服务状态与备份状态。

## 7. systemd-timer（现代定时）

systemd 自家的定时器：**一个 `.timer` unit 到点激活配套的同名 `.service`**。比 cron 更现代、与 systemd 生态无缝。

### 7.1 Timer Unit 配置

写一对文件 `/etc/systemd/system/backup.service` + `/etc/systemd/system/backup.timer`：

```ini
[Unit]
Description=Nightly backup job
[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh
```
```ini
[Unit]
Description=Run backup every day at 02:30
[Timer]
OnCalendar=*-*-* 02:30:00      # 每天 02:30
OnBootSec=5min                 # 每次开机后 5 分钟触发一次
Persistent=true                # 开机时若错过上次调度，补跑
[Install]
WantedBy=timers.target
```
启用与查看：
```bash
sudo systemctl daemon-reload && sudo systemctl enable --now backup.timer  # 只 enable timer！
systemctl list-timers
```
预期输出（列：NEXT/LEFT/LAST/PASSED/UNIT/ACTIVATES）：
```
NEXT                          LEFT        UNIT          ACTIVATES
Tue 2026-08-11 02:30:00 CST   17h left    backup.timer  backup.service
```

### 7.2 OnCalendar / OnBootSec / OnUnitActiveSec / Persistent 语义

| 指令 | 语义 | 例子 |
|---|---|---|
| `OnCalendar=` | 日历表达式（类 cron 但更强） | `daily`、`Mon..Fri *-*-* 09:00:00`、`*-*-* 0/6:00:00` |
| `OnBootSec=` | 开机后相对时间 | `5min`、`30s` |
| `OnUnitActiveSec=` | **距上次激活后**的相对时间（滚动周期） | `1h` = 上次跑完 1 小时后再跑 |
| `Persistent=` | 开机时补跑"错过了的调度" | 服务器停机整晚，开机补上昨晚备份 |
| `RandomizedDelaySec=` | 随机延迟避免惊群 | 多机同时 `OnCalendar` 时错峰 |

### 7.3 systemd-analyze calendar 调试日历表达式

```bash
systemd-analyze calendar "Mon..Fri *-*-* 09:00:00"   # 换任意表达式调试
```
预期输出：
```
Normalized form: Mon..Fri *-*-* 09:00:00
    Next elapse: Mon 2026-08-11 09:00:00 CST
```
解读：写日历表达式**别靠猜**——先跑一遍看标准化形式与下一次触发时间。语法比 cron 灵活（`Mon..Fri`、`0/15` 每 15 分钟、`..` 区间、星期名等），对不上的坑在这里提前暴露。

### 7.4 timer vs cron 对比

| 维度 | cron | systemd-timer |
|---|---|---|
| 精度 | 分钟级 | 秒级 + 毫秒计时 |
| 持久化 | 无（错过就错过） | `Persistent=` 可补跑 |
| 依赖管理 | 无（脚本自理） | After/Requires 等 unit 依赖系统 |
| 日志 | `/var/log/cron` | journal，`journalctl -u xxx.timer` |
| 错峰 | 手动随机 | `RandomizedDelaySec=` |
| 与 systemd 集成 | 无 | `systemd-analyze calendar`、list-timers、开机自启 |

::: important 结论
新项目优先 systemd-timer：精度高、有日志、有依赖管理、能补跑。cron 在"简单、全网普及、老系统兼容"上仍有价值。掌握两者，按需选用。
:::

## 8. 日志与服务排障联动

排障是"看状态 → 看日志 → 看配置 → 修"的闭环，把前几节的工具串起来用。

### 8.1 服务起不来的排查套路

```bash
systemctl status myapp                                   # ① 状态与退出码
journalctl -u myapp -n 50 --since "5 min ago" -x         # ② 该 unit 近期日志（-x 带解释）
systemctl cat myapp                                      # ③ 复核配置文件
```
预期输出（常见失败形态）：
```
Active: failed (Result: exit-code)
Main PID: 4242 (code=exited, status=1/FAILURE)
```
`status` 里 `status=N` 的 `N` 就是**进程退出码**：

| 退出码/信号 | 含义 |
|---|---|
| `0` | 正常退出（若 Type 不该退却退了，说明配置/逻辑问题） |
| `1`/`2`/… | 程序自行报告的通用错误（看日志定位） |
| `127` | 命令不存在（`ExecStart` 路径写错，见 3.1） |
| `signal: KILL` | 被 SIGKILL（可能 OOM，看 journal 是否有 oom 记录） |

排障顺序：**status 拿退出码 → journalctl 看程序报错 → cat 复核配置 → 手动执行 ExecStart 复现**。这套闭环就是 [排查方法论](/kb/os/问题排查/00-系统问题排查方法论/) 在服务管理上的实例化，进一步参考 [启动排查](/kb/os/问题排查/06-系统启动与内核崩溃/)。

### 8.2 崩溃自动重启：Restart + RestartSec

```ini
[Service]
Restart=on-failure
RestartSec=3
```
| `Restart=` | 何时自动重启 |
|---|---|
| `no`（默认） | 不自动重启 |
| `on-success` | 退出码 0 时 |
| `on-failure` | 非零退出、被信号杀、超时（**最常用**） |
| `always` | 任何退出都重启 |

`RestartSec=` 设重启间隔（默认 100ms 几乎等于炸死重启，建议 3~5s）；另有 `StartLimitIntervalSec`/`StartLimitBurst` 启动限速兜底（默认 5 次/10s），超限进 failed 且拒绝再启，需 `systemctl reset-failed` 解除。

### 8.3 启动超时与资源限制

```ini
# 超时控制
TimeoutStartSec=90      # 启动允许时长，默认 90s
TimeoutStopSec=30       # 停止（等 SIGTERM 后 SIGKILL）时长
# 资源限制（[Service] 段）
LimitNOFILE=65535       # 打开文件描述符上限 → [[../Linux/15 文件描述符详解|fd]] 篇
MemoryMax=512M          # cgroup 内存上限，超了 OOM-kill → [[../Linux/09 Linux调度器原理|cgroup]]
```
解读：`LimitNOFILE` 对应第 15 篇的 fd 上限（高并发必调）；`MemoryMax` 走 cgroup v2，超限被 OOM 杀掉并记入 journal——"服务突然被杀"先查 journal 有无 `oom-kill`。`TimeoutStartSec` 超时判 failed，常见于启动脚本卡死。

### 8.4 定时任务故障定位

```bash
journalctl -u backup.service -n 50                 # ① timer 触发的 service 日志
systemctl status backup.timer backup.service       # ② 两方状态；list-timers --all 看下次触发
```
| 现象 | 先查哪 |
|---|---|
| timer 根本没到点 | 日历表达式错了 → `systemd-analyze calendar` |
| 到了点 service 没跑 | `journalctl -u xxx.timer`（timer 激活记录） |
| service 跑了但失败 | `journalctl -u xxx.service` + 退出码 |
| 服务器关机错过 | `Persistent=` 没开，开机不补跑 |

```bash
grep backup /var/log/cron     # cron 一侧同理，或 journalctl _COMM=crond
```
解读：定位定时任务 = **先确认"到底有没有触发"，再查"触发后干了什么"**。timer 走 journal、cron 走 `/var/log/cron`，两路都对得上号，任务才算健康。

## 9. 本章小结

- **systemd 一切皆 Unit**：`.service`/`.socket`/`.target`/`.timer`… 文件放 `/usr/lib`（厂商）/`/etc/systemd/system`（管理员，优先）；依赖 `Requires`（硬）+`Wants`（软）+`After`（顺序），target 是 runlevel 的语义化进化。
- **systemctl 控制面**：`start/stop/restart/reload`（reload 不中断）、`enable/disable`（软链接挂 target）、`mask/unmask`（连启都不行）、`status` 读 Loaded/Active/Sub/Main PID/CGroup、`is-active/is-enabled` 给脚本用、`cat` 看文件。改 unit 必 `daemon-reload`。
- **临时和兼容入口**：`systemd-run` 创建 transient service/timer，`systemd-analyze verify` 在 reload 前校验；`loginctl` 管会话与 user manager，`hostnamectl` 管主机名；旧系统认识 `service`/`chkconfig`，原生 systemd unit 优先用 `systemctl`。
- **Unit 文件三段式**：`[Unit]` 依赖、`[Service]` 运行、`[Install]` 自启；`Type=simple/forking/oneshot/notify` 决定"成功"的判定；`Restart=`+`RestartSec=` 崩溃自愈；`StandardOutput=journal` 默认接管输出。
- **Unit 进阶**：`systemctl edit` 写 drop-in override，`systemctl revert` 撤销本地覆盖；`.socket` 先监听再按需拉起 service，`.path` 监听路径变化触发同名 service。
- **journalctl 查日志**：`-b/-u/-p/-n/-f/-x/-o json-pretty`，`--since/--until` 按时间、`_PID=` 按字段；journal 在 `/var/log/journal`，用 `--vacuum-*` 控制大小。
- **高级日志**：`--list-boots`/`-k`/`-g` 跨启动、查内核和按消息正则过滤；`logger` 写结构化事件，`systemd-cat` 收集命令输出；文本日志用 `logrotate -d` 预演、`-f` 强制轮转。
- **cron 周期**：五字段 `分时日月周`（周 0 和 7 都是周日，日/周是 OR），`*/n`/`-`/`,`/`@daily`；环境极简、路径要绝对、时间看系统时区；日志在 `/var/log/cron`。
- **at/anacron/run-parts**：`at`/`batch` 处理一次性或低负载任务，`anacron` 处理按天/周/月且可补跑的任务，`run-parts` 批量执行系统任务目录；`nice`/`ionice` 可降低定时作业的 CPU/IO 优先级。
- **at 一次性 / timer 现代派**：`echo cmd \| at now + 5 minutes`、`atq`/`atrm`；timer 用 `OnCalendar`/`OnBootSec`/`OnUnitActiveSec`/`Persistent`，`systemd-analyze calendar` 验证，秒级精度 + 补跑 + 依赖管理，新项目首选。
- **维护和电源控制**：`systemd-inhibit` 防止关键任务期间被关机/休眠，`wall` 广播维护消息，`shutdown`/`reboot`/`poweroff`/`halt` 执行明确的电源动作；主机时区和终端环境延伸见未来的 [时间终端与环境管理命令](/kb/os/Bash/19-时间终端与环境管理命令/)。
- **排障闭环**：status 拿退出码 → journalctl 看日志 → cat 复核 → 手动复现；Restart/LimitNOFILE/MemoryMax/TimeoutStartSec 是四大运维旋钮。

## 10. 动手实验

1. **启用禁用一个真实服务**：`sudo systemctl status nginx ssh` 看状态；`sudo systemctl enable --now nginx` 后 `is-enabled`/`is-active`；再 `disable` + `stop` 恢复。观察 enable 建了哪个软链接（`ls -l /etc/systemd/system/multi-user.target.wants/`）。
2. **写一个自定义 service 并托管**：按 3.5 的 ticker 示例走一遍：写脚本 → 写 unit → `daemon-reload` → `enable --now` → `status` 确认 `active (running)`；故意把 `ExecStart` 路径写错再 `restart`，用 `status` 看 `failed` 与退出码，恢复后 `reset-failed`。
3. **journalctl 过滤练习**：对 `mytime` 执行 `journalctl -u mytime -f`（实时 tick）、`-p warning`（应无输出，都是 info）、`--since "1 min ago"`、`-o json-pretty -n 1`（看结构化字段）。
4. **crontab 定时练习**：`crontab -e` 加一行 `*/2 * * * * date >> /tmp/cronlog`；两分钟后 `cat /tmp/cronlog` 确认；`crontab -l` 检查、`tail /var/log/cron`（或 `grep CRON /var/log/syslog`）看调度记录；最后删除该行。
5. **at 一次性任务**：`echo 'date > /tmp/atlog' | at now + 1 minute`，`atq` 看到任务，一分钟后 `cat /tmp/atlog`；再提交一个任务用 `atrm` 删掉，验证 `atq` 里消失。
6. **systemd-timer 实践**：把练习 4 的脚本改写成 `myclock.service` + `myclock.timer`（`OnCalendar=*:0/2` 每 2 分钟），`enable --now` timer，`systemctl list-timers` 看 NEXT/LEFT，`systemd-analyze calendar "*:0/2"` 验证表达式，`journalctl -u myclock.service` 验证执行。
7. **Unit 校验与 override**：为 `myclock.service` 写一个 `systemctl edit myclock` drop-in，设置 `Nice=10` 和 `RestartSec=5s`；先用 `systemd-analyze verify`，再 `daemon-reload`/`restart`，用 `systemctl cat` 和 `show -p DropInPaths` 确认覆盖生效，最后 `systemctl revert` 清理。
8. **journal 与 logrotate 练习**：执行 `logger -t bash-note 'manual event'`、`printf 'timer event\n' | systemd-cat -t bash-note`，用 `journalctl -t bash-note -g 'event'` 查询；在临时日志路径写一个 logrotate 配置，用 `logrotate -d -v` 预演，不在系统配置上直接 `-f`。
9. **anacron/run-parts 观察**：`run-parts --test /etc/cron.daily` 列出合法脚本，读取 `/etc/anacrontab` 对照间隔/延迟/时间戳；不要在生产主机上用 `anacron -n -f` 触发全量系统任务。
10. **资源受控的一次性任务**：用 `echo 'sleep 20' | batch` 提交低负载任务，用 `atq`/`atrm` 管理；再以 `nice -n 10 ionice -c2 -n7` 包装临时压缩任务，比较 `ps -o ni` 和 `ionice -p PID`。
11. **socket/path unit 观察**：按 3.7 创建临时 `hello.socket` 或 `incoming.path`，先 `systemctl status` 观察监听/监控 unit，再触发连接或目录变化，用 `journalctl -u` 验证配套 service 被按需激活。
12. **维护抑制演练**：对 `sleep 30` 执行 `systemd-inhibit --what=shutdown:sleep --why='test' -- sleep 30`，另一个终端用 `systemd-inhibit --list` 观察锁，命令结束后确认锁自动消失；不要在真实维护任务上测试关机。

## 11. 自测题

1. **`systemctl enable nginx` 和 `systemctl start nginx` 的区别？** enable 创建开机自启软链接（挂进 target 的 `.wants/`），不立即启动；start 立即激活，不开机自启。想一步到位 `enable --now`。
2. **`systemctl reload nginx` 与 `systemctl restart nginx` 的区别？** reload 只发 SIGHUP 让进程重读自身配置，不断连接；restart 停止再启动，会断连接。另外 reload 动的是**服务自己的配置**，改 unit 文件则必须 `daemon-reload`。
3. **unit 文件修改后为什么必须先 `daemon-reload`？** systemd 启动时把 unit 定义缓存进内存，直接 restart 用的还是旧定义；`daemon-reload` 强制重读磁盘上的 unit 文件。
4. **`mask` 和 `disable` 的区别？** disable 只取消开机自启（仍可手动 start）；mask 把 unit 软链到 /dev/null，任何 start/enable 都被拒绝，是"彻底禁用"。不想卸载又要绝对禁止启动时用 mask。
5. **判断 crontab 表达式 `0 0 1 * 1` 的执行语义。** 每月 1 号的 0 点 **和/或** 每周一的 0 点执行（日、周字段任一匹配即执行，OR 语义），不是"1 号且周一"。这是 cron 五大字段最常见的坑。
6. **写出"每个工作日的 09:15 执行 backup.sh"的 crontab 行，并说明含义。** `15 9 * * 1-5 /usr/local/bin/backup.sh`——分钟 15、小时 9、日`*`、月`*`、周 1-5（周一至周五）；命令用绝对路径。
7. **`journalctl -u nginx -p err` 和 `journalctl -u nginx` 的区别？** `-p err` 只显示 err 及以上优先级（err/crit/alert/emerg），过滤掉 info/debug 等噪音；不带 `-p` 显示全部。排障时先看 err 快速定位，再放开看上下文。
8. **cron 与 systemd-timer 各适合什么场景？为什么推荐新项目用 timer？** cron 适合简单、跨系统一致的周期任务；timer 有秒级精度、`Persistent=` 补跑、unit 依赖管理、日志进 journal、`RandomizedDelaySec` 错峰，与 systemd 生态一体，故新项目优先；cron 在"只求简单/老系统"上仍有价值。
9. **`systemd-analyze verify` 和 `daemon-reload` 分别解决什么问题？** `verify` 读取 unit 并报告语法、未知键和部分依赖错误；`daemon-reload` 让 PID 1 重新加载磁盘上的 unit。通常先 verify，再 reload，最后 restart/start。
10. **`systemctl edit nginx` 为什么比直接改 `/usr/lib/systemd/system/nginx.service` 更好？** 它把差异写进 `/etc/...service.d/override.conf`，不改包管理器文件，升级不覆盖；查看合并结果用 `systemctl cat`，清除本地覆盖用 `systemctl revert`。
11. **`journalctl -b -1 -k`、`journalctl -g`、`logger`、`systemd-cat` 的作用如何区分？** `-b -1 -k` 查上次启动的内核日志，`-g` 按 MESSAGE 正则过滤，`logger` 写入一条 syslog/journal 事件，`systemd-cat` 收集命令的 stdout/stderr。
12. **cron、anacron、batch、systemd-timer 各解决什么时间问题？** cron 按分钟周期执行，anacron 按日/周/月并在错过后补跑，batch 等低负载后执行一次，systemd-timer 提供 unit 依赖、journal、精度和 `Persistent=` 补跑。
13. **为什么定时备份常用 `nice` + `ionice`？** cron 只决定启动时间；`nice` 降低 CPU 优先级，`ionice` 降低块 IO 优先级，让备份在业务负载下让路，但它们不是带宽硬限制，仍需观察资源和日志。
14. **`systemd-inhibit` 能否永久禁止关机？** 不能也不应该；它只在被包装的命令存活期间持有 inhibitor lock，命令退出锁自动释放。用 `--list` 检查当前锁，维护结束后应确认没有残留。
