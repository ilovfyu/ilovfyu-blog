::: abstract 本章定位
网络是系统排障时最常"背锅"的环节。本篇覆盖**完整网络命令集**：`ip` 管接口/路由，`ss`/`lsof` 看端口，`ping`/`traceroute`/`mtr` 测连通，`dig` 查 DNS，`curl`/`wget` 发 HTTP，`nc`/`nmap` 探端口，`tcpdump` 抓包。Linux 实操篇 [已讲过连接与 TCP 状态机](/kb/os/Linux/05-Linux网络与系统调用实操/)，本篇聚焦命令用法与排障组合。
:::

"网络又挂了？"先别甩锅。从本机接口、路由、DNS 到对端端口，每层都有"一句话命令"，把它们排成一条排查流水线：`ip` 看接口 → `ip route` 看路由 → `ss` 看端口 → `dig` 看 DNS → `ping`/`nc` 测对端。本篇是 [命令学习路线](/kb/os/Bash/00-Bash命令学习路线总览/) 的"四大金刚"之一，下一篇 [系统监控命令](/kb/os/Bash/07-系统监控与性能命令/) 讲资源，本篇讲网络。

## 1. ip 命令家族：现代网络配置

`ip` 是 `iproute2` 的现代命令，一个二进制管住所有网络对象：`addr`（地址）、`link`（链路/接口）、`route`（路由）、`neigh`（邻居缓存/ARP）。

### 1.1 ip addr：查看 IP/MAC/状态

```bash
ip addr            # 等价简写：ip a
```
预期输出片段：
```
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 qdisc noqueue state UNKNOWN ...
    inet 127.0.0.1/8 scope host lo
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP ...
    link/ether 52:54:00:12:34:56 brd ff:ff:ff:ff:ff:ff
    inet 192.168.1.100/24 brd 192.168.1.255 scope global dynamic eth0
```

### 1.2 ip a 各字段解读

以 `2: eth0` 那行为例逐段拆解：

| 字段 | 含义 |
|---|---|
| `2:` | 接口编号（内核索引） |
| `eth0` | 接口名 |
| `mtu 1500` | 最大传输单元，默认 1500 字节（以太网） |
| `state UP` | 链路状态：`UP`/`DOWN`/`UNKNOWN`（lo 常为 UNKNOWN） |
| `link/ether ...` | **MAC 地址**（物理地址） |
| `inet 192.168.1.100/24` | **IPv4 地址 + 前缀**，`/24` = 掩码 255.255.255.0 |
| `brd 192.168.1.255` | 广播地址 |
| `scope global dynamic` | 作用域（global 可跨网段）；`dynamic` = DHCP 分配 |
| `inet6 fe80::...` | IPv6 链路本地地址 |

### 1.3 ip link：链路层状态与统计

```bash
ip link                  # 查看所有接口
ip -s link show eth0     # -s：附加收发字节/包/错误统计
```
预期输出片段（`-s`）：
```
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 ... state UP
    RX: bytes  packets  errors  dropped overrun mcast
        12345678 123456   0       12      0      0
    TX: bytes  packets  errors  dropped carrier collsns
        9876543  98765   0       3       0      0
```
解读：`RX`/`TX` 两侧 errors/dropped 非 0 值得警惕——`RX errors` 多为物理层问题（网线/协商速率），`TX errors` 多为对端或双工问题。

### 1.4 ip route：路由表

```bash
ip route            # 等价简写：ip r
```
预期输出片段：
```
default via 192.168.1.1 dev eth0 proto dhcp metric 100
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.100
```
解读：
- 第一行 **default 路由（默认网关）**：路由表查不到的目标都发给 `192.168.1.1`（路由器）；第二行 **直连路由**：到 `192.168.1.0/24` 这个网段不用网关，直接走 eth0（`scope link`）。

::: important "网络不通先看路由"
数据包走向由路由表决定。`ping 不出去`时 `ip route` 是必查项：没有 default 路由 = 只能到本网段，上不了外网。
:::

### 1.5 ip neigh：ARP 邻居缓存

```bash
ip neigh           # 等价简写：ip n
```
预期输出片段：
```
192.168.1.1 dev eth0 lladdr 60:da:88:xx:xx:xx REACHABLE
192.168.1.9 dev eth0 FAILED
```
解读：`neigh` 是 ARP 表——"IP 对应哪个 MAC"。`REACHABLE` = 刚通信过，`STALE` = 一段时间没用，`FAILED` = ARP 没回应（对端关机或被防火墙挡）。

### 1.6 ip vs ifconfig 对比

| 功能 | 现代 `ip` | 老 `ifconfig` | 说明 |
|---|---|---|---|
| 看所有接口 | `ip addr` / `ip link` | `ifconfig -a` | ip 是唯一标准 |
| 只看 IP | `ip -4 -o addr` | `ifconfig eth0` | 脚本用 ip |
| 启用/禁用 | `ip link set eth0 up/down` | `ifconfig eth0 up/down` | 见 1.7 |
| 看路由 | `ip route` | `route -n` | route 属 net-tools |
| 看 ARP | `ip neigh` | `arp -a` | 数据来源相同 |

::: warning ifconfig 可能没装
新发行版（尤其容器镜像）默认不带 net-tools，只带 `iproute2`。**优先用 `ip`**，它是未来；ifconfig 只存在于老文档和老习惯里。
:::

### 1.7 启用/禁用接口

```bash
sudo ip link set eth0 down     # 关闭 eth0（模拟断网，小心 SSH 掉线！）
sudo ip link set eth0 up       # 重新启用
ip link set eth0 mtu 1400      # 临时改 MTU（排查 MSS 问题常用）
```

## 2. 连接与端口：ss / netstat / lsof

### 2.1 ss：现代连接统计

```bash
ss -tunlp          # -t TCP -u UDP -n 不解析域名 -l 仅监听 -p 显示进程
```
预期输出片段：
```
Netid  State   Local Address:Port   Peer Address:Port   Process
tcp    LISTEN  0.0.0.0:22           0.0.0.0:*           users:(("sshd",pid=523,fd=3))
tcp    LISTEN  127.0.0.1:3306       0.0.0.0:*           users:(("mysqld",pid=1120,fd=7))
```
解读：`0.0.0.0:22` = 在所有网卡上监听 22；`127.0.0.1:3306` = 只在本机回环监听（外部访问不到，属安全设计）。`-p` 需 root 才能看到别人进程的 PID。

```bash
# 状态统计：各 TCP 状态各有多少连接
ss -tan | awk 'NR>1 {print $1}' | sort | uniq -c
```
预期输出片段：
```
  40 TIME-WAIT
   3 ESTAB
   2 LISTEN
```
::: note TIME_WAIT 是正常的
高并发短连接必然产生大量 TIME_WAIT（主动关闭方等 2MSL），不是故障。**若堆积的是 `CLOSE_WAIT` 才要警惕**（被动方收到 FIN 但应用没 close = 代码泄漏）。原理见 [网络栈原理](/kb/os/Linux/13-Linux网络栈内核原理/)。
:::

```bash
# 看连接拥塞窗口 cwnd 与往返时间 rtt（TCP 细节）
ss -tin            # -i 显示 socket 内部信息
```
预期输出片段：
```
ESTAB 0 0 192.168.1.100:22 192.168.1.9:40001
     cubic rtt:18.5/0.5 mss:1448 cwnd:10 ssthresh:7
```
解读：`cwnd`（拥塞窗口）是当前能一口气发出的报文数，网络卡顿/丢包时会被砍掉重爬；`ssthresh` 是慢启动阈值。线上"看 TCP 在干什么"，`ss -tin` 是零开销入口。

### 2.2 netstat：经典兼容

```bash
netstat -tunlp
```
预期输出片段：
```
Proto Recv-Q Send-Q Local Address  Foreign Address State   PID/Program name
tcp        0      0 0.0.0.0:22     0.0.0.0:*        LISTEN  523/sshd
```
解读：功能与 `ss` 重叠，脚本兼容性好。**`Recv-Q`/`Send-Q` 非 0 = 数据堆积**（`Recv-Q` 大 = 应用读太慢，`Send-Q` 大 = 对端收不动）。

### 2.3 lsof -i：谁占着端口

```bash
sudo lsof -iTCP         # 所有 TCP
sudo lsof -iUDP         # 所有 UDP
sudo lsof -iTCP:80      # 组合协议与端口
```
预期输出片段：
```
COMMAND  PID  USER   FD   TYPE DEVICE  SIZE/OFF NODE NAME
java    8123 app    11u  IPv4 654321       0t0  TCP *:8080 (LISTEN)
nginx   1200 root   12u  IPv4 998877       0t0  TCP *:80 (LISTEN)
```

### 2.4 端口占用排查：谁占了 8080

"端口起不来 / Address already in use"是最高频故障，快速定位：

```bash
sudo lsof -i :8080               # 谁打开着 8080
sudo lsof -i :8080 -sTCP:LISTEN  # 只找监听的（排除已建立的）
```
::: tip 找不到监听进程？
`lsof` 查不到 PID 时先 `ss -tlnp` 对比（容器里是 `docker-proxy`）。杀掉进程后端口可能仍在 TIME_WAIT，`ss -tan | grep 8080` 确认，不必强杀。
:::

## 3. ping 与连通性

### 3.1 ping：ICMP 连通性测试

```bash
ping -c 4 -i 0.5 -s 100 baidu.com   # -c 次数 -i 间隔秒 -s 包大小
```
预期输出：
```
PING baidu.com (39.156.66.10) 100(128) bytes of data.
108 bytes from 39.156.66.10: icmp_seq=1 ttl=52 time=18.9 ms

--- baidu.com ping statistics ---
4 packets transmitted, 4 received, 0% packet loss
rtt min/avg/max/mdev = 18.7/18.9/19.1/0.17 ms
```

| 字段 | 含义 |
|---|---|
| `icmp_seq=1` | 报文序号，缺号 = 丢包 |
| `ttl=52` | **Time To Live**：每过一个路由器减 1，减到 0 丢弃。Linux 初始 64，`64-52=12` = 过了 12 跳 |
| `time=18.9 ms` | 往返时间 RTT |
| `0% packet loss` | 丢包率 |
| `rtt avg/mdev` | 平均延迟 / **抖动**（mdev 大 = 网络不稳） |

### 3.2 ping vs 防火墙禁 ICMP

- **ping 不通未必是网络问题**：很多云厂商/公司防火墙默认丢弃 ICMP，TCP 却是通的；**不要只用 ping 下结论**，改用 TCP 端口测试（`nc -zv`、`curl`）或 `traceroute -T`（TCP 探测）。
- 反方向：你要禁 ping，用 `iptables -A INPUT -p icmp --icmp-type echo-request -j DROP`（或 firewalld 移除 `echo-request` 服务）。

::: warning 结论要写协议
报告"网络不通"前必须写清用的什么协议：`ping 通 = ICMP 通，未必 HTTP 通；ping 不通 = ICMP 被禁，未必服务不通`。连接可达以 **TCP 三次握手是否成功** 为准。
:::

### 3.3 traceroute：看路径与定位断点

```bash
traceroute -n -w 2 baidu.com   # -n 不做反解DNS（更快） -w 每跳等待2秒
```
预期输出片段：
```
traceroute to baidu.com (39.156.66.10), 30 hops max, 60 byte packets
 1  192.168.1.1    0.5 ms  0.4 ms  0.4 ms
 2  10.0.0.1       2.1 ms  2.0 ms  2.2 ms
 3  61.148.3.5     8.3 ms  8.1 ms  8.4 ms
 4  * * *
 5  39.156.66.10  18.9 ms  19.2 ms  19.0 ms
```
解读：
- 每一行 = 路径上**第 N 个路由器**（TTL=1 的第一个路由回 TTL exceeded，依此类推）；每跳 3 个 RTT 能看出"慢在哪一跳"。
- `* * *` = 该跳不回应 ICMP（可能被防火墙丢，**不代表断**）；连续多跳 `*` 才值得怀疑。加 `-T` 改用 **TCP SYN** 探测（`traceroute -T -p 443`）能穿透禁 ICMP 的防火墙。

### 3.4 mtr：traceroute + ping 合体

```bash
mtr -n baidu.com        # 实时刷新每一跳的丢包率与延迟
```
预期输出片段（交互界面）：
```
HOST: myhost               Loss%  Snt   Last  Avg  Best  Wrst
 1. 192.168.1.1             0.0%   10   0.5   0.6   0.4   0.8
 2. 10.0.0.1                0.0%   10   2.1   2.0   1.9   2.3
 3. 61.148.3.5             20.0%   10   8.3   15.6   8.1   41.2
 4. 39.156.66.10            0.0%   10   18.9   19.3   18.7   21.0
```
解读：`mtr` = traceroute 的路径 + ping 的持续统计。**哪一跳 `Loss%` 高，哪一跳就是瓶颈**（注意：路径中段路由常因限速故意丢包，只有最后一跳丢包才直接对应服务故障）。运维报障常直接贴 mtr 结果。

## 4. DNS 工具

### 4.1 dig：DNS 查询瑞士军刀

```bash
dig example.com              # 默认查询 A 记录（IPv4）
dig +short example.com       # 只输出 IP，脚本友好
dig +trace example.com       # 从根服务器逐级追踪（看完整解析链）
```
预期输出（完整 A 查询）：
```
;; ANSWER SECTION:
example.com.        3600    IN      A       93.184.216.34
;; Query time: 12 msec
;; SERVER: 127.0.0.53#53(127.0.0.53)
```
解读：`ANSWER SECTION` 里 `3600` 是 **TTL（缓存秒数）**，`A` 是记录类型；`+short` 模式只回 `93.184.216.34` 一行。`SERVER: 127.0.0.53` 说明走的是本机 systemd-resolved 转发（见 4.4），`Query time` 是查询耗时。

```bash
dig +short example.com MX     # 邮件服务器记录
dig +short example.com TXT    # 文本记录（SPF/DKIM 验证）
dig +short example.com NS     # 权威域名服务器
dig @8.8.8.8 example.com      # 指定 DNS 服务器（跳过本地缓存）
```
::: tip 记录类型速查
A/AAAA（IPv4/IPv6 地址）、CNAME（别名）、MX（邮件）、NS（域名服务器）、TXT（SPF/验证）、PTR（反向：IP 查域名，`dig -x 8.8.8.8`）。
:::

### 4.2 nslookup：老牌 DNS 工具

```bash
nslookup example.com
```
预期输出：
```
Server:		127.0.0.53
Address:	127.0.0.53#53
Non-authoritative answer:
Name:	example.com
Address: 93.184.216.34
```
解读：`Non-authoritative answer` = 缓存/递归结果而非权威答案（**绝大多数日常查询都如此**，正常）；交互模式输入 `server 8.8.8.8` 可切换 DNS。

### 4.3 dig vs nslookup vs host

| 工具 | 优点 | 缺点 | 用在哪 |
|---|---|---|---|
| `dig` | 信息最全（TTL、SERVER、+trace）、可脚本 | 输出冗长 | **首选**，排障/调试 |
| `nslookup` | 老、交互友好、简单查询快 | 信息少、显示"非权威"让人困惑 | 简单确认域名有记录 |
| `host` | 输出最精简（`host example.com` 一行出 IP） | 选项少 | 快速查 IP/PTR |

### 4.4 /etc/resolv.conf 与 /etc/hosts

```bash
cat /etc/resolv.conf
```
预期输出（systemd-resolved 管理时）：
```
nameserver 127.0.0.53
options edns0
```
```bash
cat /etc/hosts
```
预期输出片段：
```
127.0.0.1   localhost
::1         localhost ip6-localhost
```
解读：`nameserver` 列表 = 解析发往哪，**127.0.0.53 是本机 systemd-resolved 的转发器**，真正的上游由 `resolvectl status` 显示；`/etc/hosts` 是**静态映射**，本机测试域名/内网机器名都写这，且**优先级高于 DNS**。

### 4.5 systemd-resolved 与 resolvectl

```bash
resolvectl status                 # 看当前生效的 DNS 服务器与搜索域
resolvectl query example.com      # 查询并显示来源（cache/upstream）
resolvectl flush-caches           # 清空 DNS 缓存（改了 hosts/上游后很有用）
```
::: note 为什么域名解析"变了但没变"
systemd-resolved 有缓存，改完上游后不生效先 `resolvectl flush-caches`。`nslookup` 走 127.0.0.53 也会被同一缓存影响——这正是 **`dig`/`nslookup` 结果不一致**的常见原因（一个走了缓存、一个指定了 `@8.8.8.8`）。
:::

```bash
time dig example.com          # 第一次：Query time 12 msec
time dig example.com          # 第二次：Query time 0 msec（缓存命中）
```

## 5. HTTP 工具：curl 与 wget

### 5.1 curl：全能 HTTP 客户端

```bash
curl -I https://example.com            # -I 只取响应头
curl -X POST -d 'name=alice' https://api.example.com/login   # -X 方法 -d 表单数据
curl -H 'Authorization: Bearer token' https://api.example.com/me   # -H 自定义头
curl -o index.html https://example.com # -o 下载保存为文件名
```
预期输出（`curl -I`）：
```
HTTP/2 200
content-type: text/html
server: nginx
content-length: 1256
```
解读：第一行 `HTTP/2 200` 是**状态行**（协议版本 + 状态码）。状态码速记：`2xx` 成功、`3xx` 重定向、`4xx` 客户端错（404/403）、`5xx` 服务端错（500/502/503）。

### 5.2 curl -w：时间分解（接口慢在哪）

```bash
curl -s -o /dev/null -w '连接建立: %{time_connect}s\n首字节: %{time_starttransfer}s\n总计: %{time_total}s\n' https://example.com
```
预期输出：
```
连接建立: 0.018s
首字节: 0.221s
总计: 0.224s
```
解读：`-o /dev/null` 丢弃响应体，`-w` 输出格式化时间。**定位接口慢的标准手法**：

| 变量 | 含义 | 慢的指向 |
|---|---|---|
| `time_namelookup` | DNS 解析耗时 | DNS 慢/上游慢 |
| `time_connect` | TCP 三次握手 | 网络/防火墙 |
| `time_appconnect` | TLS 握手 | 证书/加密协商 |
| `time_starttransfer` | 到首字节 | **服务器处理慢**（后端/DB） |
| `time_total` | 总耗时 | 加传输时间 |

::: tip API 调试三件套
`curl -v` 打印请求/响应全过程；`-k` 忽略自签名证书错误（仅测试用）；`--max-time 10` 设超时上限防挂死。REST 模板：`curl -X POST -H 'Content-Type: application/json' -d '{"k":"v"}'`。
:::

### 5.3 wget：下载器

```bash
wget -c https://example.com/big.iso      # -c 断点续传（下载中断后继续）
wget -r -np https://example.com/docs/    # -r 递归下载整站 -np 不跳上级目录
wget -O my.html https://example.com/     # -O 改名保存
wget --limit-rate=100k https://example.com/big.iso   # 限速 100KB/s
```
::: note -c 续传的原理
`wget -c` 通过 HTTP 的 `Range` 头（`Range: bytes=已下载-`）从断点继续，服务端须支持 Range 才有效（静态文件服务器支持，动态页面通常不支持）。
:::

### 5.4 curl vs wget 对比

| 维度 | `curl` | `wget` |
|---|---|---|
| 定位 | HTTP/API 调试工具 | 下载工具 |
| 默认行为 | 输出到屏幕 | 保存成文件 |
| 方法/POST/头 | 原生支持（`-X -d -H`） | 不擅长 |
| 断点续传 | `-C -` | `-c` |
| 递归下载 | 不支持 | `-r` |

## 6. 连通性测试与端口扫描

### 6.1 nc/ncat：瑞士军刀

```bash
nc -zv example.com 80       # -z 只探测端口不传数据 -v 显示详情
```
预期输出：
```
Connection to example.com (93.184.216.34) port 80 [tcp/http] succeeded!
```
解读：**端口通不通最可靠的测试**——它真的做一次 TCP 握手。相比 ping（可能被 ICMP 防火墙挡），`nc -zv` 测的是目标服务真实监听的端口。

```bash
nc -l 9000                  # 监听 9000（配合测传输）
nc 10.0.0.5 9000 < file     # 发文件；另一台 nc -l 9000 > file 收——最简单的局域网传文件
```
::: warning nc 别在生产乱玩
`nc -l` 监听任意端口 + 裸传文件不加密、无鉴权。正经传文件用 `scp`/`rsync`。
:::

### 6.2 telnet：老式端口测试

```bash
telnet example.com 80
# 连接成功后直接敲一行 HTTP 请求：
GET / HTTP/1.0
```
预期输出：
```
Trying 93.184.216.34...
Connected to example.com.
Escape character is '^]'.
```
解读：telnet 时代的"手动敲协议"。现在只剩两个用途：**测端口通不通**（`telnet host 80`，通就显示 `Connected to`）、**手搓 HTTP/SMTP 等文本协议**（连上后输入 `GET / HTTP/1.0` 能收到响应头）。多数系统默认没装 telnet-client，`nc` 是更现代的替代。

### 6.3 nmap：端口扫描

```bash
nmap -sn 192.168.1.0/24          # -sn 主机发现（旧写法 -sP 已废弃保留为别名）：网段内哪些主机在线
nmap -sS -p 1-1000 192.168.1.10  # -sS SYN半开扫描（需 root）-p 端口范围
nmap -sT -p 22,80,443 192.168.1.10  # 非 root 时退化为全连接扫描
```
预期输出片段：
```
PORT   STATE SERVICE
22/tcp open  ssh
80/tcp open  http
443/tcp open  https
```
解读：`open` = 有服务监听；`filtered` = 被防火墙挡了（无响应）。`-sS` 发 SYN 不完成握手（半开扫描），比全连接扫描隐蔽、快。
::: warning nmap 使用边界
扫描自己/内网测试环境没问题；**未经授权扫描他人机器违反法律**（中国《网络安全法》明确禁止）。生产环境谨慎，扫描前确认权限。
:::

## 7. 路由与转发

### 7.1 ip route 增删改查

```bash
ip route add 10.0.0.0/8 via 192.168.1.1 dev eth0      # 加一条静态路由
ip route del 10.0.0.0/8                                # 删除
ip route add default via 192.168.1.1                   # 设置默认网关
ip route replace default via 192.168.1.2               # 替换默认网关
ip route show                                          # 查询（同 ip route）
```
::: note 临时的！
`ip route` 改动**重启即失效**（内存态）。要持久化：CentOS/RHEL 写 `/etc/sysconfig/network-scripts/route-eth0`，Debian/Ubuntu 写 `/etc/network/interfaces` 或 netplan。
:::

### 7.2 route 旧命令

```bash
route -n
```
预期输出片段：
```
Kernel IP routing table
Destination  Gateway      Genmask          Iface
0.0.0.0      192.168.1.1  0.0.0.0           eth0
192.168.1.0  0.0.0.0      255.255.255.0     eth0
```
解读：`route -n` 是老工具（net-tools），`0.0.0.0/0.0.0.0` 即默认路由。新老都可能遇到，看懂了就行，**新环境用 `ip route`**。

### 7.3 策略路由简介

默认一个路由表，策略路由（Policy Routing）允许**按源地址/标记走不同表**：

```bash
ip rule add from 192.168.1.100 table 100   # 来源 IP 走路由表 100
ip route add default via 10.0.0.1 table 100
```
解读：`ip rule` 管理"路由策略"（按优先级匹配），`table 100` 是独立路由表（表号在 `/etc/iproute2/rt_tables`）。典型场景：双线机房按源走不同出口、VPN 分流。日常少见，理解"路由不止一张表"即可。

### 7.4 连通性排障顺序：从本机到对端逐层

网络排障 = 从自己脚下逐步往外扫，**每层测通才进下一层**：

| 顺序 | 命令 | 验证什么 |
|---|---|---|
| 1. 本机回环 | `ping -c1 127.0.0.1` | 协议栈本身 OK |
| 2. 本机网卡 | `ip addr`（有 IP、state UP） | 接口配好、链路 UP |
| 3. 网关 | `ping -c1 192.168.1.1` | 局域网通 |
| 4. 路由表 | `ip route`（有 default） | 出得去 |
| 5. DNS | `dig +short example.com` | 域名能解析 |
| 6. 外网/对端 | `ping -c3 8.8.8.8`、`nc -zv host port` | 公网通、目标端口开 |

::: tip 分层定位口诀
**"自己 → 网关 → DNS → 对端"**。哪一步挂，问题就在那一层：第 3 步挂 = 局域网/网线；第 5 步挂 = DNS；第 6 步端口挂 = 目标服务或防火墙。呼应 [排查方法论](/kb/os/问题排查/00-系统问题排查方法论/) 的"先缩小范围再深挖"。
:::

## 8. 网络排障实战

### 8.1 一条命令组合：快速体检

```bash
ip a && ip route && ss -tlnp && dig +short example.com
```
解读：四段连发，一次拿到**接口、路由、监听端口、DNS 解析**四份快照。报障时"随手贴一条"让同事快速看全貌，也适合写进排障 checklist 开头。

### 8.2 tcpdump：抓包看真相

```bash
sudo tcpdump -i eth0 -nn -c 20 -w /tmp/cap.pcap
```
预期输出片段：
```
20:13:42.123456 IP 192.168.1.100.45210 > 93.184.216.34.443: Flags [S], seq 123, win 64240, length 0
20:13:42.123460 IP 93.184.216.34.443 > 192.168.1.100.45210: Flags [S.], seq 456, ack 124, length 0
20:13:42.123464 IP 192.168.1.100.45210 > 93.184.216.34.443: Flags [.], ack 457, length 0
```
解读：`-i eth0` 指定网卡、`-nn` 不解析域名/端口名、`-c 20` 抓 20 个包就停、`-w` 写 pcap（供 Wireshark 分析）。上面三行正是 **TCP 三次握手**（`S`=SYN、`S.`=SYN+ACK、`.`=ACK）——之前 `nc -zv`、`curl` 的底层过程。

```bash
sudo tcpdump -i any 'port 8080'          # 只看 8080 端口的流量
sudo tcpdump -i eth0 'tcp and dst port 443 and tcp[13] & 2 != 0'  # 只看入向 SYN
```
::: note 呼应 [Linux 实操篇 tcpdump](/kb/os/Linux/05-Linux网络与系统调用实操/)
那里讲了 `tcpdump` 与连接状态的关系；本篇补充**表达式过滤**（`port`/`host`/`tcp`、`and`/`or`、`tcp[13]`）。"说连不上却抓不到 SYN"时它是仲裁者：包没到 = 网络/防火墙；包到了 = 本机应用。
:::

### 8.3 实时流量监控

```bash
sudo nload            # 实时看每网卡收发流量（数值大屏）
sudo iftop            # 按连接排名的实时带宽（类似 top，按流量排序）
```
解读：`nload` 看**总量**（谁在进出），`iftop` 看**明细**（哪条连接最占带宽，类似 top 按流量排序）。排查"带宽被打满"首选 iftop。默认没装就 `apt install nload iftop` 或 `yum install`。

### 8.4 常见网络问题定位链路

结合 [排查方法论](/kb/os/问题排查/00-系统问题排查方法论/) 的框架，网络问题的标准定位链路：

| 症状 | 首选命令 | 若失败再看 |
|---|---|---|
| 完全不通 | `ip a` → `ip route` → `ping 网关` | `ip link` 看 state、`dmesg` 看网卡报错 |
| 能 ping 通但网页打不开 | `dig` → `nc -zv host 443` | `curl -v` 看 TLS 是否握手成功 |
| 域名解析失败 | `dig example.com` → `resolvectl status` | 换 `@8.8.8.8` 排除本地缓存 |
| 慢（非完全不通） | `curl -w` 时间分解 | `mtr` 看丢包、`ss -tin` 看 rtt/cwnd |
| 端口冲突起不来 | `ss -tlnp` / `lsof -i :port` | `fuser -k port/tcp` 强杀（谨慎） |
| 数据疑似丢包 | `ping -c100` 看 loss | `tcpdump` 抓包数 SYN/重传 |

::: important 一句排障心法
先**逐层排除**（接口→路由→DNS→对端），再**抓包仲裁**（tcpdump 看包到底到没到）。永远让数据说话，不要凭感觉重启服务。
:::

## 9. 链路硬件与驱动：ethtool

`ethtool` 直接查询网卡驱动，是定位“接口是 UP，但吞吐低/丢包高”的第一站。它通常不是最小化系统的默认包：Debian/Ubuntu 安装 `ethtool`，RHEL/Fedora 安装同名包；虚拟网卡、无线网卡和部分云厂商网卡不一定实现全部操作。

### 9.1 link：速率、双工与自协商

```bash
sudo ethtool eth0
```

预期输出片段：

```text
Settings for eth0:
        Supported link modes:   1000baseT/Full
        Advertised auto-negotiation: Yes
        Speed: 1000Mb/s
        Duplex: Full
        Auto-negotiation: on
        Link detected: yes
```

参数与解读：命令末尾直接写接口名即查询 link settings。`Link detected: yes` 说明物理载波存在；`Speed`/`Duplex` 是实际协商结果。千兆链路意外落到 `100Mb/s`，或一端全双工、一端半双工，常表现为吞吐低、重传和 CRC 错误增加。

```bash
sudo ethtool -i eth0       # 驱动名、固件版本、总线信息
sudo ethtool -P eth0       # permanent MAC，排除系统改名/改 MAC 的干扰
```

::: warning 远程机器不要随意重协商
`ethtool -s eth0 speed 1000 duplex full autoneg off` 会改变链路，可能立即断开 SSH，而且交换机端必须匹配。先通过带外控制台确认回滚路径；日常排障优先只读查询。持久化方式由 NetworkManager、systemd-networkd 或发行版网络配置决定，直接执行通常只在当前启动周期有效。
:::

### 9.2 offload：硬件卸载

```bash
sudo ethtool -k eth0
```

预期输出片段：

```text
Features for eth0:
rx-checksumming: on
tx-checksumming: on
tcp-segmentation-offload: on
generic-segmentation-offload: on
generic-receive-offload: on
```

```bash
sudo ethtool -K eth0 gro off gso off tso off   # 临时关闭，便于按线上报文大小抓包
sudo ethtool -K eth0 gro on gso on tso on      # 测试后恢复
```

参数与解读：`-k` 查看 feature，`-K` 修改 feature。TSO/GSO 在发送端合并分段，GRO/LRO 在接收端聚合包，可降低 CPU 开销；因此主机上的 `tcpdump` 可能看到“大于 MTU”的逻辑包，这不表示线上真的发了超大以太帧。

::: note 安全与差异
关闭 offload 会显著增加 CPU 和包率，只应短时诊断。`[fixed]` 表示驱动不允许修改；容器内常没有权限，虚拟网卡也可能只暴露部分 feature。抓线上真实帧时，优先在交换机镜像口或对端抓包，而不是长期关闭卸载。
:::

### 9.3 ring、channel 与统计

```bash
sudo ethtool -g eth0                    # 查看 RX/TX ring 当前值与上限
sudo ethtool -l eth0                    # 查看 channel/队列数
sudo ethtool -S eth0                    # 驱动私有统计
sudo ethtool --show-eee eth0            # 查看 Energy Efficient Ethernet（硬件支持时）
```

预期输出片段：

```text
Ring parameters for eth0:
Pre-set maximums:
RX:             4096
TX:             4096
Current hardware settings:
RX:             512
TX:             512
```

```bash
sudo ethtool -G eth0 rx 1024 tx 1024    # 增大 ring，临时缓解突发流量丢包
sudo ethtool -L eth0 combined 4          # 设置 combined channel 数
sudo ethtool -S eth0 | grep -Ei 'drop|miss|error|crc|timeout'
```

参数与解读：`-g/-G` 查询/设置描述符 ring；ring 太小可能在突发流量下出现 `rx_missed_errors`，过大则增加排队延迟。`-l/-L` 查询/设置硬件队列，队列数应结合 CPU、IRQ affinity/RPS/RFS 调整。`-S` 字段由驱动定义，重点观察计数是否持续增长，而不只是非零历史值。

::: tip 联动定位
`ip -s link` 看接口通用计数，`ethtool -S` 看驱动/硬件细分计数，`nstat` 看 IP/TCP 协议栈计数。IRQ、驱动模块和内核参数继续参考 [内核模块硬件与系统参数命令](/kb/os/Bash/17-内核模块硬件与系统参数命令/)。
:::

## 10. 内核计数、拓扑与流量控制

### 10.1 nstat：IP/TCP 协议栈计数器

`nstat` 属于 `iproute2`，读取 `/proc/net/netstat` 与 `/proc/net/snmp`，比解析 `netstat -s` 更适合脚本。

```bash
nstat -az 'Tcp*' 'Ip*'          # -a 绝对值，-z 连零值也显示，支持模式过滤
nstat -s 'TcpRetransSegs'       # -s 读取但不更新 nstat 的历史快照
nstat -r                        # 清除 nstat 自己保存的历史基线，不清内核计数
```

预期输出片段：

```text
#kernel
IpInReceives                    184025             0.0
IpInDiscards                    12                 0.0
TcpActiveOpens                  1532               0.0
TcpRetransSegs                  87                 0.0
```

解读：`TcpRetransSegs` 持续快速增长表示 TCP 重传；`IpInDiscards` 增长说明包进入 IP 层后被丢弃。默认运行会显示相对上次快照的增量并更新快照，`-a` 看自启动以来的绝对计数，`-s` 适合只观察而不改变工具基线。计数是全主机累计值，容器视图和网络命名空间可能不同。

### 10.2 rtmon 与 ip monitor：记录路由事件

```bash
ip monitor link address route neigh       # 前台实时看链路、地址、路由、邻居变化
sudo rtmon file /var/log/rtmon.log link address route
ip monitor file /var/log/rtmon.log        # 回放 rtmon 的二进制日志
```

预期输出片段：

```text
Deleted 192.168.1.0/24 dev eth0 proto kernel scope link
2: eth0: <BROADCAST,MULTICAST> mtu 1500 state DOWN
192.168.1.1 dev eth0 lladdr 60:da:88:00:00:01 STALE
```

参数与解读：`ip monitor` 只看到启动后的事件；`rtmon file` 适合在开机早期或后台长期记录 Netlink 事件，再用 `ip monitor file` 回放。输出中的 `Deleted`、`state DOWN` 能证明“路由被谁改之前发生过链路抖动”。二者属于 `iproute2`；日志会持续增长，应交给 logrotate，并限制权限，因为地址与拓扑属于敏感信息。

### 10.3 bridge：Linux 网桥与 FDB/VLAN

```bash
bridge link show                      # 端口及其所属网桥、STP 状态
bridge fdb show br br0                # 转发表：MAC 从哪个端口学到
bridge vlan show                      # VLAN membership/PVID
bridge mdb show                       # 组播数据库
```

预期输出片段：

```text
2: eth0 state UP @if3: <BROADCAST,MULTICAST,UP,LOWER_UP> master br0
52:54:00:12:34:56 dev veth0 master br0
port              vlan-id
eth0              1 PVID Egress Untagged
```

```bash
sudo ip link add br0 type bridge
sudo ip link set eth1 master br0
sudo ip link set br0 up
sudo bridge vlan add dev eth1 vid 10 pvid untagged
```

解读：`bridge fdb` 是二层 MAC 转发表，不是三层 `ip neigh`；`self` 表示网桥设备自身，`master` 表示桥内转发项。`bridge vlan` 操作要求网桥启用 VLAN filtering 才有预期隔离效果。

::: warning 网桥变更会改数据路径
把承载当前 SSH 的物理接口直接 enslave 到网桥，原接口上的 IP 通常应迁到 `br0`，否则可能立即断线。生产配置应交给 NetworkManager/systemd-networkd 持久化；Docker、Podman、libvirt、Kubernetes 也会创建和管理网桥，不要手工改其 FDB/端口。
:::

### 10.4 tc qdisc/class/filter 基础

`tc` 同属 `iproute2`。qdisc 决定如何排队，class 划分带宽层级，filter 把流量导入 class。

```bash
tc qdisc show dev eth0
tc -s qdisc show dev eth0              # -s 附带 sent/dropped/overlimits 计数
sudo tc qdisc replace dev eth0 root fq_codel
```

预期输出片段：

```text
qdisc fq_codel 0: root refcnt 2 limit 10240p flows 1024 quantum 1514
 Sent 12830492 bytes 92341 pkt (dropped 12, overlimits 0 requeues 3)
```

解读：`fq_codel` 通过按流分队和主动队列管理降低 bufferbloat；`dropped` 少量增长可能是算法主动控制延迟，不等同于网卡硬件丢包。`replace` 可重复执行，比 `add` 遇到已存在 qdisc 时更适合脚本。

一个最小 HTB 分类示例：

```bash
sudo tc qdisc replace dev eth0 root handle 1: htb default 20
sudo tc class replace dev eth0 parent 1: classid 1:1 htb rate 100mbit ceil 100mbit
sudo tc class replace dev eth0 parent 1:1 classid 1:10 htb rate 10mbit ceil 20mbit
sudo tc class replace dev eth0 parent 1:1 classid 1:20 htb rate 90mbit ceil 100mbit
sudo tc filter replace dev eth0 protocol ip parent 1: prio 1 u32 \
  match ip dst 203.0.113.0/24 flowid 1:10
tc -s class show dev eth0
tc filter show dev eth0 parent 1:
```

预期输出片段：

```text
class htb 1:10 parent 1:1 prio 0 rate 10Mbit ceil 20Mbit
 Sent 188420 bytes 1432 pkt (dropped 0, overlimits 91 requeues 0)
```

参数与解读：`handle 1:` 给根 qdisc 编号；`classid 1:10` 是受限 class；`rate` 是保证速率，`ceil` 是可借用上限；`default 20` 接住未命中过滤器的流量；filter 按目标网段把包送到 `flowid 1:10`。整套示例控制的是 **eth0 出方向**，入方向限速通常使用 IFB 重定向，复杂度更高。

```bash
sudo tc qdisc del dev eth0 root           # 删除实验 qdisc，恢复接口默认队列规则
```

::: warning tc 的生产风险
错误的默认 class、速率单位或 filter 会让 SSH 和业务一起限速。先保存 `tc -s qdisc/class/filter show` 输出，在测试接口验证，并准备带外访问。单位 `mbit` 是 Mbit/s，不是 MB/s；发行版默认 qdisc 可由 `net.core.default_qdisc` 和网络管理器设置。
:::

### 10.5 conntrack：连接跟踪观察

`conntrack` 用户态工具来自 Debian/Ubuntu 的 `conntrack` 包、RHEL/Fedora 的 `conntrack-tools` 包；它查看 Netfilter/NAT 使用的状态表。

```bash
sudo conntrack -L -p tcp --dport 443      # 列出目标端口 443 的 TCP 状态项
sudo conntrack -E -o timestamp,extended   # 实时监听 NEW/UPDATE/DESTROY 事件
sudo conntrack -S                         # 查看 searched/found/insert/drop 等统计
```

预期输出片段：

```text
tcp  6 431999 ESTABLISHED src=192.168.1.100 dst=203.0.113.10 sport=51522 dport=443 src=203.0.113.10 dst=192.168.1.100 sport=443 dport=51522 [ASSURED] mark=0 use=1
```

解读：同一项包含原方向和回复方向两个五元组；`ESTABLISHED` 是 conntrack 状态，`[ASSURED]` 表示已看到双向有效流量。`conntrack -S` 中 `insert_failed`/`drop` 增长可能意味着表满，再结合 `sysctl net.netfilter.nf_conntrack_count` 与 `nf_conntrack_max` 验证。

::: warning 只读与破坏性操作分开
`-L/-E/-S` 是观察；`conntrack -D` 删除匹配会话，`-F` 清空全部状态，会让现有 TCP/NAT 会话中断。删除与清空的安全流程见 [防火墙与网络安全命令](/kb/os/Bash/15-防火墙与网络安全命令/)，不要把 `-F` 当成普通排障动作。
:::

## 11. 邻居、路径与地址辅助工具

### 11.1 arping：同一二层网络验证 ARP

```bash
sudo arping -I eth0 -c 3 192.168.1.1
sudo arping -D -I eth0 -c 3 192.168.1.100   # DAD：检测准备使用的 IPv4 是否冲突
```

预期输出片段：

```text
ARPING 192.168.1.1 from 192.168.1.100 eth0
Unicast reply from 192.168.1.1 [60:DA:88:00:00:01]  0.812ms
Sent 3 probes (1 broadcast(s)); Received 3 response(s)
```

解读：`-I` 指接口，`-c` 限次数；能收到 ARP 回复说明本机到目标的二层广播域可达，即使目标禁了 ICMP ping。`-D` 没收到回复通常表示地址未被占用，收到回复则可能 IP 冲突。

发行版差异：Debian/Ubuntu 常见包为 `iputils-arping`，RHEL/Fedora 通常随 `iputils`；另有 Thomas Habets 版 `arping`，参数略有差异，先看 `arping --help`。ARP 不跨路由器，只对本地链路有意义，通常需要 `CAP_NET_RAW`/root。

### 11.2 tracepath：免 root 的路径 MTU 探测

```bash
tracepath -n example.com
tracepath -n -m 20 203.0.113.10
```

预期输出片段：

```text
 1?: [LOCALHOST]                      pmtu 1500
 1:  192.168.1.1                       0.624ms
 2:  10.0.0.1                          2.103ms
 5:  203.0.113.10                     18.912ms reached
     Resume: pmtu 1500 hops 5 back 5
```

解读：`-n` 禁止 DNS 反查，`-m` 限最大 hop。`pmtu` 是路径 MTU，途中下降可定位隧道/VPN 的 MTU 瓶颈。它通常用 UDP 错误队列且不要求 root；防火墙丢弃 ICMP 错误时同样可能显示 `no reply`。Debian/Ubuntu 包为 `iputils-tracepath`，RHEL/Fedora 通常在 `iputils`。

### 11.3 whois：查询注册与地址归属

```bash
whois example.com
whois 8.8.8.8
```

预期输出片段：

```text
Domain Name: EXAMPLE.COM
Registry Expiry Date: 2027-08-13T04:00:00Z
NetRange: 8.8.8.0 - 8.8.8.255
OrgName: Google LLC
```

解读：域名查询关注 registrar、状态和到期时间；IP 查询关注 RIR、网段与组织。WHOIS 字段因 ICANN/RIR 和隐私保护而异，联系人可能被隐藏，结果不是“IP 当前使用者”的法律证明。工具通常来自 `whois` 包；查询走 TCP/43，企业出口可能拦截，也应避免高频批量查询触发限速。

### 11.4 ipcalc：校验网段边界

```bash
ipcalc 192.168.10.37/24
ipcalc 10.0.0.0/20 --split 24       # 选项由 ipcalc 实现版本决定
```

预期输出片段：

```text
Address:   192.168.10.37       11000000.10101000.00001010.00100101
Netmask:   255.255.255.0 = 24
Network:   192.168.10.0/24
Broadcast: 192.168.10.255
HostMin:   192.168.10.1
HostMax:   192.168.10.254
Hosts/Net: 254
```

解读：它把地址、前缀、网络地址、广播地址和主机范围展开，适合在写路由/防火墙 CIDR 前防止边界算错。Debian 的 `ipcalc`、Fedora/RHEL 的 `ipcalc` 与新版 `ipcalc-ng` 选项不完全一致，脚本中先固定实现并检查 `ipcalc --version`；IPv6 没有广播地址。

## 12. 网络管理器与无线网络

### 12.1 resolvectl query/status 强化

```bash
resolvectl status                         # 全局与逐链路 DNS、搜索域、协议状态
resolvectl status eth0                    # 只看指定链路
resolvectl query -4 example.com           # 强制 IPv4 地址查询并显示来源接口/协议
resolvectl query -t MX example.com        # 指定 DNS RR 类型
resolvectl statistics                     # 缓存命中、失败查询等统计
```

预期输出片段：

```text
Link 2 (eth0)
    Current Scopes: DNS
         Protocols: +DefaultRoute +LLMNR -mDNS -DNSOverTLS DNSSEC=no/unsupported
Current DNS Server: 192.168.1.1
       DNS Servers: 192.168.1.1 1.1.1.1

example.com: 93.184.216.34                 -- link: eth0
             (example.com)
-- Information acquired via protocol DNS in 12.3ms.
```

解读：`status` 中逐 link 的 DNS 比只看 `/etc/resolv.conf` 更接近真实配置；`query` 输出 `-- link: eth0` 和协议，可发现 VPN split DNS 把某个域名送错接口。`resolvectl` 只适用于 systemd-resolved；未启用时用 NetworkManager 的 `nmcli dev show`、`dig` 和真实 `/etc/resolv.conf`。临时 `resolvectl dns eth0 ...` 会改变解析路径，远程机器先确认回滚方式。

### 12.2 nmcli：NetworkManager 的脚本接口

```bash
nmcli general status
nmcli device status
nmcli -f GENERAL,IP4,IP6,DNS device show eth0
nmcli connection show
nmcli connection show --active
```

预期输出片段：

```text
DEVICE  TYPE      STATE                   CONNECTION
eth0    ethernet  connected               Wired connection 1
wlan0   wifi      disconnected            --
lo      loopback  connected (externally)  lo
```

```bash
sudo nmcli connection up 'Wired connection 1'
sudo nmcli connection modify 'Wired connection 1' ipv4.dns '1.1.1.1 8.8.8.8'
sudo nmcli device reapply eth0
nmcli -t -f DEVICE,STATE device            # -t terse，适合脚本
```

参数与解读：`device` 看当前设备状态，`connection` 看持久化 profile；修改 profile 后用 `connection up` 重新激活，或在支持的属性上用 `device reapply` 尽量无断线应用。NetworkManager 是桌面 Linux、RHEL/Fedora、Ubuntu Server 部分安装方式的常见管理器。

::: warning 先判断谁在管理接口
`nmcli connection down` 会主动断链，不要对当前 SSH 接口执行。若接口由 netplan/systemd-networkd、ifupdown、云初始化或 Kubernetes 管理，手改 nmcli 可能不持久或与上层配置冲突；先看 `nmcli device status` 中是否为 `unmanaged`。
:::

### 12.3 networkctl：systemd-networkd 状态与重载

```bash
networkctl list
networkctl status eth0
networkctl lldp eth0                    # 对端交换机启用 LLDP 时显示邻居
sudo networkctl reload                  # 重读 .network/.netdev 配置
sudo networkctl reconfigure eth0        # 重新配置指定接口
sudo networkctl renew eth0              # 重新申请 DHCP 租约（版本支持时）
```

预期输出片段：

```text
● 2: eth0
                   Link File: /usr/lib/systemd/network/99-default.link
                Network File: /etc/systemd/network/20-wired.network
                       State: routable (configured)
                Online state: online
                        Type: ether
                     Address: 192.168.1.100
                     Gateway: 192.168.1.1
```

解读：`Network File` 能证明是哪份配置接管接口；`routable` 表示至少有可路由地址。该工具随 systemd 提供，只管理 systemd-networkd；服务没启用或接口由 NetworkManager 管理时，输出可能是 `unmanaged`。`reconfigure`/`renew` 可能短暂断网，且不同 systemd 版本的子命令有差异，执行前看 `networkctl --help`。

### 12.4 iw、iwctl 与 rfkill：无线排障

```bash
iw dev                                  # 无线 PHY/接口列表
iw dev wlan0 link                       # 当前 SSID、AP MAC、频率、信号、码率
sudo iw dev wlan0 scan                  # 主动扫描，输出很长且通常需 root
iw reg get                              # 当前无线监管域
rfkill list                             # 软件/硬件飞行模式状态
sudo rfkill unblock wifi
```

预期输出片段：

```text
Connected to 00:11:22:33:44:55 (on wlan0)
        SSID: corp-wifi
        freq: 5180
        signal: -57 dBm
        tx bitrate: 866.7 MBit/s

0: phy0: Wireless LAN
        Soft blocked: no
        Hard blocked: no
```

解读：信号约 `-30 dBm` 很强，`-67 dBm` 左右通常可用，低于 `-75 dBm` 易抖动，实际阈值依业务而定；`Hard blocked: yes` 通常要拨物理开关/BIOS，`rfkill unblock` 只能解除 soft block。`iw` 来自 `iw` 包，`rfkill` 来自同名包，它们只做底层查询/控制，不负责 WPA 认证。

iwd 管理环境可用 `iwctl`：

```text
$ iwctl
[iwd]# device list
[iwd]# station wlan0 scan
[iwd]# station wlan0 get-networks
[iwd]# station wlan0 connect corp-wifi
[iwd]# station wlan0 show
```

`iwctl` 来自非默认的 `iwd` 包；NetworkManager 可能使用 iwd 作为 Wi-Fi backend，但连接 profile 仍应通过 `nmcli` 管理，避免两个控制面同时抢接口。扫描结果包含周边 SSID/BSSID，分享排障输出前应脱敏。

## 13. socat 与 iperf3：转发和性能验证

### 13.1 socat：TCP/UDP/Unix socket 双向中继

`socat` 通常不是默认安装，Debian/Ubuntu、RHEL/Fedora 均使用 `socat` 包。它把两个“地址”连接起来，功能比 `nc` 更系统。

TCP：

```bash
socat -v TCP-LISTEN:9000,reuseaddr,fork STDOUT     # 服务端监听，每连接 fork
printf 'hello\n' | socat - TCP:192.168.1.10:9000  # 客户端，- 表示标准输入/输出
```

UDP：

```bash
socat -v UDP-RECVFROM:9001,reuseaddr,fork STDOUT
printf 'metric=1\n' | socat - UDP:192.168.1.10:9001
```

Unix domain socket：

```bash
socat UNIX-LISTEN:/tmp/demo.sock,unlink-early,fork STDOUT
printf 'local message\n' | socat - UNIX-CONNECT:/tmp/demo.sock
ss -xl | grep demo.sock
```

TCP 端口转发：

```bash
socat TCP-LISTEN:8443,bind=127.0.0.1,reuseaddr,fork TCP:10.0.0.5:443
```

预期 `-v` 输出片段：

```text
> 2026/08/10 12:00:00.000000  length=6 from=0 to=5
hello
```

参数与解读：`LISTEN`/`RECVFROM` 创建监听端，`fork` 支持多个客户端，`reuseaddr` 允许快速重启，`unlink-early` 清理旧 Unix socket，`bind=127.0.0.1` 限制本机访问，`-v` 把传输内容打印到 stderr。

::: warning socat 不是安全网关
上述 TCP/UDP 转发没有认证、访问控制和加密；省略 `bind` 往往监听所有地址。生产公网转发应配防火墙、TLS/VPN/SSH 隧道和进程托管，敏感数据不要开 `-v`。Unix socket 还要用 `mode=`、目录权限和 `umask` 控制访问。
:::

### 13.2 iperf3：吞吐、反向与 UDP 测试

两端都需安装非默认的 `iperf3` 包。先在测试目标启动服务端：

```bash
iperf3 -s                         # 默认监听 TCP 5201
iperf3 -s -1                      # 只服务一个客户端后退出，适合临时测试
```

客户端常用模式：

```bash
iperf3 -c 192.168.1.10 -t 10               # 单流 TCP，持续 10 秒
iperf3 -c 192.168.1.10 -P 4 -t 20           # 4 个并行流
iperf3 -c 192.168.1.10 -R                    # reverse：服务端向客户端发
iperf3 -c 192.168.1.10 -u -b 100M -t 10     # UDP，目标发送速率 100 Mbit/s
iperf3 -c 192.168.1.10 --get-server-output   # 客户端同时取回服务端视角
```

预期输出片段：

```text
[  5]   0.00-10.00  sec  1.08 GBytes   928 Mbits/sec    4  sender
[  5]   0.00-10.00  sec  1.08 GBytes   927 Mbits/sec       receiver
```

UDP 输出还会有 `Jitter` 与 `Lost/Total Datagrams`。解读：TCP 的 sender `Retr` 是重传次数；并行流明显更快可能说明单流受 RTT/窗口限制；`-R` 可识别上下行不对称；UDP 的 `-b` 是主动施加的速率，不等于链路能力，逐级提高才能找丢包拐点。

::: warning 性能测试会制造真实流量
先确认测试窗口和带宽上限，生产环境避免直接 `-P 16` 或无限提高 UDP `-b`。iperf3 默认没有业务级认证和加密，5201 只对白名单开放，测试后退出服务端；公网上可通过 VPN/SSH 隧道保护控制连接，但隧道本身会影响性能结果。
:::

## 14. tcpdump 过滤强化与 tshark

### 14.1 tcpdump：TCP flags、ICMP 与 ARP

```bash
sudo tcpdump -i any -nn -tttt -vv 'tcp port 443'
```

输出中的 TCP flags 速查：

| 显示 | 含义 |
|---|---|
| `[S]` | SYN，新建连接 |
| `[S.]` | SYN + ACK |
| `[.]` | ACK |
| `[P.]` | PSH + ACK，常携带应用数据 |
| `[F.]` | FIN + ACK，正常关闭 |
| `[R]`/`[R.]` | RST，立即复位 |

精准过滤：

```bash
# 只看发起连接的 SYN，不含 SYN+ACK
sudo tcpdump -i any -nn 'tcp[tcpflags] & (tcp-syn|tcp-ack) == tcp-syn'
# 只看 RST
sudo tcpdump -i any -nn 'tcp[tcpflags] & tcp-rst != 0'
# IPv4 ICMP echo request/reply；IPv6 ICMP 使用 icmp6
sudo tcpdump -i any -nn 'icmp[icmptype] == icmp-echo or icmp[icmptype] == icmp-echoreply'
sudo tcpdump -i any -nn 'icmp6'
# ARP 请求/响应，可进一步限定目标主机
sudo tcpdump -i eth0 -nne 'arp and host 192.168.1.1'
```

预期输出片段：

```text
2026-08-10 12:10:01.123456 IP 192.168.1.100.51522 > 203.0.113.10.443: Flags [S], seq 1, win 64240, length 0
2026-08-10 12:10:03.000001 ARP, Request who-has 192.168.1.1 tell 192.168.1.100, length 28
```

解读：只重复看到 `[S]` 而没有 `[S.]`，说明 SYN-ACK 没回来；立即 `[R]` 常表示目标没有监听或主动拒绝；ARP request 无 reply 指向二层/VLAN/目标离线问题。`-e` 显示二层 MAC，`-nn` 禁止名称解析，`-tttt` 给完整时间，`-vv` 展开更多字段。

::: note 捕获安全
抓包通常需要 root/`CAP_NET_RAW`，pcap 可能包含 Cookie、Token、内网地址和明文业务数据。用最窄 BPF、`-c`/`-G`/`-C` 限制规模，设置文件权限，分析后按数据保留政策删除。`-i any` 在 Linux 使用 cooked capture，二层字段与指定物理接口时可能不同。
:::

### 14.2 tshark：Wireshark 的命令行界面

`tshark` 通常不是默认安装：Debian/Ubuntu 包为 `tshark`，RHEL/Fedora 常在 `wireshark-cli`。抓包权限组配置因发行版而异，最小权限优于长期 sudo。

```bash
tshark -D                                      # 列出可抓接口及编号
sudo tshark -i eth0 -f 'tcp port 443' -c 20   # -f 是捕获过滤器（BPF）
sudo tshark -i eth0 -f 'tcp' \
  -Y 'tcp.flags.syn == 1 && tcp.flags.ack == 0' -c 20
tshark -r /tmp/cap.pcap -Y 'dns.flags.response == 1' \
  -T fields -e frame.time -e ip.src -e dns.qry.name -e dns.a
```

预期字段输出：

```text
Aug 10, 2026 12:20:00.123456  192.168.1.1  example.com  93.184.216.34
```

参数与解读：`-f` 在捕获前由内核过滤，语法同 tcpdump，能降低开销和文件体积；`-Y` 是 Wireshark display filter，协议字段丰富，但通常在捕获/读取后过滤；`-r` 读 pcap；`-T fields -e ...` 适合导出结构化字段。不要把 tcpdump 的 `tcp[13]` 语法写进 `-Y`，也不要把 `tcp.flags.syn` 写进 `-f`。

## 本章小结

- **接口与路由用 `ip` 家族**：`ip addr` 看 IP/MAC/状态，`ip link set up/down` 控制接口，`ip route` 看网关，`ip neigh` 看 ARP——全部为 ifconfig/route/arp 的现代替代。
- **端口与连接用 `ss`/`lsof`**：`ss -tunlp` 看监听，`ss -tin` 看 rtt/cwnd；`lsof -i :port` 找"谁占着端口"；TIME_WAIT 正常、CLOSE_WAIT 堆积才是问题。
- **连通性分层测**：`ping` 测 ICMP（可能被禁），`nc -zv` 测真实 TCP 端口，`traceroute`/`mtr` 定位路径断点。报"不通"要说明用的什么协议。
- **DNS 用 `dig`**：`+short` 取 IP、指定类型 A/MX/TXT、`@8.8.8.8` 绕过本地缓存；解析顺序 `/etc/hosts` 优先于 DNS，systemd-resolved 缓存用 `resolvectl flush-caches` 清。
- **HTTP 用 `curl`/`wget`**：`curl` 是 API 调试器（`-I`/`-X`/`-d`/`-H`/`-w`/`-k`/`--max-time`），`wget` 是下载器（`-c`/`-r`/`-O`）。
- **探端口用 `nc`/`nmap`**：`nc -zv host port` 是最准的端口测试；nmap 扫描必须获得授权。
- **最终裁决用 `tcpdump`**：包到没到、重传没重传，抓包一锤定音。排障铁律：逐层排除 → 抓包仲裁 → 数据说话。
- **链路硬件用 `ethtool`**：link 看速率/双工，`-k/-K` 看改 offload，`-g/-G` 管 ring，`-l/-L` 管 channel，`-S` 看驱动丢包；变更可能断链，只读排查优先。
- **内核与流控用 `nstat`/`rtmon`/`bridge`/`tc`/`conntrack`**：从协议计数、Netlink 事件、二层转发表、排队分类到状态连接，覆盖“包在哪一层丢”的证据链。
- **网络控制面先辨识**：NetworkManager 用 `nmcli`，systemd-networkd 用 `networkctl`，systemd-resolved 用 `resolvectl`；无线底层用 `iw`/`rfkill`，iwd 环境再用 `iwctl`，不要多个管理器抢同一接口。
- **临时中继与性能验证**：`socat` 覆盖 TCP/UDP/Unix socket/转发但不自带安全边界；`iperf3` 用 TCP、反向和 UDP 模式测吞吐，必须控制测试流量并限制服务端来源。
- **抓包分两层过滤**：tcpdump BPF 可看 TCP flags、ICMP、ARP；tshark 的 `-f` 是捕获过滤，`-Y` 是显示过滤。相关内核/硬件参数见 [内核模块硬件与系统参数命令](/kb/os/Bash/17-内核模块硬件与系统参数命令/)，替代工具与现代工作流见 [现代高效命令行工具](/kb/os/Bash/20-现代高效命令行工具/)。

## 动手实验

1. **ip addr 解读**：运行 `ip -br addr` 与 `ip addr`，识别本机的接口名、IP、子网掩码、MAC、接口状态；再用 `ip link set <接口> down`（用测试网卡/虚拟机）观察 `ip a` 中该接口从 `UP` 变 `DOWN`，记得改回来。
2. **ss 找监听端口**：`python3 -m http.server 8000` 起临时服务，用 `ss -tlnp | grep 8000`、`netstat -tunlp | grep 8000`、`lsof -i :8000` 三种方式找出它的 PID，验证"三兄弟"能互相印证。
3. **dig 查 DNS**：`dig +short baidu.com`、`dig baidu.com MX`、`dig @8.8.8.8 baidu.com` 各执行一遍，对比结果；再 `cat /etc/resolv.conf` 与 `resolvectl status`，弄清本机真正的上游 DNS 是谁。
4. **curl -w 时间分解**：对 `https://www.baidu.com` 跑 `curl -s -o /dev/null -w 'DNS:%{time_namelookup} 连接:%{time_connect} 首字节:%{time_starttransfer} 总:%{time_total}\n'`，指出哪一段耗时最长。
5. **nc 端口测试**：`nc -zv 127.0.0.1 22`（应通）、`nc -zv 127.0.0.1 9999`（应 failed），理解"端口通 = 服务真实在监听"。
6. **traceroute 看路径**：`traceroute -n baidu.com` 观察经过几跳、哪跳有 `*`；再 `mtr -n baidu.com` 按 `q` 退出，比较两者信息差异。
7. **三层计数交叉验证**：记录 `ip -s link show <接口>`、`sudo ethtool -S <接口>` 和 `nstat -az 'TcpRetransSegs' 'IpInDiscards'`，传输一个大文件后重查，说明每组计数位于驱动、接口还是协议栈。
8. **路径 MTU 与二层可达**：在测试网执行 `sudo arping -I <接口> -c 3 <网关>` 和 `tracepath -n <目标>`，分别解释 ARP 回复、hop 与 `pmtu`；不要对非本地网段使用 arping 下结论。
9. **iperf3 双向测试**：测试机 A 执行 `iperf3 -s -1`，B 分别执行普通 TCP、`-P 4` 和 `-R`；记录 sender/receiver、Retr 与方向差异。确保 5201 只对实验网开放。
10. **socat 三种地址**：在本机分别建立 TCP 9000、UDP 9001 和 `/tmp/demo.sock`，用客户端发送一行文本；再将 TCP listener 加 `bind=127.0.0.1`，用 `ss -ltnp` 验证暴露范围。
11. **抓握手与拒绝**：对一个开放端口和一个关闭端口执行 `nc -zv`，同时用 tcpdump 的 SYN/RST 过滤器观察 `[S]`、`[S.]`、`[R]`；把 pcap 交给 `tshark -r` 提取源/目标与 flags。
12. **tc 仅在隔离环境实验**：在网络命名空间或虚拟机给测试接口挂 `fq_codel`，用 `tc -s qdisc` 观察计数，最后 `tc qdisc del dev <接口> root` 清理。不要在当前 SSH 出口直接套 HTB 示例。

## 自测题

1. **`ip a` 中 `state UP`、`inet 192.168.1.100/24`、`link/ether` 分别代表什么？** 接口链路状态；IPv4 地址及前缀（/24=255.255.255.0）；MAC 物理地址。
2. **`ss -tan | awk 'NR>1{print $1}' | sort | uniq -c` 的意图？** 统计 TCP 各状态（ESTAB/TIME-WAIT/LISTEN…）的连接数量，快速判断是否有异常堆积（如 CLOSE_WAIT 过多）。
3. **ping 通但网页打不开，优先查什么？** ① DNS（`dig` 是否解析出 IP）；② 目标端口（`nc -zv host 443`）；③ `curl -v` 看 TLS/HTTP 细节。ping 走 ICMP 与 HTTP 不是一回事。
4. **`traceroute` 中连续 `* * *` 一定代表断网吗？** 不一定——该路由器可能禁 ICMP（TTL-exceeded 不回）。可改用 `traceroute -T`（TCP）探测，或结合 `nc`/`curl` 判断真正断点。
5. **`curl` 与 `wget` 怎么选？** 调接口/看响应头/测时间/发 POST 用 `curl`；下载大文件、断点续传（`-c`）、递归镜像站点用 `wget`。
6. **`dig` 和 `nslookup` 都查不到记录，但浏览器能打开，为什么？** 浏览器可能命中缓存、或走 HTTP/3（QUIC）直连 IP 绕过 DNS，或 `/etc/hosts` 已写死；用 `dig @8.8.8.8` 指定权威上游再验证。
7. **`nc -zv host 80` succeeded 代表什么？** 该主机 80 端口上有进程监听、TCP 三次握手成功——比 ping 更真实的"服务可达"证据。但只说明端口开，不代表应用层正常（还需 `curl` 验证 HTTP 响应）。
8. **排查"网站访问慢"的标准命令顺序？** `curl -w` 时间分解（看是哪段慢）→ `mtr` 看路径丢包 → `ss -tin` 看 rtt/cwnd → 必要时 `tcpdump` 抓包看重传；逐层排除、让数据说话。
9. **`ethtool -S`、`ip -s link`、`nstat` 各看哪一层？** `ethtool -S` 是驱动/硬件私有计数，`ip -s link` 是接口通用收发统计，`nstat` 是 IP/TCP 协议栈计数；要看计数增长趋势并互相印证。
10. **`tc` 的 qdisc/class/filter 分别负责什么？** qdisc 负责排队算法，class 划分层级和速率，filter 按包字段把流量导入 class；`rate` 是保证速率，`ceil` 是可借用上限。
11. **`tshark -f` 与 `-Y` 有什么区别？** `-f` 是抓取前执行的 BPF capture filter，开销低；`-Y` 是 Wireshark display filter，可按解析后的协议字段筛选。两套语法不能混用。
12. **为什么 `conntrack -F` 不是普通“清缓存”？** 它清空防火墙/NAT 的全部连接状态，已有 TCP 和地址转换会话可能立即失效；日常先用 `-L/-E/-S` 观察，只在有回滚和影响评估时精确 `-D`。
13. **`nmcli` 与 `networkctl` 应该同时配置同一接口吗？** 不应该。先确认接口由 NetworkManager 还是 systemd-networkd 管理，只使用对应控制面；上层还有 netplan/云初始化时应修改其源配置。
14. **iperf3 的 `-R` 和 UDP `-b` 分别验证什么？** `-R` 反转数据方向，用于发现上下行不对称；UDP `-b` 设置主动发送目标速率，通过 jitter/loss 找链路承载拐点，并不直接代表链路额定带宽。
