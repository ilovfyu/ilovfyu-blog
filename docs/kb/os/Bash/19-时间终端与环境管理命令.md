::: abstract 本章定位
本篇补齐一组日常高频却常被分散讲解的 Linux 命令：时间与时区、环境变量与命令解析、locale、终端设备、登录会话、Readline、历史记录和终端录制。目标不是背选项，而是能回答“时间为什么差 8 小时”“明明改了 PATH 为什么还执行旧程序”“SSH 后中文为什么乱码”“终端为什么不回显”这类问题。
:::
前置组合技巧见 [实用命令组合与技巧](/kb/os/Bash/10-实用命令组合与技巧/)，远程终端与持久会话见 [远程操作与文件同步](/kb/os/Bash/11-远程操作与文件同步/)，时间同步服务与定时任务见 [服务管理与定时任务](/kb/os/Bash/12-服务管理与定时任务/)，综合排障方法可迁移到 [案例](/kb/os/问题排查/12-疑难案例集锦/)。
## 1. 先建立两组心智模型
### 1.1 系统时钟、硬件时钟、时区不是一回事
```text
RTC/硬件时钟（主板芯片，断电仍走）
          │ 开机读取 / hwclock --hctosys
          ▼
系统时钟（内核维护的 UTC 时间线） ← chronyd/systemd-timesyncd 校准
          │ 加载时区规则
          ▼
本地民用时间（例如 Asia/Shanghai 的 2026-08-10 15:30:00 +0800）
```
- **系统时钟**是内核中的时间，进程通过 `clock_gettime` 等系统调用读取；Unix 时间戳按 UTC 时间线表达。
- **RTC**（Real-Time Clock）是主板硬件时钟。Linux 通常建议 RTC 保存 UTC，Windows 双系统有时把它当本地时间。
- **时区**只是把时间线转换成当地日期/时刻的一组规则，来自 IANA tzdata；改时区不会让 Unix 时间戳跳变。
- **NTP 客户端**估计本机相对时间源的偏差，并通过 step（跳变）或 slew（渐进调速）校正系统时钟。
### 1.2 终端、会话、Shell 也不是一回事
```text
键盘/SSH 客户端 ↔ tty/pty 终端设备 ↔ bash/zsh Shell ↔ 前台进程组
                                      │
                                      └─ 环境、Readline、history、启动文件
```
- **TTY** 原指物理电传终端；现代本地控制台常是 `/dev/tty1`，图形终端/SSH 常是伪终端 `/dev/pts/N`。
- **会话**由登录、systemd-logind、PAM 等共同管理；一名用户可以同时有多个会话和多个终端。
- **Shell**只是终端上运行的一个程序。换成 `bash` 不等于重新登录，打开新终端也不一定是 login shell。
- **Readline**是 Bash 等程序使用的行编辑库；`Ctrl+A`、反向搜索和 `~/.inputrc` 属于这一层。
## 2. `date`：查看、格式化与解析时间
### 2.1 常用格式化
```bash
$ date '+%F %T %z %Z'
2026-08-10 15:30:42 +0800 CST
$ date -u '+%FT%TZ'
2026-08-10T07:30:42Z
$ date '+epoch=%s nano=%N week=%G-W%V-%u'
epoch=1786347042 nano=123456789 week=2026-W33-1
```
解读：
- `%F` 等于 `%Y-%m-%d`，`%T` 等于 `%H:%M:%S`，`%s` 是 Unix 秒时间戳，`%N` 是纳秒字段。
- `%z` 是数值偏移，`%Z` 是缩写。日志应优先保存 `%z` 或 UTC；`CST` 可同时指中国、美国中部等，天然有歧义。
- ISO 周日期要组合 `%G-W%V-%u`；年初/年末的 ISO 周所属年份可能不同于普通 `%Y`。
- `-u` 只改变显示/解析所用时区，不修改系统时钟。
::: tip 机器可读时间
跨系统日志推荐 RFC 3339/ISO 8601，例如 `date --iso-8601=seconds` 或 `date '+%Y-%m-%dT%H:%M:%S%:z'`。文件名可用 `date -u '+%Y%m%dT%H%M%SZ'`，避开空格、冒号和本地夏令时歧义。
:::
### 2.2 GNU `date -d`：解析与相对时间
```bash
$ date -d '2026-08-10 15:30:00 +0800' '+%s'
1786347000
$ date -d 'yesterday' '+%F'
2026-08-09
$ date -d '2026-01-31 +1 month' '+%F'
2026-03-03
```
解读：
- `-d/--date=STRING` 让 GNU coreutils 解析文本而不修改时钟，`@秒数` 可把 epoch 转回日期。
- `yesterday`、`2 hours ago`、`next Monday` 很适合交互查询，但脚本应固定输入格式并检查退出码。
- “加一个月”按历法归一化，不等于加固定天数；1 月 31 日加一个月可能溢出到 3 月，账期逻辑不要想当然。
- 夏令时切换日可能存在“不存在的本地时刻”或“一小时出现两次”；跨时区计算优先用 UTC/epoch。
不同实现差异：
| 平台 | 解析写法 | 备注 |
|---|---|---|
| GNU/Linux coreutils | `date -d '2 days ago'` | 支持自然语言与 `@epoch` |
| BSD/macOS | `date -v-2d`、`date -r 1786347000` | 没有 GNU `-d` 语义 |
| BusyBox | 取决于编译版本 | 解析能力通常较少，先看 `date --help` |
### 2.3 临时指定时区与设置时间
```bash
$ TZ=UTC date '+%F %T %z %Z'
2026-08-10 07:30:00 +0000 UTC
$ TZ=America/New_York date '+%F %T %z %Z'
2026-08-10 03:30:00 -0400 EDT
```
解读：`TZ=... cmd` 只改变这一次进程的时区。`sudo date --set='2026-08-10 15:30:00'` 可直接设置系统时间，但会发生跳变；运行 NTP 服务时优先让同步服务校时。
## 3. systemd 时间管理：`timedatectl`
### 3.1 一次看全局状态
```bash
$ timedatectl
               Local time: Mon 2026-08-10 15:30:42 CST
                 RTC time: Mon 2026-08-10 07:30:41
                Time zone: Asia/Shanghai (CST, +0800)
System clock synchronized: yes
              NTP service: active
          RTC in local TZ: no
```
解读：
- `Local time` 是套用当前时区后的系统时间，`Universal time` 是同一瞬间的 UTC 表示。
- `System clock synchronized: yes` 表示内核同步状态；`NTP service: active` 只表示 systemd 识别到某个同步服务已启用，两者不能互相替代。
- `RTC in local TZ: no` 表示 RTC 按 UTC 保存，是 Linux 推荐值。
- 脚本可用 `timedatectl show -p Timezone -p NTPSynchronized --value` 获取稳定字段，不要解析给人看的对齐表。
### 3.2 改时区、NTP 和 RTC 模式
```bash
timedatectl list-timezones | grep '^Asia/' | less
sudo timedatectl set-timezone Asia/Shanghai
sudo timedatectl set-ntp true
sudo timedatectl set-local-rtc 0
```
典型成功输出：无输出，再运行 `timedatectl` 验证。
发行版差异：
- `timedatectl` 属于 systemd；Alpine、精简容器、WSL 某些环境或非 systemd 系统可能没有，容器通常继承宿主机时钟且无权修改。
- `set-ntp true` 启动哪个服务取决于 systemd 与发行版集成，可能是 `systemd-timesyncd`，也可能由 `chronyd` 提供同步能力；用 `systemctl status chronyd systemd-timesyncd` 核实。
- Debian/Ubuntu 常见服务名 `chrony.service`，RHEL/Fedora 常见 `chronyd.service`；命令行客户端都叫 `chronyc`。
## 4. RTC、NTP 与时钟漂移
### 4.1 `hwclock`：读写硬件时钟
```bash
$ sudo hwclock --show
2026-08-10 07:30:41.842913+00:00
$ sudo hwclock --systohc --utc
$ sudo hwclock --hctosys
```
解读：
- `--show` 读取 RTC；`--systohc` 把系统时钟写入硬件时钟；`--hctosys` 反向把 RTC 写入系统时钟。
- `--utc` 声明 RTC 使用 UTC；传统配置可能记录在 `/etc/adjtime` 第三行 `UTC` 或 `LOCAL`。
- 正常 systemd 启动流程会处理 RTC，日常不要反复手工双向覆盖。方向弄反会把正确时钟写成错误值。
- 虚拟机可能没有可访问 RTC，容器中常见 `hwclock: Cannot access the Hardware Clock`，这不是容器内可修的问题。
### 4.2 `chronyc tracking`：当前同步质量
```bash
$ chronyc tracking
Reference ID    : C0A80101 (192.168.1.1)
Stratum         : 3
System time     : 0.000123456 seconds slow of NTP time
Last offset     : -0.000041234 seconds
Frequency       : 8.421 ppm fast
Leap status     : Normal
```
解读：
- `System time`/`Last offset` 看当前偏差，`RMS offset` 看一段时间的综合误差。
- `Frequency 8.421 ppm fast` 表示未校正时本机振荡器倾向每天快约 `8.421 × 86.4 ≈ 728 ms`；chronyd 会调频补偿。
- `Stratum` 是到参考时钟的层级，不是“精度等级”；层级低不保证网络路径更稳定。
- `Leap status: Not synchronised`、参考 ID 为 0 或参考时间很旧，说明尚未选中可用时间源。
### 4.3 `chronyc sources`：看每个时间源
```bash
$ chronyc sources -v
MS Name/IP address         Stratum Poll Reach LastRx Last sample
===============================================================================
^* ntp1.example.net              2   6   377    18   -42us[ -55us] +/-  12ms
^+ ntp2.example.net              2   6   377    20   +31us[ +31us] +/-  15ms
```
解读：
- `^` 表示服务器，`*` 是当前选中的同步源，`+` 是可参与合并的候选，`-` 是被算法排除的源，`?` 通常表示不可达或样本不足。
- `Reach` 是八进制可达寄存器，`377` 表示最近 8 次请求均成功；持续 `0` 优先查 DNS、UDP/123、防火墙和服务器 ACL。
- `LastRx` 是距上次收到样本的秒数；最后一列同时给偏差和估计误差范围。
### 4.4 `chronyc makestep`：何时允许跳变
```bash
$ sudo chronyc makestep
200 OK
$ chronyc waitsync 30 0.01
```
解读：`makestep` 请求 chronyd 立刻 step 系统时间，适合刚启动且偏差很大的机器；生产业务运行中回拨可能破坏超时、日志顺序和分布式租约，应先评估。配置 `makestep 1.0 3` 表示启动后的前三次更新中，偏差超过 1 秒可跳变，其余时候渐进校正。`waitsync 30 0.01` 最多检查 30 次，等待剩余校正小于约 10 ms。
### 4.5 `ntpq`：传统 ntpd 的历史接口
```bash
$ ntpq -pn
     remote           refid      st t when poll reach   delay   offset  jitter
==============================================================================
*192.0.2.10      203.0.113.8      2 u   31   64  377    0.812   -0.143   0.091
+192.0.2.11      203.0.113.9      2 u   28   64  377    1.201    0.088   0.120
```
解读：`*` 是系统 peer，`+` 是候选；`-n` 禁止反向 DNS，排障更快。`ntpq` 面向经典 ntpd/NTPsec，不是 chrony 的通用客户端；现代 RHEL/Fedora 默认 chrony，Ubuntu 新版本也常部署 chrony 或 systemd-timesyncd。看到旧教程的 `ntpq -p`，先确认实际守护进程，再选 `chronyc`、`timedatectl timesync-status` 或 `ntpq`。
### 4.6 时钟漂移排查清单
```bash
date -u '+%FT%T.%N%:z'
timedatectl
chronyc tracking
chronyc sources -v
systemctl status chronyd systemd-timesyncd --no-pager
journalctl -u chronyd -u systemd-timesyncd --since '-30 min'
```
按顺序收敛：
1. 先分清是**显示时区错**还是 Unix 时间线真错：比较 `date +%s` 与可信主机，而不是只看墙上时钟。
2. 查同步服务是否运行且选中 source；“服务 active”不代表已同步。
3. `Reach=0` 查 DNS、路由、UDP/123 和上游 ACL；虚拟机还要查宿主机时间同步是否与 guest NTP 互相拉扯。
4. 偏差反复累积，查看 `Frequency`、虚拟机 steal/暂停恢复、CPU TSC/内核日志；睡眠或快照恢复可造成瞬时大偏差。
5. 比较 RTC 只在开机后立刻错、重启后复发时特别有价值；运行期漂移主要看系统时钟与 NTP。
6. 不要同时运行多个会主动校时的守护进程。保留一个权威客户端，停用重复服务。
## 5. 时区数据库：`zdump`、`tzselect` 与 `/etc/localtime`
### 5.1 `/etc/localtime` 和 `/etc/timezone`
```bash
$ readlink -f /etc/localtime
/usr/share/zoneinfo/Asia/Shanghai
$ cat /etc/timezone
Asia/Shanghai
```
解读：`/etc/localtime` 是程序默认读取的二进制 tzfile，常是到 `/usr/share/zoneinfo/...` 的软链接，也可能是复制文件。`/etc/timezone` 是 Debian/Ubuntu 常见文本配置，并非所有发行版都有。不要用文本编辑器改 `/etc/localtime`；用 `timedatectl set-timezone`，或在非 systemd 系统正确建立软链接。
### 5.2 `zdump`：验证夏令时转换
```bash
$ zdump -v America/New_York | grep '2026'
America/New_York  Sun Mar  8 07:00:00 2026 UT = Sun Mar  8 03:00:00 2026 EDT isdst=1 gmtoff=-14400
America/New_York  Sun Nov  1 06:00:00 2026 UT = Sun Nov  1 01:00:00 2026 EST isdst=0 gmtoff=-18000
```
解读：3 月从 `01:59:59` 跳到 `03:00:00`，所以当地 `02:30` 不存在；11 月 `01:00–01:59` 重复一次。glibc 新版常支持 `zdump -V -c 2026,2027 zone` 限定年份；不同 tzcode 版本选项有差异，先看 `zdump --help`。
### 5.3 `tzselect` 只负责“选择”
```bash
$ tzselect
Please identify a location so that time zone rules can be set correctly.
```
最终输出示例：`Asia/Shanghai`。
`tzselect` 是交互式问答，通常只把推荐的 `TZ` 值打印出来，**不会自动修改系统时区**。用户级临时使用可 `export TZ=Asia/Shanghai`；系统级仍用 `timedatectl set-timezone Asia/Shanghai`。
## 6. 环境变量与 Shell 变量
### 6.1 `env`、`printenv` 与临时变量
```bash
$ printenv HOME SHELL
/home/zhang
$ env | sort | head
HOME=/home/zhang
LANG=zh_CN.UTF-8
$ APP_ENV=test DEBUG=1 env | grep -E '^(APP_ENV|DEBUG)='
APP_ENV=test
DEBUG=1
$ VAR=x sh -c 'printf "%s\n" "$VAR"'
x
```
解读：
- `printenv NAME` 精确查看导出的环境变量；`env` 无参数列出环境，也能以 `NAME=VALUE` 前缀运行命令。
- `VAR=x cmd` 只把变量加入这一次命令及其子进程环境，不污染当前 Shell。
- 在 Bash 中，前缀赋值给外部命令和函数时细节不同；可移植脚本把它理解为“命令的临时环境”，不要依赖函数的边缘行为。
### 6.2 Shell 变量何时变成环境变量
```bash
$ project=blog
$ bash -c 'echo "$project"'
$ export project
$ bash -c 'echo "$project"'
blog
$ export API_URL=https://api.example.com
$ unset API_URL
```
解读：普通 Shell 变量只存在当前 Shell；`export` 给变量打上导出属性，之后创建的子进程会收到副本。子进程不能反向修改父 Shell 的环境，所以执行脚本 `./setenv.sh` 无法永久改当前环境，必须 `source setenv.sh`，同时承担执行其中任意命令的风险。
### 6.3 `set`、`declare`、`readonly`、`unset`
```bash
$ declare -p project
declare -x project="blog"
$ declare -ir RETRIES=3
$ readonly RELEASE=2026.08
$ RETRIES=4
bash: RETRIES: readonly variable
$ unset project
```
解读：
- `set` 无参数输出 Shell 变量、环境变量和函数，内容多且可能含秘密；`set -o` 查看 Shell 选项，含义不要与“列环境”混为一谈。
- `declare -p name` 可复现变量的值与属性；`-x` 导出、`-i` 整数、`-r` 只读、`-a/-A` 索引/关联数组。这些是 Bash 内建，并非 POSIX `sh` 通用语法。
- `readonly` 后当前 Shell 中不能重赋或 `unset`；退出该 Shell 才消失。它保护的是变量绑定，不是一个安全边界。
- `unset NAME` 删除变量；`unset -f func` 删除函数。对输入可控的名称，应避免让它被解释为任意函数/变量名。
### 6.4 `env -i`：从近乎空白的环境启动
```bash
$ env -i PATH=/usr/bin:/bin HOME="$HOME" LANG=C /usr/bin/bash --noprofile --norc
bash-5.2$ env
HOME=/home/zhang
LANG=C
PATH=/usr/bin:/bin
```
解读：`-i` 忽略继承环境，但新程序仍可自行添加 `PWD`、`SHLVL`、`_` 等变量，因此不是数学意义的空集合。它适合复现“是否被本机 dotfile/代理变量污染”；不是沙箱，不能提供文件、网络或权限隔离。
::: warning 环境可能泄密
API token 放进环境后，子进程会继承；同用户通常可通过 `/proc/&lt;pid&gt;/environ` 或调试接口读取。`env`、`set`、终端录制和故障工单都可能把秘密抄走。长期凭据应交给权限受控的 secret 文件、凭据代理或服务管理器的凭据机制。
:::
## 7. `PATH` 与命令解析
### 7.1 Bash 大致按什么顺序找命令
对简单命令名，Bash 会处理关键字/语法，随后查函数、内建命令、哈希缓存与 `PATH` 中的可执行文件；alias 更早在解析阶段展开。精确类别不要靠记忆，直接问 Shell：
```bash
$ type -a printf
printf is a shell builtin
printf is /usr/bin/printf
$ type -a python
python is /usr/local/bin/python
$ command -V cd
cd is a shell builtin
```
解读：
- `type -a` 是 Bash 中最可靠的交互诊断，能同时列 alias、函数、内建和多个外部路径。
- `command name` 绕过同名函数（通常也避开 alias，因为 alias 在解析前展开；脚本中 alias 默认不展开），但仍可调用 Shell builtin。
- `builtin printf` 强制调用 Bash 内建；绝对路径 `/usr/bin/printf` 强制调用指定外部文件。
- `which` 通常是外部程序，只按当前 `PATH` 找文件，不可靠地理解 alias、函数和 builtin；适合粗看，不应作为 Shell 解析真相。
### 7.2 正确构造 `PATH`
```bash
export PATH="$HOME/.local/bin:$PATH"
printf '%s\n' "${PATH//:/$'\n'}"
command -v python3
```
典型输出：`/home/zhang/.local/bin/python3`。
解读：`PATH` 从左到右搜索，用户目录放前面会覆盖系统同名命令。空字段（开头/结尾的冒号或 `::`）在常见 Shell 中表示当前目录，存在命令劫持风险；root 的 `PATH` 尤其不要含 `.`。追加目录前可用 `case ":$PATH:" in *":$dir:"*) ;; *) PATH="$dir:$PATH";; esac` 防重复。
### 7.3 `hash` 缓存为何让新 PATH“不生效”
```bash
$ hash
hits    command
   3    /usr/bin/python3
$ hash -t python3
/usr/bin/python3
$ hash -r
$ command -v python3
/opt/python/bin/python3
```
解读：Bash 会缓存执行过的外部命令路径，减少反复扫描目录。安装了新版本或移动文件后若仍命中旧路径，执行 `hash -r` 清空全部缓存；`hash -d python3` 只删一项。Bash 在 `PATH` 赋新值时通常清缓存，但排障时显式 `hash -r` 最直观。zsh 对应常见命令是 `rehash`。
## 8. locale：语言、编码与文本规则
### 8.1 `locale` 看当前规则
```bash
$ locale
LANG=zh_CN.UTF-8
LC_CTYPE="zh_CN.UTF-8"
LC_TIME="zh_CN.UTF-8"
LC_COLLATE="zh_CN.UTF-8"
LC_ALL=
$ locale charmap
UTF-8
$ locale -a | grep -i 'zh_cn\|c\.utf'
C.utf8
zh_CN.utf8
```
解读：
- `LANG` 是默认值，各 `LC_*` 可按类别覆盖；非空 `LC_ALL` 优先级最高，临时覆盖所有类别。
- `LC_CTYPE` 决定字符分类、大小写与多字节编码解释；`LC_COLLATE` 决定排序和范围表达式；`LC_TIME` 影响日期名称；`LC_NUMERIC` 影响小数点格式。
- `locale -a` 列出的名字才是本机已生成 locale；`zh_CN.UTF-8` 与列出的 `zh_CN.utf8` 通常可等价解析，但脚本应在目标环境验证。
- `C.UTF-8` 提供 UTF-8 编码和较可预测的 C 风格行为，但可用性依发行版/libc；极简 musl/旧系统先查 `locale -a`。
### 8.2 临时覆盖与优先级
```bash
$ LANG=zh_CN.UTF-8 LC_TIME=C date '+%A %B'
Monday August
$ LC_ALL=C sort names.txt
$ printf '中' | LC_CTYPE=C wc -m
3
$ printf '中' | LC_CTYPE=C.UTF-8 wc -m
1
```
解读：同一个 UTF-8 汉字是 3 个字节；在 UTF-8 locale 中 `wc -m` 按字符计为 1，在 `C` locale 中每个字节被当成一个字符。`LC_ALL=C` 常用于让脚本获得稳定英文诊断、字节序排序和更高性能，但会改变 Unicode 字符类行为，不能无脑全局设置。
优先级可记为：`LC_ALL` > 对应 `LC_*` > `LANG` > 程序默认。`LANGUAGE` 是 GNU gettext 常见的消息语言偏好，不取代字符编码规则，也不是 POSIX locale 类别。
### 8.3 locale 如何影响排序、正则和编码
```bash
$ printf 'Z\na\nä\n' | LC_ALL=C sort
Z
a
ä
$ printf 'Z\na\nä\n' | LC_ALL=de_DE.UTF-8 sort
a
ä
Z
```
解读：自然语言 locale 可能按语言规则把 `ä` 与 `a` 放在一起；`C` 按字节值排序。依赖稳定顺序的构建、校验和、`comm`/`join` 前置排序，应统一 `LC_ALL=C`。
```bash
$ printf 'é\n' | LC_ALL=C grep -E '^[[:alpha:]]+$'
$ printf 'é\n' | LC_ALL=en_US.UTF-8 grep -E '^[[:alpha:]]+$'
é
```
解读：字符类 `[[:alpha:]]` 由 `LC_CTYPE` 定义；范围 `[a-z]` 还可能受 `LC_COLLATE` 影响。二进制/协议解析固定 `LC_ALL=C`，面向人的 Unicode 文本则明确使用 UTF-8 locale。乱码还可能来自文件本身不是 UTF-8，可用 `file -bi file`、`iconv -f GB18030 -t UTF-8` 验证转换，切勿只靠改 `LANG` 猜编码。
### 8.4 `localectl`、`locale-gen` 与发行版差异
```bash
$ localectl status
   System Locale: LANG=zh_CN.UTF-8
       VC Keymap: us
      X11 Layout: us
$ sudo localectl set-locale LANG=zh_CN.UTF-8
```
Debian/Ubuntu：
```bash
sudo sed -i 's/^# *zh_CN.UTF-8 UTF-8/zh_CN.UTF-8 UTF-8/' /etc/locale.gen
sudo locale-gen
sudo update-locale LANG=zh_CN.UTF-8
```
RHEL/Fedora：
```bash
sudo dnf install glibc-langpack-zh
sudo localectl set-locale LANG=zh_CN.UTF-8
```
解读：`locale-gen` 是 Debian 系常见封装，不是所有发行版通用；RHEL/Fedora 使用 glibc langpack。`localectl` 需要 systemd，系统配置通常落到 `/etc/locale.conf`；当前 Shell 不会因配置文件改变而自动刷新，应重新登录或显式导出。不要为了修一个 SSH 会话就全局设置 `LC_ALL`，先确定服务端是否安装对应 locale。
## 9. 终端身份、用户与消息
### 9.1 我是谁、在哪个终端、谁在线
```bash
$ whoami
zhang
$ tty
/dev/pts/3
$ who
zhang    pts/3        2026-08-10 14:01 (192.0.2.8)
ops      pts/5        2026-08-10 14:22 (192.0.2.9)
$ users
ops zhang
```
解读：`whoami` 输出当前**有效 UID**对应用户名，等价于 `id -un`；它不保证是最初登录者，`sudo` 后会变。`tty` 打印标准输入连接的终端，无控制终端或被管道调用时可能输出 `not a tty` 并返回非零。`who`/`users` 读取 utmp 会话记录，容器或精简系统中记录可能不完整。
```bash
$ w
USER  TTY   FROM       LOGIN@ IDLE   JCPU   PCPU WHAT
zhang pts/3 192.0.2.8  14:01  0.00s  0.12s  0.01s w
ops   pts/5 192.0.2.9  14:22  8:10   1.22s  0.30s vim deploy.conf
```
`w` 把 uptime/load、登录来源、空闲时间和前台命令合在一起。`WHAT` 是会话当前前台活动，不等于该用户所有进程；排查会话异常再配合 `ps -ft pts/5`。
### 9.2 `mesg`、`write`、`wall`
```bash
$ mesg
is y
$ mesg n
$ write ops pts/5
Deploy starts at 16:00. Please save your work.
Ctrl+D
```
解读：`mesg y/n` 控制其他普通用户是否可向本终端写消息；root 往往仍可发送。`write user [tty]` 点对点发送，用户多会话时明确指定 `pts/N`。`wall` 向所有允许接收的终端广播，通常受权限与 PAM/systemd 策略限制：
```bash
printf 'Host reboot in 10 minutes\n' | sudo wall
```
不要用 `write/wall` 传密码、token 或隐私内容；消息出现在屏幕、录屏和终端日志中。
## 10. `stty`、`reset` 与基础显示控制
### 10.1 `stty -a` 看终端行规程
```bash
$ stty -a
speed 38400 baud; rows 40; columns 120; line = 0;
intr = ^C; quit = ^\; erase = ^?; kill = ^U; eof = ^D;
isig icanon iexten echo echoe echok -echonl ...
```
解读：`icanon` 表示规范模式，内核按行交付输入；`isig` 让 `Ctrl+C`/`Ctrl+\` 生成信号；`echo` 控制键入字符是否回显；`intr/erase/eof` 显示控制字符绑定。伪终端显示的 baud 多半只是兼容字段，不代表 SSH 网速。
### 10.2 终端不回显的恢复
```bash
stty -echo        # 演示：输入仍有效，但屏幕不显示
stty echo         # 恢复回显
stty sane         # 恢复一组合理的行规程默认值
reset             # 重新初始化终端，通常也会清屏
```
典型现象：执行 `stty -echo` 后键入命令看不见，盲打 `stty echo` 再回车即可。`stty sane` 修复 echo、信号键、换行等多数设置；`reset` 还会按 terminfo 重置终端显示状态。远程程序崩溃留下 raw mode 时，先按 `Ctrl+J` 后盲打 `stty sane`，因为 Enter 的回车映射也可能坏了。
::: important 脚本必须清理终端状态
临时关闭回显读取密码时应使用 `read -s`，或用 `trap 'stty echo' EXIT INT TERM` 确保异常退出也恢复。终端状态属于共享设备状态，脚本崩溃不会自动替你复原。
:::
### 10.3 `clear`、`tput` 与 `tabs`
```bash
$ tput cols; tput lines; tput colors
256
$ tput bold; printf 'warning'; tput sgr0; printf '\n'
$ clear
$ tabs -4
```
解读：
- `clear` 通常发出清屏控制序列，滚动缓冲是否清除取决于终端与选项；它不等于删除 Shell history。
- `tput` 从 terminfo 查询当前 `$TERM` 对应能力，比手写 escape code 更可移植；输出不是普通文本，重定向到文件会保存控制字节。
- `tput colors` 返回 terminfo 声称支持的颜色数，但终端模拟器真实能力和 multiplexer/SSH 传递可能不同。
- `tabs -4` 设置每 4 列一个硬件/终端制表位，不会把文件中的 Tab 转成空格；恢复常见 8 列可用 `tabs -8`。不同 util-linux/BSD 实现选项略有差异。
## 11. 终端显示、颜色与 terminfo
### 11.1 ANSI escape 的最小认识
```bash
printf '\033[31mred\033[0m normal\n'
printf '\033[2J\033[H'   # 清屏并把光标移到左上角
```
典型显示：`red` 为红色；日志出现 `^[` 或 `\x1b[31m` 就是记录了控制序列。`\033[` 表示 `ESC [`（CSI），`31m` 设置前景色，`0m` 重置；程序着色前应检查 `[ -t 1 ]`。
### 11.2 `TERM`、`COLORTERM` 与 `NO_COLOR`
```bash
$ printf 'TERM=%s COLORTERM=%s\n' "$TERM" "$COLORTERM"
TERM=xterm-256color COLORTERM=truecolor
$ tput colors
256
$ NO_COLOR=1 ls --color=auto
```
解读：
- `TERM` 是 terminfo 能力名称，不是终端软件品牌，也不要随意写成能力过高的值。远端缺对应 terminfo 时会报 `unknown terminal`。
- `COLORTERM=truecolor` 是终端生态常用提示，表示可能支持 24 位色，但不是统一标准；应用仍需降级策略。
- `NO_COLOR` 是社区约定：变量存在且非空时应用应禁用非必要颜色，但是否支持取决于具体程序；GNU `ls` 不承诺读取它，必要时显式 `--color=never`。
- `TERM=dumb` 表示功能极少，CI/管道程序应退化为无光标控制的纯文本。
### 11.3 `infocmp` 与 `tic`
```bash
$ infocmp xterm-256color | head
#       Reconstructed via infocmp from file: /usr/share/terminfo/78/xterm-256color
xterm-256color|xterm with 256 colors,
$ infocmp -x tmux-256color xterm-256color
comparing tmux-256color to xterm-256color.
```
解读：`infocmp` 把编译后的 terminfo 条目反编译成人可读能力，并能比较两个条目。远端缺自定义条目时，可在可信环境导出源码再编译到用户目录：
```bash
infocmp -x tmux-256color > /tmp/tmux-256color.info
tic -x -o ~/.terminfo /tmp/tmux-256color.info
```
`tic` 是 terminfo compiler。不要从不可信来源安装条目；优先安装发行版的 ncurses/terminfo 包。SSH/tmux 颜色问题应让内外层 `TERM` 与实际能力匹配，不能只靠强行 `export TERM=xterm-256color`。
## 12. 终端录制：`script`、`scriptreplay`、`scriptlive`
### 12.1 录输出与时间信息
```bash
$ script --log-out session.log --log-timing session.time
$ uname -a
Linux web01 6.8.0 ... x86_64 GNU/Linux
$ exit
Script done.
$ scriptreplay --timing session.time --typescript session.log
```
解读：`script` 分配伪终端并启动子 Shell，把终端输出记录到 typescript；timing 文件保存播放节奏，`scriptreplay` 可按原速度重放。util-linux 新版本推荐长选项；老版本常见 `script -t 2>session.time session.log` 与 `scriptreplay session.time session.log`，具体语法以 `script --version`、`man script` 为准。
### 12.2 分离输入/输出与多流格式
```bash
script --log-in input.log --log-out output.log \
       --log-timing timing.log --logging-format advanced
```
新 util-linux 支持单独记录输入、输出和 advanced 多流 timing；较旧版本没有 `--log-in`、`--logging-format` 或长选项。**记录输入极其危险**：即使程序关闭回显，密码仍可能被 input log 原样捕获。只为审计操作时通常录输出即可，并在受控目录设置 `umask 077`。
### 12.3 `scriptlive`：实时回放输入
```bash
scriptlive --log-in input.log --log-timing timing.log
```
`scriptlive` 可按 timing 把已记录输入重新喂给当前终端，主要用于复现实验，不是普通“看录像”。它只存在于较新的 util-linux 发行版本/构建中，选项随版本演进；执行记录中的输入等价于重新执行命令，必须在隔离测试环境检查日志后使用，绝不能对生产 Shell 或不可信录制直接运行。
### 12.4 审计与隐私边界
- 终端录制会捕获屏幕上的 token、配置、客户数据、命令输出和退格前内容，文件权限至少设为 `600`。
- `script` 是用户态会话记录，不是不可抵赖审计：用户可修改日志，未必覆盖无 TTY 命令、GUI、其他会话或内核操作。
- 合规审计应结合 `auditd`、sudo I/O logging、集中日志与访问控制；sudo 可通过 `log_input`/`log_output` 记录 I/O，但必须评估密码与隐私数据处理策略。
- 分享录像前要脱敏；`sed` 删除可见字符串未必清掉 input log、timing 多流或 ANSI 隐藏内容。
## 13. 登录、提权与会话历史
### 13.1 `login`、`su`、`sudo -i/-s`
```bash
$ su app
$ su - app
$ sudo -s
# echo "$HOME $SHELL"
/root /bin/bash
$ sudo -i
# pwd
/root
```
解读：
- `login` 通常由控制台/getty 调用以认证并建立新登录会话，普通终端里很少手工使用；认证和环境还受 PAM、login.defs、systemd-logind 影响。
- `su app` 切 UID 但保留较多当前环境与目录；`su - app`/`su --login app` 模拟完整登录，重设 HOME、SHELL、PATH 并进入目标家目录。PAM 与发行版可改变保留细节。
- `sudo -s` 以目标用户运行其 Shell，环境主要按 sudoers 策略过滤，通常保留当前目录；`sudo -i` 模拟目标用户 login shell，HOME/目录/启动文件更接近目标用户登录。
- `sudo su -` 多套一层且审计语义较差，直接 `sudo -i` 更清楚。检查“原始登录者”可参考 `$SUDO_USER`、`loginctl`，但链式跳转后不能只信一个变量。
### 13.2 `last`、`lastb`、`lastlog`
```bash
$ last -F | head
zhang pts/3 192.0.2.8 Mon Aug 10 14:01:03 2026 still logged in
$ sudo lastb | head
admin ssh:notty 198.51.100.9 Mon Aug 10 03:14 - 03:14 (00:00)
$ lastlog -u zhang
Username Port From Latest
zhang pts/3 192.0.2.8 Mon Aug 10 14:01:03 +0800 2026
```
解读：`last` 读 `/var/log/wtmp`，包含登录、注销和重启；`lastb` 读 `/var/log/btmp` 的失败登录，通常需 root；`lastlog` 读每用户最后登录数据库。文件可能被 logrotate、截断或未启用，容器中也常缺失，所以“无记录”不等于“从未发生”。util-linux 新版本逐步提供 `lastlog2`，但部署尚不统一。
### 13.3 `loginctl`：systemd-logind 的会话视角
```bash
$ loginctl list-sessions
SESSION UID  USER  SEAT TTY   STATE  IDLE SINCE
      7 1000 zhang -    pts/3 active no   -
$ loginctl show-session 7 -p Name -p Remote -p RemoteHost -p Type -p State
Remote=yes
RemoteHost=192.0.2.8
State=active
```
解读：`loginctl` 查询 logind 的 session/seat/user 状态，适合确认远程来源、会话类型与 linger。`loginctl terminate-session 7` 会结束整个会话及其进程，应先核对；非 systemd 系统不可用。tmux 内的进程归属、user manager 与 SSH 生命周期还受 linger 和 cgroup 策略影响，持久任务见 [远程操作与文件同步](/kb/os/Bash/11-远程操作与文件同步/)。
### 13.4 `chsh` 与 `/etc/passwd` 中的登录 Shell
```bash
$ getent passwd zhang
zhang:x:1000:1000:Zhang:/home/zhang:/bin/bash
$ chsh -s /bin/zsh
Shell changed.
$ cat /etc/shells
/bin/bash
/bin/zsh
```
解读：`getent passwd` 经过 NSS 查询本地文件、LDAP/SSSD 等统一用户源，比直接 grep `/etc/passwd` 完整。末字段是登录 Shell；`chsh` 通常只允许选择 `/etc/shells` 中的程序，目录用户可能需管理员在身份源修改。改完只影响**之后的新登录**，当前 Shell 不会变。`/usr/sbin/nologin` 常表示禁止交互登录。
## 14. Bash 启动文件顺序
### 14.1 三个维度先判清
```bash
$ shopt -q login_shell; echo "login=$?"
login=0
$ case $- in *i*) echo interactive;; *) echo non-interactive;; esac
interactive
```
`shopt` 返回 0 表示 login shell；`$-` 含 `i` 表示 interactive；进程名以 `-bash` 开头通常也是 login shell 标志。SSH 登录通常得到 interactive login shell，图形终端常启动 interactive non-login shell，但终端配置可以改变它。
### 14.2 Bash 原生读取顺序
| 类型 | Bash 读取顺序 |
|---|---|
| interactive login | `/etc/profile`，再从 `~/.bash_profile`、`~/.bash_login`、`~/.profile` 中只读**第一个存在的** |
| interactive non-login | `~/.bashrc` |
| non-interactive Bash | 若设置 `BASH_ENV`，展开后读取该文件 |
| login shell 退出 | `~/.bash_logout`；系统文件是否读取取决于发行版补丁/配置 |
推荐让 `~/.bash_profile` 主动加载 `~/.bashrc`：
```bash
if [ -f ~/.bashrc ]; then
    . ~/.bashrc
fi
```
解读：Bash 原生不会在 interactive non-login 时自动读 `/etc/bashrc`；Debian 的 `/etc/bash.bashrc`、RHEL 的 `/etc/bashrc` 通常由发行版配置或用户文件显式 source。远程 `ssh host cmd`、SFTP、cron、systemd service 都可能是 non-interactive，不能假设会读 `~/.bashrc`。Bash 以 `sh` 名称启动、POSIX mode、远程 shell daemon 检测还有特殊规则，精确行为查 `man bash` 的 `INVOCATION`。
::: warning 不要在启动文件里无条件输出
`.bashrc` 中的 `echo`、`stty`、`tput` 或交互命令可能破坏 `scp`/`rsync`/远程协议。交互专用内容前先用 `case $- in *i*) ;; *) return;; esac`；服务和 cron 应显式配置 PATH、LANG 和工作目录。
:::
## 15. Readline 与 Bash history
### 15.1 高频 Ctrl 快捷键（默认 Emacs 模式）
| 快捷键 | 作用 | 备注 |
|---|---|---|
| `Ctrl+A` / `Ctrl+E` | 行首 / 行尾 | 对应 beginning/end-of-line |
| `Ctrl+U` | 删除光标前到行首 | 内容进入 kill ring |
| `Ctrl+K` | 删除光标后到行尾 | 可用 Ctrl+Y 粘回 |
| `Ctrl+W` | 删除前一个单词 | 终端常映射 unix-word-rubout |
| `Ctrl+Y` | yank 最近删除内容 | 类似粘贴 |
| `Ctrl+R` | 反向增量搜索历史 | 再按 Ctrl+R 找更早匹配 |
| `Ctrl+L` | 清屏并重绘当前行 | 类似 `clear`，但保留输入 |
| `Ctrl+D` | 空行发送 EOF / 有字时删字符 | 空 Shell 中常导致退出 |
| `Ctrl+C` | 向前台进程组发 SIGINT | 会取消当前输入行 |
| `Ctrl+Z` | 向前台进程组发 SIGTSTP | 作业控制见 [进程与作业控制](/kb/os/Bash/03-进程与作业控制/) |
终端驱动先处理部分控制键，Readline 处理其余编辑键，所以 `stty -a` 与 `bind -P` 要结合看。macOS 终端里的 Option 是否作为 Meta/Alt 发送还取决于模拟器设置。
### 15.2 `bind -P`、`bind -x` 与 `~/.inputrc`
```bash
$ bind -P | grep 'reverse-search-history'
reverse-search-history can be found on "\C-r".
$ bind '"\C-p": previous-history'
$ bind -x '"\C-x\C-l": printf "\n%s\n" "$PWD"'
$ bind -f ~/.inputrc
```
解读：`bind -P` 列 Readline 函数及按键，`bind -x` 把按键绑定到 Shell 命令（Bash 特性），后者能执行任意命令，加载不可信 dotfile 风险等同执行脚本。常用 `~/.inputrc`：
```text
set editing-mode emacs
set completion-ignore-case on
"\e[A": history-search-backward
"\e[B": history-search-forward
$if Bash
"\C-l": clear-screen
$endif
```
`inputrc` 语法由 Readline 解释，适用于所有使用 Readline 的程序；Bash 专用行为放 `$if Bash`。修改后新 Shell 生效，当前会话用 `bind -f ~/.inputrc` 重载。
### 15.3 history 容量、去重与多终端同步
```bash
shopt -s histappend cmdhist
HISTSIZE=10000
HISTFILESIZE=20000
HISTCONTROL=ignoreboth:erasedups
HISTIGNORE='ls:pwd:history*'
history -a     # 当前会话新记录追加到 HISTFILE
history -n     # 读取其他会话新增、尚未读入的行
history -w     # 用当前内存历史覆盖 HISTFILE，谨慎使用
```
`HISTSIZE` 是内存条数，`HISTFILESIZE` 是文件条数；`histappend` 让退出时追加而非覆盖。`ignoreboth` 等于 `ignorespace:ignoredups`，但“前置空格不记历史”不是安全机制，命令仍可能出现在审计、进程参数或终端录制中。
多终端近实时同步可在 `~/.bashrc` 中追加，而不是覆盖已有 `PROMPT_COMMAND`：
```bash
case ";${PROMPT_COMMAND:-};" in
  *';history -a; history -n;'*) ;;
  *) PROMPT_COMMAND="history -a; history -n${PROMPT_COMMAND:+; $PROMPT_COMMAND}" ;;
esac
```
每次提示符前先追加本会话，再读取其他会话增量。局限是并发顺序不完全等于真实执行顺序、同一命令可能重复，且旧 Bash 的 `PROMPT_COMMAND` 是字符串，新 Bash 也支持数组形式；已有复杂 hook 时应按其既有方式集成。历史更适合个人召回，不是合规审计日志。
## 16. 完整案例一：时间错乱与 TLS 失败
**现象**：新恢复的虚拟机访问 HTTPS 报证书尚未生效，应用日志比日志平台晚 8 小时，重启后时间再次错。
```bash
$ date '+%F %T %z'; date +%s
2026-08-10 23:40:00 +0800
1786376400
$ timedatectl
Local time: Mon 2026-08-10 23:40:00 CST
Universal time: Mon 2026-08-10 15:40:00 UTC
RTC time: Mon 2026-08-10 23:39:59
Time zone: Asia/Shanghai (CST, +0800)
System clock synchronized: no
RTC in local TZ: no
$ chronyc sources -v
^? ntp.example.net  2  6  0  -  +0ns[+0ns] +/- 0ns
```
**判断**：时区是正确的；RTC 声称按 UTC 保存，却实际写入了本地 `23:39`，因此开机读取后多 8 小时。`Reach=0` 又让 NTP 无法纠正。日志平台若按 UTC 解释无偏移时间，会再制造“晚 8 小时”的表象。
```bash
# 1. 修通 DNS/UDP 123 后确认 source 可达
$ chronyc sources -v
^* ntp.example.net  2  6  377  12  -210ms[-211ms] +/- 15ms
# 2. 在维护窗口立即校正
$ sudo chronyc makestep
200 OK
# 3. 把已同步系统时间按 UTC 写回 RTC
$ sudo hwclock --systohc --utc
$ sudo hwclock --show
2026-08-10 07:40:02.120000+00:00
```
**复盘**：
- 先比较 epoch/UTC，确认“时间线错”还是“显示时区错”；不要一上来改时区。
- RTC 模式与内容必须一致；重启才复发优先查 RTC/虚拟化平台，运行中渐漂优先查 NTP。
- 应用日志输出带 `Z` 或数值偏移，采集端按字段解析；TLS、JWT、Kerberos、数据库复制都对时钟偏差敏感。
- 校时服务交给 systemd 管理和观察，联动 [服务管理与定时任务](/kb/os/Bash/12-服务管理与定时任务/) 的 `systemctl`/`journalctl`。
## 17. 完整案例二：locale 错乱导致脚本漏匹配
**现象**：交互运行脚本能识别中文用户名，cron 中却把名字按 3 个“字符”截断；另一台机器生成的排序结果也不同。
```bash
$ locale charmap
UTF-8
$ printf '张三\n' | wc -m
3
$ env -i PATH=/usr/bin:/bin LANG=C sh -c "printf '张三\n' | wc -m"
7
$ printf 'Z\na\nä\n' | sort
a
ä
Z
$ printf 'Z\na\nä\n' | LC_ALL=C sort
Z
a
ä
```
**判断**：第一条结果含两个汉字和换行，共 3 字符；`LANG=C` 下 6 个 UTF-8 字节加换行，共 7。cron/service 没继承交互 Shell 的 locale，脚本却依赖字符计数和自然语言排序。
```bash
$ locale -a | grep -i 'c\.utf\|en_US\.utf'
C.utf8
en_US.utf8
$ LANG=C.UTF-8 LC_ALL= ./report.sh
```
**修复策略**：
- 只需要 UTF-8 字符处理且要求可重复排序：脚本分别对字符步骤用 `LC_CTYPE=C.UTF-8`，对机器排序步骤用 `LC_ALL=C`，不要让一个全局值承担冲突目标。
- 面向人的语言排序：安装并明确指定业务 locale，所有节点保持相同 glibc/tzdata/locale 基线。
- 在 cron、systemd unit 或容器清单中显式设置 `LANG`、`PATH`，不要依赖 `.bashrc`；服务配置参见 [服务管理与定时任务](/kb/os/Bash/12-服务管理与定时任务/)。
- 文件编码不确定先 `file -bi`/`iconv`，`LANG=UTF-8` 不会把 GBK 文件自动转换成 UTF-8。
## 18. 完整案例三：SSH 后乱码、退格失效且终端无回显
**现象**：经跳板机进入老服务器后中文乱码，Backspace 打出 `^?`；运行一个交互程序崩溃后，输入完全不可见，颜色程序报 `unknown terminal`。
```bash
$ tty; printf '%s\n' "$TERM $LANG $LC_CTYPE"; stty -a
/dev/pts/8
tmux-256color zh_CN.UTF-8
speed 38400 baud; rows 24; columns 80; ... erase = ^H; ... -echo ...
$ infocmp "$TERM"
infocmp: couldn't open terminfo file /usr/share/terminfo/t/tmux-256color.
$ locale -a | grep -i zh_CN
# 无输出
```
**判断**：这是三个独立故障叠加：程序崩溃留下 `-echo`；终端发送 DEL (`^?`) 而服务端 erase 配成 `^H`；远端缺 `tmux-256color` terminfo；服务端也没生成客户端转发来的 `zh_CN.UTF-8` locale。
```bash
# 1. 盲打恢复行规程
stty sane
stty erase '^?'
# 2. 优先安装发行版 terminfo 包；无 root 时安装可信条目到用户目录
tic -x -o ~/.terminfo /tmp/tmux-256color.info
# 3. 选择服务端实际存在的 UTF-8 locale
export LANG=C.UTF-8
unset LC_ALL LC_CTYPE
# 4. 验证
printf '中文 Backspace OK\n'; tput colors; infocmp "$TERM" >/dev/null
```
典型输出：中文正常显示，Backspace 正常删除，`tput colors` 返回 `256`，`infocmp` 退出码为 0。
**复盘**：
- 乱码沿链路排查：文件编码 → 进程 locale → SSH locale 转发 → 字体/终端渲染，不能只改 `$TERM`。
- 键盘行为看 `stty -a`，显示能力看 `TERM`/terminfo，这两层不要混修。
- SSH 客户端/服务端的 `SendEnv`/`AcceptEnv` 只转发获准变量，服务端还必须安装对应 locale；远程链路细节见 [远程操作与文件同步](/kb/os/Bash/11-远程操作与文件同步/)。
- 交互程序应捕获退出并恢复 termios；用户侧的应急顺序是 `stty sane` → `reset` → 重新登录。
## 本章小结
1. 系统时钟是时间线，RTC 是开机参考，时区是显示规则；先分层再决定用 `date`、`timedatectl`、`hwclock` 还是 `chronyc`。
2. 同步服务 active 不等于已同步；`tracking` 看本机偏差，`sources -v` 看上游可达与选择，`makestep` 只在理解跳变风险后使用。
3. 普通 Shell 变量不会自动传给子进程；`export` 才进入环境，`VAR=x cmd` 只影响一次，`env -i` 用于排除环境污染。
4. 命令解析优先问 `type -a`/`command -V`；`which` 看不全 Shell 世界，PATH 变化后别忘了哈希缓存。
5. locale 不只是语言，它改变编码解释、排序、字符类、日期和数字格式；可重复脚本要明确类别与目标。
6. TTY、登录会话、Shell、Readline 是不同层；`stty` 修行规程，terminfo 修显示能力，startup 文件修环境初始化。
7. `script` 便于复现但会扩大秘密暴露面；用户态录像不能替代受控、集中、不可轻易篡改的审计。
8. 完整排障坚持“观察原值 → 分层定位 → 最小修改 → 新会话/重启复验”，与 [案例](/kb/os/问题排查/12-疑难案例集锦/) 的方法一致。
## 动手实验
1. **时间三视图**：分别运行本地 `date`、`date -u`、`TZ=America/New_York date`，记录 epoch 是否改变，并用自己的话解释时区为什么不改变时间戳。
2. **DST 边界**：用 `zdump -v America/New_York` 找下一次切换，验证一个不存在和一个重复的当地时刻；生产机上只读操作，不改系统时区。
3. **chrony 体检**：执行 `chronyc tracking` 与 `chronyc sources -v`，写出当前 source、Reach、offset、frequency；没有 chrony 时记录实际同步服务及对应查询命令。
4. **环境隔离**：比较当前 `env | sort` 与 `env -i PATH=/usr/bin:/bin LANG=C /usr/bin/env`，解释新进程为何仍出现 `PWD`/`SHLVL`。
5. **命令遮蔽**：在临时 Shell 中定义 `ls(){ printf 'function\n'; }`，用 `type -a ls`、`command ls`、`/bin/ls` 对比解析；退出临时 Shell 清理。
6. **locale 对照**：用 `C` 与本机 UTF-8 locale 对包含 ASCII、汉字、重音字符的文件分别执行 `sort`、`wc -m`、`grep '[[:alpha:]]'`，记录差异。
7. **TTY 与 terminfo**：测试 `stty -echo`/`stty echo`，再记录 `$TERM`、`tput colors` 并用 `infocmp "$TERM"` 验证条目。
8. **安全录制**：`umask 077` 后用 `script` 录一段不含秘密的操作并 `scriptreplay`，检查输出日志、timing 和权限；实验后删除记录。
## 自测题
1. `date` 显示差 8 小时，应先改系统时钟还是先判断时区？
   - **答案**：先比较 UTC/epoch 与可信时间源，区分时间线错误和时区显示错误；epoch 正确只需修时区，不能把系统时钟再拨 8 小时。
2. `timedatectl` 显示 `NTP service: active`，为什么仍可能不同步？
   - **答案**：active 只说明服务启用/运行，可能没有可达 source、样本不足或被防火墙阻断；看 `System clock synchronized` 和客户端的 source/offset。
3. `hwclock --systohc` 和 `--hctosys` 的方向有何区别？
   - **答案**：前者 system-to-hardware，把系统时钟写入 RTC；后者 hardware-to-system，把 RTC 写入内核系统时钟，方向错会覆盖正确值。
4. 为什么 `name=x` 在当前 Shell 可见，子 Bash 却看不到？
   - **答案**：它只是 Shell 变量；执行 `export name` 或 `export name=x` 后，之后创建的子进程才会继承副本。
5. `type -a` 为什么比 `which` 更适合解释实际命令解析？
   - **答案**：`type` 是 Shell builtin，理解 alias、函数、builtin、哈希/PATH；外部 `which` 通常只搜索 PATH 文件。
6. `LC_ALL`、`LC_CTYPE`、`LANG` 的优先级是什么？
   - **答案**：非空 `LC_ALL` 最高，其次对应类别的 `LC_*`，最后是 `LANG` 默认值。
7. 程序崩溃后输入看不见，最快如何恢复？
   - **答案**：盲打 `stty sane` 或至少 `stty echo`；换行映射损坏时用 `Ctrl+J` 提交，再用 `reset` 重置显示状态。
8. 为什么录 `script --log-in` 比只录输出更危险？
   - **答案**：输入日志可在应用关闭回显时仍捕获密码和 token；应尽量不录输入，严格权限、保留期限和脱敏流程。
9. interactive login Bash 会同时自动读取三个用户 profile 文件吗？
   - **答案**：不会，只读取 `~/.bash_profile`、`~/.bash_login`、`~/.profile` 中第一个存在且可读的；需要它显式 source `~/.bashrc`。
10. `history -a` 与 `history -n` 各做什么？
   - **答案**：`-a` 把当前会话尚未写入的历史追加到文件；`-n` 从文件读取当前会话尚未见过的新行，用于多终端交换增量。
