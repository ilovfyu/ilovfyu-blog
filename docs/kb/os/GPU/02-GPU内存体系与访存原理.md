::: abstract 本章定位
本章回答：**GPU 的数据都存在哪？访问速度差多少？怎么访问才不浪费带宽？** 先建立"寄存器 → 共享内存 → L1 → L2 → 显存 → 主机内存"的层次全景，再逐个讲清六类可寻址内存的用途，接着深入两种显存技术（GDDR vs HBM）与带宽计算公式，最后是两个决定 GPU 访存性能的核心机制：**访存合并（Memory Coalescing）** 与 **Bank 冲突**。学完你能手算带宽、判断一段 Kernel 的访存是否合并、分析共享内存访问会不会冲突。
:::

## 1. 内存层次全景

### 1.1 金字塔

GPU 的内存体系是一棵"速度越往上越快、容量越往上越小"的树，最关键的是理解每一级的**容量量级**和**访问代价**：

```text
        ┌───────────────────────────────┐
        │  寄存器堆 Register File        │  每 SM 256KB，线程私有，0 延迟
        ├───────────────────────────────┤
        │  共享内存 Shared / L1          │  每 SM ~192~228KB，~20~30 周期
        ├───────────────────────────────┤
        │  L2（全片共享）                │  A100 40MB / H100 50MB，~200 周期
        ├───────────────────────────────┤
        │  显存 HBM/GDDR                 │  A100 80GB @ 2TB/s，400~800 周期
        ├───────────────────────────────┤
        │  主机内存（经 PCIe/NVLink）    │  容量最大，带宽 32~64 GB/s
        └───────────────────────────────┘
             容量 ▲     速度 ▼   （越往下越大、越慢）
```

::: important 两个量级直觉
1. **带宽差**：共享内存 ~10+ TB/s 量级 > 显存 2~8 TB/s > PCIe 32~64 GB/s，差 1~2 个数量级。
2. **延迟差**：寄存器 0 周期 → 共享 ~20 周期 → L2 ~200 周期 → 显存 400~800 周期。显存延迟是共享内存的 20 倍以上，必须靠并行（见 [GPU执行模型与线程调度](/kb/os/GPU/03-GPU执行模型与线程调度/)）隐藏。
:::

### 1.2 谁在管理

| 层级 | 管理方 | 可编程？ |
|---|---|---|
| 寄存器 | 编译器分配 | 不可直接寻址，靠变量 |
| 共享内存 | 程序员显式声明/拷贝 | 是（`__shared__`） |
| L1/L2 | 硬件自动 | 否（L1 可与共享内存按比例划分） |
| 显存 | 驱动/运行时（`cudaMalloc`） | 是（global/constant/texture） |

### 1.3 每一级的容量、带宽与延迟量级（A100 量级）

| 层级 | 容量 | 带宽量级 | 延迟量级 | 归属 |
|---|---|---|---|---|
| 寄存器 | 256KB/SM（每线程 ≤255 个） | 极宽（每周期 128 个 32-bit 端口） | ~0 周期 | 编译器分配 |
| 共享内存 | ≤164KB/SM | ~10+ TB/s（32 Bank × 4B × 频率） | ~20~30 周期 | 程序员显式管理 |
| L1 缓存 | 与共享内存共用 192KB | ~10 TB/s 级 | ~30 周期 | 硬件自动 |
| L2 缓存 | 40MB（全片共享） | ~5 TB/s 级 | ~200 周期 | 硬件自动 |
| 显存 HBM2e | 80GB | 2.0 TB/s | 400~800 周期 | 驱动/运行时 |
| 主机内存（PCIe Gen4） | 数百 GB~TB | 32 GB/s（双向） | 微秒级（加传输开销） | OS |

::: tip 从数字里读出的结论
共享内存比显存快约 20 倍、带宽高约 5 倍；主机内存比显存再慢 60 倍。所以优化顺序永远是：**能放寄存器/共享内存就不碰显存，能合并访存就不乱访问，能少搬主机内存就少搬**。
:::

## 2. 六类可寻址内存详解

| 类型 | 作用域 | 生命周期 | 物理位置 | 特点与坑 |
|---|---|---|---|---|
| **寄存器 Register** | 线程私有 | Kernel 执行期 | SM 寄存器堆 | 最快；每线程最多 255 个（A100）；**超限→溢出** |
| **Local Memory** | 线程私有 | 同上 | 显存（被 L1/L2 缓存） | 寄存器溢出或数组动态索引的归宿，慢 |
| **共享 Shared** | Block 内所有线程 | Block 生命周期 | SM 片上 | 可编程高速缓存；需 `__syncthreads` 同步；有 Bank 冲突 |
| **全局 Global** | Grid 内所有线程 + 主机 | `cudaMalloc` 到 `cudaFree` | 显存 | 容量大、延迟高；**必须合并访存** |
| **常量 Constant** | 所有线程（只读） | 静态 | 显存 + 常量缓存 | 仅 64KB；同一地址广播，极快 |
| **纹理 Texture/Surface** | 所有线程（只读/只写） | 显式创建 | 显存 + 纹理缓存 | 面向 2D 空间局部性；硬件插值、边界处理 |

::: warning Local Memory 是个陷阱
Local Memory 名字带"local"，物理上却在**显存**里。当每线程寄存器不够（编译器限制 255 个）或数组用动态下标访问时，数据被"溢出"到 local memory，每次访问都要走 L1/L2/显存。`ncu` 里看到 `local_load/store` 大量出现，就要减寄存器用量或改数据结构（见 [GPU性能分析与Profiling工具](/kb/os/GPU/12-GPU性能分析与Profiling工具/)）。
:::

## 3. 显存技术：GDDR 与 HBM 两条路线

### 3.1 两种思路

| 技术 | 思路 | 代表 | 位宽 | 带宽 |
|---|---|---|---|---|
| GDDR6/GDDR6X | 把**频率**做高（6X 用 PAM4 信号） | RTX 4090 | 384-bit | 1008 GB/s |
| HBM2e/HBM3/HBM3e | 把**位宽**做宽（3D 堆叠 + TSV） | A100 / H100 / B200 | 5120~8192-bit | 2.0 / 3.35 / 8 TB/s |

### 3.2 HBM 为什么能到 TB/s 级

HBM（High Bandwidth Memory）把 DRAM die **垂直堆叠**（如 8 层），层与层之间用 **TSV（硅通孔，Through-Silicon Via）** 垂直打通，再通过硅中介层（interposer）连到 GPU die：

```text
        8 层 DRAM die 垂直堆叠（每个 stack 1024-bit 接口）
        ┌──────────────────────────────┐
        │  DRAM die 7                  │
        │  DRAM die 6      ← TSV 硅通孔│
        │  ...            （垂直打孔）  │
        │  DRAM die 0                  │
        └──────────┬───────────────────┘
                   │ 硅中介层 interposer（水平走线）
        ┌──────────┴───────────────────┐
        │        GPU Die               │
        └──────────────────────────────┘
```

关键在**位宽**：一个 HBM stack 的接口是 1024-bit（128 字节），A100 用 5 个 stack 就是 5120-bit；GDDR6 单颗才 32-bit——**HBM 用"极宽的总线"换带宽，GDDR 用"极高的频率"换带宽**。宽总线不需要高频，所以 HBM 功耗更低（也因此更贵、产能更受限）。

### 3.3 带宽公式：位宽 × 频率

```text
带宽 (GB/s) = 位宽 (bit) ÷ 8 × 有效数据率 (Gbps)

RTX 4090: 384 ÷ 8 × 21    = 1008 GB/s  ✓（GDDR6X，PAM4 等效 21 Gbps）
A100:     5120 ÷ 8 × 3.2  ≈ 2048 GB/s  ✓（HBM2e，规格 2.0 TB/s）
H100:     5120 ÷ 8 × 5.2  ≈ 3328 GB/s  ✓（HBM3，规格 3.35 TB/s）
B200:     8192 ÷ 8 × 8    ≈ 8192 GB/s  ✓（HBM3e，规格 8 TB/s）
```

### 3.4 为什么带宽是 GPU 的第一指标

因为大部分 Kernel 是**带宽受限**的：向量加法、归约、矩阵乘的访存阶段，每读一个数据只做很少的运算。Roofline 模型里，一个 Kernel 能达到的最大性能 = min(峰值算力, 带宽 × 计算强度)。算力再高，带宽不够就卡住——**所以 GPU 宁可牺牲单线程性能也要堆带宽**（见 [CUDA优化技术与性能调优](/kb/os/GPU/05-CUDA优化技术与性能调优/)）。

::: tip 一条经验法则
一个 10 TFLOPS 的 Kernel 如果计算强度是 5 FLOP/B，就需要 2 TB/s 带宽才能喂饱。做性能预估时先算"带宽需求 = 算力 ÷ 计算强度"，再对照规格表。
:::

### 3.5 理论带宽 vs 实测带宽

规格表上的带宽是理论峰值（理想时钟 × 全部引脚）。实测中：读写切换、刷新、ECC、访问不连续（未合并）都会打折扣，`bandwidthTest` 之类工具测出的**有效带宽通常是理论值的 70%~85%**。做容量规划时建议按 80% 估：

```text
H100 理论 3.35 TB/s → 实际可用 ≈ 2.7~3.0 TB/s
RTX 4090 理论 1008 GB/s → 实际 ≈ 850~900 GB/s（GDDR 损耗略高）
```

这也解释了为什么"理论算力打满"极罕见：多数 Kernel 先撞上的是**有效带宽**这堵墙。

## 4. 访存合并（Memory Coalescing）

### 4.1 原理：一次事务取回一段连续数据

Warp 里 32 个线程同时执行一条 load 指令。硬件希望这 32 个地址**落在同一段 128 字节、且对齐**的区间里——这样一次内存事务就把 32 个 4 字节数据全部取回，只花一份带宽。

```text
合并访存（理想）：线程 t0~t31 访问连续 4B
地址: 0    4    8    12   ...         124
      ┌────────────────────────────────┐
      │ 一次 128B 事务（1 个 cacheline）│
      └────────────────────────────────┘
      实际事务数 = 1，带宽 100% 利用

未合并（stride=2）：每个线程跳过 4B
地址: 0    8    16   24   ...         248
      ┌────────────────┐ ┌────────────────┐
      │ 128B 事务（只用一半）│ 128B 事务（只用一半）│
      └────────────────┘ └────────────────┘
      实际事务数 = 2，带宽利用率 50%
```

未合并的极端情况（每个线程访问随机/跨很大步长的地址）会让事务数放大 32 倍，Kernel 的访存时间放大同样倍数——**这是最常见的性能杀手**。

### 4.2 判断准则与对策

| 代码模式 | 是否合并 | 说明 |
|---|---|---|
| `a[i] = b[i] + c[i]`（i = 全局线程号） | ✅ | 相邻线程访问相邻地址，完美合并 |
| `a[i*2]` 或跨大步长索引 | ❌ | stride 导致事务翻倍 |
| 行优先矩阵 `A[row][col]`，col 由线程号索引 | ✅ | 内层连续 |
| 列优先访问 `A[col][row]` | ❌ | 跨行跳 128B，每个线程独占 cacheline |
| 每线程连续读 4 个 float（float4） | ✅ | 32 线程 × 16B = 512B，拆成 4 个合并事务，指令数更少 |

::: note 现代硬件的细节
Volta 以后合并粒度细化到 **32 字节扇区**：只要 Warp 的地址落在若干完整 32B 扇区内，未用到的扇区不会白白取回，但**事务数/带宽仍按覆盖的扇区数计算**。所以"对齐 + 连续"依然是最优解，128B 的简化模型足够指导日常判断。
:::

### 4.3 事务数估算：不同访问模式的代价

| 访问模式（Warp 32 线程 × 4B） | 覆盖地址范围 | 128B 事务数 | 带宽效率 |
|---|---|---|---|
| 连续、128B 对齐 | 128B | 1 | 100% |
| 连续、偏移 4B（跨对齐边界） | 128B（跨越两段） | 2 | 50% |
| stride=2（`a[i*2]`） | 256B | 2 | 50% |
| stride=4 | 512B | 4 | 25% |
| 完全随机 | 不确定 | 最多 32 | ~3% |

::: tip 判断口诀
一个 Warp 的 load 是否高效，只看两件事：**地址是否连续**（相邻线程地址差 = 数据类型大小）与**起始是否对齐**（128B 边界）。两者都满足 → 1 次事务；只破坏一个 → 2 次；全破坏 → 灾难。
:::

## 5. 共享内存与 Bank 冲突

### 5.1 32 个 Bank 的结构

共享内存每个周期可以提供 **128 字节**带宽——它被分成 **32 个 Bank，每个 Bank 每周期 4 字节**：

```text
地址(字节)    0  4  8  12 ... 124   128  132 ...
            ┌──┬──┬──┬──┬─...─┬──┐ ┌──┬──┐
Bank 编号:   0  1  2  3 ...  31    0   1
规则：Bank = (字节地址 ÷ 4) mod 32
```

一次访存指令，32 个线程各访问一个 4B 地址。如果 32 个地址**恰好落在 32 个不同 Bank**——理想情况，一个周期完成；如果**两个以上线程命中同一个 Bank 的不同地址**——**Bank 冲突**，硬件把这些访问**串行化**（拆成多个周期）。

::: important 三种情况的代价
- 无冲突：32 线程一次取完，1 个周期。
- **广播**：多个线程访问**同一个地址**——不算冲突，1 个周期（所有线程拿到同一份数据）。
- **冲突**：N 个线程争同一个 Bank 的不同地址——需要 N 个周期，最坏 32 路冲突 = 32 倍慢。
:::

### 5.2 经典冲突案例与 pad 技巧

```c
__shared__ float s[32][32];
// 线程 tid 访问 s[tid % 32][tid / 32]  —— 按"列"读
// 第 0 列: 地址 = (tid%32)*128 + 0 → 每行差 128B → 全部命中同一 Bank → 32 路冲突！

// 解法：多开一列（pad +1）
__shared__ float s[32][33];   // 行 stride = 33，跨行 132B → 132/4 = 33 → 33 mod 32 = 1
// 第 0 列: 地址依次落在 Bank 0,1,2,...31 → 无冲突
```

原理：把每行长度从 32 改成 33（**pad +1**），行与行之间错开 1 个 Bank，冲突就消失。代价只是多 4 字节/行的存储。这是共享内存优化的最经典手法，转置、卷积滑窗、矩阵分块都会用到（见 [CUDA优化技术与性能调优](/kb/os/GPU/05-CUDA优化技术与性能调优/)）。

### 5.3 什么时候该用共享内存

| 场景 | 共享内存方案 | 为什么快 |
|---|---|---|
| 每个数据被同一 Block 多次读取 | 先合并访存搬到共享内存，之后反复读 | 把 400~800 周期的显存访问变成 20 周期的共享访问 |
| 卷积/滑窗有重叠区域 | 边界 tile 进共享内存复用 | 消除重复的全局读 |
| 需要 Block 内交换/转置数据 | 共享内存做中转（注意 Bank 冲突） | 片上交换远快于走显存 |
| 需要 Block 内归约 | 每 Block 局部归约再原子加 | 把全局原子冲突降到每 Block 一次 |

::: warning 共享内存不是越多越好
共享内存每 SM 有限（A100 164KB），占用越多，能驻留的 Block 越少，**占用率下降**（见 [GPU执行模型与线程调度](/kb/os/GPU/03-GPU执行模型与线程调度/) 第 6 节）。用共享内存换带宽时，务必核算对占用率的影响——两者是跷跷板。
:::

## 6. ECC 内存

- **作用**：HBM 支持 ECC（纠错码），典型为 **SECDED**——纠正 1 位错误、检测 2 位错误，防止宇宙射线/信号噪声导致的计算错误。
- **覆盖范围**：A100、H100 全内存启用 ECC（HBM + L2）；消费卡（如 RTX 4090）无 ECC。
- **实现方式**：HBM 用**旁带 ECC（sideband）**，额外引脚传输校验位（每 8 字节数据约 1 字节校验）；GDDR6 则有 inline ECC 可选。
- **代价**：约 2~3% 的带宽/容量开销。AI 训练动辄数天，一个不可纠正错误会毁掉整个任务，所以数据中心卡**强制 ECC**。
- 出现 ECC 错误怎么办（`nvidia-smi -q -d ECC`、Xid 错误）见 [GPU故障排查与问题定位](/kb/os/GPU/14-GPU故障排查与问题定位/)。

## 7. 缓存一致性：GPU 是"弱一致性"世界

- **L2 是全片共享**：所有 SM 的访存、原子操作（见 [GPU执行模型与线程调度](/kb/os/GPU/03-GPU执行模型与线程调度/)）都以 L2 为汇聚点，L2 是 GPU 内部的一致性点。
- **L1 每 SM 私有、不保证一致**：一个 SM 改了数据，另一个 SM 的 L1 里可能还是旧值。需要跨 SM 可见时，用 `__threadfence()` 或原子操作把更新刷到 L2。
- **CPU 与 GPU 之间没有硬件一致性**：PCIe 上没有 coherence 协议。传统模型靠 `cudaMemcpy` 显式搬运；**Unified Memory（统一内存）** 则靠驱动把页面按需迁移——CPU 访问 → 页错误 → 迁移到主机内存；GPU 访问 → 迁移回显存。迁移的开销和陷阱见 [GPU内存管理与显存分配](/kb/os/GPU/07-GPU内存管理与显存分配/)。

## 8. 本章小结

- 层次全景：寄存器（0 周期）→ 共享/L1（~20）→ L2（~200）→ 显存（400~800）→ 主机内存（PCIe）；带宽逐级下降 1~2 个数量级。
- 六类内存：寄存器/局部/共享/全局/常量/纹理，作用域、生命周期、物理位置各不相同。
- 显存技术：GDDR 靠频率、HBM 靠位宽（TSV 堆叠）；带宽 = 位宽÷8 × 有效速率。
- 合并访存：32 线程连续+对齐 → 1 次 128B 事务；stride/错位/随机 → 事务放大。
- Bank 冲突：32 Bank × 4B，多线程命中同 Bank 不同地址 → 串行化；pad +1 破解。
- ECC 与一致性：数据中心全 ECC；L2 是 GPU 一致性点，CPU-GPU 无硬件一致，UVM 靠页面迁移。

## 自测题

**1. 一块 HBM3 显存位宽 5120-bit、有效速率 5.2 Gbps，带宽是多少？写出公式。**
答：带宽 = 位宽 ÷ 8 × 有效速率 = 5120 ÷ 8 × 5.2 = 640 × 5.2 = 3328 GB/s ≈ 3.3 TB/s（H100 规格 3.35 TB/s）。

**2. RTX 4090 用 384-bit GDDR6X、21 Gbps，为什么带宽是 1008 GB/s？**
答：384 ÷ 8 × 21 = 48 × 21 = 1008 GB/s。GDDR6X 用 PAM4 信号，每个引脚等效速率 21 Gbps，但位宽只有 HBM 的十几分之一，所以带宽低于 HBM。

**3. 判断以下三种访问是否合并：`c[i]=a[i]+b[i]`；`c[i]=a[i*2]`；`c[i]=a[rand()%N]`。**
答：第一种合并（相邻线程相邻地址，1 次 128B 事务）；第二种未合并（stride=2，事务数翻倍，带宽利用率 50%）；第三种完全未合并（随机地址，每个线程几乎独占一次事务，放大最多 32 倍）。

**4. 32 线程访问共享内存地址 0,4,8,...,124（各差 4B）会发生什么？**
答：地址 0~124 除以 4 得 0~31，正好落在 32 个不同 Bank，无冲突，1 个周期完成。

**5. 32 线程访问共享内存地址 0, 128, 256, ...（各差 128B）会发生什么？**
答：128÷4=32，所有地址 mod 32 = 0，全部命中 Bank 0 的不同地址 → 32 路 Bank 冲突 → 串行化为 32 个周期，慢 32 倍。解法：把数组每行 pad 成 33 个 float，行 stride 变 132B，132÷4=33，33 mod 32=1，错开 Bank。

**6. 为什么寄存器溢出（local memory）会让 Kernel 显著变慢？**
答：local memory 物理上在显存，访问延迟 400~800 周期（虽有 L1/L2 缓存），而寄存器是 0 延迟；频繁溢出等于把热点数据放到最慢的层级。

**7. ECC 的纠错能力是什么？为什么数据中心 GPU 必须开？**
答：SECDED：纠正单比特、检测双比特错误。训练任务耗时长、结果不可错，单比特翻转会污染整次训练，所以 A100/H100 全内存 ECC，代价是约 2~3% 带宽开销。

**8. 为什么说 GPU 内存是"弱一致性"模型？Unified Memory 怎么解决 CPU-GPU 一致问题？**
答：L1 每 SM 私有且不保证跨 SM 立即可见，需 fence/原子操作刷到 L2；CPU 与 GPU 间无硬件一致性协议。Unified Memory 由驱动按页迁移：访问发生在哪一侧就把页迁到哪一侧，用页错误触发迁移（见 [GPU内存管理与显存分配](/kb/os/GPU/07-GPU内存管理与显存分配/)）。

**9. 一个 Kernel 每线程读 4B、未合并访存，带宽 2 TB/s、访存延迟 400ns，粗略估算需要多少线程同时在途才能喂饱带宽？**
答：在途数据量 = 延迟 × 带宽 = 400ns × 2 TB/s = 800KB；每线程 4B → 需要 20 万线程同时在途。若合并访存（每次事务 128B），所需线程数降为 800KB/128B = 6400——这直观解释了"合并访存 + 高占用率"双管齐下的必要性（理论依据 Little's Law，见 [GPU执行模型与线程调度](/kb/os/GPU/03-GPU执行模型与线程调度/)）。
