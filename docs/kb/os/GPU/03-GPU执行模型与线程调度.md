::: abstract 本章定位
本章回答：**成千上万个线程在 GPU 上到底怎么被安排执行？** 先区分"编程模型"（Grid/Block/Thread）与"执行模型"（Warp/SIMT），讲清 Warp 为什么是 32、SIMT 与 SIMD/SPMD 的区别，然后深入 Warp 调度与延迟隐藏（GPU 不需要大缓存的原因），再讲占用率怎么算、Block 怎么分到 SM（Waves 与 Tail Effect）、分支发散、同步与原子操作。学完你能手算占用率、解释"为什么占用率不是越高越好"、定位 Kernel 慢的调度层面原因。
:::

## 1. 编程模型 vs 执行模型

### 1.1 三层线程层次

CUDA 编程模型把线程组织成三层：**Grid（网格）→ Block（线程块）→ Thread（线程）**。

```text
Grid（一次 Kernel 启动的所有线程）
└── Block(0,0)  Block(0,1)  Block(0,2) ...
    └── Thread(0) Thread(1) ... Thread(255)
    （Block 是"逻辑上可同步、可共享内存"的线程组）
```

| 编程模型概念 | 执行模型的对应物 |
|---|---|
| Thread | Warp 里的一条 lane（通道），跑在某个 CUDA Core 上 |
| Block | 驻留在一个 SM 上的线程组；共享内存 + `__syncthreads` 同步域 |
| Grid | 一次 Kernel 启动；Block 由 GigaThread 引擎分派到各 SM |
| （编程模型看不到） | **Warp**：32 个线程的硬件调度/执行单位 |

::: important 关键区别
编程模型里 Block 内线程"可以"同步、共享内存；执行模型里 **Block 被整个放在一个 SM 上**，共享内存和同步才有硬件基础。Block 太大、资源不够时根本驻留不进去——这是占用率的由来。
:::

## 2. Warp：32 个线程绑在一起

### 2.1 什么是 Warp

**Warp = 32 个连续编号的线程**，是 GPU 硬件调度和执行的最小单位。调度器每次挑一个 Warp，把**一条指令**广播给其中 32 个线程（lane）同时执行。

### 2.2 为什么是 32

- 一个 Warp 的线程**共享程序计数器（PC）和指令流**：取指、译码的开销由 32 个线程摊薄，控制逻辑的单位成本降到 1/32。
- 32 个线程 × 4 字节 = 128 字节，恰好是一个缓存行/一次合并访存事务的宽度（见 [GPU内存体系与访存原理](/kb/os/GPU/02-GPU内存体系与访存原理/)）——访存与执行宽度互相匹配。
- 深度学习的矩阵块（如 16×16、32×32）天然是 32 的倍数。

### 2.3 SIMT：一条指令驱动 32 个独立线程

NVIDIA 把这种执行方式命名为 **SIMT（Single-Instruction, Multiple-Thread）**：一条指令、多个线程；但每个线程有自己的寄存器、自己的地址、自己的数据流，只是"同时被同一条指令驱动"。程序员的视角是"每个线程独立执行一个函数"，硬件的视角是"一个 Warp 一条指令喂 32 个 lane"。

::: note Warp 内线程的"独立性"
老架构（Fermi/Kepler）下 Warp 内线程严格锁步（lockstep），遇到分支全体一起走；**Volta 起引入独立线程调度（Independent Thread Scheduling）**，每个线程有独立 PC，可以各自发散再收敛。但**指令发射仍以 Warp 为单位**，所以发散的分支依然要串行执行——见第 8 节。
:::

## 3. SIMT vs SIMD vs SPMD

| 模型 | 代表 | 执行方式 | 程序员视角 |
|---|---|---|---|
| **SIMD** | SSE/AVX、GPU 内的执行单元 | 一条指令操作一个向量寄存器（如 8 个 float） | 数据要显式打包进向量寄存器，宽度固定 |
| **SIMT** | NVIDIA GPU 的 Warp | 一条指令驱动 32 个标量线程（各有寄存器/地址） | 写标量代码，线程数 = 数据量，天然数据并行 |
| **SPMD** | CUDA 编程模型、MPI | 同一程序在多个线程/进程上跑不同数据 | 编程约定，不是硬件执行方式 |

::: tip 一句话区分
SIMD 是"一条指令算 8 个数"（向量）；SIMT 是"一条指令喂 32 个线程"（标量线程 × 32）；SPMD 是"大家跑同一个程序、各干各的数据"——CUDA 程序看起来是 SPMD，硬件执行起来是 SIMT。
:::

## 4. Warp 调度

### 4.1 调度器结构

现代 NVIDIA SM（Kepler 起）有 **4 个 Warp Scheduler**，每个调度器管理一部分 Warp 和一组执行单元分区：

```text
                SM 内（4 个调度器，每个每周期发射 1 条指令）
┌──────────────────────────────────────────────────────┐
│  Scheduler 0: warp0 warp4 warp8 ...   → FP32/INT32 分区0│
│  Scheduler 1: warp1 warp5 warp9 ...   → FP32/INT32 分区1│
│  Scheduler 2: warp2 warp6 warp10 ...  → Tensor/LSU    │
│  Scheduler 3: warp3 warp7 warp11 ...  → Tensor/LSU    │
│        │ 每周期各自从"就绪" Warp 里挑一个发射          │
│        ▼                                               │
│  指令分发 → 32 个 lane 的执行单元（一条指令 = 一个 Warp）│
└──────────────────────────────────────────────────────┘
```

- 每个 Warp 处于四种状态之一：**就绪（可发射）/ 等待（访存、依赖）/ 停滞（资源冲突）/ 已退出**。调度器只在"就绪"里选。
- A100 SM 每周期最多发射 **4 条** Warp 指令（4 调度器 × 1）；Volta/Hopper 还支持**双发射**——同一周期额外并行发射一条独立指令（如 FP32 与访存指令）。
- Warp 切换的代价**几乎为零**：线程的寄存器都留在寄存器堆里，切换只是换一个"取指目标"，不需要保存/恢复现场——这正是延迟隐藏能成立的前提。

## 5. 延迟隐藏（Latency Hiding）

### 5.1 问题：一条访存要几百周期

GPU 的全局访存延迟 400~800 周期，一条 FMA 从发射到结果可用也要 4~20 周期。如果执行单元每次都要等结果，吞吐会跌到峰值的几十分之一。

### 5.2 答案：切换 Warp

CPU 的解法是**降低延迟**（大缓存、分支预测、乱序执行）；GPU 的解法是**提高并行度**——一个 Warp 在等内存时，调度器立刻发射另一个 Warp 的指令。只要"同时在途"的指令足够多，执行单元就永远不空转：

```text
周期:  1  2  3  4  5  6  7  8  9  ...
Warp A:  LD  .........等待 500 周期.........  用结果
Warp B:      FMA FMA FMA LD  .........等待.........
Warp C:          LD  FMA FMA FMA  .........
Warp D:              LD  FMA FMA FMA
→ 任何时刻都有指令在发射，内存等待被"藏"在别的 Warp 的执行里
```

### 5.3 需要多少 Warp？——Little's Law

**在途工作量 = 延迟 × 吞吐**（Little's Law）。要维持每周期发射 1 条指令、而每条指令要 L 个周期才有结果，就需要 **L 条指令同时在途**；每条指令属于一个 Warp，所以：

```text
需要的 Warp 数 ≈ 延迟(周期) × 每周期发射的指令数

算例：FMA 依赖延迟 ~10 周期、每周期发 1 条 → 每调度器需 ~10 个 Warp
      访存延迟 ~200 周期（L2 命中）→ 需要几十个 Warp 持续有访存在途
      （SM 上限 64 个 Warp / 4 调度器 = 每调度器 16 个）
```

从带宽侧看同样成立：**在途字节 = 延迟 × 带宽**。带宽 2 TB/s、延迟 400ns → 需要 800KB 数据在途；每线程取 4B（未合并）就要 20 万线程，合并访存后只需 6400 线程（见 [GPU内存体系与访存原理](/kb/os/GPU/02-GPU内存体系与访存原理/) 自测第 9 题）。所以：

::: important 两条腿缺一不可
**延迟隐藏（占用率）× 每次事务的字节数（合并访存）= 喂饱带宽**。占用率再高，访存不合并也白搭；访存合并了，占用率太低照样等内存。
:::

### 5.4 为什么 GPU 不需要大缓存和分支预测

因为 GPU 用"线程级并行"替代了"单线程优化"：缓存、分支预测解决的是**单条指令流**的延迟问题，而 GPU 的问题是"同时有几千条指令流"，解决手段是**并发切换**而不是单流优化。这是 [GPU硬件架构与工作原理](/kb/os/GPU/01-GPU硬件架构与工作原理/) 第 8 节的硬件设计结论在执行模型上的落地。

## 6. 占用率（Occupancy）

### 6.1 定义与四大约束

**占用率 = 实际驻留的活跃 Warp 数 ÷ SM 最大可容纳 Warp 数**（A100/H100 为 64 个，即 2048 线程）。决定一个 Block 能否驻留、能驻留几个的，是四个资源上限：

| 资源 | A100/H100 每 SM 上限 | 影响 |
|---|---|---|
| 线程数 | 2048 | Block 大小 × Block 数 ≤ 2048 |
| Block 数 | 32 | 每 SM 最多 32 个 Block |
| 寄存器 | 65536 个（256KB） | 每线程寄存器 × 线程数 ≤ 65536 |
| 共享内存 | 164KB（A100）/ 227KB（H100） | 每 Block 共享用量 × Block 数 ≤ 上限 |

### 6.2 手算占用率

```text
例 1：Block = 256 线程，每线程 32 寄存器
  每 Block 寄存器 = 256 × 32 = 8192 → 65536 ÷ 8192 = 8 个 Block
  线程数 = 8 × 256 = 2048 → 占用率 100% ✓

例 2：Block = 256 线程，每线程 64 寄存器
  每 Block = 16384 → 4 个 Block → 1024 线程 → 占用率 50%

例 3：Block = 256 线程，每 Block 共享 48KB（A100 上限 164KB）
  164 ÷ 48 = 3 个 Block → 768 线程 → 占用率 37.5%

例 4：Block = 256，每线程 40 寄存器
  每 Block = 10240 → 65536 ÷ 10240 = 6.4 → 6 个 Block
  6 × 256 = 1536 线程 → 占用率 75%（向下取整）
```

::: warning 占用率为什么不是越高越好
1. **寄存器溢出**：为了堆占用率给每线程压寄存器，可能触发溢出到 local memory（[GPU内存体系与访存原理](/kb/os/GPU/02-GPU内存体系与访存原理/) 的坑），更慢。
2. **缓存竞争**：驻留 Warp 太多，L1/共享内存被多个 Block 瓜分，命中率下降。
3. **带宽受限的 Kernel**：占用率 50% 可能已把带宽打满（Roofline 判断见 [CUDA优化技术与性能调优](/kb/os/GPU/05-CUDA优化技术与性能调优/)），再堆占用率没有收益。
4. **指令发射争抢**：几十个 Warp 抢 4 个调度器的取指带宽，取指本身成为瓶颈。
结论：占用率是"够用就好"的约束，不是优化目标；瓶颈在带宽时优先改访存，瓶颈在延迟时再提占用率。
:::

## 7. Block 到 SM 的分配：Waves 与 Tail Effect

Block 由 **GigaThread 引擎**分配给 SM（[GPU硬件架构与工作原理](/kb/os/GPU/01-GPU硬件架构与工作原理/) 第 4 节）。一次 Kernel 的 Block 通常远多于 SM 容量，于是**分波（Wave）执行**：

```text
假设：132 个 SM（H100），每 SM 同时驻留 4 个 Block → 每波容量 = 528 个 Block

Grid = 1000 个 Block：第 1 波 528 + 第 2 波 472 → 2 波，尾波利用 472/528 ≈ 89%
Grid = 1100 个 Block：1 波 528 + 尾波 44 → 尾波只用了 44/528 ≈ 8% —— Tail Effect！

对策：Block 数取"每波容量"的整数倍（528×2=1056），或干脆远大于容量
      （如 10000 个 Block），让调度器自行均衡，尾波占比趋近于零
```

**Tail Effect（尾波效应）**：最后不满的一波里大量 SM 空闲。规模小时（Block 数 ≈ 容量），尾波浪费可能超过 50%；Grid 足够大时影响可忽略。

## 8. 分支发散（Divergence）

### 8.1 问题：Warp 内走不同分支

一个 Warp 的 32 个线程共享一条指令流。`if/else` 让部分线程走 A 路径、部分走 B 路径时，硬件用**活动掩码（active mask）**把 Warp 分成两组，**两路分支串行执行**：

```c
if (tid % 2 == 0) { a[tid] = x; }   // 偶数线程
else              { a[tid] = y; }   // 奇数线程

// 硬件执行顺序：先发 if 分支指令（偶数 lane 有效）
//              再发 else 分支指令（奇数 lane 有效）
// 该 Warp 的指令数 ×2，吞吐减半；分支嵌套越多层，代价越大
```

### 8.2 代价与缓解

| 场景 | 代价 |
|---|---|
| 2 路 if/else 各一半 | 该 Warp 指令数 ×2 |
| N 路 case/switch 均分 | 指令数 ×N |
| 循环次数不一致 | 最长路径决定 Warp 退出时间 |

缓解手段：
1. **数据重排**：让同一 Warp 的线程尽量走同一分支（如按条件重排数据、用 `__ballot`/`__activemask` 统计）；
2. **谓词化（Predication）**：短分支编译器自动转成谓词指令，两路都执行、用掩码丢弃，省去分支跳转（适合代价低的分支）；
3. **牺牲分支保合并**：很多时候"统一访问 + 判断跳过"比"分支 + 未合并访存"更快——带宽是更贵的资源。

::: note Volta 之后的新变化
独立线程调度让发散线程可以各自推进（例如 A 路径先算完先发后续指令），但**指令仍按 Warp 发射**，串行执行两路的总体代价不变。真正规避发散靠的还是数据组织。
:::

## 9. 同步与原子操作

### 9.1 Block 内同步：`__syncthreads()`

Block 内所有线程到达屏障后一起放行，保证共享内存的读写顺序可见：

```c
__shared__ float s[256];
s[tid] = data[tid];
__syncthreads();              // 等所有线程写完共享内存
result = s[255 - tid];        // 才能安全地读别人写的值
```

::: warning 死锁陷阱
`__syncthreads()` 出现在**条件分支里**（一部分线程不执行）会死锁——不是所有线程都到得了屏障。同步只能放在"全 Warp/全 Block 必然经过"的位置。
:::

### 9.2 全 Grid 同步：Cooperative Groups

`grid.sync()` 需要 **cooperative launch**（所有 Block 必须同时驻留，即占用率受限），用于流水线式迭代算法；普通 Kernel 里不能全网格同步（不同 SM 的 Block 进度互不可知，只能靠 Kernel 边界）。

### 9.3 内存栅栏与原子

- `__threadfence()`：保证本线程的写操作在**全局可见顺序**上先于后续操作（配合 [GPU内存体系与访存原理](/kb/os/GPU/02-GPU内存体系与访存原理/) 的弱一致性模型理解）。
- 原子操作（`atomicAdd` 等）：全局原子在 **L2 的原子单元**执行——所有 SM 以 L2 为汇聚点，天然保证一致性；共享内存原子在 SM 内执行。
- **原子冲突**：多个 Warp 同时 `atomicAdd` 同一地址会串行化。对策：**私有化 + 归约**——每个线程先算自己的局部和，最后一次性原子加（分块归约细节见 [CUDA优化技术与性能调优](/kb/os/GPU/05-CUDA优化技术与性能调优/)）。

## 10. 指令流水线：从取指到写回

一条指令在 SM 内的旅程：

```text
取指(Fetch) → 译码(Decode) → 发射(Issue) → 执行(Execute) → 写回(Writeback)
   ▲              │              │              │
   └── 任何一级停顿都会让该 Warp 进入"等待"状态，调度器换别的 Warp 上
```

常见停顿（stall）原因：

| 停顿类型 | 原因 | 对策线索 |
|---|---|---|
| 访存停顿 | 全局/L2/共享内存未命中 | 合并访存、共享内存复用（[GPU内存体系与访存原理](/kb/os/GPU/02-GPU内存体系与访存原理/)） |
| 依赖停顿 | 指令等前一条结果 | 提高指令级并行/占用率 |
| 分歧停顿 | 分支串行执行 | 数据重排、谓词化 |
| 资源冲突 | 执行单元/LSU 争抢 | 调整指令混合 |
| 同步等待 | `__syncthreads`/原子 | 减少同步点、降低冲突 |

::: tip 停顿的实测
真机上用 `ncu` 看每个 Kernel 的 stall 占比（`stall_memory_dependency`、`stall_not_selected` 等）比猜测快得多——分类与解读见 [GPU性能分析与Profiling工具](/kb/os/GPU/12-GPU性能分析与Profiling工具/)。
:::

## 11. 本章小结

- 编程模型（Grid/Block/Thread）≠ 执行模型（Warp/SIMT）：Block 驻留 SM、Thread 是 Warp 的 lane。
- Warp = 32 线程共享指令流（SIMT），摊薄控制成本、匹配 128B 访存粒度。
- 4 个 Warp Scheduler 每周期各发射 1 条指令；切换 Warp 零成本 → **延迟隐藏**（Little's Law：在途量 = 延迟 × 吞吐）。
- 占用率 = 活跃 Warp / 64，受线程数、Block 数、寄存器、共享内存四重约束；够用就好，不是越高越好。
- Block 分波执行，尾波不满造成 Tail Effect；分支发散让 Warp 串行执行多路；同步靠 `__syncthreads`/fence，原子在 L2。

## 自测题

**1. Warp 为什么是 32 个线程？**
答：三个理由：①32 个线程共享 PC 和指令流，控制逻辑成本摊薄到 1/32；②32 × 4B = 128B，恰好匹配合并访存的一次事务宽度（[GPU内存体系与访存原理](/kb/os/GPU/02-GPU内存体系与访存原理/)）；③矩阵分块等数据并行负载天然以 32 为倍数。

**2. SIMT 与 SIMD 的区别是什么？**
答：SIMD 一条指令操作一个向量寄存器里的多个数据（数据要打包、宽度固定）；SIMT 一条指令驱动 32 个独立标量线程，每线程有自己的寄存器与地址，程序员写标量代码。SPMD 则是"同一程序多份数据"的编程约定，CUDA 程序是 SPMD 写法、SIMT 执行。

**3. 一个 SM 有 4 个调度器、最多 64 个 Warp。Block = 128 线程、每线程 40 个寄存器，占用率多少？**
答：每 Block 寄存器 = 128×40 = 5120 → 65536÷5120 = 12.8 → 12 个 Block；线程数 = 12×128 = 1536；占用率 = 1536÷2048 = 75%（活跃 Warp 48/64 = 75%）。

**4. Block = 1024 线程、每线程 64 寄存器，占用率多少？为什么？**
答：每 Block 寄存器 = 1024×64 = 65536 = SM 全部寄存器 → 只能驻留 1 个 Block → 1024/2048 = 50%。寄存器是这里的瓶颈。

**5. 为什么"占用率越高越好"是错的？**
答：①强压寄存器可能溢出到 local memory（更慢）；②Warp 太多导致 L1/共享内存与取指带宽竞争；③带宽受限 Kernel 在 50% 占用率时已打满带宽，再加无收益。占用率是约束条件，优化目标是"瓶颈资源喂饱"。

**6. 一个 SM 每周期发射 1 条指令、FMA 依赖延迟 10 周期，隐藏该延迟至少需要几个活跃 Warp？访存延迟 200 周期呢？**
答：Little's Law：在途指令数 = 延迟 × 吞吐 = 10 × 1 = 10 条 → 每调度器约 10 个 Warp 即可隐藏 FMA 延迟；访存指令要 200 个在途 → 需约 200 条访存在途，所以访存密集 Kernel 对占用率的需求远高于计算密集 Kernel，这也是为什么访存要合并（降低所需在途量）。

**7. Grid = 600 个 Block，每 SM 可驻留 4 个 Block，共 132 个 SM，说明 Waves 与 Tail Effect。**
答：每波容量 = 132×4 = 528 个 Block。600 = 528（满波）+ 72（尾波），尾波 SM 利用率仅 72/528 ≈ 13.6%。对策：Block 数取 528 的整数倍（如 1056），或远大于容量让尾波占比可忽略。

**8. Warp 内一半线程走 if、一半走 else，代价是什么？如何缓解？**
答：两路分支串行执行，该 Warp 指令数 ×2、吞吐减半（多路 switch 更严重）。缓解：按分支条件重排数据让同一 Warp 走同一路径；短分支用谓词化；用 `__ballot` 统计后统一处理。

**9. `__syncthreads()` 放在 `if (tid < 100)` 分支里会发生什么？**
答：可能死锁。只有部分线程执行到屏障，其余线程不会到达，屏障永远等不齐。同步必须放在所有线程必然经过的位置。

**10. 全局原子操作在哪里执行？多线程高频 `atomicAdd` 同一变量为什么会慢？怎么优化？**
答：在 L2 的原子单元执行（所有 SM 汇聚点）。同一地址的原子操作被串行化，冲突越频繁越慢。优化：每个线程/Block 先私有化累加（用寄存器或共享内存做局部归约），最后一次性 `atomicAdd`，把冲突次数从"每次累加"降到"每线程一次"。
