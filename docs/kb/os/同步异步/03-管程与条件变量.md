::: abstract 本章定位
信号量虽然强大，但 wait/signal 必须由程序员手动配对，极易出错。本章引入管程（monitor）：把**互斥锁 + 条件变量**封装成一个抽象数据类型，由编译器/运行时保证互斥，条件变量管理"等待某个条件成立"。C 语言中用 `pthread_mutex` + `pthread_cond_*` 实现，Java `synchronized`、Python `Condition` 是它的现代版本。
:::

## 1. 为什么需要管程

用信号量写生产者-消费者，初值错了、顺序错了、忘记 signal，都会产生**难以察觉的 bug**——而这些 bug 只有并发下才复现。教材指出：信号量的错误**无法轻易发现**，因为"逻辑正确"和"初值正确"混在一起。

管程的设计哲学：**把同步的细节从调用者手中收走，集中管理**。

- 调用者只需关心业务逻辑（"往缓冲区放数据""从缓冲区取数据"）。
- 互斥由编译器生成代码保证。
- 等待/唤醒由条件变量表达，语义清晰。

## 2. 管程的结构

一个管程是一个 ADT（抽象数据类型），结构如下：

```
┌──────────────────────────────────────┐
│  Monitor（管程）                      │
│  共享数据变量（只有管程内的过程能访问）   │
│  ┌────────────────────────────────┐  │
│  │  process1()  process2()  …     │  │  ← 入口过程（public 方法）
│  │  这些过程之间自动互斥           │  │
│  └────────────────────────────────┘  │
│  初始化代码（initialization code）     │
│  ┌────────────────────────────────┐  │
│  │  条件变量 c1, c2 …              │  │  ← 每个条件变量配一个等待队列
│  └────────────────────────────────┘  │
└──────────────────────────────────────┘
```

**关键性质**：
1. **互斥**：任意时刻**最多一个进程/线程**在管程内部执行一个过程。
2. **数据封装**：共享数据只能通过管程过程访问——从设计上杜绝了"绕过锁直接改共享数据"。
3. **条件变量**：过程需要等待某个条件时，用条件变量的 wait 挂起自己。

### 2.1 条件变量（condition variable）

条件变量 `c` 是管程内的一个"等待集合"，提供两个操作：

```
c.wait()    : 调用者挂起自己，加入 c 的等待队列，并释放管程互斥
c.signal()  : 唤醒 c 等待队列里的一个线程
```

::: important wait 必须"同时释放锁"
`c.wait()` 不是简单地睡觉——它**原子地做两件事**：(1) 释放当前持有的管程锁；(2) 挂起自己。否则持有锁睡觉会死锁（没人能进管程来 signal）。醒来后**重新获得锁**才继续执行。这是理解条件变量的核心。
:::

### 2.2 signal 的两种语义（教材讨论过）

- **Hoare 语义（signal and wait）**：signal 者立即把锁让给被唤醒者，自己等锁。
- **Mesa 语义（signal and continue）**：signal 者继续执行，被唤醒者**只能进入就绪队列，等重新抢到锁再检查条件**。

::: tip 现代系统几乎都用 Mesa 语义
因此**条件变量被唤醒后，条件可能已经不成立**（另一个线程抢先改了状态）。这就是为什么 `pthread_cond_wait` 必须放在 `while` 循环里反复检查条件，而不是 `if`。这是面试必考的细节。
:::

## 3. 管程 vs 信号量对比

| 维度 | 管程 monitor | 信号量 semaphore |
|---|---|---|
| 互斥保证 | 编译器/运行时**自动**保证 | 程序员手动配对 wait/signal |
| 同步表达 | 条件变量（条件 + 等待队列） | 计数器（初值表达资源数） |
| 出错概率 | 低（封装隔离） | 高（顺序、初值、遗漏易错） |
| 适用语言 | Java synchronized、Python、Pascal、C# | C、POSIX sem |
| 谁能访问共享数据 | 只有管程过程 | 任何线程（靠自觉） |
| 等待队列管理 | 每个条件变量一个队列 | 一个信号量一个队列 |

::: important 一句话总结差异
信号量把"同步的纪律"交给程序员；管程把"同步的纪律"写进语言结构。**管程难用错，信号量更灵活但更危险**。
:::

## 4. C 语言 Pthreads 实现

C 没有语言级管程，但 `pthread_mutex` + `pthread_cond` 组合就是管程的工程等价物：

| 管程概念 | POSIX pthread |
|---|---|
| 管程锁 | `pthread_mutex_t` |
| 条件变量 | `pthread_cond_t` |
| `c.wait()` | `pthread_cond_wait(&cond, &mutex)` |
| `c.signal()` | `pthread_cond_signal(&cond)` |
| 广播唤醒 | `pthread_cond_broadcast(&cond)` |

### 4.1 最小示例：等待一个标志

```c
#include <pthread.h>
#include <stdio.h>

pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  cond = PTHREAD_COND_INITIALIZER;
int ready = 0;

void *waiter(void *arg) {
    pthread_mutex_lock(&mtx);
    while (!ready) {                 // 必须 while！Mesa 语义
        pthread_cond_wait(&cond, &mtx);   // 释放 mtx 并睡眠；醒来后重新拿锁
    }
    printf("条件成立，继续\n");
    pthread_mutex_unlock(&mtx);
    return NULL;
}

void *signaler(void *arg) {
    pthread_mutex_lock(&mtx);
    ready = 1;                       // 修改条件
    pthread_cond_signal(&cond);      // 唤醒一个 waiter
    pthread_mutex_unlock(&mtx);
    return NULL;
}
```

```bash
gcc -pthread cond_demo.c -o cond_demo && ./cond_demo
```

::: warning 三个必须遵守的纪律
1. `pthread_cond_wait` **必须在持有 mutex 时调用**（POSIX 规定）。
2. 等待**必须用 while 循环**（Mesa 语义下条件可能已失效，且防"伪唤醒"spurious wakeup）。
3. 修改条件的代码**必须持锁**，signal 也要在锁内或锁后执行，避免丢失唤醒。
:::

## 5. 生产者-消费者用管程实现

共享一个有限环形缓冲，一个生产者、多个消费者。完整 C 代码见 [经典同步问题详解](/kb/os/同步异步/04-经典同步问题详解/)，本节给出**管程式结构**（只用一个锁 + 两个条件变量）：

```
Monitor BoundedBuffer:
    数据: 数组 buf[CAP], 头/尾指针, count
    条件变量: not_full   （缓冲不满，可写）
    条件变量: not_empty  （缓冲非空，可读）

    produce(item):
        等待: while (count == CAP) not_full.wait()
        buf[tail] = item; tail++; count++;
        not_empty.signal()          # 通知消费者有货了

    consume():
        等待: while (count == 0) not_empty.wait()
        item = buf[head]; head++; count--;
        not_full.signal()           # 通知生产者有空位
        return item
```

**为什么两个条件变量？**
- `not_full` 让"缓冲区满了"的生产者等待；
- `not_empty` 让"缓冲区空了"的消费者等待。
- 两个队列互不干扰；如果只用一个条件变量，生产者消费者可能互相误唤醒（signal 者自己等、自己唤醒，叫 **signal lost** 问题），容易死锁或饿死。

::: tip 结构感：管程让"等待什么"一目了然
条件变量名本身就在说"我在等什么"：`not_full`、`not_empty`、`has_item`。对比信号量，你必须去读初始化与 wait/signal 的配对才能推理出语义——这就是"结构正确"的价值。
:::

## 6. 现代语言的管程类比

### 6.1 Java `synchronized` / `wait` / `notify`

Java 的每个对象都有内置锁 + 内置条件变量（`wait/notify/notifyAll`）：

```java
class BoundedBuffer {
    private final Object[] buf = new Object[CAP];
    private int count = 0, in = 0, out = 0;

    public synchronized void produce(Object item) throws InterruptedException {
        while (count == CAP) wait();          // 释放内置锁并等待
        buf[in++] = item; count++;
        notifyAll();                          // 唤醒所有等待者
    }

    public synchronized Object consume() throws InterruptedException {
        while (count == 0) wait();
        Object item = buf[out++]; count--;
        notifyAll();
        return item;
    }
}
```

- `synchronized` 方法自动获得对象锁 → **互斥由语言保证**。
- `wait()` = 释放锁 + 挂起；`notify()` = 唤醒一个；`notifyAll()` = 唤醒全部。
- 建议用 `notifyAll()` 避免"只唤醒同类线程导致互相等待"的问题。

### 6.2 Python `threading.Condition`

```python
import threading

cond = threading.Condition()
buf, CAP = [], 5

def producer():
    with cond:                       # 获取锁
        while len(buf) == CAP:
            cond.wait()              # 释放锁并等待
        buf.append("item")
        cond.notify()                # 唤醒一个等待者

def consumer():
    with cond:
        while not buf:
            cond.wait()
        buf.pop(0)
        cond.notify()
```

::: tip 三种语言的同一个套路
Java 的 `wait/notify`、Python 的 `Condition.wait/notify`、C 的 `pthread_cond_wait/signal`，底层全是同一个模型：**持锁 → while 检查条件 → wait 释放锁挂起 → 醒来重抢锁 → 改条件 → notify**。学会了 C 版本，其他语言触类旁通。
:::

## 7. 为什么管程更不容易出错

| 错误类型 | 信号量写法 | 管程写法 |
|---|---|---|
| 忘记解锁 | 忘了 `signal()`，其他线程全卡死 | 互斥由语言保证，无法忘记 |
| 初值设错 | `sem_init(0)` vs `1` 语义完全不同 | 没有"初值"概念，天然无此错误 |
| 顺序写错 | wait/signal 配对错位 | 条件变量名表达意图，逻辑自洽 |
| 绕过锁访问 | 任意代码可访问共享变量 | 共享数据被封装，只能通过过程访问 |
| 信号丢失 | 条件满足时没人 signal 导致死等 | 条件检查放在 while 里，配合 notify 可重查 |

::: important 教材的核心观点
管程"把同步的细节放在语言结构中"，让并发程序的正确性**更容易论证、更难出错**。这也是 Java、C#、Python 等现代语言都提供语言级同步抽象、而 C 只能靠 pthread 库的原因。
:::

## 8. 常见误区

| 误区 | 正确理解 |
|---|---|
| "wait 只是睡觉" | wait 原子地**释放锁 + 挂起**，醒来要**重新抢锁**——所以必须在持锁状态下调用 |
| "被唤醒就能放心执行" | Mesa 语义下条件可能已不成立，必须 **while 循环重查** |
| "signal 越多越好" | signal 只唤醒一个；该用 broadcast/notifyAll 时用 signal 会导致信号丢失 |
| "条件变量就是信号量" | 条件变量**没有计数**，只有等待队列；它必须配合互斥锁（monitor）使用，不能单独当信号量 |
| "单条件变量够用" | 生产者/消费者应各用一个条件变量，否则互相误唤醒产生丢失唤醒 |

## 9. 本章小结

1. 管程 = 语言级抽象：**互斥自动保证 + 条件变量管理等待**，把同步纪律收进结构。
2. 条件变量 `wait` 的核心是"释放锁并挂起，醒来重抢锁"；`signal` 有 Hoare/Mesa 两种语义，现代系统取 Mesa。
3. Mesa 语义 ⇒ 等待条件必须用 `while` 循环检查（防伪唤醒与竞态）。
4. C 的 pthread 组合（mutex + cond）就是管程的工程等价物；Java `synchronized`、Python `Condition` 是同构的。
5. 管程更难出错，因为错误类型从"忘了配对"变成"编译器兜底"。

## 10. 自测题

1. **Q**：`pthread_cond_wait` 为什么必须传入 mutex？
   **A**：因为 wait 需要原子地"释放锁 + 挂起"，防止持锁睡觉导致死锁；同时保证唤醒者检查条件时数据一致。

2. **Q**：为什么 `pthread_cond_wait` 要在 while 循环里，而不是 if？
   **A**：Mesa 语义下唤醒后条件可能已被其他线程改变，且存在伪唤醒；while 确保只有条件真正成立才继续。

3. **Q**：Hoare 与 Mesa 语义的区别？
   **A**：Hoare：signal 者让出锁，被唤醒者立即执行；Mesa：signal 者继续执行，被唤醒者入就绪队列等锁，条件可能失效。现代系统用 Mesa。

4. **Q**：生产者-消费者为什么要两个条件变量？
   **A**：`not_full` 等空位、`not_empty` 等货，队列分离避免生产者消费者互相误唤醒导致信号丢失/饥饿。

5. **Q**：管程相对信号量不易出错的根本原因？
   **A**：互斥由语言保证（无法忘解锁）、共享数据被封装（无法绕过）、等待意图由条件变量表达（逻辑自洽）、初值概念消失。

6. **Q**：Java `notify()` 与 `notifyAll()` 该用哪个？为什么？
   **A**：优先 `notifyAll()`。只唤醒一个可能唤醒"错误类型"的等待者（比如唤醒生产者而不是消费者），导致信号丢失。

7. **Q**：条件变量和信号量的本质区别？
   **A**：信号量是带计数、可独立使用的原语（可做互斥/计数/同步）；条件变量没有计数，只有等待队列，必须配合互斥锁组成管程使用。

8. **Q**：伪唤醒（spurious wakeup）是什么？如何应对？
   **A**：被唤醒时条件其实并未满足（POSIX 允许）。应对办法就是 while 循环重查条件。
