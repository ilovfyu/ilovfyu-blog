::: abstract 本章定位
前面学的是"工具"，本章练"题目"：把信号量、管程、条件变量套用到三大经典问题——生产者-消费者（有限缓冲）、读者-写者、哲学家进餐，外加吸烟者问题，并给出可编译的 C 代码与 Linux 内核中的真实对应物。这是面试最常抽考、也最能检验是否真懂同步的一章。
:::

## 1. 生产者-消费者问题（有限缓冲）

### 1.1 问题描述

- 一个/多个**生产者**线程向缓冲区写入 item。
- 一个/多个**消费者**线程从缓冲区读出 item。
- 缓冲区有固定容量 `CAP`：
  - 满了 → 生产者必须等待（不能覆盖未消费数据）。
  - 空了 → 消费者必须等待（不能读到垃圾）。

### 1.2 信号量版本

```c
#include <pthread.h>
#include <semaphore.h>
#include <stdio.h>
#include <unistd.h>

#define CAP 5

sem_t empty;   // 空位数量，初值 CAP
sem_t full;    // 已填数量，初值 0
sem_t mutex;   // 保护缓冲区下标，初值 1
int buf[CAP], in = 0, out = 0;

void *producer(void *arg) {
    for (int i = 0; i < 10; i++) {
        sem_wait(&empty);        // 申请一个空位（无空位则阻塞）
        sem_wait(&mutex);        // 进入临界区
        buf[in] = i;
        in = (in + 1) % CAP;
        sem_post(&mutex);        // 离开临界区
        sem_post(&full);         // 增加一个"有货"
        printf("生产 %d\n", i);
        usleep(100000);
    }
    return NULL;
}

void *consumer(void *arg) {
    for (int i = 0; i < 10; i++) {
        sem_wait(&full);         // 申请一个"有货"（无货则阻塞）
        sem_wait(&mutex);
        int item = buf[out];
        out = (out + 1) % CAP;
        sem_post(&mutex);
        sem_post(&empty);        // 增加一个空位
        printf("消费 %d\n", item);
        usleep(200000);
    }
    return NULL;
}

int main() {
    pthread_t p, c;
    sem_init(&empty, 0, CAP);
    sem_init(&full, 0, 0);
    sem_init(&mutex, 0, 1);
    pthread_create(&p, NULL, producer, NULL);
    pthread_create(&c, NULL, consumer, NULL);
    pthread_join(p, NULL);
    pthread_join(c, NULL);
    return 0;
}
```

```bash
gcc -pthread pc_sem.c -o pc_sem && ./pc_sem
```

::: important 顺序为什么必须"先申请资源，后进临界区"？
`sem_wait(&empty)` 必须在 `sem_wait(&mutex)` **之前**：如果反过来，生产者拿 mutex 后再等空位，而消费者需要 mutex 才能释放空位——就形成**持有并等待的循环**，死锁。同理消费者必须先 `sem_wait(&full)`。这个顺序是经典考点。
:::

### 1.3 管程/条件变量版本

```c
#include <pthread.h>
#include <stdio.h>
#include <unistd.h>

#define CAP 5

pthread_mutex_t mtx = PTHREAD_MUTEX_INITIALIZER;
pthread_cond_t  not_full = PTHREAD_COND_INITIALIZER;
pthread_cond_t  not_empty = PTHREAD_COND_INITIALIZER;
int buf[CAP], in = 0, out = 0, count = 0;

void produce(int item) {
    pthread_mutex_lock(&mtx);
    while (count == CAP) pthread_cond_wait(&not_full, &mtx);
    buf[in] = item; in = (in + 1) % CAP; count++;
    pthread_cond_signal(&not_empty);
    pthread_mutex_unlock(&mtx);
}

int consume(void) {
    pthread_mutex_lock(&mtx);
    while (count == 0) pthread_cond_wait(&not_empty, &mtx);
    int item = buf[out]; out = (out + 1) % CAP; count--;
    pthread_cond_signal(&not_full);
    pthread_mutex_unlock(&mtx);
    return item;
}

void *producer(void *arg) {
    for (int i = 0; i < 10; i++) { produce(i); printf("生产 %d\n", i); usleep(100000); }
    return NULL;
}

void *consumer(void *arg) {
    for (int i = 0; i < 10; i++) { int it = consume(); printf("消费 %d\n", it); usleep(200000); }
    return NULL;
}

int main() {
    pthread_t p, c;
    pthread_create(&p, NULL, producer, NULL);
    pthread_create(&c, NULL, consumer, NULL);
    pthread_join(p, NULL);
    pthread_join(c, NULL);
    return 0;
}
```

```bash
gcc -pthread pc_mon.c -o pc_mon && ./pc_mon
```

::: tip 对比两个版本
- 信号量版：三个变量（empty/full/mutex），谁先 wait 有讲究，易错。
- 管程版：一把锁 + 两个条件变量，逻辑直白，"等什么"一目了然。这正是 [管程更不易出错](/kb/os/同步异步/03-管程与条件变量/) 的体现。
:::

## 2. 读者-写者问题

### 2.1 问题描述

- **读者**：只读共享数据，可多个同时读。
- **写者**：写共享数据，写时**任何人都不能访问**（读也不能）。

### 2.2 策略一：读者优先（reader-preference / readers-writers 1st）

读者优先：只要还有读者在读，新读者就**立刻**放行；写者必须等所有读者离开。

```c
#include <pthread.h>
#include <semaphore.h>

sem_t rw_mutex;   // 写者与"首位读者"共享的互斥锁，初值 1
sem_t mutex;      // 保护 reader_count，初值 1
int reader_count = 0;

void reader(void) {
    sem_wait(&mutex);
    reader_count++;
    if (reader_count == 1) sem_wait(&rw_mutex);   // 第一个读者"顶替"了写者锁
    sem_post(&mutex);

    /* 读共享数据 */

    sem_wait(&mutex);
    reader_count--;
    if (reader_count == 0) sem_post(&rw_mutex);   // 最后一个读者释放
    sem_post(&mutex);
}

void writer(void) {
    sem_wait(&rw_mutex);      // 写者拿锁，等待所有读者离开
    /* 写共享数据 */
    sem_post(&rw_mutex);
}
```

**读者优先的问题**：写者可能**饿死**——只要读者源源不断到来，`rw_mutex` 永远被读者占用。

### 2.3 策略二：写者优先 / 读写公平（writers-preference）

写者优先：新写者**优先于新读者**；读者一但开始读，写者要等。

```c
#include <pthread.h>
#include <semaphore.h>

sem_t rw_mutex;        // 读者-写者互斥，初值 1
sem_t mutex_r, mutex_w;
sem_t wsem;            // 写者信号量，优先闸门，初值 1
int reader_count = 0, writer_count = 0;

void reader(void) {
    sem_wait(&wsem);            // 写者排队优先：有写者等在 wsem 上，读者也要排队
    sem_wait(&mutex_r);
    reader_count++;
    if (reader_count == 1) sem_wait(&rw_mutex);
    sem_post(&mutex_r);
    sem_post(&wsem);

    /* 读 */

    sem_wait(&mutex_r);
    reader_count--;
    if (reader_count == 0) sem_post(&rw_mutex);
    sem_post(&mutex_r);
}

void writer(void) {
    sem_wait(&mutex_w);
    writer_count++;
    if (writer_count == 1) sem_wait(&wsem);   // 第一个写者关闸，挡住新读者
    sem_post(&mutex_w);

    sem_wait(&rw_mutex);
    /* 写 */
    sem_post(&rw_mutex);

    sem_wait(&mutex_w);
    writer_count--;
    if (writer_count == 0) sem_post(&wsem);   // 写者清空后开闸放读者
    sem_post(&mutex_w);
}
```

### 2.4 两种策略对比

| 维度 | 读者优先 | 写者优先（公平） |
|---|---|---|
| 新读者到来 | 立刻放行 | 若写者等在闸门前则排队 |
| 新写者到来 | 等所有读者读完 | 优先于读者（排队在前的读者例外） |
| 谁可能饿死 | **写者**（读者洪流） | 读者（写者洪流，但常配合队列公平缓解） |
| 适用场景 | 读远多于写、写可延迟 | 写也需要及时、公平性要求高 |

::: important 教材观点
两种实现都不理想：读者优先饿死写者，写者优先可能饿死读者。真实工程里通常用**读写公平队列**（如 Linux `pthread_rwlock` 的 writer-preference，或内核 `rwlock` 配合公平策略），并且**写者优先更被普遍采用**，因为"写者迟迟不能写"往往更严重。
:::

### 2.5 Linux 现实：`pthread_rwlock`

```c
pthread_rwlock_t rwlock = PTHREAD_RWLOCK_INITIALIZER;

// 读：
pthread_rwlock_rdlock(&rwlock);   /* 读 */ pthread_rwlock_unlock(&rwlock);
// 写：
pthread_rwlock_wrlock(&rwlock);   /* 写 */ pthread_rwlock_unlock(&rwlock);
```

::: tip 什么时候该用 rwlock 而不是 mutex？
当**读操作远多于写**、且读临界区不短时才有收益。否则维护"读者计数"的原子开销反而比一把普通 mutex 更贵——多数场景 mutex 就够了。这是工程上的"过度优化"陷阱。
:::

## 3. 哲学家进餐问题

### 3.1 问题描述

5 个哲学家围圆桌，5 根筷子，每人需要**左右两根**筷子才能吃。每根筷子是互斥资源。

朴素实现（**死锁版**）：

```c
sem_t chopstick[5];   // 每根筷子一个信号量，初值 1

// 哲学家 i 拿起左 i、右 (i+1)%5
while (1) {
    sem_wait(&chopstick[i]);         // 拿左
    sem_wait(&chopstick[(i+1) % 5]); // 拿右
    eat();
    sem_post(&chopstick[i]);
    sem_post(&chopstick[(i+1) % 5]);
    think();
}
```

**死锁场景**：5 个人同时都拿了左筷子 → 每个人都在等右边的筷子 → 循环等待 → 死锁。死锁四条件完全满足（见 [死锁](/kb/os/死锁/01-死锁特征与必要条件/)）。

### 3.2 方案一：最多 4 人同时拿筷

```c
sem_t chopstick[5];
sem_t room;   // 初值 4：最多 4 个哲学家同时想拿筷子

void philosopher(int i) {
    while (1) {
        sem_wait(&room);             // 限制并发数
        sem_wait(&chopstick[i]);
        sem_wait(&chopstick[(i+1) % 5]);
        eat();
        sem_post(&chopstick[i]);
        sem_post(&chopstick[(i+1) % 5]);
        sem_post(&room);
        think();
    }
}
```

**原理**：5 人同时抢筷是死锁的充要条件；最多 4 人参与时，总有一人能凑齐两根筷子，破坏了"循环等待"的完备性，死锁不可能发生。

### 3.3 方案二：奇偶分序（奇数先拿右）

```c
void philosopher(int i) {
    int left = chopstick[i];
    int right = chopstick[(i+1) % 5];
    while (1) {
        // 奇数哲学家先拿右、偶数先拿左 —— 打破"全部同方向拿筷"的循环
        if (i % 2 == 0) { sem_wait(&left); sem_wait(&right); }
        else            { sem_wait(&right); sem_wait(&left); }
        eat();
        sem_post(&left); sem_post(&right);
        think();
    }
}
```

**原理**：偶数先拿左、奇数先拿右，意味着**拿筷方向相反**。5 个人不可能同时只各拿了一根、且都等下一根形成完整环——至少存在一个人先拿到两根。

### 3.4 方案三：资源分级（给资源排全序）

所有资源（筷子）按编号排全序：编号小的先拿、大的后拿。上例的"奇偶分序"就是一种分级。一般化：`sem_wait(编号小的); sem_wait(编号大的);` 保证不会形成环。

::: tip 三种方案的本质
都是**破坏死锁必要条件之一**：方案一破坏"循环等待"的形成条件（限制参与人数）；方案二、三通过**资源排序**消除环路。详见 [死锁四条件](/kb/os/死锁/01-死锁特征与必要条件/)。
:::

## 4. 吸烟者问题（Smokers Problem）

### 4.1 问题描述

三个吸烟者各自缺一样材料：缺烟草（tobacco）、缺纸（paper）、缺火柴（matches）。**代理人**（agent）随机提供两种材料。吸烟者拿到自己缺的第三种材料后开始吸烟，抽完通知 agent 继续。

教材用信号量：

```
agent 提供 material[0]=tobacco+paper 时，唤醒缺 matches 的吸烟者
...
smoker 3 方案：每个材料对对应一个 semaphore，agent signal 对应者
```

**意图**：考察"**一个生产者（agent）多个消费者（smoker）的选择性唤醒**"——agent 不能盲目唤醒所有人，必须唤醒"恰好缺那一个"的吸烟者。这是**信号量丢失唤醒（lost wakeup）**问题的经典载体。

::: warning 教材强调的坑
若 agent 只用一个信号量 notify 唤醒任意一个吸烟者，可能唤醒错人（比如给了烟草+纸，却唤醒缺烟草的人），该吸烟者拿到不会用的材料就死锁。正确做法：**每种材料组合一个信号量**，只唤醒对应缺料者。
:::

## 5. Linux 内核中的实际例子

| 经典问题 | Linux 内核对应 |
|---|---|
| 生产者-消费者 | **环形缓冲 `kfifo`**（内核日志、网络 sk_buff 队列）、`waitqueue` + `schedule` |
| 读写锁 | `rwlock_t`（如文件系统、虚拟内存反向映射）、`pthread_rwlock`（用户态） |
| 哲学家/多资源 | 内核锁排序规则：**加锁必须按全局锁序**（如 `lockdep` 检测违反） |
| 并发控制 | `completion`（一个任务等待另一个完成，即"同步先后"的信号量特例） |
| 检查死锁 | `LOCKDEP`（`CONFIG_DEBUG_LOCKDEP`）：运行时检测**循环加锁顺序**，会在死锁前打印报告 |

```c
// kfifo 使用示例（内核生产者-消费者，省略部分细节）
struct kfifo fifo;
unsigned char item;
if (kfifo_put(&fifo, &item, 1) == 0)   // 缓冲满则生产者等待
    wait_event(fifo_waitq, kfifo_len(&fifo) < CAP);
```

::: tip 工程启示
Linux 从不直接照抄教材的"读者优先"，而是用 `rwlock`/`seqlock` 等带公平策略的原语；死锁靠 **`lockdep` 自动化检测**而非人工推理。工程的意义是把"理论正确"变成"可检测、可运维"。
:::

## 6. 常见误区

| 误区 | 正确理解 |
|---|---|
| "生产者先锁 mutex 再等空位" | 顺序反了会死锁：等待资源时不能先占互斥锁 |
| "读者优先最公平" | 读者优先会饿死写者；真实系统常用写者优先/公平队列 |
| "rwlock 一定比 mutex 快" | 只在读远多于写 + 临界区不短时才有收益，否则原子开销反而更贵 |
| "哲学家问题无所谓" | 它完美演示了死锁四条件，面试常考"如何破坏循环等待" |
| "agent 一个信号量就够" | 会丢失唤醒/唤醒错人，必须按材料组合分别 signal |

## 7. 本章小结

1. 生产者-消费者：信号量版三信号量（empty/full/mutex），顺序必须"先资源后锁"；管程版一锁两条件变量，更不易错。
2. 读者-写者：读者优先（写者可能饿死）vs 写者优先/公平（读者可能饿死），工程多用 rwlock。
3. 哲学家进餐：三个死锁规避方案——限制 4 人、奇偶分序、资源分级，本质都是破坏死锁必要条件。
4. 吸烟者问题：考验"选择性唤醒"，一个信号量唤醒错人会死锁。
5. Linux 工程：kfifo 环形缓冲、rwlock、completion、lockdep 是教材概念的工业实现。

## 8. 自测题

1. **Q**：生产者-消费者中，为什么 `sem_wait(&empty)` 必须在 `sem_wait(&mutex)` 之前？
   **A**：否则生产者持锁等空位、消费者持锁等放位，形成持有并等待的循环等待 → 死锁。

2. **Q**：读者优先策略下谁可能饿死？为什么？
   **A**：写者。读者不断到来时 `rw_mutex` 一直被读者占用，写者永远等不到。

3. **Q**：写者优先策略如何实现"新读者先排队"？
   **A**：用 `wsem` 闸门信号量：第一个写者到来时关闭闸门，之后新读者也要先在 `wsem` 上排队，等写者清空再放行。

4. **Q**：哲学家进餐"最多 4 人"方案凭什么避免死锁？
   **A**：5 人同时各持一筷等另一根才构成完整环；最多 4 人参与则必有哲学家的两根筷子都能拿到，打破循环等待。

5. **Q**："奇数先拿右"为什么有效？
   **A**：拿筷方向不再一致，不会形成"每人只持一根且都在等下一根"的环，从而破坏循环等待必要条件。

6. **Q**：吸烟者问题中一个信号量为何会失败？
   **A**：agent 无法精确唤醒"缺对应材料"的吸烟者，可能唤醒错人，被唤醒者拿到没用的材料导致永久等待（信号丢失）。

7. **Q**：什么时候适合用 rwlock？
   **A**：读操作远多于写操作、且读临界区足够长，维护读者计数与原子操作的收益大于开销时。

8. **Q**：Linux 用什么机制自动化检测死锁？
   **A**：`lockdep`（`CONFIG_DEBUG_LOCKDEP`），运行时检测锁的循环顺序，在死锁发生前输出报告。
