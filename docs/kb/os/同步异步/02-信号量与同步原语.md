::: abstract 本章定位
互斥锁只能回答"能不能进"。本章把同步升级为计数：信号量（semaphore）用 wait/signal 两个原子操作维护一个整数，既能做互斥（二元信号量），又能做"资源有几份、同步先后顺序"（计数信号量）。并全面对比自旋锁 vs 阻塞锁、mutex vs 信号量，映射到 Linux/Golang/Python。
:::

## 1. 信号量定义

### 1.1 数据结构

信号量 S 是一个整数变量（非负），加上两个**原子**操作：

```
wait(S)   = S-- ；若 S < 0，则阻塞当前线程（或忙等）
signal(S) = S++ ；唤醒一个被阻塞的线程（如有）
```

::: important 名字的两套叫法
- 教材：`wait` / `signal`（也作 P/V，源自荷兰语 proberen/verhogen）。
- POSIX 工程：`sem_wait` / `sem_post`。
- 两者是同一件事。面试时若听到 P/V 操作，指的就是 wait/signal。
:::

### 1.2 两种类型

| 类型 | 初值 | 用途 | 示例 |
|---|---|---|---|
| **二元信号量**（binary） | 0 或 1 | 互斥：同一资源同时只给一个线程 | 一把锁 |
| **计数信号量**（counting） | ≥ 2 | 资源计数 / 并发度控制 | 3 个许可证，最多 3 个线程同时进入 |

### 1.3 经典语义：S 可以为负吗？

两种实现有不同语义（本节看教材的"阻塞版本"）：

```
wait(S)：
     S = S - 1
     若 S < 0：把当前线程加入等待队列，阻塞

signal(S)：
     S = S + 1
     若 S ≤ 0：从等待队列唤醒一个线程
```

- 当 **S < 0** 时，`|S|` 表示**正在等待的线程数**。
- 这就是面试常问的"**信号量的计数可以是负数吗**"——阻塞实现下可以，负数代表排队人数。

::: tip 为什么"count 减到负"恰好是等待人数？
每有一个线程执行 wait，S 减一。如果 S 变负，说明"想要的人比现有资源多"，多出的部分就是排队者。所以 S = 初始许可 − 已进入 − 已排队。
:::

## 2. 信号量的两种实现方式

### 2.1 忙等待实现（自旋型）

```c
typedef struct {
    int value;
    bool lock;      // 用硬件互斥保护对 value 的访问
} semaphore;

void wait(semaphore *S) {
    while (test_and_set(&S->lock)) { /* 自旋 */ }
    S->value--;                    // 原子地修改（在自旋锁保护下）
    if (S->value < 0) { /* 加入等待队列，阻塞（实际实现不会纯忙等） */ }
    S->lock = false;
}
```

纯忙等版本的"阻塞"也是自旋：线程在 while 里空转直到有资源。教材用这个版本引出"**忙等待浪费 CPU**"的问题，从而引出阻塞实现。

### 2.2 阻塞实现（睡眠型）

```c
typedef struct {
    int value;
    queue list;      // 等待队列
} semaphore;

void wait(S) {
    S->value--;
    if (S->value < 0) {
        add_this_thread_to(S->list);
        block();              // 主动放弃 CPU，睡眠
    }
}

void signal(S) {
    S->value++;
    if (S->value <= 0) {
        remove_thread_from(S->list);
        wakeup(P);            // 唤醒一个等待线程
    }
}
```

**关键点**：`block()` / `wakeup()` 由**内核调度器**实现。线程睡眠时不再占 CPU，等 signal 唤醒。这就是现代操作系统真正的信号量实现形态。

::: warning 实现信号量本身的并发问题
注意 `S->value--` 这段代码自身也是临界区（多个线程同时 wait 会互相干扰）。因此 wait/signal 内部仍然要靠**关中断**（单核）或**原子指令 + 锁**（多核）保证原子性——同步原语也不能逃出 [临界区三要求](/kb/os/同步异步/01-临界区问题与互斥实现/) 的掌心。
:::

## 3. 自旋锁 vs 阻塞锁

### 3.1 定义

- **自旋锁（spinlock）**：拿不到锁就原地反复检查（忙等），不放弃 CPU。
- **阻塞锁（blocking mutex）**：拿不到锁就睡眠，加入等待队列，等别人释放时唤醒。

### 3.2 对比表

| 维度 | 自旋锁 spinlock | 阻塞锁 mutex/semaphore(blocking) |
|---|---|---|
| 拿不到锁时 | CPU 空转忙等 | 线程睡眠，让出 CPU |
| CPU 开销 | 自旋期间持续占 CPU | 睡眠不占 CPU |
| 需要额外开销 | 无（一次原子指令） | 上下文切换（进/出内核，保存恢复寄存器） |
| 临界区长 | 短才划算 | 无所谓（切换成本摊薄） |
| 单核 | 几乎没用（自旋等不到，还挡别人） | 合适 |
| 多核 | 合适（另一核可能正在释放） | 合适 |
| 适用场景 | 临界区极短（几十条指令）、内核态、不睡眠 | 临界区较长、可能阻塞（IO）、用户态 |
| 典型例子 | Linux 内核 spin_lock | pthread_mutex、futex 阻塞路径 |

### 3.3 怎么选：开销模型

```
总开销 ≈ 自旋时间 × 竞争概率   （自旋）
      ≈ 上下文切换成本 ≈ 微秒级   （阻塞）
```

- 如果临界区**比一次上下文切换还短**，自旋锁永远更快（多核下）。
- 如果临界区可能**较长或不确定**，阻塞锁更好——否则多个线程同时在自旋，CPU 全部空转。

::: tip 一句话决策
自旋 = "很快就会释放，我等得起"；阻塞 = "不知等多久，先睡再说"。Linux 内核的规则：**内核代码里、临界区短、且上下文不允许睡眠时用自旋锁**；用户态、可能睡眠的临界区用阻塞锁。
:::

## 4. 互斥锁 mutex 与信号量的区别

这是**最高频的面试题**，务必分清：

| 维度 | mutex（互斥锁） | semaphore（信号量） |
|---|---|---|
| 本质 | 二元：锁住/解锁 | 计数：N 个资源 |
| 能否用于计数 | 不能（只有 0/1） | 能（N ≥ 1） |
| 谁能解锁 | **只有持锁者**可以 unlock | 任何线程都可 signal（无归属概念） |
| 优先级继承/所有权 | 有 owner 概念，支持 | 无 owner 概念 |
| 典型用途 | 保护临界区（互斥） | 互斥 + **同步顺序** + 并发度控制 |
| 类比 | 房间的门锁 | 停车场剩余车位牌 |

**关键差异举例**：
- 信号量可用作"同步先后"：如 `semaphore sync = 0;` 线程 B 执行 `wait(sync)` 等待，线程 A 完成准备后 `signal(sync)`，从而"**B 必须先等 A**"。mutex 做不到这种"唤醒别人"的用法。
- mutex 的 lock/unlock **必须由同一线程成对执行**；signal 则没有这个限制。

::: warning 常见错误：用信号量当 mutex 的坑
信号量初值 1 时看起来像 mutex，但任何线程都能 signal 它，容易造成"不是持锁者也能放锁"的漏洞。现代工程语义（C++ `std::mutex`、Java `synchronized`、Golang `sync.Mutex`）都强调 mutex 的所有权与可重入性（同一线程可多次 lock 需配对 unlock）。
:::

## 5. Linux 的锁族谱

Linux 内核提供了一整套同步原语，正是本书概念的工程版：

| 内核原语 | 对应教材概念 | 特征 | 头文件 |
|---|---|---|---|
| `spin_lock` | 自旋锁 | 忙等、禁用内核抢占，临界区极短 | `include/linux/spinlock.h` |
| `mutex` | 阻塞互斥锁 | 睡眠等待、有 owner、可优先级继承 | `include/linux/mutex.h` |
| `semaphore` | 计数信号量 | 内核里已不推荐，被 mutex 取代 | `include/linux/semaphore.h` |
| `rwlock` | 读写锁 | 读共享、写独占 | `include/linux/rwlock.h` |
| `seqlock` | 顺序锁 | 写优先，读者自旋重试 | `include/linux/seqlock.h` |
| `rcu_read_lock` | RCU | 读无锁、写拷贝替换 | `include/linux/rcupdate.h` |

```c
// Linux 内核使用示例（伪代码风格）
spin_lock(&foo->lock);
foo->count++;
spin_unlock(&foo->lock);
```

::: tip 内核里"为什么优先 spinlock"
内核线程通常不可睡眠（如中断上下文、持有其他锁时），此时阻塞锁无法使用，必须自旋。而**持有自旋锁期间不能睡眠、不能长时间占用**是内核铁律——否则会死锁或卡死整个 CPU。
:::

## 6. Golang / Python 类比

把教材概念映射到日常语言，方便面试沟通：

| 教材概念 | Golang | Python |
|---|---|---|
| mutex | `sync.Mutex` / `sync.RWMutex` | `threading.Lock` / `RLock` |
| 计数信号量 | `golang.org/x/sync/semaphore`（限流） | `threading.Semaphore(N)` |
| 条件变量 | `sync.Cond` | `threading.Condition` |
| 读写锁 | `sync.RWMutex` | `threading.RLock`（配合 Lock 模拟） |
| 原子操作 | `sync/atomic` | `multiprocessing` 无直接等价，用锁替代 |
| 经典误用 | channel 不是锁！channel 是消息传递 | `GIL` 使纯 Python 无真并发，需多进程 |

```go
// Golang：信号量用于并发度控制（最多 2 个 goroutine 同时干活）
var sem = make(chan struct{}, 2)

func worker() {
    sem <- struct{}{}       // 占一个许可证
    defer func() { <-sem }() // 归还
    // do work
}
```

```python
# Python：Semaphore 控制同时下载的线程数
from threading import Semaphore, Thread

sem = Semaphore(3)

def download(i):
    with sem:
        print(f"download {i}")
```

::: warning Python GIL 的陷阱
CPython 的 GIL 保证字节码级互斥，`counter += 1` 在单线程逻辑上"安全"，但这是靠解释器串行化换来的，**不代表并发安全**；涉及多核计算需用 `multiprocessing` 或 `concurrent.futures.ProcessPoolExecutor`。GIL 是"同步的另一种解法"而非"并发能力"。
:::

## 7. 常见误区

| 误区 | 正确理解 |
|---|---|
| "信号量就是互斥锁" | 信号量更通用：互斥只是初值 1 的特例，它还能做同步先后与并发度控制 |
| "S 不能为负" | 阻塞实现下 S < 0 合法，`|S|` 就是排队等待的线程数 |
| "自旋锁一定比阻塞锁快" | 只对**极短临界区 + 多核**成立；临界区长时自旋浪费的 CPU 远超上下文切换 |
| "信号量/mutex 随便哪个都行" | mutex 有 owner 语义、可重入、可优先级继承；信号量无归属，语义不同 |
| "Linux 内核里也能随便睡" | 内核中断上下文/持锁期间不可睡眠，必须 spinlock |

## 8. 本章小结

1. 信号量 = 整数 + wait/signal 两个原子操作；二元信号量管互斥，计数信号量管资源数与同步。
2. 实现分两类：忙等待（自旋）与阻塞（睡眠队列）；阻塞版本的 S 可为负，负数表示等待人数。
3. 自旋锁 vs 阻塞锁的核心取舍：临界区长度 × 竞争概率 vs 上下文切换成本。
4. mutex 与信号量本质区别：mutex 是"有主人的二元锁"，信号量是"无归属的计数器"。
5. Linux 提供 spinlock / mutex / semaphore / rwlock / seqlock / RCU 一族；Golang/Python 对应 `sync.Mutex` / `Semaphore` 等。

## 9. 自测题

1. **Q**：信号量实现中 `S < 0` 是什么含义？
   **A**：表示有 `-S` 个线程在等待队列中（阻塞实现下）。初值 N 时，`wait` 超卖的部分就是排队者。

2. **Q**：自旋锁适合什么场景？为什么单核上几乎没用？
   **A**：多核 + 临界区极短。单核上自旋的线程占着 CPU 不让，持有锁的线程可能根本没机会跑，等同死等。

3. **Q**：mutex 和计数信号量（初值 1）有什么区别？
   **A**：mutex 有 owner（只有持锁者能解锁）、支持可重入与优先级继承；信号量无归属，任何线程都能 signal。

4. **Q**：如何用信号量实现"线程 B 必须在线程 A 完成后才开始"？
   **A**：`sem sync = 0`；B 先执行 `wait(sync)` 阻塞，A 完成时 `signal(sync)` 唤醒 B。这就是"同步先后顺序"的用法，mutex 做不到。

5. **Q**：为什么 Linux 内核中断上下文必须用 spinlock？
   **A**：中断上下文不能睡眠（调度器无法在中断里运行），阻塞锁需要睡眠，故只能自旋；同时自旋锁临界区必须极短。

6. **Q**：自旋锁与阻塞锁各自的"代价"是什么？
   **A**：自旋 = 空转占 CPU（临界区越长越亏）；阻塞 = 上下文切换（进/出内核、保存恢复现场，约微秒级），临界区短时反而更贵。

7. **Q**：wait/signal 自身是临界区吗？如何保证原子性？
   **A**：是（多个线程同时改 S->value）。单核靠关中断，多核靠原子指令 + 自旋锁保护，即"实现同步的代码也需要同步"。

8. **Q**：Golang 里想控制"最多 3 个协程同时跑"怎么实现？
   **A**：用带缓冲 channel 作为计数信号量（容量 3），进入时 `sem <- struct{}{}`，退出时 `<-sem`；或直接用 `golang.org/x/sync/semaphore`。
