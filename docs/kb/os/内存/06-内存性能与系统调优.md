::: abstract 本章定位
前五章讲机制，本章讲**性能与工程**：帧怎么分给进程（均匀/比例）、置换用全局还是局部、页大小怎么权衡、TLB 为什么靠局部性吃饭、`mmap` 文件映射的内存语义；然后把整套机制在 **Linux 内核**里对号入座——zone、buddy 分配器、slab、kswapd 回收、OOM killer、swap 机制，最后学会读 `free`、`/proc/meminfo` 并梳理内存问题排查思路。这是从"懂概念"到"能排障"的一章。

## 1. 帧分配

置换发生在"帧不够用"时，但**每个进程分到多少帧**先要定下来。常用两种：

### 1.1 均匀分配（Equal Allocation）

`m` 个帧分给 `n` 个进程：每个进程 **m/n** 帧，余数归空闲池。

- 简单，但无视进程大小差异——1MB 的进程和 1GB 的进程拿一样多帧，不公平。

### 1.2 比例分配（Proportional Allocation）

按进程虚拟地址空间大小 `S_i` 分配：

```
s_i = (S_i / ΣS) × m
```

**例题**：系统 62 个帧，3 个进程大小分别为 10、127、64 页。

```
ΣS = 10 + 127 + 64 = 201
P1: (10/201) × 62 ≈ 3.08 → 3 帧
P2: (127/201) × 62 ≈ 39.17 → 39 帧
P3: (64/201) × 62 ≈ 19.74 → 20 帧
合计 = 3 + 39 + 20 = 62 ✓
```

- 更公平，但"虚拟大小"不等于"实际使用量"；更精确的做法是按**工作集大小**（[.1 工作集（Working Set）](/kb/os/内存/05-页面置换算法/#8.1%20%E5%B7%A5%E4%BD%9C%E9%9B%86%EF%BC%88Working%20Set%EF%BC%89)）分配。

## 2. 全局置换 vs 局部置换

| 维度 | 全局置换 Global | 局部置换 Local |
|---|---|---|
| 牺牲页来自 | **任何进程**的帧（帧池共享） | 仅本进程的帧 |
| 灵活性 | 高，可偷闲帧，内存利用率高 | 低，每进程帧数固定 |
| 风险 | 一个进程可抢走别人帧，可能导致它缺页剧增 | 各进程互不影响，行为可预测 |
| 典型 | 主流 OS（Linux 用全局回收） | 帧分配严格的系统 |
| 缺点 | 需要协调，颠簸时加剧 | 可能让进程白占内存（别的进程缺帧也不让） |

::: important 现代实践
Linux 采用**全局**的页面回收（kswapd 从全局 LRU 列表回收），配合"按进程记账"（smaps 的 RSS/PSS）来兼顾公平。单纯局部置换在现代系统很少见。
:::

## 3. 页大小选择权衡

| 因素 | 大页（如 2MB/1GB） | 小页（如 4KB） |
|---|---|---|
| 页表大小 | 小（页数少） | 大 |
| TLB 覆盖范围 | 大（一页覆盖更多地址） | 小 |
| 内部碎片 | 多（每进程最后一页浪费多） | 少（≤ 页大小-1） |
| 缺页 I/O | 一次调大量数据，可能浪费 | 精细，但缺页次数多 |
| 换页粒度 | 粗 | 细 |
| 大页带来的缓存/TLB 效率 | 高 | 低 |

- 页变大 → 页表更小、TLB 命中率更高（同一 TLB 覆盖更大地址空间）、缺页次数更少；但内部碎片和"调入不必要数据"的浪费增大。
- **工程折中**：Linux 默认 4KB，同时支持 **HugePages/THP（透明大页，2MB）**——数据库等大内存应用可用大页显著降低 TLB miss。

## 4. TLB 与局部性

每次访存都要查页表（一次内存访问），页表又常驻内存 → 若每访存都查页表，成本翻倍。**TLB（Translation Lookaside Buffer）** 是页表项的缓存，在 MMU 里：

```text
逻辑地址 ──► TLB 命中？ ──是──► 直接得物理地址（约 1 周期）
              │否
              ▼
        查页表（多级，多次内存访问）──► 更新 TLB（带局部性的替换）
```

**为什么 TLB 高效**：**局部性原理**——程序访问集中在少数页面（时间局部性：刚用的页马上再用；空间局部性：相邻地址同一页）。所以 TLB 命中率常 >99%，代价是必须做得小（几十到上千条）又快（全相联/组相联）。TLB 与 EAT 结合的计算见 [.1 EAT 公式](/kb/os/内存/04-虚拟内存与按需分页/#3.1%20EAT%20%E5%85%AC%E5%BC%8F)。

## 5. 内存映射文件（mmap）

`mmap` 把**文件的一部分（或匿名内存）映射到进程地址空间**，此后读写该区域就像访问内存：

```c
void *p = mmap(addr, len, PROT_READ|PROT_WRITE, MAP_SHARED, fd, offset);
```

| 标志 | 语义 |
|---|---|
| `MAP_SHARED` | 多个进程共享同一物理页，一方的修改**对所有人可见**且会**写回文件** |
| `MAP_PRIVATE` | 私有映射，修改**不写回文件**（写时复制 COW，见 [写时复制（Copy-on-Write，COW）](/kb/os/内存/04-虚拟内存与按需分页/#4%20%E5%86%99%E6%97%B6%E5%A4%8D%E5%88%B6%EF%BC%88Copy-on-Write%EF%BC%8CCOW%EF%BC%89)） |

**与 read()/write() 的对比**：

| | `read()`/`write()` | `mmap()` |
|---|---|---|
| 路径 | 用户缓冲 ↔ 内核页缓存 ↔ 磁盘，两次拷贝 | 页缓存直接映射进地址空间，零拷贝 |
| 系统调用 | 每次都要 syscall | 映射一次后访问就是普通内存 |
| 加载 | 显式复制 | **按需缺页**惰性加载 |
| 共享 | 难（各自缓冲） | 天然支持 |

**典型用途**：共享库加载（动态链接器把 libc 映射进地址空间）、`malloc` 大块内存（>128KB 用 mmap）、进程间共享内存、数据库缓存文件。用 `cat /proc/pid/maps` 能看到大量 `libc.so.6`、`[anon]` 映射就是 mmap 的产物（见 [.3 解读 /proc/pid/maps](/kb/os/内存/03-分段与段页式/#4.3%20%E8%A7%A3%E8%AF%BB%20%2Fproc%2Fpid%2Fmaps)）。

## 6. Linux 内存管理实现

### 6.1 物理内存分区（Zones）

物理内存按用途分**zone**，每 zone 独立管理空闲页：

| Zone | 范围（64 位典型） | 用途 |
|---|---|---|
| DMA | 0 ~ 16MB | 需要 DMA 的旧设备（低地址） |
| DMA32 | 16MB ~ 4GB | 32 位设备 DMA |
| Normal | 4GB ~ 高位 | 常规内核/用户页 |
| Movable | 可迁移区 | 便于内存热插拔/防碎片 |

> 32 位系统还有 **HighMem**（高端内存）——因为内核线性映射区有限，用临时映射访问高位物理内存。

### 6.2 buddy 分配器

内核给"页"的分配器。空闲页按**2 的幂次阶（order 0~10）**组织成链表：

```
order 0: 1 页（4KB）
order 1: 2 页（8KB）
order 2: 4 页（16KB）
  ...
order 10: 1024 页（4MB）
```

- **分配**：找能满足的最小 order 块，不足时把大块**一分为二**（split）。
- **释放**：归还时若相邻兄弟块也空闲，**合并（merge）**成更大块，减少碎片。
- 经典的外部碎片问题因此得到缓解（仍是 2 的幂对齐，碎片有限）。

### 6.3 slab 分配器

内核里大量小而固定的对象（`task_struct`、`dentry`、`inode`、文件对象等）频繁分配/释放，用 buddy 直接分配太浪费。**slab**（SLUB）为每种对象建 **kmem_cache** 缓存：

- 对象从 slab 的已构造对象中分配，避免反复初始化/销毁。
- 空闲对象链表 + 每 CPU 缓存（per-cpu），分配快且并发友好。
- 可见于 `cat /proc/slabinfo`。

```text
kmem_cache (task_struct) → 若干 slab（页块）
                             每个 slab 里 N 个 task_struct 对象
分配：从空闲列表拿对象（可能新建 slab）  释放：归还空闲列表
```

### 6.4 kswapd 与回收/换出

**回收（reclaim）**发生在内存不足时，由 **kswapd 内核线程**后台驱动，或直接回收路径（同步）触发。

- **水位（watermark）**：每个 zone 维护 `min < low < high`：
  - 低于 **low**：kswapd 醒来回收，直到恢复到 high。
  - 低于 **min**：分配进入"直接回收"（进程同步等内存，会变慢甚至 OOM）。
- **回收对象**：可回收页——页缓存/文件页（干净页直接丢，脏页先写回）、匿名页（写回 swap 区）。回收顺序遵守 LRU 列表（active/inactive 链表）。
- **swap 机制**：匿名页被换出到 swap 分区/文件；`vmstat` 的 `si`（swap in）、`so`（swap out）反映换页速率，`si`/`so` 持续高 = 内存压力大，甚至接近颠簸。

### 6.5 OOM Killer

回收都满足不了时，内核启动 **OOM（Out-Of-Memory）** 处理，选一个进程杀掉。

- **overcommit**（`/proc/sys/vm/overcommit_memory`）：0=启发式（默认），1=总是允许超卖，2=禁止超卖（按 `overcommit_ratio` 限制）。
- 每个进程有 **oom_score**（内存占用越大分越高，`oom_score_adj` 可手动加减，`-1000` 表示永不 OOM）；OOM 杀 oom_score 最高且能被杀的进程。
- 保护关键进程：给 `oom_score_adj = -1000`（如 init）。

## 7. 读懂 free 命令

```
              total        used        free      shared  buff/cache   available
Mem:          16075       12345         123        1024        3607        3200
Swap:          8192        1024        7168
```

| 列 | 含义 | 来源 |
|---|---|---|
| Mem total | 物理内存总量 | /proc/meminfo `MemTotal` |
| Mem used | 实际已用 = total - free - buff/cache | 计算值 |
| Mem free | 完全空闲（未分配给任何人） | `MemFree` |
| Mem shared | 多个进程共享的页（tmpfs/shmem） | `Shmem` |
| Mem buff/cache | **内核用于文件缓存**（buffers + cached），内存紧张时可回收 | `Buffers`+`Cached`+`SReclaimable` |
| Mem available | **估算可给新进程用的内存**（含可回收缓存） | `MemAvailable` |
| Swap total/used/free | swap 区总量/已用/空闲 | `SwapTotal`/`SwapUsed` |

::: important 最易误解的三点
1. `free` 很小 ≠ 内存紧张：**buff/cache 可回收**，判断"够不够用"看 **available**，不是 free。
2. `used` 是"扣掉缓存后的已用"，与任务管理器含义不同。
3. `buffers`（块设备元数据/裸 IO）与 `cached`（文件页缓存）都属内核缓存；`available ≈ free + 可回收缓存`。
:::

关键 `/proc/meminfo` 字段速查：

| 字段 | 含义 |
|---|---|
| MemTotal / MemFree / MemAvailable | 总/空闲/可用 |
| Buffers | 块设备与文件系统元数据缓存 |
| Cached | 页缓存（文件内容） |
| Active / Inactive | 活跃/不活跃页（LRU 两链表） |
| AnonPages | 匿名页（堆/栈，换出时去 swap） |
| Mapped | 被 mmap 映射的页 |
| Shmem | tmpfs 共享内存 |
| Dirty / Writeback | 待写回/正在写回的脏页 |
| PageTables | 页表本身占用的内存 |
| SReclaimable / SUnreclaim | slab 可回收/不可回收部分 |
| SwapTotal / SwapFree / SwapCached | swap 区信息 |

## 8. 常见内存问题排查思路

排查入口依次为：**看总量 → 看单进程 → 看内核缓存 → 看 swap/回收 → 定位热点**。

1. **看总量**：`free -m` 的 available 是否过低；`vmstat 1` 看 `si`/`so`（换页）、`swpd`。
2. **看单进程**：`top`/`ps aux` 按内存排序；`cat /proc/pid/status` 看 `VmSize`（虚拟）/`VmRSS`（常驻）/`VmPeak`。
3. **看映射细节**：`cat /proc/pid/maps`、`cat /proc/pid/smaps`（每段 RSS/PSS，PSS 才反映共享页的真实占用）、`pmap -x pid`。
4. **看缓存与回收**：`cat /proc/meminfo` 的 Dirty/Cached/PageTables/SReclaimable；`drop_caches` 只应急不治本。
5. **定位热点**：`perf stat -e page-faults,minor-faults,major-faults` 统计缺页；`valgrind massif`/`heaptrack` 查泄漏；`perf top` 找分配热点。
6. **内存泄漏确认**：RSS 持续增长而不回落；进程退出后可用内存不回涨 → 疑似泄漏（用泄漏检测工具确认）。

::: tip 关键判断
RSS 高 = 常驻物理页多；VSZ 高 ≠ 真吃内存（可能只是映射了大文件/大虚拟空间）。排查先分清**虚拟内存大**还是**常驻内存大**，再决定是"限制地址空间"还是"治理真实占用"。完整方法论见 [内存与内存泄漏排查](/kb/os/问题排查/03-内存与内存泄漏排查/)。
:::

## 9. 本章小结

- 帧分配：均匀（简单不公平）vs 比例（`s_i=(S_i/ΣS)×m`，更公平）。
- 置换：全局（主流，灵活有风险）vs 局部（可控低效）。
- 页大小：大页省页表/TLB 但内部碎片多；Linux 4KB + THP 2MB。
- TLB 靠**局部性**达到 >99% 命中率，是"查页表"的成本缓冲。
- mmap：文件/匿名映射进地址空间，`MAP_SHARED` 共享写回、`MAP_PRIVATE` 写时复制，按需缺页惰性加载，零拷贝。
- Linux：zone 分物理内存 → buddy 管页块（2 的幂阶+合并）→ slab 管小对象；kswapd 按水位回收；OOM killer 兜底。
- `free`：判断内存够不够看 **available**，buff/cache 可回收；`si`/`so` 反映换页压力。
- 排查：总量 → 单进程（VmRSS）→ smaps（PSS）→ swap/回收 → 工具定位。

## 10. 自测题

**1. 系统 100 个帧，进程大小为 10、127、64 页，按比例分配各得多少帧？**
答：ΣS=201。P1=(10/201)×100≈4.98→5；P2=(127/201)×100≈63.18→63；P3=(64/201)×100≈31.84→32。合计 100 ✓。

**2. 全局置换与局部置换各有什么优缺点？Linux 用哪种？**
答：全局置换可从任意进程抢帧，内存利用率高、灵活，但可能恶化个别进程（帧被抢）；局部置换只动本进程帧，可预测但可能浪费帧。Linux 采用全局式的 kswapd 回收，配合进程级记账（RSS/PSS）平衡公平。

**3. 为什么大页能提升 TLB 命中率？代价是什么？**
答：页越大，同一 TLB 表项覆盖的地址空间越大，命中率越高、缺页更少、页表更小。代价：内部碎片增大、单次换页 I/O 变大、分配粒度过粗。所以 Linux 默认 4KB，大内存场景用 2MB THP。

**4. `mmap` 的 `MAP_SHARED` 与 `MAP_PRIVATE` 在"写"上的语义区别？**
答：`MAP_SHARED`：多进程共享同一物理页，写入对所有人可见并最终写回文件（页缓存同步）。`MAP_PRIVATE`：修改走写时复制（COW），改动只属于自己、不回写文件。

**5. 为什么 `free` 的 free 很小不代表内存不足？应该看哪列？**
答：因为 buff/cache（页缓存）在内存紧张时可以被回收供新进程使用。应看 **available**（≈ free + 可回收缓存），available 充足即内存充足；free 小只是缓存占得多。

**6. buddy 分配器如何分配 32KB（8 页）的块？释放时如何合并？**
答：从 order 3（8 页）的空闲链表找；若没有，把 order 4（16 页）块一分为二取一半，不足再向上分裂。释放时检查与它相邻的兄弟块是否空闲，若空闲则合并为 order+1 块，逐级向上合并，减少碎片。

**7. kswapd 的水位机制如何工作？低于 min 会怎样？**
答：每个 zone 有 min/low/high 三个水位。低于 low 时 kswapd 后台回收，直到回到 high；低于 min 时进入直接回收路径（调用方同步等待内存），内存极度紧张且回收无果时触发 OOM killer。

**8. 如何区分"进程虚拟内存大"和"真正常驻内存大"？排查先看哪个？**
答：`VmSize` 是虚拟地址空间（含未映射/未驻留部分），`VmRSS` 才是常驻物理页。排查先看 RSS/available，确认是否真的吃物理内存；再查 `/proc/pid/smaps` 的 PSS（分摊共享页）定位哪一段占用高。虚拟大而 RSS 小常见于大文件 mmap，未必是问题。
