::: abstract 本章定位
分页解决了物理碎片，但把用户"看不见"的地址空间压成一条线性地址流——代码、数据、栈混在一起，不便于共享和保护。本章讲**分段（Segmentation）**：按逻辑含义（段）给进程分内存，段表记录每段的 base + limit；再把分页与分段结合成**段页式**（x86 采用）。最后落到 Linux：用户态进程地址空间到底长什么样，`/proc/pid/maps` 怎么读——这是观察"段/页/虚拟地址"最直观的窗口。
:::

## 1. 分段原理

### 1.1 为什么需要分段

用户/编译器眼里的程序不是一个线性地址流，而是**若干逻辑模块**：

```
+------------+   main()
|  代码段     |   int foo()
+------------+   ...              ← 一段 = 一类逻辑单元
|  数据段     |
+------------+
|  栈段       |
+------------+
```

分段 = 按逻辑含义划分地址空间：**段（segment）** 是用户可见的、大小可变的逻辑单元。程序员的视角是 `(段, 段内偏移)`，例如 `(2, 1000)` 表示"第 2 段内的第 1000 字节"。

### 1.2 段表（Segment Table）

每进程一张段表，每段一项，记录两个关键字段：

| 字段 | 含义 |
|---|---|
| base | 段在物理内存中的起始地址 |
| limit | 段长（字节数），**段内偏移不能超过它** |

```text
逻辑地址 = (段号 s, 偏移 d)
                    │
                    ▼
        检查：s < 段表长度 且  d < 段表[s].limit ？
              └── 不满足 → 分段越界 trap（段错误 Segmentation Fault）
                    │ 满足
                    ▼
        物理地址 = 段表[s].base + d
```

**与分页的本质区别**：分页的页大小固定、用户无感知；分段的段大小可变、段号+偏移对用户可见。段表除 base 外还有 **limit**（保护），而页表不需要（页大小固定）。

### 1.3 地址转换例题

段表如下：

| 段号 | base | limit |
|---|---|---|
| 0 | 1400 | 1000 |
| 1 | 6300 | 400 |
| 2 | 4300 | 400 |
| 3 | 3200 | 1100 |

求逻辑地址 **(0, 300)** 与 **(1, 1200)**：

```
(0, 300)：300 < 1000 ✓ → 物理 = 1400 + 300 = 1700
(1, 1200)：1200 > 400 ✗ → 触发 segmentation fault
```

::: warning 段错误的真义
`Segmentation fault (core dumped)` 正是这个机制触发的：段内偏移超过 limit，硬件抛异常，OS 杀掉进程。相比分页的"越界=非法页号"，分段因为 limit 的存在，能对每一段精确防护。
:::

### 1.4 分段的优缺点

| 优点 | 缺点 |
|---|---|
| 逻辑结构清晰：代码/数据/栈天然分块 | 段大小不一 → 动态分区，产生**外部碎片** |
| 便于按段**共享**（共享库整段映射） | 段表需要 base+limit 两字段（页表只需一字段） |
| 按段保护（代码段只读）直观 | 装载需找连续空间，大段难分配 |
| 段与段之间可独立增长（栈/堆不互相干扰） | 需要紧凑来治外部碎片 |

## 2. 段页式（Segmentation + Paging）

分页无外部碎片，分段逻辑清晰——**二者结合**：先分段，再对每一段分页。

### 2.1 地址结构

```
逻辑地址
┌────────┬────────┬──────────┐
│ 段号 s │ 页号 p │ 页内偏移 d│
└────────┴────────┴──────────┘
    │        │         │
    ▼        ▼         ▼
段表[s] → (页表基址 + 页表长度) → 页表[p] → 帧号 → 物理地址
```

翻译过程两步：
1. 段表[s] 得到该段的页表基址（并检查段长/页号越界）。
2. 页表[p] 得到帧号，物理地址 = 帧号 × 页大小 + d。

### 2.2 优缺点

- 优点：既有分段的逻辑结构（共享、保护），又有分页的物理效率（无外部碎片、按页换入换出）。
- 缺点：两次查表（段表 + 页表），慢；页表多且分散；开销大于纯分页。

**教材经典对比**（4 项）：

| 机制 | 内存浪费 | 共享性 | 用户可见性 | 实现复杂度 |
|---|---|---|---|---|
| 分页 | 无外部碎片 | 差 | 无（线性空间） | 中（页表大需多级） |
| 分段 | 有外部碎片 | 好 | 有（段号可见） | 低 |
| 段页式 | 无外部碎片 | 好 | 有（段号可见） | 高（两次查表） |

## 3. Intel x86 内存管理结构（GDT/LDT）

::: note 定位
本节只需理解 x86 是如何把"段+页"组合起来做地址翻译的，理解其骨架即可，不必背寄存器细节。细节见 Intel 手册，面试很少深挖。
:::

### 3.1 x86-32 的段机制

x86-32 逻辑地址由两部分组成：**段选择子（segment selector, 16 位）+ 段内偏移（32 位）**。

```
16 位段选择子：   ┌───┬──┬────────────┐
                  │索引│TI│RPL          │   TI=0 查 GDT，TI=1 查 LDT
                  └───┴──┴────────────┘
                        ▼
   索引 → 段描述符表（GDT 或 LDT）→ 段描述符（base + limit + 属性）
                              ▼
         段页式第二阶段：线性地址 → 页表 → 物理地址
```

- **GDT（Global Descriptor Table，全局描述符表）**：系统所有进程共享，内核段、代码段等"全局段"放这里。
- **LDT（Local Descriptor Table，局部描述符表）**：每进程一张，存放该进程的私有段。
- **段描述符**：含 32 位 base、20 位 limit（配合粒度位 g：g=0 时粒度 1B，g=1 时粒度 4KB）、DPL（特权级）、存在位、类型位等。
- 现代 Linux 在 x86 上**基本不使用分段**（逻辑地址 = 段选择子固定为全 0/平坦模型，偏移=线性地址），主要靠**分页**管理内存——这是 64 位后的标准做法。

## 4. Linux 用户态内存布局

::: tip 本节是"看得见"的分段/分页
虽然内核按页管理，但用户进程的**虚拟地址空间**仍呈现出清晰的逻辑段结构。理解它，才能读懂 `pmap`、`/proc/pid/maps`、以及各种内存排查工具。
:::

### 4.1 地址空间结构（x86-64，非 PIE）

```text
高地址
┌──────────────────────────────┐  0x7FFFFFFFF000（TASK_SIZE 以下为用户空间）
│  栈 Stack（向下生长）          │
├──────────────────────────────┤  ← 栈顶（rsp 初始值附近）
│            ↓ 生长方向          │
│   （空隙）                     │
│            ↑ 生长方向          │
│  mmap 区域（共享库、mmap 文件） │  ← 共享库 libc、mmap 文件映射、堆扩展
├──────────────────────────────┤  ← brk 堆顶（向上生长）
│  堆 Heap（向上生长）           │
├──────────────────────────────┤
│  .bss 段（未初始化全局变量）     │  ← 仅记录大小，不占文件空间
├──────────────────────────────┤
│  .data 段（已初始化全局变量）    │  ← 从可执行文件加载
├──────────────────────────────┤
│  .text 段（代码）              │  ← 只读可执行
├──────────────────────────────┤
│  保留区（含环境变量、参数）       │
└──────────────────────────────┘  0x400000（ELF 默认装载点）
低地址
```

| 区域 | 内容 | 从哪来 | 增长方向 |
|---|---|---|---|
| `.text` | 代码，只读可执行 | 可执行文件 | 固定 |
| `.data` | 已初始化的全局/静态变量 | 可执行文件 | 固定 |
| `.bss` | 未初始化全局变量（全 0） | 不占文件，运行时清零 | 固定 |
| Heap | 动态内存（malloc） | `brk`/`mmap` | 向上 |
| mmap 区 | 共享库、`mmap()` 文件映射、大堆块 | `mmap` 系统调用 | 双向 |
| Stack | 局部变量、调用栈 | 内核按需建页 | 向下 |

::: warning 栈向下、堆向上
两者相向生长，若撞在一起或栈溢出到不可写页 → 触发 `Stack Overflow`（栈越界）或堆栈碰撞段错误。每个进程的用户态页表（见 [分页与页表结构](/kb/os/内存/02-分页与页表结构/)）保证了这些区域彼此隔离、按需建立（见 [虚拟内存与按需分页](/kb/os/内存/04-虚拟内存与按需分页/)）。
:::

### 4.2 进程实际布局（PIE + 共享库）

现代 Linux 默认 PIE（位置无关可执行），可执行文件本身加载在 `0x555555554000` 附近，共享库 `libc` 映射在 `0x7f...` 高地址区：

```text
0x555555554000-0x555555555000  r-xp  可执行文件 .text
0x555555755000-0x555555756000  r--p  .rodata
0x555555756000-0x555555757000  rw-p  .data / .bss
0x7f8f00000000-0x7f8f00100000  r-xp  libc.so.6
0x7f8f00300000-0x7f8f00304000  rw-p  libc 数据段
0x7fff00000000-0x7fff00001000  rw-p  [stack]
```

### 4.3 解读 /proc/pid/maps

`cat /proc/$$/maps` 每行格式：

```
起始地址-结束地址  权限  偏移  设备    inode   路径
7f8f00000000-7f8f00100000 r-xp 00000000 08:01 123456  /usr/lib/x86_64-linux-gnu/libc.so.6
```

| 字段 | 含义 |
|---|---|
| `7f8f00000000-7f8f00100000` | 虚拟地址区间（一段连续虚拟页） |
| `r-xp` | r 读 / w 写 / x 执行 / s 共享(shared) / p 私有(private) |
| `00000000` | 映射在文件中的偏移（文件映射才有意义） |
| `08:01` | 设备号（主:从） |
| `123456` | inode（0 = 匿名内存，如堆/栈） |
| 路径 | 对应的文件，或 `[stack]`、`[heap]`、`[vdso]`、`[vsyscall]` 等特殊段 |

**典型输出**（一个 shell 进程）：

```text
55f0d9c00000-55f0d9c01000 r-xp 00000000 08:01 4567      /bin/bash      ← .text
55f0d9e00000-55f0d9e01000 r--p 00001000 08:01 4567      /bin/bash      ← .rodata
55f0d9e01000-55f0d9e02000 rw-p 00002000 08:01 4567      /bin/bash      ← .data/.bss
55f0da000000-55f0da000000 rw-p 00000000 00:00 0         [heap]         ← 堆
7f3e00000000-7f3e00100000 r-xp 00000000 08:01 23456     libc.so.6      ← 共享库
7f3e00200000-7f3e00200000 rw-p 00000000 00:00 0         [anon]         ← 匿名 mmap
7ffe00000000-7ffe00001000 rw-p 00000000 00:00 0         [stack]        ← 栈
```

::: tip 阅读技巧
1. 同一 inode 出现多次 = 同一文件的不同段（.text 只读可执行、.data 可写）。
2. 权限列第一段 `r-x` 是代码；`rw-` 是数据/栈/堆；`r--` 是只读数据。
3. `[anon]`（无路径、无 inode）是 mmap 的匿名映射；`[stack]` 大小会随调用深度变化。
4. 想核对各段实际驻留内存，用 `cat /proc/pid/smaps`（每段带 RSS/PSS），或 `pmap -x $$` 一行式总览。
:::

## 5. 本章小结

- 分段按逻辑含义划分地址空间，段表记 base+limit；翻译 = `物理 = base + 段内偏移`，偏移超 limit 即段错误。
- 分页治碎片、分段好共享/保护 → **段页式**合体：先分段再分页，两次查表。
- x86-32 用 GDT（全局）/LDT（局部）描述段，现代 Linux 用平坦模型（忽略分段），内存管理核心是分页。
- Linux 用户态布局：`.text/.data/.bss`（来自可执行文件）→ heap（向上）→ mmap 区（共享库）→ stack（向下）。
- `/proc/pid/maps` 每行 = 一段虚拟地址区间，字段为 区间、权限、偏移、设备、inode、路径；`pmap`/`smaps` 看驻留细节。

## 6. 自测题

**1. 段表 base/limit 与页表条目本质区别？**
答：页表项只记"页→帧"（帧大小固定，无需 limit）；段表项必须记 base+limit，因为段长可变，越界判断依赖 limit，也承担了分段保护的职责。

**2. 段表：段0 base=900 limit=300，段1 base=5000 limit=700。求 (0, 250) 与 (1, 800) 的物理地址？**
答：(0,250)：250<300 → 900+250=1150。(1,800)：800>700 → 越界，segmentation fault。

**3. 为什么段页式能同时消除外部碎片又保留逻辑结构？**
答：段内再分页，段的大小由页填充，物理分配以页为单位 → 无外部碎片；段号+逻辑单元仍存在 → 保留共享/保护语义。

**4. x86 的段选择子 TI 位决定什么？GDT 与 LDT 区别？**
答：TI=0 时在 GDT 中索引（全局共享段），TI=1 时在 LDT 中索引（每进程私有段）。GDT 全局一张，LDT 每进程一张。

**5. Linux 为什么在 x86-64 上"淡化"分段、以分页为主？**
答：64 位地址空间足够大，分段主要价值（逻辑分区、共享、保护）用分页 + 权限位也能实现，且分段增加翻译复杂度。现代 Linux 采用平坦段模型，逻辑地址 ≈ 线性地址，分页承担全部内存管理。

**6. 写出 `/proc/pid/maps` 一行的格式，并解释 `r-xp` 与 `rw-p` 分别描述什么。**
答：格式为 `起始-结束 权限 文件偏移 设备号 inode 路径`。`r-xp`：可读、可执行、不可写、私有 → 典型 .text 代码段；`rw-p`：可读写、私有 → 数据段/堆/栈/匿名映射。

**7. 在 maps 中如何区分堆、栈、共享库？**
答：堆通常标记 `[heap]`；栈标记 `[stack]`；共享库是带路径（如 `/usr/lib/.../libc.so.6`）且 inode 非 0 的映射；匿名 mmap 无路径且 inode=0，显示 `[anon]`。

**8. `.bss` 段为什么不占可执行文件空间？运行时谁分配它的内存？**
答：.bss 只记录未初始化全局变量的**大小**（都是 0，无需存内容），故不占文件体积。运行时由内核在进程地址空间中建页，并按需映射（首访缺页补零，见 [虚拟内存与按需分页](/kb/os/内存/04-虚拟内存与按需分页/)）。
