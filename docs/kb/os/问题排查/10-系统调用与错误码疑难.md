::: abstract 本章定位
程序明明"权限够、文件在、内存还有"，系统调用却返回 `EAGAIN`/`EINTR`/`EMFILE`——errno 是内核写给用户态的"失败理由"，读不懂就无从下手。本篇把 syscall 进入/返回机制、errno 逐个拆解、strace/perf trace/bpftrace 三板斧、慢系统调用与阻塞、syscall 性能与 seccomp 全讲透。对应《Operating System Concepts》Ch2（系统结构）在真实生产里的每一种死法。
:::

排查系统调用失败，最怕的不是不会敲命令，而是**把 errno 当返回值读、把 EAGAIN 当致命错误、把 EINTR 当 bug**。先建立一张总地图：

```mermaid
flowchart TD
    A[系统调用失败] --> B{报什么错}
    B -->|EINTR / EAGAIN| C[信号打断 / 非阻塞重试<br/>§3 / §4]
    B -->|EMFILE / ENFILE| D[fd 耗尽<br/>ulimit / file-max]
    B -->|ENOSPC / EIO| E[磁盘满 / 文件系统坏<br/>[[09 文件系统与磁盘故障|09 篇]]]
    B -->|EACCES / EPERM| F[权限 / seccomp 拦截<br/>§2.7 / §8]
    B -->|ENOMEM| G[内存 / 映射上限<br/>[[08 虚拟内存与交换疑难|08 篇]]]
    B -->|ETIMEDOUT / EHOSTUNREACH| H[网络不通<br/>§2.9]
    B -->|EBADF / ENOTTY| I[fd 无效 / ioctl 用错<br/>§2.6 / §2.10]
```

## 1. 系统调用基础回顾

### 1.1 现象：返回值与 errno 混为一谈

新手最常见的错误：把 `errno` 当作函数的返回值打印。系统调用的返回约定是 **"返回值是结果，errno 是副作用"**：

```c
ssize_t n = read(fd, buf, sizeof(buf));
if (n < 0) {                       /* 这里读的是"返回值"，不是 errno */
    printf("errno=%d (%s)\n", errno, strerror(errno));
    perror("read");
}
```

::: warning -1 与 errno
Linux 上 glibc 封装后的规则：**成功返回 ≥ 0（或指针），失败返回 -1 并设置 errno**。而内核内部（syscall 层）的规则是：**成功返回 ≥ 0，失败返回 `-errno` 的负数**（如 -ENOENT = -2）。glibc 负责把内核的负数翻译成"返回 -1 + errno"的 C 接口。所以 strace 里看到的 `= -1 ENOENT` 已经是被 strace 翻译过的，千万别把 errno 数字当成返回值。
:::

### 1.2 工具：strace / perf trace / bpftrace

| 工具 | 代价 | 典型用途 |
|---|---|---|
| `strace` | 高（每条 syscall 都要上下文切换拦截） | 全量/按类/按 pid 跟踪，过滤 errno |
| `perf trace` | 中（用 tracepoint，批量输出） | 大规模看 syscall 流量，`--summary` 汇总 |
| `bpftrace` | 低（内核内聚合，不逐条转发用户态） | 计数 errno、聚合热点 syscall |

三者同源：都挂在 `sys_enter`/`sys_exit` tracepoint 上，**观察结果不会改变程序行为**，但 strace 的逐条转发会显著拖慢高频 syscall 的程序（见 §8）。

### 1.3 定位：一次 syscall 的进入与返回（x86_64）

```text
用户态               内核态
  mov $0, %rax  ───>  syscall 指令 ──>  entry_SYSCALL_64
  syscall                        （查 sys_call_table[rax]，#0=read）
  mov %rax, 返回值 <──  ret_from_syscall <──  返回：成功≥0 / 失败 -errno
```

要点：
- 系统调用号放 `%rax`，参数依次 `%rdi/%rsi/%rdx/%r10/%r8/%r9`，**入口只拷贝 <6 个参数**——所以 `openat` 这类参数多的调用要看表。
- 返回时：**内核返回负 errno**，glibc 封装里 `cmp $-4095, %rax` 判断失败区间（`-MAX_ERRNO .. -1`），失败则存 errno 并返回 -1。
- 相关内核参数都在 `/proc/sys/kernel/`：`threads-max`（clone 的 EAGAIN 上限）、`pid_max`、`sem`、`shmmni`、`msgmni`、`keys/maxkeys`——**"资源型" errno 十有八九要来这里对账**。

### 1.4 修复：让程序自己说人话

```c
errno_t err;                       /* C11 */
perror("open");                    /* open: No such file or directory */
strerror_r(errno, buf, sizeof(buf));
```

排查系统调用失败的第一条纪律：**任何失败先打印 errno 的字符串含义（`strerror`/`perror`），而不是只打印编号**。编号在不同架构/平台可能不同，字符串含义才是语义。

## 2. errno 高频疑难逐个拆解

### 2.0 先认识 errno 表（Linux x86_64）

errno 在 `<errno.h>` 中定义，编号 1–133（另有平台扩展）。高频疑难全集：

| errno | 值 | 含义 | 一句话场景 |
|---|---|---|---|
| EPERM | 1 | Operation not permitted | 操作本身不允许（缺 capability / seccomp） |
| ENOENT | 2 | No such file or directory | 路径/文件不存在 |
| EINTR | 4 | Interrupted system call | 慢系统调用被信号打断 |
| EIO | 5 | I/O error | 底层 IO 失败（硬件/文件系统） |
| EBADF | 9 | Bad file descriptor | fd 无效/已关闭/跨进程使用 |
| EAGAIN / EWOULDBLOCK | 11 | Resource temporarily unavailable | 非阻塞重试 / 资源暂缺 |
| ENOMEM | 12 | Cannot allocate memory | 内存分配/映射上限 |
| EACCES | 13 | Permission denied | 文件/路径访问权限不足 |
| ENFILE | 23 | Too many open files in system | **全系统**文件表耗尽 |
| EMFILE | 24 | Too many open files | **本进程** fd 表耗尽 |
| ENOTTY | 25 | Inappropriate ioctl for device | ioctl 用在不支持的对象上 |
| ENOSPC | 28 | No space left on device | 磁盘满 / inode 满 / 配额 |
| ETIMEDOUT | 110 | Connection timed out | 连接/读写超时（常因防火墙 DROP） |
| EHOSTUNREACH | 113 | No route to host | 目的主机不可达 |

::: note EAGAIN 与 EWOULDBLOCK 是同一个
在 Linux `<errno.h>` 中 `EWOULDBLOCK` 与 `EAGAIN` **值相同（11）**，宏别名。代码里两个都写（如 `errno == EAGAIN || errno == EWOULDBLOCK`）是为了可移植性。
:::

### 2.1 EAGAIN / EWOULDBLOCK（11）——重试，别当错误

- **含义**：现在做会阻塞/资源暂时没有，**换个时机可能成功**。
- **触发场景**：非阻塞 fd 上 read/accept/connect；socket 发送缓冲区满；`flock`/`semop` 带 `O_NONBLOCK`/`IPC_NOWAIT`；pthread mutex trylock；线程/进程创建超出 `RLIMIT_NPROC` 或 cgroup `pids.max`。
- **定位手段**：strace 看是否带 `O_NONBLOCK`、上下文是否是 trylock；`cat /proc/sys/kernel/threads-max`、`ps -eLf | wc -l` 对账线程数上限。
- **修复**：非阻塞 IO 应**短暂等待后重试**（poll/epoll 等待事件再读），而不是退出；线程创建 EAGAIN → 查 `pids.max`/`threads-max`/`ulimit -u`。细节见 §4。

### 2.2 EINTR（4）——被信号打断，不是真失败

- **含义**：阻塞中的"慢系统调用"（read/write/ioctl/futex/wait…）在等待期间收到信号并交付给了 handler。
- **触发场景**：`sleep()`/`read()` 被 SIGALRM/SIGCHLD/SIGTERM 打断；代码未设 `SA_RESTART`。
- **定位手段**：strace 输出 `= -1 EINTR (Interrupted system call)` 且前后能看到 `rt_sigaction` 设置了不带 SA_RESTART 的信号。
- **修复**：`sigaction` 加 `SA_RESTART`，或代码里显式重试。细节见 §3。

### 2.3 EMFILE / ENFILE（24 / 23）——fd 耗尽，两大等级

- **含义**：EMFILE = **本进程**打开文件数超过 `RLIMIT_NOFILE`（软限制，默认 1024）；ENFILE = **全系统**打开文件总数超过 `fs.file-max`（默认约 100 万）。
- **触发场景**：fd 泄漏（没 close）、高并发连接服务、线程数×每线程 fd 暴涨、file-max 被调小。
- **定位手段**：`ls /proc/PID/fd | wc -l` 数进程 fd；`lsof -p PID \| wc -l`；`cat /proc/sys/fs/file-nr`（已分配/空闲/上限三列）；`ulimit -n` 看软硬限制。
- **修复**：修 fd 泄漏是根本；临时缓解 `ulimit -n 65535`、`sysctl -w fs.file-max=10485760`。完整案例见 §10。

### 2.4 ENOSPC（28）——空间没了，但不只是磁盘

- **含义**：设备上没有可用空间。
- **触发场景**：磁盘满（`df -h`）；**inode 满**（小文件海量，`df -i`）；配额超限（`quota`，报 ENOSPC 或 EDQUOT）；NFS 服务端空间满。
- **定位手段**：`df -h` + `df -i` 分别看 block 和 inode；`du -x --max-depth=1 / | sort -h` 找大目录；`strace` 确认是哪个文件 `write/open` 失败。
- **修复**：清理空间/扩展磁盘/删 inode 占满的小文件；配额场景扩容 quota。

### 2.5 EIO（5）——底层 IO 真的坏了

- **含义**：底层存储/设备返回了无法恢复的错误。**这是最"硬"的错误，重试通常无效**。
- **触发场景**：坏盘/掉线 NFS、SSD 掉电、USB 拔出、文件系统损坏、dirty 页写回失败。
- **定位手段**：`dmesg -T \| tail -50` 看内核报错（ata/EXT4/NFS 等关键字）；`journalctl -k`；`smartctl -a /dev/sdX` 查健康度。
- **修复**：换盘/恢复 NFS 链路；文件系统损坏走 [fsck](/kb/os/问题排查/09-文件系统与磁盘故障/)；应用侧做好 EIO 的降级与重连。

### 2.6 EBADF（9）——fd 无效，多半是代码 bug

- **含义**：传入的 fd 在当前进程里不存在或已被 close。
- **触发场景**：double close、close 后再用、**fork 后把父进程 fd 当共享资源乱关**、跨线程 close 了别人正在用的 fd、环境里 fd 被工具关闭。
- **定位手段**：strace 精准抓：`strace -e trace=read,write,close,open -p PID`，看失败前后哪次 close 把 fd 关了。
- **修复**：修代码路径；坚持"谁 open 谁 close"；多线程共享 fd 要加锁或用 `dup` 隔离。

### 2.7 EACCES（13）与 EPERM（1）——"权限"的两层含义

| | EACCES | EPERM |
|---|---|---|
| 语义 | **访问权限**：文件/路径读不了 | **操作权限**：这个操作本身不被允许 |
| 场景 | open 无读/写权限、路径组件无 `x`、O_CREAT 到只读目录 | 缺 capability（CAP_*）、kill 他人进程、seccomp 拦截 |
| 经典 | `open("/etc/shadow", O_RDONLY)` → EACCES | `open(..., O_NOATIME)` 无 `CAP_FOWNER` → EPERM |

- **触发场景**：EACCES 查文件 mode/owner/ACL 与进程 euid 是否匹配；EPERM 查 `CapEff` 与 seccomp 状态。
- **定位手段**：`ls -l`、`namei -om 路径`（看每级目录权限）；`grep CapEff /proc/PID/status` + `capsh --decode`；`grep Seccomp /proc/PID/status`（2 = 过滤器模式，见 §8）。
- **修复**：EACCES 改权限/属主；EPERM 给 capability 或换用户；被 seccomp 拦截则调整 profile。

### 2.8 ENOMEM（12）——不是"内存用完"那么简单

- **含义**：内核无法满足该次分配/映射请求。注意与 OOM kill（SIGKILL，见 [内存篇](/kb/os/问题排查/03-内存与内存泄漏排查/)）不同——ENOMEM 是"**这次调用**失败"，进程还活着。
- **触发场景**：`mmap` 超过 `vm.max_map_count`（默认 65530，每个映射计 1）；`brk` 超 `RLIMIT_AS`；overcommit 被禁（`vm.overcommit_memory=2`）；`MAP_LOCKED` 超 `RLIMIT_MEMLOCK`。
- **定位手段**：strace 确认是哪个调用（mmap/brk）；`cat /proc/PID/maps \| wc -l` 对比 `max_map_count`；`ulimit -v`；`cat /proc/sys/vm/overcommit_memory`。
- **修复**：`sysctl -w vm.max_map_count=1000000`（高频坑）；释放进程虚拟内存；调整 overcommit 策略。详见 [篇](/kb/os/问题排查/08-虚拟内存与交换疑难/)。

### 2.9 ETIMEDOUT（110）与 EHOSTUNREACH（113）——网络故障分类

| errno | 内核判断 | 常见真实原因 |
|---|---|---|
| ETIMEDOUT | 重传超时/握手超时 | 防火墙 DROP（不回 RST）、路由黑洞、对端负载过高丢包 |
| EHOSTUNREACH | 收到 ICMP host unreachable | 路由表无目的网段、主机宕机、VPN 断开 |
| ECONNREFUSED（111） | 对端回 RST | 端口没监听/服务没起——**不是超时** |

- **定位手段**：`strace -e trace=connect -p PID` 看失败点；`ss -tnp` 看连接状态；`ping` + `traceroute` 区分"通不通"；防火墙侧查 DROP 计数。
- **修复**：ETIMEDOUT → 调防火墙放行/查中间链路；EHOSTUNREACH → 修路由；应用侧加重试与超时时间。

### 2.10 ENOTTY（25）——ioctl 用错对象

- **含义**：对不支持该 ioctl 的 fd 发了 ioctl（"Inappropriate ioctl for device"）。
- **触发场景**：把普通文件当 tty 做 `tcsetattr`/`TIOCGWINSZ`；stty 在非终端下执行；对 socket 发 tty ioctl。
- **定位手段**：strace 看 ioctl 的 fd 是什么文件：`ls -l /proc/PID/fd/&lt;n&gt;`；`strace -e trace=ioctl cmd=TIOCGWINSZ`（`strace -e ioctl=TIOCGWINSZ`）过滤。
- **修复**：先 `isatty(fd)` 再调 tty ioctl；脚本里 `[ -t 0 ]` 判断 stdin 是否是终端。

## 3. EINTR 深入：信号与慢系统调用

### 3.1 现象

strace 里隔三差五出现：

```text
read(3, ..., 4096)        = -1 EINTR (Interrupted system call)
```

网络服务里最常见：**请求处理到一半，进程收到 SIGCHLD/SIGALRM/SIGTERM（都配置了 handler），正在阻塞的 read/write 被立刻打断**。如果代码把 EINTR 当致命错误退出，就会看到"程序偶发退出一批"。

### 3.2 工具与定位：确认是信号打断

```bash
$ strace -e trace=read,rt_sigaction,rt_sigreturn -p 9001
rt_sigaction(SIGTERM, {sa_handler=0x... , sa_mask=..., sa_flags=0}, ...) = 0  # sa_flags=0，没有 SA_RESTART
read(3, "..."..., 4096) = -1 EINTR       # ← 被打断
rt_sigreturn()                            # ← 信号 handler 返回，read 不会再回来
```

关键线索：`rt_sigaction` 里 `sa_flags=0`（**没有设置 `SA_RESTART`**），则慢系统调用被打断后不重启。

### 3.3 机制：SA_RESTART 与 restart_block

内核处理信号时，在 `arch_do_signal`/`get_signal` 返回路径上决定被打断的 syscall 是否重启：

```text
阻塞中的 read ──收到信号──> 内核记录被打断 ──> 交付信号给 handler
                                                    │
                              SA_RESTART? 是 ──> 自动重放 syscall（参数保存在 pt_regs/restart_block）
                                           否 ──> 返回 -EINTR 给用户态
```

- **SA_RESTART 已设置**：`sigaction` 时置 `sa_flags |= SA_RESTART`，绝大多数系统调用（read/write/open/ioctl/futex…）被打断后**内核自动重启**，用户态根本看不到 EINTR。
- **特殊情况**：`poll/select/epoll_wait/epoll_pwait/nanosleep` 这类**即使设了 SA_RESTART 也照样返回 EINTR**（历史上就不支持自动重启），必须显式重试。
- **restart_block**：`task_struct->restart_block` 保存"从哪继续"的恢复点（如 nanosleep 剩余时间、futex 等待的地址），SA_RESTART 重启走的就是它。可用 `cat /proc/PID/syscall` 看到当前执行中的系统调用号与参数。

### 3.4 修复：两条路

```c
/* 方式一：让内核自动重启 */
struct sigaction sa = { .sa_handler = on_sig };
sigemptyset(&sa.sa_mask);
sa.sa_flags = SA_RESTART;
sigaction(SIGTERM, &sa, NULL);

/* 方式二：用户态显式重试（for poll/select/epoll_wait 等） */
ssize_t n;
do {
    n = read(fd, buf, sizeof(buf));
} while (n < 0 && errno == EINTR);
```

::: tip 为什么"写了 EINTR 处理"很重要
Java 生态不需要关心（JVM 屏蔽），但 C/C++ 必须自己写：SIGCHLD、SIGALRM、SIGWINCH、SIGTERM 这类"温和"信号一旦有 handler，就会把阻塞的 read/write/sleep 打断。**不处理 EINTR = 业务被任何一次信号随机打断**，且并发下偶发、极难复现。
:::

## 4. EAGAIN 深入：非阻塞 IO 与资源暂缺

### 4.1 现象

```text
accept(3, ...) = -1 EAGAIN (Resource temporarily unavailable)
send(4, ..., 8192, MSG_NOSIGNAL) = -1 EAGAIN
```

### 4.2 触发场景全集

| 场景 | 含义 | 处理 |
|---|---|---|
| `O_NONBLOCK` 的 fd 上 read/recv 无数据 | 现在没数据 | poll/epoll 等就绪再读 |
| `O_NONBLOCK` 的 fd 上 accept 无新连接 | 现在没连接 | 等可读事件 |
| 非阻塞 connect 建立中 | 连接还在进行 | 等可写事件 + `getsockopt(SO_ERROR)` 查结果 |
| socket 发送缓冲满 | 对端消费慢 | 等可写事件/调大 `SO_SNDBUF`/TCP 背压 |
| `flock(LOCK_NB)`/`semop(IPC_NOWAIT)`/mutex trylock | 锁被占 | 短暂退避重试 |
| `clone`/`fork`/`pthread_create` | `RLIMIT_NPROC`/`pids.max`/`threads-max` 超限 | 查 pids cgroup 与 ulimit -u |

### 4.3 定位手段

```bash
# 看调用是不是"非阻塞"上下文
$ strace -e trace=read,accept,recvfrom,sendto -p 9001
# 线程数上限三件套
$ ulimit -u && cat /proc/sys/kernel/threads-max && cat /sys/fs/cgroup/pids.max 2>/dev/null
```

### 4.4 修复：编程误区清单

- **误区一**：把 EAGAIN 当错误直接退出。非阻塞 IO 的 EAGAIN 是**正常流程**，应等事件重试。
- **误区二**：EAGAIN 与 EWOULDBLOCK 只判断一个（Linux 上相同，可移植写法两个都判）。
- **误区三**：`strerror` 看 EAGAIN 是 "Resource temporarily unavailable" 就以为内存不够——**EAGAIN 几乎与内存无关**（内存相关是 ENOMEM）。
- **误区四**：线程创建失败报 `pthread_create: Resource temporarily unavailable` 就只查内存——先查 `pids.max` 与 `nproc`，线程数常常是元凶。

## 5. 系统调用失败排查实操

### 5.1 现象

应用偶发报错，日志只有"Permission denied / No such file"，但代码路径完全看不出问题——**需要用系统调用级证据还原"内核看到的真相"**。

### 5.2 工具：strace 过滤与跟踪

```bash
# 只看文件类系统调用（open/openat/stat/access…），立刻暴露 EACCES/ENOENT
$ sudo strace -e trace=file -p 9001

# 跟随 fork/execve 的子进程（多进程/守护进程）
$ sudo strace -f -p 9001

# 只看网络类
$ sudo strace -e trace=network -p 9001

# 只看失败的系统调用（strace ≥ 5.16，-Z/--failing）
$ sudo strace -Z -e trace=file -p 9001
```

::: tip 启动时抓 vs 运行时抓
抓不到的偶发错误用 `-f` 从进程**启动就**跟踪（`strace -ff -o /tmp/trace -e trace=file ./app`），`-ff` 会为每个子进程/线程生成独立文件，多线程排查必备。
:::

### 5.3 定位：统计失败分布

```bash
$ sudo strace -c -p 9001 -- timeout 10
% time     seconds  usecs/call    calls     errors syscall
------ ----------- ----------- --------- --------- ----------------
 42.00    0.120000         24       5000      4500 epoll_wait
 38.00    0.100000         10      10000         0 read
 18.00    0.050000         50       1000        900 openat     ← 90% 失败！
```

`errors` 列直接告诉你哪个 syscall 在大量失败，配合 `-e trace=` 缩小范围再看单条。

### 5.4 修复 + 另两把刀

```bash
# perf trace：代价比 strace 低，适合生产；--summary 汇总
$ sudo perf trace -p 9001 --summary

# bpftrace：内核内聚合，统计各进程各 errno 失败计数
$ sudo bpftrace -e '
    tracepoint:raw_syscalls:sys_exit /args->ret < 0/ {
        @[comm, args->id, -args->ret] = count();   /* -ret 即 errno 正数 */
    }'
```

结论统一：**先用 `-c` 看哪类失败多，再 `-Z`/`-e trace=` 缩小，最后 bpftrace 抓全机器维度**。`args->ret < 0` 是 sys_exit 里内核原始返回（负 errno），`-args->ret` 恰好还原成 errno 编号，可与 §2.0 表对照。

## 6. 慢系统调用与阻塞

### 6.1 现象

进程状态是 `S`（可中断睡眠）或 `D`（不可中断睡眠），`top` 里 CPU 几乎为 0，但任务就是不完成——**它阻塞在某个系统调用里**。

### 6.2 工具：strace -p 与 /proc

```bash
# 附加后立刻"定格"在阻塞点
$ sudo strace -p 9001
futex(0x7f00000003e8, FUTEX_WAIT_PRIVATE, 2, NULL) = ?   ← 卡在这里，等锁
```

```bash
# 不装工具看内核函数与系统调用
$ cat /proc/9001/wchan          # 内核函数
futex_wait_queue_me
$ cat /proc/9001/syscall        # 正在执行的第几条系统调用 + 参数
202 0x7f... 2 0 0 0 0
$ cat /proc/9001/status | grep -E '^(State|SigBlk)'
State:  S (sleeping)
```

| wchan | 阻塞在 | 说明 |
|---|---|---|
| `futex_wait_queue_me` | futex 锁等待 | 用户态锁竞争，见 [并发与异常排查](/kb/os/问题排查/05-并发与异常排查/) |
| `pipe_read` / `wait_woken` | 管道/管道缓冲 | 读端等生产者 |
| `poll_schedule_timeout` | poll/epoll 等待 | 等 IO 事件 |
| `do_blockdev_read` / `xfs_buf_wait` | 块设备/文件系统 | 磁盘 IO，常伴随 D 状态 |

### 6.3 定位：S 与 D 的关键区分

```bash
$ ps -eo pid,stat,wchan:24,comm | grep -E '^ *9001'
 9001 D    xfs_buf_wait  mysqld
```

- **S（可中断睡眠）**：能被信号唤醒，说明阻塞是"可协商的"（锁、等待队列、管道）。
- **D（不可中断睡眠）**：内核 IO 路径上不响应信号，`kill -9` 也杀不掉，只能等 IO 完成或重启。典型 = 卡在坏盘/NFS 挂起/存储阵列无响应。

### 6.4 修复

- 锁等待 → 定位持有方（[wchan + 栈](/kb/os/问题排查/05-并发与异常排查/)）。
- D 状态 → 看 `iostat -x 1` 的 `%util`/`await` 与 `dmesg`（IO 超时/掉盘），与 [进程与调度篇的 D 状态](/kb/os/问题排查/07-进程与调度异常疑难/) 联动排查；修复点在存储层。
- `read`/`poll` 阻塞 → 检查是否该用超时（`SO_RCVTIMEO`/`poll(timeout)`）约束阻塞上限，避免"永远挂死"。

## 7. 常见系统调用族定位

### 7.1 现象

七大类系统调用失败各有各的"长相"，先背住每族的失败语义，排查时按图索骥：

| 系统调用族 | 常见失败 errno | 典型含义 |
|---|---|---|
| `open`/`openat` | ENOENT·EACCES·EMFILE·ENFILE·EISDIR·ENOSPC | 路径不存在/无权限/fd 表满/系统文件表满/是目录/所在 fs 满 |
| `read`/`write` | EAGAIN·EBADF·EINTR·EIO·ENOSPC | 非阻塞无数据/fd 无效/被信号打断/硬件坏/写满 |
| `close` | EBADF·EINTR | 关了个不存在的 fd /（历史遗留）可被信号打断 |
| `ioctl` | ENOTTY·EINVAL | 对象不支持/参数非法 |
| `futex` | EAGAIN·ETIMEDOUT·EINTR | 值已变/超时/被打断（futex 等待锁） |
| `brk` | ENOMEM | 堆增长失败 |
| `mmap` | ENOMEM·EAGAIN·ENOMEM | 超 max_map_count/超 RLIMIT_AS /MAP_LOCKED 超限 /超 memlock |
| `mprotect` | EACCES·EINVAL·ENOMEM | 对不可写源页改保护/参数非法/内核结构分配失败 |
| `madvise` | EINVAL·ENOMEM | 建议值非法·地址未页对齐/映射区间非法 |

### 7.2 工具与定位：fd 泄漏到 EMFILE

```bash
$ ls /proc/9001/fd | wc -l        # 当前 fd 数，快速定位泄漏
$ ls -l /proc/9001/fd | grep -c 'socket'
$ lsof -p 9001 | wc -l
$ ulimit -n                       # 软限制（决定 EMFILE 阈值）
```

定位链：**EMFILE 出现 → 先看 fd 总数是否逼近 `ulimit -n` → 若逼近，`lsof -p PID` 看重复 fd 的类型（socket 最多 → 连接泄漏）→ 对应用代码排查未 close 路径**。

### 7.3 修复要点

- **fd 泄漏**：加 close/RAII/`try-with-resources`；用 `valgrind --track-fds=yes` 自动报泄漏 fd 点。
- **futex 与锁**：大量 `futex` + EAGAIN = 锁竞争（[并发与异常排查](/kb/os/问题排查/05-并发与异常排查/)）；进程卡在 futex 用 wchan + 用户态栈找持有者。
- **madvise 性能**：JVM/大内存应用常用 `MADV_DONTNEED` 释放回 page cache；若它返回失败导致内存回收异常，先查地址是否合法映射（`/proc/PID/maps`）。它是性能优化指令，一般不会让程序崩，但**高频调用本身就是热点**（见 §8）。

## 8. 系统调用性能与安全

### 8.1 现象一：系统调用风暴

进程 CPU 高、但业务没进展；`perf top` 里全是 `do_syscall_64` 和 `sys_*` 函数——**CPU 烧在频繁进出内核上**。典型：无脑轮询、每字节一次 write、日志每次 flush。

### 8.2 工具与定位

```bash
# 看系统调用 TOP（calls 列）
$ sudo strace -c -f -p 9001 -- timeout 5
$ sudo perf trace -p 9001 --summary

# 内核侧看热点是否在 syscall 入口
$ sudo perf top
```

### 8.3 修复

| 症状 | 对策 |
|---|---|
| 高频 `write` 一次一字节 | 缓冲区攒批（`fwrite`/`iov` 批量 writev） |
| 高频 `read` 轮询（忙等） | 改事件驱动 poll/epoll |
| 高频 `clock_gettime`/`gettimeofday` | 用 `vDSO`（glibc 自动，确认没被 strace/old glibc 拖慢） |
| 高频 `futex` EAGAIN | 锁竞争，见 [并发与异常排查](/kb/os/问题排查/05-并发与异常排查/) |

::: warning strace 自身会放大风暴
strace 逐条转发会成倍放大高频 syscall 的延迟——**线上别对关键进程长跑 strace**，用 `perf trace`（tracepoint 聚合）或 bpftrace 替代；只做短时快照。
:::

### 8.4 现象二：seccomp 拦截导致 EPERM

代码跑在容器里突然报 EPERM，宿主机上同样的二进制却正常——**多半是 seccomp 过滤器把某个系统调用拒了**。

```bash
$ grep Seccomp /proc/9001/status        # 2 = 处于过滤模式
Seccomp:  2
$ sudo strace -e trace=all -p 9001      # 找到返回 EPERM 的那条
kexec_load(0x0, 0x0, 0, 0x0, 0) = -1 EPERM (Operation not permitted)
```

### 8.5 定位与修复

- **Docker 默认 seccomp profile**：容器内屏蔽约 44 个危险 syscall（`mount`/`reboot`/`kexec_load`/`swapon`/`ptrace` 等），触发即 EPERM。
- **systemd sandboxing**（`SystemCallFilter=`）、Chrome 沙箱同理。
- **修复**：确认业务真的需要该 syscall → 用 `--security-opt seccomp=unconfined` 或自定义 profile 放行；不需要就改代码绕开。capability 不足导致的 EPERM 则是另一回事（`CapEff`/`capsh --decode` 对账，见 §2.7）。机制细节见 [安全](/kb/os/安全/05-安全防御与审计/) 与 [安全机制](/kb/os/Linux/14-Linux安全机制内核原理/)。

::: note 排查顺序口诀
一个系统调用失败：① strace 确认哪条、哪个 errno；② 对照 §2.0 表定"资源类/权限类/网络类/IO 类"；③ 资源类查 `/proc/sys/`、`ulimit`、cgroup；权限类查 mode/`CapEff`/seccomp；④ 网络类看 ss/dmesg 区分超时与拒绝；⑤ 修复后 `strace -Z` 复跑确认该 errno 不再出现。
:::

## 9. 本章小结

- **errno 不是返回值**：内核返回 `-errno`，glibc 包装成"返回 -1 + errno"；`perror`/`strerror` 先读懂含义再动手。
- **EINTR**：慢系统调用被信号打断，`SA_RESTART` 自动重启（poll/select/epoll_wait/nanosleep 除外需显式重试）。
- **EAGAIN/EWOULDBLOCK**：非阻塞 IO 的正常信号，等事件重试；线程创建 EAGAIN 查 `pids.max`/`threads-max`。
- **EMFILE/ENFILE**：进程 fd 表 vs 全系统文件表两个水位，`/proc/PID/fd` + `lsof` + `ulimit -n` + `fs.file-max`。
- **EACCES vs EPERM**：访问权限 vs 操作权限；EPERM 优先查 capability 与 seccomp（容器内高发）。
- **阻塞定位**：`strace -p` 定格阻塞点，`wchan` 看内核函数，S 可唤醒/D 只能等 IO。
- **工具组合**：`strace -e/-c/-Z/-f` 精细化 → `perf trace` 低代价 → `bpftrace` 内核聚合。

## 10. 实战演练：程序频繁报 EMFILE 的全过程

::: note 场景
网关服务 prod-gw 上线后日志疯狂刷 `open(...): Too many open files`，连接开始被拒。从现象到根因，走一遍完整链路。
:::

**第 1 步：确认 errno 与失败 syscall（strace 抓现行）**

```bash
$ sudo strace -Z -e trace=open,openat,accept -p 8231 -- timeout 3
openat(AT_FDCWD, "/proc/self/maps", O_RDONLY) = -1 EMFILE (Too many open files)
```

解读：`-Z` 只打印失败的调用，EMFILE 实锤，失败在 open 上。

**第 2 步：数 fd，量化"多到什么程度"**

```bash
$ ls /proc/8231/fd | wc -l
1024
$ ulimit -n
1024
```

解读：fd 数恰好顶着软限制 1024——**本进程 fd 表满了**，这就是 EMFILE 的直接原因。

**第 3 步：区分进程级与系统级水位**

```bash
$ cat /proc/sys/fs/file-nr
20480      0      1000000
```

解读：三列是"已分配 / 未使用 / 上限"，`20480/1000000` 说明系统级 far from full → **问题在本进程**，不是 ENFILE，`file-max` 不用动。顺手把 `/proc/sys/kernel/` 也排除（threads-max 正常，不是线程数问题）。

**第 4 步：找 fd 都去哪了（lsof 分类）**

```bash
$ lsof -p 8231 | awk '{print $5}' | sort | uniq -c | sort -rn
  880  socket
  120  cwd
   24  regular file
```

解读：880 个 socket——**连接泄漏**。每进来一个客户端只建不关。

**第 5 步：追踪连接从哪泄漏（strace 看 accept→close 配对）**

```bash
$ sudo strace -e trace=accept4,close -f -p 8231 -- timeout 5 | \
    awk '/accept4/ {a++} /close/ {c++} END {print "accept="a, "close="c}'
accept=152  close=96
```

解读：5 秒 accept 152 次但 close 只有 96 次，差值 56 正是每秒泄漏的 fd 数——**某个业务分支 accept 后忘了 close**。

**第 6 步：修代码 + 验证**

```bash
# 修复：业务分支补 close / 用 RAII / 限制并发连接数
# 验证：发版后
$ ls /proc/8231/fd | wc -l
132      # 稳定在业务连接数，不再增长
```

**复盘**：strace `-Z` 确认 errno → `ulimit -n` 确认进程级阈值 → `file-nr` 排除系统级 → `lsof` 分类定位到 socket → `strace` 数 accept/close 配对锁定泄漏分支 → 补 close 验证。**EMFILE 排查铁律：先分清进程/系统两个水位，再追 fd 去向，最后找不配对。**

## 11. 自测题

1. **strace 显示 `open(...) = -1 ENOENT`，但文件明明存在，可能是什么？** 路径里有相对路径被 chdir 影响、或上一级目录无 `x` 权限导致找不到（实际报 EACCES 更常见于此），或文件名大小写/符号链接断开；先 `ls -l` 逐级 `namei -l` 验证。
2. **EAGAIN（11）与 ENOMEM（12）的区别？** EAGAIN=资源暂时不可用，稍后重试即可成功（非阻塞 IO、锁被占、线程数上限）；ENOMEM=本次分配/映射在策略上就满足不了（max_map_count、RLIMIT_AS、overcommit）。
3. **为什么 `nanosleep` 即使设了 `SA_RESTART` 被信号打断还是返回 EINTR？** 因为内核明确支持"自动重启"的系统调用集合里**不含** nanosleep/poll/select/epoll_wait，这类必须用户态显式重试（对比剩余时间重新 sleep）。
4. **EACCES 与 EPERM 各举一典型 open 场景。** EACCES：`open("/etc/shadow", O_RDONLY)` 无读权限；EPERM：`open(..., O_NOATIME)` 且无 `CAP_FOWNER`。
5. **EMFILE（24）与 ENFILE（23）的定位入口各是什么？** EMFILE 查进程：`ls /proc/PID/fd | wc -l` 对比 `ulimit -n` + `lsof`；ENFILE 查系统：`cat /proc/sys/fs/file-nr` 对比 `fs.file-max`。
6. **非阻塞 connect 返回什么？如何拿最终结果？** 立即返回 `EINPROGRESS`；用 poll/epoll 等可写事件后 `getsockopt(fd, SOL_SOCKET, SO_ERROR, &err)` 读结果（0=成功，否则是对应的 errno）。
7. **容器里 syscall 报 EPERM 但宿主机正常，优先查什么？** 先 `grep Seccomp /proc/PID/status`（=2 表示被 seccomp 过滤），再用 strace 定位是哪条 syscall 被拒，最后调整 Docker/Systemd 的 seccomp profile 或改代码绕开。
8. **一个 errno 对应多种可能，最快收敛法？** 先 `strace -Z` 复现并锁定"哪条 syscall + 哪个 errno"，对照 §2.0 分类为资源/权限/网络/IO 四类之一，再查对应 `/proc/sys/`、`ulimit`、`ss/dmesg`。
