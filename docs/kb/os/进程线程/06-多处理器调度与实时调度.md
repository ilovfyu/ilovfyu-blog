::: abstract 本章定位
单核调度算法解决"谁先上 CPU"，多核时代还要解决"进程放在哪个核上、核之间怎么分工"；实时系统则要求"期限（deadline）必须满足"，需要数学保证而非尽力而为。本章覆盖多处理器调度（SMP/亲和性/负载均衡）、实时调度（RMS/EDF + 可调度性测试手算），最后落地到 Linux 的 CFS 与实时调度类。
:::

## 1. 多处理器调度类型

### 1.1 非对称 vs 对称

| | 非对称多处理（ASMP） | 对称多处理（SMP） |
|---|---|---|
| 分工 | 一个主处理器运行调度/内核代码，其余只跑用户程序 | **所有处理器对等**，各自可调度、可跑内核代码 |
| 实现 | 简单，主核是唯一入口 | 复杂，需要处理同步（抢锁） |
| 现代系统 | 少见（如某些嵌入式） | **主流**（所有 PC/服务器/手机） |

### 1.2 SMP 的两种队列组织

| 模型 | 说明 | 优缺点 |
|---|---|---|
| 公共就绪队列 | 所有 CPU 共享一个队列 | 负载均衡天然好，但队列是共享数据结构需要锁，成为瓶颈 |
| 每 CPU 一个就绪队列 | 每个核有自己队列 | 免锁、cache 友好（进程留在本核），但负载可能不均，需要"拉取/推送" |

::: important 现代 Linux 采用每 CPU 队列
每个 CPU 有自己的 runqueue，进程天然亲和到某个核。负载不均衡时通过负载均衡器迁移进程（见 1.4）。这是"局部快、整体匀"的经典取舍。
:::

## 2. 处理器亲和性（Processor Affinity）

### 2.1 问题

进程在核 A 上跑过后，A 的 L1/L2 cache 里存着它的数据。若下次被调度到核 B，缓存全失效，性能暴跌。

### 2.2 亲和性

::: tip 软亲和 vs 硬亲和
- **软亲和（soft affinity）**：系统**尽量**把进程留在原核，但不保证（调度器可迁移）。Linux 默认行为。
- **硬亲和（hard affinity）**：通过系统调用把进程**钉死**在某些核上，其他核绝不运行它。
:::

```bash
# 查看/设置硬亲和性（taskset）
taskset -pc $$           # 查看当前 shell 允许跑在哪些核
taskset -c 0,1 ./myprog  # 限制 myprog 只在核 0、1 上跑
# 查看进程实际所在核（sched_getcpu 或 ps）
ps -eo pid,comm,psr | head   # psr 列 = 当前所在 CPU 编号
```

### 2.3 内核态观察

```c
// C 语言查看当前 CPU（glibc）
unsigned cpu = sched_getcpu();
```

| 机制 | 类型 | 作用 |
|---|---|---|
| 调度器默认"留在原核" | 软亲和 | 提升 cache 命中 |
| `sched_setaffinity` | 硬亲和 | 用户强制指定核集 |
| NUMA 感知 | 亲和 | 优先访问本地内存（见 [内存性能与系统调优](/kb/os/内存/06-内存性能与系统调优/)） |

::: warning 亲和性的代价
亲和性保住了 cache，却可能造成负载不均：某核满负荷、其他核空闲。因此亲和性必须与负载均衡配合，不能只靠亲和。
:::

## 3. 负载均衡（Load Balancing）

### 3.1 为什么需要

每 CPU 一个就绪队列 → 某个核队列排长龙，其他核空转。负载均衡把进程从拥挤的核搬到空闲的核。

### 3.2 两种机制

| 机制 | 方向 | 说明 |
|---|---|---|
| 推式迁移（push migration） | 负载重的核 → 空闲核 | 内核周期性检查各核负载，超阈值就把进程推出去 |
| 拉取迁移（pull migration） | 空闲核 ← 拥挤核 | 空闲核主动去拥挤队列"偷"任务（work stealing） |

### 3.3 代价与平衡

::: important 亲和性 vs 负载均衡的拔河
迁移（migration）会破坏亲和性：进程搬到新核，旧核的 cache 白填了。所以调度器要权衡：**cache 收益 vs 负载收益**。现代 Linux 的做法是"先尽量局部平衡，局部实在不平衡才跨核迁移"。
:::

## 4. 多线程多核调度（多核线程调度）

现代系统把"线程"直接映射到"核"。相关要点：

- **超线程（Hyper-Threading）**：一个物理核提供两个逻辑核（共享执行单元与部分 cache），调度器把逻辑核当作独立 CPU 用。
- **cache 共享**：同核的两个超线程共享 L1/L2，亲和性更有意义。
- **同进程多线程的调度策略**：可以分配到同一核（共享 cache、但无法并行）或不同核（并行、cache 各自独立）。Linux 由 CFS 的负载均衡自动决定，开发者可用亲和性干预。

## 5. 实时调度（Real-Time Scheduling）

### 5.1 硬实时 vs 软实时

| | 硬实时（Hard RT） | 软实时（Soft RT） |
|---|---|---|
| 期限要求 | **必须**在期限内完成，错过 = 灾难 | 尽量按时，偶尔错过可接受 |
| 例子 | 汽车刹车控制、心脏起搏器、导弹制导 | 多媒体播放、在线游戏、VoIP |
| 调度保证 | 需要数学可调度性测试 | 尽力而为 + 高优先级 |
| 代表算法 | RMS、EDF | Linux 的实时调度类 |

实时任务的模型：**周期任务**（periodic）每个周期 T 到达一次，需在周期内运行 C 时间（C ≤ T），利用率 U = C/T。

### 5.2 单调速率调度 RMS（Rate-Monotonic Scheduling）

::: important RMS 规则与性质
**规则**：优先级 = 周期反比（周期越短优先级越高），静态优先级（运行期不变）。
**静态优先级的抢占式最优**：教材证明，对周期性任务，RMS 是静态优先级方案中的最优。
**可调度性测试（充分条件）**：n 个周期任务，若

:::```
> U = Σ(Cᵢ/Tᵢ) ≤ n·(2^(1/n) − 1)
> ```
> 则一定可调度（保证所有期限满足）。
> - n=1：上界 1.0；n=2：0.828；n=3：0.780；n→∞：ln 2 ≈ 0.693。

### 5.3 手算：RMS 可调度性测试

**例题**：两个周期任务：

| 任务 | 周期 T | 执行时间 C | 利用率 C/T |
|---|---|---|---|
| T1 | 4 | 1 | 0.25 |
| T2 | 5 | 2 | 0.40 |

- 总利用率 U = 0.25 + 0.40 = **0.65**
- 上界（n=2）= 2·(√2 − 1) ≈ **0.828**
- 0.65 ≤ 0.828 → **可调度** ✓（RMS 保证两任务都能在期限内完成）

**反例**（RMS 测试失败的场景）：T1=(5, 3)，T2=(6, 2)：

- U = 3/5 + 2/6 = 0.6 + 0.333 = **0.933**
- 0.933 > 0.828 → **不满足 RMS 充分条件**（可能仍可调度，但 RMS 测试无法保证）

::: warning RMS 测试是"充分条件"不是"必要条件"
不满足测试公式 ≠ 一定不可调度，只是 RMS 无法保证。教材指出，RMS 利用率上界随任务数增加下降，即任务越多，RMS 能保证的负载上限越低（极限 69.3%）。
:::

### 5.4 EDF：最早截止期限优先

::: important EDF 规则与性质
**规则**：**动态优先级** = 截止期限（deadline）越近优先级越高，抢占式。
**可调度性测试（充分必要条件）**：只要总利用率 **U = Σ(Cᵢ/Tᵢ) ≤ 1**，EDF 就能保证所有期限满足。
EDF 比 RMS 更优：利用率上限 100%，且是"最优"调度算法（在可调度的前提下没有它做不到的）。
:::

**同例题用 EDF**：
- U = 0.65 ≤ 1 → **可调度** ✓
- 对反例 T1=(5,3)、T2=(6,2)：U = 0.933 ≤ 1 → **EDF 可调度** ✓（此时 RMS 测试却失败了）

**手算 EDF 排程**（T1=(4,1), T2=(5,2)），0 时刻两者同到，先截止者先跑：

```
t=0   T1 截止于4     T2 截止于5
      [T1]→(0-1, 完成)  
      T2 截止5 → (1-3, 完成)
t=4   T1 又到，截止8 → 跑 4-5
t=5   T2 又到，截止10 → 跑 5-7
t=8   T1 截止12 → 8-9
t=10  T2 截止15 → 10-12
      ... 每个任务都在自己周期内完成 ✓
```

| 对比 | RMS | EDF |
|---|---|---|
| 优先级 | 静态（周期定死） | 动态（按最新截止期） |
| 可调度上界 | n(2^(1/n)−1)，趋于 0.693 | 1.0（100%） |
| 测试性质 | 充分条件 | 充要条件 |
| 实现开销 | 低（优先级固定） | 高（每次要重排） |
| 适用 | 硬实时、任务集固定 | 任务集变化、希望更高利用率 |

::: tip 面试一句话
RMS 靠"短周期高优先"加静态优先级，简单但利用率上限低；EDF 靠"谁快死谁先跑"，动态重排但能压榨到 100% 利用率。Linux 的实时调度类本质是 RMS 式的固定优先级，不是 EDF。
:::

## 6. Linux 的 CFS 与实时调度类

### 6.1 调度策略总览

Linux 每个任务属于一个**调度类（scheduling class）**，内核按类别的优先级依次调度：实时类 > CFS 类 > idle 类。

```bash
chrt -l
# SCHED_OTHER : CFS（普通任务，默认）
# SCHED_FIFO  : 实时，先来先跑（非抢占，除非高优先级实时任务到达）
# SCHED_RR    : 实时，轮转时间片（实时任务间的 RR）
```

| 调度策略 | 类别 | 优先级 | 语义 |
|---|---|---|---|
| `SCHED_OTHER` | CFS（公平） | nice −20~19（默认 0） | 完全公平：按虚拟运行时间 vruntime 分 CPU |
| `SCHED_FIFO` | 实时（1–99） | 数字大者高 | 无时间片，只要不阻塞就永久占 CPU |
| `SCHED_RR` | 实时（1–99） | 数字大者高 | 同优先级之间按时间片轮转 |
| `SCHED_IDLE` | 极低优先级 | — | 仅在系统空闲时运行 |

### 6.2 CFS：完全公平调度器

::: important CFS 核心机制
不用"固定时间片"，而是给每个调度实体一个**虚拟运行时间 vruntime**：实际运行时间按权重折算（nice 值越小权重越大，同样跑 1ms，低 nice 进程 vruntime 增长更慢）。就绪队列用**红黑树**按 vruntime 排序，**每次选 vruntime 最小的跑**——谁"欠的 CPU 越多"谁先上，实现完全公平。
:::

```
就绪实体按 vruntime 排序（红黑树）：
       ┌──────┐
       │P2  v8│
      /        \
 ┌────┐        ┌────┐
 │P1 v5│       │P3 v12│
 └────┘        └────┘
   ↑ vruntime 最小 → 下一个被调度
```

- 新任务 vruntime 很小 → 一进来就能抢占（响应快）。
- 实时任务（`SCHED_FIFO`/`SCHED_RR`，优先级 1–99）**永远优先于** CFS 任务，所以普通用户进程不会被实时进程饿死之外的问题困扰。
- 可调参数在 `/proc/sys/kernel/sched_*`（如 `sched_latency_ns` 目标调度延迟）。

```bash
# 实验：改 nice 值观察 vruntime 分配
nice -n -5 sleep 60 &    # 高优先级
nice -n  5 sleep 60 &    # 低优先级
top -p $(pgrep -f 'sleep 60')   # 看 NI 与 CPU%
```

::: warning 小心 SCHED_FIFO
`SCHED_FIFO` 实时任务若不主动让出，会**无限期霸占 CPU** 导致系统卡死（连 shell 都反应不过来）。运行它前先想好退出方式：

:::```bash
> sudo chrt -f -p 99 $$      # 把当前 shell 变成实时（高危演示，慎用）
> # 补救：另一个终端执行  sudo chrt -f -p 0 &lt;pid&gt; 降回普通
> ```

### 6.3 现实世界的调度梯队

```
CPU 时间分配顺序：
  1. 实时调度类（SCHED_FIFO / SCHED_RR，优先级 1–99）
  2. 公平调度类（SCHED_OTHER = CFS，nice 控制权重）
  3. 空闲调度类（SCHED_IDLE）
```

这正对应教材里"优先级调度 + 多级队列"的现代实现：**高优先级实时任务优先、普通任务靠 CFS 公平、极端低优先靠 SCHED_IDLE 垫底**。

## 7. 本章小结

- 多处理器调度主流是 SMP，每 CPU 就绪队列 + 负载均衡；亲和性保 cache、负载均衡保公平，二者要权衡。
- 实时调度分硬/软：硬实时要可调度性测试。RMS 静态优先级、上限 n(2^(1/n)−1)；EDF 动态优先级、上限 100%，更优。
- Linux：CFS（vruntime 红黑树，nice 定权重）公平调度普通任务，SCHED_FIFO/SCHED_RR（1–99）满足实时需求。

## 8. 自测题

1. **软亲和与硬亲和的区别？** 软亲和是调度器"尽量"留在原核（不保证）；硬亲和用 `sched_setaffinity`/`taskset` 强制钉在指定核上。
2. **为什么需要负载均衡？** 每 CPU 独立就绪队列时，可能某核爆满、某核空闲；均衡用推/拉迁移把负载搬到空闲核。
3. **亲和性与负载均衡冲突时怎么办？** 迁移会破坏 cache，所以先做局部均衡，必要时才跨核迁移（调度器按阈值权衡）。
4. **RMS 的可调度性测试公式与含义？** U ≤ n(2^(1/n)−1)；n=2 上界 0.828，n→∞ 趋于 ln2≈0.693；是充分非必要条件。
5. **EDF 与 RMS 的优先级是静态还是动态？** RMS 静态（按周期）；EDF 动态（按当前最新截止期限）。
6. **为什么 EDF 利用率上限是 1.0？** EDF 允许任务抢占关系随截止期动态变化，总能在利用率 ≤1 时找到可行排程，是充要条件。
7. **Linux CFS 为什么用 vruntime 而非固定时间片？** 按权重折算 vruntime，谁欠得多谁先跑，天然公平且能映射 nice 权重，不用固定时间片。
8. **SCHED_FIFO 与 SCHED_RR 的区别？** FIFO 无时间片、跑完或阻塞才让出；RR 在同一实时优先级内按时间片轮转。
