::: abstract 本章定位
把"fd"这个贯穿进程、文件系统、IO 与网络四大板块的核心抽象一次讲透：它到底是一个整数还是一个对象、进程级 fd 表 / 系统级打开文件表 / inode 三层如何关联、dup/fork/exec 的复制与共享语义、`/proc` 与 `lsof` 如何观察 fd，以及 EMFILE、fd 泄漏这类生产故障的定位路径。概念底子见 [系统调用](/kb/os/进程线程/02-进程控制块与系统调用/)，故障排查联动 [fd 耗尽排查](/kb/os/问题排查/04-磁盘与IO瓶颈排查/)。
:::

教材说"打开文件返回文件描述符"，但很少解释"描述符"三个字。它既不存文件内容，也不存文件名，只是一个**非负整数**。可就是这个整数，同时串起了[进程](/kb/os/Linux/08-Linux进程与线程内核原理/)、[文件系统](/kb/os/Linux/11-Linux文件系统内核原理/)、[网络](/kb/os/Linux/05-Linux网络与系统调用实操/)和 [IO](/kb/os/Linux/04-LinuxIO与性能监控实操/)——懂了 fd，四块知识才真正连成一张网。

## 1. fd 的本质：一个整数，一串索引

### 1.1 概念：fd 是"打开文件表的索引"

`fd`（file descriptor）是一个**非负整数**，它是**进程打开文件表（fd table）的下标**。真正描述"这次打开"全部状态的，是 fd 表里那一个表项所指向的**打开文件描述（struct file）**。

所以 `open()` 返回的整数不是"文件的编号"，而是"我这次打开在第几格"——同一个文件打开两次，返回两个不同 fd，对应两份独立的文件偏移和读写模式。

### 1.2 图解：三层结构

```mermaid
graph TB
    subgraph 进程 P（用户态）
        PFD["fd 表（每进程一份）<br/>0 1 2 3 ... n<br/>每个格子存一个 struct file*"]
    end
    subgraph 内核全局
        F1["struct file A<br/>f_pos=0, flags=O_RDWR<br/>f_count=1"]
        F2["struct file B<br/>f_pos=100, flags=O_RDONLY<br/>f_count=1"]
        INODE["struct inode<br/>文件元数据+数据块<br/>i_ino / i_size / i_mode"]
    end
    PFD -->|"fd 3"| F1
    PFD -->|"fd 5"| F2
    F1 -->|"f_path.dentry→d_inode"| INODE
    F2 -->|"f_path.dentry→d_inode"| INODE
```

三层各管一件事，别混：

| 层 | 作用域 | 内核对象 | 关键字段 | 典型代表 |
|---|---|---|---|---|
| **fd 表** | 进程私有 | fdtable | bitmap + fd[] 指针数组 | `ls /proc/&lt;pid&gt;/fd` |
| **打开文件描述** | 内核全局、可共享 | `struct file` | `f_pos`（偏移）、`f_flags`、`f_count` | `lsof` 输出 |
| **inode** | 内核全局、随文件存续 | `struct inode` | `i_size`、`i_ino`、`i_mode`、数据块指针 | `stat`、`ls -li` |

::: tip 偏移在哪一层？
偏移 `f_pos` 属于 `struct file`，不属于 fd、也不属于 inode。这决定了第 3 节 dup/fork 后"两个 fd 互相影响偏移"的根本原因。
:::

### 1.3 实操：标准流与 fd 上限

每个进程启动时内核自动分配前三个 fd：**0 标准输入、1 标准输出、2 标准错误**。shell 里 `command > log 2>&1` 折腾的就是这三个格子的指向。

```bash
ulimit -n          # 当前 shell 的 fd 上限（软限制）
ulimit -Sn         # 只看软限制
ulimit -Hn         # 只看硬限制
ulimit -n 4096     # 提高（<= 硬限制才允许）
```

fd 上限为什么"早期是 20"？Unix 的 `OPEN_MAX` 最小值历史上就是 **20**（POSIX 要求至少 20），早期系统内核编译期写死。Linux 后来改成运行时限制：

| 限制 | 数值（现代 Linux） | 说明 |
|---|---|---|
| 默认软限制 | 1024 | `ulimit -n` 默认值 |
| 默认硬限制 | 1048576 | 需 root 或 `prlimit` 才能提到硬限制以上 |
| `fs.nr_open` | 1048576 | 内核允许的**单进程 fd 绝对上限**，`sysctl` 可调 |
| `fs.file-max` | 约 8×`NR_FILE`（按内存算） | **全系统**打开文件数上限 |

### 1.4 概念：fd 与 FILE* 的区别

C 标准库的 `FILE*`（fopen 返回）与 fd 不是一回事：`FILE*` 是**用户态**结构，包了一层 stdio 缓冲区；fd 是**内核态**的整数索引。`fopen` → `open` + 用户态缓冲。

```text
应用代码 → FILE*（stdio 缓冲，用户态）→ fd（内核索引）→ struct file → inode
```

所以 `fwrite` 之后直接 `close(fd)` 会**丢数据**：数据还在 stdio 缓冲里没刷进内核。必须先 `fflush(fp)` 或 `fclose(fp)`。第 8 节有专门表格。

## 2. 打开文件的系统调用与返回

### 2.1 概念：open 返回"最小可用 fd"

`open()`/`openat()`/`creat()` 成功后返回的必然是目前**编号最小的空闲 fd**。内核在 fd 表里维护一个位图，找空闲格子的算法就是**从 0 开始找第一个空闲位**（`fs/file.c` 的 `find_next_fd`）。

```c
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>
int main(void) {
    int a = open("/etc/hostname", O_RDONLY);   // 通常返回 3
    int b = open("/etc/hostname", O_RDONLY);   // 返回 4
    printf("a=%d b=%d\n", a, b);
    close(a);                                  // 释放 3
    int c = open("/etc/hostname", O_RDONLY);   // 又返回 3（最小空闲）
    printf("c=%d\n", c);
    return 0;
}
```

::: tip 为什么 shell 重定向要先 close(1) 再 open？
因为 open 返回最小空闲 fd。先 `close(1)`，再把文件 open 进来，它自然占用 1 号——这就是 `>` 重定向的内核机制，见第 4 节。
:::

### 2.2 概念：open 的标志位

| 标志 | 含义 | 要点 |
|---|---|---|
| `O_RDONLY` / `O_WRONLY` / `O_RDWR` | 读 / 写 / 读写 | 三选一，互斥 |
| `O_CREAT` | 不存在则创建 | 需带 `mode` |
| `O_TRUNC` | 打开即清空 | 与 `O_WRONLY`/`O_RDWR` 搭配 |
| `O_APPEND` | 追加写 | 每次写先移到文件尾，原子性见第 4 节 |
| `O_NONBLOCK` | 非阻塞 | 对管道/设备/网络 socket 有效（第 8 节） |
| `O_CLOEXEC` | exec 时自动关闭 | 防 fd 泄漏给子进程（第 3、8 节） |

### 2.3 实操：mode 与 umask 的交互

`O_CREAT` 时第三个参数 `mode` 指定权限位，但**最终生效值 = mode & ~umask**。umask 是进程属性，`umask` 命令可查可改，内核里存于 `task_struct->fs->umask`。

```bash
umask 022
# open("f", O_CREAT, 0666) → 实际权限 0666 & ~022 = 0644
```

```c
int fd = open("/tmp/x.txt", O_CREAT | O_WRONLY, 0666);  // 实际 0644（受 umask 影响）
```

### 2.4 实操：open 失败与 errno

`open` 失败返回 -1，具体原因看 `errno`（[errno 详解](/kb/os/问题排查/10-系统调用与错误码疑难/)）：

| errno | 含义 | 一句话诊断 |
|---|---|---|
| `EACCES` | 权限不足 | 对目录无可执行权，或文件本身 mode 不允许 |
| `ENOENT` | 文件/目录不存在 | 路径中某级不存在（注意：目录不可读也是 ENOENT） |
| `EMFILE` | 进程 fd 数达到 `ulimit -n` | **进程级**上限，`ulimit -n` 可查（第 6 节） |
| `ENFILE` | 系统打开文件数达 `file-max` | **系统级**上限，`/proc/sys/fs/file-max`（第 6 节） |
| `ENOTDIR` / `EISDIR` | 路径成分是文件 / 目标本身是目录 | 路径写错或不能以读写方式打开目录 |
| `EINTR` | 被信号打断 | 一般建议重试 open（与 close 不同！） |

::: warning EMFILE 与 ENFILE 的区别是面试与排障高频考点：EMFILE 数 `/proc/&lt;pid&gt;/fd | wc -l` 就能对上；ENFILE 则要查全局 `file-nr`，见第 6 节。
:::

### 2.5 实操：close 的语义与 EINTR

`close(fd)` 使 fd 表该项失效、`struct file` 引用计数减一；计数归零时才真正释放文件描述并回写（如删除临时文件的最后一环）。

**close 遇到 EINTR 要不要重试？不要。** POSIX 2008 明确规定：close 返回 EINTR 时，**该 fd 的状态是不确定的，且必须视为已关闭**。若盲目重试 `close(fd)`，可能关掉的是另一个后来被复用的 fd（见第 8 节 double-close 风险）。Linux 上普通文件基本不会因信号打断 close，但某些设备驱动可能，遇到时直接放弃重试。

```c
int r = close(fd);
if (r == -1 && errno == EINTR) {
    /* 不要重试 close！fd 可能已经关闭，甚至已被复用 */
}
```

## 3. fd 的复制与共享语义（本篇重点）

### 3.1 概念：dup/dup2/dup3 复制的是"表项"

`dup` 系列**不复制文件，也不复制偏移**，它复制的是 fd 表里那一个格子：新 fd 与旧 fd 指向**同一个 struct file**。因此偏移 `f_pos` 是共享的——用任一 fd 读了文件，另一个 fd 的偏移也跟着变。

```c
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>
int main(void) {
    int fd = open("/etc/hostname", O_RDONLY);
    int fd2 = dup(fd);              // fd2 与 fd 共享偏移
    char b[32];
    read(fd, b, 1);                 // 读出第 1 字节
    printf("after read(fd): off=%ld\n", lseek(fd, 0, SEEK_CUR));
    printf("after read(fd): fd2 off=%ld\n", lseek(fd2, 0, SEEK_CUR)); // 也 +1
    return 0;
}
```

### 3.2 图解：dup 之后

```
     进程 P 的 fd 表                  内核对象
┌──────────────┐
│ 0   stdin    │
│ 1   stdout   │
│ 2   stderr   │
│ 3 ───────────┼──▶ struct file X ──▶ inode
│ 4 ───────────┼──▶ struct file X  （同一个 file！f_count=2）
└──────────────┘
```

`dup2(fd, newfd)` 与 `dup(fd)` 的区别：dup 返回**最小空闲**fd（可能不是你要的号）；dup2 强制**落到指定编号**（编号已占用则先原子地关掉它）；dup3 额外支持 `O_CLOEXEC` 标志位。

::: warning dup2 的三个失败细节
`dup2(fd, newfd)` 失败返回 -1 并设 errno：`EBADF`（fd 不是合法打开号）、`EINTR`（被信号打断，**且此时 newfd 状态不确定**）、`EMFILE`（fd 表满，新副本没建成）。注意：若 `newfd == fd`，dup2 直接返回 fd 不再重复复制；若 fd 指向一个已被 close 的号，dup2 不做任何事直接 EBADF。
:::

```c
/* dup2 的正确失败处理：newfd 可能已经不再指向我们想要的东西 */
int newfd = 1;  /* 想把 stdout 重定向 */
if (dup2(fd, newfd) < 0) {
    perror("dup2");   /* 不要假设 newfd 未被改动！ */
    close(fd);
}
```

### 3.3 内核实现：三个 API 的差异

| 调用 | 落点 | 特性 |
|---|---|---|
| `dup(fd)` | 最小空闲号 | 简单 |
| `dup2(fd, n)` | 指定 n（必要时原子 close n） | 重定向的标准做法 |
| `dup3(fd, n, O_CLOEXEC)` | 指定 n | Linux 特有，可同时设 CLOEXEC |
| `fcntl(fd, F_DUPFD, n)` | ≥ n 的最小号 | 语义同 dup，从 n 起找 |
| `fcntl(fd, F_GETFD/F_SETFD)` | — | 读/写该 fd 的 `FD_CLOEXEC` 标志 |

### 3.4 概念：fork 继承、exec 保持

**fork** 时子进程复制整张 fd 表（内核 `copy_files` → `dup_fd`），父子 fd 指向**同一批 struct file**，偏移共享（这决定第 4 节父子写同一文件的行为）。此时 `struct file` 的 `f_count` 每多一个引用就 +1。

**exec** 时 fd 表**原样保留**，除非该 fd 设置了 `FD_CLOEXEC`（关闭时执行）标志。防泄漏的两条路：

```c
int fd = open("x", O_RDONLY | O_CLOEXEC);        // 打开时就带上（推荐）
fcntl(fd, F_SETFD, FD_CLOEXEC);                  // 或事后补设
```

### 3.5 实操：为什么"close 一个还报 EMFILE"？

dup 永远返回**最小空闲号**，这是理解这个"坑"的关键。经典场景（APUE 里的保护 fd 技巧）：

```c
/* 想把 fd X 暂时"让出"而不被下一次 open 复用：用 dup 填满 fd 表 */
while ((r = dup(x)) != -1)   /* 不断复制 x，直到 dup 返回 EMFILE */
    ;
/* 此时除 x 外所有 fd 都是 x 的副本。你把 x close 掉 */
close(x);
/* 但下一次 open/dup 立刻占用 x（它是最小空闲号），x 又被拿走了！
   你以为腾出了位置，其实"close 一个还报 EMFILE"。 */
```

要点：**最小空闲号会被下一个 open 立即抢走**。想要某 fd 不被占用，要么让它保持打开，要么用一个"占位"副本堵住它。真实生产中，"close 一个 fd 系统仍报 EMFILE"多半是别的 fd 还在泄漏、没有真正腾出来——这引出第 6 节的泄漏排查。

::: tip fork 后 fd 偏移判断题（自测题的高频出处）
fork 前读 1 字节（偏移=1），fork 后父子各自再 read：由于共享 file 对象，父子轮流读，偏移从 1 继续增长，谁先读谁拿第 2 字节——**不是**各自从 1 开始。
:::

## 4. 共享打开文件描述的场景

### 4.1 父子进程共享 file 对象

fork 后父子"共享偏移"，用在生产上的正面案例：**父子进程协作处理同一文件的不同部分**时，共享偏移让"谁读到哪写到哪"自动接力，不用自己管理游标（代价是需加锁防竞态）。

```c
int fd = open("/tmp/out.log", O_WRONLY | O_CREAT | O_APPEND, 0644);
if (fork() == 0) {
    write(fd, "child\n", 6);   /* 与父进程共享同一偏移 */
    _exit(0);
}
write(fd, "parent\n", 7);
```

### 4.2 O_APPEND 保证原子追加

多进程写同一文件不覆盖，靠 `O_APPEND`：内核在每次 `write` 时，**在 inode 锁内先 seek 到文件尾再写**，两步做成原子操作，杜绝"同时 seek 到 100、又同时写到 100"互相覆盖。**没有 O_APPEND 时，多进程各自 seek 再写，必然出现写坏/覆盖。**

### 4.3 dup 实现重定向：shell 的 `>`

shell 执行 `cmd > out.txt` 的内核动作，就是标准的 dup2：

```c
/* 伪代码：shell 处理 '>' */
fd = open("out.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
dup2(fd, STDOUT_FILENO);   /* 让 1 号指向 out.txt 的 file 对象 */
close(fd);                 /* 原 fd 可关，1 号还指着它 */
/* 然后 exec 子进程：子进程的 stdout 自然写进文件 */
```

```bash
# 同一个道理的命令级验证：把 1 重定向到文件后，fd 0/1/2 仍是文件
bash -c 'ls > /tmp/t.txt; ls -l /proc/$$/fd'
```

### 4.4 pipe 的读写端 fd

`pipe(fds)` 返回两个 fd：`fds[0]` 读端、`fds[1]` 写端。关键特性：**写端不 close，读端 read 永远等不到 EOF**；双方 fd 都 close 后，内核回收管道。这就是管道通信"以 EOF 表示对端关闭"的基础，是 [网络与系统调用](/kb/os/Linux/05-Linux网络与系统调用实操/) 与 shell 管道的共同地基。

## 5. 用 /proc 观察 fd

### 5.1 /proc/&lt;pid&gt;/fd 目录

每个进程的 fd 都会在 `/proc/&lt;pid&gt;/fd/` 下露出一个**数字软链接**，链接目标就是"这个 fd 现在指着什么"：

```bash
ls -l /proc/$$/fd
```

预期输出片段：

```
lrwx------ 1 u u 64 Aug 10 10:00 0 -> /dev/ttys000
lrwx------ 1 u u 64 Aug 10 10:00 1 -> /dev/ttys000
lrwx------ 1 u u 64 Aug 10 10:00 2 -> /dev/ttys000
lrwx------ 1 u u 64 Aug 10 10:00 3 -> /Users/u/code/a.txt
```

| 软链接目标 | 含义 |
|---|---|
| `/some/path` | 普通文件，路径即文件 |
| `pipe:[12345]` | 管道，`[]` 里是管道 inode 号 |
| `socket:[67890]` | socket，`[]` 里是 socket inode 号 |
| `/path (deleted)` | 文件已被删除但进程仍握着 fd（第 6 节重点） |
| `anon_inode:[eventpoll]` | epoll 实例自身 |
| `memfd:name (deleted)` | memfd 内存文件 |

### 5.2 fdinfo：偏移、标志、挂载

```bash
cat /proc/$$/fdinfo/3
```

```
pos:    0
flags:  0100002
mnt_id: 22
```

`pos` 就是 struct file 的 `f_pos`（偏移）；`flags` 是八进制打开标志（`0100002` 的低位 `2` 即 O_WRONLY，`0100000` 是 O_LARGEFILE，`02000000` 是 O_CLOEXEC）。**读 fdinfo 可以直接验证第 3 节"dup 共享偏移"**。

### 5.3 lsof 与 ss

```bash
lsof -p 1234                # 列出 pid 1234 的所有打开文件
lsof +L1 -p 1234            # 只看已删除但仍打开的文件（+L1 表示 link count < 1）
lsof -nP -iTCP -sTCP:LISTEN # 看监听端口对应哪个进程哪个 fd
ss -tunlp                   # 系统层面看 socket 与所属进程 fd（见 05 篇）
```

| 工具 | 数据来源 | 适用场景 |
|---|---|---|
| `ls -l /proc/&lt;pid&gt;/fd` | procfs | 快、无依赖，适合脚本计数 |
| `lsof` | 遍历 /proc + 设备表 | 功能全：过滤、排序、deleted 标记 |
| `ss` | netlink（内核直接） | socket 专用，开销最小 |
| `fdinfo` | procfs | 看偏移/标志等细节 |

### 5.4 系统级：file-nr

```bash
cat /proc/sys/fs/file-nr
```

输出三个数：**已分配文件句柄数 / 空闲未用句柄数 / 系统上限（= file-max）**。第一列持续逼近第三列，就是系统级文件耗尽的前兆（第 6 节 ENFILE 的判据）。

```bash
# 实时监控：3 秒刷一次 file-nr 第一列（已分配）与上限的关系
watch -n3 'awk "{print \"used=\"\$1\" max=\"\$3}" /proc/sys/fs/file-nr'
# 直接读一个进程到底开了多少个 fd（shell 里 $BASHPID 是本进程）
ls /proc/$BASHPID/fd | wc -l
```

::: tip fdinfo 里的 flags 怎么读？
`flags` 是八进制数，与打开标志按位对应：低 3 位是访问模式（`0`=O_RDONLY、`1`=O_WRONLY、`2`=O_RDWR），高位含 `O_APPEND`(0100000)、`O_NONBLOCK`(04000)、`O_CLOEXEC`(02000000)。`printf "%o\n"` 对不上就 `python3 -c 'import sys; print(oct(int(sys.argv[1],8)))' &lt;flags&gt;` 再逐位查。
:::

## 6. 超限与泄漏：联动故障排查

### 6.1 EMFILE vs ENFILE 区分

| 现象 | 级别 | 指标 | 处理 |
|---|---|---|---|
| `EMFILE: Too many open files` | **进程级** | `ls /proc/&lt;pid&gt;/fd \| wc -l` 已达 `ulimit -n` | 改 `ulimit`/`LimitNOFILE`，更要修泄漏 |
| `ENFILE: Too many open files in system` | **系统级** | `file-nr` 第一列逼近 `file-max` | 调 `sysctl fs.file-max`，找出"谁在全系统狂开文件" |

**先查进程级（EMFILE 最常见），再查系统级**。两个都报错时，看 `dmesg` 是否有 `out of file handles`。

### 6.2 fd 泄漏定位三步

1. **看曲线**：`watch -n1 'ls /proc/&lt;pid&gt;/fd | wc -l'` 观察 fd 数是否随请求量线性上涨且不回落。
2. **看对象**：`lsof -p &lt;pid&gt;` 找反复出现的 `pipe`/`socket`/临时文件——**没 close 的 socket 是最常见泄漏源**。
3. **看系统调用**：`strace -f -e trace=open,openat,dup,close -p &lt;pid&gt;` 或提前用 `strace -ff -o /tmp/tr -e trace=open,close &lt;cmd&gt;`，随后统计 open/close 是否配对：

```bash
strace -e trace=open,openat,close ./leaky
grep -c 'openat(' /tmp/tr* 2>/dev/null   # 开了多少次
grep -c 'close(' /tmp/tr* 2>/dev/null    # 关了多少次
```

::: warning 泄漏的进程危害不止"自己的 EMFILE"：它占用的 `struct file` 让内核缓存（page cache）里该文件的页、dentry 全部滞留无法回收，最终可能拖到系统级 ENFILE，甚至把同主机的其他进程一起拖垮。进程内无救时**重启是唯一手段**——这就是为什么很多服务强制重启前要查 lsof 曲线。
:::

### 6.3 上限调整

| 层 | 命令/文件 | 说明 |
|---|---|---|
| 会话 | `ulimit -n 65535`（软） | 临时，重登失效；软 ≤ 硬 |
| 硬限制 | `prlimit --nofile=65535:65535 -p &lt;pid&gt;` | 可调已运行进程，root 才能越过硬限制 |
| systemd | 服务文件里 `LimitNOFILE=65535` | 应用部署标准做法 |
| 内核 | `sysctl fs.nr_open=2000000` | 单进程绝对上限，需先于 ulimit 提高 |
| 内核 | `sysctl fs.file-max=2097152` | 全系统上限，临时用 `sysctl -w`，持久写 `/etc/sysctl.d/` |

### 6.4 典型泄漏场景

- 每次请求 new 一个 socket 连接，异常路径没走 close；
- 线程池/连接池的线程长驻，但每个任务都 `open` 不 `close`，fd 数只增不减；
- 每次 `fopen`/`opendir` 对应 `fclose`/`closedir` 漏配；
- fork+exec 子进程没设 CLOEXEC，把父进程一堆 fd 全带过去，子进程又不清。

## 7. fd 与 epoll/select

### 7.1 fd 在事件驱动中的角色

IO 多路复用的本质：**把"等哪个 fd 就绪"这件事交给内核**，进程一次等一大片 fd。`select` 用位图描述 fd 集合（受 `FD_SETSIZE` 限制，通常 1024），每次调用都要把整张位图拷进拷出内核；`epoll` 把要监视的 fd **注册进内核**，事件就绪由内核维护，进程只取结果。

```bash
# 感受一下：单进程开 5 万个 socket 连接（先调大限制）
ulimit -n 65535
python3 -c 'import socket; [socket.socket() for _ in range(50000)]; input("ok")' &
ss -tan | wc -l
```

### 7.2 epoll 内部怎么用 fd

内核里每个被监视的 fd 对应一个 `struct epitem`，按 `(fd, struct file*)` 做 key 挂在一棵 **红黑树**（`ep->rbr`）上，增删查都是 O(log n)；就绪的 epitem 再挂到**就绪链表** `rdllist` 由 `epoll_wait` 取走。

```text
epoll 实例（eventpoll）
 ├── rbr（红黑树）：epitem × N，key=(fd, file*)   ← 注册/删除走这里
 └── rdllist（就绪链表）：只有触发事件的 epitem     ← epoll_wait 走这里
```

**关闭 fd 会自动从 epoll 移除**：`close(fd)` 使 struct file 引用计数归零，内核 `eventpoll_release_file` 找到对应 epitem 摘除，无需显式 `EPOLL_CTL_DEL`。但反过来要注意：**FD_CLOEXEC 也要配**，否则 fork+exec 后子进程继承了 epoll fd 和其中所有 fd，父进程 close 时计数不清零，造成 "close 了但 epoll 还留着" 的幽灵事件。

另一个隐蔽点：**把一个 fd 注册进 epoll 后，如果该 fd 被 dup 出副本，再 close 原 fd，注册不会移除**——因为 epitem 以 `(fd, struct file*)` 为 key，只要还有一个引用指向该 file 对象，事件就继续上报。清理要 `EPOLL_CTL_DEL` 或把最后一个引用 close 掉。

```c
int efd = epoll_create1(0);
struct epoll_event ev = {.events = EPOLLIN, .data.fd = conn};
epoll_ctl(efd, EPOLL_CTL_ADD, conn, &ev);
close(conn);                       /* 若 conn 另有引用（如 dup 副本），注册仍残留 */
/* 稳妥：先 epoll_ctl(efd, EPOLL_CTL_DEL, conn, NULL) 再 close */
```

### 7.3 LT 与 ET 对 fd 的读取要求

- **LT（水平触发，默认）**：fd 只要有未读数据，epoll_wait 就反复上报。可以慢慢读，读不完下次再报，好写不易漏。
- **ET（边沿触发）**：只在"无→有"的边界上报一次。要求**一次性把数据读干净到 EAGAIN**，否则剩余数据再也不上报——`while (read()>0);` 读到 EAGAIN 是标准写法。

| | LT | ET |
|---|---|---|
| 上报时机 | 数据存在即上报 | 状态跃迁时上报 |
| 读取要求 | 宽松 | 必须读到 EAGAIN |
| 配合 | 简单 | 常配 `O_NONBLOCK` |
| 风险 | 频繁唤醒 | 漏读 → 数据卡死 |

### 7.4 大量 fd 的性能

fd 多到几万时，`select`/`poll` 的 O(n) 全量扫描与位图拷贝不可接受；epoll 的注册/就绪分离设计让单进程撑住 **十万级连接**。这也是 nginx、redis 单线程高性能模型的物理基础：事件驱动 + 非阻塞 fd，见 [网络实操](/kb/os/Linux/05-Linux网络与系统调用实操/) 与 [调度器原理](/kb/os/Linux/09-Linux调度器原理/)。

## 8. 常见易错点总结表

| 易错点 | 后果 | 正确做法 |
|---|---|---|
| 忘 close | fd 泄漏，最终 EMFILE（第 6 节） | RAII/`defer`/作用域末尾 close；压测 `ls /proc/&lt;pid&gt;/fd \| wc -l` 监控 |
| close 两次 | 第二次可能 EBADF；**更危险**：期间该 fd 号被复用，等于把别人的 fd 关了 | 关闭后立即置 -1，或保证单点管理 |
| fd 与 FILE 混用 | `write` 进内核但 stdio 缓冲未刷，`close(fd)` 丢数据 | 同一文件要么全用 fd 要么全用 FILE；换层前先 `fflush` |
| 漏设 CLOEXEC | fork+exec 后泄漏 fd 给子进程（子孙越生越多） | `open(..., O_CLOEXEC)` 或 `fcntl(F_SETFD)` |
| 多线程共享 close | use-after-close：A 线程还在 read，B 线程已 close，fd 复用后 A 读到别人的数据 | close 与使用必须同线程或加锁；用引用计数方案 |
| 只 setvbuf 不理解缓冲 | 性能假象，退出时未 `fclose` 丢日志 | 日志/数据必须 flush 或 fclose 落盘 |
| 忽略 O_NONBLOCK 语义 | read/write 返回 EAGAIN 被当错误 | EAGAIN 是"稍后再试"不是失败 |
| open 失败不查 errno | EMFILE/ENFILE 误当"权限问题"瞎改 mode | 按第 2 节 errno 表逐项对 |

```c
/* double close 危险演示：fd 号被复用的典型剧情 */
int fd = open("a", O_RDONLY);
close(fd);                 /* 第 1 次 */
int fd2 = open("b", O_RDONLY);  /* fd2 恰好复用 fd 这个编号 */
close(fd);                 /* 第 2 次：关的其实是 fd2！b 文件被意外关闭 */
```

## 本章小结

fd 是贯穿 Linux 用户态与内核态的"句柄"抽象：**进程级 fd 表 → 系统级 struct file → inode** 三层关系决定了偏移、引用与共享的全部语义。dup/fork 复制的是表项、共享的是 file 对象，因此偏移互相影响；exec 默认保持 fd，CLOEXEC 是防泄漏的开关。故障定位要分清 EMFILE（进程级）与 ENFILE（系统级），用 `/proc/&lt;pid&gt;/fd`、fdinfo、lsof、strace 四件套定位泄漏。epoll 把 fd 挂进内核红黑树，才撑得起高并发——fd 不只属于文件系统，它是整个 IO 世界的地基。

## 动手实验

1. **C 验证 dup 共享偏移**：写第 3.1 节的程序，`read(fd, b, 1)` 后打印两个 fd 的 `lseek(SEEK_CUR)`，确认都 +1；再对两个 fd 分别 read，看偏移连续增长。
2. **/proc/&lt;pid&gt;/fd 观察**：写个循环 `while(1){ int f=open("/etc/hostname",O_RDONLY); }` 不 close，另一终端 `ls -l /proc/&lt;pid&gt;/fd | wc -l` 观察计数上涨，Ctrl+C 后归零。
3. **制造 EMFILE**：`ulimit -n 64` 后运行实验 2 的程序，观察 open 何时返回 -1 且 `errno==EMFILE`；再用 `lsof -p &lt;pid&gt;` 看满屏 `/etc/hostname`。
4. **lsof +L1 抓 deleted**：终端 A `tail -f /tmp/keep.log`；终端 B `rm /tmp/keep.log` 后 `lsof +L1 | grep keep`，看到 `(deleted)` 仍占用空间——这就是"删了文件但磁盘不释放"的根因。
5. **fd 泄漏模拟 + strace 定位**：写个"每循环开 socket 不关"的小程序，`strace -e trace=socket,close` 跑起来，统计 socket 与 close 次数不匹配，定位到泄漏点。
6. **dup2 重定向实验**：C 里 `dup2(fd, 1)` 后 `printf`，观察输出进文件——复刻 shell `>`。
7. **fork 偏移判断题验证**：fork 后父子各 read 一个字节，打印字节和各自偏移，验证"共享偏移接力读"而非各自从起点读。

## 自测题

1. `open` 返回的整数，本质是什么？为什么同一个文件 open 两次返回不同整数？
2. 某进程 open 返回 -1 且 `errno==EMFILE`，与返回 -1 且 `errno==ENFILE` 分别代表什么级别的耗尽？各看哪个指标？
3. 进程 fd 表满了（EMFILE）。此时 close 一个 fd 后立刻 open 一个新文件，返回的编号是多少？为什么"close 一个还报 EMFILE"的思路是错的？
4. dup(fd) 之后，两个 fd 的偏移是什么关系？如果这时 fork，父子进程各自的 fd 与父进程原 fd 又是什么关系？（写一写偏移怎么流动）
5. 一段程序先 `fprintf(fp, "hello")` 再立刻 `close(fileno(fp))`，会发生什么？如何修复？
6. 服务器子进程继承了大量 fd，如何在打开时一次性杜绝？给了 `dup`、`dup2`、`dup3` 三个函数，选哪个、加什么标志？
7. epoll 里把 fd 设为 ET（边沿触发），read 没读干净会发生什么？为什么标准做法是"循环读到 EAGAIN"？
8. `rm` 掉一个文件后，用 `lsof +L1` 仍能看到某进程握着它。此时文件的数据还能读到吗？磁盘空间为什么不释放？要怎样才真正释放？

<details>
<summary>答案</summary>

1. fd 是进程打开文件表的下标；open 两次创建两个独立的 `struct file`（独立偏移/模式），所以返回两个不同整数。
2. EMFILE 是**进程级** fd 数达 `ulimit -n`，看 `ls /proc/&lt;pid&gt;/fd | wc -l`；ENFILE 是**系统级**打开文件总数达 `fs.file-max`，看 `/proc/sys/fs/file-nr` 第一列。
3. open 总是返回**最小空闲号**：close 掉的那个编号会被下一次 open 立即复用。若程序仍是"只 close 一个"却指望腾出大量空间，逻辑本身就是错的——EMFILE 下应找到并关闭真正的泄漏源，而不是靠 close 一个试探。
4. dup 后两个 fd 共享同一个 `struct file`，**偏移完全一致、互相影响**；fork 后子进程复制 fd 表，但指向的仍是同一批 `struct file`，所以父子**也共享偏移**——偏移是"接力流动"而非各自复制。
5. "hello" 还在 stdio 用户态缓冲里，`close(fileno(fp))` 直接关掉内核 fd，缓冲数据丢失。修复：先 `fflush(fp)` 再 close，或直接 `fclose(fp)`。
6. 用 `dup3(fd, n, O_CLOEXEC)`（或 `open(..., O_CLOEXEC)`/`fcntl(F_SETFD, FD_CLOEXEC)`），exec 时内核自动关闭该 fd，不随子进程泄漏。
7. ET 只在"无→有"边界上报一次；没读干净，剩余数据不会再次触发 epoll_wait，造成数据卡死。循环 `read` 直到 EAGAIN 才能保证读完。
8. 能，`struct file` 仍指向 inode，数据完整。磁盘空间不释放是因为 inode 的引用计数仍 >0（进程还握着 fd）。等该进程 close（或进程退出）后内核才真正释放数据块与空间。
</details>
