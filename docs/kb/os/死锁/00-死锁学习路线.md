::: abstract 本章定位
死锁是并发编程里"资源争夺失控"的产物，也是面试操作系统必考的核心模块。本目录用 5 篇笔记把《Operating System Concepts》Ch8 Deadlocks 讲透：先识别死锁长什么样（四条件、资源分配图），再讲三种应对策略（预防 → 避免 → 检测与恢复），最后落到 Linux 内核、数据库和真实线上排查。
:::

死锁的本质是一个**循环等待**：一组进程中的每个进程都在等一个只有该组内其他进程才能释放的资源，于是谁也无法前进。理解死锁的关键不是背定义，而是掌握一条主线：**从"为什么会发生"到"能不能从源头杜绝"，再到"杜绝不了时怎么动态避免"、"避免不了时怎么检测并恢复"**。

## 4. 实验清单

::: warning 环境说明
以下命令多数依赖 Linux 内核特性（如 lockdep、`/proc/&lt;pid&gt;/stack`）。本机为 macOS 时，建议在 Linux 虚拟机或 WSL2 中执行（macOS 的 `ps` 不支持 `wchan` 列）。
:::

### 4.1 制造一个死锁（C + pthread）

两个线程按**相反顺序**抢两把互斥锁，必然循环等待。保存为 `deadlock.c`：

```c
#include <pthread.h>
#include <stdio.h>
#include <unistd.h>

pthread_mutex_t lock_a = PTHREAD_MUTEX_INITIALIZER;
pthread_mutex_t lock_b = PTHREAD_MUTEX_INITIALIZER;

void *worker1(void *arg) {
    pthread_mutex_lock(&lock_a);
    sleep(1);                          // 确保两个线程都先拿到第一把锁
    pthread_mutex_lock(&lock_b);       // 死锁点
    pthread_mutex_unlock(&lock_b);
    pthread_mutex_unlock(&lock_a);
    return NULL;
}

void *worker2(void *arg) {
    pthread_mutex_lock(&lock_b);       // 顺序与 worker1 相反
    sleep(1);
    pthread_mutex_lock(&lock_a);       // 死锁点
    pthread_mutex_unlock(&lock_a);
    pthread_mutex_unlock(&lock_b);
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, worker1, NULL);
    pthread_create(&t2, NULL, worker2, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    return 0;
}
```

编译并运行：

```bash
gcc -pthread deadlock.c -o deadlock
./deadlock            # 程序卡死
```

### 4.2 观察死锁线程（三招）

```bash
# 1) 看所有线程的内核等待点（阻塞在哪个内核函数）
ps -eo pid,tid,wchan:30,stat,comm | grep deadlock
#    死锁时 wchan 通常显示为 futex_wait_queue_me / do_futex，且两个线程互相等

# 2) 抓线程栈（等价于 "线程在等谁"）
pstack &lt;PID&gt;          # 或 gstack &lt;PID&gt;，列出所有线程的用户态栈

# 3) gdb 附加：thread apply all bt 一次性打印所有线程栈
gdb -p &lt;PID&gt;
(gdb) thread apply all bt
```

::: tip 从栈里读死锁
如果线程 A 停在 `lock(lock_b)`、线程 B 停在 `lock(lock_a)`，两把锁正好互相持有——这就是教科书死锁在真实系统里的样子。用 `pstack`/`gdb` 分别抓两次栈对比，就能确认"谁持有谁在等"。
:::

### 4.3 观察阻塞而非死锁（对照实验）

把 `worker2` 的顺序改成和 `worker1` 一致（都先 A 后 B），程序会正常结束——只有锁顺序相反才会死锁。这一正一反两个实验，帮你理解"循环等待"才是死锁的必要条件，单纯的等待（hold and wait）并不够。

### 4.4 体验内核 lockdep

启用 `CONFIG_PROVE_LOCKING` 的内核（大多数发行版 debug 内核默认开）：

```bash
dmesg | grep -i "lockdep\|possible deadlock"     # 若程序里锁序不一致,内核会主动报警
cat /proc/lockdep                                 # lockdep 统计
```

### 4.5 数据库死锁（MySQL）

两个终端会话互相更新同一批行：

```sql
-- 会话 A
SET autocommit=0;
UPDATE account SET balance=balance-100 WHERE id=1;   -- 锁第1行

-- 会话 B
SET autocommit=0;
UPDATE account SET balance=balance-100 WHERE id=2;   -- 锁第2行
UPDATE account SET balance=balance+100 WHERE id=1;   -- 等 A 释放 → 等待
```

A 随后也去更新 id=2，形成循环等待，InnoDB 会选中一个事务回滚并报死锁。执行 `SHOW ENGINE INNODB STATUS\G` 查看 `LATEST DETECTED DEADLOCK` 段。

### 4.6 Java 死锁

```java
Object a = new Object();
Object b = new Object();
// 线程1: synchronized(a){ synchronized(b){ } }
// 线程2: synchronized(b){ synchronized(a){ } }
```

运行后用 `jstack &lt;PID&gt;` 找 `Found one Java-level deadlock` 段落，会直接告诉你两个线程各持有哪把 monitor。

## 6. 本章小结

死锁的处理不是"一个方法"，而是**一条从静态到动态的谱系**：预防（不给条件成立的机会）→ 避免（动态保证安全）→ 检测与恢复（出了事再救）。前两者需要提前知道进程的资源需求（银行家算法要求已知 Max），后者不需要任何先验信息，代价是"死锁可能已经发生"。三者的复杂度、开销、适用场景各不相同，选择取决于系统对"死锁代价"和"运行开销"的权衡。

## 7. 自测题

1. 死锁的四必要条件能否同时出现在单线程程序里？为什么？
   - **不能**。单线程不存在"一组进程互相等待"，循环等待要求至少两个执行体。

2. 破坏"持有并等待"最直观的办法是什么？
   - 一次性申请所有资源再开始执行，拿不到就一个都不拿（预分配）。

3. 资源分配图里有环，为什么还不能确定死锁？
   - 因为资源可能有多个实例，环中的进程可能拿到"环外"的空闲实例继续运行（见 [资源分配图与死锁建模](/kb/os/死锁/02-资源分配图与死锁建模/)）。

4. 银行家算法要求系统提前知道什么信息？
   - 每个进程对每类资源的**最大需求（Max）**，这是它在现实中难用的根源。

5. 死锁检测与死锁避免的本质区别？
   - 避免是在分配时就拒绝可能导致死锁的请求（事前）；检测是允许死锁发生，事后找出并恢复（事后）。
