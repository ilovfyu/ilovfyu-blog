::: abstract 本章定位
死锁预防 = 从**设计上**不让死锁发生：既然死锁需要四个必要条件同时成立，那就破坏其中一个。本章逐个分析"破坏互斥 / 持有并等待 / 非抢占 / 循环等待"的实现方式与代价，回答面试高频题：**为什么破坏互斥基本不可行？每种预防策略付什么代价？**
:::

## 1. 总览：预防的思路

死锁的四个必要条件是 [死锁特征与必要条件](/kb/os/死锁/01-死锁特征与必要条件/) 中定义的四条。预防策略就是"打地鼠"——只要保证至少一个条件永不成立，死锁就从"可能发生"变成"不可能发生"：

| 破坏的条件 | 策略名称 | 一句话做法 |
|---|---|---|
| 互斥 | 尽量共享资源 | 让资源可并发使用（现实中受限） |
| 持有并等待 | 预分配 | 一次性申请所有资源，拿不全就不干活 |
| 非抢占 | 可剥夺 | 申请不到新资源时，强制释放已持有资源 |
| 循环等待 | 有序分配 | 给资源全局编号，所有进程按编号升序申请 |

::: warning 关键认知
预防是**静态**手段：在设计阶段就定下规则，运行时零额外开销（不像[死锁避免与银行家算法](/kb/os/死锁/04-死锁避免与银行家算法/)那样每次分配都要跑算法）。代价是**资源利用率低、并发度差**——为杜绝死锁付出了大量"宁可空着不用"的代价。
:::

## 2. 策略一：破坏互斥（Mutual Exclusion）

### 2.1 做法与不可行性

要让互斥不成立，就得让"会引发死锁的资源"都能被多个进程同时使用。但问题在于：

- **本质不可共享的资源**：互斥锁、打印机、写文件、单写者数据库行——它们的语义就是"同时只能一个人用"，强行共享会破坏数据一致性。
- **能共享的资源本来就不死锁**：只读文件、CPU 这类本就可共享/可抢占的资源，从来不构成死锁主角。所以"破坏互斥"能改善的，恰恰是无法改善的资源。

::: important 结论
破坏互斥在绝大多数现实系统中**不可行**，因为资源的互斥性由业务语义决定，不是 OS 能改变的。唯一能做到的，是"尽量选择可共享的实现"（如读写锁允许读者并发、COW 文件系统避免写锁），但这只是缓解，不是根除。
:::

### 2.2 折中：读写锁缓解互斥

```c
// 多个读者可同时持有读锁（共享），写者独占
pthread_rwlock_t rwlock = PTHREAD_RWLOCK_INITIALIZER;

void reader(void) { pthread_rwlock_rdlock(&rwlock); /* 读数据 */ pthread_rwlock_unlock(&rwlock); }
void writer(void) { pthread_rwlock_wrlock(&rwlock); /* 写数据 */ pthread_rwlock_unlock(&rwlock); }
```

读写锁没有打破互斥，只是把"互斥的粒度"变小（读读不互斥），减少死锁的触发面，属工程优化，不是严格意义的预防。

## 3. 策略二：破坏持有并等待（Hold and Wait）

### 3.1 做法：预分配（一次全拿）

规定：进程**要么一次申请到它需要的全部资源，要么一个都不拿**。在它持有期间，不会再提出新的资源请求。

```c
// 伪代码：一次性申请所有资源
void process(void) {
    for (;;) {
        acquire(all_needed_resources);   // 一次拿全
        do_work();
        release(all_needed_resources);   // 用完一起放
    }
}
```

### 3.2 用锁实现时的注意点

真正的工程实现更常用"先锁全部、再干活"的模式，但注意它并没有真正原子地"一次拿全"——仍是按序加锁，只是"加锁阶段不许干活、不许再申请别的资源"：

```c
// 锁的"申请阶段"必须放在工作之前，且申请阶段不允许再提出新的资源请求
pthread_mutex_lock(&lock_a);
pthread_mutex_lock(&lock_b);
/* 工作区：此时绝不请求任何新资源 */
pthread_mutex_unlock(&lock_b);
pthread_mutex_unlock(&lock_a);
```

### 3.3 代价

| 代价 | 说明 |
|---|---|
| 资源利用率极低 | 进程可能持有大量资源但只用其中一小部分，其余资源被白白占用 |
| 并发度低 | 一个进程预占全部资源时，其他进程只能干等 |
| 饥饿风险 | 资源总量不够所有进程同时"全拿"时，后来的进程可能永远等不到（要区分死锁与饥饿） |
| 需要预知需求 | 必须提前知道"所有需要哪些资源"，很多场景做不到 |

::: tip 典型不适用的场景
交互式程序、增量式消费数据的程序（如边读边算的处理管线）无法预知未来需要多少资源，预分配无从谈起。它只适合资源集合小且明确的批处理任务。
:::

## 4. 策略三：破坏非抢占（No Preemption）

### 4.1 做法：请求失败就释放重试

当一个进程请求新资源被拒绝时，**不允许它抱着已持有的资源继续等**，而是强制它释放全部已持有资源，稍后从头再申请（可加入退避随机等待避免活锁）。这样"持有"与"等待"永远不会同时发生。

```c
// 伪代码：申请失败 → 释放全部 → 让位重试
while (1) {
    if (trylock(&lock_a)) {                       // 先拿 A
        if (trylock(&lock_b)) {                   // 再试 B
            do_work();
            unlock(&lock_b);
            unlock(&lock_a);
            break;
        }
        unlock(&lock_a);                          // B 拿不到 → 释放 A（破坏"持有并等待"）
        usleep(rand() % 1000);                    // 随机退避，避免两个进程同时重试成活锁
    }
}
```

### 4.2 代价

| 代价 | 说明 |
|---|---|
| 实现复杂 | 资源要有"状态可保存/可恢复"的能力，才能被中途收回（锁/寄存器没问题，半写文件就很麻烦） |
| 效率低下 | 反复"拿了又放、放了又拿"，系统调用和上下文切换开销大 |
| 活锁风险 | 若所有进程同时退避又同时重试，会陷入[死锁特征与必要条件](/kb/os/死锁/01-死锁特征与必要条件/)的活锁 |
| 不适用于有状态资源 | 正在被写入的缓冲区、事务中的记录，抢占会导致数据不一致 |

## 5. 策略四：破坏循环等待（Circular Wait）

### 5.1 做法：资源有序分配法

给每类资源一个**全局唯一的整数编号**，规定所有进程**只能按编号递增的顺序申请资源**。这样等待关系永远是"从小编号指向大编号"，不可能形成环。

例如规定 `编号: lock_a=1 < lock_b=2 < lock_c=3`，那么：

```c
// 正确：按编号升序申请
pthread_mutex_lock(&lock_a);   // 编号 1
pthread_mutex_lock(&lock_b);   // 编号 2 ✓
pthread_mutex_lock(&lock_c);   // 编号 3 ✓

// 错误：先申请编号大的再申请编号小的 —— 环的温床
pthread_mutex_lock(&lock_b);   // 编号 2
pthread_mutex_lock(&lock_a);   // 编号 1 ✗ 破坏规则
```

**为什么按升序申请就不会有环？** 反证：若存在环，环上必然有一条边从"编号大的资源持有者"向"编号小的资源申请者"。而申请必须升序，意味着每个进程申请新资源时编号只会变大——矛盾。于是环不存在，死锁从结构上被消灭。

### 5.2 工程上的对应：锁顺序（lock ordering）

Linux 内核、数据库、大型 C++ 项目普遍把"全局锁顺序"写进编码规范：

```c
// 规则: 永远先拿全局锁, 再拿局部锁; 永远不能反过来
pthread_mutex_lock(&global_lock);
pthread_mutex_lock(&per_object_lock);
// ... 工作 ...
pthread_mutex_unlock(&per_object_lock);
pthread_mutex_unlock(&global_lock);
```

::: warning 有序分配的隐性前提
资源编号一旦发布就必须是全局约定，且新增资源要能插入编号体系。如果两个子系统各自编号、互不知道对方，跨子系统的调用仍可能死锁。这也是"锁顺序规范"要作为团队级纪律的原因。
:::

### 5.3 代价

| 代价 | 说明 |
|---|---|
| 编号设计难 | 需要全局一致的编号，新增资源要重新排号，维护成本高 |
| 限制程序结构 | 某些天然"先拿大再拿小"的业务逻辑被迫改写 |
| 编号不等于分层 | 编号只防环，不保证公平，仍可能有饥饿 |

## 6. 四种预防策略对比总结

| 策略 | 破坏的条件 | 核心做法 | 主要代价 | 现实可行性 |
|---|---|---|---|---|
| 破坏互斥 | 互斥 | 资源可共享化 | 违反资源语义，基本不可行 | ★☆☆ 基本不可行 |
| 破坏持有并等待 | 持有并等待 | 预分配 / 一次全拿 | 资源利用率低、并发度低、可能饥饿 | ★★☆ 适合资源集合小的批处理 |
| 破坏非抢占 | 非抢占 | 失败即释放重试 | 实现复杂、开销大、可能活锁 | ★★☆ 适合可保存状态的资源 |
| 破坏循环等待 | 循环等待 | 资源编号有序申请 | 编号设计难、限制结构 | ★★★ 最常用、最务实 |

::: important 为什么"有序分配"是工程上最被认可的方法
破坏循环等待不需要预知全部需求（不像预分配），不需要资源可恢复（不像抢占），也不要求资源能共享（不像破坏互斥）。它只是要求"申请顺序遵守一条全局规则"，因而成为锁规范、内核锁序、数据库加锁顺序的共同选择。
:::

## 7. 本章小结

预防的核心是一句话：**让四个必要条件中至少一个永远不成立**。四选一各有代价——破坏互斥基本不可行，破坏持有并等待牺牲利用率，破坏非抢占牺牲效率，破坏循环等待（资源有序分配）代价最小、最贴合工程实践，是"锁顺序/锁分级规范"的理论出处。预防的优点是运行时零开销、无需进程申报需求；缺点是静态、保守，在并发度要求高的系统里常常显得"过度防御"，这就给动态的[死锁避免与银行家算法](/kb/os/死锁/04-死锁避免与银行家算法/)留下了用武之地。

## 8. 自测题

1. 死锁预防的总体思路是什么？
   - 保证四个必要条件至少一个不成立，使死锁从结构上不可能发生。

2. 为什么说"破坏互斥"基本不可行？
   - 很多资源的互斥性是业务语义决定的（如互斥锁、单写者数据库行），无法被共享；能共享的资源本就不构成死锁。

3. 预分配策略破坏的是哪个条件？有什么主要缺点？
   - 破坏"持有并等待"；缺点是资源利用率低、并发度低、可能造成饥饿，且需要预知资源需求。

4. "申请失败就释放已持资源再重试"破坏哪个条件？它可能引发什么新问题？
   - 破坏"持有并等待"；可能引发活锁（同时退避同时重试）、开销大，且要求资源状态可保存/恢复。

5. 资源有序分配法破坏哪个条件？为什么按编号升序申请就能消除环？
   - 破坏"循环等待"。若存在环，就存在从大编号向小编号申请的边，与"只能升序申请"矛盾，环不存在。

6. 四种预防策略里，哪一种最符合 Linux 内核与数据库的工程实践？为什么？
   - 破坏循环等待（锁顺序规范）。它不需要预知需求、不要求资源可抢占/可共享，只需遵守全局加锁顺序。

7. 预防和避免的区别是什么？
   - 预防是静态的、靠设计规则杜绝死锁，零运行时开销但利用率低；避免是动态的、每次分配时用算法判断"是否安全"（见 [死锁避免与银行家算法](/kb/os/死锁/04-死锁避免与银行家算法/)），开销更高但资源利用更充分。
