::: abstract 本章定位
死锁 = 一组进程互相等待、谁也不前进。本章回答三个问题：死锁怎么精确定义？满足哪四个必要条件才会死锁？它和饥饿、活锁有什么区别？这是理解后续所有死锁处理策略的理论地基。
:::

## 1. 死锁的定义与直观例子

### 1.1 教科书定义

一组进程中的**每个进程都在等待一个事件，而该事件只能由该组进程中的另一个进程触发**。在资源语境下，这个事件就是"其他进程释放资源"。因为大家都在等，事件永远不可能发生，所有进程永久阻塞。

::: important 两个关键词
- **循环**：等待关系构成一个环，A 等 B，B 等 A。
- **每个进程**：不是"某些"，而是环里的每个进程都阻塞，才能叫死锁。
:::

### 1.2 直观例子：两把锁

两个线程、两把互斥锁，线程 1 先拿锁 A 再拿锁 B，线程 2 先拿锁 B 再拿锁 A：

```
线程1:  获得 lock_a  ──►  等 lock_b  ✖
线程2:  获得 lock_b  ──►  等 lock_a  ✖
```

- 线程 1 拿着 A 等 B；B 在线程 2 手里。
- 线程 2 拿着 B 等 A；A 在线程 1 手里。
- 谁都不会先释放手上的锁（释放前必须拿到另一把），于是互相等死。

生活中的类比：两条单行桥交叉，东行的车占着路口西半段等东半段空出，西行的车占着东半段等西半段空出，谁也走不了。

## 2. 死锁的四个必要条件

>Coffman 条件。四个条件**同时满足**时死锁才可能发生（必要非充分）；反过来，**破坏任意一个**，死锁就不可能发生——这正是[死锁预防](/kb/os/死锁/03-死锁预防/)的出发点。

### 2.1 条件一：互斥（Mutual Exclusion）

**含义**：至少有一类资源是不可共享的，同一时刻只允许一个进程使用（比如互斥锁、打印机、单个磁盘分区）。

**为什么需要它**：如果所有资源都可共享，多个进程可以同时使用，根本不存在"等你释放"的理由。

**例子**：

```c
pthread_mutex_lock(&lock);        // 同一时刻只有持锁者能进入
// ... 临界区 ...
pthread_mutex_unlock(&lock);
```

### 2.2 条件二：持有并等待（Hold and Wait）

**含义**：进程已经持有了至少一个资源，又在等待获得其他进程持有的额外资源。

**例子**：

```c
pthread_mutex_lock(&lock_a);      // 已经持有 A
pthread_mutex_lock(&lock_b);      // 又在等 B —— 持有并等待
```

**为什么需要它**：如果进程要么一次拿全部、要么不拿，就不会出现"占着坑还去抢别的坑"的僵局。

### 2.3 条件三：非抢占（No Preemption）

**含义**：资源不能被系统强制剥夺，只能由持有者自愿释放。进程握着一个资源不放，等不到下一个就不释放。

**为什么需要它**：如果资源可被抢占，系统可以在必要时把进程 A 手上的锁夺给 B，等待链就断了。

**例子**：普通 `pthread_mutex` 就是非抢占的——你无法从持锁线程手里抢走它；而 CPU 时间片可被调度器抢占，所以 CPU 永远不会成为死锁资源。

### 2.4 条件四：循环等待（Circular Wait）

**含义**：存在一个进程等待环：P₀ 等 P₁ 占用的资源，P₁ 等 P₂ 占用的资源，…，Pₙ₋₁ 等 P₀ 占用的资源。

```
P0 ──等──► P1 ──等──► P2 ──等──► P0
```

**为什么需要它**：即使前面三个条件都满足，如果等待关系不成环（比如所有进程都按同一顺序申请锁），死锁也不会发生——至多是阻塞，而不会互相卡死。

### 2.5 四条件汇总

| 条件 | 直观说法 | 破不破坏它 | 对应预防手段 |
|---|---|---|---|
| 互斥 | 资源不能共享 | 几乎不可能（见 [死锁预防](/kb/os/死锁/03-死锁预防/)） | 尽量使用可共享资源（现实中受限） |
| 持有并等待 | 占着坑还等别的坑 | 预分配：一次全拿 | 一次性申请所有资源 |
| 非抢占 | 资源抢不走 | 允许剥夺 | 申请失败就释放已持资源 |
| 循环等待 | 等成一个环 | 打破环：统一申请顺序 | 资源全局编号，按序申请 |

::: warning 四条件"缺一不可"
死锁检测的正确姿势是"四个条件**同时满足才可能**死锁"。很多"死锁排查"实际只是线程阻塞（只满足持有并等待），并不满足循环等待——不是死锁，只要持有者最终会释放就能自愈。
:::

## 3. 资源类型

死锁分析里的"资源"不是简单的锁，教材把资源分成两个维度。

### 3.1 按是否可抢占分

| 类型 | 定义 | 例子 | 会不会参与死锁 |
|---|---|---|---|
| **可抢占（preemptible）** | 资源可以被系统强制收回而不会损坏 | CPU（时间片）、内存（可换出） | 一般不参与，调度器可强制剥夺 |
| **不可抢占（nonpreemptible）** | 收回会导致数据损坏或逻辑错误 | 互斥锁、文件写锁、打印机 | 死锁的主角 |

### 3.2 按是否可复用分

| 类型 | 定义 | 例子 | 说明 |
|---|---|---|---|
| **可复用（reusable）** | 用完后归还、可反复使用 | CPU、内存、磁盘、锁、文件 | 持有者用完必须释放，否则就会饥饿别人 |
| **可消耗（consumable）** | 被消耗后不再存在 | 消息、信号、I/O 缓冲区中的数据 | 典型是"生产者——消费者"之间传递的消息；若生产者等消费者释放缓冲区、消费者等生产者发消息，也会死锁 |

::: tip 可消耗资源也会死锁
一个经典例子：进程 P 等一个信号量（消息），同时持有一个缓冲区；进程 Q 持有消息，却在等一个空闲缓冲区。P 等 Q 的消息，Q 等 P 的缓冲区——互等死锁。
:::

## 4. 死锁 vs 饥饿 vs 活锁

三者都表现为"进程迟迟不前进"，但机制完全不同。

| 维度 | 死锁（Deadlock） | 饥饿（Starvation） | 活锁（Livelock） |
|---|---|---|---|
| 进程状态 | **永久阻塞**，被卡死 | 阻塞或可运行，但**永远轮不到**资源 | **一直运行**，但每步都在撤销/回退，毫无进展 |
| 根因 | 循环等待（结构性） | 资源分配策略不公平（调度问题） | 冲突响应策略互相让路（同步协议问题） |
| 是否占用 CPU | 否（阻塞态） | 可能占（被跳过而非被卡） | 是（忙等/反复重试，浪费 CPU） |
| 是否能自愈 | 不能，必须外力干预 | 可能自愈（其他进程离开后轮到它） | 可能自愈（冲突消失）也可能永久 |
| 典型例子 | 两把锁交叉申请 | SJF 短作业优先让长作业饿死 | 两个进程都检测到冲突，同时释放后退避，再同时重试，循环往复 |

**活锁的关键区别**：进程**没有阻塞**，而是在"抢占—退让"的循环里空转。现实中典型的活锁是：两个线程都用"先 trylock，失败就放弃并重试"的策略，同时撞车时互相让路，永远在让路。

## 5. 递归锁：一把锁引发的"自死锁"

### 5.1 自相矛盾的现象

非递归锁（如 Linux `pthread_mutex`，POSIX 未定义重入行为、多数实现直接死锁）**在同一线程里被连续加两次锁**时，会发生"自己等自己"：

```c
#include <pthread.h>
#include <stdio.h>

pthread_mutex_t lock = PTHREAD_MUTEX_INITIALIZER;

void helper(void) {
    pthread_mutex_lock(&lock);   // 第二次加锁：持锁者就是自己
    // ...
    pthread_mutex_unlock(&lock);
}

void work(void) {
    pthread_mutex_lock(&lock);   // 第一次加锁
    helper();                    // 单线程内递归调用 → 死锁（自死锁）
    pthread_mutex_unlock(&lock);
}

int main(void) {
    work();   // 永远阻塞在 helper 里的 pthread_mutex_lock
    return 0;
}
```

为什么这是"自相矛盾"？因为死锁四条件要求"一组进程互相等待"，而这里只有**一个线程**——它等的是自己手里那把锁，循环等待退化成了"自环"。它是死锁的特例，一般叫 **self-deadlock / recursive deadlock**。

### 5.2 解决方案：递归锁（reentrant mutex）

- C++：`std::recursive_mutex`，同一线程可多次加锁，内部维护"持有者线程 + 重入计数"，只有计数归零才真正释放。
- Java：`ReentrantLock`（synchronized 本身可重入）。
- Linux pthread 默认**不提供**递归互斥锁；若确实需要，可用 `PTHREAD_MUTEX_RECURSIVE` 初始化属性。

```cpp
#include &lt;mutex&gt;

std::recursive_mutex m;   // 同一线程可重入

void helper() { std::lock_guard<std::recursive_mutex> g(m); }
void work()   { std::lock_guard<std::recursive_mutex> g(m); helper(); }
// 不卡死：重入计数 +1，helper 返回后计数 -1
```

::: warning 递归锁是"止痛药"不是"补丁"
能用递归锁掩盖的往往是不良设计（锁的粒度太粗、函数边界不清）。递归锁无法解决多线程之间的真正死锁，只能解决"同线程重入"。更好的做法是：缩小临界区，让同一把锁绝不跨递归层。
:::

## 6. 本章小结

死锁是并发世界里"环"的形状：**每个进程都在等环内其他进程的资源**。识别它只需记住两条——四个必要条件要**同时**成立；它是结构性的循环等待，区别于调度不公平导致的饥饿、区别于忙等空转的活锁。而"递归锁自死锁"提醒我们：环可以退化到一个点（自己等自己）。理解到这里，就为后续的三板斧（[死锁预防](/kb/os/死锁/03-死锁预防/) / [死锁避免与银行家算法](/kb/os/死锁/04-死锁避免与银行家算法/) / [死锁实战与内核实现](/kb/os/死锁/05-死锁实战与内核实现/)）备好了全部概念弹药。

## 7. 自测题

1. 死锁四必要条件是哪四个？各自一句话解释。
   - 互斥（资源不可共享）、持有并等待（占着资源还等别的）、非抢占（资源只能自愿释放）、循环等待（等待关系成环）。

2. 为什么说"互斥"这个条件很难被破坏？
   - 因为很多资源（互斥锁、打印机、文件写锁）从本质上就不能同时共享，强行共享会破坏数据一致性。

3. 饥饿和死锁的本质区别是什么？
   - 饥饿是调度/分配策略不公平，进程"一直轮不到"，可能自愈；死锁是结构性循环等待，无外力干预不会自愈，进程永久阻塞。

4. 活锁里的进程是"忙等"还是"阻塞"？
   - 忙等（可运行状态、持续占用 CPU），它在反复"试了又退让"，有执行但无进展。

5. 非递归锁在同一线程里加两次，算满足哪几个死锁条件？
   - 互斥（锁不可共享）、持有并等待（已持有又申请）、非抢占（抢不回来）、循环等待（自己等自己，自环）。四个条件"退化版"同时成立，属于自死锁。

6. 一个只满足"持有并等待"但不满足"循环等待"的线程，最终会怎样？
   - 只是阻塞，不是死锁：持有者在完成工作后会释放资源，等待者最终拿到资源继续运行。

7. 可消耗资源（如消息）会不会导致死锁？举一个例子。
   - 会。生产者占满缓冲区等消费者取走消息，消费者等生产者腾出缓冲区，两者互等即成死锁。
