容器应该可替换，数据不能随容器一起消失。本篇区分可写层、volume、bind mount 和 tmpfs，并建立备份与恢复意识。

## 1. 容器文件系统为什么不是数据盘

镜像层是只读的，运行容器会增加一个可写层：

```text
容器可写层    <- 日志、临时修改、新文件
镜像层 N      <- 只读
镜像层 ...    <- 只读
基础镜像层    <- 只读
```

删除容器时，可写层随之删除。即使容器未删除，它也不适合作为业务数据盘：

- 与单个容器生命周期绑定。
- 难以迁移和备份。
- 写时复制可能有额外开销。
- 重新创建容器不会自动带回数据。

## 2. 四种数据位置

| 类型 | 由谁管理 | 典型用途 | 生命周期 |
| --- | --- | --- | --- |
| 容器可写层 | Docker | 临时运行状态 | 随容器 |
| Named volume | Docker | 数据库、队列、上传文件 | 独立于容器 |
| Bind mount | 用户/宿主机 | 源码、明确配置文件 | 由宿主路径决定 |
| tmpfs | 内存 | 临时文件、敏感短期数据 | 容器停止即消失 |

选择原则：

- 持久服务数据优先 named volume。
- 开发源码同步或明确宿主文件优先 bind mount。
- 不需要持久化的敏感/高速临时数据用 tmpfs。
- 镜像内固定资源通过 Dockerfile `COPY`，不是运行时挂载。

## 3. 为什么教学优先 `--mount`

简写 `-v` 很常见：

```bash
docker run -v mydata:/data alpine:3.22
```

本教程优先显式语法：

```bash
docker run --mount type=volume,source=mydata,target=/data alpine:3.22
```

`--mount` 的类型、源和目标更清楚，也能避免 bind 源路径拼错时某些简写行为造成误解。

## 4. Named volume 基础

创建：

```bash
docker volume create app-data
```

查看：

```bash
docker volume ls
docker volume inspect app-data
```

写入：

```bash
docker run --rm \
  --mount type=volume,source=app-data,target=/data \
  alpine:3.22 \
  sh -c 'date -u > /data/created-at.txt'
```

换一个容器读取：

```bash
docker run --rm \
  --mount type=volume,source=app-data,target=/data,readonly \
  alpine:3.22 \
  cat /data/created-at.txt
```

容器已经更换，数据仍存在。这就是生命周期解耦。

删除前确认用途：

```bash
docker volume rm app-data
```

## 5. 自动创建与显式创建

引用不存在的 named volume 时，Docker 可以自动创建：

```bash
docker run --rm \
  --mount type=volume,source=auto-data,target=/data \
  alpine:3.22 true
```

重要数据更建议显式创建或由 Compose 声明，这能使名称、driver、labels 和管理责任清晰。

添加标签：

```bash
docker volume create \
  --label com.example.project=tutorial \
  app-data
```

## 6. Bind mount 基础

把当前目录挂到容器：

```bash
docker run --rm \
  --mount type=bind,source="$PWD",target=/workspace,readonly \
  alpine:3.22 \
  ls -la /workspace
```

特点：

- 容器直接看到宿主路径。
- 宿主文件修改可立即反映到容器。
- 容器对可写挂载的修改会直接影响宿主文件。
- 路径依赖宿主机，移植性弱于 volume。
- Desktop 上会跨虚拟机文件共享边界。

配置文件应优先只读：

```bash
docker run --rm \
  --mount type=bind,source="$PWD/nginx.conf",target=/etc/nginx/nginx.conf,readonly \
  nginx:1.28-alpine nginx -t
```

源文件必须存在，且文件/目录类型要与目标用途一致。

## 7. Bind mount 会遮蔽镜像内容

若镜像的 `/app` 已有文件，再把空目录挂到 `/app`：

```bash
docker run --rm \
  --mount type=bind,source="$PWD/empty",target=/app \
  app:1.0.0
```

容器看到的是宿主目录，镜像原有 `/app` 内容被挂载遮蔽，并非被删除。卸载通常意味着重建不带该 mount 的容器。

这是“镜像里明明有文件，运行后却不见了”的常见原因。

## 8. 只读挂载与只读根文件系统

只读 volume：

```bash
docker run --rm \
  --mount type=volume,source=app-data,target=/data,readonly \
  alpine:3.22 touch /data/test
```

命令应因只读而失败。

只读根文件系统：

```bash
docker run --rm \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  alpine:3.22 \
  sh -c 'echo ok > /tmp/result && cat /tmp/result'
```

设计目标是只开放必要写入点，而不是让应用任意写整个根文件系统。

## 9. tmpfs

```bash
docker run --rm \
  --mount type=tmpfs,target=/run/secrets,tmpfs-size=1048576,tmpfs-mode=0700 \
  alpine:3.22 \
  sh -c 'echo transient > /run/secrets/value && cat /run/secrets/value'
```

适用场景：

- 运行期临时文件。
- 不希望落入容器可写层的数据。
- 可丢失的缓存。

注意：

- 受内存和 swap 行为影响。
- 停止容器后数据消失。
- tmpfs 不是备份和长期 Secret 管理方案。
- 必须设置合理大小，避免内存失控。

## 10. 数据库使用 named volume

```bash
docker volume create postgres-data
```

```bash
docker run -d \
  --name postgres-lab \
  --env POSTGRES_DB=app \
  --env POSTGRES_USER=app \
  --env POSTGRES_PASSWORD='replace-this-development-password' \
  --mount type=volume,source=postgres-data,target=/var/lib/postgresql \
  postgres:18-alpine
```

等待就绪：

```bash
docker exec postgres-lab pg_isready -U app -d app
```

写入数据：

```bash
docker exec postgres-lab \
  psql -U app -d app -c 'create table notes(id int primary key, body text);'
docker exec postgres-lab \
  psql -U app -d app -c "insert into notes values (1, 'persistent');"
```

删除并重建容器：

```bash
docker rm -f postgres-lab
docker run -d \
  --name postgres-lab \
  --env POSTGRES_DB=app \
  --env POSTGRES_USER=app \
  --env POSTGRES_PASSWORD='replace-this-development-password' \
  --mount type=volume,source=postgres-data,target=/var/lib/postgresql \
  postgres:18-alpine
```

查询原数据：

```bash
docker exec postgres-lab psql -U app -d app -c 'select * from notes;'
```

::: warning
示例密码只用于本地练习。生产密码不应写入 shell 历史、Compose 文件或公开仓库。
:::

## 11. 初始化目录不是迁移系统

许多数据库官方镜像会在**空数据目录首次初始化**时执行指定目录中的脚本，例如 PostgreSQL 的 `/docker-entrypoint-initdb.d`。

这类脚本：

- 通常只在数据目录为空时执行。
- 适合首次创建库和测试数据。
- 不会在已有 volume 上自动重跑。
- 不能代替 Flyway、Liquibase、Alembic 等版本化迁移方案。

升级应用时应显式管理 schema 迁移，并准备回滚或前向修复方案。

## 12. Compose 中声明 volume

```yaml
services:
  db:
    image: postgres:18-alpine
    environment:
      POSTGRES_DB: app
      POSTGRES_USER: app
      POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:?set POSTGRES_PASSWORD}
    volumes:
      - type: volume
        source: postgres_data
        target: /var/lib/postgresql

volumes:
  postgres_data:
```

这里使用 Compose Specification，不写废弃的顶层 `version`。

启动后实际 volume 名通常带项目名前缀：

```bash
docker compose up -d
docker volume ls
docker compose down
```

`docker compose down` 默认不删除 named volume；以下命令会删除：

```bash
docker compose down --volumes
```

对数据库执行前必须确认数据已备份或确实可丢弃。

## 13. 外部 volume

已有基础设施管理的 volume：

```yaml
services:
  db:
    image: postgres:18-alpine
    volumes:
      - db_data:/var/lib/postgresql

volumes:
  db_data:
    external: true
    name: production-postgres-data
```

Compose 不负责创建或删除 external volume。部署前必须确保它存在：

```bash
docker volume inspect production-postgres-data
```

## 14. Compose 中 bind mount

```yaml
services:
  web:
    image: nginx:1.28-alpine
    volumes:
      - type: bind
        source: ./nginx.conf
        target: /etc/nginx/nginx.conf
        read_only: true
```

相对路径以 Compose 项目解析规则为准。部署脚本中先执行：

```bash
docker compose config
```

检查最终路径和插值结果。

## 15. 权限、UID 与 GID

容器内用户写宿主 bind mount 时，Linux 最终按数字 UID/GID 判断权限，不按用户名文本判断。

先检查容器用户：

```bash
docker run --rm alpine:3.22 id
```

检查文件数字所有者：

```bash
ls -ln
```

稳妥方案：

- 镜像使用明确非 root UID/GID。
- 部署前让目标目录归该 UID/GID 所有。
- 只授予必要读写权限。
- 避免为了省事使用 `chmod 777`。
- 在 SELinux 主机上正确处理标签，而不是关闭 SELinux。

Desktop 文件共享的权限语义可能与原生 Linux 不同，生产前必须在目标平台测试。

## 16. SELinux 提示

在启用 SELinux 的 Linux 上，bind mount 即使 Unix 权限正确，也可能被策略阻止。短语法常见 `:z`/`:Z` 选项，但其影响取决于共享需求：

- `z`：内容可被多个容器共享。
- `Z`：内容获得私有标签。

执行重新标记前阅读官方说明，尤其不要对 `/home`、`/usr` 等宽泛系统目录随意应用标签变更。

## 17. 备份不是复制正在变化的数据目录

数据库运行时直接打包其文件目录可能得到不一致备份。优先顺序：

1. 使用数据库原生逻辑备份，如 `pg_dump`。
2. 使用存储快照前执行数据库要求的一致性流程。
3. 记录镜像版本、schema 版本和恢复步骤。
4. 定期执行恢复演练。

逻辑备份示例：

```bash
docker exec postgres-lab \
  pg_dump -U app -d app --format=custom \
  > app.dump
```

验证备份文件存在且非空：

```bash
ls -lh app.dump
```

注意重定向由宿主 shell 执行，因此 `app.dump` 位于宿主当前目录。

## 18. 恢复演练

创建独立测试 volume 和容器：

```bash
docker volume create postgres-restore-test
docker run -d \
  --name postgres-restore \
  -e POSTGRES_DB=restore_test \
  -e POSTGRES_USER=app \
  -e POSTGRES_PASSWORD='temporary-test-password' \
  --mount type=volume,source=postgres-restore-test,target=/var/lib/postgresql \
  postgres:18-alpine
```

等待就绪并恢复：

```bash
until docker exec postgres-restore pg_isready -U app -d restore_test; do sleep 1; done
docker exec -i postgres-restore \
  pg_restore -U app -d restore_test --clean --if-exists \
  < app.dump
```

检查关键表和行数。恢复命令应按实际备份参数和数据库权限调整。

清理测试资源：

```bash
docker rm -f postgres-restore
docker volume rm postgres-restore-test
```

## 19. 通用文件型 volume 归档

对已停写或已保证一致性的普通文件 volume，可用临时容器读取并归档：

```bash
docker run --rm \
  --mount type=volume,source=app-data,target=/source,readonly \
  --mount type=bind,source="$PWD/backups",target=/backup \
  alpine:3.22 \
  tar -czf /backup/app-data.tgz -C /source .
```

恢复到空 volume：

```bash
docker volume create app-data-restored
docker run --rm \
  --mount type=volume,source=app-data-restored,target=/target \
  --mount type=bind,source="$PWD/backups",target=/backup,readonly \
  alpine:3.22 \
  tar -xzf /backup/app-data.tgz -C /target
```

先校验归档完整性和来源，再恢复。数据库优先采用数据库原生工具。

## 20. 清理策略

列出 volume：

```bash
docker volume ls
docker volume ls --filter dangling=true
```

查看容器实际引用：

```bash
docker ps -a --filter volume=postgres-data
```

删除明确无用的 volume：

```bash
docker volume rm &lt;volume-name&gt;
```

批量清理风险高：

```bash
docker volume prune
```

执行前至少确认：

- 是否有已停止但将来要恢复的服务。
- volume 是否由外部流程管理。
- 是否存在有效备份。
- volume 标签和名称是否能说明所有者。

## 21. 常见陷阱

### 删除容器后数据丢失

数据写在可写层，未挂载目标数据目录。用 `docker inspect` 检查 `.Mounts`，并核对应用真实写入路径。

### 挂载了 volume，数据还是不见

- target 路径写错。
- 应用配置把数据写到另一处。
- 使用了另一个同名/带前缀 volume。
- Docker context 或 Compose project 不同。

### `permission denied`

检查 UID/GID、只读标志、父目录权限、SELinux/AppArmor 和应用降权行为。不要第一反应改成 root。

### Compose 重建后用了“新数据库”

项目名变化可能让 Compose 创建另一个前缀 volume。运行：

```bash
docker compose ls
docker volume ls
docker compose config
```

### 把宿主机数据库目录直接挂给另一版本

数据库物理格式可能不兼容。升级应遵循数据库官方升级流程，不能只改镜像 tag。

## 22. 决策清单

- [ ] 业务数据使用 named volume 或外部存储。
- [ ] 开发源码才使用可写 bind mount。
- [ ] 配置和证书挂载默认只读。
- [ ] 临时数据使用有大小限制的 tmpfs。
- [ ] 已确认应用真实数据目录。
- [ ] 容器以非 root 用户运行且目录权限匹配。
- [ ] 有备份保留策略和异地副本。
- [ ] 定期在独立环境恢复验证。
- [ ] 清楚 `compose down --volumes` 的后果。
- [ ] 数据库升级遵循其官方迁移流程。

## 23. 练习

1. 创建 `notes-data`，由一个容器写入文件，再由另一个只读容器读取。
2. 尝试在只读挂载中写文件，观察错误。
3. 用 bind mount 只读查看当前目录。
4. 使用 tmpfs 写入临时文件，容器退出后重新运行验证数据消失。
5. 给 volume 添加项目标签并按标签筛选。
6. 为普通文件 volume 做归档，并恢复到新 volume。
