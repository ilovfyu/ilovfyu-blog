网络问题最容易混淆三件事：应用监听地址、容器端口和宿主机发布端口。本篇从数据流向开始拆解。

## 1. 三层地址

假设运行：

```bash
docker run -d --name web -p 127.0.0.1:8080:80 nginx:1.28-alpine
```

访问路径是：

```text
客户端 -> 宿主机 127.0.0.1:8080 -> Docker 转发 -> 容器 web:80
```

端口参数顺序永远从外到内：

```text
[宿主机 IP:]宿主机端口:容器端口[/协议]
```

因此：

- 浏览器访问 `http://127.0.0.1:8080`。
- Nginx 在容器里监听 `80`。
- 把顺序写成 `80:8080` 会改变含义。
- `127.0.0.1` 表示只允许宿主机本地访问。

## 2. `EXPOSE` 不会发布端口

Dockerfile 中：

```dockerfile
EXPOSE 8080
```

它只是镜像元数据，表达应用预计监听 `8080`。它不会：

- 创建宿主机监听端口；
- 配置防火墙；
- 让公网能够访问；
- 自动替代 `--publish`。

真正发布端口必须使用：

```bash
docker run -p 127.0.0.1:8080:8080 app:1.0.0
```

或 Compose 的 `ports`。

## 3. 应用必须监听正确地址

容器内应用若只监听 `127.0.0.1`，通常无法通过容器网络或端口发布访问。

容器服务一般应监听：

```text
0.0.0.0:8080
```

这里的 `0.0.0.0` 是容器自己的全部接口，不等于一定向公网开放。公网暴露取决于端口发布、宿主机接口、防火墙和云安全组。

诊断监听地址，可在有工具的镜像中执行：

```bash
docker exec web ss -lntp
```

若镜像没有 `ss`，优先查看应用启动日志或使用诊断容器，不要临时污染生产容器。

## 4. 端口发布形式

### 仅本机访问

```bash
docker run -d -p 127.0.0.1:8080:80 nginx:1.28-alpine
```

适用于开发服务、管理界面和由宿主机反向代理接入的服务。

### 监听所有宿主机接口

```bash
docker run -d -p 8080:80 nginx:1.28-alpine
```

省略 IP 通常等价于发布到所有地址。不要误以为宿主机防火墙一定会阻挡它；发布前明确评估暴露面。

### UDP

```bash
docker run -d -p 127.0.0.1:5353:53/udp &lt;dns-image&gt;:&lt;version&gt;
```

TCP 与 UDP 是不同映射，必要时分别声明。

### 随机宿主机端口

```bash
docker run -d --name random-web -p 127.0.0.1::80 nginx:1.28-alpine
docker port random-web
```

适合并行测试，生产入口通常需要稳定端口或负载均衡器发现机制。

### `-P` 的含义

```bash
docker run -d -P nginx:1.28-alpine
```

大写 `-P` 会把镜像声明的 exposed ports 发布到随机宿主机端口。它与小写 `-p` 不同，也不能证明 `EXPOSE` 自己发布了端口。

## 5. 查看实际映射

```bash
docker ps --format 'table {{.Names}}\t{{.Ports}}'
docker port web
docker inspect --format '{{json .NetworkSettings.Ports}}' web
```

从宿主机测试：

```bash
curl -v http://127.0.0.1:8080
```

分层测试比“反复重启”更有效：

1. 应用进程是否存活？
2. 容器内是否监听目标端口？
3. 端口是否正确发布？
4. 宿主机本地是否可访问？
5. 防火墙和云安全组是否允许远程访问？
6. DNS、反向代理和 TLS 是否正确？

## 6. Docker 网络驱动概览

```bash
docker network ls
```

| 驱动 | 适用场景 | 关键特点 |
| --- | --- | --- |
| `bridge` | 单机容器通信 | Linux 默认常见选择 |
| `host` | 与宿主共享网络命名空间 | 隔离更少、端口语义不同 |
| `none` | 禁用常规网络 | 高隔离或特殊网络 |
| `overlay` | 多主机编排 | 常见于 Swarm |
| `macvlan`/`ipvlan` | 接入物理网络 | 需网络规划与交换机配合 |

日常单机应用应优先使用**用户定义 bridge**。

## 7. 为什么不用默认 bridge 做应用网络

创建网络：

```bash
docker network create app-net
```

启动后端：

```bash
docker run -d \
  --name api \
  --network app-net \
  nginx:1.28-alpine
```

用同网络诊断容器访问：

```bash
docker run --rm \
  --network app-net \
  curlimages/curl:8.16.0 \
  http://api:80
```

用户定义 bridge 提供内置 DNS，容器可通过名称 `api` 解析。优势包括：

- 容器名 DNS，不依赖易变 IP。
- 更明确的隔离边界。
- 容器可动态加入和离开网络。
- 每个应用可拥有独立网络。

清理：

```bash
docker rm -f api
docker network rm app-net
```

## 8. 容器间访问不需要发布端口

同一个用户定义网络中的容器可直接访问目标容器端口：

```text
http://api:8080
```

无需先发布到宿主机。`ports`/`-p` 主要服务于“宿主机或外部客户端进入容器”。

错误思路：

```text
web 容器 -> localhost:8080 -> api 容器
```

正确思路：

```text
web 容器 -> api:8080
```

容器内的 `localhost` 指当前容器本身，不是宿主机，也不是另一个容器。

## 9. DNS 与服务发现

检查网络：

```bash
docker network inspect app-net
```

网络别名：

```bash
docker network connect --alias backend app-net api
```

同网络容器随后可访问 `backend`。应用应在每次新连接时正常解析 DNS，并处理目标容器重建导致的 IP 变化。

不要把 `docker inspect` 得到的容器 IP 写死在配置里。

## 10. 一个容器连接多个网络

创建前后端网络：

```bash
docker network create frontend-net
docker network create backend-net
```

代理可同时连接两者，数据库只连接后端网络：

```bash
docker run -d --name proxy --network frontend-net nginx:1.28-alpine
docker network connect backend-net proxy
docker run -d --name db --network backend-net postgres:18-alpine
```

这形成清晰边界：公网入口无需和数据库共享前端网络。网络隔离不是身份认证的替代品，数据库仍需密码、TLS 和最小权限。

## 11. 动态连接与断开

```bash
docker network connect app-net web
docker network disconnect app-net web
```

容器可连接多个网络，每个网络拥有独立地址和别名。断开前确认应用没有活动依赖。

## 12. 访问宿主机服务

Docker Desktop 通常提供：

```text
host.docker.internal
```

例如宿主机开发 API 在 `8000`：

```bash
docker run --rm curlimages/curl:8.16.0 \
  http://host.docker.internal:8000
```

Linux Engine 可按环境显式映射 host gateway：

```bash
docker run --rm \
  --add-host host.docker.internal:host-gateway \
  curlimages/curl:8.16.0 \
  http://host.docker.internal:8000
```

宿主机服务也必须监听容器能够到达的地址，并受防火墙保护。生产架构不要无意依赖 Desktop 专用行为。

## 13. Host 网络模式

```bash
docker run --rm --network host nginx:1.28-alpine
```

在支持的平台上，容器与宿主共享网络命名空间：

- 通常不再使用 `-p` 做 NAT 映射。
- 应用端口直接占用宿主机端口。
- 网络隔离明显减少。
- 平台支持和行为存在差异。

只有在性能、端口规模或特殊网络需求明确时才使用，不应作为“网络不会配”的绕过方案。

## 14. `none` 网络

```bash
docker run --rm --network none alpine:3.22 ip addr
```

容器仅有 loopback 等最小网络能力。适合不需要联网的批处理任务和隔离实验。

## 15. 自定义子网

```bash
docker network create \
  --driver bridge \
  --subnet 172.30.0.0/24 \
  app-net
```

只有在避免 VPN、局域网或其他 Docker 网络地址冲突时才显式规划子网。不要随意选择可能与企业网络重叠的网段。

固定容器 IP 往往降低可维护性。服务发现优先使用 DNS 名称。

## 16. Compose 中的网络

```yaml
services:
  web:
    image: nginx:1.28-alpine
    ports:
      - "127.0.0.1:8080:80"
    networks:
      - frontend

  api:
    image: ghcr.io/example/api:1.4.2
    networks:
      - frontend
      - backend

  db:
    image: postgres:18-alpine
    networks:
      - backend

networks:
  frontend:
  backend:
    internal: true
```

Compose Specification 不需要顶层 `version`。Compose 默认会为项目创建网络，服务名就是 DNS 名。

`internal: true` 限制该网络的外部连接能力，仍应结合具体平台测试，并保留认证和授权。

## 17. `ports` 与 `expose`

Compose 示例：

```yaml
services:
  api:
    image: ghcr.io/example/api:1.4.2
    expose:
      - "8080"
```

`expose` 表达容器端口信息，不发布到宿主机。同网络服务即使不写 `expose`，只要应用监听正确端口，通常也能直接访问。

发布到宿主机使用：

```yaml
ports:
  - "127.0.0.1:8080:8080"
```

## 18. 数据库为什么通常不发布端口

应用和数据库同在 Docker 网络中时：

```text
DATABASE_URL=postgresql://app:password@db:5432/app
```

数据库无需：

```yaml
ports:
  - "5432:5432"
```

不发布可以缩小宿主机暴露面。开发者确实需要从宿主机连接时，可只绑定回环地址：

```yaml
ports:
  - "127.0.0.1:5432:5432"
```

## 19. 常见网络故障定位

### `connection refused`

通常表示已经到达目标地址，但目标端口没有监听：

- 应用尚未启动。
- 应用监听错端口。
- 应用只监听容器内 `127.0.0.1`。
- 使用了错误的宿主/容器端口。

### 超时

更可能是路由、防火墙、安全组、代理或网络隔离。检查目标是否可达，再检查端口。

### `Could not resolve host`

- 两个容器不在同一用户定义网络。
- 使用了错误服务名或别名。
- DNS 配置被覆盖。
- 容器刚重建，应用缓存了旧解析。

### 宿主能访问，另一个容器不能

不要从另一个容器访问宿主机发布地址；让双方加入同一网络，用目标服务名和容器端口。

### 本机能访问，远程不能

- 端口只绑定 `127.0.0.1`，这是有意的安全边界。
- 宿主机防火墙阻止。
- 云安全组未开放。
- 路由或上游负载均衡配置错误。

不要为解决远程访问而盲目关闭防火墙。

## 20. 诊断工具箱

查看容器网络配置：

```bash
docker inspect --format '{{json .NetworkSettings.Networks}}' api
docker network inspect app-net
```

使用临时诊断容器：

```bash
docker run --rm -it \
  --network app-net \
  nicolaka/netshoot:v0.14 \
  sh
```

容器中可按需使用：

```bash
getent hosts api
curl -v http://api:8080/health
nc -vz db 5432
```

诊断镜像应固定审核过的版本，不在生产网络长期运行，也不要授予不必要 capabilities。

## 21. 安全清单

- [ ] 只发布确实需要从宿主机进入的端口。
- [ ] 开发和管理端口优先绑定 `127.0.0.1`。
- [ ] 容器间使用用户定义 bridge 与服务名 DNS。
- [ ] 数据库不因“方便”直接发布到公网接口。
- [ ] 前端、后端和数据层按需要划分网络。
- [ ] 网络隔离之外仍启用认证、授权和 TLS。
- [ ] 不写死容器 IP。
- [ ] 明白 `EXPOSE` 不会发布端口。
- [ ] 明白 `宿主机端口:容器端口` 的顺序。

## 22. 练习

1. 创建 `lab-net`。
2. 在其中启动名为 `web` 的 Nginx，不发布端口。
3. 用 curl 诊断容器通过 `http://web:80` 访问。
4. 再把一个 Nginx 发布为 `127.0.0.1:8088:80`。
5. 比较从宿主机和同网络容器访问时使用的地址。
6. 检查 `docker network inspect lab-net`。
7. 删除容器后再删除网络。

参考命令：

```bash
docker network create lab-net
docker run -d --name web --network lab-net nginx:1.28-alpine
docker run --rm --network lab-net curlimages/curl:8.16.0 http://web:80
docker run -d --name published-web -p 127.0.0.1:8088:80 nginx:1.28-alpine
curl http://127.0.0.1:8088
docker network inspect lab-net
docker rm -f web published-web
docker network rm lab-net
```
