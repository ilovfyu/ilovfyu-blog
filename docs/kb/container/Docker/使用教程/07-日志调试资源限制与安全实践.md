容器能启动只是起点。可运维的容器必须可观察、可诊断、有资源边界，并默认采用最小权限。

## 1. 排障顺序

面对“服务不可用”，按层次收集事实：

1. Docker daemon 是否健康？
2. 容器是否存在、运行或反复重启？
3. 主进程退出码和错误是什么？
4. 日志是否显示配置、权限或依赖错误？
5. 健康检查为什么失败？
6. 端口、网络 DNS 和监听地址是否正确？
7. mount 是否存在，权限和容量是否正常？
8. 是否触发 OOM、CPU、PID 或磁盘限制？
9. 安全约束是否阻止了应用的未声明行为？

先观察，再改变环境。不要一上来就重建、清缓存或关闭安全策略。

## 2. 容器状态

```bash
docker ps -a
docker inspect --format '{{json .State}}' &lt;container&gt;
```

重点字段：

| 字段 | 含义 |
| --- | --- |
| `Status` | created/running/exited 等 |
| `Running` | 当前是否运行 |
| `ExitCode` | 主进程退出码 |
| `Error` | runtime 启动错误 |
| `OOMKilled` | 是否因内存不足被杀 |
| `StartedAt` | 启动时间 |
| `FinishedAt` | 结束时间 |
| `Health` | 健康检查结果 |

简洁输出：

```bash
docker inspect --format \
  'status={{.State.Status}} exit={{.State.ExitCode}} oom={{.State.OOMKilled}} error={{json .State.Error}}' \
  &lt;container&gt;
```

## 3. 退出码快速判断

常见但非绝对：

| 退出码 | 常见解释 |
| --- | --- |
| `0` | 正常完成 |
| `1` | 应用通用错误 |
| `126` | 命令存在但不能执行 |
| `127` | 命令不存在 |
| `137` | 收到 SIGKILL，可能 OOM 或人为 kill |
| `143` | 收到 SIGTERM 后退出 |

`137` 不等于必然 OOM，必须检查 `.State.OOMKilled`、daemon/内核日志和监控。

## 4. 日志基础

```bash
docker logs &lt;container&gt;
docker logs --tail 100 &lt;container&gt;
docker logs --since 15m --timestamps &lt;container&gt;
docker logs --follow &lt;container&gt;
```

Compose：

```bash
docker compose logs --follow --tail 100
docker compose logs --since 10m api db
```

应用日志原则：

- 普通事件写 stdout。
- 错误写 stderr。
- 单条日志包含时间、级别、服务、事件和关联 ID。
- 不记录密码、token、Cookie、完整身份证号等秘密或敏感数据。
- 结构化 JSON 便于机器检索。
- 多行堆栈要保证采集端能正确合并或解析。

## 5. 日志驱动与轮转

查看容器日志驱动：

```bash
docker inspect --format '{{.HostConfig.LogConfig.Type}}' &lt;container&gt;
```

默认 `json-file` 若不限制，日志可能持续占用磁盘。单容器配置：

```bash
docker run -d \
  --name web \
  --log-driver local \
  --log-opt max-size=10m \
  --log-opt max-file=3 \
  nginx:1.28-alpine
```

Compose：

```yaml
services:
  web:
    image: nginx:1.28-alpine
    logging:
      driver: local
      options:
        max-size: "10m"
        max-file: "3"
```

`local` 驱动针对本地存储进行了优化并支持轮转。集中日志系统可使用对应驱动或采集 agent，但要评估网络故障时阻塞、丢失与缓冲行为。

不要直接手工截断 Docker 管理的日志文件；通过日志策略和 daemon 配置治理。

## 6. 日志不是审计和指标

- 日志回答“发生了什么细节”。
- 指标回答“趋势和阈值是否异常”。
- Trace 回答“一个请求跨服务经过哪里”。
- 审计记录回答“谁在何时执行了什么敏感操作”。

生产可观测性至少应覆盖：

- 请求率、错误率、延迟。
- CPU、内存、磁盘、网络、PID。
- 容器重启和健康状态。
- volume 容量与备份结果。
- 证书、镜像和依赖过期情况。

## 7. `exec` 调试

```bash
docker exec -it &lt;container&gt; sh
```

单条命令比交互 shell 更容易记录：

```bash
docker exec &lt;container&gt; id
docker exec &lt;container&gt; env
docker exec &lt;container&gt; ls -la /app
```

分享 `env` 输出前脱敏。生产镜像可能没有 shell，这是减少攻击面的正常结果。

`exec` 中的临时修改不可复现，容器重建后消失。确认根因后把修复放回 Dockerfile、Compose 或外部配置。

## 8. 临时诊断容器

网络诊断：

```bash
docker run --rm -it \
  --network container:&lt;container&gt; \
  nicolaka/netshoot:v0.14 \
  sh
```

共享目标容器网络命名空间后，可检查：

```bash
ss -lntp
dig example.com
curl -v http://127.0.0.1:8080/health
```

另一种方式是加入同一用户定义网络：

```bash
docker run --rm \
  --network app-net \
  curlimages/curl:8.16.0 \
  -v http://api:8080/health
```

诊断镜像要固定版本、限制权限、用后即删。不要顺手挂载 Docker socket 或宿主机根目录。

## 9. 进程与 PID 1

```bash
docker top &lt;container&gt;
docker inspect --format '{{.State.Pid}}' &lt;container&gt;
```

容器主进程是容器 PID 1，需要：

- 正确接收并处理 `SIGTERM`。
- 回收孤儿子进程。
- 在超时前完成优雅关闭。

Dockerfile 使用 exec form：

```dockerfile
CMD ["node", "server.js"]
```

若应用会产生无法自行回收的子进程，可启用轻量 init：

```bash
docker run --init app:1.4.2
```

Compose：

```yaml
services:
  app:
    image: app:1.4.2
    init: true
    stop_grace_period: 30s
```

`init` 不能替代应用自身的信号处理。

## 10. 实时资源观察

```bash
docker stats
docker stats --no-stream &lt;container&gt;
```

自定义输出：

```bash
docker stats --no-stream \
  --format 'table {{.Name}}\t{{.CPUPerc}}\t{{.MemUsage}}\t{{.MemPerc}}\t{{.PIDs}}'
```

同时检查磁盘：

```bash
docker system df --verbose
docker inspect --size &lt;container&gt;
```

容器可写层突然增大常见原因：应用把日志、上传、缓存或数据库文件写错位置。

## 11. 内存限制

```bash
docker run --rm \
  --memory 512m \
  --memory-swap 512m \
  app:1.4.2
```

这里总内存+swap 上限与内存上限相同，等价于不提供额外 swap 空间的常见配置意图；具体行为受宿主机 cgroup 和 swap 配置影响，应在目标环境验证。

Compose：

```yaml
services:
  app:
    image: app:1.4.2
    mem_limit: 512m
```

内存预算包括：

- 应用堆。
- 线程栈。
- 原生库和运行时。
- 文件缓存与 mmap。
- sidecar 不在同一个容器预算内，但占宿主总量。

JVM、Node.js 等运行时最好显式配置与容器限制匹配的堆上限，并留出堆外空间。

## 12. OOM 排查

```bash
docker inspect --format '{{.State.OOMKilled}}' &lt;container&gt;
docker stats --no-stream &lt;container&gt;
```

处理顺序：

1. 确认是否 OOM，而非人工 `kill`。
2. 查看内存增长曲线和请求负载。
3. 检查泄漏、无限缓存和并发上限。
4. 校准应用堆与容器限制。
5. 只有确认业务确需后才提高限制。

单纯增大内存可能推迟故障，不能修复泄漏。

## 13. CPU 限制

限制最多使用约 1.5 个 CPU：

```bash
docker run --rm --cpus 1.5 app:1.4.2
```

绑定 CPU：

```bash
docker run --rm --cpuset-cpus 0-1 app:1.4.2
```

Compose：

```yaml
services:
  app:
    image: app:1.4.2
    cpus: 1.5
```

CPU 限流表现通常是延迟升高，不一定让容器退出。压测时观察 throttling、队列和尾延迟。

## 14. PID 限制

```bash
docker run --rm --pids-limit 200 app:1.4.2
```

Compose：

```yaml
services:
  app:
    image: app:1.4.2
    pids_limit: 200
```

PID 限制可降低 fork bomb 和异常线程/进程增长风险。上限要覆盖应用工作模型和峰值。

## 15. Block I/O 与磁盘

容器的写层和 volume 最终消耗宿主存储。重点治理：

- 日志轮转。
- 数据库 volume 容量告警。
- 构建缓存清理策略。
- 临时文件生命周期。
- inode 使用率。
- 备份与快照占用。

```bash
docker system df
docker system df --verbose
docker builder prune --filter 'until=168h'
```

执行 prune 前确认共享 builder 和缓存需求。不要自动清理未知 volume。

## 16. 健康检查设计

Compose：

```yaml
healthcheck:
  test: ["CMD", "/app/server", "healthcheck"]
  interval: 30s
  timeout: 3s
  retries: 3
  start_period: 20s
```

区分：

- Liveness：进程是否陷入不可恢复状态。
- Readiness：当前是否适合接收流量。
- Startup：慢启动阶段是否仍在允许窗口。

Docker 单机健康检查模型没有完整等价于所有编排平台的三类探针。设计时避免把昂贵查询和全部下游依赖塞入一个检查，防止依赖抖动造成级联故障。

查看历史：

```bash
docker inspect --format '{{json .State.Health}}' &lt;container&gt;
```

## 17. 重启循环

```bash
docker ps -a
docker logs --tail 200 &lt;container&gt;
docker inspect --format '{{.RestartCount}}' &lt;container&gt;
```

常见原因：

- 配置或 secret 缺失。
- 启动命令错误。
- 数据目录权限错误。
- 依赖尚未可用且应用没有重试。
- 内存不足。
- 健康检查工具不存在，但外部机制据此重启。

排障时可暂时关闭自动化重启或运行一次性容器复现，但修复后恢复明确策略。

## 18. 最小权限：非 root

Dockerfile：

```dockerfile
RUN addgroup --system --gid 10001 app \
    && adduser --system --uid 10001 --ingroup app app
COPY --chown=10001:10001 . /app
USER 10001:10001
```

运行时验证：

```bash
docker run --rm app:1.4.2 id
```

非 root 降低容器进程被利用后的能力，但不是完整隔离。仍需 capabilities、mount、seccomp、内核和 daemon 权限共同防护。

## 19. Capabilities

默认移除全部，再按需添加：

```bash
docker run --rm \
  --cap-drop ALL \
  app:1.4.2
```

若明确需要绑定低端口：

```bash
docker run --rm \
  --cap-drop ALL \
  --cap-add NET_BIND_SERVICE \
  app:1.4.2
```

更简单的方案通常是让应用监听 `8080`，由代理或端口发布映射到外部端口。

不要用 `--privileged` 修复普通权限错误。它会显著扩大容器对宿主机的控制面。

## 20. 只读根文件系统

```bash
docker run --rm \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --mount type=volume,source=app-data,target=/app/data \
  app:1.4.2
```

这让写入点可枚举：

- `/tmp` 可丢失且有大小限制。
- `/app/data` 是明确持久数据。
- 其他根文件系统不可写。

`noexec`、`nosuid`、`nodev` 等选项应按挂载用途使用并测试应用兼容性。

## 21. `no-new-privileges`

```bash
docker run --rm \
  --security-opt no-new-privileges=true \
  app:1.4.2
```

它阻止进程及其子进程通过 `execve` 获得额外权限。Compose：

```yaml
security_opt:
  - no-new-privileges:true
```

## 22. Seccomp、AppArmor 与 SELinux

Docker 默认 seccomp profile 会限制部分高风险系统调用。一般原则：

- 不要无理由使用 `seccomp=unconfined`。
- 应用确需系统调用时，创建最小自定义 profile 并审查。
- Ubuntu 等平台可结合 AppArmor。
- RHEL/Fedora 等平台正确使用 SELinux 标签。
- 不要通过关闭宿主安全模块解决 mount 权限问题。

检查容器安全选项：

```bash
docker inspect --format '{{json .HostConfig.SecurityOpt}}' &lt;container&gt;
docker info --format '{{json .SecurityOptions}}'
```

## 23. Mount 与 Docker socket 风险

危险示例：

```text
/var/run/docker.sock:/var/run/docker.sock
/:/host
```

获得 Docker socket 控制权通常近似获得宿主 root 权限。CI runner、管理面板和自动更新工具若挂载 socket，必须视为高权限基础设施：

- 使用隔离主机或专用 daemon。
- 限制谁能修改其镜像和配置。
- 固定并验证镜像来源。
- 不把 socket 暴露给普通业务容器。
- 不依赖“只读挂载 socket”提供真正只读 API 权限。

## 24. 镜像供应链

生产镜像实践：

- 使用可信基础镜像。
- 明确 tag，部署时可固定 digest。
- CI 中构建，不在生产机手工修改。
- 生成 SBOM。
- 扫描操作系统包和语言依赖漏洞。
- 对镜像签名并在部署入口验证。
- 定期重建以获取基础镜像安全修复。
- 保留源码 commit、流水线和 digest 对应关系。

示例扫描：

```bash
docker scout quickview app:1.4.2
docker scout cves app:1.4.2
```

具体 Scout 能力取决于安装、登录和订阅。扫描结果要区分可利用性、运行路径和修复版本，不能只追求“零条目”。

## 25. Secrets 安全

不要把 secrets 放入：

- Dockerfile `ENV`。
- `ARG` 构建参数。
- 镜像层中的配置文件。
- Git 仓库中的 `.env`。
- 命令行明文参数和 CI 日志。
- 容器标签。

构建期使用 BuildKit secret：

```dockerfile
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc npm ci
```

运行期使用目标平台 secret manager 或受限文件挂载。应用应支持轮换，不把 secret 写回日志。

## 26. 网络暴露

只允许本机访问：

```bash
docker run -d -p 127.0.0.1:8080:8080 app:1.4.2
```

数据库和内部服务通常不发布端口，通过用户定义网络 DNS 访问。公网入口应经过认证、TLS、速率限制和反向代理策略。

记住端口顺序：

```text
宿主机端口:容器端口
```

Dockerfile `EXPOSE` 只提供元数据，不会发布端口或修改防火墙。

## 27. Daemon 与主机安全

- 及时更新受支持的 Docker Engine 和宿主内核。
- 限制 `docker` 组成员。
- 评估 rootless mode 或 user namespace remapping。
- 不把未加密 daemon TCP API 暴露到网络。
- 远程管理优先受控 SSH context 或双向 TLS。
- 对 `/var/lib/docker`、volume 和备份设置正确权限。
- Docker Desktop 环境检查企业许可和集中策略。
- daemon 配置变更先在测试环境验证。

截至 2026-08-04，最新稳定 Docker Engine 为 29.7.1，Docker Desktop 为 4.85.0。生产升级应结合 release notes、兼容性测试与回滚计划。

## 28. 安全化 Compose 模板

```yaml
services:
  api:
    image: registry.example.com/team/api:1.4.2
    user: "10001:10001"
    read_only: true
    tmpfs:
      - /tmp:size=64m,mode=1777
    cap_drop:
      - ALL
    security_opt:
      - no-new-privileges:true
    pids_limit: 200
    mem_limit: 512m
    cpus: 1.0
    init: true
    stop_grace_period: 30s
    restart: unless-stopped
    logging:
      driver: local
      options:
        max-size: "10m"
        max-file: "3"
    healthcheck:
      test: ["CMD", "/app/server", "healthcheck"]
      interval: 30s
      timeout: 3s
      retries: 3
      start_period: 20s
```

这不是无脑复制模板。每一项都需要与应用行为、宿主能力和故障策略一起测试。

## 29. 事件与 daemon 日志

实时 Docker 事件：

```bash
docker events
docker events --since 30m
docker events --filter container=&lt;container&gt;
```

可看到 create、start、die、oom、health_status 等事件。

Linux daemon 日志：

```bash
sudo journalctl -u docker --since "30 minutes ago" --no-pager
```

Docker Desktop 则使用 Desktop 自带诊断与日志入口。不要在公开 issue 中上传未经脱敏的诊断包。

## 30. 一套故障采集命令

```bash
docker version
docker info
docker context show
docker ps -a
docker system df
docker inspect &lt;container&gt;
docker logs --timestamps --tail 500 &lt;container&gt;
docker stats --no-stream &lt;container&gt;
docker events --since 30m --filter container=&lt;container&gt;
```

分享前删除：

- 密码、token、证书和内部域名。
- 环境变量中的敏感值。
- 客户数据和个人信息。
- 私有 registry 凭据。

记录问题时间窗口、版本、变更和复现步骤，远比只说“容器挂了”有价值。

## 31. 常见误区

### “容器里是 root，所以等于宿主 root”

不完全等同，但风险不能忽略。namespace、capabilities 和安全模块提供隔离；危险 mount、内核漏洞、privileged 或 daemon socket 会显著扩大影响。

### “用了非 root 就安全了”

非 root 只是纵深防御一层，还需只读根文件系统、最小 capabilities、资源限制、网络隔离和供应链安全。

### “重启恢复了，所以问题解决了”

重启只清除症状。仍需分析退出码、OOM、日志、事件和负载模式。

### “容器有内存限制，宿主就不会出问题”

宿主运行多个容器、daemon、缓存和系统服务。必须做整体容量规划与预留。

### “扫描没有高危漏洞就可以上线”

还要验证配置、secret、权限、应用逻辑、依赖暴露、镜像来源和运行时行为。

## 32. 上线前检查

- [ ] 应用日志进入 stdout/stderr 且不含秘密。
- [ ] 日志驱动有轮转或集中采集策略。
- [ ] 指标、健康状态和重启有告警。
- [ ] CPU、内存、PID 和磁盘有合理限制与容量预留。
- [ ] 应用可优雅处理 `SIGTERM`。
- [ ] 容器默认以非 root 运行。
- [ ] 根文件系统只读，写入点明确。
- [ ] capabilities 默认全部移除后按需添加。
- [ ] 启用 `no-new-privileges` 并保留默认 seccomp。
- [ ] 不挂载 Docker socket 或宿主根目录。
- [ ] 端口只发布到必要接口。
- [ ] 镜像固定明确版本或 digest。
- [ ] CI 完成测试、SBOM、扫描和来源记录。
- [ ] Secret 不在镜像、仓库和日志中。
- [ ] volume 有一致性备份与恢复演练。
- [ ] Engine、Desktop 和宿主系统有升级计划。

## 33. 练习

1. 运行一个内存受限容器，使用 `docker stats` 观察。
2. 为 Nginx 配置 `local` 日志驱动与轮转。
3. 以只读根文件系统运行应用，为必要目录提供 tmpfs。
4. 使用 `cap-drop ALL`，记录应用真正需要的 capability。
5. 故意运行不存在的命令，检查退出码和日志。
6. 使用 `docker events` 观察容器 create/start/die 生命周期。
7. 为已有 Compose 服务加入非 root、资源限制和健康检查，并逐项回归测试。
8. 写一份故障记录，包含时间线、版本、事实、根因、修复和预防措施。
