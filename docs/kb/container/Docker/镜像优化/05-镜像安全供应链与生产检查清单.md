## 本篇目标

镜像安全不是发布前执行一次漏洞扫描。

它覆盖从基础镜像选择到生产部署的完整链路：

- 构建输入是否可信
- 依赖是否可重复解析
- 凭据是否进入层或日志
- 构建过程是否可追溯
- 镜像内容是否可枚举
- 漏洞是否有明确门禁
- 部署对象是否由 digest 唯一标识
- 运行时是否遵循最小权限
- 漏洞修复后是否能快速重建

本文版本背景为 2026-08-04：

- Docker Engine 29.7.1
- Docker Desktop 4.85.0
- BuildKit 默认启用
- Buildx 可生成 provenance 与 SBOM attestation

具体 Scout 功能、策略和授权取决于当前产品版本与订阅。

## 先画出供应链

典型镜像供应链包括：

```text
源码与 lockfile
       ↓
基础镜像与系统包仓库
       ↓
BuildKit builder
       ↓
测试、扫描与策略门禁
       ↓
OCI Registry
       ↓
部署系统按 digest 拉取
       ↓
生产运行与持续监控
```

每个箭头都是信任边界。

只保护 Registry 密码不够。

## 威胁模型

至少考虑以下风险：

- 上游基础镜像 tag 被移动
- 依赖仓库返回恶意或被替换的包
- lockfile 未提交或被绕过
- CI runner 被不可信 PR 利用
- 构建参数泄露 token
- 构建缓存被跨信任域污染
- Registry tag 被覆盖
- 镜像含高危漏洞或恶意文件
- 部署时拉取了与审批对象不同的内容
- 容器以 root 身份运行
- 运行时文件系统可任意写入

安全控制应对应威胁，而不是堆叠工具名称。

## tag 与 digest

tag 是可变引用：

```text
registry.example.com/team/api:1.8.0
```

digest 是内容寻址引用：

```text
registry.example.com/team/api@sha256:&lt;digest&gt;
```

同一个 tag 可以被重新指向新内容。

同一个 digest 对应确定的 manifest 或 image index 内容。

多平台 tag 通常指向 index digest。

index 内每个平台还有自己的 manifest digest。

生产部署优先记录和使用已审批 index digest。

## 为什么不能盲用 `latest`

`latest` 只是未显式指定 tag 时的默认名称。

它不保证：

- 发布时间最新
- 版本最高
- 没有漏洞
- 与上一次构建相同
- 与生产兼容

合理策略是：

- 使用有语义的 tag 便于阅读
- 同时按 digest 固定真实输入
- 自动发现新 digest
- 通过 PR 更新
- 重建、测试和扫描
- 审批后部署

## 基础镜像选择

优先选择：

- 官方或可信供应商维护
- 更新节奏透明
- 支持目标平台
- 提供清晰版本生命周期
- 只包含所需运行时
- 可获得 SBOM 或来源信息

常见选项包括 slim、Alpine、distroless 和 `scratch`。

体积最小不等于风险最低。

维护质量和兼容性同样重要。

## 固定基础镜像

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-bookworm-slim@sha256:&lt;reviewed-index-digest&gt; AS build
```

digest 固定可重复输入。

但固定也会停止自动获取安全修复。

必须配套更新机器人或定期审查流程。

不要把固定 digest 误解为“永远不更新”。

## 使用 `--pull` 重建

对仍使用 tag 的输入，重建时显式检查上游：

```bash
docker buildx build --pull -t api:test --load .
```

对固定 digest 的输入，`--pull` 不会神奇地改变 digest。

它仍有助于确保 builder 获取指定内容。

更新安全补丁需要主动更新 Dockerfile 中的 digest。

## 可重复依赖

应用依赖应使用 lockfile：

- Node 使用 `package-lock.json` 并执行 `npm ci`
- Go 提交 `go.mod` 和 `go.sum`
- Python 使用锁定版本，关键环境可校验 hash
- Rust 提交应用的 `Cargo.lock`
- Java 使用 dependency locking 或等价机制

不要在生产构建中静默重写 lockfile。

不要使用宽泛范围后假设两次构建相同。

## 生产 Dockerfile 基线

```dockerfile
# syntax=docker/dockerfile:1

FROM node:24-bookworm-slim@sha256:&lt;reviewed-digest&gt; AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci
COPY . .
RUN npm test \
    && npm run build \
    && npm prune --omit=dev

FROM node:24-bookworm-slim@sha256:&lt;reviewed-digest&gt; AS production
ENV NODE_ENV=production
WORKDIR /app
COPY --from=build --chown=node:node /app/package.json ./
COPY --from=build --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/dist ./dist
USER node
EXPOSE 3000
ENTRYPOINT ["node", "dist/server.js"]
```

真实项目中 builder 和 runtime 可以使用不同的受审 digest。

示例占位 digest 必须替换为 Registry 返回的完整值。

## 非 root 用户

Dockerfile 中显式设置：

```dockerfile
RUN groupadd --gid 10001 app \
    && useradd --uid 10001 --gid app --no-create-home app
COPY --chown=10001:10001 app /app
USER 10001:10001
```

检查：

```bash
docker inspect api:test --format '{{.Config.User}}'
docker run --rm api:test id
```

非 root 不能消除全部容器逃逸风险。

它能降低许多误配置和应用漏洞的影响。

## 最小运行时

最终阶段不应包含：

- 编译器
- 包管理器缓存
- 测试数据
- VCS 历史
- 私钥与 token
- 不必要 shell 和诊断工具
- 源码映射，除非明确需要

但不要误删：

- CA 证书
- 时区数据
- 动态链接库
- 字体或 locale
- 应用许可证要求的文件

“最小”必须由运行需求定义。

## 秘密不能进入层

错误示例：

```dockerfile
ARG TOKEN
ENV TOKEN=$TOKEN
RUN curl -H "Authorization: Bearer $TOKEN" https://example.com/artifact
```

`ARG` 和 `ENV` 都不适合秘密。

构建参数还可能出现在 provenance 中。

正确示例：

```dockerfile
# syntax=docker/dockerfile:1
RUN --mount=type=secret,id=token,required=true \
    TOKEN="$(cat /run/secrets/token)" \
    fetch-private-artifact
```

```bash
docker buildx build --secret id=token,env=TOKEN .
```

秘密只在该 `RUN` 中可见。

构建命令也不应把秘密打印到日志。

## SSH 凭据

私有 Git 仓库使用 SSH mount：

```dockerfile
# syntax=docker/dockerfile:1
RUN --mount=type=ssh,required=true \
    git clone git@github.com:example/private.git /src/private
```

```bash
docker buildx build --ssh default="$SSH_AUTH_SOCK" .
```

不要 `COPY ~/.ssh`。

不要在后续层删除后以为私钥已经消失。

## `.dockerignore` 的安全作用

```dockerignore
.git
.env
.env.*
!.env.example
*.pem
*.key
id_rsa
node_modules
coverage
dist
.cache
```

`.dockerignore` 降低误复制风险。

它不是秘密管理系统。

敏感文件本就不应出现在不受控工作区。

## 构建器信任边界

builder 可以接触：

- 构建上下文
- secret mount
- SSH agent
- Registry 凭据
- 外部缓存
- 输出推送权限

因此 builder 本身是高价值基础设施。

应做到：

- 隔离可信发布与不可信 PR
- 使用短期凭据
- 最小化 Registry 权限
- 及时更新 BuildKit
- 审核远程 builder 节点
- 定义缓存保留与清理策略

## 不可信 PR

来自 fork 的 PR 不应自动获得：

- 生产 Registry push 权限
- 发布签名密钥
- 私有依赖 token
- 主分支缓存写权限
- 部署凭据

可在无秘密环境执行静态检查与普通测试。

合并后的可信 commit 再进入发布 job。

## provenance 是什么

provenance attestation 描述镜像如何构建。

BuildKit 生成的记录采用 in-toto statement，并表达 SLSA provenance 信息。

Buildx 默认会为镜像生成最低级别 provenance，具体默认行为取决于 exporter 和版本。

显式请求完整模式：

```bash
docker buildx build \
  --provenance=mode=max \
  -t registry.example.com/team/api:1.8.0 \
  --push .
```

`mode=max` 可能包含更多构建参数和元数据。

这也是秘密不能放进 build args 的原因之一。

## SBOM 是什么

SBOM 是软件物料清单。

它列出镜像中识别到的软件包和文件信息。

Buildx 可在构建时生成 SBOM attestation：

```bash
docker buildx build \
  --sbom=true \
  -t registry.example.com/team/api:1.8.0 \
  --push .
```

同时生成 SBOM 和 provenance：

```bash
docker buildx build \
  --provenance=mode=max \
  --sbom=true \
  -t registry.example.com/team/api:1.8.0 \
  --push .
```

attestation 通常附着在 Registry 中的 image index 上。

仅 `--load` 到某些本地输出时，保留形式可能不同。

发布流程应在目标 Registry 验证实际结果。

## SBOM 不等于漏洞扫描

SBOM 回答“包含什么”。

漏洞扫描回答“已知漏洞数据库如何评价这些组件”。

两者都不能证明应用没有未知漏洞或业务逻辑漏洞。

SBOM 质量还受软件包识别能力影响。

## Docker Scout

快速概览：

```bash
docker scout quickview registry.example.com/team/api:1.8.0
```

列出漏洞：

```bash
docker scout cves registry.example.com/team/api:1.8.0
```

查看基础镜像更新建议：

```bash
docker scout recommendations registry.example.com/team/api:1.8.0
```

策略比较可使用当前 Scout CLI 支持的 policy 命令。

命令选项会随版本和订阅变化，应以当前官方文档为准。

## 扫描结果如何设门禁

不要简单规定“任何 CVE 都失败”。

成熟门禁至少考虑：

- 严重等级
- 是否有修复版本
- 组件是否实际存在于最终镜像
- 是否可达或可利用
- 暴露面
- 已批准例外及到期时间
- 基础镜像与应用依赖责任归属

示例策略：

- 新增 Critical 且有修复：阻断
- 新增 High 且有修复：默认阻断
- 无修复漏洞：建立有期限风险接受
- 超期例外：阻断
- 扫描器失败或数据库过旧：发布失败

门禁规则应版本化并可审计。

## 扫描什么对象

应扫描最终推送 digest。

不要只扫描：

- builder 阶段
- 本地临时 tag
- 与部署不同的重新构建镜像
- 仅 amd64 而忽略 arm64

多平台镜像应检查每个平台变体。

## 推送后再获取 digest

```bash
docker buildx build \
  --pull \
  --platform linux/amd64,linux/arm64 \
  --provenance=mode=max \
  --sbom=true \
  -t registry.example.com/team/api:"$GIT_SHA" \
  --push .
```

检查：

```bash
docker buildx imagetools inspect \
  registry.example.com/team/api:"$GIT_SHA"
```

将 index digest 写入发布记录。

部署系统使用：

```text
registry.example.com/team/api@sha256:&lt;approved-index-digest&gt;
```

## 签名与验证

attestation 提供信息，不自动等于身份验证。

组织可使用 Sigstore Cosign 等工具签名镜像 digest 和 attestation。

示意：

```bash
cosign sign registry.example.com/team/api@sha256:&lt;digest&gt;
cosign verify registry.example.com/team/api@sha256:&lt;digest&gt;
```

生产应优先采用短期身份和 keyless/OIDC 工作流，或受控 KMS 密钥。

签名策略、证书身份和 transparency log 要求应由组织明确定义。

不要只验证“存在某个签名”。

还要验证签名者身份与工作流来源。

## OCI Registry 控制

Registry 应配置：

- TLS
- 最小权限账户
- 不可变发布 tag 或防覆盖策略
- 审计日志
- 保留与垃圾回收策略
- 跨区域复制策略
- attestation 和 OCI artifact 支持
- 管理员与 CI 账户分离

即使 tag 不可变，部署仍建议使用 digest。

## 运行时基线

镜像安全必须落到容器运行配置。

示例：

```bash
docker run --rm \
  --read-only \
  --tmpfs /tmp:rw,noexec,nosuid,size=64m \
  --cap-drop ALL \
  --security-opt no-new-privileges=true \
  --user 10001:10001 \
  registry.example.com/team/api@sha256:&lt;digest&gt;
```

这些参数不能机械应用。

应用需要绑定低端口、写文件或特定 capability 时应明确授权。

原则是默认拒绝，再增加最小必要权限。

## HEALTHCHECK 的边界

Dockerfile 可声明健康检查：

```dockerfile
HEALTHCHECK --interval=30s --timeout=3s --start-period=10s --retries=3 \
  CMD ["/app/healthcheck"]
```

但 distroless 镜像可能没有 curl 或 shell。

可使用应用自带小型健康检查二进制。

在 Kubernetes 中通常由平台配置 probes。

不要仅为了 HEALTHCHECK 安装大型工具集。

## 只读文件系统

启用只读 root filesystem 前，找出合法写路径：

- `/tmp`
- 上传暂存目录
- 应用缓存
- PID 或 socket 目录

将它们映射为 tmpfs 或受控 volume。

应用日志优先输出 stdout/stderr。

不要在镜像层内持续写日志。

## 生产发布流程

一个合理顺序是：

1. 固定源码 commit
2. 校验 lockfile 与依赖策略
3. 构建 test target
4. 使用 `--pull` 构建生产 target
5. 生成 provenance 与 SBOM
6. 推送不可变 commit tag
7. 获取远程 digest
8. 扫描每个平台 manifest
9. 执行策略门禁
10. 签名已批准 digest
11. 按 digest 部署
12. 记录审批、扫描和回滚 digest

构建一次，提升同一个 digest。

不要在每个环境重新构建“相同版本”。

## 漏洞修复流程

发现基础镜像漏洞后：

1. 确认受影响 digest 和平台
2. 查找有修复的上游基础镜像 digest
3. 通过 PR 更新固定 digest
4. 使用 `--pull` 完整重建
5. 运行测试和扫描
6. 生成新 attestation
7. 推送并记录新 digest
8. 灰度部署
9. 验证后扩大范围
10. 保留明确回滚策略

容器镜像不是打补丁后原地修改。

应从受控输入重新构建。

## 检查镜像配置

```bash
docker image inspect api:test
docker inspect api:test --format '{{.Config.User}}'
docker inspect api:test --format '{{json .Config.Env}}'
docker inspect api:test --format '{{json .Config.Entrypoint}}'
docker history --no-trunc api:test
```

重点检查：

- 用户是否为空或 root
- ENV 是否含凭据
- ENTRYPOINT 是否使用 exec form
- 是否有异常大层
- 是否包含不必要端口和 volume 声明

## 检查镜像内容

```bash
docker scout cves api:test
docker scout recommendations api:test
```

还可使用组织批准的 SBOM 和扫描工具交叉验证。

工具数量不是目标。

重点是有一致输入、可复现结果和明确责任人。

## 常见失败模式

### 扫描通过后重新构建

重新构建可能得到不同依赖或基础层。

应部署已扫描的同一 digest。

### 固定 digest 但从不更新

可重复不等于安全。

必须持续发现和审查更新。

### 把秘密写入 `ARG`

秘密可能出现在元数据、日志或 provenance。

使用 secret mount。

### 只看镜像大小

小镜像也可能包含高危应用依赖。

### 只扫描一个平台

不同平台基础层和原生包可能不同。

### 例外没有到期时间

永久例外会让门禁逐渐失效。

### 生产容器仍以 root 运行

Dockerfile 的最小镜像无法弥补运行时过度权限。

## 构建前检查清单

- [ ] 源码 commit 唯一且已审核
- [ ] lockfile 已提交且未在构建中重写
- [ ] `.dockerignore` 排除了秘密与无关文件
- [ ] 基础镜像来源可信
- [ ] 基础镜像使用审查过的 digest
- [ ] 有自动化 digest 更新流程
- [ ] 没有盲目使用 `latest`
- [ ] 不可信 PR 与发布凭据隔离
- [ ] builder 和缓存权限符合信任边界

## Dockerfile 检查清单

- [ ] 首行使用现代 syntax directive
- [ ] 使用多阶段构建隔离工具链
- [ ] 依赖描述文件先复制
- [ ] cache mount 只用于非秘密缓存
- [ ] secret 使用 secret mount
- [ ] Git 凭据使用 SSH mount
- [ ] `ARG` 和 `ENV` 不含秘密
- [ ] 最终阶段只复制明确产物
- [ ] 最终镜像使用非 root 用户
- [ ] 使用 exec form ENTRYPOINT/CMD
- [ ] 运行时保留必要 CA 和动态库
- [ ] 没有不必要编译器、shell 和包缓存

## 构建与发布检查清单

- [ ] 构建使用 `--pull`
- [ ] test target 已显式执行
- [ ] 生产 target 只构建一次
- [ ] 多平台目标逐个平台测试
- [ ] 已生成 provenance
- [ ] 已生成 SBOM
- [ ] attestation 已随镜像推送
- [ ] 已获取远程 index digest
- [ ] 已扫描最终推送 digest
- [ ] 门禁数据库和扫描器状态正常
- [ ] 风险例外有责任人和到期时间
- [ ] 签名身份符合策略
- [ ] 发布 tag 受防覆盖策略保护

## 部署检查清单

- [ ] 部署引用使用已审批 digest
- [ ] 非 root 运行得到平台策略保证
- [ ] 默认 drop capabilities
- [ ] 启用 `no-new-privileges`
- [ ] 根文件系统尽可能只读
- [ ] 可写目录使用受控 tmpfs 或 volume
- [ ] Secret 由运行时注入而非烘焙进镜像
- [ ] 资源 requests/limits 已定义
- [ ] 健康检查不依赖不必要工具
- [ ] 日志输出 stdout/stderr
- [ ] 网络访问遵循最小权限
- [ ] 回滚 digest 已记录并可用

## 持续运营检查清单

- [ ] 持续监控新 CVE
- [ ] 定期更新基础镜像 digest
- [ ] 定期轮换构建与 Registry 凭据
- [ ] 审计 tag 覆盖和 push 事件
- [ ] 清理过期缓存与无引用镜像
- [ ] 保留发布 attestation 和审批记录
- [ ] 定期验证签名与部署策略
- [ ] 对例外执行到期复审
- [ ] 定期演练漏洞紧急重建
- [ ] 定期验证多架构镜像仍可启动

## 小结

安全镜像需要把“构建什么”“如何构建”和“部署哪个对象”连接起来。

digest 提供不可变身份，SBOM 描述内容，provenance 描述构建过程。

扫描、签名和策略门禁在此基础上做判断。

最终仍要通过非 root、最小权限、持续更新和可回滚发布落实到生产。
