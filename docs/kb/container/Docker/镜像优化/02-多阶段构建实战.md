## 为什么需要多阶段构建

应用构建环境和运行环境的需求通常完全不同。

构建阶段可能需要：

- 编译器
- 包管理器
- 头文件
- 测试工具
- 源码
- 调试符号

生产运行阶段通常只需要：

- 可执行文件或编译产物
- 最少运行时依赖
- CA 证书与必要时区数据
- 非 root 用户
- 启动命令

多阶段构建用多个 `FROM` 分开这些职责。

每个 `FROM` 开启一个新阶段。

最终阶段只通过 `COPY --from=&lt;stage&gt;` 接收明确的产物。

本文版本背景为 2026-08-04：Engine 29.7.1、Desktop 4.85.0，BuildKit 默认启用。

## 最小示例

```dockerfile
# syntax=docker/dockerfile:1
FROM golang:1.26-bookworm AS build
WORKDIR /src
COPY . .
RUN CGO_ENABLED=0 go build -o /out/hello ./cmd/hello

FROM scratch AS production
COPY --from=build /out/hello /hello
ENTRYPOINT ["/hello"]
```

构建最终阶段：

```bash
docker build --pull -t hello:production .
```

只构建某个阶段：

```bash
docker build --target build -t hello:build .
```

阶段必须命名。

用 `build` 比用数字 `0` 更能承受 Dockerfile 重排。

## 阶段不是按文本顺序全部执行

BuildKit 只构建目标依赖的阶段。

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-bookworm-slim AS base
WORKDIR /app

FROM base AS lint
COPY . .
RUN npm run lint

FROM base AS production
COPY dist ./dist
CMD ["node", "dist/server.js"]
```

如果 `production` 不依赖 `lint`，构建生产目标不会自动执行 lint。

这点非常重要。

不要把“阶段写在前面”误认为“发布前一定执行”。

CI 应显式构建测试目标：

```bash
docker buildx build --target lint --progress=plain .
docker buildx build --target test --progress=plain .
docker buildx build --target production -t registry.example.com/app:sha --push .
```

## Node 优化前

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-bookworm
WORKDIR /app
COPY . .
RUN npm install
RUN npm run build
CMD ["npm", "start"]
```

问题：

- 开发依赖留在生产镜像
- TypeScript 源码和测试可能被复制
- 每次源码变更都重装依赖
- 构建工具进入运行环境
- root 运行风险
- `npm start` 可能多一层进程包装

## Node 多阶段生产示例

假设应用构建为 `dist/`，运行时仍需要生产依赖。

```dockerfile
# syntax=docker/dockerfile:1

FROM node:24-bookworm-slim AS deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci

FROM deps AS test
COPY . .
RUN npm run lint
RUN npm test

FROM deps AS build
COPY . .
RUN npm run build
RUN npm prune --omit=dev

FROM node:24-bookworm-slim AS production
ENV NODE_ENV=production
WORKDIR /app

COPY --from=build --chown=node:node /app/package.json ./package.json
COPY --from=build --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/dist ./dist

USER node
EXPOSE 3000
ENTRYPOINT ["node", "dist/server.js"]
```

构建各目标：

```bash
docker buildx build --target test --progress=plain .
docker buildx build --target production --pull -t node-demo:prod --load .
```

这里的 `test` 与 `build` 都继承 `deps`。

生产构建不会因为存在 `test` 阶段而自动测试。

CI 必须分别执行它们。

## Node 原生依赖注意事项

如果 `node_modules` 包含原生扩展：

- builder 与 runtime 应使用兼容 libc
- CPU 架构必须一致或正确交叉构建
- 不要在 glibc builder 中安装后复制到 Alpine/musl runtime
- `npm prune --omit=dev` 后应做启动测试
- 多平台构建应逐架构验证原生包

若框架支持 standalone 输出，优先复制其声明的最小运行集。

不要凭猜测手工删除 `node_modules` 子目录。

## Node 更严格的依赖阶段

生产依赖和构建依赖也可以分开安装：

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-bookworm-slim AS prod-deps
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci --omit=dev

FROM node:24-bookworm-slim AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm \
    npm ci
COPY . .
RUN npm run build

FROM node:24-bookworm-slim AS production
ENV NODE_ENV=production
WORKDIR /app
COPY --from=prod-deps --chown=node:node /app/node_modules ./node_modules
COPY --from=build --chown=node:node /app/dist ./dist
COPY --chown=node:node package.json ./
USER node
CMD ["node", "dist/server.js"]
```

优点是生产依赖集合更明确。

代价是可能执行两次依赖解析，但 cache mount 会减少重复下载。

## Go 优化前

```dockerfile
# syntax=docker/dockerfile:1
FROM golang:1.26-bookworm
WORKDIR /src
COPY . .
RUN go build -o app ./cmd/api
CMD ["./app"]
```

最终镜像包含 Go SDK、源码和构建缓存。

## Go 多阶段实战

```dockerfile
# syntax=docker/dockerfile:1

FROM golang:1.26-bookworm AS base
WORKDIR /src
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download

FROM base AS test
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    go test ./...

FROM base AS build
ARG VERSION=dev
ARG COMMIT=unknown
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 go build \
      -trimpath \
      -ldflags="-s -w -X main.version=${VERSION} -X main.commit=${COMMIT}" \
      -o /out/api ./cmd/api

FROM gcr.io/distroless/static-debian12:nonroot AS production
COPY --from=build /out/api /api
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/api"]
```

构建：

```bash
docker buildx build \
  --target production \
  --pull \
  --build-arg VERSION=1.8.0 \
  --build-arg COMMIT="$(git rev-parse HEAD)" \
  -t api:1.8.0 \
  --load .
```

版本号和 commit 不是秘密，可以使用 `ARG`。

token、私钥和密码不可以。

## Go 的 CGO 分支

需要 CGO 时，`scratch` 或 static distroless 往往不适用。

示意：

```dockerfile
# syntax=docker/dockerfile:1
FROM golang:1.26-bookworm AS build
WORKDIR /src
RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt,sharing=locked \
    apt-get update \
    && apt-get install -y --no-install-recommends gcc libc6-dev
COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod go mod download
COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=1 go build -trimpath -o /out/api ./cmd/api

FROM gcr.io/distroless/base-debian12:nonroot AS production
COPY --from=build /out/api /api
USER nonroot:nonroot
ENTRYPOINT ["/api"]
```

用 `ldd` 检查动态依赖：

```bash
docker build --target build -t api:builder .
docker run --rm api:builder ldd /out/api
```

最终基础镜像必须提供这些共享库。

## Python 优化前

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.14
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["python", "app.py"]
```

源码变化会使依赖安装层失效。

编译 wheel 所需工具也可能留在镜像中。

## Python wheel 多阶段示例

```dockerfile
# syntax=docker/dockerfile:1

FROM python:3.14-slim-bookworm AS build
WORKDIR /build
RUN --mount=type=cache,target=/var/cache/apt,sharing=locked \
    --mount=type=cache,target=/var/lib/apt,sharing=locked \
    apt-get update \
    && apt-get install -y --no-install-recommends build-essential
COPY requirements.txt ./
RUN --mount=type=cache,target=/root/.cache/pip \
    python -m pip wheel \
      --wheel-dir=/wheels \
      -r requirements.txt

FROM python:3.14-slim-bookworm AS production
ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1
WORKDIR /app

RUN groupadd --gid 10001 app \
    && useradd --uid 10001 --gid app --no-create-home app

COPY requirements.txt ./
COPY --from=build /wheels /wheels
RUN python -m pip install \
      --no-cache-dir \
      --no-index \
      --find-links=/wheels \
      -r requirements.txt \
    && rm -rf /wheels

COPY --chown=app:app src ./src
USER app
CMD ["python", "-m", "src.app"]
```

builder 与 runtime 的 Python ABI、架构和 libc 必须兼容。

更严格的项目应使用带 hash 的锁定依赖。

例如生成并审查 requirements lock，而不是使用宽泛版本范围。

## 共享基础阶段

可以抽取稳定公共配置：

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-bookworm-slim AS base
WORKDIR /app
ENV CI=true

FROM base AS deps
COPY package.json package-lock.json ./
RUN --mount=type=cache,target=/root/.npm npm ci

FROM deps AS test
COPY . .
RUN npm test

FROM deps AS build
COPY . .
RUN npm run build
```

不要为了“复用”建立深而难懂的阶段继承树。

阶段应该对应清晰职责。

## 从外部镜像复制文件

`COPY --from` 也能引用外部镜像：

```dockerfile
# syntax=docker/dockerfile:1
FROM debian:bookworm-slim
COPY --from=busybox:1.37.0-uclibc /bin/busybox /usr/local/bin/busybox
```

生产中应固定外部镜像 digest：

```dockerfile
COPY --from=busybox:1.37.0-uclibc@sha256:&lt;reviewed-digest&gt; \
  /bin/busybox /usr/local/bin/busybox
```

它和 `FROM` 一样是供应链输入。

## Debug 与 production 目标

Distroless 镜像通常没有 shell。

不要把 shell 永久加回生产镜像只为偶发排障。

可以提供单独的 debug 目标：

```dockerfile
# syntax=docker/dockerfile:1
FROM debian:bookworm-slim AS runtime-base
WORKDIR /app
RUN groupadd -g 10001 app \
    && useradd -u 10001 -g app --no-create-home app

FROM runtime-base AS debug
RUN apt-get update \
    && apt-get install -y --no-install-recommends curl procps \
    && rm -rf /var/lib/apt/lists/*
COPY --from=build /out/api /app/api
USER app
ENTRYPOINT ["/app/api"]

FROM gcr.io/distroless/static-debian12:nonroot AS production
COPY --from=build /out/api /api
USER nonroot:nonroot
ENTRYPOINT ["/api"]
```

构建不同目标：

```bash
docker buildx build --target debug -t api:debug --load .
docker buildx build --target production -t api:prod --load .
```

debug 镜像不应被误推送为生产 tag。

Registry 权限和 CI job 应区分两者。

## 导出构建产物

多阶段不只用于生成镜像。

```dockerfile
# syntax=docker/dockerfile:1
FROM golang:1.26 AS build
WORKDIR /src
COPY . .
RUN go build -o /out/app ./cmd/app

FROM scratch AS artifact
COPY --from=build /out/app /
```

导出到本地目录：

```bash
docker buildx build --target artifact --output type=local,dest=./dist .
```

这样本机不需要安装 Go 工具链。

## 不要跨阶段传秘密

错误示例：

```dockerfile
ARG PRIVATE_TOKEN
RUN echo "$PRIVATE_TOKEN" > /root/token
```

即使最终阶段没有复制该文件，秘密也可能进入：

- builder 缓存
- 构建历史
- CI 日志
- provenance 参数

正确做法是 secret mount：

```dockerfile
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci
```

构建命令：

```bash
docker buildx build --secret id=npmrc,src="$HOME/.npmrc" .
```

秘密只在该 `RUN` 执行时挂载。

应用仍可能把凭据复制到输出中，因此还要检查产物。

## 所有权与权限

不推荐：

```dockerfile
COPY --from=build /out /app
RUN chown -R app:app /app
```

`chown` 可能产生一个复制大量元数据的新层。

优先：

```dockerfile
COPY --from=build --chown=10001:10001 /out /app
USER 10001:10001
```

数字 UID/GID 在没有用户数据库的镜像中更明确。

如果应用或平台要求用户名，需确保 `/etc/passwd` 中存在对应记录。

## 验证最终阶段没有污染

查看历史：

```bash
docker history --no-trunc api:prod
```

查看用户与入口：

```bash
docker inspect api:prod --format '{{.Config.User}}'
docker inspect api:prod --format '{{json .Config.Entrypoint}}'
docker inspect api:prod --format '{{json .Config.Cmd}}'
```

检查文件系统：

```bash
docker export "$(docker create api:prod)" -o rootfs.tar
tar -tf rootfs.tar
```

实际使用时要清理临时容器和 tar 文件。

检查是否存在常见构建工具：

```bash
docker run --rm api:prod sh -c 'command -v gcc || true'
```

Distroless 或 scratch 没有 shell时，此命令本来就无法运行。

应改用导出文件系统或 SBOM 检查。

## 常见失败模式

### 最终阶段复制整个工作目录

```dockerfile
COPY --from=build /app /app
```

它可能连测试、缓存和秘密残留一起复制。

应逐项复制已知产物。

### 测试阶段没有成为发布门禁

阶段存在不等于阶段执行。

CI 必须显式构建 `test` target，并让失败阻断发布。

### builder 与 runtime ABI 不一致

典型案例是 Debian builder 加 Alpine runtime。

纯静态二进制可能可行，动态依赖通常出问题。

### 用生产阶段做调试工具箱

把 curl、bash、编译器都装入生产镜像会扩大攻击面。

使用独立 debug target 或临时调试容器。

### 只比较未压缩大小

本地大小、压缩传输大小和共享层占用并不相同。

应结合 Registry、历史层和实际拉取测试。

## CI 示例流程

```bash
docker buildx build \
  --target test \
  --pull \
  --progress=plain \
  .

docker buildx build \
  --target production \
  --pull \
  --provenance=mode=max \
  --sbom=true \
  -t registry.example.com/team/api:"$GIT_SHA" \
  --push \
  .
```

推送后应解析 digest：

```bash
docker buildx imagetools inspect registry.example.com/team/api:"$GIT_SHA"
```

部署记录应优先保存 digest，而不只保存 tag。

## 检查清单

- [ ] 每个阶段职责清晰并已命名
- [ ] 依赖清单先于源码复制
- [ ] 构建缓存使用 cache mount
- [ ] 测试 target 在 CI 中显式执行
- [ ] production target 不含编译器和源码
- [ ] 只复制明确的构建产物
- [ ] builder 与 runtime ABI 兼容
- [ ] CGO 和动态链接需求经过验证
- [ ] Node 原生依赖逐架构验证
- [ ] Python wheel 与 runtime ABI 一致
- [ ] 最终阶段以非 root 用户运行
- [ ] 使用 `COPY --chown` 控制所有权
- [ ] 秘密通过 secret 或 SSH mount 使用
- [ ] debug 与 production 使用不同 target/tag
- [ ] 基础镜像由 digest 固定并受控更新
- [ ] 构建使用 `--pull`
- [ ] 已运行启动、停止和健康检查
- [ ] 已扫描最终镜像而非只扫描 builder
- [ ] 已记录最终推送 digest

## 小结

多阶段构建的核心不是“写多个 `FROM`”。

它是在 Dockerfile 中建立可信的产物边界。

构建、测试、调试和生产各自拥有独立职责。

最终镜像只接受经过选择的文件，而不是整个构建现场。
