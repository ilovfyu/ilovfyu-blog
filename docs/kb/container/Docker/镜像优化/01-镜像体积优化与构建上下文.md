## 本篇目标

镜像优化不是单纯追求一个更小的数字。

真正的目标是同时改善：

- 拉取和启动速度
- Registry 存储与网络成本
- 缓存命中率
- 攻击面
- 构建的可重复性
- 排障与维护成本

本文版本背景为 2026-08-04：

- Docker Engine 29.7.1
- Docker Desktop 4.85.0
- BuildKit 已是默认构建后端
- Dockerfile 示例统一使用 `# syntax=docker/dockerfile:1`

版本会变化，原则比具体标签更重要。

## 先建立正确的心智模型

Docker 镜像由只读层组成。

Dockerfile 中多数会改变文件系统的指令会生成层。

后续层删除文件，不会让早期层里的字节消失。

例如下面的写法并没有真正移除下载包：

```dockerfile
# syntax=docker/dockerfile:1
FROM debian:bookworm-slim
RUN curl -o /tmp/tool.tar.gz https://example.com/tool.tar.gz
RUN tar -xf /tmp/tool.tar.gz -C /usr/local/bin
RUN rm /tmp/tool.tar.gz
```

压缩包仍存在于第一个 `RUN` 产生的层中。

至少应合并为同一个层：

```dockerfile
# syntax=docker/dockerfile:1
FROM debian:bookworm-slim
RUN curl -fsSLo /tmp/tool.tar.gz https://example.com/tool.tar.gz \
    && tar -xf /tmp/tool.tar.gz -C /usr/local/bin \
    && rm -f /tmp/tool.tar.gz
```

更好的方案通常是多阶段构建。

下载和解压发生在构建阶段，最终阶段只复制结果。

## 先测量，再优化

构建一个可追踪的基线：

```bash
docker build --pull --progress=plain -t demo:before .
docker image inspect demo:before --format '{{.Size}}'
docker image history --no-trunc demo:before
docker images demo
```

可读尺寸可以这样查看：

```bash
docker image ls demo:before
docker system df -v
```

检查镜像配置：

```bash
docker image inspect demo:before
docker inspect demo:before --format '{{json .Config.Env}}'
docker inspect demo:before --format '{{json .Config.User}}'
docker inspect demo:before --format '{{json .RootFS.Layers}}'
```

`docker history` 的 `CREATED BY` 能帮助定位异常大层。

但它显示的是层视角，不等于容器可写层或 Registry 压缩后大小。

需要更直观地分析文件时，可使用 Dive：

```bash
dive demo:before
```

也可以用 Docker Scout 查看软件包和漏洞：

```bash
docker scout quickview demo:before
docker scout cves demo:before
```

Scout 的可用命令和授权方式取决于 Docker 订阅及当前 CLI 插件版本。

## 构建上下文是什么

最后一个参数 `.` 不是装饰。

```bash
docker build -t demo:dev .
```

它把当前目录指定为构建上下文。

`COPY` 和 `ADD` 默认只能读取上下文中的内容。

BuildKit 会高效传输上下文，但无关文件仍会带来问题：

- 首次传输更慢
- 文件元数据计算更多
- 无关变更可能破坏缓存
- 敏感文件可能被意外 `COPY`
- 构建器会接触到本不需要的数据

观察构建日志中的这一行：

```text
=> [internal] load build context
=> => transferring context: 184.2MB
```

如果应用源码只有几 MB，而上下文有几百 MB，先处理上下文。

## `.dockerignore` 是第一道优化

Node 项目常见配置：

```dockerignore
.git
.gitignore
.env
.env.*
!.env.example
node_modules
npm-debug.log*
yarn-error.log*
coverage
dist
.next
.turbo
.cache
Dockerfile*
compose*.yaml
README.md
docs
```

不要机械照抄。

如果镜像构建确实需要 `README.md`、`dist` 或某个环境模板，就不能忽略它。

Go 项目常见配置：

```dockerignore
.git
.env
bin
dist
coverage.out
*.test
*.prof
vendor
tmp
Dockerfile*
compose*.yaml
```

如果项目依赖 vendoring，不能忽略 `vendor`。

Python 项目常见配置：

```dockerignore
.git
.env
.venv
venv
__pycache__
*.py[cod]
.pytest_cache
.mypy_cache
.ruff_cache
.coverage
htmlcov
dist
build
*.egg-info
Dockerfile*
compose*.yaml
```

重要规则：

- `.dockerignore` 位于构建上下文根目录
- 规则语义与 `.gitignore` 相近，但并非完全相同
- `!pattern` 可以重新包含文件
- 最后的匹配规则决定结果
- Dockerfile 专用忽略文件可命名为 `Dockerfile.dockerignore`
- 专用忽略文件优先于根目录 `.dockerignore`

检查上下文最直接的方法是看 plain 构建日志：

```bash
docker build --no-cache --progress=plain -t demo:context-check .
```

## 不要把仓库根目录永远当上下文

单体仓库中可以缩小上下文：

```text
repo/
├── services/
│   ├── api/
│   │   ├── Dockerfile
│   │   └── src/
│   └── web/
└── shared/
```

如果 API 不依赖仓库其他目录：

```bash
docker build -f services/api/Dockerfile -t api:dev services/api
```

如果需要 `shared`，仓库根可能仍必须作为上下文：

```bash
docker build -f services/api/Dockerfile -t api:dev .
```

此时要用根目录 `.dockerignore` 精确排除无关内容。

BuildKit 还支持命名上下文：

```bash
docker buildx build \
  --build-context shared=./shared \
  -f services/api/Dockerfile \
  -t api:dev \
  services/api
```

Dockerfile 中可像阶段一样读取：

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-bookworm-slim AS build
WORKDIR /app
COPY --from=shared . ./shared
COPY . .
RUN npm run build
```

命名上下文能明确边界，但不要因此跳过 `.dockerignore`。

## Node：优化前

下面是常见但低效的 Dockerfile：

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24
WORKDIR /app
COPY . .
RUN npm install
EXPOSE 3000
CMD ["npm", "start"]
```

问题包括：

- 基础镜像包含不必要工具
- 任意源码变更都会使依赖安装失去层缓存
- `npm install` 不严格遵循 lockfile
- 开发依赖进入生产镜像
- 可能把 `node_modules`、`.git`、`.env` 复制进去
- 默认用户可能是 root
- 构建工具和源码都留在最终镜像

## Node：第一步改进

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-bookworm-slim

ENV NODE_ENV=production
WORKDIR /app

COPY package.json package-lock.json ./
RUN npm ci --omit=dev \
    && npm cache clean --force

COPY --chown=node:node src ./src

USER node
EXPOSE 3000
CMD ["node", "src/server.js"]
```

改进点：

- 先复制依赖清单
- lockfile 不变时可复用依赖层
- `npm ci` 提供更确定的安装
- 排除开发依赖
- 用 `COPY --chown` 避免额外 `chown` 层
- 以镜像自带的非 root 用户运行
- 使用 exec form 让信号直接送达 Node

如果项目需要编译 TypeScript 或原生模块，应使用多阶段构建。

不要为了省几 MB 删除应用运行所需的 CA 证书或时区数据。

## Go：优化前

```dockerfile
# syntax=docker/dockerfile:1
FROM golang:1.26
WORKDIR /src
COPY . .
RUN go build -o server ./cmd/server
CMD ["./server"]
```

这会把 Go 工具链和源码带进生产镜像。

## Go：多阶段后的结果

```dockerfile
# syntax=docker/dockerfile:1
FROM golang:1.26-bookworm AS build
WORKDIR /src

COPY go.mod go.sum ./
RUN --mount=type=cache,target=/go/pkg/mod \
    go mod download

COPY . .
RUN --mount=type=cache,target=/go/pkg/mod \
    --mount=type=cache,target=/root/.cache/go-build \
    CGO_ENABLED=0 go build \
      -trimpath \
      -ldflags="-s -w" \
      -o /out/server ./cmd/server

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/server /server
USER nonroot:nonroot
ENTRYPOINT ["/server"]
```

`-s -w` 会移除调试信息。

这能减小二进制，但会降低崩溃分析能力。

需要符号化调试时，应保留带符号构件或单独输出 debug artifact。

`CGO_ENABLED=0` 不是无条件正确。

依赖 C 库、系统 DNS 行为或 SQLite CGO 驱动时，需要重新验证。

## 基础镜像如何选择

选择顺序可以是：

1. 明确运行时需要什么
2. 选择可信维护者和稳定更新渠道
3. 验证目标架构支持
4. 比较漏洞、兼容性和体积
5. 用 digest 固定生产输入
6. 建立受控更新流程

常见选项：

| 方案 | 优点 | 代价 |
| --- | --- | --- |
| Debian/Ubuntu slim | 兼容性好、易排障 | 比极简镜像大 |
| Alpine | 较小 | musl 兼容性需验证 |
| Distroless | 攻击面小、无 shell | 排障和动态依赖要求更严格 |
| `scratch` | 最小 | 无 CA、shell、用户数据库等 |

小不等于自动安全。

一个及时修复漏洞的 slim 镜像，可能优于长期无人维护的小镜像。

不要仅为了体积，把 glibc 应用换成 Alpine 后假设一切正常。

## tag 与 digest

tag 是可变的人类友好名称：

```text
node:24-bookworm-slim
```

digest 是内容寻址标识：

```text
node:24-bookworm-slim@sha256:&lt;digest&gt;
```

tag 可在未来指向新内容。

digest 精确标识某个 manifest 或 image index。

查询 digest：

```bash
docker buildx imagetools inspect node:24-bookworm-slim
docker pull node:24-bookworm-slim
docker image inspect node:24-bookworm-slim --format '{{json .RepoDigests}}'
```

生产 Dockerfile 可记录 tag 的可读语义，同时固定 digest：

```dockerfile
# syntax=docker/dockerfile:1
FROM node:24-bookworm-slim@sha256:&lt;reviewed-digest&gt;
```

固定 digest 会停止自动获取安全修复。

所以正确策略不是“永不更新”，而是：

- 由 Renovate、Dependabot 或内部机器人发现更新
- 在 PR 中展示新旧 digest 和上游 tag
- 重建、测试、扫描
- 审批后更新
- 保留回滚所需旧 digest

不要在生产流程中盲目依赖 `latest`。

`latest` 只是普通 tag，没有“最新且安全”的保证。

## 包管理器的清理

Debian/Ubuntu 示例：

```dockerfile
RUN apt-get update \
    && apt-get install -y --no-install-recommends ca-certificates curl \
    && rm -rf /var/lib/apt/lists/*
```

`apt-get update` 和安装应在同一个 `RUN` 中。

否则索引层可能陈旧，且删除发生在后层时无法缩小前层。

Alpine 示例：

```dockerfile
RUN apk add --no-cache ca-certificates tzdata
```

但最终镜像不应保留只在构建期使用的编译器。

把编译器放到 builder 阶段更稳妥。

## `COPY` 的几个细节

优先精确复制：

```dockerfile
COPY package.json package-lock.json ./
COPY src ./src
COPY public ./public
```

而不是一开始就：

```dockerfile
COPY . .
```

用 `--chown` 一步设置所有权：

```dockerfile
COPY --chown=10001:10001 app /app
```

在支持的场景可用 `--link` 改善重用与 rebase：

```dockerfile
COPY --link --from=build /out/app /app
```

使用前应验证构建器、目标布局和 symlink 语义是否适合。

## 常见失败优化

### 失败一：只合并所有 `RUN`

超长 `RUN` 可能少几个层，却让缓存粒度和可维护性变差。

层数本身通常不是主要问题。

应围绕生命周期和缓存边界组织指令。

### 失败二：后面再删除秘密

```dockerfile
COPY .npmrc /root/.npmrc
RUN npm ci
RUN rm /root/.npmrc
```

秘密仍在早期层中。

应使用 BuildKit secret mount。

### 失败三：用 `ARG` 传 token

```dockerfile
ARG NPM_TOKEN
RUN npm config set //registry.npmjs.org/:_authToken "$NPM_TOKEN"
```

构建参数不适合秘密。

它可能进入构建记录、缓存元数据或 provenance。

### 失败四：一律换 `scratch`

应用可能需要：

- CA 证书
- 时区数据库
- 动态链接库
- `/etc/passwd`
- DNS/NSS 配置
- 调试入口

缺少这些内容会把“体积优化”变成生产事故。

### 失败五：删除 lockfile

lockfile 是可重复构建和依赖审计的核心输入。

删掉它通常只会换来不可控版本漂移。

### 失败六：每次都 `--no-cache`

`--no-cache` 是诊断工具，不是日常优化策略。

日常构建应保留缓存，同时用 `--pull` 检查基础镜像更新：

```bash
docker buildx build --pull -t demo:test --load .
```

定期做无缓存重建可验证流程，但不应代替正确缓存设计。

## 优化验收

比较前后镜像：

```bash
docker image inspect demo:before --format '{{.Size}}'
docker image inspect demo:after --format '{{.Size}}'
docker history demo:before
docker history demo:after
```

验证容器用户：

```bash
docker run --rm demo:after id
docker inspect demo:after --format '{{.Config.User}}'
```

验证应用和信号处理：

```bash
docker run --name demo-test -d -p 3000:3000 demo:after
docker stop --time 10 demo-test
docker rm demo-test
```

验证健康接口：

```bash
curl --fail http://127.0.0.1:3000/healthz
```

查看镜像平台：

```bash
docker image inspect demo:after --format '{{.Os}}/{{.Architecture}}'
```

扫描并记录结果：

```bash
docker scout cves demo:after
docker scout recommendations demo:after
```

## 实战检查清单

- [ ] 已记录优化前镜像大小和构建时间
- [ ] 已查看 `docker history --no-trunc`
- [ ] 构建上下文只包含必要文件
- [ ] `.dockerignore` 排除了 VCS、缓存、产物和本地秘密
- [ ] 依赖清单先于源码复制
- [ ] 使用 lockfile 对应的确定性安装命令
- [ ] 编译器只存在于构建阶段
- [ ] 最终镜像只含运行时必需内容
- [ ] 使用可信、持续维护的基础镜像
- [ ] 生产基础镜像按 digest 固定并受控更新
- [ ] 没有盲目使用 `latest`
- [ ] 软件包索引与缓存未残留在最终层
- [ ] 应用以非 root 用户运行
- [ ] 未通过 `ARG`、`ENV` 或 `COPY` 注入秘密
- [ ] 已用 `--pull` 重建并运行测试
- [ ] 已扫描漏洞并定义处置策略
- [ ] 已验证 CA、时区、DNS 和动态库需求
- [ ] 已验证停止信号和退出时间
- [ ] 已保存优化前后数据，而非只凭感觉判断

## 小结

镜像体积优化应从测量和上下文开始。

最有价值的动作通常不是压缩某个文件，而是改变边界：

- 不把无关文件送入构建器
- 不让源码变更使依赖缓存失效
- 不把构建工具带入运行时
- 不把秘密写进任何层
- 不用不可控 tag 代替依赖治理

体积、速度、安全和可维护性需要一起验收。
