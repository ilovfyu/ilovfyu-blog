::: info 文档基线
本文只讨论 Ray Core，依据 2026-08-01 的 Ray latest 官方文档。Ray 能重试执行和重建部分对象，但不会自动恢复任意业务状态，也不承诺 exactly-once。
:::

容错设计的第一步不是把重试次数调大，而是区分 application-level failure 与 system-level failure，并明确 task、actor、object、owner、node 和 GCS 各自的恢复边界。

## 1. Application failure 与 system failure

### Application-level failure

用户代码抛出 Python 异常。Ray 把异常包装为 `RayTaskError`，在 `ray.get()` 或下游 task 解析依赖时抛出。若用户异常类型可被继承，捕获到的对象同时是 `RayTaskError` 和原异常类型；不可继承时从 `e.cause` 取原始异常。如果异常本身不可序列化，cause 会退化为 `RayError`。

```python
import ray

ray.init()

class TemporaryError(Exception):
    pass

@ray.remote
def validate(x):
    if x < 0:
        raise ValueError("x must be non-negative")
    return x

try:
    ray.get(validate.remote(-1))
except ValueError as exc:
    print("application error:", exc)

ray.shutdown()
```

### System-level failure

worker crash、进程被 kill、节点死亡、网络不可达或对象副本丢失等。Ray 可能重试 task、重启 actor、重建对象，也可能抛 `WorkerCrashedError`、`RayActorError`、`ActorUnavailableError`、`OwnerDiedError` 或 `ObjectLostError`。

边界很重要：应用异常默认不重试；系统故障的 task 默认会重试。不要用宽泛的 `except Exception` 把业务 bug 当成瞬态错误无限重放。

## 2. 普通 task 的重试

远程函数的 `max_retries` 控制 worker 意外死亡或对象 lineage reconstruction 时的额外尝试次数。默认 3，`0` 禁用，`-1` 无限。集群默认值可通过 driver/runtime env 的 `RAY_TASK_MAX_RETRIES` 覆盖。

```python
import os
import ray

ray.init()

@ray.remote(max_retries=1)
def crash_once(marker):
    if not os.path.exists(marker):
        with open(marker, "w", encoding="utf-8") as f:
            f.write("created")
        os._exit(1)  # 模拟系统级 worker crash
    return "recovered"

marker = os.path.abspath("ray-crash-once.marker")
if os.path.exists(marker):
    os.remove(marker)
print(ray.get(crash_once.remote(marker)))
os.remove(marker)
ray.shutdown()
```

::: note 示例边界
本地 marker 只适合单节点演示。多节点重试可能换节点，应把去重记录放在共享数据库/对象存储中。
:::

### 2.1 对指定应用异常重试

`retry_exceptions` 默认 `False`。可设为 `True` 重试所有应用异常，但更推荐异常 allowlist：

```python
import ray

class TemporaryError(Exception):
    pass

@ray.remote(max_retries=3, retry_exceptions=[TemporaryError])
def call_service(attempt):
    if attempt < 2:
        raise TemporaryError("retryable")
    return "ok"

# 每次自动重试参数不变；真实代码应让外部状态或内部逻辑最终恢复。
try:
    print(ray.get(call_service.remote(0)))
except TemporaryError:
    print("failed after retries")
```

`ValueError`、schema 错误等确定性 bug 不应重试。取消的 task 不会自动重试。CPU task 的 worker 默认可复用；第三方库泄漏时可设 `max_calls` 让 worker 执行若干次后退出。GPU task 默认每个 worker 只调用一次以释放显存；显式 `max_calls=0` 才无限复用。

### 2.2 重试意味着什么

系统级失败常发生在“副作用已经提交，但结果尚未返回”的窗口，因此 task 可能执行多次。Ray 提供的是重放机制，不是事务协调器。无限重试还可能隐藏永久故障并持续消耗资源，应有超时、告警和死信策略。

## 3. Actor restart 与 actor task retry

Actor 有两个独立旋钮：

- `max_restarts`：actor 进程意外死亡后重建多少次，默认 0，`-1` 无限。
- `max_task_retries`：actor method 因系统错误/不可达而重试多少次，默认 0。

重启会重新运行 `__init__`，内存状态归零，除非构造器从外部 checkpoint 恢复。

```python
import json
import os
import ray

ray.init()
checkpoint = os.path.abspath("actor-state.json")

@ray.remote(max_restarts=2, max_task_retries=3, num_cpus=1)
class Counter:
    def __init__(self, path):
        self.path = path
        if os.path.exists(path):
            with open(path, encoding="utf-8") as f:
                self.value = json.load(f)["value"]
        else:
            self.value = 0

    def set(self, request_id, value):
        # 覆盖写比 increment 更容易做成幂等；生产中需原子写和 request_id 去重。
        self.value = value
        temp = self.path + ".tmp"
        with open(temp, "w", encoding="utf-8") as f:
            json.dump({"request_id": request_id, "value": value}, f)
        os.replace(temp, self.path)
        return self.value

actor = Counter.remote(checkpoint)
print(ray.get(actor.set.remote("req-42", 42)))
ray.shutdown()
```

checkpoint 必须对重启后的任意候选节点可见，例如 S3、数据库或共享文件系统；节点本地文件不够。checkpoint 与外部副作用之间仍需事务/幂等协议，单纯先后写两个系统存在崩溃窗口。

Actor task 默认是 at-most-once 尝试：出错不重试，但调用者收到错误并不证明方法没有执行。`max_task_retries>0` 转为 at-least-once 风格，完成回复前崩溃可能导致重复执行。应用异常重试由 `@ray.method(retry_exceptions=...)` 或 `actor.method.options(retry_exceptions=..., max_task_retries=...)` 开启；解析优先级是调用选项、方法装饰器、actor 创建选项、actor 类装饰器、默认 0。

同步单线程 actor 在 at-least-once 重试时会尽力维持初始提交顺序；async/threaded actor 本来就不保证顺序，重启后只重试未完成调用。并发与顺序细节见 [Actor 深入](/kb/ai/Ray/Ray-Core/05-Actor-深入/)。

### 3.1 `ActorUnavailableError` 与 `RayActorError`

`ActorUnavailableError` 表示暂时不可访问：可能正在重启、网络瞬断或死亡尚未确认。该调用是否执行过不确定，但在未启用 retries 时 Ray 不会执行两次。最佳做法是先 quarantine actor，停止新流量，周期性 ping，直到恢复或收到确认死亡的错误。

`max_task_retries>0` 时，Ray 对 unavailable 调用重试；actor 构造器仍在运行也会消耗一次重试。构造器较慢可增大 `max_task_retries` 或调整 `RAY_task_retry_delay_ms`，但首先应让构造器快速、可重入。

`RayActorError` 通常表示 actor 确认死亡、owner 死亡或重启预算耗尽。用 `ray list actors --detail` 看 death cause。

## 4. Object lineage reconstruction

Ray object 包含数据与元数据。数据位于分布式 object store，元数据位于对象 owner。owner 是创建原始 ObjectRef 的 worker：例如 driver 调用 `f.remote()`，driver 是返回 ref 的 owner，尽管值由远端 worker 计算并存于别的节点。

对象数据副本因节点故障丢失时，Ray 先寻找其他副本；都没有则沿 lineage 重新执行生成 task，并递归重建参数。这受以下边界限制：

- 对象及传递依赖必须由 task/actor task 生成；`ray.put()` 对象没有可重放的生成 task，无法 lineage reconstruction。
- 普通 task 重建受 `max_retries` 限制，默认最多额外 3 次。
- actor task 结果默认不可重建；需非零 `max_task_retries`，且 actor/state 必须支持安全重放。
- owner 必须仍存活。
- 生成 task 应确定且幂等，否则重建值可能不同或重复副作用。

```python
import numpy as np
import ray

ray.init()

@ray.remote(max_retries=3)
def generated(seed):
    # 固定 seed，使 lineage 重放得到同样的值。
    return np.random.default_rng(seed).integers(0, 100, size=8)

recoverable_ref = generated.remote(123)
not_reconstructable_ref = ray.put(np.arange(8))
print(ray.get(recoverable_ref))
print(ray.get(not_reconstructable_ref))
ray.shutdown()
```

driver 为可重建对象保留 task 描述，lineage 可能增加 driver 内存；`RAY_max_lineage_bytes` 默认 1 GiB，超过后可淘汰 lineage。设置 `RAY_TASK_MAX_RETRIES=0` 可禁用普通 task 的自动 reconstruction；所有副本丢失后会抛 `ObjectLostError`。对象共享、pinning 与 spilling 见 [内存与对象溢写](/kb/ai/Ray/Ray-Core/08-内存与对象溢写/)。

## 5. Owner failure 是不可恢复边界

Ray 能从**数据副本丢失**中重建，但当前不能从**owner 死亡**中恢复对象元数据。owner worker/node 死亡后，Ray 清理残余数据副本以避免泄漏；其他 worker 再取值会收到 `OwnerDiedError`。

Actor 也有 owner：普通 actor 的 owner 是调用 `ActorClass.remote()` 的进程。owner 死亡时 actor fate-share，即便 `max_restarts=-1` 也不会恢复。detached actor 没有 owner 进程，可跨创建者死亡继续存在并按 `max_restarts` 重建，但需要手动销毁。

设计建议：关键长期 actor 使用明确 namespace、name 与 `lifetime="detached"`；长期对象不能只依赖某个短命 task 拥有其 ref，应把真正持久数据写入外部存储，而不是把 object store 当数据库。

## 6. Node failure

worker node 死亡时：

- 节点上运行的 task/actor 失败，并按各自重试/重启策略恢复。
- 由该节点 worker 拥有的对象发生 owner failure，不可恢复。
- 仅存储在该节点但 owner 在别处的对象，可从副本或 lineage 重建。
- raylet 崩溃等价于节点失败；即使同一机器重启 raylet，也以新 node ID 加入。
- [Placement Group](/kb/ai/Ray/Ray-Core/07-Placement-Group/) 中丢失 bundle 会尝试在其他节点重建，存活 bundle 可继续工作。

head node 默认承载 GCS；没有 GCS FT 时 head 失败意味着整个 Ray cluster 失败，不只是一个 worker node 故障。

## 7. GCS fault tolerance

GCS 管理集群级元数据及 actor、PG、node 等操作。默认数据只在内存中，GCS/头节点失败会使集群失败。配置高可用外部 Redis 后，重启的 GCS 可重新加载状态。

恢复期间不可用的操作包括 actor 创建/删除/重建、PG 创建/删除/重建、资源管理、worker node 注册和新 worker 进程创建；已运行 task/actor 仍存活，现有对象仍可用。raylet 默认 60 秒无法重连 GCS 就退出，可用 `RAY_gcs_rpc_server_reconnect_timeout_s` 调整。

```bash
RAY_REDIS_ADDRESS=redis.example.com:6379 \
ray start --head \
  --redis-username default \
  --redis-password "$REDIS_PASSWORD"
```

::: warning 支持边界
latest 官方文档说明：外部 Redis 的 GCS FT 仅在 KubeRay 的 Ray Serve FT 场景获得官方支持；其他场景需自行检测并重启 GCS/head，风险自担。本文只解释 Ray Core 的 GCS 机制，不展开 Ray Serve。还必须保证任意时刻只有一个 GCS 存活，并在 IP 可能变化时用稳定 FQDN。
:::

## 8. 幂等：重试前的必修课

Ray 没有 exactly-once。可靠方法通常是“at-least-once 执行 + 业务幂等/事务”。

### 8.1 幂等键与去重记录

```python
import sqlite3
import ray

@ray.remote(max_retries=3, retry_exceptions=[sqlite3.OperationalError])
def apply_payment(db_path, request_id, amount):
    # 单节点可运行示例。多节点应换成共享事务数据库。
    connection = sqlite3.connect(db_path)
    try:
        connection.execute(
            "CREATE TABLE IF NOT EXISTS payments "
            "(request_id TEXT PRIMARY KEY, amount INTEGER NOT NULL)"
        )
        connection.execute(
            "INSERT OR IGNORE INTO payments(request_id, amount) VALUES (?, ?)",
            (request_id, amount),
        )
        connection.commit()
        row = connection.execute(
            "SELECT amount FROM payments WHERE request_id = ?", (request_id,)
        ).fetchone()
        return row[0]
    finally:
        connection.close()
```

唯一键让同一 `request_id` 重放不会重复插入。真实支付还需校验相同 key 的 payload 是否一致，并使用支持并发和跨节点的事务存储。

### 8.2 常见幂等模式

- 把 `increment(1)` 改为 `set(version, value)`，用版本号做 compare-and-set。
- 外部写入带 request ID，并用唯一约束保存结果。
- 文件写到临时路径后原子 rename；对象存储使用条件写/版本。
- 把“副作用 + 去重标记”放在同一事务中；跨系统使用 outbox/saga，而不是假装原子。
- 随机数、时间、外部读取影响结果时，把 seed/输入快照显式作为 task 参数，保证 lineage 重放确定性。

## 9. 错误类型与排错

| 错误/现象 | 含义 | 首要行动 |
| --- | --- | --- |
| `RayTaskError` | 用户代码异常或其包装 | 查看 cause，不默认重试所有异常 |
| `WorkerCrashedError` | worker 意外退出且重试耗尽 | 查 worker/raylet 日志、OOM/segfault |
| `ActorUnavailableError` | actor 暂时不可达，执行结果不确定 | quarantine + 探活，副作用勿盲重放 |
| `RayActorError` | actor/owner 死亡或重启耗尽 | 查 actor death cause 与 owner |
| `OwnerDiedError` | ObjectRef owner 死亡 | 无法 lineage 恢复；从外部源重新生成 |
| `ObjectReconstructionFailedError` | lineage/依赖/重试不满足 | 检查 `ray.put`、actor result、重试预算 |
| `ObjectLostError` | 所有副本丢失且不能/未启用重建 | 重新计算或从持久存储加载 |
| `ObjectFetchTimedOutError` | 跨节点抓取超时，通常是系统问题 | 查网络与 raylet；默认超时约 10 分钟 |
| task attempt 数增加 | 系统重试或对象重建 | 用 task ID 查看每次 attempt 原因 |

```bash
ray status
ray list tasks --detail
ray list tasks -f task_id=&lt;task-id&gt;
ray list actors --detail
ray list nodes --detail
ray list placement-groups --detail
```

日志中关联 task ID、actor ID、worker PID、node ID 与 `ATTEMPT_NUMBER`。先确认是应用异常、worker crash、OOM kill、node death 还是 owner death，再调整策略；“增加重试”不是通用修复。

## 10. 最佳实践

1. 为每个远程操作写清楚：可否重试、最多几次、副作用、幂等键、超时与最终失败处理。
2. 应用异常用 allowlist 重试；参数错误和确定性 bug 立即失败。
3. task 不盲设 `-1`，actor 不盲设 `max_restarts=-1`；无限恢复必须配告警与熔断。
4. actor checkpoint 放到跨节点存储，构造器快速、可重入，恢复后验证版本。
5. 不把 object store/spill 当持久存储；重要数据写外部 durable system。
6. 管理 owner 生命周期：短命 task 不应拥有长期关键对象或普通 actor。
7. 对随机/时间相关计算显式传入 seed 和输入快照，使 lineage reconstruction 确定。
8. 将 OOM kill、PG bundle 恢复、node replacement 纳入故障演练，而不只测试 Python exception。
