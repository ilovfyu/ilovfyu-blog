# Ray Core 可观测性与调试

::: abstract 本文范围
本文依据 2026-08-01 Ray `latest` 官方文档，建立 Ray Core 从 cluster 到 Job、Task/Actor、Worker、Object 的观测与排错方法。依赖和 namespace 见 [Runtime Environment 与命名空间](/kb/ai/Ray/Ray-Core/10-Runtime-Environment-与命名空间/)，程序结构问题见 [设计模式与反模式](/kb/ai/Ray/Ray-Core/12-设计模式与反模式/)。
:::

## 1. 先建立证据链

Ray 问题常被笼统描述为“卡住”，但至少要区分四层：

| 层次 | 关键问题 | 首选工具 |
|---|---|---|
| Cluster/Node | 节点健康吗，资源是否存在 | `ray status`、Dashboard Cluster/Metrics |
| 调度状态 | Task/Actor 为什么 pending | Dashboard Jobs、`ray summary/list tasks` |
| Worker 进程 | 正在计算、等待、死锁还是崩溃 | logs、Stack Trace、`ray stack` |
| Object/内存 | 对象是否 pinned、spill，heap 是否 OOM | `ray memory`、State Objects、Metrics |

推荐顺序：先摘要，再过滤异常实体，再查看单项详情和日志，最后才进程级 profile。不要先在海量 worker 日志中盲搜。

## 2. Dashboard

安装并启动：

```bash
python -m pip install -U "ray[default]"
```

```python
import ray

context = ray.init()
print(context.dashboard_url)  # 通常为 127.0.0.1:8265
```

容器内手动启动时需监听容器外地址：

```bash
ray start --head --dashboard-host=0.0.0.0
```

生产上通过 SSH tunnel、反向代理或平台访问控制暴露 Dashboard；8265 不应直接公开到不可信网络。

### 2.1 各视图怎么用

- **Overview/Cluster**：节点、Worker、CPU/GPU、内存、磁盘、网络的当前状态。
- **Jobs**：Job 进度，Task/Actor 按状态和名称聚合，父子 Task/Actor 展开，错误与日志入口。
- **Actors**：Actor 状态、PID、所在节点、方法历史、日志和 profiling。
- **Logs**：按节点和文件浏览、搜索系统与应用日志。
- **Metrics**：逻辑资源与物理使用率的时间序列，需要 Prometheus 和 Grafana。
- **Events**：Job 与 autoscaler 事件。

Dashboard 单个 Job 最多展示/检索 10,000 个 Task，超出部分会显示未统计数量。因此 UI 的“没有看到”不等于不存在；大规模 Job 应结合 State CLI、指标和应用级计数。

## 3. `ray status`：先看容量与需求

在 head 节点运行：

```bash
ray status
ray status -v
```

它回答：

- 哪些节点 Healthy、Pending 或近期失败。
- CPU、GPU、memory、object store memory 等逻辑资源使用。
- 当前无法满足的 resource demands。
- autoscaler 正在扩还是缩，以及为什么节点不能缩容。

`ray status` 是 cluster 聚合视角，不按 Job 隔离。多个 Job 共用集群时，需求可能来自别的 Job。看到 `CPU: 0/64` 也不表示没有内存、对象存储、custom resource 或 placement group 瓶颈。

## 4. State CLI 与 Python API

State API 需要 Dashboard 组件。CLI 是稳定 API，Python SDK 位于 `ray.util.state`，截至本文日期仍是 DeveloperAPI；自动化优先 CLI 或对 SDK 版本做严格固定。

### 4.1 Summary -> List -> Get

```bash
# 先聚合
ray summary tasks
ray summary actors
ray summary objects

# 再过滤异常个体
ray list tasks -f state=PENDING_NODE_ASSIGNMENT --detail
ray list tasks -f state=RUNNING --detail
ray list actors -f state=DEAD --detail
ray list placement-groups --detail
ray list runtime-envs --detail

# 最后获取单项
ray get tasks <TASK_ID>
ray get actors <ACTOR_ID>
ray get nodes <NODE_ID>
```

可用资源包括 tasks、actors、objects、jobs、nodes、workers、placement-groups、runtime-envs 和 cluster-events。字段、状态值和可过滤列以当前 `ray list &lt;resource&gt; --help` 为准。

Python 诊断示例：

```python
from ray.util.state import list_actors, list_tasks, summarize_tasks

print(summarize_tasks())

running = list_tasks(
    filters=[("state", "=", "RUNNING")],
    detail=True,
    limit=100,
)
for task in running:
    print(task.task_id, task.name, task.node_id, task.worker_pid)

alive = list_actors(filters=[("state", "=", "ALIVE")], limit=100)
for actor in alive:
    print(actor.actor_id, actor.name, actor.pid)
```

### 4.2 State API 的边界

State 是诊断快照，不是事务数据库：

- GCS、raylet 等数据源不可用时，CLI 可能返回部分结果并警告；Python SDK 默认可能抛异常。
- 实体超过 100,000 条时可能截断，无法指定被截断的是哪一部分。
- FINISHED Task、DEAD Actor 等历史元数据可能已被垃圾回收。
- 不要用 State API 作为业务账本、精确审计源或完成语义。

## 5. 日志

### 5.1 日志流向和目录

Task/Actor 的 stdout/stderr 默认写入 Worker 日志并流到 Driver，前缀包含 Task/Actor、PID 和 IP。可关闭 Driver 汇聚：

```python
ray.init(log_to_driver=False)
```

默认目录为 `/tmp/ray/session_*/logs`，`/tmp/ray/session_latest` 指向当前 session。常见文件：

- `job-driver-<submission_id>.log`：通过 Jobs API 提交的 Driver。
- `worker-<worker_id>-<job_id>-&lt;pid&gt;.out|err`：Task/Actor 应用输出。
- `raylet.out|err`：节点调度、Worker 与内存监控。
- `gcs_server.out|err`：head 节点元数据服务。
- `runtime_env_agent.*`、`runtime_env_setup-<job_id>.log`：环境创建与安装。

目录和文件名不保证向后兼容，且节点停止后 `/tmp` 可能消失。生产必须用 sidecar/agent 把日志送到持久系统。

### 5.2 用 State Log API 获取

```bash
ray logs actor --id=<ACTOR_ID> --follow
ray logs worker --pid=&lt;PID&gt; --follow
ray logs raylet.out --node-ip=<NODE_IP> --follow
ray logs cluster gcs_server.out --node-id=<NODE_ID>
```

Python SDK：

```python
from ray.util.state import get_log

for line in get_log(actor_id="<ACTOR_ID>", follow=False, tail=200):
    print(line, end="")
```

死节点上的日志无法通过 State Log API 获取，这也是集中持久化日志的理由。

### 5.3 结构化日志与上下文

```python
import logging
import ray

ray.init(
    log_to_driver=False,
    logging_config=ray.LoggingConfig(
        encoding="JSON",
        log_level="INFO",
        additional_log_standard_attrs=["name"],
    ),
)

logger = logging.getLogger("app")


@ray.remote
def process(item_id: str):
    logger.info("processing", extra={"item_id": item_id})
    return item_id


ray.get(process.options(name="process-item").remote("item-42"))
ray.shutdown()
```

`LoggingConfig` 会给 Driver、Task 和 Actor 的记录附加可用的 `job_id`、`worker_id`、`node_id`、`task_id`、`actor_id` 等字段。设置 `log_to_driver=False` 可避免 Driver 转发前缀破坏 JSON。

Ray 默认去重跨 Worker 重复日志。调试时需完整输出，可在 **导入 Ray 前** 设置：

```bash
RAY_DEDUP_LOGS=0 python app.py
```

## 6. Runtime Context：在代码中标记“我是谁”

```python
import os
import ray

ray.init(namespace="debug-demo")


@ray.remote
def identify() -> dict[str, str | int]:
    ctx = ray.get_runtime_context()
    return {
        "job_id": str(ctx.get_job_id()),
        "task_id": str(ctx.get_task_id()),
        "node_id": str(ctx.get_node_id()),
        "namespace": ctx.namespace,
        "pid": os.getpid(),
    }


print(ray.get(identify.options(name="identify-request").remote()))
ray.shutdown()
```

Actor 内可取 `get_actor_id()`。Runtime Context 适合关联应用日志、State 行和节点；Job Submission ID 尚不能从这里直接获得，应由提交系统作为应用元数据显式传递。

给 Task/Actor 设置有意义的 `.options(name=...)`，让 Dashboard 聚合和日志检索可读；不要把高基数字段如 request ID 直接当成 Task 名，否则聚合失效。

## 7. Timeline、Stack 与 Profiling

### 7.1 Timeline

首选从 Dashboard 的 Job 页面下载 Timeline。若使用 DeveloperAPI `ray.timeline()`，必须在 Ray 启动前开启 profiling 并让 Task Events 立即上报：

```bash
RAY_PROFILING=1 RAY_task_events_report_interval_ms=0 python app.py
```

```python
import ray

ray.init()
# 运行一段代表性负载后导出 Chrome trace。
ray.timeline(filename="timeline.json")
```

将文件放入 Perfetto UI 打开。Ray Core CLI 没有 `ray timeline` 子命令；不要把 `ray.timeline()` 当成稳定的默认生产接口。重点观察：

- Worker 是否有大片空闲区，说明提交、依赖或资源供给不足。
- 序列化/反序列化是否占比过高。
- Task 是否过细，调度开销接近计算时间。
- 长尾 Task 是否拖慢按提交顺序消费。
- Actor 方法是否因单线程串行形成队头阻塞。

Timeline 是调度事件视图，不替代业务 tracing；大集群导出成本和文件体积都需要控制。

### 7.2 Stack Trace 与 CPU Flame Graph

Dashboard profiling endpoint 出于安全原因默认关闭。只在受控且已鉴权的 Dashboard 上，于 head node 启动 Ray 前开启：

```bash
export RAY_DASHBOARD_ENABLE_PROFILING=1
ray start --head
```

开启后，Dashboard 可对运行中的 Driver、Worker、Task 和 Actor 执行：

- **Stack Trace**：用 `py-spy` 采样当前 Python 栈。
- **CPU Flame Graph**：一段时间内多次采样，定位 CPU 热点。

高级 URL 参数包括 Linux 下的 `native=1`、包含阻塞线程的 `idle=1`、包含子进程的 `subprocesses=1`。容器内 ptrace 权限常导致 `py-spy` 失败，应按最小权限原则配置 capability/安全上下文，不要为了 profile 长期让整个集群以 root 运行。

当前节点所有 Ray Worker 的栈：

```bash
ray stack
```

`No stack counts found` 可能只是进程最近在 sleep；`No such file or directory` 可能表示 Worker 已退出，需结合 State 和日志判断。

### 7.3 `cProfile` 与 `memray`

Driver 提交路径可用 `cProfile` 找出 `ray.get` 阻塞和序列化开销。Task/Actor 的 heap 泄漏可用 `memray`：

```python
import ray


@ray.remote
def profiled_task() -> int:
    import memray

    task_id = ray.get_runtime_context().get_task_id()
    path = f"/tmp/ray/session_latest/logs/{task_id}_memray.bin"
    with memray.Tracker(path):
        value = bytearray(10_000_000)
        return len(value)


ray.init(runtime_env={"pip": ["memray"]})
print(ray.get(profiled_task.remote()))
ray.shutdown()
```

`ray.init(runtime_env=...)` 只把 `memray` 安装到子 Task/Actor 环境，因此示例必须在 Task 内导入；它不会把包安装到入口 Driver。从 Dashboard Logs 下载后运行 `memray flamegraph file.bin`。短 Task 会生成大量 profile 文件，只对采样任务启用并治理磁盘。

## 8. Import 与 Runtime Environment 错误

典型症状是 `ModuleNotFoundError`、`FileNotFoundError`、environment setup timeout 或 Task 长期不启动。

排查：

```bash
ray list runtime-envs --detail
ray logs cluster 'runtime_env_setup-*'
ray logs cluster runtime_env_agent.log
```

按以下问题判断：

1. 错误在 Driver 还是 Worker？`ray.init(runtime_env=...)` 不影响入口 Driver。
2. `working_dir` 是否被 ignore/excludes 排除，是否超过本地 500 MiB 限制？
3. 子 Task/Actor 是否覆盖了父级整个 `pip`/`py_modules` 字段？
4. Python、Ray、平台 wheel、Conda ABI 是否与集群一致？
5. 包仓库、DNS、代理、证书和节点磁盘是否正常？

完整机制见 [Runtime Environment 与命名空间](/kb/ai/Ray/Ray-Core/10-Runtime-Environment-与命名空间/)。

## 9. Pending：到底在等什么

先执行：

```bash
ray status
ray summary tasks
ray list tasks --detail
ray list placement-groups --detail
```

常见状态与解释：

| 现象/状态 | 常见原因 | 修复方向 |
|---|---|---|
| `PENDING_NODE_ASSIGNMENT` | 没有节点满足 CPU/GPU/custom resources，或调度策略不可满足 | 修正资源声明、扩容、检查节点标签 |
| `PENDING_ARGS_AVAIL` | 上游 ObjectRef 未就绪或丢失 | 查父 Task、对象 owner、上游错误 |
| `PENDING_OBJ_STORE_MEM_AVAIL` | 返回值等待 object store 空间 | 消费/释放引用、开启 spill、减小并发/对象 |
| placement group Pending | bundles 无法同时满足，可能是碎片化或策略过严 | 检查 bundle、PACK/SPREAD/STRICT 策略和容量 |
| Actor 创建 Pending | 默认资源、runtime env、placement group 或节点亲和约束 | 查看 Actor creation task 与 env 日志 |

重要边界：Ray 的 `num_cpus`/custom resources 是调度许可，不是物理 CPU、内存隔离。声明错误会造成过度并发或永远 pending。`memory` 也是调度资源，不能替代操作系统限制。

## 10. Hang 与死锁

### 10.1 三类常见 hang

**资源死锁**：父 Task/Actor 持有资源，同时同步等待需要相同资源的子 Task。尤其是 Actor 内 `ray.get` 子任务，而所有 CPU 已被 Actor 占用。

**Actor 队头阻塞**：普通 Actor 单线程执行；一个无限循环/长 I/O 方法不返回，后续健康检查也无法执行。改用 Async Actor 并 `await`，或拆分 Actor，见 [. Async Actor：并发 I/O，不是并行 CPU](/kb/ai/Ray/Ray-Core/12-设计模式与反模式/#5.%20Async%20Actor%EF%BC%9A%E5%B9%B6%E5%8F%91%20I%2FO%EF%BC%8C%E4%B8%8D%E6%98%AF%E5%B9%B6%E8%A1%8C%20CPU)。

**应用锁/外部 I/O**：Worker 处于 Python lock、socket、数据库、文件系统或 native library。State 只显示 RUNNING，必须看 stack，Flame Graph 开 `idle=1`。

### 10.2 定位顺序

1. `ray status` 看不可满足资源需求。
2. `ray list tasks --detail` 分离 pending 与 running。
3. 找到 `node_id`、`worker_pid`，看对应日志。
4. Dashboard Stack Trace 或 `ray stack` 看阻塞点。
5. 检查代码中的 `ray.get`、锁、无限循环和同步外部调用。
6. 给外部 I/O、`ray.get(..., timeout=...)` 和业务阶段设置超时；超时后保留诊断信息，而不是无条件重试风暴。

## 11. 分布式 Debugger

Ray Distributed Debugger 由后端和 VS Code/兼容 IDE 扩展组成，支持远程断点与 Task 异常后的 post-mortem。安装：

```bash
python -m pip install "ray[default]" debugpy
```

可运行示例：

```python
import ray

ray.init(runtime_env={
    "env_vars": {"RAY_DEBUG_POST_MORTEM": "1"},
})


@ray.remote
def divide(x: int, y: int) -> float:
    breakpoint()
    return x / y


print(ray.get(divide.remote(10, 2)))
```

将 VS Code Ray 扩展连接到 Dashboard 地址，Paused Tasks 中 attach。Post-mortem 会冻结未捕获异常的 Task 等待 attach，可能占用 Worker 与资源；只在隔离的开发/预生产环境开启，不要在生产全局开启。

`local_mode=True` 不是可靠的分布式语义测试替代品；它改变执行模型，适合极小范围单步验证，最终必须在真实多进程环境复现。

## 12. 内存排查

Ray 节点内存至少分为：

- Worker heap：普通 Python/Native 分配，进程私有。
- Object store：共享内存中的 Ray Object，可 spill 到磁盘。
- Ray 系统进程：raylet、GCS、Dashboard 等。

### 12.1 ObjectRef 和对象存储

启用创建位置后启动集群：

```bash
RAY_record_ref_creation_sites=1 ray start --head
ray memory --sort-by=OBJECT_SIZE --group-by=STACK_TRACE
ray summary objects
ray list objects --detail
```

`ray memory` 重点看引用类型、对象大小、创建栈和哪个进程 pin 住对象。常见泄漏来源：Driver 无界保存 refs、pending queue 无界、Actor 字段长期保存 refs、闭包捕获大对象、ObjectRef 被带外序列化。修复模式见 [. `ray.wait` 背压：限制 in-flight，而非伪装资源调度](/kb/ai/Ray/Ray-Core/12-设计模式与反模式/#6.%20%60ray.wait%60%20%E8%83%8C%E5%8E%8B%EF%BC%9A%E9%99%90%E5%88%B6%20in-flight%EF%BC%8C%E8%80%8C%E9%9D%9E%E4%BC%AA%E8%A3%85%E8%B5%84%E6%BA%90%E8%B0%83%E5%BA%A6)。

### 12.2 Heap/OOM

Ray memory monitor 在节点达到阈值时会优先杀 Worker并抛 `OutOfMemoryError`，比 Linux OOM killer 的 SIGKILL 更可诊断。若只见 `WorkerCrashedError`/连接断开，仍要查 `raylet.out`、worker 日志和 Linux `dmesg`。

Dashboard per-component memory 通常用 `RSS - SHR` 估计进程私有内存；SHR 主要含多个进程共享的 object store 映射，不能把每个进程 SHR 简单求和。

降低风险：

- 用资源声明限制运行并发；高内存 Task 可增加 `num_cpus` 作为粗粒度节流。
- 用 `ray.wait` 限制 pending 数和 Driver 保存的 refs。
- 用 generator/yield 分块返回大结果。
- 尽早删除无用 refs，避免 Driver 聚合所有大结果。
- 配置 object spilling 和足够磁盘；spill 不是无限内存。
- head 节点只承担控制面时以 `--num-cpus=0` 启动，避免业务 Task 与 GCS/Dashboard 争内存。

不要把提高 `RAY_memory_usage_threshold` 或关闭 memory monitor 当成首选修复；这会把可诊断的 Ray OOM 变成更危险的 OS OOM。

## 13. Error、崩溃与重试

`ray.get()` 会把远端异常以 `RayTaskError` 等形式带回。先保留原始 traceback，再判断：

- **确定性业务异常**：输入/代码必然失败，重试无益，应修复或送死信。
- **Worker crash/OOM**：查节点、PID、raylet/worker 日志和内存趋势。
- **Node lost**：查 autoscaler、节点事件和基础设施；对象是否可重建取决于 lineage/owner。
- **Actor died**：看 `death_cause`、`max_restarts`、方法 `max_task_retries`，并确认 Actor 状态是否可恢复。
- **Object lost/owner died**：检查 ObjectRef 所有者生命周期，避免把 refs 存到外部系统后让 owner 退出。

重试必须配合幂等性、退避、上限和去重键。无限重试会把确定性错误变成资源占用和日志风暴。

## 14. 一套可复用的故障 Runbook

```bash
# 1. 集群与需求
ray status -v

# 2. 摘要
ray summary tasks
ray summary actors
ray summary objects

# 3. 异常实体
ray list tasks --detail
ray list actors --detail
ray list placement-groups --detail
ray list runtime-envs --detail

# 4. 组件日志
ray logs raylet.out --node-ip=<NODE_IP>
ray logs actor --id=<ACTOR_ID>

# 5. 当前节点栈
ray stack
```

每次事故记录 Ray/Python 版本、cluster 配置、Job/Task/Actor/Node ID、namespace、runtime env、时间窗口、输入规模和首次异常。没有这些上下文，分布式错误很难稳定复现。

## 15. 生产最佳实践

- Dashboard + Prometheus + Grafana + 集中日志同时部署；State 快照不替代时序指标。
- Task/Actor 使用低基数语义名称，日志使用 JSON 并附业务 correlation ID。
- 为 pending、失败率、重试、OOM kill、object spill、节点失败、runtime env 安装时长设告警。
- State CLI 用于操作诊断；业务完成状态写入自己的持久系统。
- 日志离开 `/tmp` 持久化，设置保留期、轮转、脱敏和访问控制。
- 所有外部调用有超时，所有重试有上限，所有写操作考虑幂等。
- 先在接近生产的多进程/多节点环境验证，不依赖 local mode 得出结论。
