# Ray Core 设计模式与反模式

::: abstract 本文范围
本文依据 2026-08-01 Ray `latest` 官方文档，专讲 Ray Core Task、Actor 和 ObjectRef 的组织方式。各模式提供可运行的完整 Python 示例，反模式章节另含用于正反对照的局部片段；生产观测见 [可观测性与调试](/kb/ai/Ray/Ray-Core/11-可观测性与调试/)，依赖与 namespace 见 [Runtime Environment 与命名空间](/kb/ai/Ray/Ray-Core/10-Runtime-Environment-与命名空间/)。
:::

## 1. 先用四个问题选模式

1. 工作是 CPU 计算、I/O 等待，还是长期状态？CPU/无状态优先 Task，状态优先 Actor，I/O 并发可用 Async Actor。
2. 限制的是 **pending 数** 还是 **running 数**？前者用 `ray.wait` 背压，后者用资源声明。
3. 数据是一个完整对象还是流？大对象流优先 generator，阶段流优先 pipeline。
4. 谁拥有状态和 ObjectRef？所有权决定故障恢复、垃圾回收和生命周期。

## 2. Nested Parallelism：父任务动态展开子任务

Nested task 让一个 Task 根据输入动态创建子 Task，适合递归、分层分片和每个输入展开数量不同的工作流。

```python
import ray

ray.init(num_cpus=4)


@ray.remote
def square(x: int) -> int:
    return x * x


@ray.remote
def sum_squares(values: list[int]) -> int:
    refs = [square.remote(x) for x in values]
    return sum(ray.get(refs))


groups = [[1, 2, 3], [4, 5], [6, 7, 8]]
print(ray.get([sum_squares.remote(group) for group in groups]))
ray.shutdown()
```

机制：父 Task 的 `.remote()` 与 Driver 提交相同，会在运行时构建新的依赖图。Dashboard 会把子 Task 嵌套显示在父 Task 下。

边界与生产建议：

- 父 Task 同步 `ray.get` 子任务时会占住其 Worker；根据资源配置可能造成资源死锁或降低利用率。
- 若父层只做编排，考虑父 Task `num_cpus=0`，但必须确认它确实不做 CPU 密集工作，且不会无限制造控制面压力。
- 限制每个父任务的 fan-out；动态递归要有深度、节点数和重试上限。
- 子任务直接接收上游 ObjectRef，避免父任务先 `ray.get` 大对象再重新提交。

## 3. Generator：分块返回，降低峰值 heap

普通 Task 先构造完整列表再返回，会同时持有全部结果。Generator Task 每次 `yield` 一个对象，使 Worker 有机会释放上一块 heap，并让消费者逐块处理。

### 3.1 动态返回生成器

```python
import ray

ray.init()


@ray.remote
def chunks(total: int, chunk_size: int):
    for start in range(0, total, chunk_size):
        yield list(range(start, min(start + chunk_size, total)))


generator = chunks.remote(20, 6)
total = 0
for chunk_ref in generator:
    chunk = ray.get(chunk_ref)
    print(chunk)
    total += sum(chunk)

print(total)
ray.shutdown()
```

每次迭代得到的是 `ObjectRef`，再 `ray.get` 具体块。动态 generator 适合返回数量事先未知；若数量已知，也可设置固定 `num_returns=N`。

### 3.2 边界

- Generator 降低 Task 进程 heap 峰值，不保证消费者足够慢时生产者完全不占对象存储；仍需背压和及时释放 refs。
- 分块过小会增加调度、对象元数据和序列化开销；按目标块大小与处理时间做基准测试。
- 重试意味着 generator Task 可能重新执行，外部副作用必须幂等；消费者要能处理重复或从 checkpoint 恢复。
- 不要把所有 chunk 重新收集成列表再一次性 `ray.get`，否则重新制造峰值。

## 4. Resource Throttle：用资源限制运行并发

Ray 根据每个 Task/Actor 的逻辑资源需求决定同时运行多少实例。若节点有 8 CPU，把每个 Task 声明为 2 CPU，最多约 4 个同时运行：

```python
import os
import time
import ray

ray.init(num_cpus=4)


@ray.remote(num_cpus=2)
def memory_heavy(i: int) -> tuple[int, int]:
    payload = bytearray(20_000_000)
    time.sleep(0.2)
    return i, os.getpid()


print(ray.get([memory_heavy.remote(i) for i in range(8)]))
ray.shutdown()
```

资源是调度许可，不是 cgroup 隔离。Task 即使声明 2 CPU，也可创建更多线程；反之声明 0.1 CPU 也不会物理限速。生产建议：

- CPU 计算按真实占用声明，并设置 `OMP_NUM_THREADS`、`MKL_NUM_THREADS` 等，避免每个 Worker 再抢满所有核。
- 高内存 Task 可增加 `num_cpus` 作为粗粒度并发阀；同时用指标校准，不要假设“每 CPU 固定内存”。
- 特殊许可可使用 custom resource，例如节点配置 `{"ingest_slot": 4}`，Task 用 `resources={"ingest_slot": 1}`；它仍只是逻辑标签。
- 限制 running 数用资源；限制已提交但未完成的 in-flight 数用下一节的 `ray.wait`。

## 5. Async Actor：并发 I/O，不是并行 CPU

普通 Actor 默认单线程串行处理方法。Async Actor 在一个 asyncio event loop 上并发运行协程；`await` 时主动让出控制。

```python
import asyncio
import ray

ray.init()


@ray.remote(max_concurrency=32)
class Fetcher:
    def __init__(self):
        self.in_flight = 0

    async def fetch(self, item: int) -> int:
        self.in_flight += 1
        try:
            await asyncio.sleep(0.1)  # 模拟异步网络 I/O
            return item * 10
        finally:
            self.in_flight -= 1

    async def stats(self) -> int:
        return self.in_flight


fetcher = Fetcher.remote()
refs = [fetcher.fetch.remote(i) for i in range(20)]
print(ray.get(fetcher.stats.remote()))
print(ray.get(refs))
ray.shutdown()
```

关键规则：

- 在 Async Actor 内等待 ObjectRef 用 `await ref`，不要用阻塞的 `ray.get(ref)`。
- `max_concurrency` 限制可并发方法数；值太大会压垮数据库、socket pool 或 Actor heap。
- CPU 密集 Python 代码不会因 asyncio 并行，应拆成普通 Task；需要线程并发可考虑 threaded actor。
- 协程在 `await` 之间仍会修改共享 Actor 状态，保证不变量时使用短临界区或显式 `asyncio.Lock`，不要在持锁时做远程等待。

## 6. `ray.wait` 背压：限制 in-flight，而非伪装资源调度

无界提交会积累 Task 元数据、参数、ObjectRef 和 Actor mailbox。保持固定窗口：

```python
import time
import ray

ray.init(num_cpus=4)


@ray.remote
def process(i: int) -> int:
    time.sleep(0.05)
    return i * i


MAX_IN_FLIGHT = 16
pending: list[ray.ObjectRef] = []
results: list[int] = []

for i in range(100):
    pending.append(process.remote(i))
    if len(pending) >= MAX_IN_FLIGHT:
        ready, pending = ray.wait(pending, num_returns=1)
        results.extend(ray.get(ready))

while pending:
    ready, pending = ray.wait(pending, num_returns=1)
    results.extend(ray.get(ready))

print(len(results), sum(results))
ray.shutdown()
```

窗口应按 Task 延迟、提交速率、参数/结果大小和可容忍内存测量。`ray.wait` 主要限制 pending/in-flight；若只想限制 running 数，资源调度更高效。生产循环还应处理失败、取消、超时和优雅停止。

## 7. Supervisor/Actor Tree：分层拥有与恢复

Supervisor Actor 创建并持有 Worker Actor handles，把 Worker 生命周期和故障处理集中起来，Driver 只管理少量 Supervisor。

```python
import ray

ray.init(num_cpus=4)


@ray.remote
class Worker:
    def __init__(self, shard: int):
        self.shard = shard

    def process(self, value: int) -> tuple[int, int]:
        return self.shard, value * 2


@ray.remote
class Supervisor:
    def __init__(self, shards: int):
        self.workers = [Worker.remote(i) for i in range(shards)]

    def map(self, values: list[int]):
        refs = [
            self.workers[i % len(self.workers)].process.remote(value)
            for i, value in enumerate(values)
        ]
        return ray.get(refs)


supervisor = Supervisor.remote(3)
print(ray.get(supervisor.map.remote(list(range(9)))))
ray.shutdown()
```

Actor 引用计数形成所有权树：Supervisor 或其所有者 Driver 退出时，普通子 Actor 通常随引用消失而终止。边界：

- Supervisor 本身成为故障域和潜在吞吐瓶颈；多个 Supervisor 可分区。
- Actor restart 不会自动恢复 Python 内存状态。Supervisor 要保存可重建的配置/checkpoint，而不是只保存瞬时 handle。
- 不要无意把 Worker handle 返回并长期散落到树外，否则生命周期和访问控制变模糊。
- 跨 Job 长期服务才考虑 named + detached，并配置外部状态和清理，见 [. Namespace：名称的逻辑边界](/kb/ai/Ray/Ray-Core/10-Runtime-Environment-与命名空间/#8.%20Namespace%EF%BC%9A%E5%90%8D%E7%A7%B0%E7%9A%84%E9%80%BB%E8%BE%91%E8%BE%B9%E7%95%8C)。

## 8. Pipelining：重叠通信与计算

预取下一项，同时处理当前项，可隐藏 RPC/对象传输延迟：

```python
import time
import ray

ray.init()


@ray.remote
class Queue:
    def __init__(self):
        self.items = list(range(10))

    def next(self):
        time.sleep(0.02)  # 模拟远程读取
        return self.items.pop(0) if self.items else None


@ray.remote
class Worker:
    def run(self, queue: ray.actor.ActorHandle) -> list[int]:
        outputs = []
        next_ref = queue.next.remote()
        while True:
            item = ray.get(next_ref)
            if item is None:
                return outputs
            next_ref = queue.next.remote()  # 先发起下一次 I/O
            time.sleep(0.03)                # 再处理当前项
            outputs.append(item * 2)


queue = Queue.remote()
worker = Worker.remote()
print(ray.get(worker.run.remote(queue)))
ray.shutdown()
```

可扩展为深度 N 的预取窗口，但窗口越深，内存、未完成请求和失败时浪费越大。流水线提高稳定态吞吐，不一定降低单项延迟；各阶段速率不平衡时仍需有界队列和背压。

## 9. 官方反模式总览

| 反模式 | 主要损害 | 首选替代 |
|---|---|---|
| 循环中 `ray.get` | 并行退化为串行 | 先提交，再批量 get/wait |
| 不必要的 `ray.get` | Driver 往返、数据复制、破坏 DAG | 直接传 ObjectRef |
| 在 Task 参数上 `ray.get` | 父 Worker 阻塞、数据绕行 | 顶层参数直接传 ref |
| 按提交顺序 get | 被慢任务队头阻塞 | `ray.wait` 按完成顺序 |
| 一次 get 太多对象 | Driver heap OOM | 分批 wait/get/聚合 |
| Task 过细 | 调度开销超过计算 | batch |
| 循环重定义 remote | 重复导出函数/类 | 模块级定义一次 |
| 大参数反复按值传 | 重复序列化与复制 | `ray.put` 一次复用 |
| 闭包捕获大对象 | 隐式复制，定义体巨大 | 显式 ObjectRef 参数 |
| globals 共享状态 | 多进程/多节点不一致 | Actor/外部存储 |
| Task 返回 `ray.put` ref | 多一层 ref，降低容错 | 直接返回值 |
| 带外序列化 ObjectRef | 对象泄漏或意外 GC | 通过 Ray 参数/返回值传 ref |
| `fork` 新进程 | 继承 Ray 线程/连接导致死锁 | `spawn`/`forkserver` 或 Ray Task |

## 10. `ray.get` 家族反模式

### 10.1 循环中立即 get

```python
# 反模式：每次等待后才提交下一项
results = [ray.get(process.remote(i)) for i in range(100)]

# 正确：暴露并行性
refs = [process.remote(i) for i in range(100)]
results = ray.get(refs)
```

### 10.2 不必要的 get

```python
@ray.remote
def produce():
    return [1, 2, 3]


@ray.remote
def consume(values):
    return sum(values)


# 反模式：对象先拉回 Driver，再传回 Worker
result_ref = consume.remote(ray.get(produce.remote()))

# 正确：顶层 ObjectRef 依赖由 Ray 自动等待和解引用
result_ref = consume.remote(produce.remote())
```

同理，远程函数若收到一个 `ObjectRef` 作为顶层参数，Ray 已在执行前解析；不要再围绕参数设计多余 `ray.get`。只有 ref 嵌套在 list/dict 中且你明确需要时，才考虑在 Task 内解析，但通常更清晰的做法是改变参数形状。

### 10.3 按提交顺序处理

```python
# 反模式：第一个慢任务阻塞后面已完成结果
for ref in refs:
    handle(ray.get(ref))

# 正确：完成一个处理一个
pending = refs
while pending:
    ready, pending = ray.wait(pending, num_returns=1)
    handle(ray.get(ready[0]))
```

若业务必须维持输出顺序，可在结果携带 index，按完成顺序计算，最终小范围重排；不要让执行和消费都受提交顺序限制。

### 10.4 一次 get 太多

`ray.get(百万个 refs)` 会把所有结果同时物化到 Driver，可能造成 heap OOM，即使集群总内存足够。用固定窗口 `ray.wait`，在远端分层聚合，或用 generator 流式消费。不要仅把一个巨大 `get` 拆成仍然巨大的几个列表而不做容量测量。

## 11. 粒度、定义与参数反模式

### 11.1 过细 Task

Ray 每个 Task 都有提交、调度、序列化和元数据成本。官方性能指南指出，小于约 10 ms 的 Task 通常很难获得收益，但具体阈值必须在目标集群测量。

```python
@ray.remote
def batch_square(values: list[int]) -> list[int]:
    return [x * x for x in values]


batches = [list(range(i, i + 1000)) for i in range(0, 100_000, 1000)]
results = ray.get([batch_square.remote(batch) for batch in batches])
```

Batch 太大又会降低负载均衡、失败重试粒度和尾延迟；以 Task 时间、序列化占比和长尾做折中。

### 11.2 循环中重定义 remote function/class

```python
# 反模式
for scale in range(10):
    @ray.remote
    def multiply(x):
        return x * scale
    multiply.remote(2)

# 正确
@ray.remote
def multiply(x, scale):
    return x * scale

refs = [multiply.remote(2, scale) for scale in range(10)]
```

每次定义都要导出函数/类并增加控制面开销；闭包里的 `scale` 还容易产生 late binding 错误。远程定义放模块级，变化作为参数传递。

### 11.3 同一大参数反复按值传

```python
import numpy as np

large = np.zeros(100_000_000, dtype=np.uint8)

# 反模式：每次 remote 都可能重复序列化/复制
bad_refs = [consume.remote(large) for _ in range(10)]

# 正确：放入 object store 一次
large_ref = ray.put(large)
good_refs = [consume.remote(large_ref) for _ in range(10)]
```

对同一次 `.remote()` 调用，顶层 ObjectRef 会自动解引用成值。`ray.put` 适用于复用已在 Driver 中的大对象，不要对每个小参数机械使用。

### 11.4 闭包捕获大对象

```python
# 反模式：函数定义隐式捕获大对象
large_model = load_model()

@ray.remote
def infer(x):
    return large_model(x)

# 更好：显式传 ObjectRef；若需要长期加载与可变缓存，用 Actor
model_ref = ray.put(large_model)

@ray.remote
def infer(model, x):
    return model(x)
```

显式参数使数据流、所有权和内存可观测。模型无法高效序列化或每次反序列化昂贵时，创建 Actor 在 `__init__` 加载一次，而不是闭包捕获。

## 12. 状态与 ObjectRef 反模式

### 12.1 用 globals 共享状态

```python
counter = 0


@ray.remote
def bad_increment():
    global counter
    counter += 1
    return counter
```

Task 可能运行在不同 Worker/节点，globals 是每进程副本，Worker 重启后还会丢失。正确选择：

- 单一、低吞吐可变状态：Actor。
- 高吞吐可分片状态：多个 Actor + 路由。
- 跨集群重启持久状态：数据库/对象存储等外部系统。
- 只读大对象：`ray.put` + ObjectRef。

### 12.2 Task 返回 `ray.put()`

```python
@ray.remote
def bad():
    value = expensive_compute()
    return ray.put(value)  # 反模式：返回嵌套 ObjectRef


@ray.remote
def good():
    return expensive_compute()
```

直接返回时，Task 的返回对象与 Task lineage/owner 关联，Ray 能更好地恢复。Task 内 `ray.put` 再返回 ref 会多一层 ObjectRef，增加调用和所有权复杂度；创建 `put` 对象的 Worker 失败时，容错更差。只有确有“返回引用本身而不是值”的高级协议才应采用，并需明确 owner 生命周期。

### 12.3 带外序列化 ObjectRef

不要用 `pickle`/数据库/消息队列把 ObjectRef bytes 送出 Ray 参数和返回值通道。Ray 使用分布式引用计数：

- 普通 `pickle` 可能让 Ray 不知道外部仍有引用，底层对象被意外回收，后续 `ray.get` 挂住。
- `ray.cloudpickle` 为安全可能把对象 pin 到 Worker 生命周期，造成 object store 泄漏和 spill。

调试检测：

```python
import ray

ray.init(runtime_env={
    "env_vars": {"RAY_allow_out_of_band_object_ref_serialization": "0"}
})
```

正确做法是通过 Task/Actor 参数、返回值或 Actor 状态传递 ObjectRef；跨系统传输应写入真正的外部对象存储，并传稳定 URI/业务 ID，而不是 Ray 内部引用。

## 13. Fork 反模式

Ray Worker 是多线程进程，已经持有网络连接、锁和 runtime 状态。在 Task/Actor 内 `os.fork()` 或默认 `fork` 的 `multiprocessing` 会复制“只有一个线程幸存”的不一致状态，可能死锁、连接损坏或崩溃。

```python
# 若确实需要 Python 子进程，显式使用安全启动方式。
import multiprocessing as mp

ctx = mp.get_context("spawn")  # Linux 也显式指定
process = ctx.Process(target=standalone_function, args=(value,))
process.start()
process.join()
```

更常见且更可调度的方案是直接把子工作变成 Ray Task。边界：

- `spawn` 要求 target 和参数可 pickle，入口使用 `if __name__ == "__main__":`。
- 子进程资源不被 Ray 自动精确调度；声明父 Task 足够的 CPU/GPU，并处理子进程退出、stdout 和超时。
- 不要在 Actor 初始化后再 fork 复制连接池、GPU context 或锁。

## 14. 组合案例：有界流水线

下面组合 generator、资源节流、`ray.wait` 与分阶段 ObjectRef 传递：

```python
import ray

ray.init(num_cpus=4)


@ray.remote
def source(count: int, batch_size: int):
    for start in range(0, count, batch_size):
        yield list(range(start, min(start + batch_size, count)))


@ray.remote(num_cpus=1)
def transform(batch: list[int]) -> list[int]:
    return [x * x for x in batch]


@ray.remote
def aggregate(batch: list[int]) -> int:
    return sum(batch)


MAX_IN_FLIGHT = 8
pending: list[ray.ObjectRef] = []
partial_sums: list[int] = []

stream = source.remote(10_000, 500)
for batch_ref in stream:
    transformed_ref = transform.remote(batch_ref)
    pending.append(aggregate.remote(transformed_ref))

    if len(pending) >= MAX_IN_FLIGHT:
        ready, pending = ray.wait(pending, num_returns=1)
        partial_sums.extend(ray.get(ready))

while pending:
    ready, pending = ray.wait(pending, num_returns=1)
    partial_sums.extend(ray.get(ready))

print(sum(partial_sums))
ray.shutdown()
```

数据不经过 Driver 解引用再提交；窗口限制控制面和 Driver ref 数；资源声明限制实际 transform 并发；每批失败可独立重试。生产版还应加入输入 checkpoint、幂等输出、超时、失败分类和指标。

## 15. 排错映射

| 症状 | 优先检查的模式/反模式 | 工具 |
|---|---|---|
| CPU 很闲但程序很慢 | get loop、submission order、无 pipeline | Timeline、cProfile |
| Task 数巨大，Dashboard 截断 | fine-grained、redefine | `ray summary tasks`、Timeline |
| Driver OOM | get too many、无界 refs、large arg | `ray memory`、Driver profile |
| Object store 不断 spill | out-of-band ref、closure、无界 pending | `ray summary objects`、`ray memory` |
| Actor 健康检查也卡住 | 同步长方法、Async Actor 中 `ray.get` | Stack Trace、Actor methods |
| Task 永远 pending | 资源声明、placement group、nested deadlock | `ray status`、State Tasks |
| Worker 随机死锁/崩溃 | fork、native library、OOM | worker/raylet logs、`ray stack` |
| 相同输入结果不一致 | globals、非幂等重试、Actor 状态未恢复 | Runtime Context、结构化日志 |

完整工具链见 [可观测性与调试](/kb/ai/Ray/Ray-Core/11-可观测性与调试/)。

## 16. 生产检查清单

- 先批量提交，再批量或按完成顺序消费；循环中不立即 `ray.get`。
- ObjectRef 直接连接阶段，不让大对象无谓往返 Driver。
- Task 以数十毫秒以上为起点做基准，按开销、长尾和重试粒度调 batch。
- in-flight 有界，running 由资源控制，两者分别设计。
- Async Actor 只并发可 `await` 的 I/O；CPU 工作交给 Task。
- Actor tree 有明确 owner、恢复配置、外部 checkpoint 和故障域。
- 大共享参数 `ray.put` 一次；不闭包捕获、不 globals 共享。
- Task 直接返回值，不返回 `ray.put` 的引用。
- ObjectRef 不带外序列化；跨系统使用 URI/业务 ID。
- Worker 内不 `fork`；必须起子进程时使用 `spawn`/`forkserver` 并声明资源。
- 所有队列、递归 fan-out、重试和日志都有上限。
