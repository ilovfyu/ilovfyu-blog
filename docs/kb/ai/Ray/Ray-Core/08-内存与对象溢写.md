::: info 文档基线
本文只讨论 Ray Core，依据 2026-08-01 的 Ray latest 官方文档。内存 monitor 目前面向 Linux，并在 cgroup v1/v2 容器中测试；macOS 可运行多数示例，但 object store 后端和 OOM 行为不同。
:::

Ray 的“内存”至少包含 worker heap、object store、共享映射和系统进程。排查 OOM 时若只看一个进程的 RSS，很容易重复计算共享内存，或把 heap 泄漏误判成 object store 满。

## 1. 内存版图

| 区域 | 存放内容 | 谁管理 | 主要风险 |
| --- | --- | --- | --- |
| Worker heap | Python 对象、框架状态、actor 字段 | Python/原生库 | 节点 OOM，worker 被杀 |
| Object store | `ray.put`、task/actor 的大返回值 | 每节点 Plasma/object store | 引用 pinning、spill I/O |
| Shared memory mapping | worker `ray.get` 后对本地对象的零拷贝视图 | OS + object store | RSS 看似重复、对象无法回收 |
| Ray system memory | raylet、GCS 等元数据 | Ray | head/raylet 受压导致集群不稳 |

Linux 默认 object store 使用 `/dev/shm`，启动时通常预留可用内存约 30%；逻辑 `memory` 默认约为可用内存 70%。macOS 的 object store 使用 `/tmp`（磁盘），性能不可类比 Linux 生产环境。容量可用 `ray.init(object_store_memory=...)` 或 `ray start --object-store-memory=...` 配置。

## 2. Worker heap 与 object store 的区别

```python
import numpy as np
import ray

ray.init(object_store_memory=200 * 1024 * 1024)

# Python/NumPy 本地变量主要属于 driver heap。
heap_array = np.zeros(32 * 1024 * 1024, dtype=np.uint8)

# ray.put 后，序列化结果进入 object store；ref 本身很小。
ref = ray.put(heap_array)

@ray.remote
def make_array():
    # 大返回值进入执行节点的 object store。
    return np.ones(32 * 1024 * 1024, dtype=np.uint8)

result_ref = make_array.remote()
print(ray.get(result_ref).nbytes)
ray.shutdown()
```

对 NumPy 等支持零拷贝反序列化的数据，`ray.get(ref)` 可能返回直接指向 object store shared memory 的只读视图。多个 worker 共享同一对象时无需各复制完整数据。这是性能优势，也是“删除 ObjectRef 后对象仍不释放”的常见原因。

在 `top`/`ps` 中估算 worker heap 时，使用 `RSS - SHR`，因为同一段 object store shared memory 会出现在多个 worker 的 RSS 中；直接相加会重复统计。对不支持零拷贝的 Python 对象，反序列化仍可能分配 heap。

## 3. Distributed reference counting 与 pinning

只要集群内仍有某个 `ObjectRef` 在作用域中，Ray 就 pin 住对象。pinning 不只来自当前 driver 的变量：

1. `LOCAL_REFERENCE`：driver、task 或 actor 中的本地 ObjectRef。
2. `PINNED_IN_MEMORY`：反序列化值仍直接引用 object store buffer，即使 ObjectRef 已删除。
3. `USED_BY_PENDING_TASK`：未完成 task 的顶层参数依赖。
4. 序列化 ObjectRef：ObjectRef 被嵌进 list/dict 并传给 worker，worker 可能持有本地引用。
5. `CAPTURED_IN_OBJECT`：一个 object store 对象内部包含另一个 ObjectRef。

```python
import gc
import numpy as np
import ray

ray.init()
ref = ray.put(np.zeros(64 * 1024 * 1024, dtype=np.uint8))
view = ray.get(ref)

del ref
gc.collect()
# view 仍直接指向共享内存，底层对象继续被 PINNED_IN_MEMORY。

del view
gc.collect()
# 没有其他分布式引用后才具备回收条件；回收是异步的。
ray.shutdown()
```

ActorHandle 也可能出现在 `ray memory` 汇总中；actor 内把 refs 永久存进字段，是典型分布式“内存泄漏”。应使用有界队列/LRU，并在消费后删除引用。

## 4. `ray memory` 定位谁在 pin

`ray memory` 需要安装 `ray[default]`，会列出 driver、actor、task 当前持有的 ObjectRef、大小、引用类型和创建调用点：

```bash
ray memory
ray memory --sort-by=OBJECT_SIZE --group-by=STACK_TRACE
ray memory --stats-only
ray memory --help
```

建议排查顺序：

1. 看 aggregate 的 Plasma 使用率、spill/restore 吞吐。
2. 按 `OBJECT_SIZE` 找最大对象。
3. 按 `STACK_TRACE` 聚合，找批量创建 refs 的代码路径。
4. 区分 `LOCAL_REFERENCE`、`PINNED_IN_MEMORY`、`USED_BY_PENDING_TASK` 与 `CAPTURED_IN_OBJECT`。
5. 检查 actor 字段、闭包、容器和未完成 future 是否长期持有 refs。

`del ref` 只删当前 Python 名称，不保证其他 handle、嵌套对象或 pending task 已释放引用；不要把强制内部 free API 当作常规生命周期管理。

## 5. Object spilling

object store 空间不足时，Ray 把可溢写对象落到本地文件系统，需要时再 restore。默认目录位于 Ray 临时 session 下；生产中应指向容量和吞吐可控的独立磁盘：

```python
import os
import tempfile
import ray

spill_dir = os.path.join(tempfile.gettempdir(), "ray-spill-demo")
os.makedirs(spill_dir, exist_ok=True)

ray.init(
    object_store_memory=100 * 1024 * 1024,
    object_spilling_directory=spill_dir,
)
print(ray.get_runtime_context().get_node_id())
ray.shutdown()
```

集群启动可用：

```bash
ray start --head --object-spilling-directory=/mnt/nvme/ray-spill
```

raylet 日志会报告 `Spilled ... write throughput` 与 `Restored ... read throughput`，`ray memory --stats-only` 给出集群汇总。

Spilling 的边界：

- spilling 只缓解 object store 容量，不会把 worker heap 自动换出。
- 被 worker 的零拷贝视图 `PINNED_IN_MEMORY` 的对象不能靠 spilling 腾出当前映射。
- 磁盘满、inode 耗尽、权限错误或慢盘会让任务阻塞/失败。
- restore 可能产生磁盘抖动和网络搬运；频繁 spill/restore 是工作集或并发设计不合理的信号。
- spilling 不是持久化或备份。节点/磁盘故障后的对象恢复依赖副本或 lineage，见 [容错](/kb/ai/Ray/Ray-Core/09-容错/)。

## 6. Memory-aware scheduling

Ray 无法预知 Python 代码会分配多少 heap。已知估算值时可声明 `memory`，让调度器进行准入控制：

```python
import ray

ray.init()

@ray.remote(memory=500 * 1024 * 1024, num_cpus=1)
def process_partition(partition):
    return len(partition)

ref = process_partition.options(
    memory=256 * 1024 * 1024
).remote([1, 2, 3])
print(ray.get(ref))
ray.shutdown()
```

`memory` 不是硬限制，也不代表实际预分配了这块 RAM；任务用超后仍可能触发节点 OOM。它针对 heap 调度，不是 `object_store_memory`。估算应覆盖峰值（输入反序列化、临时中间量、框架 workspace），再用压测校准。逻辑资源机制详见 [资源与调度](/kb/ai/Ray/Ray-Core/06-资源与调度/)。

## 7. OOM prevention：raylet memory monitor

每个节点的 raylet 定期检查 worker heap、object store 与 raylet 的组合内存。超过阈值时，它每次选择并杀死一个 task/actor worker，等待其退出后再选下一个，以尽量避免 OS 直接杀 raylet 或控制进程。

环境变量必须在 Ray 节点启动时生效：

```bash
RAY_memory_usage_threshold=0.90 \
RAY_memory_monitor_refresh_ms=250 \
ray start --head
```

- `RAY_memory_usage_threshold` 默认 `0.95`，范围 `[0, 1]`。
- `RAY_memory_monitor_refresh_ms` 默认 `250` ms，设 `0` 会禁用 worker killing；通常不应禁用。
- `RAY_event_stats_print_interval_ms=1000` 可在实验时更频繁打印 kill 摘要。

::: warning 平台边界
memory monitor 在 Linux 可用，并主要在 cgroup v1/v2 容器中验证。不要依据 macOS 本地实验推断 Linux 集群的 kill 选择与阈值行为。
:::

### 7.1 Kill 与 retry 策略

monitor 优先杀可重试工作。默认 task 有系统故障重试，而 actor 默认 `max_restarts=0`，所以通常优先杀 task。多个 caller 之间，它选择运行 task 最多的 caller；并列时偏向最晚开始的一组；同一 caller 内杀最晚开始的 task，以保证公平和至少一个 task 能推进。

因 memory monitor 被杀的 task 采用指数退避（最长 60 秒）且会无限重试，不遵守普通 `max_retries`；但若杀掉某 caller 在该节点最后一个可运行 task 仍无法保证进度，Ray 会以 `OutOfMemoryError` 失败，避免无限循环。actor 被杀后仍遵守 `max_restarts`，默认不会重建。

这与一般系统故障重试语义不同，容错参数详见 [容错](/kb/ai/Ray/Ray-Core/09-容错/)。

## 8. 控制并发比调阈值更重要

若每个 task 峰值 1 GiB，节点 8 GiB 却并发 16 个 task，根因是无界提交而不是阈值太保守。可通过资源请求限制并发：

```python
import ray

ray.init(num_cpus=4)

@ray.remote(num_cpus=1, memory=1024 * 1024 * 1024)
def heavy(i):
    data = bytearray(128 * 1024 * 1024)
    return i, len(data)

# ray.wait 维持最多 4 个未完成引用，避免 driver 和集群积压。
pending = []
results = []
for i in range(20):
    pending.append(heavy.remote(i))
    if len(pending) >= 4:
        done, pending = ray.wait(pending, num_returns=1)
        results.extend(ray.get(done))

results.extend(ray.get(pending))
print(len(results))
ray.shutdown()
```

流式/生成器结果、分区处理、actor 内有界队列都比“一次创建所有大对象再 get”更稳健。`ray.wait` 只限制 driver 保留的 in-flight refs；若 task 自己递归生成大量 child，还需在生成侧背压。

## 9. 典型故障的判别

| 症状 | 更可能的区域 | 证据 | 修复 |
| --- | --- | --- | --- |
| `ObjectStoreFullError`/频繁 spill | object store 或 refs pinning | `ray memory` Plasma、引用类型 | 释放 refs、增 store/磁盘、流式化 |
| 节点报 `OutOfMemoryError` | worker heap + store 总压力 | raylet.out 的 worker kill | 降并发/峰值、声明 memory、扩容 |
| RSS 总和远超物理内存 | shared memory 重复计数 | RSS 与 SHR 差异 | 用 `RSS-SHR` 看 heap |
| `del ref` 后空间不降 | view/嵌套/pending 引用 | `PINNED_IN_MEMORY` 等 | 删除 view/容器，等待依赖完成 |
| restore 延迟暴涨 | spill 盘慢或工作集过大 | spill/restore throughput | NVMe、减工作集、改善 locality |
| head 节点 dashboard 卡死 | head heap/system 受压 | head raylet/GCS 日志 | head 设 0 CPU、隔离应用工作 |
| 磁盘突然写满 | spilling | session spill 文件与日志 | 独立目录、容量告警、及时回收 |

日志通常位于 `/tmp/ray/session_latest/logs/`；重点看 `raylet.out`、对应 worker 日志与 Dashboard memory 页面。

## 10. 最佳实践

1. 分开预算 worker heap、object store、系统余量和 spill 磁盘，不用单一“总内存”数字。
2. Linux 上确保 `/dev/shm` 足够；容器默认很小，容量不足会严重影响 object store。
3. 大对象只 `ray.put` 一次并传 ObjectRef，避免重复按值序列化；但不要把 refs 永久积在 actor 字段。
4. 对 producer 施加背压，用 `ray.wait`、分区或生成器维持有界 in-flight 数据。
5. 把 spill 目录放在有监控的本地高速盘；磁盘满要提前告警。
6. 用 `memory` 请求限制并发，但不要误认为它是硬 quota。
7. 不要以关闭 memory monitor 或盲目提高阈值掩盖泄漏；先定位 heap、pinning 与峰值。
8. 会因 OOM 被重试的操作必须幂等，尤其是写外部系统的 task/actor method。
