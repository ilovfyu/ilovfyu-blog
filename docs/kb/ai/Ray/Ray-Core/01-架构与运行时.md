## 1. 从一个最小程序看全貌

安装与运行：

```bash
pip install -U "ray[default]"
python app.py
```

`app.py`：

```python
import os
import ray

ray.init()


@ray.remote
def square(x: int) -> dict:
    context = ray.get_runtime_context()
    return {
        "value": x * x,
        "pid": os.getpid(),
        "node_id": context.get_node_id(),
        "worker_id": context.get_worker_id(),
    }


refs = [square.remote(i) for i in range(4)]
print(ray.get(refs))
ray.shutdown()
```

关键事实：

- `python app.py` 的主进程是 **Driver**。
- `square.remote(i)` 提交异步 Task，立即返回 `ObjectRef`，不是立即返回字典。
- Ray 在一个或多个 **Worker** 进程中执行 `square`。
- 返回值进入 Ray 的对象传输与存储体系，Driver 用 `ray.get` 取回。
- 单机 `ray.init()` 会启动本地 Ray 运行时并连接；多节点一般先用 CLI 或集群管理工具启动集群，再让 Driver 连接。

## 2. 进程与组件

### 2.1 Driver：应用的控制起点

Driver 是执行顶层用户代码、调用 `ray.init()` 并提交工作的进程。它通常负责：

- 定义或导入 remote function / actor class；
- 构造 Task DAG，持有根 `ObjectRef` 和 Actor handle；
- 通过 `ray.get`、`ray.wait`、`await ref` 消费结果；
- 处理应用级重试、超时、取消和最终输出。

Driver 本身也是一个 Ray job 中的重要参与者。由 Driver 调用 `f.remote()` 创建的返回 `ObjectRef`，其 **owner 通常是 Driver**，即使真正的值由远端 Worker 计算并存储在另一节点。Driver 退出不仅意味着“不再提交任务”：若它拥有的对象仍被其他进程引用，owner 消失仍可能导致 `OwnerDiedError`。

::: warning Driver 不是可靠的永久元数据服务
不要把短命 Driver 创建的 `ObjectRef` 当成可跨集群、跨 job、永久保存的地址。需要持久化时应把值写入外部存储，而不是持久化 ObjectRef。
:::

### 2.2 Worker：执行用户代码的进程

Worker 执行普通 Task 或承载 Actor。普通 Task 的 Worker 可连续执行多个调用，进程堆上的普通 Python 全局状态不应被当成可靠状态：下一次调用可能在另一个 Worker，Worker 也可能退出或故障重启。

```python
import os
import ray

ray.init()


@ray.remote
def where_am_i():
    return os.getpid(), ray.get_runtime_context().get_node_id()


print(ray.get([where_am_i.remote() for _ in range(8)]))
```

不要根据 PID 是否相同推断 API 语义。若需要有状态、固定进程语义，使用 Actor，见 [Actor 深入](/kb/ai/Ray/Ray-Core/05-Actor-深入/)。

### 2.3 raylet：每节点的控制面代理

每个 Ray 节点有一个 raylet。按当前架构，它承担节点级控制职责，例如：

- 节点资源信息与本地调度；
- Worker 进程管理；
- 与其他节点协调 Task 放置；
- 协调本节点对象管理与数据传输；
- 向集群控制面报告节点状态。

可把 raylet 理解为“节点管家”，但不要依赖内部 RPC、线程、端口或具体调度算法。用户应通过资源声明和公开调度 API 表达意图，而不是假设“某 Task 必定先经过头节点集中调度”。

### 2.4 GCS：集群级控制元数据

**GCS（Global Control Service）**运行在 head node，维护和协调集群级控制信息，例如节点成员、Actor 等元数据，并支撑控制面服务。它不是放置所有用户返回值的中央数据库，也不是用户数据的传输中转站。

需要区分：

- **控制元数据**：节点、Actor、作业等集群状态，涉及 GCS；
- **对象元数据**：对象位置等关键信息由对象 owner 管理；
- **对象数据**：通常位于各节点 object store，按需在节点间传输。

因此，“GCS 活着”不等于任意 ObjectRef 在 owner 死亡后仍可恢复。

### 2.5 Object store：每节点的共享对象存储

每个节点有一个共享内存 object store。大对象、Task 返回值和 `ray.put` 对象可存放于其中，同节点 Worker 能高效共享；远端节点需要数据时按需拉取，不会因 `ray.put` 自动广播全集群。

对象存储与 Worker heap 是两类内存：

- **Worker heap**：普通 Python 对象、临时变量、反序列化后不走零拷贝的数据；
- **Object store memory**：Ray remote object；同节点多个 Worker 可共享，其中 NumPy 等可零拷贝读取。

对象不可变。若需要修改 NumPy 数组，应在 Worker 中 `arr.copy()` 后改本地副本。对象存储满时可 spill 到磁盘，入门见 [Object 与序列化](/kb/ai/Ray/Ray-Core/04-Object-与序列化/)；spilling 不是无限内存，磁盘容量与 I/O 仍是瓶颈。

## 3. 一次 Task 的生命周期

以下是概念流程，而非稳定的内部调用序列：

1. Driver 导入/定义 `@ray.remote` 函数。
2. `f.remote(args)` 序列化 Task 描述和必要参数，立即创建返回 `ObjectRef`。
3. 调度器根据逻辑资源、调度策略、节点可用性和可能的数据局部性选择可行节点。
4. 若顶层参数含 `ObjectRef`，Task 等其值可用；必要时跨节点取数。
5. raylet 将工作交给合适 Worker，Worker 反序列化并执行用户函数。
6. 返回值被序列化；较大数据通常进入对象存储，返回对象位置由 owner 体系跟踪。
7. `ray.get(ref)` 等待可用、必要时拉到本节点，然后反序列化或建立共享内存视图。
8. 集群中不再有有效引用后，distributed reference counting 允许回收对象数据。

Task 的“提交完成”“执行完成”“对象本地可读”是三个不同时间点。`ray.wait(..., fetch_local=False)` 可在对象存在于集群某处时返回；默认 `fetch_local=True` 会等待数据取到本地节点。

## 4. Owner、ObjectRef 与生命周期

### 4.1 Owner 是谁

owner 是**最初创建 ObjectRef 的 Worker 进程**：

- Driver 调用 `ray.put(x)`：Driver 同时创建 ref 和值，Driver 是 owner；
- Driver 调用 `f.remote()`：Driver 创建返回 ref，因此 Driver 是 owner，但远端 Worker 计算值；
- 一个 Task 内调用 `child.remote()`：父 Task 所在 Worker 创建 child 的返回 ref，因此该 Worker 是 owner。

owner 保存对象关键元数据并参与 distributed reference counting。对象可以在其他节点有数据副本，但副本的位置不决定 ownership。

### 4.2 引用如何延长对象生命

以下均可能让对象保持存活：

- Driver/Worker 中的本地 `ObjectRef`；
- 尚未执行完的 Task 参数；
- 被序列化进另一个 Ray object 的嵌套 ref；
- remote function 闭包捕获的 ref；
- `ray.get` 得到的、直接指向共享内存的 NumPy 视图。

```python
import gc
import numpy as np
import ray

ray.init()

ref = ray.put(np.zeros(1_000_000))
view = ray.get(ref)  # 同节点通常是只读共享内存视图
del ref
gc.collect()
# view 仍可能 pin 住 object store 数据
print(view.flags.writeable)  # 通常为 False
del view
gc.collect()
```

Python `del` 只删除当前名字；其他引用存在时不会释放对象。回收也可能受 Python GC 和 distributed reference counting 消息传播影响，不保证瞬时发生。

### 4.3 数据丢失与 owner 丢失

- **数据副本丢失**：Ray 可先寻找其他副本；若对象来自可重试、可重放 Task，可尝试 lineage reconstruction。
- **`ray.put` 数据丢失**：没有可重放的创建 Task，通常不可用 lineage 重建。
- **owner 死亡**：当前官方语义是不支持从 owner failure 恢复，使用者可能收到 `OwnerDiedError`。
- **重建前提**：创建链仍可用，owner 存活，且未超过 Task 重试限制。

这也是 Task 应尽量幂等、确定性的原因。重建本质上可能再次执行函数；外部写入、扣费、发消息等副作用必须自行做幂等控制。

## 5. 资源与调度

Ray 的 CPU/GPU/custom resource 是**逻辑资源**，主要用于准入和放置，不等于操作系统硬隔离。

```python
import ray

ray.init(num_cpus=4, resources={"fast_disk": 1})


@ray.remote(num_cpus=2, resources={"fast_disk": 0.25})
def work(x):
    return x * 2


# 每次调用可覆盖声明，不修改原 remote function。
ref = work.options(num_cpus=1, name="double-21").remote(21)
print(ray.get(ref))
```

常见参数：

| 参数 | 作用 | 易错点 |
|---|---|---|
| `num_cpus` | 调度时预留逻辑 CPU | 不限制线程数，也不限制实际 CPU 占用 |
| `num_gpus` | 预留 GPU 资源 | GPU Task 的 Worker 生命周期和环境有额外成本 |
| `resources` | 数值型自定义资源 | 不应拿它表示普通标签语义 |
| `memory` | 调度准入所需 heap 内存估计 | 不是内存上限 |
| `scheduling_strategy` | `DEFAULT`、`SPREAD`、placement group 等 | 显式策略可能压过数据局部性 |
| `runtime_env` | Task/Actor 及子任务的环境 | 安装和打包有冷启动成本 |

默认策略会在满足硬资源约束的节点间平衡负载并考虑局部性。具体评分、top-k 和阈值是实现细节，应用不应据此依赖精确节点顺序。

## 6. 单机与多节点启动

### 6.1 单机开发

```python
import ray

context = ray.init(num_cpus=4)
print(context.address_info)
# ...
ray.shutdown()
```

`local_mode=True` 适合有限调试，但不能代表真实多进程序列化、并发、资源竞争和故障语义，不应作为性能测试。

### 6.2 已有集群

```python
import ray

ray.init(address="auto")
print(ray.cluster_resources())
```

多节点环境必须保证 Worker 能获得代码、Python 包、文件和环境变量。可预装依赖或使用 `runtime_env`。不要假定 Driver 本地绝对路径在远端节点存在。

## 7. 运行时错误如何定位

### 7.1 用户异常

Worker 中的 Python 异常会通过 Task 返回结果传播，`ray.get` 时通常表现为 `RayTaskError`，并可能同时是用户异常类型。

```python
import ray

ray.init()


@ray.remote
def divide(a, b):
    return a / b


try:
    ray.get(divide.remote(1, 0))
except ZeroDivisionError as exc:
    print("remote error:", exc)
```

### 7.2 无法调度

Task 长期 pending 常见原因是资源不可行，而不一定是死锁：例如请求 `num_gpus=1`，集群没有 GPU。先比较：

```python
print(ray.cluster_resources())
print(ray.available_resources())
```

前者是总逻辑资源，后者是当前近似可用资源，均可能动态变化。

### 7.3 内存与对象引用

安装 `ray[default]` 后可使用：

```bash
ray memory --stats-only
ray memory --sort-by=OBJECT_SIZE --group-by=STACK_TRACE
ray summary tasks
ray list tasks
```

日志通常位于 Ray session 目录（默认根目录常为 `/tmp/ray`；macOS 的对象存储也可能受磁盘路径影响）。日志文件名和内部布局可能变化，优先用 Dashboard、State API/CLI 和公开命令。

## 8. 性能心智模型

一次很小的 Task 仍有提交、调度、进程间通信、序列化和结果跟踪开销。优化顺序通常是：

1. 增大单个 Task 的计算粒度，避免把微秒级 Python 运算拆成海量 Task。
2. 批量提交后再 `ray.get(refs)`，不要提交一个就同步 `get` 一个。
3. 用 `ray.wait` 控制 pending 数量和流水消费，避免 Driver 无界提交。
4. 大型只读参数只 `ray.put` 一次，并复用 ref。
5. 尽量把计算调度到数据附近，但不要用脆弱的节点 ID 硬编码替代高层策略。
6. 区分 Worker heap OOM 与 object store 压力；两者诊断与解决方式不同。
7. 将网络、磁盘 spill、序列化时间纳入端到端基准，而非只测函数体。

反模式：

```python
# 串行化了整个循环。
results = [ray.get(work.remote(i)) for i in range(100)]

# 正确的基本并行模式。
refs = [work.remote(i) for i in range(100)]
results = ray.get(refs)
```

## 9. 最佳实践清单

- 把 `ObjectRef` 当作同一 Ray 集群内的 future，不当作持久化对象地址。
- 普通 Task 写成幂等、可重试函数；副作用使用业务幂等键或事务。
- 明确声明资源，不用 `os.cpu_count()` 推测 Ray 分配给 Task 的逻辑 CPU。
- 大参数复用 `ray.put`，但不要对小对象滥用 `put`。
- Driver 保持存活直到其拥有的结果不再被消费；跨作业共享使用外部存储或合适的 Actor 设计。
- 用公开 API 观察系统，不依赖 raylet/GCS 私有实现、私有 API或内部文件格式。
- 把本地测试、多进程测试和真正多节点测试分开；网络和对象传输只在后者充分暴露。
- 关闭时用 `ray.shutdown()` 断开当前 Driver；集群服务的启停由部署方式管理。
