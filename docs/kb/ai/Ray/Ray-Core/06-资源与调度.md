::: info 文档基线
本文只讨论 Ray Core，依据 2026-08-01 的 Ray latest 官方文档。示例以 Python API 为主。labels 的成熟度在官方概览中为 Beta，而 `ray.remote` API 参考仍标注 `label_selector` 为 Experimental；生产使用应固定版本并回归测试。
:::

Ray 调度分两步理解：资源决定节点是否**可行**，调度策略在可行节点中决定放到哪里。资源不足是硬约束：有对应总容量但暂时被占用叫 unavailable，会排队；集群中没有任何节点满足完整请求叫 infeasible，通常要改变请求或扩容。

## 1. 逻辑资源不是物理隔离

Ray 资源是名称到浮点数量的逻辑账本，主要用于准入控制和并发限制：

- `CPU` 不会绑核，也不会阻止任务创建更多线程。
- `GPU` 会通过 `CUDA_VISIBLE_DEVICES` 等环境变量提供可见设备隔离，但应用仍可绕过环境变量。
- `memory` 是 worker heap 的调度请求，不是上限。
- custom resource 是数值约束，不代表 Ray 管理了对应硬件。
- `object_store_memory` 不是可供 task/actor 申请的调度资源。

节点启动后不能动态修改其资源容量；需重启节点。`ray.cluster_resources()` 看集群总量，`ray.available_resources()` 只是某一时刻的近似可用量，不应当作强一致的业务锁。

```python
import ray

ray.init(
    num_cpus=4,
    num_gpus=0,
    resources={"ssd_slots": 2},
)
print(ray.cluster_resources())
print(ray.available_resources())
ray.shutdown()
```

在集群 CLI 中可用 `ray start --head --num-cpus=4 --resources='{"ssd_slots": 2}'`。保留 head 节点给系统进程时，可把 head 的逻辑 CPU 配成 0。

## 2. CPU、GPU、custom 与 memory API

```python
import ray

ray.init(num_cpus=4, resources={"ssd_slots": 2})

@ray.remote(
    num_cpus=1.5,
    num_gpus=0,
    memory=256 * 1024 * 1024,
    resources={"ssd_slots": 0.5},
)
def transform(x):
    return x * 2

# .options() 只覆盖这次提交的资源配置。
ref = transform.options(num_cpus=0.5, memory=128 * 1024 * 1024).remote(21)
print(ray.get(ref))
ray.shutdown()
```

默认 task 运行时占 1 CPU。默认 actor 在调度创建时要求 1 CPU，运行时占 0 CPU；只要显式指定 actor 资源，资源会在调度和整个 actor 生命周期中占用。建议始终显式写 actor 的 `num_cpus`。

`memory=N` 以字节表示 Ray 估计的可用 heap 准入需求，不限制 RSS，也不涵盖 object store 配额。真实进程超过 N 不会被立即截断；OOM 机制见 [内存与对象溢写](/kb/ai/Ray/Ray-Core/08-内存与对象溢写/)。

## 3. Fractional resource

Ray 支持最小精度 0.0001 的小数资源。典型用途是低 CPU 的 I/O actor，或多个模型副本共享一张 GPU：

```python
import os
import ray

ray.init(num_cpus=2, num_gpus=1)

@ray.remote(num_cpus=0.25, num_gpus=0.5)
class InferenceReplica:
    def assigned(self):
        return {
            "ids": ray.get_runtime_context().get_accelerator_ids(),
            "visible": os.environ.get("CUDA_VISIBLE_DEVICES"),
        }

actors = [InferenceReplica.remote() for _ in range(2)]
print(ray.get([a.assigned.remote() for a in actors]))
ray.shutdown()
```

边界：

- fractional GPU 只共享可见设备，不限制显存或算力；需在框架中自行限额。
- Ray 会尽量先填满同一加速器，减少碎片。
- 大于 1 的 GPU、TPU、`neuron_cores` 请求必须是整数，例如 1.5 GPU 非法。
- 并非所有加速器支持小数；NVIDIA GPU 完整支持，AMD/Intel/METAX GPU、Ascend NPU 属社区实验支持；Neuron、TPU、HPU、RBLN、Furiosa 不支持 fractional。
- `num_cpus=0` 可能制造无界并发，只适合确实无需 CPU 且另有背压的工作。

## 4. Custom resource 与 labels 如何选

custom resource 适合**数值容量**，如节点有 4 个许可证 slot：`resources={"license": 1}`。labels 适合**属性筛选**，如区域、实例类型、磁盘类型。不要再用 `{"node:ip": 0.001}` 一类伪资源表达标签。

### 4.1 Labels（Beta / Experimental API）

Ray 2.49+ 可用 labels；Ray 保留 `ray.io/*` 命名空间。默认标签包括唯一的 `ray.io/node-id`，有加速器的节点还有 `ray.io/accelerator-type`。

```python
import ray

ray.init(labels={"environment": "dev", "cpu-family": "arm64"})

@ray.remote(label_selector={
    "environment": "dev",
    "cpu-family": "in(arm64,x86_64)",
})
def inspect_node():
    ctx = ray.get_runtime_context()
    return ctx.get_node_id(), ctx.get_node_labels()

print(ray.get(inspect_node.remote()))
ray.shutdown()
```

selector 支持：精确值 `"v"`、不等于 `"!v"`、集合 `"in(a,b)"`、排除集合 `"!in(a,b)"`；多个 key 是 AND。集群节点可用 `ray start --labels="region=cn-east-1,disk=nvme"` 配置。Autoscaler V2 从 Ray 2.50+ 可根据 worker group 的 labels 扩容。

::: warning 边界
label 不匹配是硬约束，任务可能永久 pending。官方推荐 labels 逐步替代 `NodeAffinitySchedulingStrategy(soft=False)` 和 `accelerator_type`，但迁移前须确认集群版本、Autoscaler V2 与节点标签配置。
:::

## 5. DEFAULT 与 SPREAD

### DEFAULT

默认策略兼顾 locality 和负载。节点按逻辑资源利用率打分，并在 top-k 候选中随机选择，避免大集群冷启动抖动。低于 `RAY_scheduler_spread_threshold`（默认 0.5）的利用率得分相同；top-k 默认约占节点数 20%。这些环境变量属于运行时调优面，除非压测证明确有必要，不建议依赖其内部细节。

```python
@ray.remote(scheduling_strategy="DEFAULT")
def normal_task():
    return ray.get_runtime_context().get_node_id()

@ray.remote(scheduling_strategy="SPREAD")
def spread_task():
    return ray.get_runtime_context().get_node_id()
```

没有任何资源请求的 zero-CPU actor 在 DEFAULT 下会随机选节点，效果近似 spread，并不考虑利用率。

### SPREAD

`SPREAD` 尽力把 task/actor 分散到当前可用节点，但不是“每个实例必须不同节点”的硬保证。需要 bundle 级严格分散时使用 [Placement Group](/kb/ai/Ray/Ray-Core/07-Placement-Group/) 的 `STRICT_SPREAD`。

## 6. Locality-aware scheduling

DEFAULT 对**task**会优先选择拥有大参数本地副本的节点，以减少网络传输；若多个大对象作为参数，则偏向本地对象字节最多的节点。该 locality 优先于 DEFAULT 的资源利用率评分，但本地节点忙时仍可调到别处。

```python
import numpy as np
import ray

ray.init()

@ray.remote
def make_data():
    return np.zeros(16 * 1024 * 1024, dtype="uint8")

@ray.remote
def consume(data):
    return len(data), ray.get_runtime_context().get_node_id()

data = make_data.remote()
print(ray.get(consume.remote(data)))
ray.shutdown()
```

边界：locality-aware 仅适用于 task，不适用于 actor；小对象可能内联传输，不触发该偏好；一旦显式指定 SPREAD、node affinity 或 PG 等其他策略，数据 locality 不再参与决策。把大对象先 `ray.get()` 到 driver 再按值传递，会破坏此模式并增加复制。

## 7. Node affinity 与“本地执行”

`NodeAffinitySchedulingStrategy` 按 node ID 定点调度，是低层策略：

```python
import ray
from ray.util.scheduling_strategies import NodeAffinitySchedulingStrategy

ray.init()
local_node = ray.get_runtime_context().get_node_id()

@ray.remote
def where():
    return ray.get_runtime_context().get_node_id()

ref = where.options(
    scheduling_strategy=NodeAffinitySchedulingStrategy(
        node_id=local_node,
        soft=False,
    )
).remote()
assert ray.get(ref) == local_node
ray.shutdown()
```

`soft=False`：目标节点不存在或资源不可行时，task/actor 以 `TaskUnschedulableError`/`ActorUnschedulableError` 失败；节点活着且可行但资源正忙时仍会等待。`soft=True`：仅当目标节点不存在或不可行时才回退到其他可行节点；目标节点只是暂时忙时不会回退。

固定 node ID 不利于 autoscaling、故障恢复和多租户优化。优先使用 labels；共同放置一组组件时使用 PG。所谓“local”不是单独的字符串策略，而是对当前 `get_node_id()` 使用 node affinity。

## 8. Accelerator 调度

NVIDIA GPU 与 Google TPU 由 Ray 团队完整测试；AMD/Intel/METAX GPU、Neuron、HPU、NPU、RBLN、Furiosa 等在 latest 文档中标为社区支持的 Experimental。常用写法：

```python
import os
import ray

@ray.remote(num_gpus=1)
def gpu_task():
    return (
        ray.get_runtime_context().get_accelerator_ids(),
        os.environ.get("CUDA_VISIBLE_DEVICES"),
    )
```

旧式类型约束可写：

```python
from ray.util.accelerators import NVIDIA_TESLA_V100

@ray.remote(num_gpus=1, accelerator_type=NVIDIA_TESLA_V100)
def train():
    return "ok"
```

`accelerator_type` 内部通过极小 custom resource 实现。latest 调度概览建议逐步改用 `label_selector={"ray.io/accelerator-type": "V100"}`。资源是逻辑值，虚报 `num_gpus` 不会创造物理 GPU。GPU task 默认不复用 worker，以释放框架残留显存；显式 `max_calls=0` 可恢复复用，但要确认库确实释放显存。

## 9. 可行性与排错

先区分三类状态：

| 状态 | 含义 | 行动 |
| --- | --- | --- |
| feasible + available | 有节点且资源空闲 | 应很快调度，检查依赖/runtime env |
| feasible + unavailable | 有节点能满足但资源在用 | 等待、降低并发或扩容 |
| infeasible | 没有单节点满足完整硬约束 | 改请求、labels 或节点类型 |

```bash
ray status
ray list tasks --detail
ray list actors --detail
ray list nodes --detail
```

常见陷阱：请求 9 CPU 不能跨两个 8 CPU 节点拼出来；资源名大小写错误；节点启动后才想添加 custom resource；label 值未配置；actor 忘记显式 CPU；fractional GPU 共享导致显存 OOM；在 PG 外的任务无法使用已预留资源。

## 10. 最佳实践

1. 把资源请求当作容量模型，而非安全沙箱；应用仍要限制线程、显存和 heap。
2. task/actor 都显式写 CPU，actor 尤其不要依赖历史默认值。
3. custom resource 只表达数值容量，属性与拓扑使用 labels。
4. 优先 DEFAULT 与数据 locality；只有明确的故障域或均衡目标才用 SPREAD。
5. node affinity 是最后手段，硬亲和优先迁移到 labels。
6. 对不可行请求设置应用级超时，并通过 State API 暴露告警。
7. 需要一组资源同时可用时，不要逐个启动 actor，使用 [Placement Group](/kb/ai/Ray/Ray-Core/07-Placement-Group/)。
