::: abstract 系列定位
本系列不是“万能提示词大全”，而是一套从需求定义、提示设计、场景落地到评测、发布与安全治理的工程教程。内容综合主流模型厂商文档、开放课程、系统综述、经典论文、OWASP 与 NIST 风险框架，以及代表性提示词工程书籍。
:::

::: info 资料基线
本系列于 **2026-08-03** 整理。模型能力、角色层级、API、采样参数、structured output 和工具调用接口会变化。通用原则仍需在目标模型、固定版本、真实数据和完整运行配置上验证；模型特定语法以当前官方文档为准。
:::

## 1. 核心结论

提示词工程可以概括为：

```text
需求契约
  + 受控上下文
  + 输入与示例
  + 输出协议
  + 失败策略
  + 评测闭环
  + 应用层安全控制
= 可维护的 LLM 行为接口
```

必须先建立六个认识：

1. 提示词影响概率模型的输出分布，不像普通程序那样保证唯一执行路径。
2. 清晰指令、优质上下文和代表性示例解决不同问题，不能互相替代。
3. JSON、工具参数和业务动作必须由 schema 与确定性代码验证，不能只靠文字要求。
4. 单次成功不是可靠性证据；优化必须建立测试集、指标、错误分类和版本记录。
5. RAG、工具调用、工作流、换模型和微调有各自适用边界，不应把所有问题都归因于提示词。
6. Prompt injection 没有万无一失的纯提示防御；权限、隔离、审批、验证和审计必须在应用层落实。

## 3. 基础教程

### [提示词工程基础与核心心智模型](/kb/ai/提示词工程/提示词教程/01-提示词工程基础与核心心智模型/)

从概率生成、行为契约和系统边界理解提示词工程。重点区分模型能力、提示质量、上下文质量和集成问题，并建立最小评测意识。

### [提示词结构角色指令上下文与约束](/kb/ai/提示词工程/提示词教程/02-提示词结构角色指令上下文与约束/)

拆解角色、任务、背景、输入、约束、输出契约和失败策略。说明 API 消息角色与逻辑提示组件并非同一概念，角色优先级依平台实现。

### [Zero-shot Few-shot与示例设计](/kb/ai/提示词工程/提示词教程/03-Zero-shot-Few-shot与示例设计/)

学习何时使用 zero-shot、one-shot 和 few-shot，如何覆盖正常、边界、歧义与拒答样本，以及如何避免示例标签泄漏、顺序偏差和上下文浪费。

### [输出格式结构化输出与约束生成](/kb/ai/提示词工程/提示词教程/04-输出格式结构化输出与约束生成/)

从自然语言格式进入 JSON Schema、字段语义、枚举、空值、解析、重试和业务验证。生产系统优先使用平台原生 structured output，再做代码验证。

### [复杂任务分解推理与提示链](/kb/ai/提示词工程/提示词教程/05-复杂任务分解推理与提示链/)

讲解任务分解、阶段化工作流、提示链、校验节点与停止条件。区分可验证的中间产物和模型私有推理，不把索取完整思维链作为生产依赖。

### [多轮对话上下文管理与澄清策略](/kb/ai/提示词工程/提示词教程/06-多轮对话上下文管理与澄清策略/)

把多轮对话理解为显式状态管理，处理滑动窗口、摘要、记忆、上下文污染、关键澄清问题、工具失败和会话停止条件。

## 4. 提示词优化

### [从模糊需求到可测试提示词](/kb/ai/提示词工程/提示词优化/01-从模糊需求到可测试提示词/)

把“回答得更好”转化为任务范围、输入分布、成功标准、禁止行为、延迟成本和失败状态，建立 baseline 与设计文档。

### [提示词诊断错误分类与最小修改](/kb/ai/提示词工程/提示词优化/02-提示词诊断错误分类与最小修改/)

通过错误 taxonomy 区分指令遗漏、知识不足、上下文冲突、格式失败、工具失败和模型能力边界。坚持一次只改变一个主要变量。

### [评测集指标Rubric与LLM-as-Judge](/kb/ai/提示词工程/提示词优化/03-评测集指标Rubric与LLM-as-Judge/)

设计分层评测集、原子 Rubric 和任务指标，处理随机输出、多次采样与人工复核。LLM-as-Judge 需要校准、盲测和偏差控制，不能被视为真值。

### [A-B测试回归测试与版本管理](/kb/ai/提示词工程/提示词优化/04-A-B测试回归测试与版本管理/)

将离线回归、配对比较、小流量实验、显著性与业务决策连接起来，并固定 model、prompt、参数、schema、工具和检索配置。

### [Token成本延迟稳定性与模型选择](/kb/ai/提示词工程/提示词优化/05-Token成本延迟稳定性与模型选择/)

不只优化“答案质量”，还要管理输入/输出 token、p50/p95 延迟、并发、超时、重试、缓存、路由和模型升级风险。

### [自动提示词优化与高级方法](/kb/ai/提示词工程/提示词优化/06-自动提示词优化与高级方法/)

介绍 prompt search、mutation、APE、OPRO、DSPy 类优化思想，强调隔离数据集、多目标约束、预算、过拟合防范和独立验证。

## 5. 常见场景

### [摘要改写翻译与内容创作](/kb/ai/提示词工程/常见场景/01-摘要改写翻译与内容创作/)

覆盖信息保真、长度与风格控制、术语表、受众、创作自由度和事实边界，避免摘要遗漏、翻译增译和内容创作中的虚构事实。

### [信息抽取分类打标与结构化转换](/kb/ai/提示词工程/常见场景/02-信息抽取分类打标与结构化转换/)

设计标签定义、schema、`null`/`unknown`、证据 span、多标签规则和歧义处理，建立 precision、recall、F1 和 schema valid rate。

### [问答研究事实核查与引用设计](/kb/ai/提示词工程/常见场景/03-问答研究事实核查与引用设计/)

把开放问答升级为查询规划、来源筛选、证据提取、逐条引用、冲突处理和无法证实时保留未知的研究流程。

### [编程代码生成调试测试与Code Review](/kb/ai/提示词工程/常见场景/04-编程代码生成调试测试与Code-Review/)

明确仓库上下文、运行环境、允许修改范围、最小 diff、测试命令、安全要求和评审格式。模型生成代码不能绕过执行隔离与人工 review。

### [数据分析SQL报表与决策支持](/kb/ai/提示词工程/常见场景/05-数据分析SQL报表与决策支持/)

围绕 schema、SQL dialect、指标口径、只读权限、扫描上限和结果验证设计提示词，区分数据事实、分析推断和业务建议。

### [教学辅导学习计划与知识测验](/kb/ai/提示词工程/常见场景/06-教学辅导学习计划与知识测验/)

根据学习者水平设计渐进解释、苏格拉底式提问、提示阶梯、测验与反馈；避免直接代做、虚假掌握判断和不合适的认知负荷。

### [图像多模态与视觉任务提示词](/kb/ai/提示词工程/常见场景/07-图像多模态与视觉任务提示词/)

处理图像定位、OCR、不确定区域、跨模态证据和多图关系；图像生成则从主体、构图、环境、风格、光线和约束建立可测试描述。

## 10. 从需求到上线的标准流程

```text
1. 定义目标、用户、非目标与风险
2. 收集真实输入和失败样本
3. 建立最简单 baseline
4. 定义输出 schema 和失败状态
5. 建立分层评测集与指标
6. 运行 baseline 并做错误分类
7. 一次修改一个主要变量
8. 离线回归与人工复核
9. 安全测试与威胁建模
10. 固定完整 release manifest
11. 小流量灰度与在线监控
12. 达不到门禁立即回滚
```

## 11. 优化决策树

| 失败表现 | 首先检查 | 可能方案 |
|---|---|---|
| 不理解任务 | 指令、标签和示例 | 澄清契约、补边界示例 |
| 缺少私域或最新事实 | 上下文和证据 | RAG、搜索、数据库工具 |
| JSON 不合法 | 输出机制 | 原生 structured output、schema 校验 |
| 计算错误 | 工具能力 | 计算器、代码执行、确定性程序 |
| 复杂流程丢步骤 | 工作流设计 | 提示链、状态机、校验节点 |
| 风格不一致 | 示例与 Rubric | few-shot、风格指南、后处理 |
| 长上下文遗漏 | 内容选择和位置 | 检索、压缩、重排、任务分段 |
| 成本或延迟过高 | token 与调用图 | 压缩、缓存、路由、小模型 |
| 全面能力不足 | 模型能力 | 换模型或调整系统架构 |
| 稳定行为需规模化 | 数据与维护成本 | 评估微调，不先假定微调必要 |
| 出现越权风险 | 权限与执行器 | 最小权限、审批、隔离、验证 |

## 12. 生产质量门禁

至少回答以下问题后才能上线：

- 任务成功如何量化？
- 测试集是否覆盖正常、边界、歧义、对抗和关键子群？
- 模型、prompt、参数、schema、工具与 retriever 是否全部版本化？
- 输出是否经过结构和业务语义验证？
- 信息不足、工具超时和上游失败时会发生什么？
- 敏感数据是否在发送、日志、缓存和评测集中最小化？
- RAG 文档和工具结果是否被当作不可信输入？
- 高风险动作是否需要绑定参数的人工批准？
- 是否定义质量、成本、延迟和安全 SLO？
- 是否有灰度、fallback、kill switch 和已演练 rollback？

## 14. 使用建议

1. 先选一个真实任务，不要从收藏大量“万能 prompt”开始。
2. 用需求评审模板定义成功、失败和风险。
3. 建立最简单 baseline，再添加结构、示例或工作流。
4. 每次改动都在固定测试集上比较，不凭主观印象决定。
5. 把失败样本沉淀为回归测试，而不是只修改措辞。
6. 模型升级时重新运行完整评测与安全门禁。
7. 所有会触发外部副作用的动作都让确定性代码掌握最终授权。
