## 1. 文档用途

本清单用于评审带有 LLM、RAG、structured output 或工具调用的生产系统。
它不是“prompt 写得好不好”的审美检查，而是对需求、数据、权限、威胁、评测、SLO、fallback、rollback 和运营能力的工程审查。

## 2. 评审结论

可选结论：

- `APPROVED`：所有硬门禁通过，可按计划发布；
- `APPROVED_WITH_ACTIONS`：非阻断项有负责人和期限；
- `REVISE`：设计缺口需修订后复审；
- `REJECTED`：风险或价值不支持上线；
- `EXPERIMENT_ONLY`：仅限隔离实验，不得接生产数据或工具。

任何跨租户泄露、未批准高风险副作用或不可回滚的关键缺口都不应以“带风险上线”处理。

## 3. 一页摘要

评审材料第一页回答：

- 用户是谁？
- 要解决什么任务？
- 为什么需要 LLM？
- 不使用 LLM 的基线是什么？
- 系统会读取什么数据？
- 系统能执行什么动作？
- 最坏错误是什么？
- 如何测量价值与风险？
- 失败时用户看到什么？
- 如何在分钟级停止和回滚？

## 4. 范围与非目标

- [ ] 明确用户角色、地区、语言和无障碍需求。
- [ ] 明确支持和不支持的意图。
- [ ] 明确是否生成事实、建议、决策或执行动作。
- [ ] 明确是否处理高风险领域。
- [ ] 明确 beta 与正式承诺的差异。
- [ ] 明确不应自动化的任务。
- [ ] 明确责任最终由谁承担。
- [ ] 明确数据保留和删除范围。

## 5. 成功标准

成功标准必须可评测：

```yaml
business:
  ticket_resolution_rate: ">= 35%"
quality:
  grounded_claim_rate: ">= 97%"
  unanswerable_abstain_recall: ">= 95%"
safety:
  cross_tenant_leakage: "0"
  unapproved_high_risk_action: "0"
reliability:
  availability: ">= 99.9%"
  p95_latency_ms: "<= 2500"
cost:
  cost_per_success_usd: "<= 0.08"
```

同时定义失败标准和停止发布阈值。

## 6. 架构评审

- [ ] 提供端到端数据流图。
- [ ] 标出身份、授权、模型、检索、工具和第三方边界。
- [ ] 标出同步与异步链路。
- [ ] 标出数据持久化位置。
- [ ] 标出秘密注入位置。
- [ ] 标出所有外部网络出口。
- [ ] 标出所有有副作用的 sink。
- [ ] 标出人工审批点。
- [ ] 标出 fallback 与熔断点。
- [ ] 标出配置和索引回滚点。

## 7. Threat Model

### 7.1 主体

- 普通用户；
- 恶意用户；
- 租户管理员；
- 内部运营人员；
- 第三方内容提供者；
- 被攻陷的数据源；
- 被攻陷的工具或供应商；
- 误配置的服务身份。

### 7.2 资产

- 用户和企业数据；
- 跨租户隔离；
- 凭据和 token；
- 工具权限；
- 系统配置；
- 业务数据完整性；
- 合规证据；
- 服务可用性和成本预算。

### 7.3 入口

- 用户消息；
- 上传文件；
- RAG 文档；
- 网页、邮件和工单；
- 工具返回；
- 模型输出；
- 管理控制台；
- 配置仓库；
- webhook 和回调。

### 7.4 威胁

- direct/indirect/stored prompt injection；
- jailbreak；
- 跨租户读取；
- 敏感数据外泄；
- 未授权工具调用；
- SSRF、任意代码或 SQL；
- 重复副作用；
- 供应链和模型漂移；
- 日志与缓存泄露；
- 成本耗尽和拒绝服务；
- 评测集投毒。

### 7.5 控制验证

对每个威胁记录：

| 字段 | 内容 |
|---|---|
| Threat ID | 稳定编号 |
| 场景 | 攻击步骤 |
| 资产 | 受影响对象 |
| 可能性 | 有依据的等级 |
| 影响 | 用户、财务、合规 |
| 预防控制 | 隔离、权限、验证 |
| 检测控制 | 日志、告警 |
| 响应 | 熔断、轮换、回滚 |
| 测试 | 对应红队用例 |
| 残余风险 | 接受人和期限 |

安全基线参考 [Prompt Injection越权与数据泄露防护](/kb/ai/提示词工程/工程化与安全/03-Prompt-Injection越权与数据泄露防护/)。

## 8. 数据治理

- [ ] 数据源有 owner 和使用依据。
- [ ] 数据分类已完成。
- [ ] 只发送任务所需字段。
- [ ] PII、秘密和受监管字段有处理策略。
- [ ] 跨境和第三方处理已审查。
- [ ] 保留期限和删除流程已实现。
- [ ] 用户删除会传播到索引、缓存、日志和评测集。
- [ ] 训练/改进用途与服务用途区分。
- [ ] 评测样本有授权和脱敏。
- [ ] 日志访问被审计。

## 9. 身份与授权

- [ ] 用户身份来自可信认证层。
- [ ] 租户 ID 不来自模型或用户自由字段。
- [ ] 数据访问前执行 ACL。
- [ ] 工具端再次验证资源权限。
- [ ] 服务凭据短期且限 scope。
- [ ] 权限撤销及时生效。
- [ ] 缓存键包含权限范围。
- [ ] 管理操作使用 MFA 和审计。
- [ ] 没有共享的全能生产凭据。
- [ ] 权限失败 fail closed。

## 10. RAG 评审

- [ ] retrieved content 明确作为不可信数据，而不是指令。
- [ ] 数据源摄入有审核、版本和回滚。
- [ ] 检索前过滤租户与权限。
- [ ] chunk 保留来源、标题、生效时间和稳定 ID。
- [ ] 查询改写不会扩大权限。
- [ ] 引用只能使用本次证据 ID。
- [ ] 结论与引用执行蕴含检查。
- [ ] 证据不足时 abstain。
- [ ] 证据冲突有显式状态。
- [ ] 失效文档能及时下线。
- [ ] 索引同步和新鲜度有 SLO。
- [ ] 恶意文档进入红队集。

详见 [RAG提示词与基于证据的回答](/kb/ai/提示词工程/工程化与安全/01-RAG提示词与基于证据的回答/)。

## 11. Agent 与工具评审

- [ ] 每个工具有严格 schema。
- [ ] 未知字段被拒绝。
- [ ] 工具描述与真实副作用一致。
- [ ] 前置条件由代码执行。
- [ ] 后置条件由代码验证。
- [ ] 写操作有 idempotency key。
- [ ] 超时写操作先查状态再重试。
- [ ] 模型不持有凭据。
- [ ] 每次运行有步数、时间、token、成本和工具预算。
- [ ] 有机器可判定停止条件。
- [ ] 状态机由编排器控制。
- [ ] 有循环检测与取消传播。
- [ ] 高风险动作由人类知情批准。
- [ ] 批准绑定准确参数、资源和有效期。
- [ ] 工具结果按不可信数据处理。

详见 [工具调用Agent提示词与状态机](/kb/ai/提示词工程/工程化与安全/02-工具调用Agent提示词与状态机/)。

## 12. Prompt 与输出契约

- [ ] 任务、边界、输入和输出契约明确。
- [ ] 控制指令与不可信数据分离。
- [ ] 不依赖模型暴露私有推理。
- [ ] 输出使用 structured output/schema。
- [ ] schema 之外字段被拒绝。
- [ ] 缺失、冲突、拒绝和失败状态明确。
- [ ] 不把模型文本直接拼接进危险 sink。
- [ ] 用户可见理由简短、真实、可核验。
- [ ] 系统不承诺不可实现的确定性。

## 13. 配置版本化

一个 release 必须固定：

- [ ] model；
- [ ] prompt；
- [ ] params；
- [ ] schema；
- [ ] tools；
- [ ] retriever；
- [ ] policy；
- [ ] eval dataset 和 gates。

详见 [提示词模板版本配置与可观测性](/kb/ai/提示词工程/工程化与安全/04-提示词模板版本配置与可观测性/)。

## 14. Eval 设计

评测集应覆盖：

- 正常高频任务；
- 低频关键任务；
- 边界输入；
- 信息不足；
- 证据冲突；
- 多语言；
- 长上下文；
- 权限不足；
- 直接和间接 prompt injection；
- 工具失败、超时和部分成功；
- 高风险动作审批；
- fallback 场景。

评测方法组合：

- 确定性断言；
- 业务规则；
- 人工专家评审；
- 模型评审器；
- 线上指标和用户反馈。

模型评审器必须用人工集校准，不能成为唯一安全裁判。

## 15. Eval Gates

```yaml
hard_gates:
  cross_tenant_leakage_rate: 0
  unapproved_high_risk_action_rate: 0
  known_secret_exfiltration_rate: 0
  schema_validity: ">= 0.995"
  grounded_claim_rate: ">= 0.97"
  unanswerable_abstain_recall: ">= 0.95"

regression_gates:
  task_success_delta: ">= -0.01"
  p95_latency_delta: "<= 15%"
  cost_per_success_delta: "<= 10%"
```

门禁规则：

- 硬门禁不得用平均收益抵消；
- 同时要求绝对阈值和相对回归阈值；
- 按风险、语言、意图和用户群分桶；
- 样本量不足时不宣称改善；
- 失败样本进入根因分类。

## 16. SLO

至少定义：

- 可用性；
- 端到端延迟；
- 检索新鲜度；
- schema 有效率；
- grounded answer 比例；
- 高风险安全不变量；
- 每成功任务成本；
- 人工升级响应时间。

示例：

```text
30 天窗口内 99.9% 可用；
p95 端到端延迟不超过 2.5 秒；
政策源更新后 30 分钟内完成索引；
跨租户数据使用和未批准高风险动作必须为 0。
```

## 17. 容量与成本

- [ ] 估算平均和峰值 QPS。
- [ ] 估算输入、输出和检索 token。
- [ ] 估算重排、工具和存储成本。
- [ ] 按成功任务计算成本。
- [ ] 设置用户、租户和全局速率限制。
- [ ] 设置 Agent 硬预算。
- [ ] 防止无限重试和循环。
- [ ] 压测 provider 限流与排队。
- [ ] 定义成本异常熔断。
- [ ] 评估 fallback 的容量。

## 18. Fallback 设计

Fallback 不是“换另一个模型继续猜”。

可选策略：

- 返回确定性搜索结果；
- 退回只读模式；
- 禁用高风险工具，只生成草稿；
- 返回缓存的公开信息；
- 转人工队列；
- 请求用户稍后重试；
- 对信息不足明确 abstain；
- 使用经独立评测的备用模型和匹配 schema。

每种 fallback 定义：

- 触发条件；
- 能力差异；
- 用户提示；
- 数据和权限范围；
- SLO；
- 恢复条件；
- 如何避免 fallback 级联。

## 19. Rollback 设计

回滚应覆盖完整构件：

- 应用代码；
- model 路由；
- prompt 和 params；
- schema；
- tools 与权限；
- retriever 与索引快照；
- policy；
- 缓存和状态兼容策略。

验证：

- [ ] 上一版本构件仍可部署。
- [ ] 数据库变更向后兼容或有恢复步骤。
- [ ] Agent 运行中的状态可安全停止或迁移。
- [ ] 已执行副作用不会被“回滚配置”自动撤销。
- [ ] 索引快照可恢复。
- [ ] 缓存可按 release 清除。
- [ ] 回滚权限和负责人明确。
- [ ] 定期演练并记录恢复时间。

## 20. 故障模式

### 模型不可用

采用超时、熔断、受控重试和 fallback。

### 模型输出漂移

固定版本、金丝雀评测、schema 验证、停止灰度。

### 检索为空

abstain 或确定性搜索，不用常识补齐组织事实。

### 索引过期

标记新鲜度，切回有效快照，阻止高风险回答。

### 工具超时

查询事务状态，避免重复副作用。

### 评审器不可用

安全关键操作 fail closed；低风险请求按策略降级。

### 日志系统不可用

决定哪些操作必须停止，避免无审计地继续高风险动作。

## 21. 可观测性

- [ ] 每请求有 trace ID 和 release ID。
- [ ] 记录 model/prompt/params/schema/tools/retriever 版本。
- [ ] 分阶段记录延迟、错误和成本。
- [ ] 记录检索片段 ID，而非默认记录全文。
- [ ] 记录授权、审批和策略决策。
- [ ] 记录停止与 fallback 原因。
- [ ] 指标支持按版本、意图和风险分桶。
- [ ] 高基数字段不污染指标系统。
- [ ] 敏感日志有脱敏、RBAC 和保留期。
- [ ] 告警链接到运行手册。

## 22. 安全测试

- [ ] 直接 prompt injection。
- [ ] RAG 间接 injection。
- [ ] PDF/OCR/图片注入。
- [ ] 工具结果注入。
- [ ] 多语言与编码混淆。
- [ ] 系统提示词探测。
- [ ] 跨租户资源枚举。
- [ ] SSRF 与重定向。
- [ ] 路径穿越。
- [ ] SQL/shell 参数注入。
- [ ] 未批准副作用。
- [ ] 审批后参数替换。
- [ ] 重复提交和重放。
- [ ] 日志、缓存和错误信息泄露。
- [ ] 成本耗尽与长循环。

## 23. 用户体验

- [ ] 明确用户正在与 AI 系统交互。
- [ ] 不夸大能力、准确性或实时性。
- [ ] 引用可打开且与结论对应。
- [ ] 拒答说明缺失信息和下一步。
- [ ] 高风险操作前展示准确摘要。
- [ ] 用户可取消、修改和撤回。
- [ ] 用户能报告错误和安全问题。
- [ ] 人工接管路径真实可用。
- [ ] fallback 不伪装成正常高能力状态。
- [ ] 无障碍和多语言行为经过测试。

## 24. 合规与供应商

- [ ] 法务、隐私和安全评审按风险完成。
- [ ] 供应商数据使用、保留和训练条款明确。
- [ ] 数据区域和子处理方明确。
- [ ] 模型/API 变更通知机制明确。
- [ ] 配额、限流和支持等级满足 SLO。
- [ ] 内容安全配置已评估。
- [ ] 退出供应商和数据删除方案存在。
- [ ] 许可证和来源引用符合要求。
- [ ] 高风险决策符合适用的人类监督要求。

## 25. 发布前演练

1. 模型 provider 故障。
2. 检索索引损坏。
3. prompt injection 触发工具外发。
4. 未授权跨租户请求。
5. 写工具超时但实际已成功。
6. 审批 token 被重放。
7. 日志平台不可用。
8. 成本突然增长十倍。
9. 新发布 schema 与客户端不兼容。
10. 完整 rollback。

每次演练记录发现时间、决策时间、恢复时间、数据影响和后续项。

## 26. 灰度计划

```yaml
canary:
  phase_1:
    traffic: 1%
    duration: 2h
    audience: internal
  phase_2:
    traffic: 5%
    duration: 24h
  phase_3:
    traffic: 25%
    duration: 48h
  phase_4:
    traffic: 100%
stop_conditions:
  - "cross_tenant_leakage > 0"
  - "unapproved_high_risk_action > 0"
  - "p95_latency > slo for 15m"
  - "schema_failure > 1% for 10m"
```

灰度用户选择应避免把高风险弱势群体作为默认实验对象。

## 27. 上线日检查

- [ ] 发布构件哈希与批准版本一致。
- [ ] 生产权限和工具集合符合设计。
- [ ] secrets 来自正确环境。
- [ ] 索引版本和新鲜度正常。
- [ ] dashboard、告警和 on-call 就绪。
- [ ] fallback 容量可用。
- [ ] 回滚命令和权限已验证。
- [ ] 支持与运营收到变更说明。
- [ ] 安全团队知道高风险告警路径。
- [ ] 发布窗口内无冲突依赖变更。
- [ ] 金丝雀样本通过。
- [ ] 灰度开关可即时关闭。

## 28. 上线后 24 小时

- [ ] 对比基线质量、延迟和成本。
- [ ] 审查拒答和人工升级样本。
- [ ] 审查安全阻断与误报。
- [ ] 检查按租户、语言和意图分桶指标。
- [ ] 检查工具重复和超时未知状态。
- [ ] 检查用户反馈与支持工单。
- [ ] 确认无日志或缓存泄露。
- [ ] 记录是否继续扩大流量。

## 29. 上线后 7 天

- [ ] 人工审计随机样本。
- [ ] 复核 SLO 和错误预算。

## 31. 阻断项清单

以下任一项通常应阻断上线：

- 未完成身份或租户隔离；
- 模型能直接使用长期高权限凭据；
- 高风险工具无人工审批；
- 未定义 abstain；
- retrieved content 被当作可执行指令；
- 无 injection 红队；
- 无 eval gates 或只凭演示判断；
- 无 SLO 与告警；
- 无可用 fallback；
- 无完整 rollback；
- 日志默认收集秘密或敏感原文；
- 安全事件无法快速禁用工具和出口。

## 32. 最终原则

1. 先证明任务值得自动化，再讨论模型能力。
2. 先限制最坏后果，再优化平均表现。
3. Prompt injection 没有万无一失的纯提示词解法。
4. 权限、隔离、验证和审批必须由系统执行。
5. RAG 回答必须引用证据，并能在不足时 abstain。
6. Agent 必须受 schema、状态机、预算和停止条件约束。
7. 配置必须整体版本化、可观测和可回滚。
8. Eval gates、SLO、fallback、rollback 都是上线前置条件。
9. 安全门禁不能被平均业务收益抵消。
10. 发布不是终点，持续监控、红队和事件学习决定长期可靠性。

评审通过的证据、附条件项和最终 Release ID 应归档，并绑定下一次复审日期。
归档记录还应包含实际回滚目标与当值负责人。
