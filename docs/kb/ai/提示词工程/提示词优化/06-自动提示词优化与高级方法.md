## 学习目标

- 理解 prompt search、mutation 与反思式优化。
- 理解 DSPy、OPRO、APE 类方法的共同抽象。
- 在不绑定易变 API 的前提下搭建优化器。
- 定义搜索空间、目标函数和预算。
- 防止评测集泄漏与搜索过拟合。
- 保留候选差异和可解释性。
- 使用独立验证、隐藏测试和人工复核。
- 判断何时应改 RAG、工具、微调或模型。

## 一、自动优化不是闭环替代品

可靠闭环仍然是：

1. 定义任务与约束。
2. 建立 baseline。
3. 建立分层测试集。
4. 错误分类。
5. 一次一个变量。
6. 离线评测。
7. 人工复核。
8. 小流量上线。
9. 监控回滚。

自动优化只加速候选生成和筛选。
它不能代替：

- 业务目标定义。
- 标签仲裁。
- 风险判断。
- Judge 校准。
- 上线批准。
- 生产监控。
## 二、自动优化的统一抽象

一个优化器包含：

```text
初始程序 P0
+ 搜索空间 S
+ 开发数据 Ddev
+ 评测函数 E
+ 候选生成器 G
+ 选择策略 A
+ 预算 B
-> 候选 P*
```

其中“程序”可能包括：
- Prompt 指令。
- Few-shot 示例集合。
- 示例顺序。
- 模块化调用链。
- 检索查询模板。
- 工具选择规则。

不要默认优化对象只有一段自然语言。

## 三、何时值得自动优化

适合：

- 已有稳定任务契约。
- 有足够开发样本。
- 评测器与人工较一致。
- 单次评测成本可控。
- 搜索空间能被明确限制。
- baseline 已接近可用，需要系统探索。

不适合：

- 业务仍无法定义成功。
- 数据标签错误很多。
- 正确证据没有进入上下文。
- 工具接口本身不可靠。
- 高风险任务无人审查。
- 预算不足以验证候选。

## 四、Prompt Search

### 枚举搜索
预先定义候选组件：

- 三种任务描述。
- 两种标签布局。
- 四组 few-shot。
- 两种输出约束。

组合后离线评测。

优点：

- 可解释。
- 可复现。
- 易做消融。

缺点：

- 组合爆炸。
- 依赖人工设计空间。

### 随机搜索
在有限组件空间随机采样。

实践中常比穷举更省预算。

必须固定随机种子并保存候选。

### 贝叶斯或代理模型搜索

根据历史候选预测下一个有希望区域。

适用于评测昂贵时。

但代理目标若有偏差，会系统性放大偏差。

## 五、Mutation

Mutation 是对现有 Prompt 做局部变换。

### 常见变异算子

- 重写任务描述。
- 明确一个标签边界。
- 删除重复规则。
- 增加一个反例。
- 调整示例顺序。
- 将复合规则拆开。
- 增加拒答路径。
- 压缩输出说明。

### 受控 Mutation

每个候选应记录：

- 父版本。
- 变异算子。
- 精确 diff。
- 修改理由。
- 目标错误类别。
- 预期改善切片。
- token 变化。

### 不受控 Mutation 的问题

让模型“彻底改写并优化”会同时改变大量变量。

即使分数提升，也难解释和维护。

## 六、反思式优化

典型过程：

1. 运行当前 Prompt。
2. 收集失败样本。
3. 让分析器按 taxonomy 总结模式。
4. 生成最小修改候选。
5. 在开发集评测。
6. 保留符合门槛的候选。

分析器输出只是根因假设。

必须通过独立样本验证。

### 分析提示模板

```text
根据任务契约、失败输入、期望输出和实际输出：
1. 选择一个主错误类别；
2. 引用支持诊断的最短证据；
3. 提出一个可证伪根因；
4. 只提出一个最小 Prompt 修改；
5. 列出可能回归的切片。

不要改动标签真值，不要查看测试集。
```

## 七、DSPy 类思路

DSPy 类方法把 LM 程序视为可优化模块，而不是只手写一整段 Prompt。

共同思想包括：

- 声明输入输出签名。
- 组合模块。
- 用示例和指标编译或优化。
- 自动选择指令或 demonstrations。

工程上可借鉴：

- 将任务接口结构化。
- 把检索、生成和验证分模块评测。
- 用训练/开发数据优化。
- 用独立测试集确认。

具体库 API 会变化。

设计文档应描述抽象、数据和指标，而不是依赖某个易变函数名。

## 八、OPRO 类思路

OPRO 类方法把优化过程本身表达给模型：

- 提供历史候选。
- 提供对应分数。
- 要求生成更优候选。

优势：

- 可利用自然语言反馈。
- 能探索人工未想到的措辞。

风险：

- 追逐噪声分数。
- 过拟合开发集。
- 候选越来越长。
- 历史上下文泄露答案。
- 难以归因。

控制方法：

- 只提供聚合错误模式，不提供测试答案。
- 限制每次 diff。
- 设置 token 上限。
- 在独立验证集选择。
- 定期从简单 baseline 重新比较。

## 九、APE 类思路

APE 类方法通常让模型根据任务示例提出指令候选，再由执行和评测筛选。

通用流程：

1. 从开发样本生成若干指令。
2. 低成本子集预筛。
3. 在完整开发集复评。
4. 对入围候选重复采样。
5. 在验证集选择。
6. 在隐藏测试集确认。

核心风险是示例泄漏。

生成候选的数据与最终测试数据必须隔离。

## 十、搜索空间设计

### 太窄

无法跳出 baseline 局部最优。

### 太宽

- 预算爆炸。
- 多重比较加剧。
- 难以解释。
- 更容易偶然命中开发集。

### 推荐分层空间

#### 第一层：删除和澄清

- 去重。
- 消除冲突。
- 明确定义。

#### 第二层：边界示例

- 添加一个正例。
- 添加一个反例。
- 调整示例选择。

#### 第三层：结构

- 模块拆分。
- 先检索后回答。
- 增加验证器。

每层独立评测，通过后再扩大空间。

## 十一、多目标优化

不能只最大化 Judge 分数。

目标包括：

- Accuracy / F1。
- 关键类 precision/recall。
- JSON valid rate。
- Groundedness。
- Task success。
- Token cost。
- Latency。
- Stability。
- 安全硬门槛。

### 约束优化

推荐：

```text
maximize task_success
subject to:
  critical_recall >= 0.95
  groundedness >= 0.97
  json_valid_rate >= 0.999
  cost_per_success <= budget
  p95_latency <= SLA
  S1_regressions = 0
```

这比把所有指标随意加权更清楚。

### Pareto 前沿

保留非支配候选，再由业务约束选择。

不要过早把质量和成本压成一个分数。

## 十二、预算管理

### 总调用估算

```text
calls = candidates × samples × repetitions × judges
```

若：

- 100 个候选。
- 500 个样本。
- 每样本 3 次。
- 2 个 judge。

仅评测就需要 300,000 次 judge 相关判断量级。

### 多阶段筛选

1. 静态检查。
2. 20 条烟雾集。
3. 100 条开发子集。
4. 完整开发集。
5. 独立验证集。
6. 隐藏测试集。
7. 人工复核。

越昂贵的评测越靠后。

### 早停

候选出现以下情况可早停：

- S1/S2 失败。
- JSON 大量无效。
- 成本超过硬预算。
- 关键 recall 明显低于 baseline。
- Prompt 超过长度上限。

## 十三、数据泄漏

### 直接泄漏

- 测试输入和答案提供给候选生成器。
- 测试失败被逐条写进 Prompt。
- 隐藏集分数反复反馈给优化器。

### 间接泄漏

- 测试样本改写版进入开发集。
- 同一文档片段跨集合。
- Judge 提示中包含答案模式。
- 搜索日志保存隐藏集细节。

### 防护

- 组级切分和近重复检查。
- 权限隔离。
- 隐藏集单独服务。
- 只返回发布通过/失败，不返回逐条答案。
- 记录每次访问。
- 定期轮换隐藏集。

## 十四、过拟合与多重比较

尝试足够多候选，总会有一个因随机波动得高分。

### 症状

- Dev 大幅提升，validation 无提升。
- 只有少数样本贡献增益。
- Prompt 越来越针对具体措辞。
- 新数据表现下降。
- 换 judge 后排名翻转。

### 控制

- 独立 validation。
- 限制搜索轮数。
- 报告尝试候选总数。
- 使用置信区间。
- 对冠军候选重新独立运行。
- 保留隐藏审计集。
- 优先更短、更可解释的候选。

## 十五、可解释性

自动优化产物必须能回答：

- 修改了什么？
- 为什么修改？
- 针对哪个错误类别？
- 改善了哪些样本？
- 回归了哪些样本？
- 成本和 token 如何变化？
- 人能否维护？

### 候选卡

```markdown
# Candidate C-017

- parent：P-1.4.0
- operator：add_boundary_rule
- diff：新增 refund/status 冲突规则
- target_error：B2 优先级错误
- dev_delta：Macro F1 +2.1pp
- validation_delta：+1.4pp
- regressions：3 个，最高 S3
- token_delta：+27
- cost_delta：+0.8%
- stability_delta：all_pass@5 +1.0pp
- interpretation：规则明确，保留
```

## 十六、最小自动优化器伪代码

```text
parent = baseline
archive = [baseline]

for round in budget:
    errors = classify_failures(parent, dev_set)
    mutation = propose_one_change(parent, errors)
    candidate = apply(mutation)

    if not static_checks(candidate):
        continue

    smoke = evaluate(candidate, smoke_set)
    if violates_hard_gate(smoke):
        continue

    dev = evaluate(candidate, dev_set, repetitions=k)
    if dominates_or_improves(dev, parent):
        archive.append(candidate)
        parent = choose_interpretable_candidate(archive)

finalists = evaluate(archive, validation_set)
winner = choose_under_constraints(finalists)
confirm_once(winner, hidden_test_set)
human_review(winner)
```

## 十七、Python 标准库搜索骨架

```python
import hashlib
import itertools
import json
from dataclasses import dataclass


@dataclass(frozen=True)
class Candidate:
    instruction: str
    examples: tuple[str, ...]

    @property
    def candidate_id(self):
        body = json.dumps(
            {"instruction": self.instruction, "examples": self.examples},
            ensure_ascii=False,
            sort_keys=True,
        )
        return hashlib.sha256(body.encode("utf-8")).hexdigest()[:12]


def candidates(instructions, example_sets):
    for instruction, examples in itertools.product(instructions, example_sets):
        yield Candidate(instruction, tuple(examples))


def select(results, min_groundedness, max_cost):
    feasible = [
        row for row in results
        if row["groundedness"] >= min_groundedness
        and row["cost"] <= max_cost
        and row["s1_regressions"] == 0
    ]
    return max(feasible, key=lambda row: row["task_success"], default=None)
```

该骨架故意不绑定供应商 API。

执行器、judge 和数据访问应通过项目适配层注入。

## 十八、候选缓存与可恢复执行

自动搜索可能持续数小时或数天。

需要：

- 按候选 hash 缓存。
- 按样本和版本缓存原始输出。
- 幂等写入。
- 中断恢复。
- 预算计数。
- 异常隔离。
- 敏感日志清理。

缓存键必须包括：

- Model。
- Prompt。
- Config。
- Tools。
- Retrieval。
- Dataset case。
- Repetition。

## 十九、Judge 在自动优化中的风险

自动优化会主动寻找 judge 的漏洞。

这类似指标被“攻破”。

### 可能现象

- 候选输出 judge 喜欢的套话。
- 输出更长以获得“完整”高分。
- 在答案中对 judge 发指令。
- 复制 Rubric 关键词。
- 牺牲真实任务换取代理分数。

### 防护

- 原子 Rubric。
- Judge 输入隔离与注入防护。
- 规则指标交叉验证。
- 多 judge 和人工抽查。
- 隐藏 judge 配置。
- 检查输出长度相关性。
- 对最终候选做盲审。

Judge 不能视为真值。

## 二十、自动 Few-shot 选择

### 固定示例集

全请求使用相同示例。

优点：稳定、易缓存。

缺点：无法适配多样输入。

### 动态示例检索

按输入选择相似示例。

风险：

- 检索延迟。
- 标签泄漏。
- 选择偏差。
- 对抗输入影响示例。
- 示例与规则冲突。

应独立版本化示例库、检索器和 top-k。

## 二十一、模块化 LM 程序

复杂任务可拆为：

```text
输入检查
-> 检索
-> 证据选择
-> 草稿生成
-> 规则验证
-> 工具确认
-> 最终输出
```

优点：

- 每个模块可单测。
- 错误责任清楚。
- 可为模块选择不同模型。
- 硬规则可由代码执行。

缺点：

- 调用次数增加。
- 延迟和成本增加。
- 模块间错误传播。

不要为追求“Agent 化”无端拆分简单任务。

## 二十二、RAG 联合优化

生成质量依赖：

- 查询改写。
- 召回。
- 重排。
- Chunk。
- 上下文组装。
- 生成 Prompt。

联合优化前先建立分层指标：

- Recall@k。
- NDCG 或排序指标。
- Context precision。
- Citation precision/recall。
- Groundedness。
- Task success。

若 Recall@k 很低，生成 Prompt 优化不是首要动作。

## 二十三、工具联合优化

工具型系统应分别测：

- 是否该调用。
- 工具选择。
- 参数正确性。
- 调用顺序。
- 错误处理。
- 副作用确认。
- 最终 task success。

工具 schema 文本也是 Prompt 的一部分。

更改 schema 描述必须版本化和回归。

确定性参数约束应放在代码中验证。

## 二十四、微调的决策边界

微调不是“更强的 Prompt 优化”。

适合：

- 有大量高质量示例。
- 输出模式稳定。
- 行为需规模化复用。
- 长示例导致成本显著。

不适合单独解决：

- 实时知识。
- 工具权限。
- 业务规则尚未确定。
- 标签本身质量低。

微调后仍需 Prompt、评测集、版本管理和回滚。

## 二十五、换模型的决策边界

换模型适合：

- 当前能力有明确上限。
- 新模态或语言不支持。
- 上下文、工具或部署不满足。
- 质量成本 Pareto 明显更优。

公平比较分两阶段：

1. 同 Prompt 初筛。
2. 相同优化预算分别适配。

不能给偏爱模型更多搜索预算，再声称客观胜出。

## 二十七、自动优化运行清单

### 启动前

- [ ] 任务契约冻结。
- [ ] Baseline 达到最低可用性。
- [ ] 错误 taxonomy 可操作。
- [ ] 数据按组切分。
- [ ] 测试和隐藏集隔离。
- [ ] Judge 已用专家集校准。
- [ ] 预算和停止条件明确。

### 搜索中

- [ ] 每个候选有父版本和 diff。
- [ ] 一次 mutation 尽量只有一个变化。
- [ ] 保存 model/prompt/config/tools/retrieval。
- [ ] 统计候选总数和调用成本。
- [ ] 硬门槛失败立即停止候选。
- [ ] 不向生成器反馈隐藏集答案。
- [ ] 定期检查 Prompt 长度膨胀。

### 选择时

- [ ] 使用独立 validation。
- [ ] 对随机输出重复采样。
- [ ] 报告置信区间。
- [ ] 检查关键切片。
- [ ] 检查所有回归。
- [ ] 比较成本与延迟。
- [ ] 优先可解释的非支配候选。

### 发布前

- [ ] 隐藏集只确认一次。
- [ ] 人工盲审完成。
- [ ] Judge 不作为唯一依据。
- [ ] 小流量计划已批准。
- [ ] 监控和回滚已演练。

## 二十八、常见误区

### 误区 1：让优化器访问测试集

最终分数将失去泛化意义。

### 误区 2：只优化单一 Judge 分

优化器会寻找代理指标漏洞。

### 误区 3：无限生成候选

多重比较和预算都会失控。

### 误区 4：冠军候选不复跑

它可能只是采样噪声赢家。

### 误区 5：自动改任务契约

优化器可能通过降低任务难度得高分。

### 误区 6：忽略 Prompt 可维护性

难以解释的长 Prompt 会增加后续风险。

### 误区 7：同一个模型生成、执行、裁判

同源偏差被循环放大。

### 误区 8：把 DSPy/OPRO/APE 当固定 API

它们更重要的是方法抽象，库接口会变化。

### 误区 9：自动优化能补救坏数据

它更可能拟合错误标签。

### 误区 10：离线冠军直接全量上线

仍需人工、小流量、监控和回滚。

## 二十九、练习

### 练习 1：是否自动优化

团队尚未决定“简洁摘要”的长度和必含字段，是否启动 prompt search？

<details>
<summary>参考答案</summary>

不应。

先定义任务契约和 Rubric，否则优化器只会追逐模糊或任意的代理分数。

</details>

### 练习 2：泄漏判断

优化器看到测试集每条失败及答案，再改规则。这是什么问题？

<details>
<summary>参考答案</summary>

这是直接测试集泄漏。

应只在开发集分析；测试集用于低频确认，隐藏集进一步隔离。

</details>

### 练习 3：多目标

候选 task success 提升 2 点，但成本翻倍、p95 超 SLA，应选吗？

<details>
<summary>参考答案</summary>

若成本和 SLA 是预设硬约束，则不可选。

可继续压缩、路由或寻找 Pareto 更优候选。

</details>

## 三十、本章小结

自动优化的正确定位是“受约束的实验自动化”。

它需要：

- 稳定任务契约。
- 分层且隔离的数据。
- 原子 Rubric 与校准 judge。
- 受限搜索空间。
- 明确预算。
- 多目标硬约束。
- 候选 diff 与可解释性。
- 独立验证和隐藏测试。
- 人工复核、小流量与回滚。

Prompt search、mutation、DSPy、OPRO、APE 类方法提供不同搜索策略，但都不能绕过测量与治理。
