## 学习目标

- 建立稳定、互斥且可行动的错误分类法。
- 区分提示词错误与数据、检索、工具、模型错误。
- 从失败样本提出可证伪假设。
- 一次只修改一个变量。
- 用最小差异降低回归风险。
- 通过错误矩阵决定修改优先级。
- 将新失败沉淀为回归样本。

## 一、诊断在闭环中的位置

完整闭环是：

1. 定义任务与约束。
2. 建立 baseline。
3. 建立分层测试集。
4. 错误分类。
5. 一次一个变量。
6. 离线评测。
7. 人工复核。
8. 小流量上线。
9. 监控回滚。

本章聚焦第 4 和第 5 步。

诊断输入包括：

- 冻结的任务契约。
- baseline 配置。
- 测试样本。
- 原始输出。
- 期望结果。
- 运行日志。
- 成本与延迟。
- 人工判定理由。

诊断输出不是“新提示词”。

诊断输出应是：

- 错误类别。
- 错误严重度。
- 可能责任层。
- 可证伪假设。
- 最小修改。
- 预期改善切片。
- 潜在回归切片。

## 二、先判断是不是提示词问题

### 系统分层

一次模型请求可能经过：

1. 输入采集。
2. 清洗与截断。
3. 检索。
4. 重排。
5. Prompt 组装。
6. 模型推理。
7. 工具调用。
8. 输出解析。
9. 业务规则。
10. UI 展示。

任何一层都可能失败。

### 责任层速查

| 现象 | 优先检查 | 不要先做 |
|---|---|---|
| 答案缺少关键事实 | 检索召回与截断 | 加“请更准确” |
| JSON 被解析失败 | 输出契约与解析器 | 换知识库 |
| 算术错误 | 计算工具 | 增加形容词 |
| 工具报 403 | 权限与凭证 | 改模型角色 |
| 标签边界混乱 | 标签定义与示例 | 增大 max tokens |
| 旧政策被引用 | 索引快照与时效 | 强调“最新” |
| 多语言明显退化 | 模型能力与样本 | 只加中文示例 |
| 请求超时 | 调用链与 token | 加更多推理步骤 |

### 五个排除问题

- 模型看到了完整输入吗？
- 正确证据进入上下文了吗？
- 工具是否返回成功且结果未被截断？
- 输出是否在解析或后处理时被改变？
- 当前模型是否具备完成任务的基本能力？

只有这些问题排除后，才优先改提示词。

## 三、错误分类法设计原则

好的 taxonomy 应满足：

- **可定义**：标注员理解一致。
- **可复现**：同类错误能稳定归组。
- **可行动**：类别能指向修改或责任层。
- **近似互斥**：主因只有一个。
- **允许多标签**：次因可补充记录。
- **不过细**：每类有足够样本。
- **可演化**：新模式可新增或合并。

### 主因与症状

“回答很差”是症状。

“关键约束遗漏”是错误类别。

“提示词中约束埋在长上下文末尾”是候选根因。

“把关键约束移到明确规则区”是修改。

四者不要混为一谈。

## 四、通用错误分类

### A. 任务理解错误

#### A1 意图识别错误

模型执行了相邻但不同的任务。

例：用户要求抽取，模型进行了总结。

#### A2 范围越界

输出包含任务明确禁止的内容。

例：只问当前政策，却补充历史推测。

#### A3 角色或受众错误

语言面向错误对象。

例：给患者输出医生内部术语。

### B. 指令遵循错误

#### B1 约束遗漏

漏掉长度、字段、语气或引用要求。

#### B2 优先级错误

冲突规则选择错误。

#### B3 否定指令反转

把“不要执行”理解成执行。

#### B4 示例过拟合

机械复制示例内容或结构。

### C. 内容质量错误

#### C1 事实错误

主张与可靠事实不符。

#### C2 无依据主张

来源无法支持主张。

#### C3 信息遗漏

缺少完成任务所需的关键点。

#### C4 无关信息

输出包含不帮助任务的内容。

#### C5 内部矛盾

同一输出前后冲突。

### D. 推理与决策错误

#### D1 规则应用错误

规则存在但应用错。

#### D2 多步依赖遗漏

跳过必要步骤。

#### D3 比较维度错误

在不同单位或口径上比较。

#### D4 不确定性处理错误

证据不足仍断言。

### E. 格式与接口错误

#### E1 JSON 语法无效

#### E2 Schema 不合法

#### E3 字段语义错误

#### E4 额外文本

#### E5 引用格式错误

#### E6 编码或转义错误

### F. RAG 错误

#### F1 未召回

正确文档不在候选中。

#### F2 排序错误

正确文档存在但位置过低。

#### F3 上下文选择错误

组装器丢弃关键片段。

#### F4 来源冲突未处理

#### F5 引用与主张不匹配

#### F6 文档注入被遵循

### G. 工具错误

#### G1 未调用必要工具

#### G2 调用错误工具

#### G3 参数错误

#### G4 调用顺序错误

#### G5 忽略工具错误

#### G6 伪造工具结果

#### G7 未经确认产生副作用

### H. 安全与治理错误

#### H1 泄露敏感数据

#### H2 越权操作

#### H3 提示注入成功

#### H4 拒答过度

#### H5 应拒不拒

#### H6 审计信息缺失

### I. 非功能错误

#### I1 成本越界

#### I2 延迟越界

#### I3 输出波动

#### I4 超时或限流

#### I5 上下文溢出

## 五、错误记录模板

```markdown
## 错误记录

- error_id：ERR-2026-0042
- sample_id：refund-017
- run_id：run-...
- 严重度：S1 / S2 / S3 / S4
- 主错误：B2 优先级错误
- 次错误：C3 信息遗漏
- 责任层：prompt
- 输入切片：billing_refund_boundary
- 期望：refund
- 实际：billing
- 证据：用户明确说“退回重复扣的一笔”
- 可复现次数：4/5
- 根因假设：定义列出两个标签，但未给冲突优先级
- 最小修改：增加一条 refund 优先规则
- 预期改善：billing_refund_boundary recall
- 可能回归：仅询问退款进度但没有申请退款的样本
- 验证集：dev-boundary-v2
- 结论：接受 / 拒绝 / 待观察
```

## 六、严重度与优先级

### 严重度定义

| 等级 | 定义 | 示例 |
|---|---|---|
| S1 | 安全、法律、资金或不可逆影响 | 未确认即付款 |
| S2 | 核心任务失败或高价值用户受损 | 紧急工单漏报 |
| S3 | 可恢复的质量问题 | 摘要漏次要细节 |
| S4 | 轻微风格或展示问题 | 标点不一致 |

### 优先级不是频率排序

可用简化评分：

```text
priority = frequency × severity × exposure × fix_confidence
```

其中：

- frequency：出现概率。
- severity：单次影响。
- exposure：将触达的流量。
- fix_confidence：有明确修复方案的程度。

不要把该公式伪装成客观真理。

它只是讨论工具。

S1 即使低频，也可直接阻止上线。

## 七、从错误到可证伪假设

### 坏假设

> 模型不够聪明。

无法直接验证，也不指向最小修改。

### 好假设

> 当 `billing` 与 `refund` 同时出现时，因为提示词没有定义冲突优先级，模型会偏向前文先出现的 `billing`；加入一条优先规则后，该切片 recall 会提高，纯 billing precision 不应下降超过 1 个百分点。

好假设包含：

- 触发条件。
- 候选机制。
- 修改动作。
- 预期指标。
- 回归护栏。
- 否证条件。

### 假设模板

```text
在 [切片/条件] 下，
因为 [候选机制]，
系统出现 [可观察错误]。
若只修改 [一个变量]，
则 [主指标] 应从 [基线] 改善到 [目标]，
同时 [护栏指标] 不低于 [阈值]；
否则拒绝该假设。
```

## 八、最小修改原则

### 为什么要小

最小修改能够：

- 提高因果归因能力。
- 减少未知回归面。
- 方便 code review。
- 方便回滚。
- 降低 token 成本。
- 保留已验证行为。

### 修改优先级

通常从低复杂度到高复杂度：

1. 删除冲突或冗余文字。
2. 明确一个定义。
3. 增加一个优先规则。
4. 调整输出契约。
5. 增加一个边界正例。
6. 增加一个反例。
7. 重排指令结构。
8. 拆分任务。
9. 引入检索或工具。
10. 换模型或微调。

### 一次一个变量

变量包括：

- system prompt。
- user template。
- few-shot 示例。
- 示例顺序。
- model。
- temperature。
- max tokens。
- tool schema。
- 检索 top-k。
- reranker。
- 文档快照。
- 后处理器。

一次实验只改变一个。

若必须组合变更，应做消融：

- baseline。
- 仅 A。
- 仅 B。
- A+B。

## 九、最小修改正反例

### 案例 1：标签冲突

**失败提示词**：

```text
billing：扣费、支付和账单问题。
refund：退款问题。
```

**过度修改**：

```text
你是一位拥有二十年经验、极其严谨的客服专家。
请深呼吸并逐步思考所有可能性……
```

没有修复定义冲突。

**最小修改**：

```text
冲突规则：若用户明确要求退回已支付款项，选择 refund；
仅询问扣费原因、账单或支付失败时选择 billing。
```

### 案例 2：引用漂移

**失败**：回答有引用，但引用不支持句子。

**错误修改**：增加“请务必准确引用”。

**最小修改**：

```text
把答案拆成独立事实句。
每个事实句末尾只列直接支持该句的来源编号。
来源仅相关但不支持时，不得引用。
```

同时需要 claim-level 评测。

### 案例 3：JSON 外有解释

**失败**：

```text
当然，结果如下：
{"label":"refund"}
```

**最小修改**：

```text
响应必须从 `{` 开始并以 `}` 结束。
不要输出 Markdown、解释或前后缀。
```

更可靠时，应使用供应商支持的结构化输出能力。

### 案例 4：证据不足仍回答

**失败原因候选**：没有明确“不足”的输出路径。

**最小修改**：

```text
若资料不能直接支持答案，返回：
{"status":"insufficient_evidence","answer":null}
```

## 十、提示词结构诊断

推荐检查顺序：

1. 任务是否一句话可说清。
2. 数据与指令是否有边界。
3. 标签或字段是否有完整定义。
4. 冲突是否有优先级。
5. 不确定时是否有合法路径。
6. 输出契约是否自洽。
7. 示例是否与规则一致。
8. 关键规则是否被长上下文淹没。
9. 是否存在重复和相互矛盾的约束。
10. 是否要求模型完成做不到的动作。

### 冗余检测

相同规则重复五次不一定更可靠。

它会：

- 增加 token。
- 放大局部措辞差异。
- 提高维护成本。
- 掩盖真正优先级。

每条指令应能映射到：

- 任务要求。
- 已知错误。
- 安全约束。
- 输出接口。

无法映射的段落应考虑删除。

## 十一、错误聚类标准库示例

下面代码汇总错误类别和切片。

```python
import csv
from collections import Counter, defaultdict


def summarize(path):
    by_error = Counter()
    by_slice = defaultdict(Counter)
    severity = Counter()

    with open(path, newline="", encoding="utf-8") as file:
        for row in csv.DictReader(file):
            if row["passed"].lower() == "true":
                continue
            error = row["primary_error"]
            by_error[error] += 1
            severity[row["severity"]] += 1
            for name in row["slices"].split("|"):
                if name:
                    by_slice[name][error] += 1

    return {
        "by_error": by_error,
        "by_slice": dict(by_slice),
        "severity": severity,
    }
```

### 配对差异检查

同一批样本上比较 A 与 B：

```python
def paired_changes(rows):
    improved = []
    regressed = []
    unchanged = []

    for row in rows:
        before = row["a_pass"]
        after = row["b_pass"]
        if not before and after:
            improved.append(row["id"])
        elif before and not after:
            regressed.append(row["id"])
        else:
            unchanged.append(row["id"])

    return improved, regressed, unchanged
```

总分上涨时，也必须逐条查看 `regressed`。

## 十二、配对评测与不确定性

提示词 A 和 B 应在同一输入上比较。

这样可以减少样本难度差异。

随机输出时：

- 每个版本使用相同采样次数。
- 尽可能使用相同运行窗口。
- 保存每次原始结果。
- 按样本聚合稳定性。
- 不挑最好的一次比较。

### 报告表

| 指标 | A | B | 差值 | 95% CI | 门槛 |
|---|---:|---:|---:|---:|---:|
| Macro F1 | 0.86 | 0.89 | +0.03 | [+0.01,+0.05] | ≥0 |
| Refund recall | 0.91 | 0.96 | +0.05 | [+0.01,+0.09] | ≥0.95 |
| JSON valid | 99.8% | 99.9% | +0.1pp | 待估计 | ≥99.9% |
| p95 latency | 1.8s | 1.9s | +0.1s | - | ≤2.5s |
| mean cost | 0.008 | 0.009 | +12.5% | - | ≤0.010 |

### 不要只比较点估计

差值可能来自随机波动。

关注：

- 置信区间。
- 实际业务效应。
- 高风险切片。
- 重复运行稳定性。
- 多重比较问题。

## 十三、人工复核协议

人工复核不应只看“改进样本”。

至少抽查：

- 所有 S1/S2 样本。
- 所有回归样本。
- judge 与规则评测不一致的样本。
- 高分但可疑的样本。
- 低置信区间切片。
- 随机多次输出不一致的样本。

### 盲审字段

复核员应看到：

- 输入。
- 允许来源。
- 候选输出。
- Rubric。

复核员不应看到：

- 输出来自 A 还是 B。
- 哪个是团队偏好的版本。
- 其他评审的结论。
- 自动 judge 分数。

这可降低确认偏差。

## 十五、何时升级到其他方案

### 提示优化

适用于：

- 任务边界不清。
- 规则冲突。
- 输出契约不稳。
- 少量示例能表达边界。

### RAG

适用于：

- 缺少私有知识。
- 知识频繁更新。
- 输出需要来源。

先修召回和排序，再修生成提示词。

### 工具

适用于：

- 精确计算。
- 实时查询。
- 数据库读写。
- 需要真实副作用。

### 微调

适用于：

- 大量稳定示例。
- 固定行为需规模化复用。
- 提示词过长且模式稳定。

仍需独立评测和回滚。

### 换模型

适用于：

- 能力上限不足。
- 语言或模态不支持。
- 当前成本延迟不合适。
- 安全或部署边界不满足。

## 十六、常见误区

### 误区 1：看到失败就加一句规则

规则会无限膨胀并彼此冲突。

先聚类，确认错误具有代表性。

### 误区 2：只修失败样本

这会形成测试集过拟合。

应修复错误模式，并用未见同类样本验证。

### 误区 3：把模型解释当根因真值

模型对自身行为的解释可能只是事后合理化。

根因必须通过对照实验验证。

### 误区 4：只看改善数，不看回归数

十个低风险改善不能自动抵消一个 S1 回归。

### 误区 5：taxonomy 一开始就过细

几十个类别会导致低一致性和低统计效力。

先用 8-15 个主类，再按数据细分。

### 误区 6：让同一个 LLM 生成、诊断并裁判

同源偏差会被放大。

使用规则、人工和不同 judge 交叉验证。

### 误区 7：改变提示词却不更新 hash

结果无法复现。

任何空格外的语义变更都应生成新版本。

### 误区 8：忽略成本和延迟回归

质量提升可能由输出变长和多次调用换来。

必须同时报告 cost 与 latency。

## 十八、练习

### 练习 1：责任层判断

正确政策文档没有进入 top-20 检索结果，模型给了旧答案。应先改提示词吗？

<details>
<summary>参考答案</summary>

不应。

主错误是 RAG 未召回。

应检查查询改写、索引、过滤和召回策略。

生成提示词无法使用未进入上下文的事实。

</details>

### 练习 2：写假设

模型经常把“查询退款进度”误判为“申请退款”。写出可证伪假设。

<details>
<summary>参考答案</summary>

在包含“退款”但没有申请动作的样本中，因为标签定义只依赖关键词，系统过度预测 refund_request。

若增加“已申请后的进度查询属于 refund_status”规则和一个边界对，则 refund_status recall 应提高至少 5 个百分点，同时 refund_request precision 不得下降。

</details>

## 十九、本章小结

有效诊断遵循一条证据链：

```text
失败样本
-> 错误类别
-> 责任层
-> 可证伪根因假设
-> 一个最小修改
-> 配对离线评测
-> 人工复核
-> 回归样本沉淀
```

不要把 judge、模型自解释或平均分当作真值。
错误分类的价值，在于让每次修改有理由、有边界、可回滚。
