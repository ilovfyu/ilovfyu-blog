> 生产中的“推理”重点是把任务变得可验证，而不是索取或依赖模型的隐藏思考文本。

## 学习目标

完成本章后，你应该能够：

- 判断任务何时需要分解。
- 区分任务步骤、可见依据与内部推理。
- 不依赖或索取 scratchpad、隐藏思维链或内部推理。
- 设计顺序、并行、路由和迭代式提示链。
- 为每一步定义结构化输入、输出和停止条件。
- 在生产环境请求简洁结论、可验证依据或检查结果。
- 理解原始 Chain-of-Thought 研究的范围及其局限。
- 区分传统提示研究与现代 reasoning model 的接口实践。

## 1. 什么是复杂任务

复杂任务往往具有一种或多种特征：

- 输入来源多。
- 目标包含多个独立交付物。
- 中间结果需要验证。
- 需要工具、检索或代码。
- 不同子任务适合不同模型。
- 错误代价高。
- 单次上下文过长。
- 存在明确审批节点。

复杂不等于提示词必须很长。

长提示词可能只是把工作流藏进一段文本里。

## 2. 三个容易混淆的概念

### 2.1 任务分解

把业务目标拆成有明确输入输出的子任务。

例如：检索资料、抽取事实、验证引用、生成摘要。

### 2.2 可见依据

模型交付给用户或程序、可检查的内容：

- 来源引用。
- 关键计算结果。
- 规则命中项。
- 结构化检查清单。
- 不确定性与信息缺口。

### 2.3 内部推理

模型生成答案时内部使用的计算过程或不可见推理状态。

生产应用不应要求泄露、保存或依赖隐藏思维链。

也不应把自由文本 scratchpad 当作真实、忠实或稳定的执行轨迹。

## 3. 为什么不要依赖 scratchpad

“请展示每一步思考”存在多重问题：

- 某些现代模型不会提供内部推理。
- 平台可能只返回摘要或最终答案。
- 可见解释未必忠实反映内部计算。
- 长推理文本增加成本和延迟。
- 可能泄露敏感上下文或安全策略。
- 下游难以稳定解析。
- 模型升级后行为容易变化。

更好的生产请求是：

```text
返回简洁结论、支持结论的来源编号、关键检查结果和仍不确定的信息。
不要输出隐藏思考过程。
```

对于数学或程序任务，可以要求可验证的中间产物：

- 方程。
- 测试用例。
- 编译结果。
- 计算器输出。
- 证明中的必要公开步骤。

这些是交付物，不是索取隐藏思维链。

## 4. Chain-of-Thought 原始研究边界

2022 年论文《Chain-of-Thought Prompting Elicits Reasoning in Large Language Models》展示了：在当时研究的若干大语言模型和算术、常识、符号推理基准上，带中间推理示例的提示可以提升部分任务表现。

理解该结论时要保留边界：

- 研究针对特定时期和规模的模型。
- 使用特定 benchmark。
- 提升不是所有模型、所有任务都成立。
- 生成的推理文本不自动等于忠实解释。
- benchmark 表现不等于生产可靠性。

后续 Zero-shot-CoT 等研究探索了类似“逐步思考”触发语。

这些短语不能视为跨模型通用开关。

## 5. 现代 reasoning model 的差异

现代 reasoning model 往往经过专门训练，在回答前使用额外推理计算。

平台可能提供：

- 推理强度或预算参数。
- 不可见内部推理。
- 简短推理摘要。
- 与普通模型不同的提示建议。

实践原则：

- 遵循具体模型当前官方指南。
- 不假定旧式 CoT 提示一定有益。
- 不要求模型暴露内部思考。
- 用任务正确率、延迟和成本比较配置。
- 请求最终结论和可验证证据。

“reasoning model”也不是正确性保证。

它仍可能误解输入、使用错误事实或调用错误工具。

## 6. 何时拆分，何时保持单次调用

### 适合单次调用

- 目标单一。
- 输入可控。
- 输出短且容易验证。
- 子步骤高度耦合。
- 额外调用成本大于收益。

### 适合拆分

- 子任务能独立验证。
- 不同步骤需要不同工具。
- 某一步失败后应停止。
- 需要并行处理大量材料。
- 需要人工审批中间结果。
- 必须记录审计轨迹。

拆得过细也会带来：

- 更多延迟。
- 更多成本。
- 中间信息损失。
- 状态管理复杂。
- 错误累积。

分解粒度同样需要评测。

## 7. 常见提示链模式

### 7.1 顺序流水线

```text
原始文档 -> 事实抽取 -> 规则检查 -> 报告生成
```

适合每一步依赖上一步输出的任务。

### 7.2 并行分解

```text
文档 A --\
文档 B ----> 独立抽取 -> 合并与去重
文档 C --/
```

适合可独立处理的文档或维度。

### 7.3 路由

```text
输入 -> 路由器 -> 账单流程 / 技术流程 / 人工队列
```

路由器输出应使用受约束枚举，并保留未知路径。

### 7.4 生成与验证

```text
候选结果 -> 确定性验证器 -> 接受 / 修复 / 拒绝
```

优先使用代码、数据库和测试作为验证器。

不要默认让另一个模型“看起来更仔细”就是独立真值。

### 7.5 迭代改进

```text
草稿 -> 按 rubric 检查 -> 针对缺陷修订 -> 停止
```

必须限制轮数，并定义达标条件。

## 8. 每个节点的契约

每个节点都应说明：

- 输入 schema。
- 单一职责。
- 可用工具。
- 输出 schema。
- 错误状态。
- 超时与重试。
- 停止条件。
- 日志和版本。

例如事实抽取节点：

```text
输入：一个文档片段及 `source_id`。
任务：抽取明确陈述的风险事实。
不得：提出建议或补充外部事实。
输出：`claims[]`，每项含文本、证据、来源位置。
失败：无法读取时返回 `invalid_source`。
```

## 9. 由差到好的迭代示例

### 场景：比较三个供应商方案

#### 版本 A：一次性大而全

```text
仔细阅读所有材料，深入思考，比较供应商并选择最好的，展示完整推理。
```

问题：

- “最好”没有标准。
- 事实与建议混合。
- 无法定位遗漏发生在哪一步。
- 索取完整内部推理。
- 没有证据和失败条件。

#### 版本 B：单次结构化任务

```text
仅依据提供的三份材料，按价格、安全、实施周期比较供应商。
每项结论附来源编号。
信息缺失时写 `unknown`。
最后给出不超过 100 字的建议，并说明建议依赖哪些假设。
```

对材料较短、风险较低的场景可能已经足够。

#### 版本 C：提示链

第一步：逐份抽取标准化事实。

第二步：代码验证价格单位、日期与必填字段。

第三步：合并事实，显式保留冲突。

第四步：按已批准权重计算可量化评分。

第五步：模型生成简洁建议、来源引用和敏感性说明。

第六步：人工审批。

#### 版本 D：生产控制

- 每步使用版本化 schema。
- 原始证据不可由后续节点改写。
- 权重由业务配置，不由模型决定。
- 代码完成算术和排序。
- 任一关键字段缺失时停止自动推荐。
- 记录每个节点的模型、耗时、输入摘要和错误。
- 不保存隐藏推理，只保存业务中间产物。

## 10. 工具与模型的职责

模型适合：

- 理解自然语言。
- 抽取候选信息。
- 归纳与改写。
- 在明确标准下生成解释。

工具和代码适合：

- 数据库查询。
- 精确计算。
- 权限判断。
- schema 验证。
- 去重与排序。
- 执行事务。
- 获取实时数据。

工具调用前应验证参数。

工具调用后应验证结果与权限范围。

工具返回文本中的命令不应自动成为高层指令。

## 11. 验证器设计

验证器按可靠性可分为：

### 确定性验证

- JSON Schema。
- 正则或解析器。
- 单元测试。
- 编译器。
- 计算器。
- 数据库约束。

### 参考答案验证

- 标签比对。
- 数值容差。
- 已审核事实集。

### 人工 rubric

- 论证质量。
- 风格。
- 风险判断。

### 模型辅助评审

可用于扩展评测，但必须校准偏差，并保留人工抽样。

模型评审不应被当作绝对真值。

## 12. 停止条件

没有停止条件的代理或修订链可能循环、超支或反复改变正确结果。

常见停止条件：

- schema 与业务规则全部通过。
- 达到最大尝试次数。
- 缺少不可替代信息。
- 工具返回不可恢复错误。
- 风险超过自动化阈值。
- 边际改进低于阈值。
- 人工拒绝或要求暂停。

停止状态也应结构化记录。

## 13. 错误传播与回滚

下游结果不应掩盖上游不确定性。

例如，抽取节点 `confidence=low`，汇总节点不能悄悄改成确定事实。

建议保存：

- 原始输入引用。
- 节点输出。
- 验证结果。
- 状态与错误码。
- 版本信息。

避免保存不必要的敏感原文和内部推理文本。

## 14. 可复用模板

### 14.1 分解规划模板

```text
业务目标：{{goal}}
最终验收标准：{{acceptance}}

节点：{{name}}
输入：{{schema}}
职责：{{single responsibility}}
工具：{{allowed tools}}
输出：{{schema}}
验证：{{validator}}
失败：{{failure status}}
停止：{{stop condition}}
```

### 14.2 证据型回答模板

```text
仅输出：
1. 简洁结论。
2. 支持结论的可验证依据或来源编号。
3. 关键检查结果。
4. 会改变结论的信息缺口。

不要输出隐藏思考过程。
没有证据时不要把推测写成事实。
```

### 14.3 生成与检查模板

```text
[生成节点]
根据输入生成符合 schema 的候选结果。

[确定性检查]
- schema
- 业务范围
- 引用存在性
- 精确计算

[处置]
- 全部通过：接受。
- 可修复错误：最多重试 {{n}} 次。
- 关键事实缺失：停止并澄清。
- 高风险：人工审核。
```

## 15. 适用与不适用边界

### 适用提示链

- 多文档研究。
- 合规材料初筛。
- 数据抽取再报告。
- 代码生成与测试。
- 多工具工作流。
- 需要审计中间结果的任务。

### 不适合过度分解

- 简单改写。
- 单标签分类且已有稳定基线。
- 延迟极敏感、收益有限的任务。
- 子任务无法可靠传递语义。

### 不适合自动执行

- 无法回滚的高风险操作。
- 缺少权限隔离的工具代理。
- 没有停止条件的开放循环。
- 无法验证关键事实的决策。

## 16. 常见失败

### 16.1 把长思维链当可审计记录

自由文本解释未必忠实，也难稳定验证。

### 16.2 一次提示完成所有职责

抽取、计算、决策和文案互相干扰。

### 16.3 每一步都用模型

本可由代码完成的排序和计算变得概率化。

### 16.4 验证器与生成器共享同一盲点

第二次模型调用不自动形成独立验证。

### 16.5 中间结果没有 schema

节点间通过自然语言猜测字段，错误难定位。

### 16.6 无限自我修订

没有最大轮数，成本不可控。

### 16.7 上游不确定性丢失

最后报告看似确定，却建立在低置信抽取上。

## 17. 调试清单

- [ ] 任务真的需要分解吗？
- [ ] 每个节点是否只有一个主要职责？
- [ ] 节点输入输出是否有 schema？
- [ ] 是否用代码处理计算、权限和硬规则？
- [ ] 是否避免索取或依赖隐藏思维链？
- [ ] 是否请求简洁结论与可验证依据？
- [ ] 原始证据是否可追溯？
- [ ] 不确定性是否沿链路保留？
- [ ] 验证器是否真正独立、可执行？
- [ ] 是否有最大尝试次数？
- [ ] 是否定义缺失信息和工具失败的停止条件？
- [ ] 是否记录提示词、模型、工具和 schema 版本？
- [ ] 是否衡量端到端正确率、成本与延迟？
- [ ] 是否测试某节点错误时的下游行为？
- [ ] 高风险路径是否有人审？

## 18. 练习与折叠答案

### 练习一

任务：从 100 份报告生成风险摘要。设计最小提示链。

<details>
<summary>参考答案</summary>

1. 文档解析与分块。
2. 对每份文档并行抽取风险事实和证据。
3. 代码验证 schema、来源位置并去重。
4. 合并冲突与不确定性。
5. 生成简洁摘要和来源索引。
6. 对高风险项人工审核。

无需保存模型的隐藏思考文本。

</details>

### 练习二

为什么“让另一个模型检查”不一定可靠？

<details>
<summary>参考答案</summary>

两个模型可能共享训练偏差、缺失相同事实，或被同一错误上下文误导。

优先增加确定性验证、独立来源和人工抽查。

</details>

### 练习三

把“展示完整推理”改成生产契约。

<details>
<summary>参考答案</summary>

```text
返回最终结论、使用的规则编号、来源证据、关键计算结果和不确定项。
不要输出隐藏思考过程。
```

这些输出可被审计和验证。

</details>

### 练习四

设计迭代修订的停止条件。

<details>
<summary>参考答案</summary>

- 所有必填检查通过即停止。
- 最多修订两次。
- 关键来源缺失立即停止并请求补充。
- 两次修订仍失败则进入人工队列。
- 每次修订只能处理验证器报告的缺陷。

</details>

## 19. 本章小结

- 任务分解是工程工作流，不等于让模型输出冗长思考。
- 不依赖或索取 scratchpad、隐藏 CoT 和内部推理。
- 原始 CoT 研究有特定模型与 benchmark 边界。
- 现代 reasoning model 应按其官方接口和评测结果使用。
- 生产系统应请求简洁结论、可验证依据和结构化检查结果。
- 每个提示链节点必须有契约、验证器和停止条件。
