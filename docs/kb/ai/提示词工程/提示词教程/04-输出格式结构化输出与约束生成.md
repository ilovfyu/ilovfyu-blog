> 机器可读不是“看起来像 JSON”，而是结构、类型与业务语义都经过验证。

## 学习目标

完成本章后，你应该能够：

- 区分展示格式、语法合法性、schema 合法性和业务正确性。
- 为人类阅读与机器消费分别设计输出契约。
- 优先使用 API 原生 Structured Outputs 或 schema 能力。
- 在服务端解析、验证并安全处理模型输出。
- 设计结构化成功、失败和澄清结果。
- 识别约束解码的能力边界。
- 建立格式通过率与语义质量评测。

## 1. 输出契约的四个层次

### 1.1 展示层

例如 Markdown 标题、表格、项目列表与摘要顺序。

它主要服务人类阅读。

### 1.2 语法层

例如输出是否为合法 JSON。

合法 JSON 不代表字段正确。

### 1.3 schema 层

例如必填字段、类型、枚举和嵌套结构是否满足 JSON Schema。

schema 正确不代表业务事实正确。

### 1.4 业务语义层

例如：

- `order_id` 是否真实存在。
- `total` 是否等于明细之和。
- 引用是否支持对应结论。
- 日期是否处于允许范围。
- 分类是否符合业务定义。

生产系统必须明确四层分别由谁负责。

## 2. 人类输出与机器输出

### 2.1 面向人类

关注：

- 先结论还是先背景。
- 读者知识水平。
- 可扫描性。
- 证据位置。
- 篇幅与语气。

示例契约：

```text
先用不超过 80 字给出结论。
随后列出最多 3 条证据，每条标注来源编号。
最后列出仍需确认的信息。
```

### 2.2 面向机器

关注：

- 稳定字段。
- 明确类型。
- 有限枚举。
- 必填与可空规则。
- 版本兼容。
- 失败结构。

不要让下游程序依赖自然语言标题或标点切割。

### 2.3 同时服务两者

可以返回结构化数据，其中包含简洁的人类摘要字段。

也可以让后端先获得结构化结果，再由界面渲染。

避免让模型同时维护两份可能互相矛盾的事实表示。

## 3. JSON 的可靠性阶梯

### 3.1 仅靠文字要求

```text
只输出 JSON，不要包含其他内容。
```

这是最弱方案。

模型仍可能输出代码围栏、前言、尾注或非法转义。

### 3.2 JSON 模式

某些 API 提供“合法 JSON”模式。

它通常改善语法合法性，但未必保证符合特定 schema。

具体保证依平台文档。

### 3.3 原生 Structured Outputs 或 schema

优先使用 API 提供的 JSON Schema、Structured Outputs、受约束工具参数或等价能力。

它通常能把字段和类型约束纳入解码或服务端保证。

但仍需确认：

- 支持哪些 schema 关键字。
- 是否允许递归。
- 可选字段如何表达。
- 拒答或截断时返回什么。
- 流式输出如何验证。
- SDK 是否自动解析。

### 3.4 服务端代码验证

即使使用原生 schema，也必须验证：

- API 是否成功完成。
- 输出是否被截断或拒绝。
- 结构是否通过本地 schema。
- 业务不变量是否成立。
- 字符串是否需要转义后再展示。
- 标识符是否有权限访问。

原生 schema 与代码验证是互补关系。

## 4. Schema 设计原则

### 4.1 使用有限枚举

较弱：

```json
{"priority":"任意文本"}
```

较强：

```json
{"priority":"low | medium | high"}
```

### 4.2 区分缺失、未知和不适用

这三者可能有不同业务含义。

可以使用状态字段：

```json
{
  "status": "complete",
  "value": "...",
  "missing_fields": []
}
```

不要用空字符串同时表达所有情况。

### 4.3 避免自由文本承载控制逻辑

让 `action` 使用枚举。

让 `explanation` 只用于展示和审核。

下游不得通过关键词猜测动作。

### 4.4 控制嵌套深度

过深结构增加 token、验证和维护成本。

只为真实业务关系增加嵌套。

### 4.5 明确版本

对长期集成可加入：

```json
{"schema_version":"1.0"}
```

版本迁移应由应用代码管理，而不是要求模型兼容所有历史格式。

## 5. 成功与失败使用同一协议

一种可复用的联合结构：

```json
{
  "status": "ok | needs_clarification | invalid_input | insufficient_evidence | tool_error",
  "data": {},
  "questions": [],
  "errors": []
}
```

实际 schema 可使用 `oneOf` 或平台支持的等价设计，为每种状态限定字段。

例如：

- `ok` 必须包含 `data`。
- `needs_clarification` 必须包含最少一个问题。
- `tool_error` 必须包含机器可处理的错误码。

不要把内部堆栈、秘密或敏感工具参数返回给用户。

## 6. 提示词与 Schema 的职责分工

Schema 适合定义：

- 字段名。
- 数据类型。
- 枚举。
- 必填项。
- 数组长度。
- 基础格式。

提示词适合定义：

- 字段语义。
- 信息来源边界。
- 分类标准。
- 证据要求。
- 冲突和缺失策略。

代码适合定义：

- 权限。
- 业务不变量。
- 数据库存在性。
- 精确计算。
- 跨字段一致性。
- 重试与事务。

## 7. 代码验证示例

下面是语言无关的伪代码：

```text
response = call_model(prompt, response_schema)

if response.transport_error:
    return handle_transport_error()

if response.refusal or response.truncated:
    return handle_incomplete_response()

parsed = parse_json(response.content)
validate_schema(parsed, response_schema)
validate_business_rules(parsed)
validate_references(parsed, source_documents)

return parsed
```

Python 中可以使用项目已有的 schema 库：

```python
from typing import Literal
from pydantic import BaseModel, Field


class TicketResult(BaseModel):
    status: Literal["ok", "needs_clarification"]
    category: Literal["billing", "technical", "account"] | None = None
    evidence: list[str] = Field(max_length=3)
    question: str | None = None


result = TicketResult.model_validate(model_payload)

if result.status == "ok" and result.category is None:
    raise ValueError("ok result must contain category")
if result.status == "needs_clarification" and not result.question:
    raise ValueError("clarification result must contain question")
```

生产项目应根据所用 SDK 直接绑定 schema，避免手工复制定义造成漂移。

## 8. 由差到好的迭代示例

### 场景：从合同片段抽取续约信息

#### 版本 A

```text
抽取续约日期和条款，输出 JSON。
```

问题：字段、日期格式和未知策略均不明确。

#### 版本 B

```text
只输出：
{"renewal_date":"YYYY-MM-DD","auto_renew":true,"notice_days":30}
```

问题：示例值可能被当作真实默认值；无法表达未知。

#### 版本 C

```text
仅依据 &lt;contract&gt; 抽取续约信息。
不得根据常见合同惯例补全。
相对日期无法确定时保留原文并标记 `needs_review`。
每个抽取值附支持它的原文片段。
输出遵守调用方提供的 schema。
```

Schema 定义：

- `status`：`complete`、`needs_review`、`not_found`。
- `renewal_date`：日期或 `null`。
- `auto_renew`：布尔值或 `null`。
- `notice_days`：非负整数或 `null`。
- `evidence`：原文证据数组。

#### 版本 D：生产方案

- 使用 API 原生 schema。
- 本地再次验证结构。
- 日期解析器检查合法日期。
- 证据匹配器确认片段来自合同。
- 高风险字段由法务抽样审核。
- 对扫描错误和冲突条款设独立状态。
- 记录模型、schema、提示词和合同解析器版本。

## 9. 约束生成的边界

受约束生成能显著改善结构合法性。

它不能保证：

- 事实正确。
- 引用真实。
- 计算正确。
- 分类符合业务。
- 输入没有提示注入。
- 工具调用有权限。

合法结构可以装载错误内容。

因此“schema 通过率 100%”不是任务成功率。

## 10. Markdown、表格与其他格式

Markdown 适合人类阅读，不适合作为严格数据协议。

表格在以下情况容易失败：

- 单元格包含换行。
- 内容包含竖线。
- 列数动态变化。
- 长文本难阅读。

CSV 需要严格处理引号、逗号和换行。

XML 也需要解析与 schema 验证。

如果下游是程序，选择有成熟解析器和平台原生约束支持的格式。

## 11. 流式输出

流式 token 在完成前往往不是合法 JSON。

设计时应明确：

- 客户端是否等待完整对象后解析。
- SDK 是否提供结构化增量事件。
- 中途中断如何标记。
- 是否允许展示未验证内容。

高风险动作不要在对象尚未完成验证时执行。

## 12. 重试与修复

不要无限重试同一个无效请求。

可采用有限策略：

1. 原生 schema 调用。
2. 若发生可重试的传输错误，按退避策略重试。
3. 若输出截断，减少任务或增加允许输出长度。
4. 若语义校验失败，记录错误并有限次重新请求。
5. 仍失败则降级或人工处理。

“请修复以下 JSON”可作为降级手段，但不优于原生约束，也可能改变语义。

## 13. 输出评测

至少记录：

- API 成功率。
- 拒绝与截断率。
- JSON 解析通过率。
- schema 通过率。
- 业务规则通过率。
- 引用有效率。
- 任务正确率。
- 重试次数。
- 延迟与 token 成本。

错误应分类，而不是归入“模型输出不好”。

## 14. 可复用模板

### 14.1 结构化抽取模板

```text
任务：仅从 &lt;source&gt; 抽取 schema 定义的信息。

语义规则：
- 不使用外部常识补全缺失值。
- 字段没有证据时使用 schema 规定的 `null` 或状态。
- 每个关键值关联原文证据。
- 冲突值不得静默合并。

&lt;source&gt;
{{source}}
&lt;/source&gt;

输出：严格遵守 API 调用方提供的 schema。
```

### 14.2 面向人类的报告模板

```text
按以下顺序输出 Markdown：
## 结论
不超过 {{n}} 字。

## 依据
最多 {{m}} 条，每条附来源编号。

## 不确定性
只列会影响决策的信息缺口。

不得输出未被材料支持的事实。
```

### 14.3 验证计划模板

```text
语法验证：{{解析器}}
Schema 验证：{{schema/version}}
业务验证：{{不变量列表}}
引用验证：{{匹配规则}}
失败处理：{{重试/降级/人工}}
监控指标：{{指标与阈值}}
```

## 15. 适用与不适用边界

### 适用

- 信息抽取。
- 分类路由。
- 工具参数生成。
- 工作流中间结果。
- 可审计报告的数据层。

### 不适合只靠输出约束

- 精确财务计算。
- 权限检查。
- 数据库事务。
- 事实真实性保证。
- 法规合规最终判断。
- 未经验证直接执行不可逆操作。

## 16. 常见失败

### 16.1 只写“输出 JSON”

没有 schema，也没有验证器。

### 16.2 示例值变成默认值

模型在缺失信息时复制示例中的日期或数字。

### 16.3 可选字段语义混乱

字段缺失、`null` 和空字符串被下游当成同一含义。

### 16.4 自由文本驱动程序

程序通过“建议退款”等关键词执行动作，容易误触发。

### 16.5 信任 schema 内的事实

格式合法被误认为内容真实。

### 16.6 忽略截断与拒答

解析错误被错误地当作普通模型失败。

### 16.7 schema 过度复杂

维护困难，模型能力和平台支持也可能不足。

## 17. 调试清单

- [ ] 输出主要给人还是给机器？
- [ ] 是否优先使用平台原生 Structured Outputs/schema？
- [ ] 是否核对当前 API 的具体保证？
- [ ] 字段类型、枚举和必填项是否明确？
- [ ] 缺失、未知、不适用是否区分？
- [ ] 成功和失败是否都有稳定结构？
- [ ] 是否在服务端重新解析和验证？
- [ ] 是否验证跨字段业务规则？
- [ ] 是否核对引用来自原文？
- [ ] 是否避免用自由文本控制动作？
- [ ] 是否处理拒答、截断、超时和流中断？
- [ ] 是否限制重试次数？
- [ ] 是否记录 schema 和提示词版本？
- [ ] 是否分别计算结构与语义指标？
- [ ] 高风险动作是否等待完整验证？

## 18. 练习与折叠答案

### 练习一

合法 JSON 是否等于结构化输出成功？

<details>
<summary>参考答案</summary>

不等于。

还需验证 schema、业务不变量、事实依据和调用完成状态。

</details>

### 练习二

设计一个澄清结果。

<details>
<summary>参考答案</summary>

```json
{
  "status": "needs_clarification",
  "data": null,
  "questions": [
    {"field": "order_id", "question": "请提供订单号。"}
  ],
  "errors": []
}
```

真实 schema 应约束状态与字段组合。

</details>

### 练习三

模型返回的总价与明细之和不一致，应该加一句“认真计算”吗？

<details>
<summary>参考答案</summary>

不应把提示词作为主要修复。

让模型抽取明细，由代码计算总价并验证货币精度。

</details>

### 练习四

为什么流式 JSON 不能边收到边执行工具？

<details>
<summary>参考答案</summary>

中间片段可能不完整、未通过 schema、随后被修改或最终截断。

应使用平台提供的完整受约束工具参数事件，并在验证和权限检查后执行。

</details>

## 19. 本章小结

- 输出契约包含展示、语法、schema 和业务语义四层。
- JSON 场景优先使用 API 原生 Structured Outputs/schema，而非只靠文字。
- 任何模型输出都应经过代码解析与业务验证。
- 约束生成改善合法性，不保证事实正确性。
- 结构、语义、成本与失败率应分别评测。
