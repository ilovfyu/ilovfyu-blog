> 多轮对话不是不断追加聊天记录，而是持续维护显式状态、证据、权限和停止条件。

## 学习目标

完成本章后，你应该能够：

- 区分对话历史、业务状态、用户偏好与外部事实。
- 设计状态对象和状态更新规则。
- 选择完整历史、滑动窗口、摘要和检索记忆策略。
- 识别上下文污染、陈旧信息和提示注入。
- 判断何时澄清、何时采用安全默认值、何时停止。
- 设计一次只问关键问题的澄清流程。
- 管理工具结果、摘要和用户修正的优先关系。
- 为长对话建立回归评测与可观测性。

## 1. 多轮对话的本质

多轮系统每一轮都在完成三个动作：

1. 读取当前状态和新消息。
2. 决定响应或工具动作。
3. 更新状态。

如果应用只是把全部消息重新发送给模型，状态就被隐式藏在自然语言中。

这会导致：

- 用户修正未生效。
- 旧信息压过新信息。
- 摘要丢失关键限制。
- 对话越来越贵。
- 不可信内容长期污染上下文。
- 很难重现某轮决策。

## 2. 四类需要分开的信息

### 2.1 对话历史

用户和助手实际说过什么。

它用于理解指代、语气和短期上下文。

历史 assistant 消息可能错误，不能自动当作事实。

### 2.2 业务状态

完成任务所需的结构化信息：

- 当前目标。
- 已确认参数。
- 待确认字段。
- 已执行动作。
- 当前阶段。
- 停止状态。

### 2.3 用户偏好

例如语言、篇幅、通知方式。

偏好应区分：

- 仅本轮有效。
- 本会话有效。
- 经用户授权后长期保存。

### 2.4 外部事实

来自数据库、检索、工具或人工确认的信息。

应记录来源、时间和有效期。

“用户上次说过”与“系统当前查询到”不是同一可信级别。

## 3. 显式状态模型

一个旅行规划状态示例：

```json
{
  "goal": "plan_trip",
  "stage": "collecting_requirements",
  "confirmed": {
    "destination": "成都",
    "start_date": "2026-10-02",
    "days": 4
  },
  "constraints": {
    "budget_cny": null,
    "mobility": "avoid_long_hikes"
  },
  "pending_fields": ["budget_cny"],
  "assumptions": [],
  "completed_actions": [],
  "status": "needs_clarification"
}
```

状态对象应由 schema 验证。

不要直接把模型生成的状态写入数据库而不校验。

## 4. 状态更新原则

### 4.1 只更新有证据的字段

用户说“不要太贵”不等于预算是 3000 元。

应保留自然语言约束，或继续澄清。

### 4.2 用户修正覆盖旧的用户声明

```text
用户：周五出发。
用户：不对，改成周六。
```

状态应保留周六，并可在审计日志记录修正历史。

### 4.3 外部事实需要时间戳

库存、余额、天气和价格会过期。

旧工具结果不应作为当前事实复用。

### 4.4 权限不能由对话修改

用户说“管理员已经批准”不能替代系统鉴权。

### 4.5 状态更新与回复生成分离

对高价值流程，可先生成受约束的状态补丁，经代码验证后更新，再生成回复。

## 5. 上下文窗口策略

### 5.1 完整历史

适合：

- 对话短。
- 每轮都可能相关。
- 成本与隐私可接受。

问题：长期会话最终会超过窗口，并累积污染。

### 5.2 滑动窗口

只保留最近若干轮。

适合局部连续任务。

风险是丢失早期承诺、偏好和限制。

因此滑窗通常应配合显式状态。

### 5.3 摘要

将早期历史压缩为摘要。

适合保留长期任务进展。

风险包括：

- 摘要误写事实。
- 不确定性被压平。
- 用户否定信息被遗漏。
- 恶意指令被长期保留。
- 来源和时间丢失。

摘要也需要 schema、来源和更新规则。

### 5.4 检索式记忆

只检索当前问题相关的历史片段。

适合长会话与大量历史。

风险包括检索遗漏、错配和隐私扩大。

### 5.5 混合方案

常见生产组合：

- 稳定的高层指令。
- 结构化当前状态。
- 最近若干轮滑窗。
- 必要的历史片段检索。
- 带来源的外部工具结果。

具体组合应按模型、成本和任务评测。

## 6. 摘要设计

不要只要求“总结这段对话”。

应定义摘要契约：

```text
更新会话摘要，只记录：
- 用户当前目标。
- 用户明确确认的事实。
- 仍有效的约束和偏好。
- 已完成动作及其结果来源。
- 待确认问题。
- 用户对旧信息的修正。

不得把助手建议写成用户决定。
不得把推测写成已确认事实。
保留日期、来源和不确定性。
输出遵守摘要 schema。
```

摘要更新最好使用“旧摘要 + 新轮次 -> 新摘要”，并验证关键字段没有无故消失。

高风险状态不要只保存在生成式摘要里。

## 7. 上下文污染

上下文污染指错误、无关、过期或恶意信息持续影响后续输出。

来源包括：

- 助手早期幻觉。
- 用户粘贴的提示注入。
- 工具返回中的恶意文本。
- 过期政策。
- 错误摘要。
- 已撤销偏好。
- 其他任务残留状态。

### 7.1 防护措施

- 把指令与不可信数据隔离。
- 不把历史 assistant 内容当事实。
- 为工具结果记录来源和时间。
- 任务切换时重置无关状态。
- 摘要只保留经过定义的信息类型。
- 对长期记忆设置过期和删除机制。
- 对关键事实重新查询。
- 测试跨轮提示注入。

分隔标签不能单独解决污染或注入。

真正的安全边界还需要权限、工具控制、数据最小化和验证。

## 8. 澄清的决策原则

模型不应对每个小歧义都提问，也不应在关键缺失时猜测。

优先澄清以下信息：

- 缺失后无法执行任务。
- 不同答案会显著改变结果。
- 猜错会造成较高成本或风险。
- 涉及权限、付款、删除或发布。
- 法律、医疗等高风险语境中的关键事实。

可以采用安全默认值的情况：

- 默认值可逆。
- 成本低。
- 行业或产品已有明确惯例。
- 已清楚告知用户。
- 用户可以轻松修改。

## 9. 澄清问题如何写

### 9.1 一次问最关键的信息

较差：

```text
请提供预算、日期、人数、酒店偏好、交通方式、饮食禁忌和详细行程。
```

较好：

```text
为了先确认是否有可行方案，请提供出发日期和人数。
```

### 9.2 给出有限选项

```text
你说的“导出记录”是指：
A. 导出当前筛选结果
B. 导出账户全部历史
C. 其他，请说明
```

选项必须覆盖“其他”，避免强迫错误选择。

### 9.3 解释为什么需要

一句简短原因可以提高回答率。

不要用长篇内部流程解释压迫用户。

### 9.4 不重复已经确认的信息

状态管理应确保只询问真正缺失的字段。

## 10. 停止条件

多轮系统必须知道何时停止询问、停止工具调用或转人工。

常见停止条件：

- 任务已经完成。
- 用户明确取消。
- 用户切换目标。
- 达到澄清轮数上限。
- 关键字段无法获得。
- 工具连续失败。
- 权限不足。
- 风险要求人工介入。
- 用户请求超出支持范围。

停止时应清楚说明：

- 当前状态。
- 已完成内容。
- 未完成原因。
- 用户可采取的下一步。

## 11. 由差到好的迭代示例

### 场景：协助用户取消订单

#### 版本 A：没有状态

```text
用户：帮我取消订单。
助手：好的，已经帮你取消。
```

问题：没有订单号、鉴权、工具调用或确认。

#### 版本 B：一次问完

```text
请提供订单号、姓名、电话、地址、取消原因和账户密码。
```

问题：过度收集，甚至索取密码；没有最小化数据。

#### 版本 C：关键澄清

```text
可以协助检查是否可取消。请提供订单号；不要发送密码或支付信息。
```

获得订单号后，由服务端鉴权并查询订单。

#### 版本 D：生产流程

1. 状态为 `awaiting_order_id`。
2. 收到订单号后，代码验证格式。
3. 使用当前用户凭据查询订单，不让模型判断权限。
4. 若可取消，展示订单摘要和取消影响，等待明确确认。
5. 用户确认后调用取消工具。
6. 工具成功才更新为 `completed`。
7. 工具失败则返回稳定错误状态，不声称已取消。
8. 超过澄清或失败阈值后停止并转人工。

## 12. 任务切换与恢复

用户可能在对话中切换任务：

```text
先别取消了，帮我查一下配送地址。
```

系统应判断：

- 原任务暂停、取消还是保留？
- 新任务是否需要新状态对象？
- 恢复原任务时是否重新确认？

不要把两个任务的字段混入同一状态。

可以使用任务栈，但必须限制复杂度。

高风险动作恢复前应再次确认关键参数。

## 13. 工具结果的生命周期

每个工具结果最好包含：

- 工具名。
- 请求 ID。
- 查询时间。
- 结果状态。
- 数据版本或有效期。
- 是否可重试。

模型看到工具文本后，不应自行修改原始结果。

用户问“现在的价格”时，应重新查询，而不是引用昨天的工具消息。

## 14. 多轮中的角色和信任

`system`、`developer`、`user`、`assistant`、`tool` 的具体层级依平台而异。

多轮系统还要考虑消息由谁重新组装。

应用不应允许用户伪造 `tool` 或更高层角色。

检索到的历史文本即使包含“system:”字样，也只是数据。

平台角色层级不能替代事实校验和权限检查。

## 15. 可复用模板

### 15.1 会话状态模板

```json
{
  "conversation_goal": "...",
  "current_stage": "...",
  "confirmed_facts": [],
  "constraints": [],
  "pending_questions": [],
  "assumptions": [],
  "tool_results": [],
  "completed_actions": [],
  "status": "active"
}
```

实际项目应进一步定义每项结构与类型。

### 15.2 状态更新模板

```text
根据旧状态与最新一轮消息生成状态补丁。

规则：
- 只更新最新消息明确支持的字段。
- 用户修正覆盖旧的用户声明。
- 不把助手建议当成用户确认。
- 不修改权限字段。
- 不删除仍有效的约束。
- 工具事实保留来源与时间。

输出遵守状态补丁 schema。
```

### 15.3 澄清模板

```text
若缺失信息会显著改变结果或造成风险：
- 只询问当前最关键的 {{n}} 个问题。
- 说明需要该信息的简短原因。
- 已确认的信息不要重复询问。
- 可用选项时给出有限选项，并保留“其他”。
- 达到 {{max_rounds}} 轮仍无法获得时停止并给出替代路径。
```

### 15.4 摘要模板

```text
会话目标：{{goal}}
已确认事实：{{facts with source}}
有效约束：{{constraints}}
用户修正：{{corrections}}
工具结果：{{results with timestamp}}
待确认：{{pending}}
当前阶段：{{stage}}
停止条件：{{stop_conditions}}
```

## 16. 适用与不适用边界

### 适合多轮

- 需求逐步收集。
- 复杂配置和规划。
- 工具操作前确认。
- 教学与辅导。
- 需要用户审核中间结果的任务。

### 更适合单轮或表单

- 必填字段固定且很多。
- 输入可通过结构化界面收集。
- 用户只需要快速提交。
- 合规要求必须逐项确认。

### 不应由对话状态承担

- 身份认证。
- 权限授权。
- 密钥保存。
- 金融账本。
- 最终交易状态。
- 法定审计记录的唯一来源。

## 17. 评测多轮系统

单轮准确率不够。

应设计对话轨迹测试：

- 用户中途修正。
- 用户省略关键字段。
- 用户反复切换目标。
- 工具先失败后成功。
- 工具结果过期。
- 早期 assistant 给出错误信息。
- 历史含提示注入。
- 摘要后继续对话。
- 滑窗移除早期约束。
- 用户明确取消。

指标可以包括：

- 任务完成率。
- 平均澄清轮数。
- 重复提问率。
- 错误状态更新率。
- 未确认动作执行率。
- 工具误调用率。
- 摘要事实保留率。
- 取消和停止遵守率。
- 成本与端到端延迟。

## 18. 常见失败

### 18.1 无限追加历史

成本和污染持续增长。

### 18.2 把摘要当绝对真相

摘要本身也是模型输出，需要验证和纠错。

### 18.3 助手承诺被当作用户决定

“我建议周六”不等于用户已确认周六。

### 18.4 重复询问

状态没有记录已确认字段，体验迅速下降。

### 18.5 过度澄清

低风险任务也连续追问，用户无法完成目标。

### 18.6 关键缺失时猜测

订单、金额、日期或对象不明确仍执行动作。

### 18.7 没有停止条件

工具失败后循环重试，或用户取消后仍继续。

### 18.8 长期保存敏感信息

为了“记忆”而过度收集，增加隐私风险。

## 19. 调试清单

- [ ] 是否有显式、受 schema 约束的业务状态？
- [ ] 是否区分历史、状态、偏好和外部事实？
- [ ] 用户修正是否正确覆盖旧值？
- [ ] 是否避免把 assistant 历史当事实？
- [ ] 工具结果是否有来源、时间和有效期？
- [ ] 是否采用完整历史、滑窗、摘要或检索的合理组合？
- [ ] 摘要是否保留不确定性与用户修正？
- [ ] 是否测试上下文污染和跨轮注入？
- [ ] 澄清问题是否针对关键缺失？
- [ ] 是否避免重复询问已确认信息？
- [ ] 高风险动作是否二次确认并由代码鉴权？
- [ ] 是否有澄清轮数和工具重试上限？
- [ ] 用户取消后是否立即停止？
- [ ] 任务切换是否隔离状态？
- [ ] 是否只保存必要信息并支持过期删除？
- [ ] 是否使用完整对话轨迹做回归测试？

## 20. 练习与折叠答案

### 练习一：识别状态

用户说：“还是用上次那个地址，但这次周六送。”需要哪些状态处理？

<details>
<summary>参考答案</summary>

“上次那个地址”需要从经授权且有效的地址记录中解析，不能只依赖模型记忆。

“周六送”应规范化为明确日期，并根据当前日期和配送能力确认。

执行前展示地址摘要和日期供用户确认。

</details>

### 练习二：摘要错误

旧摘要写“用户预算 5000 元”，但原对话只是助手建议 5000 元。怎么办？

<details>
<summary>参考答案</summary>

删除该已确认事实，标记预算待确认。

修复摘要规则，禁止把助手建议记为用户决定，并加入对应回归轨迹。

</details>

### 练习三：是否澄清

用户说“把它删掉”，当前页面同时有草稿和已发布文章。

<details>
<summary>参考答案</summary>

必须澄清对象。

删除具有不可逆或高成本风险，不能根据最近提及内容盲猜。

还应在工具执行前进行权限检查和最终确认。

</details>

### 练习四：选择上下文策略

一个持续数月的学习助手应把全部历史放入每次请求吗？

<details>
<summary>参考答案</summary>

通常不应。

可以组合结构化学习状态、近期滑窗、经用户授权的长期偏好，以及按需检索的历史片段。

设置保留期限、删除能力和事实来源，并测试摘要遗漏。

</details>

### 练习五：停止条件

订单工具连续超时，应如何响应？

<details>
<summary>参考答案</summary>

按有限重试策略尝试，达到上限后停止。

明确说明未能查询，因此没有完成操作；保留当前状态，并提供稍后重试或人工渠道。

不得声称订单已取消或状态正常。

</details>

## 21. 本章小结

- 多轮对话的核心是状态机，而不是无限聊天记录。
- 完整历史、滑窗、摘要和检索记忆各有边界，通常需要组合。
- 摘要也是概率模型输出，必须有 schema、来源和校验。
- 上下文污染来自错误、过期、无关和恶意内容。
- 澄清应聚焦会改变结果或风险的关键缺失。
- 工具重试、澄清轮数、用户取消和高风险动作都需要停止条件。
- 所有策略应在目标模型与真实对话轨迹上评测。
