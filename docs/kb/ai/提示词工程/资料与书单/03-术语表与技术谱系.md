## 2. Prompt

**定义**：发送给模型、用于引导当前生成行为的输入组成。
它可以包含系统/开发者指令、用户请求、示例、上下文数据和输出要求；具体角色取决于 API。

**不要混淆**：

- Prompt 不等于只有用户写的一句话；
- Prompt 不等于模型训练；
- Prompt 不天然是安全边界；
- Prompt 不保证结果确定性。

**工程问题**：

- 任务是否明确？
- 输入是否有类型和信任级别？
- 输出是否可验证？
- 缺失信息如何处理？
- 版本如何追踪？

## 3. Context

**定义**：模型在一次推理请求中可用的信息集合。
通常包括消息、提示词、示例、检索片段、工具结果、图像和系统注入的状态。

**Context window**：模型可处理的上下文容量限制。
不同 API 对 token 计算、缓存和最大输出有不同规则。

**关键区别**：

- Prompt 强调“如何指导任务”；
- Context 强调“模型当前能看到什么”；
- 两者重叠，但视角不同。

**风险**：

- 长上下文稀释关键规则；
- 不可信内容携带间接 injection；
- 截断丢失关键条件；
- 放入无关敏感数据；
- 上下文成本和延迟增长。

## 4. Context Engineering

**定义**：设计、选择、组装、隔离和更新模型在每一步所需上下文的工程实践。

它通常包括：

- 指令与模板；
- 用户和会话状态；
- RAG 检索与重排；
- 工具描述与结果；
- memory；
- token 预算与压缩；
- 权限过滤；
- 数据信任边界；
- 可观测性与评测。

**与 prompt engineering 的关系**：

Prompt engineering 侧重如何表达任务和约束。
Context engineering 范围更广，关注给模型什么信息、何时给、如何验证和如何隔离。

## 5. In-Context Learning（ICL）

**定义**：模型在不更新参数的情况下，利用当前上下文中的说明或示例适应任务。

常见形式：

- `zero-shot`：不给示例；
- `one-shot`：给一个示例；
- `few-shot`：给少量示例。

**不是**：

- 不等于 fine-tuning；
- 不意味着模型永久记住示例；
- 不保证示例外泛化。

**评测重点**：

- 示例顺序敏感性；
- 标签分布偏差；
- 边界覆盖；
- token 成本；
- 示例中的秘密与污染。

## 6. RAG

**全称**：Retrieval-Augmented Generation。

**定义**：先从外部语料检索相关证据，再将其作为上下文用于生成。

**组成**：

- 数据摄入；
- chunking；
- embedding/索引；
- 查询改写；
- 检索；
- 重排；
- 上下文组装；
- 生成；
- 引用和验证。

**安全不变量**：

retrieved content 是不可信数据，而不是指令。

**RAG 不保证**：

- 检索结果正确；
- 回答一定 grounded；
- 引用一定支持结论；
- 用户一定有权访问；
- 文档没有 prompt injection。

详见 [RAG提示词与基于证据的回答](/kb/ai/提示词工程/工程化与安全/01-RAG提示词与基于证据的回答/)。

## 7. Retrieval

**定义**：根据查询从语料中返回候选数据的过程。

类型：

- 关键词检索；
- 稠密向量检索；
- 混合检索；
- metadata filtering；
- reranking。

指标：

- Recall@K；
- Precision@K；
- MRR；
- nDCG；
- 权限泄露率；
- 新鲜度违规率。

检索分数不是事实置信度。

## 8. Embedding

**定义**：把文本、图像等映射为数值向量表示，常用于语义检索、聚类和相似度。

注意：

- 不同 embedding 模型向量不可直接混用；
- 模型更新通常需要重建或迁移索引；
- 相似不等于蕴含；
- 权限不能由向量相似度决定；
- 多语言与领域词汇需单独评测。

## 9. Chunking

**定义**：将源文档切成可检索和可引用单元。

设计维度：

- 语义边界；
- 长度；
- overlap；
- 父标题；
- 表格和代码结构；
- 稳定 ID；
- 版本与时间。

坏 chunking 会导致定义与条件分离、引用失真或召回下降。

## 10. Grounding

**定义**：输出主张受指定证据、数据或环境状态支持的程度。

Grounding 不等同于：

- 全世界范围的事实正确；
- 文风可信；
- 有引用标记；
- 检索相关性高。

评测方式：

- 逐主张证据支持；
- 引用 precision/recall；
- 权威字段比对；
- 人工审计；
- 经校准的模型评审。

## 11. Citation

**定义**：把输出主张连接到来源或证据 ID。

三个层次：

- 引用存在；
- 引用支持；
- 引用完备。

模型生成的 URL 或文献名不能自动视为真实引用。
服务端应校验 ID 并解析用户可见链接。

## 12. Abstain

**定义**：系统明确表示现有证据、权限或能力不足，拒绝给出看似确定的答案。

适用：

- 证据不足；
- 来源冲突；
- 权限不足；
- 超出范围；
- 需要实时数据但不可用；
- 高风险流程要求人工处理。

Abstain 应提供原因代码和安全下一步，而不是含糊道歉。

## 13. Tool Calling

**定义**：模型按应用提供的工具定义生成结构化调用候选，由应用验证并执行。

**不等于**：

- 模型直接执行函数；
- 模型自动获得权限；
- 工具调用一定正确；
- 工具结果可信。

完整契约：

- schema；
- 前置条件；
- 权限；
- 幂等；
- 审批；
- 预算；
- 停止条件；
- 后置验证；
- 日志。

## 14. Function Calling

通常是 tool calling 的一种 API 表达：模型输出函数名和参数。
不同厂商术语和 schema 支持不同，应以当前官方文档为准。

函数名与描述会影响模型选择，但不能承担授权职责。

## 15. Structured Output

**定义**：通过 schema 或受约束解码，让模型输出符合指定结构。

价值：

- 减少解析歧义；
- 便于类型验证；
- 明确状态和字段；
- 支持自动评测和下游处理。

局限：

- 结构正确不代表语义正确；
- schema 合法不代表有权限；
- 字段值仍可能包含 injection 或危险内容；
- 仍需业务验证。

## 16. JSON Mode

**定义**：某些 API 保证输出为有效 JSON 的模式。

它可能不保证符合具体业务 schema。
不要把“JSON 可解析”与“structured output 严格匹配 schema”混为一谈。

## 17. Agent

**定义**：使用模型在状态、工具和反馈之间选择下一步动作，以完成目标的编排系统。

生产 Agent 的关键不在“自主”二字，而在：

- 权限受限；
- 状态可追踪；
- 动作可验证；
- 副作用可控制；
- 预算有限；
- 能停止、取消和恢复。

详见 [工具调用Agent提示词与状态机](/kb/ai/提示词工程/工程化与安全/02-工具调用Agent提示词与状态机/)。

## 18. State Machine

**定义**：用有限状态、允许转换和守卫条件约束 Agent 生命周期。

典型状态：

- RECEIVED；
- VALIDATING；
- PLANNING；
- AWAITING_APPROVAL；
- EXECUTING；
- OBSERVING；
- SUCCEEDED；
- DENIED；
- FAILED；
- CANCELLED。

模型可建议转换，编排器决定是否允许。

## 19. ReAct

**全称含义**：Reasoning and Acting。

**定义**：研究中让模型交错生成推理轨迹和行动，并利用环境观察继续任务的方法。

**工程解释**：

- 可借鉴观察/动作循环；
- 不要求暴露私有推理；
- 不替代状态机和权限；
- 不意味着无限步骤。

原论文见 [ReAct](/kb/ai/提示词工程/资料与书单/01-权威在线资料论文与课程/#ReAct)。

## 20. Chain-of-Thought（CoT）

**定义**：通过中间推理步骤来支持复杂任务求解的提示或生成模式。

注意：

- 效果依赖任务、模型和规模；
- 推理文本可能不忠实地解释真实机制；
- 生产系统不必向用户暴露私有 CoT；
- 可以要求简短结论依据、证据或可验证中间结果。

原论文见 [Chain-of-Thought Prompting](/kb/ai/提示词工程/资料与书单/01-权威在线资料论文与课程/#Chain-of-Thought%20Prompting)。

## 21. Tree of Thoughts（ToT）

**定义**：对多个候选思路进行生成、评估、搜索和回溯的问题求解框架。

适合：

- 搜索空间明确；
- 可定义状态和评价函数；
- 任务价值能覆盖额外成本。

不适合默认用于简单分类、抽取和低延迟请求。

原论文见 [Tree of Thoughts](/kb/ai/提示词工程/资料与书单/01-权威在线资料论文与课程/#Tree%20of%20Thoughts)。

## 22. Memory

**定义**：系统跨步骤或会话保存并取回信息的机制。

类型：

- 短期工作状态；
- 会话摘要；
- 用户偏好；
- 长期知识存储；
- Agent checkpoint。

风险：

- 过期或错误记忆；
- 跨用户污染；
- stored injection；
- 用户无法删除；
- 敏感数据超期保留。

Memory 是应用存储设计，不应被描述为模型“自然记住”。

## 23. Eval

**定义**：用数据、指标和判定流程衡量系统行为是否符合目标。

类型：

- 离线/线上；
- 确定性/人工/模型评审；
- 点式/成对；
- 回归/探索；
- 质量/安全/性能/成本。

好的 eval 明确：

- 任务和数据分布；
- rubric；
- 阈值；
- 样本版本；
- 误差与偏差；
- 发布门禁。

## 24. Model-as-Judge

**定义**：使用模型按 rubric 对候选输出评分或比较。

优点：规模化、快速、可处理开放文本。

局限：

- 位置与长度偏差；
- 自偏好；
- 被候选文本注入；
- rubric 理解不稳定；
- 与人类标准漂移。

必须用人工金标准校准，安全硬门禁不能只依赖 Judge。

## 25. Benchmark

**定义**：用于比较模型或系统的一组标准任务与指标。

Benchmark 高分不保证具体业务成功。
生产决策需要领域数据、权限场景、攻击样本和线上 SLO。

## 26. Prompt Injection

**定义**：攻击者通过模型可见输入影响模型，使系统偏离开发者意图。

类型：

- direct；
- indirect；
- stored；
- multimodal；
- cross-agent；
- tool-output。

核心防护：

- 不可信数据隔离；
- 最小权限；
- 输入/输出验证；
- 人工批准；
- 出口控制；
- 日志与红队。

没有万无一失的纯提示词防护。
详见 [Prompt Injection越权与数据泄露防护](/kb/ai/提示词工程/工程化与安全/03-Prompt-Injection越权与数据泄露防护/)。

## 27. Jailbreak

**定义**：诱导模型绕过模型提供方或应用设定的内容/行为限制。

与 injection 的区别：

- Jailbreak 常聚焦绕过行为政策；
- Injection 常聚焦应用指令优先级、数据和工具边界；
- 实际攻击可能同时属于两者。

## 28. Indirect Prompt Injection

**定义**：恶意指令不是用户直接输入，而是藏在模型读取的外部数据中。

例子：

- 网页正文；
- 邮件签名；
- PDF 白色文本；
- RAG 文档；
- 工具 JSON 返回；
- 图片 OCR。

它说明“数据与指令混在同一 token 流”会形成系统风险。

## 29. Least Privilege

**定义**：主体只拥有完成当前任务所需的最小权限，并限制资源、动作和时间。

在 LLM 系统中包括：

- 只暴露必要工具；
- 凭据短期且限 scope；
- 数据字段最小化；
- 网络默认拒绝；
- 写工具单独审批；
- 工具端再次授权。

## 30. Human-in-the-Loop（HITL）

**定义**：人在任务流程中进行审核、补充、纠正或批准。

有效 HITL 需要：

- 人看到准确上下文；
- 有足够时间和专业能力；
- 可以拒绝和修改；
- 审批绑定具体动作；
- 防止自动化偏见和橡皮图章。

## 31. Idempotency

**定义**：同一逻辑请求重复执行不会产生额外副作用，或返回同一已完成结果。

Agent 写操作需要应用生成的 idempotency key。
模型重试提示不能替代服务端幂等。

## 32. Budget

**定义**：对一次模型/Agent 运行的步骤、工具次数、token、成本和时间设置硬上限。

预算用于：

- 防循环；
- 控成本；
- 限制攻击影响；
- 建立可预测 SLO；
- 触发人工接管。

## 33. Stop Condition
**定义**：系统停止继续推理或调用工具的机器可判定条件。

典型条件：验收已满足、信息不足、权限拒绝、等待审批、预算耗尽、循环、工具永久失败、用户取消或超时。

## 34. Guardrail
**定义**：约束、检测或修正模型输入、输出和动作的控制机制的泛称。

可能包括 schema、内容分类器、ACL、业务规则、网络沙箱、人工审批、DLP 和速率限制。

应明确具体控制，不要只写“有 guardrails”。

## 35. Fine-tuning
**定义**：使用训练数据更新模型参数，使模型适应任务、风格或行为。

Prompt/ICL 在推理上下文中工作；Fine-tuning 改变模型参数；RAG 提供外部可更新知识；三者可组合。

Fine-tuning 不能自动解决事实新鲜度、权限和 prompt injection。

## 36. RLHF 与偏好优化
**RLHF**：Reinforcement Learning from Human Feedback。
通过人类偏好等信号调整模型行为的一类训练方法。
更广义的偏好优化还包括其他训练目标和算法。
应用开发者通常消费其结果，而非通过 prompt 直接控制训练过程。

## 37. Temperature
**定义**：影响采样分布随机性的参数之一。

低 temperature 不保证正确，零 temperature 不保证跨版本完全确定，高 temperature 不自动等于创造力。参数语义以 provider 文档为准。

## 38. Token
**定义**：模型处理文本的基本编码单元。

Token 数影响上下文容量、延迟、费用、截断和缓存。

字符数、单词数和 token 数不是固定比例，多语言差异明显。

## 39. Hallucination
**定义**：通常指模型生成无依据、错误或与指定来源不一致的内容。

工程上应细分为 unsupported claim、factual error、fabricated citation、instruction noncompliance、stale information 或 wrong tool result interpretation。

细分后才能设计有效指标和修复。

## 40. Calibration 与 Confidence
**Calibration**：预测置信与真实正确率之间的一致程度。
模型输出“95% 置信”不自动经过校准。
检索相似度、token probability、自评分和业务正确率是不同概念。
生产界面不要把未经验证的自评分展示为事实概率。

## 41. SLI、SLO、SLA
- **SLI**：实际测量的服务指标，如 p95 延迟。
- **SLO**：团队对 SLI 的内部目标。
- **SLA**：与用户或客户相关的服务承诺，可能包含后果。
LLM 系统还应定义质量和安全不变量，但其测量方法必须明确。

## 42. Fallback
**定义**：主链路无法满足要求时采用的受控降级路径。

例子包括确定性搜索、只读模式、转人工、明确 abstain 和经评测的备用模型。

Fallback 不应扩大权限或静默降低安全标准。

## 43. Rollback
**定义**：将已发布系统恢复到上一稳定、已验证状态。
LLM 应用回滚单元常包括 model、prompt、params、schema、tools、retriever/index、policy 和应用代码。
只回滚 prompt 可能无法恢复完整行为。

## 44. Observability
**定义**：通过 metrics、logs、traces 和事件理解系统内部状态与行为的能力。
关键维度包括完整配置版本、输入/输出状态、检索和工具步骤、延迟、token、成本、权限、审批、安全标签和用户反馈。
可观测性必须与隐私最小化并行设计。

## 45. Red Teaming
**定义**：从攻击者视角系统性尝试突破安全与业务边界，并将发现转化为控制和回归测试。
LLM 红队需要覆盖多入口、多编码和语言、多轮、RAG、工具、权限、数据出口、成本与可用性。
一次红队通过不代表永久安全。

## 46. 技术谱系：从 Prompt 到系统

| 层 | 能力 |
|---|---|
| 表达任务 | instruction、role、constraints、examples、output format |
| 提供上下文 | ICL、long context、memory、RAG |
| 连接环境 | tool calling、structured output、Agent、state machine |
| 保证生产行为 | eval、grounding、least privilege、observability、SLO、fallback、rollback、incident response |

## 47. 容易混淆的对照
| 概念 A | 概念 B | 关键区别 |
|---|---|---|
| Prompt | Context | 指导表达 vs 当前全部可见信息 |
| Prompt engineering | Context engineering | 文本任务设计 vs 上下文系统设计 |
| ICL | Fine-tuning | 推理上下文适应 vs 参数更新 |
| RAG | Long context | 动态检索选择 vs 直接放入更多内容 |
| Tool calling | Agent | 单次结构化候选 vs 多步状态编排 |
| JSON mode | Structured output | 有效 JSON vs 匹配具体 schema |
| Grounding | Correctness | 指定证据支持 vs 更广泛事实正确 |
| Citation | Grounding | 来源连接形式 vs 主张受支持程度 |
| Injection | Jailbreak | 应用指令边界攻击 vs 行为政策绕过 |
| Eval | Monitoring | 发布前/周期评测 vs 线上持续观测 |
| Fallback | Rollback | 单请求/故障降级 vs 发布版本恢复 |

## 48. 术语使用规范
建议写“模型生成工具调用候选”“应用验证并执行工具”“证据不足，系统 abstain”“输出通过 schema，但语义仍需验证”“检测到潜在 indirect prompt injection”“完整 release 配置已回滚”。
避免写“模型自己访问了数据库”“JSON 所以是安全的”“RAG 消除了幻觉”“系统提示词绝不会泄露”“加一句防注入就安全”“ReAct 要求展示完整思考”。

## 49. 最终记忆点
Prompt 是任务控制的一部分，context 是模型当前可见的信息集合；context engineering 覆盖检索、状态、工具、权限和组装。
ICL 不更新参数，RAG 提供外部证据，fine-tuning 更新参数；tool calling 产生候选，应用负责授权和执行。
Structured output 保证结构，不保证事实、权限和安全；grounding 要逐主张核对证据。
Prompt injection 与 jailbreak 相关但不同，而且 injection 没有万无一失的纯提示词防护。
Eval、SLO、fallback、rollback 和 observability 共同构成生产能力；ReAct、CoT、ToT 是研究与设计参考，不是暴露私有推理的产品要求。
