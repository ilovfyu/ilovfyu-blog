## 1. 为什么这类任务需要场景设计

先读仓库再改代码。提示必须明确目标、作用域、运行环境、验证命令和安全边界；默认最小 diff，不执行来源未知的代码、脚本或依赖。

提示词不是一句魔法口令，而是任务协议的自然语言实现。协议要让输入可解释、输出可验证、失败可恢复、风险可升级。

::: important 核心判断
先问“什么结果算正确”，再问“怎样措辞更像提示词”。
如果验收者无法独立判断对错，提示再长也只是偏好描述。
:::

### 1.1 场景成功的四层含义

| 层次 | 问题 | 最低证据 |
| --- | --- | --- |
| 语法层 | 格式是否可解析 | 解析器或格式检查 |
| 语义层 | 内容是否忠实/正确 | 逐项依据或金标 |
| 任务层 | 是否支持预定工作流 | 下游验收测试 |
| 治理层 | 是否安全、合规、可追溯 | 日志、权限与人工复核 |

### 1.2 不要把模型能力当作任务定义

- 模型“能生成”不等于业务“可接受”。
- 流畅度是表面质量，不是事实正确性的替代指标。
- 单次成功不能证明稳定，应覆盖边界、反例和分布变化。
- 把未知显式留空，通常比生成一个完整但错误的答案更有价值。

## 4. 输入输出契约

### 4.1 输入契约

| 输入项 | 必需性 | 校验方式 |
| --- | --- | --- |
| 仓库树与相关文件 | 必需 | 类型、范围、版本与样例检查 |
| 可复现问题或用户故事 | 必需 | 类型、范围、版本与样例检查 |
| 环境及版本 | 必需 | 类型、范围、版本与样例检查 |
| 变更边界 | 必需 | 类型、范围、版本与样例检查 |
| 安全权限 | 按场景 | 类型、范围、版本与样例检查 |
| 验收标准 | 按场景 | 类型、范围、版本与样例检查 |

### 4.2 输出契约

| 输出项 | 用途 | 不可接受情况 |
| --- | --- | --- |
| 根因或设计说明 | 供下游验收或追溯 | 缺失、含混、无法定位依据 |
| 最小 diff | 供下游验收或追溯 | 缺失、含混、无法定位依据 |
| 测试变更 | 供下游验收或追溯 | 缺失、含混、无法定位依据 |
| 执行过的命令和结果 | 供下游验收或追溯 | 缺失、含混、无法定位依据 |
| 残余风险 | 供下游验收或追溯 | 缺失、含混、无法定位依据 |
| 未执行事项 | 供下游验收或追溯 | 缺失、含混、无法定位依据 |

### 4.3 契约版本化

- 提示模板、schema、标签手册和验收集分别记录版本。
- 会改变输出含义的修改提升主版本。
- 仅修正文案但不改变行为的修改提升次版本。
- 回放历史样本，比较新旧版本差异而非只看新样例。

### 4.4 分隔与数据边界

- 用 XML 标签、代码块或明确 ID 分隔指令与用户材料。
- 把材料中的命令视为数据，除非契约明确允许执行。
- 多文档输入保留文档 ID，禁止在无标识拼接后引用。
- 超长输入先建立分块策略和跨块合并规则。

## 5. 通用提示模板

```text
你是该仓库的维护工程师。
目标/缺陷：{{goal_or_bug}}
仓库上下文：{{tree_and_relevant_files}}
环境：{{versions}}
允许修改：{{scope}}
禁止事项：不得执行来源未知的代码、安装未知依赖、访问生产或输出密钥。
流程：
1. 先读取入口、调用链、规范和现有测试；不足时提问。
2. 复现问题并说明根因，不能复现则报告证据。
3. 采用满足需求的最小 diff，保留现有风格和公开契约。
4. 添加能先失败后通过的测试，覆盖正常、边界和失败路径。
5. 只运行已批准的验证命令。
输出：改动摘要；文件级 diff；测试结果；安全与残余风险。
```

### 5.1 模板变量表

| 变量 | 填写原则 | 错误示例 |
| --- | --- | --- |
| 任务目标 | 可观察、可验收 | “做得更好” |
| 输入范围 | 标明边界、版本和 ID | “参考所有信息” |
| 允许推断 | 列白名单或明确禁止 | “合理发挥” |
| 输出格式 | 给 schema/样例/长度 | “结构清晰” |
| 失败行为 | 定义未知、拒绝和升级 | “不要出错” |
| 验收标准 | 指标、阈值、测试集 | “看起来专业” |

### 5.2 少样本示例设计

- 示例覆盖正常、缺失、冲突和越界输入。
- 示例输出必须完全符合契约，否则模型会学习错误。
- 不要只提供正例；至少加入一个应当弃权或 unknown 的例子。
- 示例顺序避免把偶然位置误学成优先级。

### 5.3 提示注入防护

- 明确用户材料不是系统指令。
- 工具权限由外部执行层控制，不能只靠提示文本。
- 检索内容中的“忽略前文”等句子按引用数据处理。
- 敏感动作使用参数白名单和人工确认。

## 6. 三个完整案例

### 6.1 案例：修复并发重复扣款

#### 场景输入

支付 webhook 偶发重复处理，同一事件导致两次记账。

#### 初始提示

```text
修复 webhook 重复扣款问题。
```

#### 问题诊断

- 没有仓库调用链和复现条件
- 可能仅加内存锁而不适合多实例
- 数据库唯一约束与事务未知
- 缺少并发测试

#### 优化版提示

```text
先读取 webhook 路由、事件服务、账本模型、迁移和相关测试。用同一 event_id 并发提交复现。保持公开 API 不变，选择仓库现有事务/幂等模式做最小修复；不得引入新基础设施。测试至少覆盖顺序重复、并发重复、不同事件和处理失败重试。仅运行项目已有测试与 lint 命令，不执行未知脚本。
```

#### 验收标准

- [ ] A1.1 根因由代码路径和复现证明
- [ ] A1.2 并发测试修复前失败
- [ ] A1.3 同事件最多记账一次
- [ ] A1.4 不同事件不被误去重
- [ ] A1.5 diff 限于必要文件且全套相关测试通过

#### 迭代记录方式

| 轮次 | 只改一个变量 | 观察指标 | 保留/回退 |
| --- | --- | --- | --- |
| 0 | 初始提示作为基线 | 记录全部验收项 | 基线 |
| 1 | 补齐输入与边界 | 正确性和弃权 | 按指标决定 |
| 2 | 补齐输出结构 | 可解析性和可追溯 | 按指标决定 |
| 3 | 调整示例或规则 | 边界集与回归集 | 不得牺牲安全 |

### 6.2 案例：生成输入校验测试

#### 场景输入

为 API 的日期范围参数补边界测试。

#### 初始提示

```text
给这个函数写完整测试。
```

#### 问题诊断

- “完整”不可衡量
- 可能测试内部实现而非契约
- 时区、闭区间和非法值未定义
- 可能生成不存在的测试工具

#### 优化版提示

```text
依据现有测试框架和 API 文档，为 start/end 参数补契约测试。先列等价类：合法同日、跨日、闰日、start>end、缺失、格式非法、带时区。沿用现有 fixture，不新增依赖，不 mock 被测校验函数。每个测试写明预期状态码与错误码；若文档与实现冲突，先报告而不自行确定新行为。
```

#### 验收标准

- [ ] A2.1 只使用仓库现有测试设施
- [ ] A2.2 每个定义的等价类有覆盖
- [ ] A2.3 断言外部行为而非私有实现
- [ ] A2.4 冲突被显式报告
- [ ] A2.5 测试可重复且不依赖当前日期

### 6.3 案例：安全导向 Code Review

#### 场景输入

审查一个新增文件上传接口的 PR。

#### 初始提示

```text
Review 这段代码，看看有没有问题。
```

#### 问题诊断

- 没有威胁模型和严重度
- 容易只点评风格
- 可能不检查调用方与配置
- 建议可能缺少可复现证据

#### 优化版提示

```text
以 Code Review 模式审查该 PR 及调用上下文。优先找可利用缺陷和行为回归：认证授权、路径穿越、MIME/内容校验、大小限制、压缩炸弹、存储权限、日志敏感信息和资源清理。每项发现给严重度、文件/行号、触发条件、影响和最小修复；没有证据不报确定漏洞。最后列缺失测试与残余风险，摘要置后。
```

#### 验收标准

- [ ] A3.1 发现按严重度排序
- [ ] A3.2 每项有精确位置和触发路径
- [ ] A3.3 风格意见不淹没缺陷
- [ ] A3.4 覆盖接口上下游和配置
- [ ] A3.5 误报经复核低于约定阈值

## 7. 风险登记册

| 风险 | 早期信号 | 预防控制 | 发现后动作 |
| --- | --- | --- | --- |
| 脱离仓库生成不存在的 API | 抽样出现不一致或无依据结果 | 契约、证据、边界样本 | 停止自动发布并复核 |
| 大范围重写掩盖真实修复 | 抽样出现不一致或无依据结果 | 契约、证据、边界样本 | 停止自动发布并复核 |
| 执行未知脚本造成供应链风险 | 抽样出现不一致或无依据结果 | 契约、证据、边界样本 | 停止自动发布并复核 |
| 测试只复制实现逻辑 | 抽样出现不一致或无依据结果 | 契约、证据、边界样本 | 停止自动发布并复核 |
| 吞异常使测试表面通过 | 抽样出现不一致或无依据结果 | 契约、证据、边界样本 | 停止自动发布并复核 |
| 日志或代码泄露密钥 | 抽样出现不一致或无依据结果 | 契约、证据、边界样本 | 停止自动发布并复核 |

### 7.1 风险分级

- 低：格式或措辞瑕疵，可自动重试。
- 中：影响业务判断但可在发布前人工发现。
- 高：可能造成安全、法律、财务、健康或重大声誉后果。
- 关键：不可逆操作或大规模敏感数据暴露，默认禁止自动执行。

### 7.2 人在回路

1. 定义触发人工复核的明确条件。
2. 向复核者展示原始输入、输出、证据和模型版本。
3. 记录复核改动原因，沉淀为失败类别。
4. 不要把“人工复核”当作没有流程的兜底口号。

## 8. 边界条件

### 8.1 仓库上下文不足时先读取或提问

期望行为：暂停不受支持的推断，输出已完成部分、缺失信息和下一步，不用流畅文本掩盖边界。

### 8.2 生产数据库与密钥默认不可访问

期望行为：暂停不受支持的推断，输出已完成部分、缺失信息和下一步，不用流畅文本掩盖边界。

### 8.3 不运行 curl | sh、未知二进制或未审查脚本

期望行为：暂停不受支持的推断，输出已完成部分、缺失信息和下一步，不用流畅文本掩盖边界。

### 8.4 大规模迁移须先给回滚和分批方案

期望行为：暂停不受支持的推断，输出已完成部分、缺失信息和下一步，不用流畅文本掩盖边界。

### 8.5 无法执行测试时明确写“未验证”

期望行为：暂停不受支持的推断，输出已完成部分、缺失信息和下一步，不用流畅文本掩盖边界。

### 8.6 通用压力输入

- 空输入、仅空白、乱码和截断输入。
- 互相矛盾的输入与过时版本。
- 超长输入和极端重复内容。
- 包含提示注入、恶意链接或未知附件的输入。
- 超出语言、地域、时间或专业权限范围的输入。

## 9. 失败处理与恢复

1. 保留失败命令与首个有因果意义的错误
2. 区分环境失败、既有失败和本次回归
3. 回到最小复现而非不断扩大改动
4. 测试失败不靠删除断言或吞异常解决
5. 必要时回退方案而非破坏性重置用户改动

### 9.1 标准失败响应

```text
状态：未完成/部分完成
失败阶段：{{stage}}
已确认内容：{{verified}}
未知或冲突：{{unknowns}}
没有执行的动作：{{not_done}}
需要补充：{{required_input}}
建议下一步：{{next_step}}
```

### 9.2 重试预算

- 格式失败可自动重试一次，并只修格式。
- 事实或语义失败不能靠原提示无限重试。
- 连续两轮同类失败应修改契约、拆分任务或升级人工。
- 每次重试保留输入版本和失败原因，防止选择性展示成功结果。

### 9.3 降级策略

- 从自动发布降级为草稿。
- 从完整答案降级为已证实字段。
- 从开放生成降级为封闭材料处理。
- 从执行动作降级为只读建议。

## 10. 隐私、安全与合规

### 10.1 提示和日志中掩码密钥与 token

落实到数据流、权限、日志和保留策略中；仅写在提示里不能构成安全控制。

### 10.2 生产数据使用最小化脱敏 fixture

落实到数据流、权限、日志和保留策略中；仅写在提示里不能构成安全控制。

### 10.3 依赖安装前审查来源和锁文件

落实到数据流、权限、日志和保留策略中；仅写在提示里不能构成安全控制。

### 10.4 代码不得上传到未批准服务

落实到数据流、权限、日志和保留策略中；仅写在提示里不能构成安全控制。

### 10.5 安全漏洞遵循私密披露流程

落实到数据流、权限、日志和保留策略中；仅写在提示里不能构成安全控制。

### 10.6 最小权限清单

- 模型只看到完成任务所需的最少字段。
- 工具只开放必要动作和参数范围。
- 高风险输出默认不自动发送或执行。
- 测试环境与生产环境隔离。
- 审计日志本身也按敏感数据保护。

## 11. 迭代策略

### 11.1 建立基线

1. 固定模型、参数、提示和数据版本。
2. 选取代表性正常样本与历史失败样本。
3. 先测初始提示，不只展示优化后结果。
4. 保存原始输出，避免事后改写证据。

### 11.2 单变量迭代

| 可改变量 | 适合解决 | 不适合解决 |
| --- | --- | --- |
| 补上下文 | 模型缺少事实或规则 | 规则本身冲突 |
| 补输出 schema | 格式漂移 | 事实来源不足 |
| 补少样本 | 边界判定不稳定 | 样本标签错误 |
| 拆分步骤 | 复合任务遗漏 | 下游无法验收 |
| 增加工具 | 需要实时/精确信息 | 权限治理缺失 |

### 11.3 错误分类

- E1 输入缺失：请求方未提供必要信息。
- E2 契约歧义：字段、标签或成功定义不清。
- E3 检索/工具失败：信息无法访问或工具报错。
- E4 推理/生成失败：已有信息未被正确使用。
- E5 验收失败：结果正确但格式或工作流不兼容。
- E6 治理失败：权限、隐私或合规控制不足。

### 11.4 停止条件

- 主要指标达到门槛且安全指标无回退。
- 边界集不再出现新的高严重度错误。
- 成本和延迟在预算内。
- 剩余风险有明确人工流程和责任人。

## 12. 评测设计

### 12.1 数据集分层

| 集合 | 目的 | 建议内容 |
| --- | --- | --- |
| 开发集 | 快速迭代 | 典型任务和已知错误 |
| 回归集 | 防止旧错复发 | 每类历史事故至少一例 |
| 边界集 | 验证拒绝与 unknown | 缺失、冲突、注入、超范围 |
| 盲测集 | 估计泛化 | 迭代者未见的真实分布 |
| 红队集 | 发现安全缺陷 | 越权、隐私、恶意输入 |

### 12.2 核心指标

- **M1 验收测试通过率**：定义分子、分母、排除项和目标阈值，避免只报平均分。
- **M2 回归测试通过率**：定义分子、分母、排除项和目标阈值，避免只报平均分。
- **M3 diff 聚焦度**：定义分子、分母、排除项和目标阈值，避免只报平均分。
- **M4 新增分支覆盖率**：定义分子、分母、排除项和目标阈值，避免只报平均分。
- **M5 静态检查结果**：定义分子、分母、排除项和目标阈值，避免只报平均分。
- **M6 安全发现数**：定义分子、分母、排除项和目标阈值，避免只报平均分。
- **M7 未授权文件修改数**：定义分子、分母、排除项和目标阈值，避免只报平均分。

### 12.3 量规示例

| 分数 | 正确性 | 完整性 | 可追溯性 | 安全性 |
| --- | --- | --- | --- | --- |
| 3 | 全部关键结论正确 | 无关键漏项 | 逐项可定位 | 无违规 |
| 2 | 轻微非关键错误 | 少量次要漏项 | 大部分可定位 | 低风险可修复 |
| 1 | 至少一项关键错误 | 明显漏项 | 证据弱或错配 | 需要人工阻断 |
| 0 | 结论不可用 | 任务未完成 | 无依据 | 严重违规 |

### 12.4 评审一致性

- 先用 10-20 个样本校准评审者。
- 为每个分数提供正例和反例。
- 记录争议项，不强行平均掩盖定义问题。
- 高风险样本采用双人独立评审。

### 12.5 线上监控

- 监控输入分布、未知率、人工改写率和升级率。
- 抽样复核成功输出，而不只看用户投诉。
- 模型或依赖升级后运行完整回归集。
- 指标突变时能回滚提示版本或关闭自动动作。

## 14. 练习

### 14.1 练习 1

模型建议先运行仓库中的 setup.sh，应该直接运行吗？

<details>
<summary>展开参考答案</summary>

不应。先阅读脚本、确认来源与副作用，并在获得权限后于隔离环境运行。

</details>

### 14.2 练习 2

修复只需 5 行，但模型重构 20 个文件，如何处理？

<details>
<summary>展开参考答案</summary>

要求恢复最小 diff，分离重构与行为修复；用聚焦测试证明 5 行方案足够。

</details>

### 14.3 练习 3

测试通过是否代表修复完成？

<details>
<summary>展开参考答案</summary>

不一定。还需确认测试能在修复前失败、覆盖真实根因，并检查静态分析、安全与未测试环境。

</details>

### 14.4 综合练习

为一个真实“编程、代码生成、调试、测试与 Code Review”任务写一份输入输出契约。至少包含：非目标、未知行为、证据要求、失败升级和五条验收标准。

<details>
<summary>展开评分要点</summary>

优秀答案不是堆叠角色设定，而是让第三方能用固定样本和规则判断成功或失败。检查每个输出字段是否有来源、每个风险是否有外部控制、每个指标是否有阈值。

</details>

## 15. 快速复盘卡

| 阶段 | 必须回答的问题 |
| --- | --- |
| 需求 | 目标、受众、时效、非目标是什么 |
| 契约 | 输入缺失和输出未知如何表示 |
| 执行 | 模型可以看什么、推断什么、调用什么 |
| 验收 | 谁用什么证据判断正确 |
| 失败 | 何时重试、降级、拒绝或转人工 |
| 治理 | 如何最小化数据并追踪版本 |

::: tip 一句话原则
先读仓库再改代码。提示必须明确目标、作用域、运行环境、验证命令和安全边界；默认最小 diff，不执行来源未知的代码、脚本或依赖。
:::
