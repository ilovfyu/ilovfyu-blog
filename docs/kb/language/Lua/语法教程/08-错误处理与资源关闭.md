## 错误对象

`error(value [, level])` 抛出错误且不返回。Lua 自身通常抛字符串，但程序可抛除 nil 外的任意值。库边界最好统一错误对象约定，否则日志和调用方处理会混乱。

```lua
local function positive(value)
  if value <= 0 then error("value must be positive", 2) end
  return value
end
```

`level=2` 把错误位置归因到调用者，适合参数检查辅助函数；0 不添加位置信息。

## assert

`assert(value, message, ...)` 在 value 为假时抛错，否则返回全部参数：

```lua
local file, err = io.open("config.txt", "r")
file = assert(file, err)
```

对于预期会失败的用户输入或网络结果，不应全部用 assert；应返回 `nil, error` 让调用方决定。

## pcall

`pcall(fn, ...)` 保护函数调用。成功返回 `true, fn 的结果...`，失败返回 `false, error_object`：

```lua
local ok, result = pcall(function()
  return positive(-1)
end)

if not ok then
  io.stderr:write("failed: ", tostring(result), "\n")
end
```

pcall 只捕获调用期间错误。语法错误要先通过 `load` 返回值处理，或把 `loadfile` 放入受保护调用。

## xpcall 与 traceback

`xpcall(fn, message_handler, ...)` 在栈展开前调用 message handler，适合生成 traceback：

```lua
local function traceback(err)
  return debug.traceback(tostring(err), 2)
end

local ok, result = xpcall(function()
  error("boom")
end, traceback)

if not ok then io.stderr:write(result, "\n") end
```

message handler 自身应短小可靠。它不处理内存分配错误、finalizer 错误或 handler 自己引发的某些失败。生产环境可由宿主提供结构化错误记录。

## 错误返回还是异常

惯例建议：

| 场景 | 方式 |
|---|---|
| 可预期运行失败，如文件不存在 | `nil, message` 或 `false, message` |
| 调用契约违反、内部不变量破坏 | `error` / `assert` |
| 应用边界统一收口 | `xpcall` + traceback |

不要在每一层 pcall 后忽略错误；保护调用应位于真正能恢复、转换或记录错误的边界。

## To-be-closed 变量

`local resource &lt;close&gt; = value` 在变量离开作用域时关闭 value，包括正常结束、return、break、goto 和错误展开。value 必须是 false/nil，或拥有 `__close` 元方法的值。

标准文件句柄支持关闭协议：

```lua
local function first_line(path)
  local file &lt;close&gt; = assert(io.open(path, "r"))
  return file:read("l")
end
```

自定义资源：

```lua
local Resource = {}
Resource.__index = Resource

function Resource.new(name)
  return setmetatable({name = name, closed = false}, Resource)
end

function Resource:__close(err)
  if not self.closed then
    self.closed = true
    print("closing", self.name, "because", err)
  end
end

do
  local resource &lt;close&gt; = Resource.new("demo")
  print("using", resource.name)
end
```

`__close(value, err)` 的第二个参数在错误展开时是原错误对象，正常关闭通常为 nil。关闭方法若抛新错误，错误传播会变复杂；清理应尽量幂等、短小。

同一声明列表最多一个 `&lt;close&gt;` 变量。关闭顺序与作用域退出规则相关，设计多资源依赖时按获取顺序和逆序清理要求编写小块。

## `&lt;close&gt;` 与 `__gc`

`&lt;close&gt;` 是确定性的词法作用域清理；`__gc` 由垃圾回收器在不可预测时间运行。文件、锁、事务等资源优先 `&lt;close&gt;` 或显式关闭，`__gc` 只能作为兜底。

## warn

`warn(...)` 发送警告，不改变控制流。独立解释器中的警告输出可受选项控制；嵌入场景可由宿主设置 warning function。不要用 warn 替代错误返回。

## 常见错误

- pcall 成功后只取一个结果，意外丢弃函数其他返回值。
- 捕获错误后静默忽略，程序继续处于无效状态。
- 用 assert 处理所有用户可恢复错误。
- 依赖 `__gc` 及时关闭文件。
- `__close` 不幂等，或清理期间执行大量可能失败的工作。
- 在受限代码环境暴露 debug 库，允许绕过封装。

## 练习

1. 写安全除法，参数错误抛错，除数为零返回 nil/message。
2. 用 xpcall 为嵌套调用生成 traceback。
3. 写计时资源，在 `__close` 中输出作用域耗时。
4. 比较正常 return 和 error 时 `__close` 接收的第二个参数。
