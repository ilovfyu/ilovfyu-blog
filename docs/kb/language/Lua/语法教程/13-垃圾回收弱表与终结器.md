## 可达性模型

Lua 自动管理 string、table、function、thread、full userdata 和内部结构。对象不再能从 Lua 根集合访问时可被回收；具体回收时间不确定。C registry 中的引用属于根，忘记释放 registry 引用会阻止对象回收。

GC 只管理 Lua 所知的内存。文件描述符、socket、数据库事务等外部资源必须优先使用显式 close 或 `&lt;close&gt;`。

## 两种 GC 模式

Lua 5.5 支持 incremental 和 generational：

- **增量模式**：mark-and-sweep 周期拆成小步骤，与程序执行交错。
- **分代模式**：频繁 minor collection 处理新对象，达到条件后切换 major collection。

Lua 5.5 的重要变化是 generational 模式的 major collections 也增量执行，减少一次 major GC 的长停顿风险。默认参数适合多数程序，调整前必须在真实分配模式上测量吞吐、暂停和内存。

## collectgarbage

常用操作：

```lua
print(collectgarbage("count")) -- 近似 Lua 内存 KiB
collectgarbage("collect")      -- 完整回收周期
collectgarbage("step", 100)    -- 推进一步
collectgarbage("stop")
collectgarbage("restart")
collectgarbage("incremental")
collectgarbage("generational")
```

频繁手动 `collect` 往往降低性能；`count` 也不代表进程全部内存。嵌入程序、C 库、allocator 和 OS 都可能持有额外内存。

## 弱表

metatable 的 `__mode` 控制弱引用：

```lua
local weak_values = setmetatable({}, {__mode = "v"})
local weak_keys = setmetatable({}, {__mode = "k"})
local weak_both = setmetatable({}, {__mode = "kv"})
```

若对象只剩弱引用，GC 可收集它并删除对应条目。弱值 cache：

```lua
local cache = setmetatable({}, {__mode = "v"})

local function intern(key, factory)
  local value = cache[key]
  if value == nil then
    value = factory(key)
    cache[key] = value
  end
  return value
end
```

弱缓存不保证命中；调用方必须允许对象随时被重建。数字、light C function 等不可回收值不会因弱引用消失。字符串虽然受 GC 管理，但按值构造/相等，官方定义中不会像显式构造对象那样从弱表移除。

## Ephemeron table

弱键强值表是 ephemeron：只有 key 在表外可达时，value 才因该条目被视为可达。这适合给对象附加元数据，不让元数据值反向把 key 保活。

```lua
local metadata = setmetatable({}, {__mode = "k"})
local object = {}
metadata[object] = {created_at = os.time()}
```

当 object 没有其他强引用，键值对最终可被移除。

## `__gc` 终结器

table 和 full userdata 可有 `__gc`。对象在关联 metatable 时，metatable 必须已经含 `__gc`，它才被标记为需要终结：

```lua
local mt = {
  __gc = function(object)
    -- 只做最小、不可 yield 的兜底清理
    object.closed = true
  end,
}

local object = setmetatable({closed = false}, mt)
```

finalizer 时机不可预测、不可 yield、不能运行 GC。finalizer 错误只生成 warning，不按普通错误传播。对象会暂时复活以供 finalizer 使用；若存入全局会永久复活，行为复杂且应避免。

关闭 Lua state 时，已标记对象的 finalizer 按反向标记顺序调用。不要让不同 finalizer 依赖脆弱的全局资源仍然存在。

## `__gc` 与 `__close` 的选择

| 机制 | 时机 | 适用场景 |
|---|---|---|
| 显式 `close()` | 调用点 | 所有重要外部资源 |
| `&lt;close&gt;` / `__close` | 词法作用域退出 | 文件、锁、事务、临时资源 |
| `__gc` | GC 认为对象死亡后 | 遗漏关闭的最后兜底 |

确定性资源管理不能依赖 GC。

## 大数组与 Lua 5.5

Lua 5.5 改进 table 的 array representation，官方发布说明称大型数组内存可减少约 60%。这是实现层优化，不改变 sequence 语义；仍应使用连续 integer keys，并通过测量判断实际收益。`table.create` 可进一步减少已知规模数组构建时的扩容。

## 常见错误

- 看到进程 RSS 未下降就断言 Lua GC 泄漏。
- 每轮业务都调用完整 collect。
- 弱值 cache 假定值永远存在。
- 用弱 table 保存 string 并期待其按普通对象方式消失。
- 设置 metatable 后才添加 `__gc`。
- 用 `__gc` 替代文件/事务的确定性关闭。
- finalizer 执行复杂逻辑、yield 或复活对象。

## 练习

1. 构建弱值 cache，移除强引用后执行 GC 观察条目。
2. 用弱键表给 table 对象附加 metadata。
3. 比较 `&lt;close&gt;` 和 `__gc` 的触发确定性。
4. 对大量短命 table 分配分别基准 incremental 和 generational 模式。
