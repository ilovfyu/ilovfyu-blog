# 未来展望

> 上一章：[-最佳实践](/kb/language/JavaScript/核心语法/27-最佳实践/) · 下一章：[总索引](/kb/language/JavaScript/核心语法/README/)

## 学习目标

- 理解 ECMAScript 与 Web 平台如何标准化和演进
- 建立评估新语法、新 API 和兼容性的可靠方法
- 掌握渐进增强、功能检测、转译与 polyfill 的边界
- 认识 JavaScript 在类型、并发、服务端、WebAssembly 与 AI 时代的发展方向

## 1. JavaScript 不等于浏览器 API

JavaScript 通常指 ECMAScript 语言及其宿主环境提供的能力。`Array`、`Promise`、模块语法属于 ECMAScript；DOM、fetch、Web Worker 属于 Web 平台；Node.js 又提供文件系统、进程和服务端网络 API。

区分标准来源有助于判断兼容性：某个 Node.js 版本支持新语法，不代表目标浏览器支持同名 Web API；TypeScript 能通过类型检查，也不代表运行环境存在该能力。

## 2. 标准如何演进

ECMAScript 提案在 TC39 流程中逐步成熟，通常经历 Stage 0 到 Stage 4。只有进入 Stage 4 并纳入正式规范，才可视为标准语言特性。Web API 则由 WHATWG、W3C 等组织持续制定，并通过浏览器实现和互操作测试落地。

面对新特性应检查：

- 是否已经标准化，还是实验提案
- 目标浏览器或运行时的实际支持范围
- 是否需要语法转译或运行时 polyfill
- 语义是否稳定，失败时是否能降级
- 引入后对包体积、性能和维护成本的影响

不要仅凭一篇旧博客或浏览器厂商公告做生产决策。优先查规范、MDN、Can I Use、Node.js 文档和目标运行时发布说明。

## 3. 渐进增强与功能检测

未来友好的应用先提供可靠基础能力，再对支持新 API 的环境增强体验。

```js
async function copyText(text) {
  if (navigator.clipboard?.writeText && window.isSecureContext) {
    await navigator.clipboard.writeText(text);
    return;
  }

  const textarea = document.createElement("textarea");
  textarea.value = text;
  textarea.style.position = "fixed";
  textarea.style.opacity = "0";
  document.body.append(textarea);
  textarea.select();
  const copied = document.execCommand("copy");
  textarea.remove();
  if (!copied) throw new Error("当前环境无法复制文本");
}
```

功能存在不一定代表行为完全可用，还可能受 HTTPS、安全权限、用户手势和设备能力约束。检测、调用、捕获失败和降级应形成完整路径。

## 4. 转译、polyfill 与目标环境

转译器可把部分新语法转换为旧语法，例如箭头函数或可选链；polyfill 则补充运行时缺失的对象和方法，例如旧环境中的 `Promise`。两者不是一回事。

某些能力无法被完整 polyfill：

- Worker 和 Service Worker 依赖浏览器线程与生命周期模型
- 流、导航和图形 API 依赖宿主实现
- 私有字段等语言语义只能近似转换，可能有性能和行为差异
- 新协议和安全能力需要浏览器与服务器共同支持

现代构建应从明确的目标环境出发，避免把所有历史 polyfill 无差别发送给现代浏览器。依赖库最好声明支持范围，应用通过自动化兼容性测试验证承诺。

## 5. 语言表达力继续增强

JavaScript 的演进方向通常不是彻底重写语言，而是补齐高频表达、改善安全性并减少样板代码。近年来的能力包括私有字段、顶层 await、逻辑赋值、`Array.prototype.at()`、不可变数组方法和更完善的国际化 API。

不可变数组方法适合状态更新，不修改原数组：

```js
const scores = [30, 10, 20];
const sorted = scores.toSorted((a, b) => a - b);
const updated = scores.with(1, 99);

console.log(scores);  // [30, 10, 20]
console.log(sorted);  // [10, 20, 30]
console.log(updated); // [30, 99, 20]
```

`Object.groupBy()` 可表达常见分组需求：

```js
const tasks = [
  { title: "测试", done: true },
  { title: "文档", done: false },
  { title: "发布", done: false }
];

const grouped = Object.groupBy(tasks, (task) => task.done ? "done" : "open");
console.log(grouped.open.map((task) => task.title));
```

使用这些 API 前应依据项目目标环境确认支持情况，而不是因“语法更现代”就立即替换稳定代码。

## 6. 类型生态

JavaScript 保持动态类型，但 TypeScript、JSDoc 和编辑器语言服务让大型项目获得静态分析能力。类型系统可以发现接口不匹配、辅助重构和生成文档，却不能替代运行时校验。

纯 JavaScript 项目也可使用 JSDoc：

```js
/**
 * @typedef {{ id: string, price: number, quantity: number }} LineItem
 */

/**
 * @param {LineItem[]} items
 * @returns {number}
 */
export function total(items) {
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}
```

长期趋势是工具更深入理解代码，而运行时边界仍通过模式校验、协议和测试保证。

## 7. 并发与调度

JavaScript 主线程仍以事件循环为核心，但平台不断增加更精细的并发与调度能力：Worker、流、AbortSignal、优先级调度、OffscreenCanvas、AudioWorklet 和 WebGPU 等让应用能处理更重任务。

统一取消信号可组合多个异步操作：

```js
async function loadPageData(signal) {
  const requests = [
    fetch("/api/profile", { signal }),
    fetch("/api/feed", { signal })
  ];
  const responses = await Promise.all(requests);
  if (responses.some((response) => !response.ok)) {
    throw new Error("页面数据加载失败");
  }
  return Promise.all(responses.map((response) => response.json()));
}

const controller = new AbortController();
loadPageData(controller.signal).catch((error) => {
  if (error.name !== "AbortError") console.error(error);
});
// 路由变化时：controller.abort();
```

未来并发设计依旧应优先结构化生命周期：任务由谁创建、何时取消、结果是否过时、资源如何释放。

## 8. WebAssembly 与 JavaScript 协作

WebAssembly（Wasm）为浏览器和其他运行时提供可移植的低级字节码，适合图像、音视频、压缩、科学计算、游戏和现有原生库迁移。它不是 JavaScript 的替代品：DOM、网络、界面状态和业务编排通常仍由 JavaScript 负责。

```js
async function loadWasm(url, imports = {}) {
  const response = await fetch(url);
  if (!response.ok) throw new Error(`Wasm 加载失败：${response.status}`);

  const { instance } = await WebAssembly.instantiateStreaming(response, imports);
  return instance.exports;
}

loadWasm("./math.wasm").then(({ add }) => console.log(add(2, 3)));
```

服务端需以正确的 `application/wasm` 类型响应。Wasm 与 JavaScript 频繁跨边界调用也有成本，应把足够大的计算单元交给 Wasm，并用基准测试判断收益。

## 9. 多运行时 JavaScript

JavaScript 已覆盖浏览器、Node.js、边缘运行时、桌面、移动和嵌入式环境。Web 标准 API 正逐渐成为多运行时共同接口，例如 fetch、URL、Web Streams、Web Crypto 和 AbortController。

编写可移植模块时：

- 把业务逻辑与 DOM、文件系统等宿主 API 分离
- 通过参数注入网络、时钟、随机数和持久化能力
- 使用标准 API，但确认各运行时的细节和版本支持
- 通过包 `exports` 提供必要的条件入口，避免运行时探测散落各处
- 不假设边缘运行时拥有完整 Node.js API 或持久进程

## 10. AI 与本地计算

生成式 AI 和浏览器端机器学习会扩大 JavaScript 的编排角色。模型可能通过云端 API、WebGPU、Wasm 或平台内置能力运行。工程重点仍是通用问题：流式结果、取消、隐私、成本、缓存、错误恢复和不可信输出。

```js
async function consumeLines(response, onLine) {
  if (!response.body) throw new Error("响应流不可用");
  const reader = response.body.pipeThrough(new TextDecoderStream()).getReader();
  let buffer = "";

  while (true) {
    const { value = "", done } = await reader.read();
    buffer += value;
    const lines = buffer.split("\n");
    buffer = lines.pop() ?? "";
    for (const line of lines) onLine(line);
    if (done) break;
  }
  if (buffer) onLine(buffer);
}
```

模型输出必须视为不可信输入，不能未经验证直接执行、拼入 HTML、查询数据库或调用高权限工具。涉及个人和企业数据时，应明确数据发送范围、保留策略和用户同意。

## 11. 隐私与安全模型趋严

浏览器正在减少跨站跟踪能力，加强权限、存储分区和安全上下文要求。应用不应依赖第三方 Cookie 或隐蔽指纹识别维持核心功能。第一方数据、最小权限和明确用户选择会越来越重要。

新能力往往仅在 HTTPS、安全响应头或用户授权下工作。部署配置已成为前端能力的一部分：CSP、Permissions Policy、COOP/COEP、正确 MIME 类型和跨源策略需要前后端共同维护。

## 12. 如何持续学习

面对快速演进的生态，可以建立稳定流程：

1. 从业务问题出发，不为追逐新语法而迁移
2. 查阅规范状态和权威兼容性数据
3. 在隔离原型中验证语义、性能和失败路径
4. 定义目标环境、降级策略与删除旧兼容层的条件
5. 用自动测试、真实用户监控和小流量发布降低风险
6. 定期删除已经失去必要性的 polyfill、实验标志和抽象层

## 常见陷阱与最佳实践

- 不把早期提案当成已稳定标准，不在核心数据格式中依赖易变语义
- 不混淆语法转译与运行时 polyfill
- 使用功能检测和实际调用兜底，而不是只检测 User-Agent
- 明确目标环境，基于数据决定兼容范围
- 新 API 先小范围验证，再建立监控和降级路径
- Wasm、Worker、WebGPU 只在测量证明值得时引入
- 将 AI 输出和跨运行时输入视为不可信数据
- 依赖平台标准的同时，保留清晰的宿主边界

## 章节小结

JavaScript 的未来不是单一新语法，而是语言、Web 平台、工具链和多运行时共同演进。可靠的现代化策略是理解标准成熟度，明确目标环境，以渐进增强和功能检测控制兼容性，并用测量判断新技术收益。保持边界清晰、数据可信度明确和生命周期可控，代码才能适应下一轮平台变化。
