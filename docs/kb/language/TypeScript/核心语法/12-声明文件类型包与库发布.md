::: info 版本基线
本文以 TypeScript 7.0.2 为基线。声明文件描述 JavaScript 的静态形状，不实现运行时行为；高质量类型包必须与实际导出结构和最低运行时版本一致。
:::

## 学习目标

- 理解 `.d.ts`、ambient declaration 与普通 `.ts` 实现的边界。
- 为无类型 JavaScript、全局变量和资源模块补充声明。
- 正确消费 `@types`，并理解 TypeScript 7 的 `types` 默认行为。
- 为库生成、映射、测试并发布声明文件。
- 安全使用声明合并、模块扩充和 `skipLibCheck`。

## 1. `.d.ts` 的角色

声明文件以 `.d.ts` 结尾，只描述类型和可见 API：

```ts
// calculator.d.ts
export interface Options {
  precision?: number;
}

export declare function add(a: number, b: number, options?: Options): number;
```

它不会生成 JavaScript，也不提供 `add` 的实现。运行时必须另有真实模块：

```js
// calculator.js
export function add(a, b, options = {}) {
  const precision = options.precision ?? 2;
  return Number((a + b).toFixed(precision));
}
```

`.d.ts` 可以来自：

- TypeScript 源码通过 `declaration` 自动生成。
- JavaScript 库作者手写并随包发布。
- DefinitelyTyped 中独立发布的 `@types/*` 包。
- 应用项目为运行时、资源加载器或无类型依赖编写的本地声明。

::: warning 声明不是验证器
声明文件无法确认运行时对象真的符合类型。错误的 `.d.ts` 会让编译器“自信地出错”，因此必须测试声明与 JavaScript 行为的一致性。
:::

## 2. Ambient Declaration（环境声明）

`declare` 表示“这个实体由别处提供，这里只描述它”：

```ts
declare const APP_VERSION: string;

declare function reportMetric(
  name: string,
  value: number,
): void;

declare class RuntimeClient {
  constructor(endpoint: string);
  send(payload: unknown): Promise&lt;void&gt;;
}
```

环境声明中通常不能写实现：

```ts
declare function add(a: number, b: number): number;
// declare function bad() { return 1; } // 错误：环境上下文不能有实现
```

只在运行环境确实注入这些值时声明它们。例如构建工具替换 `APP_VERSION`，或宿主页面提供全局 SDK。

## 3. 声明外部模块

### 3.1 为无类型包写最小声明

```ts
// types/legacy-parser.d.ts
declare module "legacy-parser" {
  export interface ParseOptions {
    tolerant?: boolean;
  }

  export function parse(
    source: string,
    options?: ParseOptions,
  ): unknown;
}
```

然后确保文件被 `tsconfig.json` 的 `include` 覆盖：

```json
{
  "include": ["src", "types"]
}
```

不要长期停留在以下草率声明：

```ts
declare module "legacy-parser";
```

它会使整个模块近似 `any`，只能作为短期迁移垫片。

### 3.2 资源模块

```ts
// types/assets.d.ts
declare module "*.svg" {
  const url: string;
  export default url;
}

declare module "*.css" {
  const classes: Readonly<Record<string, string>>;
  export default classes;
}
```

声明必须匹配 loader/bundler 的真实输出。有的 SVG 插件导出组件而非 URL，不能照搬模板。

### 3.3 Ambient module 与 module augmentation 的区别

没有顶层 `import`/`export` 的脚本式 `.d.ts` 中，`declare module "x"` 可创建新的环境模块。若文件本身是模块，同样语法通常表示扩充已存在模块：

```ts
export {};

declare module "legacy-parser" {
  // 这是 augmentation，不是从零创建模块
  export function stringify(value: unknown): string;
}
```

混淆二者会导致模块无法解析或意外覆盖认知。扩充前必须确保原模块声明已被加载。

## 4. 扩充全局作用域

在模块文件中使用 `declare global`：

```ts
// types/runtime.d.ts
export {};

declare global {
  interface Window {
    analytics: {
      track(event: string): void;
    };
  }

  var __BUILD_ID__: string;
}
```

```ts
window.analytics.track("page_view");
console.log(__BUILD_ID__);
```

全局扩充会影响整个程序，应尽量缩小范围并使用不易冲突的名字。若值可以通过模块导入获得，优先模块 API，而不是增加全局变量。

## 5. 类型从哪里来

TypeScript 查找包类型时通常会考虑：

- 包内 `package.json` 的 `exports` 中匹配的 `types` 条件。
- 包根部的 `types`（或旧别名 `typings`）字段。
- 与 JavaScript 文件相邻的 `.d.ts`、`.d.mts`、`.d.cts`。
- `node_modules/@types` 中可见的类型包。

```json
{
  "name": "tiny-lib",
  "type": "module",
  "main": "./dist/index.js",
  "types": "./dist/index.d.ts"
}
```

`types` 指定包的主声明入口，但有 `exports` 时，现代解析优先遵循导出映射。两者应保持一致，不要让编辑器看到一个入口、Node 运行另一个入口。

## 6. `@types` 包

若依赖没有自带类型，先查找对应 DefinitelyTyped 包：

```bash
npm install -D @types/node
npm install -D @types/express
```

作用域包 `@scope/pkg` 通常映射为形如 `@types/scope__pkg` 的名称。不是所有包都有 `@types`；现代库往往直接捆绑声明。

类型包版本应与运行时库主版本和目标 Node/DOM 环境兼容。升级 TypeScript 后出现标准库类型冲突时，先更新相关 `@types`，不要立刻用 `skipLibCheck` 隐藏。

## 7. TypeScript 7 的 `types` 默认值

TypeScript 7 的配置默认更强调显式环境，`types` 默认按空列表 `[]` 处理。结果是：安装在可见 `node_modules/@types` 中的包，不会自动把全局声明全部注入项目。

Node 项目应明确配置：

```json
{
  "compilerOptions": {
    "types": ["node"]
  }
}
```

测试项目可在专用配置中加入测试框架：

```json
{
  "extends": "./tsconfig.json",
  "compilerOptions": {
    "types": ["node", "vitest/globals"]
  },
  "include": ["src", "test"]
}
```

`types` 主要控制哪些类型包把全局声明纳入编译，不会阻止从某包显式导入类型。显式列表能避免 Jest、Mocha、Node 与 DOM 全局变量意外污染或冲突。

::: note 与旧项目的差异
从 TypeScript 5.x/6.x 迁移时，不要依赖“安装 `@types/node` 后自动出现 `process`”的偶然行为。把所需环境写入 `types`，并把源代码、测试、脚本按不同 `tsconfig` 隔离。
:::

## 8. 生成声明文件

用于发布库的典型配置：

```json
{
  "compilerOptions": {
    "target": "esnext",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "rootDir": "src",
    "outDir": "dist",
    "strict": true,
    "declaration": true,
    "declarationMap": true,
    "sourceMap": true,
    "verbatimModuleSyntax": true,
    "types": []
  },
  "include": ["src"]
}
```

### 8.1 `declaration`

`declaration: true` 会为项目中参与 emit 的源文件生成对应 `.d.ts`，而不是只生成“从入口可达”的声明。哪些文件真正成为消费者契约，还取决于发布布局、`files` 和 `package.json` 的 `exports`；若需要单一声明入口，应使用声明 bundler 或专门的 API 提取流程。

```ts
// src/index.ts
export interface ClientOptions {
  timeout?: number;
}

export class Client {
  constructor(options?: ClientOptions) {}
  request(path: string): Promise&lt;Response&gt; {
    return fetch(path);
  }
}
```

生成的声明大致为：

```ts
export interface ClientOptions {
  timeout?: number;
}
export declare class Client {
  constructor(options?: ClientOptions);
  request(path: string): Promise&lt;Response&gt;;
}
```

### 8.2 `declarationMap`

`declarationMap: true` 生成 `.d.ts.map`，让消费者“转到定义”时尽可能跳回库的 TypeScript 源码。若发布映射，通常也应把相应源码纳入包，或确认映射路径在发布产物中有效。

### 8.3 `emitDeclarationOnly`

```json
{
  "compilerOptions": {
    "declaration": true,
    "declarationMap": true,
    "emitDeclarationOnly": true,
    "outDir": "dist/types"
  }
}
```

适合 JavaScript 由 Rollup、esbuild、SWC 等生成，而 TypeScript 只负责类型检查与声明输出的流程。必须确保 bundler 的公开入口与声明入口一一对应。

不要发布带类型错误生成的声明。构建脚本应先成功完成类型检查，再打包、测试产物并执行 `npm pack` 检查。

## 9. `package.json` 的类型入口与 `exports`

单一 ESM 入口：

```json
{
  "name": "@acme/client",
  "version": "1.0.0",
  "type": "module",
  "files": ["dist"],
  "types": "./dist/index.d.ts",
  "exports": {
    ".": {
      "types": "./dist/index.d.ts",
      "import": "./dist/index.js"
    },
    "./testing": {
      "types": "./dist/testing.d.ts",
      "import": "./dist/testing.js"
    }
  }
}
```

关键规则：

- `exports` 是公开 API 白名单，未列出的深导入会被封锁。
- 每个运行时子路径都应有对应类型子路径。
- 条件对象中的 `types` 放在匹配运行时条件之前。
- 导出目标使用包内相对路径并以 `./` 开头。
- `.d.ts` 的模块格式必须与对应 JavaScript 一致。

双格式包应分别考虑 `import` 与 `require`：

```json
{
  "exports": {
    ".": {
      "import": {
        "types": "./dist/index.d.mts",
        "default": "./dist/index.mjs"
      },
      "require": {
        "types": "./dist/index.d.cts",
        "default": "./dist/index.cjs"
      }
    }
  }
}
```

双包发布极易出现 default export、条件解析、状态重复和声明格式错误。若没有明确消费者需求，发布单一 ESM 格式通常更简单。

## 10. 编写并发布一个库

推荐流程如下：

1. 先定义最小公开入口，内部文件不要全部从根入口导出。
2. 使用显式返回类型稳定公共函数的契约，避免实现细节泄漏到 `.d.ts`。
3. 开启 `strict`、`declaration` 和 `declarationMap`。
4. 让模块模式匹配发布格式，Node 包使用现代 Node 模式。
5. 构建到干净的 `dist`，不要把测试和内部脚本混进声明。
6. 配置 `files` 与 `exports`，明确根入口和合法子路径。
7. 在临时消费者项目中同时测试运行时导入和类型检查。
8. 执行 `npm pack --dry-run` 或检查 tarball，确认声明、映射和 JavaScript 都被包含。
9. 用最低支持的 Node、TypeScript 和 bundler 组合做 CI 测试。
10. 把公共类型变化按 API 破坏性变化管理，而不是视为“只有类型变化”。

### 10.1 避免泄漏不可命名类型

```ts
class InternalTransport {
  send() {}
}

export function createClient() {
  return new InternalTransport();
}
```

推断结果可能把内部实现暴露进声明。公共边界应提供稳定接口：

```ts
export interface Client {
  send(): void;
}

class InternalTransport implements Client {
  send() {}
}

export function createClient(): Client {
  return new InternalTransport();
}
```

这让实现可替换，也减少无意的 semver 破坏。

## 11. 声明合并

同名 `interface` 会合并：

```ts
interface RequestContext {
  requestId: string;
}

interface RequestContext {
  userId?: string;
}

const context: RequestContext = {
  requestId: "r1",
  userId: "u1",
};
```

常见可合并组合包括接口与接口、namespace 与类/函数/枚举等。但 TypeScript 7 与 `erasableSyntaxOnly` 强调可擦除和标准 JavaScript，新库不应为了组织静态成员而依赖带运行时代码的 namespace 合并。

同名非函数成员必须类型兼容；函数成员会形成重载。合并跨文件发生，容易被全局污染触发，因此模块化代码中应避免通用全局接口名。

## 12. Module Augmentation（模块扩充）

扩充第三方模块已有接口：

```ts
// src/express-session.d.ts
import "express-session";

declare module "express-session" {
  interface SessionData {
    userId: string;
  }
}
```

导入原模块确保这是扩充，并让基础声明被加载。扩充只能补充已有声明，不能通过 augmentation 添加新的顶层默认导出；默认导出也无法直接按名字扩充。

运行时必须同步安装或执行对应实现。仅扩充接口不会真的给对象增加方法：

```ts
import "third-party/register-feature.js"; // 真正打补丁
```

augmentation `.d.ts` 应通过 `include`、`files` 或声明依赖纳入 TypeScript Program。纯 `.d.ts` 不会生成 JavaScript，不要为了加载类型而编造 `./third-party-augmentation.js` 运行时导入。

猴子补丁容易受版本变化影响。能用包装器或适配器时，通常比全局扩充更稳健。

## 13. `skipLibCheck` 的取舍

```json
{
  "compilerOptions": {
    "skipLibCheck": true
  }
}
```

它跳过对 `.d.ts` 文件内部的一部分检查，可缩短大型项目构建时间，也能暂时绕过依赖间重复/冲突声明。

代价包括：

- 依赖声明内部的不一致可能被隐藏。
- 某些错误会在你使用相关类型时以更难理解的方式出现。
- 它不能保证所有声明冲突都消失；TypeScript 7 对部分来自非 `.d.ts` 位置的冲突会继续报告。
- 发布库若一直开启它，可能把有问题的声明交给消费者。

推荐策略：应用可基于构建性能权衡开启，但定期在 CI 运行一次 `skipLibCheck: false`；库的发布检查尽量关闭。遇到冲突先统一依赖版本、更新 `@types` 或修正类型包，而不是永久静音。

## 14. 测试声明文件

### 14.1 正向与反向用例

```ts
import { createClient } from "@acme/client";

const client = createClient({ timeout: 1000 });
client.send("/health");

// @ts-expect-error timeout 必须是 number
createClient({ timeout: "fast" });

// @ts-expect-error send 需要 path
client.send();
```

`@ts-expect-error` 在下一行不再报错时会自身报错，适合验证应被拒绝的调用。不要使用不会验证预期是否仍成立的 `@ts-ignore`。

### 14.2 类型相等测试

```ts
type Equal<A, B> =
  (&lt;T&gt;() => T extends A ? 1 : 2) extends
  (&lt;T&gt;() => T extends B ? 1 : 2) ? true : false;

type Expect&lt;T extends true&gt; = T;

declare const client: { send(path: string): Promise&lt;Response&gt; };
type _Return = Expect<Equal<ReturnType&lt;typeof client.send&gt;, Promise&lt;Response&gt;>>;
```

复杂公共类型可使用专门工具如 `tsd` 或项目自己的 fixture。更重要的是建立真实消费者测试：把 `npm pack` 产物安装到 ESM/CJS/Node/bundler 样例项目，运行 `tsc --noEmit` 和实际代码。

### 14.3 测试发布产物而非源码捷径

workspace 或 `paths` 可能让测试直接解析到 `src`，从而漏掉错误的 `exports`、缺失 `.d.ts` 和 tarball 文件。至少一组 CI 应安装打包后的 `.tgz`，从包名导入。

## 15. TypeScript 7 的程序化 API 注意事项

TypeScript 7 是原生端口，官方原生编译器仓库明确将传统 Programmatic API 标为不可用/未就绪。依赖 `typescript` JavaScript 包中 `createProgram`、AST 节点、Transformer、Language Service 私有结构或编译器插件的工具，不能假定只升级版本号就可工作。

::: warning 不要把 CLI 兼容等同于 API 兼容
`tsc`/`tsconfig`、检查和声明 emit 可用，不代表旧 TypeScript 6 JavaScript Compiler API 在 TypeScript 7 中存在同构替代。代码生成器、文档工具、lint 插件和自定义 transformer 应先查各自的 TypeScript 7 支持矩阵。
:::

迁移方案取决于工具：

- 只需检查或声明输出时，优先调用受支持的 CLI，并以退出码和文件为边界。
- 需要语法分析时，选择明确支持目标 TypeScript 语法的独立 parser。
- 依赖 compiler internals 的工具应锁定兼容版本，等待官方 API 或维护者迁移说明。
- 不要解析人类可读诊断文本作为稳定协议；若需要机器接口，等待或采用官方明确支持的结构化方案。

## 常见陷阱

- `.d.ts` 声明了 API，却没有对应运行时实现。
- 使用宽泛 `declare module "*"` 或无内容模块声明，使依赖退化为 `any`。
- `types` 未显式列出 Node/测试环境，升级 TypeScript 7 后全局名字消失。
- `exports` 指向 JavaScript，却漏掉 `types` 或某个子路径声明。
- 用一个 `.d.ts` 粗略描述行为不同的 ESM 与 CJS 入口。
- 声明扩充了方法，却忘记加载真正添加方法的运行时代码。
- `skipLibCheck` 长期开启，掩盖要发布给消费者的声明缺陷。
- 测试只引用仓库源码，没有安装 tarball 验证发布布局。
- 工具依赖旧 Compiler API，却把 TypeScript 7 当作无缝替换。

## 练习

1. 为一个只提供 JavaScript 的 `slugify` 包编写具名导出声明。
2. 为 `*.md` loader 编写声明，并说明默认导出的真实运行时形状。
3. 配置 `declaration`、`declarationMap` 与 `emitDeclarationOnly`，比较产物。
4. 为根入口和 `./node` 子入口设计 `exports` 与 `types` 条件。
5. 使用 `@ts-expect-error` 测试一个函数的非法参数和只读返回值。
6. 将依赖 Compiler API 的构建脚本改造成以 `tsc` CLI 和产物文件为边界。

## 发布检查清单

- [ ] `.d.ts` 与实际 JavaScript 导出名称、默认导出和模块格式一致。
- [ ] `types` 显式列出项目需要的环境类型。
- [ ] 每个 `exports` 子路径都有对应的类型入口。
- [ ] `declarationMap` 指向包内可访问源码，或已关闭该选项。
- [ ] 公共 API 没有泄漏内部类、私有路径或不可命名类型。
- [ ] 正向、反向类型用例均已测试。
- [ ] tarball 安装测试同时验证类型检查和实际运行。
- [ ] 发布 CI 至少有一组关闭 `skipLibCheck`。
- [ ] 编译器集成没有假定 TypeScript 7 提供旧 JavaScript Programmatic API。
