> TypeScript 采用结构类型系统：一个值能否使用，主要取决于它“有什么”，而不是它“叫什么”。

## 学习目标

- 用匿名对象类型、`interface` 和 `type` 描述数据结构
- 正确建模必选、可选和只读属性
- 理解 `exactOptionalPropertyTypes` 带来的语义差异
- 使用索引签名和 `Record` 描述动态键
- 理解多余属性检查及其边界
- 根据扩展方式选择接口或类型别名
- 掌握结构类型、交叉类型与兼容性
- 深入使用元组和只读元组
- 了解接口声明合并的能力与风险

## 心智模型：描述形状，而不是创建对象

以下类型不会在运行时创建任何值：

```ts
type Point = {
  x: number;
  y: number;
};
```

它只描述可接受对象的最小结构。

```ts
function distanceFromOrigin(point: Point): number {
  return Math.hypot(point.x, point.y);
}

distanceFromOrigin({ x: 3, y: 4 });
```

类型成员之间可用分号或逗号，团队应保持一致。

## 匿名对象类型

一次性参数可以内联描述：

```ts
function printUser(user: { id: string; name: string }): void {
  console.log(`${user.id}: ${user.name}`);
}
```

当形状会复用、嵌套较深或属于公共 API 时，应给它命名。

```ts
type User = {
  id: string;
  name: string;
};

function printUser(user: User): void {
  console.log(`${user.id}: ${user.name}`);
}
```

## 嵌套对象

```ts
type Order = {
  id: string;
  customer: {
    id: string;
    address: {
      city: string;
      street: string;
    };
  };
};
```

若内层概念独立复用，应拆出名字：

```ts
type Address = {
  city: string;
  street: string;
};

type Customer = {
  id: string;
  address: Address;
};
```

拆分依据是领域概念和复用，不是机械地让每个对象都有名字。

## 可选属性

属性名后的 `?` 表示可以不出现：

```ts
type Profile = {
  username: string;
  bio?: string;
};

const a: Profile = { username: "lin" };
const b: Profile = { username: "ada", bio: "programmer" };
```

读取可选属性时会得到包含 `undefined` 的类型：

```ts
function bioLength(profile: Profile): number {
  return profile.bio?.length ?? 0;
}
```

“属性不存在”和“属性存在且值为 `undefined`”在 JavaScript 中可被区分：

```ts
const absent = {};
const present = { bio: undefined };

console.log("bio" in absent);  // false
console.log("bio" in present); // true
```

## exactOptionalPropertyTypes

启用 `exactOptionalPropertyTypes` 后：

```ts
interface Preferences {
  colorScheme?: "light" | "dark";
}

const preferences: Preferences = {};
preferences.colorScheme = "dark";
// preferences.colorScheme = undefined; // 类型错误
```

`colorScheme?: T` 精确表示“属性可缺席；出现时必须是 T”。

如果业务允许属性显式存在且为 `undefined`，应写出来：

```ts
interface Preferences {
  colorScheme?: "light" | "dark" | undefined;
}
```

若属性必须存在但值可能为空，则写：

```ts
interface RequiredPreferences {
  colorScheme: "light" | "dark" | undefined;
}
```

这三种模型的写入语义不同，不要只根据读取结果判断。

## readonly 属性

```ts
interface Account {
  readonly id: string;
  displayName: string;
}

const account: Account = {
  id: "u-1",
  displayName: "Lin",
};

account.displayName = "Ada";
// account.id = "u-2"; // 类型错误
```

`readonly` 防止通过该类型位置重新赋值，不代表值被运行时冻结。

它也是浅层的：

```ts
interface Team {
  readonly owner: {
    name: string;
  };
}

const team: Team = { owner: { name: "Lin" } };
team.owner.name = "Ada"; // 合法，owner 引用没有被替换
```

需要深层不可变时要递归建模或使用专门工具，并考虑运行时策略。

## 索引签名

当属性名事先未知、值类型已知时使用索引签名：

```ts
interface StringMap {
  [key: string]: string;
}

const headers: StringMap = {
  accept: "application/json",
  authorization: "Bearer token",
};
```

已声明属性也必须兼容索引签名：

```ts
interface Inventory {
  [sku: string]: number;
  total: number;
}
```

下面则不兼容：

```ts
interface BrokenInventory {
  [sku: string]: number;
  // label: string; // string 不能赋给 number 索引结果
}
```

只读索引签名：

```ts
interface ReadonlyScores {
  readonly [player: string]: number;
}
```

若启用 `noUncheckedIndexedAccess`，未知键读取会包含 `undefined`：

```ts
declare const scores: Record<string, number>;
const score = scores["unknown"]; // number | undefined
```

这更符合运行时对象查找可能失败的事实。

## Record 实用示例

`Record<K, V>` 表示键集合 `K` 到值类型 `V` 的映射。

固定键集合：

```ts
type Role = "admin" | "editor" | "viewer";

const labels: Record<Role, string> = {
  admin: "管理员",
  editor: "编辑者",
  viewer: "访客",
};
```

遗漏或多写角色都会被检查。

动态字符串键：

```ts
type CacheEntry = {
  value: string;
  expiresAt: number;
};

const cache: Record<string, CacheEntry> = {};
cache.session = {
  value: "abc",
  expiresAt: Date.now() + 60_000,
};
```

`Record<string, V>` 不保证任意字符串键在运行时确实存在。

搭配 `noUncheckedIndexedAccess` 才会在读取时反映这一点。

还可以用 `satisfies` 同时检查完整性并保留每项细节：

```ts
type Route = "home" | "settings";

const routes = {
  home: { path: "/", public: true },
  settings: { path: "/settings", public: false },
} satisfies Record<Route, { path: string; public: boolean }>;
```

## 多余属性检查

对象字面量直接出现在目标类型位置时，会检查意外属性：

```ts
interface User {
  name: string;
}

function saveUser(user: User): void {
  console.log(user.name);
}

saveUser({
  name: "Ada",
  // admin: true, // 对象字面量多出未知属性
});
```

这能抓住拼写错误：

```ts
interface Options {
  timeout?: number;
}

// const options: Options = { timeuot: 1000 };
```

但多余属性检查不是“所有对象永远不能有额外字段”。

先存入变量时，应用的是普通结构兼容：

```ts
const candidate = {
  name: "Ada",
  admin: true,
};

saveUser(candidate); // 合法，至少拥有 name: string
```

不要用无意义断言绕过检查；先确认是拼写错误、API 设计问题，还是确实需要开放键。

## interface

接口专门命名对象、函数和类实例等结构：

```ts
interface Product {
  readonly id: string;
  name: string;
  price: number;
}
```

接口可通过 `extends` 扩展：

```ts
interface Timestamped {
  createdAt: Date;
  updatedAt: Date;
}

interface Product extends Timestamped {
  id: string;
  name: string;
}
```

也可扩展多个接口：

```ts
interface Identified {
  id: string;
}

interface Named {
  name: string;
}

interface Category extends Identified, Named {
  parentId?: string;
}
```

## type 类型别名

`type` 可以命名任意类型，不限于对象：

```ts
type Id = string | number;
type Point = [number, number];
type Predicate = (value: string) => boolean;
type Product = {
  id: Id;
  name: string;
};
```

类型别名不是名义上的新类型：

```ts
type UserId = string;
type OrderId = string;

const userId: UserId = "u-1";
const orderId: OrderId = userId; // 合法，二者都是 string
```

若需要品牌类型，要在结构中加入独特标记；这是后续类型技巧，不是普通别名自动提供的能力。

## interface 与 type 如何选择

共同点：

- 都能描述对象属性
- 都支持泛型
- 都能被结构兼容性检查
- 多数普通对象模型可自由选择

关键差异：

| 需求 | 更自然的选择 |
| --- | --- |
| 可由第三方扩展的对象契约 | `interface` |
| 类实现的公开结构 | `interface` |
| 联合、元组、原始类型别名 | `type` |
| 映射类型、条件类型组合 | `type` |
| 必须禁止声明合并 | `type` |

实用原则：对象扩展层次优先考虑 `interface`；类型运算和联合优先使用 `type`。

团队一致性通常比个人偏好更重要。

## 结构类型系统

兼容性看结构，不要求显式声明“实现”关系：

```ts
interface Named {
  name: string;
}

class Person {
  constructor(
    public name: string,
    public age: number,
  ) {}
}

function greet(value: Named): string {
  return `你好，${value.name}`;
}

greet(new Person("Ada", 36));
const visitor = { name: "Lin", city: "杭州" };
greet(visitor);
```

普通结构兼容允许调用者有更多字段，只要需要的字段类型兼容。直接传入 `{ name: "Lin", city: "杭州" }` 这样的新鲜对象字面量则会触发多余属性检查；先保存为变量是为了展示结构兼容，而不是建议绕过输入检查。

这让 JavaScript 风格的组合非常自然，但也意味着同形状别名不会自动隔离领域概念。

## 交叉类型

交叉类型 `A & B` 要求同时满足两边：

```ts
type Identified = {
  id: string;
};

type Timestamped = {
  createdAt: Date;
};

type Entity = Identified & Timestamped;

const entity: Entity = {
  id: "e-1",
  createdAt: new Date(),
};
```

不要把交叉理解为对象展开。

冲突属性可能得到无法构造的类型：

```ts
type A = { value: string };
type B = { value: number };
type Impossible = A & B;

// Impossible["value"] 是 never
```

若同名字段语义不同，重新设计名称通常比强行交叉更清晰。

## 元组

元组是具有已知位置语义的数组类型：

```ts
type HttpResult = [status: number, body: string];

const result: HttpResult = [200, "OK"];
const [status, body] = result;
```

可选元素必须位于必选元素之后：

```ts
type Range = [start: number, end?: number];

const fromFive: Range = [5];
const between: Range = [5, 10];
```

剩余元素：

```ts
type Command = [name: string, ...args: string[]];

const command: Command = ["copy", "a.txt", "b.txt"];
```

元组标签只改善可读性，不改变兼容性。

```ts
type PointA = [x: number, y: number];
type PointB = [horizontal: number, vertical: number];

const pointA: PointA = [1, 2];
const pointB: PointB = pointA;
```

## readonly 元组

```ts
type RGB = readonly [red: number, green: number, blue: number];

const black: RGB = [0, 0, 0];
// black[0] = 255; // 类型错误
```

`as const` 常推断只读元组：

```ts
const route = ["/users", "GET"] as const;
// readonly ["/users", "GET"]
```

接受数据但不修改的函数应考虑只读参数：

```ts
function formatRgb([r, g, b]: RGB): string {
  return `rgb(${r}, ${g}, ${b})`;
}
```

只读元组可接收普通元组，反方向通常不成立，因为可写位置不能安全接收只读值。

## 声明合并

同名接口声明会合并：

```ts
interface WindowOptions {
  width: number;
}

interface WindowOptions {
  height: number;
}

const options: WindowOptions = {
  width: 800,
  height: 600,
};
```

类型别名不能重复声明：

```ts
type Size = { width: number };
// type Size = { height: number }; // 重复标识符
```

声明合并对扩展平台或第三方库类型很有用，例如模块增强和全局声明。

但它也可能让接口在远处被意外改变。

应用内部模型若不需要开放扩展，使用 `type` 可以明确阻止重新打开。

合并后的同名非函数属性必须类型兼容，否则会报错。

不要依赖导入顺序制造隐式契约。

## 实战：配置注册表

```ts
type Environment = "development" | "test" | "production";

interface AppConfig {
  readonly apiBaseUrl: string;
  timeoutMs?: number;
  features: Record<string, boolean>;
}

const configs = {
  development: {
    apiBaseUrl: "http://localhost:3000",
    features: { debugPanel: true },
  },
  test: {
    apiBaseUrl: "http://localhost:3001",
    timeoutMs: 500,
    features: {},
  },
  production: {
    apiBaseUrl: "https://api.example.com",
    timeoutMs: 3000,
    features: { analytics: true },
  },
} satisfies Record<Environment, AppConfig>;

function getConfig(environment: Environment): AppConfig {
  return configs[environment];
}
```

这个模型同时展示：固定环境键、可选属性、只读契约、动态功能键和 `satisfies` 完整性检查。

## 常见陷阱

### 把 ? 当作 T | undefined 的完全同义词

启用 `exactOptionalPropertyTypes` 后，两者的写入语义不同。

### 用宽索引签名掩盖拼写错误

若键集合有限，优先用字面量联合配合 `Record`。

### 认为 readonly 会冻结运行时对象

它只参与类型检查；运行时不可变需要另外实现。

### 用断言绕过多余属性检查

先修复错别字或重新设计开放字段，而不是立即 `as Options`。

### 交叉冲突字段

查看同名属性交叉后的实际类型，避免制造 `never`。

### 无意触发声明合并

公共名字要足够明确；不希望开放时选择类型别名。

## 动手练习

1. 为博客文章定义必选、可选和只读属性。
2. 分别建模“属性可缺席”和“属性必须存在但可为 undefined”。
3. 用 `Record` 建立三种日志级别到中文标签的完整映射。
4. 观察对象字面量与中间变量触发多余属性检查的差异。
5. 用两个接口 `extends` 创建实体类型，再用交叉类型实现一次。
6. 定义带标签的只读三元组表示 RGB。
7. 写两个同名接口观察声明合并，再改成 `type` 查看错误。
