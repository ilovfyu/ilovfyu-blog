::: info 版本基线
本文以 TypeScript 7.0.2 为基线。工具类型只存在于类型系统中，编译后不会生成 JavaScript，也不会在运行时校验数据。
:::

## 学习目标

- 用标准工具类型从已有类型派生新类型，避免重复声明。
- 区分对象键变换、联合类型过滤、函数签名提取和异步解包。
- 将工具类型用于表单、补丁、DTO、事件表和依赖注入等真实场景。
- 知道何时应停止“类型体操”，改用简单类型或运行时校验。

## 1. 对象属性修饰

先准备一个领域类型：

```ts
interface User {
  id: string;
  name: string;
  email: string | null;
  role: "admin" | "member";
  profile?: {
    bio: string;
  };
}
```

### 1.1 `Partial&lt;T&gt;`：所有属性可选

```ts
type UserPatch = Partial&lt;User&gt;;

function updateUser(id: string, patch: UserPatch): void {
  // 向服务端发送 PATCH 请求
}

updateUser("u1", { name: "Ada" });
```

它大致等价于：

```ts
type MyPartial&lt;T&gt; = {
  [K in keyof T]?: T[K];
};
```

`Partial` 是浅层变换，`profile` 一旦出现，仍须满足原有内部结构：

```ts
const bad: Partial&lt;User&gt; = {
  profile: {}, // 错误：缺少 bio
};
```

### 1.2 `Required&lt;T&gt;`：所有属性必填

```ts
type CompleteUser = Required&lt;User&gt;;

const user: CompleteUser = {
  id: "u1",
  name: "Ada",
  email: null,
  role: "admin",
  profile: { bio: "Compiler engineer" },
};
```

`Required` 的职责是移除属性可选标记，不等同于 `NonNullable`：必选属性中显式存在的 `null`/`undefined` 不会因此消失。可选属性涉及的 `undefined` 结果还受 `exactOptionalPropertyTypes` 和映射类型语义影响，不要把 `Required&lt;T&gt;` 理解为简单保留所有值联合。

### 1.3 `Readonly&lt;T&gt;`：所有属性只读

```ts
type UserSnapshot = Readonly&lt;User&gt;;

function render(user: UserSnapshot) {
  // user.name = "Grace"; // 错误
  return user.name;
}
```

`readonly` 是编译期约束，并非冻结对象；它也是浅层的。需要运行时不可变性时，应配合不可变更新策略或 `Object.freeze`，并理解后者同样默认是浅冻结。

## 2. 选择与删除键

### 2.1 `Pick<T, K>`：保留指定键

```ts
type UserCard = Pick<User, "id" | "name" | "role">;

const card: UserCard = {
  id: "u1",
  name: "Ada",
  role: "admin",
};
```

### 2.2 `Omit<T, K>`：排除指定键

```ts
type CreateUserInput = Omit<User, "id">;

function createUser(input: CreateUserInput): User {
  return { id: crypto.randomUUID(), ...input };
}
```

实践中，公开 API 的输入类型更适合显式 `Pick`，因为领域对象未来新增敏感字段时，不会被输入类型自动接纳。`Omit` 更适合“除少量键外其余保持同步”的内部派生类型。

## 3. `Record<K, V>`：键值映射

`Record` 适合已知键集合，而不是任意字符串字典：

```ts
type Role = User["role"];

const roleLabels: Record<Role, string> = {
  admin: "管理员",
  member: "成员",
};
```

新增联合成员时，映射表会立即报错，适合做穷尽性配置。

```ts
type Cache = Record<string, User | undefined>;

const cache: Cache = {};
const maybeUser = cache["u1"];
```

若配置了 `noUncheckedIndexedAccess`，普通字符串索引会自然得到 `User | undefined`；不要用类型断言假装键一定存在。

## 4. 联合类型集合运算

### 4.1 `Exclude<T, U>`：从联合中排除

```ts
type Status = "idle" | "loading" | "success" | "error";
type SettledStatus = Exclude<Status, "idle" | "loading">;
// "success" | "error"
```

### 4.2 `Extract<T, U>`：保留可赋给 U 的成员

```ts
type Primitive = string | number | boolean | Date;
type TextLike = Extract<Primitive, string | number>;
// string | number
```

二者通过分布式条件类型工作，大致定义如下：

```ts
type MyExclude<T, U> = T extends U ? never : T;
type MyExtract<T, U> = T extends U ? T : never;
```

### 4.3 `NonNullable&lt;T&gt;`：排除空值

```ts
type Email = User["email"];          // string | null
type PresentEmail = NonNullable&lt;Email&gt;; // string

function requireEmail(user: User): NonNullable<User["email"]> {
  if (user.email == null) {
    throw new Error("用户没有邮箱");
  }
  return user.email;
}
```

工具类型不会做运行时检查。外部数据必须先校验或收窄，不能直接 `as NonNullable&lt;T&gt;`。

## 5. 函数与构造函数提取

```ts
function search(query: string, limit = 20) {
  return Promise.resolve([{ id: "u1", score: 0.98 }]);
}

type SearchArgs = Parameters&lt;typeof search&gt;;
// [query: string, limit?: number]

type SearchPromise = ReturnType&lt;typeof search&gt;;
// Promise<{ id: string; score: number }[]>
```

`Parameters&lt;F&gt;` 获取参数元组，`ReturnType&lt;F&gt;` 获取返回类型。对于重载函数，它们只观察最后一个重载签名，因此不要用它们推断某个具体重载调用的精确结果。

```ts
class ApiClient {
  constructor(
    public readonly baseUrl: string,
    public readonly timeout: number,
  ) {}
}

type ApiClientArgs = ConstructorParameters&lt;typeof ApiClient&gt;;
// [baseUrl: string, timeout: number]

type ApiClientInstance = InstanceType&lt;typeof ApiClient&gt;;
// ApiClient

function make<A extends unknown[], T>(
  Constructor: new (...args: A) => T,
  ...args: A
): T {
  return new Constructor(...args);
}
```

这里必须使用可实例化的 `new` 签名。`abstract new` 适合“接受但不创建抽象构造器”的 API；若函数内部执行 `new Constructor()`，就不能允许抽象类。

这里 `typeof ApiClient` 是构造器值的类型，`ApiClient` 则是实例类型，详见下一章。

## 6. `Awaited&lt;T&gt;`：递归解包异步结果

```ts
type SearchResult = Awaited<ReturnType&lt;typeof search&gt;>;
// { id: string; score: number }[]

type A = Awaited<Promise<Promise&lt;number&gt;>>; // number
type B = Awaited&lt;boolean | Promise&lt;string&gt;>; // boolean | string
```

`Awaited` 模拟 `await` 的语义，能处理 Promise-like 对象和联合类型。通常优于手写 `T extends Promise&lt;infer U&gt; ? U : T`，因为手写版本容易漏掉递归与 thenable 细节。

## 7. 显式 `this` 相关工具

```ts
interface Logger {
  prefix: string;
}

function log(this: Logger, message: string) {
  console.log(`${this.prefix}: ${message}`);
}

type LogReceiver = ThisParameterType&lt;typeof log&gt;; // Logger
type StandaloneLog = OmitThisParameter&lt;typeof log&gt;; // (message: string) => void

const logger: Logger = { prefix: "API" };
const boundLog: StandaloneLog = log.bind(logger);
boundLog("started");
```

显式 `this` 参数只用于类型检查，不计入运行时参数列表。`ThisParameterType&lt;F&gt;` 在没有显式 `this` 时得到 `unknown`；`OmitThisParameter&lt;F&gt;` 会移除显式接收者，并对泛型/重载签名有所简化。

### 7.1 `ThisType&lt;T&gt;`：上下文 this 标记

`ThisType&lt;T&gt;` 不是普通变换类型，而是上下文类型标记，需要启用 `noImplicitThis`（`strict` 已包含）：

```ts
type ObjectDescriptor<D, M> = {
  data?: D;
  methods?: M & ThisType&lt;D & M&gt;;
};

function defineObject<D, M>(descriptor: ObjectDescriptor<D, M>): D & M {
  return { ...descriptor.data, ...descriptor.methods } as D & M;
}

const counter = defineObject({
  data: { value: 0 },
  methods: {
    increment() {
      this.value += 1;
    },
  },
});
```

这类 API 容易掩盖运行时对象组合细节。若普通类或闭包已经足够清晰，不必为了展示技巧使用 `ThisType`。

## 8. `NoInfer&lt;T&gt;`：阻止某处参与推断

`NoInfer&lt;T&gt;` 不改变最终类型，只阻止该位置成为类型参数的推断来源：

```ts
function choose&lt;C extends string&gt;(
  choices: readonly C[],
  defaultChoice?: NoInfer&lt;C&gt;,
): C {
  return defaultChoice ?? choices[0]!;
}

choose(["red", "yellow", "green"] as const, "red");
// choose(["red", "yellow", "green"] as const, "blue"); // 错误
```

没有 `NoInfer` 时，`"blue"` 可能反过来拓宽 `C`，让错误默认值混入候选联合。应只在“主参数决定类型、次参数必须服从”的 API 中使用它，不要把它当作修复所有泛型推断问题的开关。

## 9. 实战配方

### 9.1 精确补丁：至少包含一个字段

```ts
type AtLeastOne&lt;T&gt; = {
  [K in keyof T]-?: Required<Pick<T, K>> & Partial<Omit<T, K>>;
}[keyof T];

type EditableUser = Pick<User, "name" | "email" | "profile">;
type NonEmptyUserPatch = AtLeastOne&lt;EditableUser&gt;;

function patchUser(id: string, patch: NonEmptyUserPatch) {}

patchUser("u1", { email: null });
// patchUser("u1", {}); // 错误
```

### 9.2 可辨识联合过滤

```ts
type Event =
  | { type: "created"; user: User }
  | { type: "renamed"; id: string; name: string }
  | { type: "deleted"; id: string };

type EventOf&lt;T extends Event["type"]&gt; = Extract<Event, { type: T }>;
type DeletedEvent = EventOf<"deleted">;

function on&lt;T extends Event["type"]&gt;(
  type: T,
  handler: (event: EventOf&lt;T&gt;) => void,
) {}
```

### 9.3 从服务函数生成客户端契约

```ts
type AsyncFunction = (...args: any[]) => Promise&lt;unknown&gt;;

type ClientMethod&lt;F extends AsyncFunction&gt; = (
  ...args: Parameters&lt;F&gt;
) => Promise<Awaited<ReturnType&lt;F&gt;>>;

type SearchClient = ClientMethod&lt;typeof search&gt;;
```

只提取类型不能保证网络两端真的一致。跨进程边界还要用 schema、契约测试或代码生成校验 JSON。

### 9.4 表单状态

```ts
type FormState&lt;T extends object&gt; = {
  values: T;
  errors: Partial<Record&lt;keyof T, string&gt;>;
  touched: Partial<Record&lt;keyof T, boolean&gt;>;
};

type UserForm = FormState<Pick<User, "name" | "email">>;
```

## 10. 不要过度类型体操

::: warning 可读性和错误信息也是 API 的一部分
能写出递归条件类型，不代表应该写。类型越聪明，编译成本、维护成本和报错复杂度通常越高。
:::

出现以下信号时应简化：

- 使用者必须展开多层条件类型才能知道参数是什么。
- 错误信息充满内部辅助类型，无法指出业务问题。
- 为支持极少发生的调用形式加入大量分支。
- 递归类型触发“类型实例化过深”或明显拖慢编辑器。
- 类型声称保证的事实其实依赖运行时数据。
- 一段显式接口声明比通用类型短且更容易修改。

优先顺序通常是：推断现有值、简单接口/联合、标准工具类型、少量自定义映射类型，最后才是递归条件类型。复杂公共类型应有类型测试和用途注释。

## 常见陷阱

- `Partial`、`Readonly`、`Required` 都是浅层操作。
- `readonly` 不等于运行时冻结，也不保证引用对象深层不可变。
- `Record<string, T>` 不代表任意键在运行时一定存在。
- `Omit` 不会删除运行时属性，只改变静态可见形状。
- 工具类型不能替代对 JSON、表单或环境变量的运行时验证。
- `ReturnType` 和 `Parameters` 对重载只取最后一个签名。
- `any` 会穿透许多类型安全边界；辅助类型中优先考虑 `unknown`，仅在构造签名约束等必要位置使用 `any`。

## 练习

1. 为 `User` 定义仅允许修改 `name`、`email` 的非空补丁类型。
2. 定义 `Result = { ok: true; data: User } | { ok: false; error: Error }`，用 `Extract` 得到成功分支。
3. 写一个 `invoke` 函数，参数由 `Parameters&lt;F&gt;` 决定，返回值为 `ReturnType&lt;F&gt;`。
4. 给一个异步仓储方法生成其已解析实体类型。
5. 比较手写 DTO 与 `Omit<User, "id">`：当 `User` 新增 `passwordHash` 时，哪一种更安全？

## 检查清单

- [ ] 我知道每个工具类型是作用于对象、联合、函数还是 Promise。
- [ ] 我没有把浅层变换误认为深层变换。
- [ ] 外部数据经过了运行时校验。
- [ ] 公共输入类型不会意外暴露未来新增字段。
- [ ] 自定义高级类型有清晰命名、类型测试和真实复用价值。
- [ ] 简单接口能解决时，我没有炫技式地加入递归条件类型。
