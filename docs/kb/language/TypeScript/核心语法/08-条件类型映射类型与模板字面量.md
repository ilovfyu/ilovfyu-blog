## 学习目标

- 使用条件类型表达类型级分支，理解裸类型参数触发的分布式行为。
- 用 `infer` 从函数、数组、Promise 和字符串结构中提取类型。
- 用映射类型遍历键，增删 `readonly`、可选修饰符并重映射键。
- 用模板字面量类型组合、约束和解析字符串协议。
- 了解 `Uppercase` 等内置字符串变换及 TS 7 的 Unicode code-point 行为。
- 控制递归深度、联合规模与类型实例化成本。
- 在 DTO、事件系统等真实场景中组合这些能力。

## 1. 条件类型

条件类型形如 `T extends U ? X : Y`。这里的 `extends` 是可赋值性判断，不是运行时分支，也不生成 JavaScript。

```ts
type IsString&lt;T&gt; = T extends string ? true : false;

type A = IsString<"hello">; // true
type B = IsString&lt;number&gt;;   // false
```

条件类型适合根据输入类型保持关联：

```ts
interface IdLabel { id: number }
interface NameLabel { name: string }

type LabelFor&lt;T extends number | string&gt; =
  T extends number ? IdLabel : NameLabel;

function createLabel&lt;T extends number | string&gt;(value: T): LabelFor&lt;T&gt; {
  return (typeof value === "number"
    ? { id: value }
    : { name: value }) as LabelFor&lt;T&gt;;
}
```

实现内部的断言源于泛型函数体里编译器不能总把运行时分支与尚未实例化的条件结果对应起来；公开返回类型仍精确。应确保断言覆盖所有运行时分支并测试实现。

### 1.1 约束位置的差异

把约束写在泛型参数上会拒绝不满足者；把判断写进条件类型可为不满足者产生 `never`。

```ts
type MessageOf&lt;T&gt; = T extends { message: unknown } ? T["message"] : never;

type EmailMessage = MessageOf<{ message: string }>; // string
type NoMessage = MessageOf<{ code: number }>;       // never
```

## 2. 分布式条件类型

当检查项是“裸类型参数” `T` 时，传入联合会对每个成员分别计算，再把结果联合起来。

```ts
type ToArray&lt;T&gt; = T extends unknown ? T[] : never;
type Distributed = ToArray&lt;string | number&gt;;
// string[] | number[]
```

这不同于 `(string | number)[]`：前者每个数组内部同质，后者一个数组可混合两类元素。

常见过滤器利用 `never` 在联合中被消去：

```ts
type OnlyStrings&lt;T&gt; = T extends string ? T : never;
type Names = OnlyStrings<"alice" | 1 | "bob" | false>;
// "alice" | "bob"
```

### 2.1 禁止分布

把检查双方包在单元素元组中，就会整体比较联合：

```ts
type ToArrayNonDist&lt;T&gt; = [T] extends [unknown] ? T[] : never;
type NonDistributed = ToArrayNonDist&lt;string | number&gt;;
// (string | number)[]
```

判断一个联合整体是否满足条件时应关闭分布；对成员做映射、筛选时使用分布。读到条件类型先问：“我希望逐成员处理，还是整体判断？”

### 2.2 `never` 的特殊表现

`never` 可视为没有成员的联合。分布式条件类型对零个成员分布，结果仍为 `never`。

```ts
type IsNeverWrong&lt;T&gt; = T extends never ? true : false;
type Wrong = IsNeverWrong&lt;never&gt;; // never，不是 true

type IsNever&lt;T&gt; = [T] extends [never] ? true : false;
type Right = IsNever&lt;never&gt;; // true
```

## 3. 使用 `infer` 提取类型

`infer X` 只能出现在条件类型的 `extends` 分支模式中，用来声明待推断的局部类型变量。

```ts
type ElementOf&lt;T&gt; = T extends readonly (infer Item)[] ? Item : never;

type Item = ElementOf&lt;readonly [string, number]&gt;;
// string | number
```

### 3.1 函数参数与返回值

```ts
type MyReturnType&lt;T&gt; = T extends (...args: never[]) => infer R ? R : never;
type MyParameters&lt;T&gt; = T extends (...args: infer P) => unknown ? P : never;

type Fn = (id: string, force?: boolean) => Promise&lt;number&gt;;
type Params = MyParameters&lt;Fn&gt;; // [id: string, force?: boolean]
type Result = MyReturnType&lt;Fn&gt;; // Promise&lt;number&gt;
```

对于具有多个重载签名的函数，条件推断通常从最后一个、最宽泛的签名进行，不能根据某一组参数执行重载解析。

### 3.2 Promise 解包与递归

```ts
type AwaitedValue&lt;T&gt; =
  T extends null | undefined ? T
    : T extends PromiseLike&lt;infer U&gt; ? AwaitedValue&lt;U&gt;
      : T;

type Data = AwaitedValue<Promise<Promise<{ id: string }>>>;
// { id: string }
```

实际项目优先使用内置 `Awaited&lt;T&gt;`；这里重写只是为了理解递归和 `infer`。

### 3.3 模板字符串中推断

```ts
type EventProperty&lt;S extends string&gt; =
  S extends `${infer Key}Changed` ? Key : never;

type Key = EventProperty<"nameChanged">; // "name"
```

`infer` 是模式匹配，不是任意字符串解析器。多个插值位置、重复分隔符及宽 `string` 都会影响结果，应为边界例子写类型测试。

## 4. 映射类型

映射类型遍历 `PropertyKey` 联合，通常来自 `keyof T`。

```ts
type Flags&lt;T&gt; = {
  [K in keyof T]: boolean;
};

interface Features {
  search(): void;
  export(): void;
}

type FeatureFlags = Flags&lt;Features&gt;;
// { search: boolean; export: boolean }
```

`K` 可用于读取原属性 `T[K]`：

```ts
type Nullable&lt;T&gt; = {
  [K in keyof T]: T[K] | null;
};
```

### 4.1 修改可选与只读修饰符

`+` 表示添加，`-` 表示移除；添加时 `+` 可省略。

```ts
type Mutable&lt;T&gt; = {
  -readonly [K in keyof T]: T[K];
};

type RequiredFields&lt;T&gt; = {
  [K in keyof T]-?: T[K];
};

type OptionalReadonly&lt;T&gt; = {
  readonly [K in keyof T]?: T[K];
};
```

映射类型通常保留原属性修饰符，除非显式修改。`-?` 移除的是可选修饰符；在严格空值语义下，它不一定移除属性值中显式写入的 `undefined`。

```ts
interface Input {
  value?: string;
  explicit: string | undefined;
}

type R = RequiredFields&lt;Input&gt;;
// value 变为必选；explicit 仍允许 undefined
```

## 5. 键重映射与过滤

TypeScript 允许在映射键后使用 `as` 生成新键。映射为 `never` 的键会被删除。

```ts
type Getters&lt;T&gt; = {
  [K in keyof T as K extends string
    ? `get${Capitalize&lt;K&gt;}`
    : never]: () => T[K];
};

interface Person {
  name: string;
  age: number;
}

type PersonGetters = Getters&lt;Person&gt;;
// { getName: () => string; getAge: () => number }
```

按值类型过滤属性：

```ts
type PickByValue<T, V> = {
  [K in keyof T as T[K] extends V ? K : never]: T[K];
};

type StringFields = PickByValue<{
  id: string;
  count: number;
  note: string;
}, string>;
// { id: string; note: string }
```

若可选属性的 `T[K]` 包含 `undefined`，它可能无法满足 `extends V`。应根据语义选择 `NonNullable<T[K]> extends V`，而不是盲目修改。

## 6. 模板字面量类型

模板字面量类型位于类型空间，拼接字符串字面量类型。插值包含联合时会做笛卡尔积。

```ts
type Lang = "zh" | "en";
type Section = "home" | "profile";
type MessageKey = `${Lang}.${Section}.title`;
// "zh.home.title" | "zh.profile.title"
// | "en.home.title" | "en.profile.title"
```

它适合规模有限、规则稳定的字符串协议。联合规模很大时，官方建议提前生成字符串联合，而不是让编译器反复展开。

### 6.1 与 `keyof` 组合

模板插值需要可表示为字符串的成员，因此常写 `string & keyof T` 或 `Extract&lt;keyof T, string&gt;`。

```ts
type ChangedEvent&lt;T&gt; = `${Extract&lt;keyof T, string&gt;}Changed`;

interface Model {
  name: string;
  age: number;
}

type ModelEvent = ChangedEvent&lt;Model&gt;;
// "nameChanged" | "ageChanged"
```

### 6.2 内置字符串操作类型

编译器内置四个 intrinsic 类型：

- `Uppercase&lt;S&gt;`：转换为大写。
- `Lowercase&lt;S&gt;`：转换为小写。
- `Capitalize&lt;S&gt;`：转换首个 code point。
- `Uncapitalize&lt;S&gt;`：转换首个 code point。

```ts
type Header = Uppercase<"content-type">; // "CONTENT-TYPE"
type Method = Lowercase<"POST">;          // "post"
type Getter = `get${Capitalize<"displayName">}`; // "getDisplayName"
```

这些变换不是 locale-aware，不适合承诺土耳其语等区域化大小写规则。它们用于类型级协议命名，而不是国际化文本处理。

## 7. TS 7 的 Unicode code-point 行为

TypeScript 7.0 改变了模板字面量类型中相邻 `infer` 片段的字符串推断：现在按完整 Unicode code point 前进；旧编译器按 UTF-16 code unit 前进，因此可能把辅助平面字符拆成两个 surrogate。这个变化不代表按 grapheme cluster（用户感知字符）处理；带组合附加符的字形和 ZWJ emoji 序列仍可能由多个 code point 组成。

例如，类型级“取首字符”的递归写法在 TS 7.0.2 中会以 code point 为推进单位：

```ts
type HeadTail&lt;S extends string&gt; =
  S extends `${infer Head}${infer Tail}` ? [Head, Tail] : never;

type Emoji = HeadTail<"😀ok">; // ["😀", "ok"]
```

::: warning
JavaScript 运行时的 `str.length` 和 `str[0]` 仍按 UTF-16 code unit 工作。不要从类型级推断改进推导出运行时索引语义已经改变。需要遍历 code point 时使用 `for...of` 或 `Array.from`；需要 grapheme cluster 时使用 `Intl.Segmenter` 等专门工具。
:::

内置大小写变换底层遵循 JavaScript 风格的、非区域化字符串映射。某些 Unicode 字符映射后长度可能变化，所以不要假设 `Uppercase&lt;S&gt;` 与 `S` 等长。

## 8. 实战一：DTO 转换

后端实体常包含客户端不应写入的字段。可用键过滤和递归映射构造 DTO，但要明确递归边界。

```ts
type ServerManaged = "id" | "createdAt" | "updatedAt";

type CreateDto&lt;T&gt; = {
  [K in keyof T as K extends ServerManaged ? never : K]:
    T[K] extends readonly (infer Item)[]
      ? CreateDto&lt;Item&gt;[]
      : T[K] extends object
        ? CreateDto<T[K]>
        : T[K];
};

interface UserEntity {
  id: string;
  name: string;
  createdAt: Date;
  updatedAt: Date;
  profile: {
    bio: string;
  };
}

type NewUser = CreateDto&lt;UserEntity&gt;;
```

这个示例仍有局限：`Date` 也满足 `object`，递归后未必得到想要的类型。生产代码应先列出叶子类型：

```ts
type Primitive = string | number | boolean | bigint | symbol | null | undefined;

type JsonDto&lt;T&gt; =
  T extends Date ? string
    : T extends Primitive ? T
      : T extends readonly (infer U)[] ? JsonDto&lt;U&gt;[]
        : T extends object ? { [K in keyof T]: JsonDto<T[K]> }
          : never;
```

类型转换不会真的把 `Date` 序列化成字符串，运行时仍需实现转换器并测试。类型只描述目标形状。

## 9. 实战二：类型安全事件系统

从模型键生成事件名，并让回调载荷与属性类型关联：

```ts
type EventSource&lt;T extends object&gt; = {
  on&lt;K extends Extract&lt;keyof T, string&gt;>(
    event: `${K}Changed`,
    listener: (value: T[K]) => void,
  ): void;
};

declare function watch&lt;T extends object&gt;(value: T): T & EventSource&lt;T&gt;;

const person = watch({ name: "Ada", age: 37 });

person.on("nameChanged", name => {
  name.toUpperCase(); // string
});

person.on("ageChanged", age => {
  age.toFixed(0); // number
});

// person.on("unknownChanged", () => {}); // 错误
```

反向解析事件名也可得到属性名：

```ts
type PropertyFromEvent&lt;T extends object, E extends string&gt; =
  E extends `${infer K}Changed`
    ? K extends keyof T ? K : never
    : never;

type AgeKey = PropertyFromEvent<{ age: number }, "ageChanged">; // "age"
```

若实现真实事件总线，运行时仍必须管理监听器、取消订阅、异常隔离和事件名构造。声明签名与实现应放在同一测试覆盖下。

## 10. 递归与性能边界

类型系统不是无限资源。递归条件类型、模板字面量笛卡尔积和大型映射类型可能造成“类型实例化过深”、联合过大、编辑器延迟或内存消耗。

### 10.1 典型高成本模式

- 对长元组逐项递归，每层又生成多个分支。
- 模板字面量中交叉组合多个大型联合。
- `DeepPartial` 一类递归映射反复穿透第三方复杂类型。
- 在分布式条件类型内部再次分布，导致组合爆炸。
- 递归缺少明确终止条件，或宽类型 `string`、`any` 进入递归。

### 10.2 实用控制策略

- 对大型字符串集合使用构建时生成，而非模板字面量笛卡尔积。
- 先处理 `Date`、函数、原始值等叶子类型，再递归对象。
- 用深度参数限制递归，只建模业务实际需要的层数。
- 使用 `[T] extends [U]` 关闭不必要的分布。
- 在公共 API 导出命名中间类型，避免到处重复展开巨型表达式。
- 用 `tsc --extendedDiagnostics` 和性能追踪定位热点，不凭感觉微调。
- 当简单显式联合足够清晰时，不为“类型体操”增加抽象。

一个带深度预算的示意：

```ts
type Prev = [never, 0, 1, 2, 3, 4, 5];

type DeepReadonly<T, D extends number = 5> =
  D extends 0 ? T
    : T extends (...args: never[]) => unknown ? T
      : T extends object
        ? { readonly [K in keyof T]: DeepReadonly<T[K], Prev[D]> }
        : T;
```

该技巧本身也有成本，只应在确有深层转换需求时使用。对固定 DTO，手写类型经常更可读、更稳定。

## 11. 常见陷阱

### 11.1 忘记分布式行为

`T extends U` 与 `[T] extends [U]` 语义不同。联合输入出现意外结果时，首先检查是否发生了分布。

### 11.2 `any` 污染条件类型

`any` 可能让条件两侧都参与并产生不直观结果。边界优先使用 `unknown`，不要把 `any` 输入复杂类型工具。

### 11.3 递归把函数和内建对象拆开

函数、`Date`、`Map`、`Set` 都是对象。无差别 `{ [K in keyof T]: ... }` 可能破坏其语义，必须先定义叶子类型或特判。

### 11.4 生成的事件名与运行时不一致

模板字面量类型只约束静态字符串。若运行时拼成 `${key}:changed`，类型却写 `${K}Changed`，安全是假象。

### 11.5 用类型运算替代数据校验

DTO、事件载荷和 API 响应来自运行时。映射类型与条件类型无法验证网络数据，也不会执行序列化。

### 11.6 巨大联合改善了自动补全却拖慢项目

枚举出几十个事件很有价值；展开几十万条国际化键通常不值得。对大集合使用普通 `string` 加运行时校验或代码生成。

## 练习

1. 实现 `ExcludeByValue<T, V>`，删除值类型可赋给 `V` 的键，并测试可选属性。
2. 实现非分布式 `IsUnion&lt;T&gt;` 或解释为何它需要同时保存原始联合与当前分支。
3. 从 `{ firstName: string; age: number }` 生成 `setFirstName(value: string)`、`setAge(value: number)`。
4. 实现 `Path&lt;T&gt;` 生成至多三层的点路径，排除函数和 symbol 键，并观察联合规模。
5. 为 `JsonDto&lt;T&gt;` 增加 `Map` 的处理策略，同时实现对应运行时转换器。
6. 用包含辅助平面 emoji、组合附加符和 ZWJ 序列的字符串测试“code point”与“grapheme cluster”的区别。

## 检查清单

- [ ] 明确条件类型要逐联合成员分布还是整体判断。
- [ ] `infer` 模式有不匹配时的合理 false 分支。
- [ ] 映射类型是否应保留、添加或移除可选与只读修饰符已经明确。
- [ ] 键重映射正确处理了非字符串键。
- [ ] 模板字面量联合规模保持可控，大集合考虑预生成。
- [ ] Unicode 逻辑区分 code unit、code point 和 grapheme cluster。
- [ ] 递归类型先处理叶子类型，并有终止条件或深度预算。
- [ ] 类型级 DTO 与事件协议有对应的运行时实现和验证。
- [ ] 没有让 `any` 穿过复杂条件类型。
- [ ] 类型抽象确实提升业务 API，而非单纯展示技巧。
