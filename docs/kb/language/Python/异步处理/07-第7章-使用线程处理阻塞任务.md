::: abstract 本章定位
现实系统常要调用没有异步接口的文件、数据库或第三方 SDK。本章关注如何把这些阻塞边界隔离到线程，以及线程与事件循环之间如何安全通信。内容对应原书第 7 章，不把线程误当作所有并发问题的通解。
:::

## 本章目标/地图

- 理解 `threading`、`ThreadPoolExecutor` 与 `asyncio` Task 的职责差异。
- 掌握 `run_in_executor()` 和 `asyncio.to_thread()` 包装阻塞调用的方法。
- 从其他线程用 `run_coroutine_threadsafe()` 安全提交协程。
- 正确选择 `threading.Lock` 与 `asyncio.Lock`，识别死锁模式。
- 理解 `contextvars` 在线程边界的传播，以及 GIL 何时会释放。

```text
asyncio event loop thread
    |-- async I/O -----------------------------------|
    |-- await to_thread(blocking_call)               |
    |                         worker thread ----------|
    |<-- run_coroutine_threadsafe(coro, loop) --------|
```

## 概念精讲

### 阻塞边界

同步函数若等待磁盘、网络或数据库，会把调用它的线程停住。它在事件循环线程中运行时，所有 Task 都无法前进。迁移旧系统时，不必先重写整个依赖：可以把明确的阻塞调用放入 worker 线程，协程只异步等待结果。

线程卸载是边界适配，不是让任意同步对象突然线程安全。数据库连接、客户端 session 或文件句柄能否跨线程使用，仍取决于库的约定。通常应让资源在同一 worker 调用内创建和使用，或者使用库提供的线程安全连接池。

### `threading`、线程池与 `to_thread`

`threading.Thread` 适合需要明确线程入口和生命周期的长期线程，如消费传统阻塞队列。大量短调用更适合 `ThreadPoolExecutor`，因为线程被复用且可以限制数量。

`asyncio.to_thread(func, *args)` 是高层便捷 API：它在默认线程池执行函数，并把当前 `contextvars.Context` 传播过去。需要独立池、明确容量或自定义 shutdown 时，使用 `ThreadPoolExecutor` 配合 `run_in_executor()`。

### 从线程回到 loop

绝大多数 asyncio 对象不是线程安全的。worker 线程不应直接 `await`，也不应直接修改 loop 所属的 `Queue`、Future 或 Transport。

- 提交普通回调：`loop.call_soon_threadsafe(callback, *args)`。
- 提交协程：`asyncio.run_coroutine_threadsafe(coro, loop)`。

后者返回 `concurrent.futures.Future`，供提交线程调用 `.result(timeout=...)`。不能在事件循环线程里对它同步 `.result()`，否则 loop 等自己执行该协程，形成死锁。

### 两类锁不能互换

`threading.Lock` 协调操作系统线程，获取时会阻塞线程；`asyncio.Lock` 协调同一 loop 内的协程，等待时让出 loop。协程若直接等待一个正被 worker 持有的线程锁，可能冻结整个事件循环。可共享的数据应尽量由单一执行域拥有，以消息传递取代跨域加锁。

典型死锁条件包括互斥、占有并等待、不可抢占和循环等待。工程上可通过固定锁顺序、禁止锁中调用未知代码、设置超时、缩小临界区来破坏这些条件。

### `contextvars`

请求 ID、租户 ID 等逻辑上下文不适合用 `threading.local()` 表达，因为多个协程共享一个线程。`ContextVar` 会随 Task 上下文正确隔离。`asyncio.to_thread()` 会复制当前上下文到 worker；低层 `run_in_executor()` 不应被假定具有同样传播语义，如需要可显式 `contextvars.copy_context().run(...)`。

线程中对 ContextVar 的修改发生在复制的 Context 中，不会自动反向合并到原 Task。

### GIL 释放

CPython 的 GIL 通常使多个线程不能同时执行 Python 字节码，所以纯 Python CPU 循环优先使用上一章的多进程方案。但阻塞系统调用会释放 GIL，许多 C 扩展也会在压缩、哈希、数值计算等重活期间主动释放 GIL。此时线程既能保持 loop 响应，也可能获得实际并行；必须查阅具体库文档并基准测试。

## API

| API | 用途 | 注意点 |
|---|---|---|
| `threading.Thread` | 创建和控制长期线程 | 非 daemon 线程应在关闭阶段 `join()` |
| `threading.Lock/RLock` | 在线程间保护同步状态 | 不要在 event loop 线程阻塞等待 |
| `ThreadPoolExecutor(max_workers=n)` | 有界复用 worker 线程 | 独立池便于隔离不同阻塞资源 |
| `loop.run_in_executor(pool, fn, *args)` | 在指定或默认 executor 执行 | 默认 executor 是线程池；不自动传播全部语义 |
| `asyncio.to_thread(fn, *args)` | 在默认线程池执行阻塞函数 | 传播当前 Context；Python 3.9+ |
| `asyncio.run_coroutine_threadsafe(coro, loop)` | 从别的线程向 loop 提交协程 | 返回 concurrent Future，需处理超时/异常 |
| `loop.call_soon_threadsafe(cb, *args)` | 从别的线程调度普通回调 | 比直接碰 asyncio 对象安全 |
| `contextvars.ContextVar` | 保存任务局部逻辑上下文 | 适合 request ID、trace 信息 |

## 完整原创可运行示例

示例模拟一个传统阻塞生产者线程：它生成记录，通过 `run_coroutine_threadsafe()` 投递到 asyncio 队列。异步消费者再用 `to_thread()` 调用阻塞解析函数。`ContextVar` 展示请求上下文传播，`threading.Lock` 只保护线程域的计数器。

```python
import asyncio
import contextvars
import threading
import time


request_id: contextvars.ContextVar[str] = contextvars.ContextVar("request_id")
counter_lock = threading.Lock()
produced = 0


def blocking_parse(raw: str) -> str:
    time.sleep(0.08)  # 模拟没有 async API 的阻塞库
    return f"{request_id.get('missing')}:{raw.upper()}"


def legacy_producer(
    loop: asyncio.AbstractEventLoop,
    queue: asyncio.Queue[str | None],
) -> None:
    global produced
    for index in range(5):
        time.sleep(0.05)
        with counter_lock:
            produced += 1
        future = asyncio.run_coroutine_threadsafe(
            queue.put(f"record-{index}"), loop
        )
        future.result(timeout=1)  # 此处位于生产者线程，不会卡住 event loop

    asyncio.run_coroutine_threadsafe(queue.put(None), loop).result(timeout=1)


async def consume(queue: asyncio.Queue[str | None]) -> None:
    request_id.set("import-2026")
    while (item := await queue.get()) is not None:
        parsed = await asyncio.to_thread(blocking_parse, item)
        print(parsed)


async def main() -> None:
    queue: asyncio.Queue[str | None] = asyncio.Queue(maxsize=2)
    loop = asyncio.get_running_loop()
    producer = threading.Thread(
        target=legacy_producer,
        args=(loop, queue),
        name="legacy-producer",
    )
    producer.start()

    await consume(queue)
    # join 可能阻塞，因此也放进 worker；正常情况下生产者此时已经结束。
    await asyncio.to_thread(producer.join)
    with counter_lock:
        print("produced:", produced)


if __name__ == "__main__":
    asyncio.run(main())
```

运行：

```bash
python chapter07_thread_bridge.py
```

## 执行流程

1. 主线程创建 event loop、一个容量为 2 的 asyncio Queue 和传统生产者线程。
2. 生产者通过 `threading.Lock` 更新仅在线程域读取的计数器。
3. 生产者不能直接调用异步队列，于是把 `queue.put()` 协程安全提交给 loop。
4. 队列满时，返回的 concurrent Future 直到异步消费者腾出位置才完成，形成背压。
5. 消费者设置 `request_id`，`to_thread()` 将该 Context 复制给解析 worker。
6. `time.sleep()` 只阻塞 worker，不阻塞 event loop。
7. 哨兵 `None` 结束消费，主协程在线程池中执行 `join()`，最后读取计数。

## 错误陷阱

- **在协程中直接调用 `time.sleep()` 或同步 SDK**：会阻塞 loop。改为异步 API 或线程卸载。
- **无限扩张线程**：线程占内存，外部服务也有容量上限。使用有界线程池和上游背压。
- **跨线程直接操作 asyncio 对象**：行为未定义或竞态。使用 `call_soon_threadsafe()` / `run_coroutine_threadsafe()`。
- **在 loop 线程调用 concurrent Future 的 `.result()`**：可能自我死锁；协程中应 `await` 对应 asyncio Future。
- **持有 `threading.Lock` 后 `await`**：锁跨越不确定暂停期，worker 可能反向等 loop。把状态复制出来再释放锁。
- **在 loop 中阻塞获取线程锁**：竞争时冻结所有 Task。重新划分状态所有权或在线程侧完成同步操作。
- **两个锁获取顺序不一致**：线程 A 持 L1 等 L2，线程 B 持 L2 等 L1。建立全局锁顺序。
- **假设取消协程能停掉线程**：已运行的同步函数通常继续执行；应传入线程安全停止标志并让函数协作退出。
- **把线程池用于纯 Python CPU 热循环**：GIL 下扩展性差。使用进程池，除非 C 扩展明确释放 GIL。
- **依赖隐式 Context 传播**：`to_thread()` 明确传播；自建 Thread 或低层 executor 要显式设计。

## 现代Python补充

### Python 3.11+

- `asyncio.to_thread()` 是包装短小阻塞边界的首选；若要设置 `max_workers`、线程名前缀或资源隔离，再显式建立 `ThreadPoolExecutor`。
- `asyncio.timeout()` 可以限制协程等待线程结果的时间，但不会强杀底层线程。同步函数必须支持自己的 socket timeout、取消 Event 或截止时间。
- `TaskGroup` 能组织多个线程卸载调用的等待和异常传播。Task 被取消后，底层已开始的线程调用仍可能继续。
- `ExceptionGroup` 允许一次报告多个并发失败；处理时可用 `except*` 按异常类型拆分。
- `asyncio.Runner` 可显式管理 loop 生命周期，适合嵌入同步程序；跨线程提交前仍必须确保该 loop 正在运行。

在支持自由线程构建的更新版本 CPython 中，GIL 的假设可能变化，但扩展库的线程安全和共享状态竞态不会因此消失。Python 3.11 常规构建仍应按“Python 字节码受 GIL 约束”设计。

### 异步程序中的文件 I/O

`asyncio` 没有提供通用的异步 `open()`。普通磁盘文件始终被视为可读或可写，selector 无法像监听 socket 那样可靠地等待“文件就绪”；一次 `read()`、`write()`、`flush()`、压缩或文件系统元数据操作仍可能阻塞事件循环。小配置文件可在启动阶段同步读取；请求路径中的不可控文件操作应使用 `asyncio.to_thread()`，大量文件任务还要用 Semaphore 或有界 worker 数量限制并发。

```python
import asyncio
from pathlib import Path


async def read_text(path: Path, slots: asyncio.Semaphore) -> str:
    async with slots:
        return await asyncio.to_thread(path.read_text, encoding="utf-8")


async def main() -> None:
    slots = asyncio.Semaphore(4)
    texts = await asyncio.gather(
        *(read_text(path, slots) for path in Path(".").glob("*.md"))
    )
    print(sum(map(len, texts)))


asyncio.run(main())
```

第三方 `aiofiles` 提供 `async with`/`await` 风格，但常见实现本质上仍把文件操作委托给线程池，并不会让磁盘变成原生非阻塞设备。无论使用哪种封装，都应考虑线程池容量、打开文件数、写入原子性、刷新/落盘语义，以及取消 await 后底层线程可能继续执行的事实。

## 实践清单

- [ ] 标记所有可能阻塞的同步调用及其最坏耗时。
- [ ] 优先使用原生异步库；无法替换时才跨线程适配。
- [ ] 为不同外部资源配置合理的线程池容量和超时。
- [ ] 不跨线程直接操作 loop、Task、asyncio Queue 或 Transport。
- [ ] 线程回调 loop 时保存明确的 loop 引用并处理提交失败。
- [ ] 明确共享状态的所有者；锁只保护短小同步临界区。
- [ ] 统一多锁获取顺序，并测试关闭、取消和异常路径。
- [ ] 使用 `ContextVar` 传请求上下文，验证跨线程传播方式。
- [ ] 给阻塞函数设计协作取消或内部超时，而不只取消 await。
- [ ] 根据 GIL 释放行为与实测结果决定线程还是进程。
- [ ] 请求路径中的文件 I/O 已卸载并限制并发；取消后不会误报写入已停止。
