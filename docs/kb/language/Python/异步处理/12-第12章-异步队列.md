> 对应 Matthew Fowler《Python Concurrency with asyncio》第 12 章。本文用原创生产者—消费者案例重建知识结构。

## 目标 / 地图

- `Queue`：FIFO；`PriorityQueue`：最小项优先；`LifoQueue`：后进先出。
- `put/get` 负责传递，`task_done/join` 负责完成追踪。
- 有界容量提供背压；sentinel 或现代 `shutdown()` 负责关闭。
- 完整关闭顺序：停止生产、处理积压、结束消费者、回收任务。

共享状态同步见 [第11章 同步原语](/kb/language/Python/异步处理/11-第11章-同步原语/)；3.13 更新见 [现代 asyncio 补遗](/kb/language/Python/异步处理/15-现代-asyncio-补遗/)。

## 概念机制

无界队列会把生产与消费速差变成内存增长。`Queue(maxsize=n)` 满时让 `put()` 等待，将压力传回上游。`qsize/empty/full` 只是瞬时观测，适合指标，不适合“先检查再操作”。

FIFO 保持入队顺序。优先级队列使用最小堆，常放 `(priority, sequence, payload)`：序号提供同优先级稳定性，也避免比较不可比较的 payload。LIFO 偏好新任务，但可能饿死旧任务。

每次成功 `put()` 都令未完成计数加一；每个取出的项目处理完后必须恰好调用一次 `task_done()`；`join()` 等这个计数归零。它不等于队列为空，因为项目可能已取出但仍在处理。把 `task_done()` 放在 `finally`。

旧式关闭常用唯一 sentinel。一个消费者会取走一个，因此通常每个消费者放一个；sentinel 必须排在全部正常工作之后，它本身也要 `task_done()`。正常协议是：等待生产者结束，`join()` 普通工作，发送 sentinel，再等待消费者退出。失败时不能盲等 `join()`，因为消费者崩溃会令积压永远无人完成。

## API

| API | 行为 |
|---|---|
| `Queue(maxsize=0)` | FIFO，0 为无界 |
| `PriorityQueue()` / `LifoQueue()` | 最小项优先 / 后进先出 |
| `await put(item)` / `put_nowait` | 满时等待 / 抛 `QueueFull` |
| `await get()` / `get_nowait` | 空时等待 / 抛 `QueueEmpty` |
| `task_done()` | 未完成计数减一 |
| `await join()` | 等未完成计数归零 |
| `qsize/empty/full` | 瞬时观测，不是同步保证 |

异步队列不是线程安全队列，也不接受 `timeout=`。

## 完整原创可运行示例

```python
import asyncio
import itertools
from dataclasses import dataclass, field
from typing import Any


@dataclass(order=True)
class Job:
    priority: int
    sequence: int
    payload: Any = field(compare=False)


STOP = object()


async def producer(name, queue, sequence):
    for priority, text in [(2, "report"), (1, "invoice"), (3, "notes")]:
        job = Job(priority, next(sequence), f"{name}:{text}")
        await queue.put(job)  # 满时暂停，形成背压
        print("queued", job.payload)


async def consumer(name, queue):
    while True:
        job = await queue.get()
        try:
            if job.payload is STOP:
                return
            await asyncio.sleep(0.03)
            print(name, "printed", job.payload)
        finally:
            queue.task_done()


async def main():
    queue = asyncio.PriorityQueue(maxsize=3)
    sequence = itertools.count()
    workers = [asyncio.create_task(consumer(f"p{i}", queue)) for i in range(2)]
    await asyncio.gather(
        producer("alice", queue, sequence),
        producer("bob", queue, sequence),
    )
    await queue.join()
    for _ in workers:
        await queue.put(Job(10_000, next(sequence), STOP))
    await queue.join()
    await asyncio.gather(*workers)


asyncio.run(main())
```

将可比较的普通项目放入 `asyncio.Queue` 或 `asyncio.LifoQueue`，可分别实验 FIFO 与 LIFO。不要在优先级队列混放无法比较的裸对象。

## 时序

```text
生产者 --put--> 有界队列（满则等待） --get--> 消费者
消费者 --处理完成/task_done--> 未完成计数 -1
主任务 --join--> 计数归零 --每个消费者一个 STOP--> 回收消费者
```

`get()` 只减少容器中的元素；只有 `task_done()` 推进 `join()`。

## 陷阱

- 无限队列吸收持续流量，最终耗尽内存。
- 忘记 `task_done()`、多调一次，或处理前过早调用。
- 消费者崩溃后仍永久等待 `join()`。
- sentinel 与数据冲突、数量少于消费者，或在生产结束前发送。
- `(priority, payload)` 的 payload 在同优先级时不可比较。
- LIFO/优先级调度没有防饥饿策略。
- 取消发生在 `get()` 后；必须明确重试、丢弃或持久化策略。

## 现代 Python 补充

- 3.11+ 用 `TaskGroup` 传播流水线失败，用 `asyncio.timeout()` 包住队列等待。
- 3.13 的三类队列均有 `shutdown(immediate=False)` 和 `QueueShutDown`：禁止新 `put()`，正常模式允许排空，排空后 `get()` 抛异常，可取代 sentinel。
- `shutdown(immediate=True)` 会立即排空队列，阻塞的 `get()` 以 `QueueShutDown` 结束，并解除阻塞中的 `join()`，即使未完成计数并未按通常方式归零。因此它明确打破了“每个入队项目都调用 `task_done()` 后 `join()` 才返回”的不变量；已经被消费者取走的项目若仍继续处理，依然应与 `task_done()` 正确配对，但调用方不能再把这次 `join()` 返回解释为全部工作完成。该模式只适合明确接受丢弃积压的紧急停止。
- 最低版本早于 3.13 的项目继续使用 sentinel。详见 [现代 asyncio 补遗](/kb/language/Python/异步处理/15-现代-asyncio-补遗/)。

## 实践清单

- [ ] 队列顺序、公平性、`maxsize` 有业务依据。
- [ ] 每个 `get()` 恰好对应一个 `finally` 中的 `task_done()`。
- [ ] 不用 `qsize()` 决定正确性。
- [ ] 正常关闭先停生产，失败关闭能取消整条流水线。
- [ ] sentinel 唯一且数量正确，或统一采用 3.13 `shutdown()`。
