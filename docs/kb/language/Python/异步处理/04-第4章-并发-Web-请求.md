## 本章目标

- 使用异步上下文管理器可靠管理 `ClientSession` 和响应体。
- 配置连接、读取和整体 HTTP timeout。
- 用 `gather()` 并发请求并理解结果/异常行为。
- 用 `as_completed()` 按完成顺序处理结果。
- 用 `wait()` 观察 done/pending 集合并实现自定义策略。
- 在批量超时、任务取消、连接池和业务限流之间建立清晰边界。

## 章节地图

1. **4.1 aiohttp 入门**：同步客户端会阻塞事件循环，aiohttp 在 socket 等待处让出控制权。
2. **4.2 异步上下文管理器**：`async with` 的进入/退出可等待；正确关闭 session、response 与 timeout。
3. **4.3 再看并发任务**：先把 coroutine 安排为 Task，才可观察并发进展。
4. **4.4 gather**：一次等待全部结果，返回顺序与输入一致；讨论异常处理。
5. **4.5 as_completed**：谁先完成先处理，并可设置整体等待期限。
6. **4.6 wait**：以 `ALL_COMPLETED`、`FIRST_EXCEPTION`、`FIRST_COMPLETED` 获取 done/pending；timeout 后显式收尾 pending；解释为何要先包装 Task。

## 概念精讲

### 4.1 aiohttp 与非阻塞 HTTP

`aiohttp.ClientSession` 持有连接池、DNS 缓存、Cookie 和默认配置，应按应用/服务边界复用，而不是每个请求新建。底层连接、等待响应头和读取响应体都能暂停当前 Task，使同一事件循环处理其他请求。

并发量不是越大越好。Session 的 connector limit 控制 TCP 连接池容量，`Semaphore` 可控制整个业务操作（包括重试、解析等）的并发数；两者边界不同。还要遵守远端速率限制、文件描述符和本机临时端口容量。

### 4.2 异步上下文管理器与 timeout

异步上下文管理器实现 `__aenter__`/`__aexit__`，退出过程允许等待网络清理。`async with ClientSession(...)` 确保连接池关闭；`async with session.get(...) as response` 确保响应释放回池。要读取响应体或显式 `release()`，否则连接复用会受影响。

`aiohttp.ClientTimeout` 可分别设置 `total`、`connect`、`sock_connect`、`sock_read`。连接池排队也可能计入连接/整体时间，具体应查当前版本文档。外层 `asyncio.timeout()` 适合约束含重试、解析和多个请求的业务期限；内层 aiohttp timeout 负责阶段诊断。两层应从同一个截止时间预算推导，避免互相矛盾。

### 4.3 创建并发任务

协程对象只是配方。`create_task()` 会立即调度；如果先逐个 `await fetch(url)`，仍然串行。Task 还让 `wait()` 返回稳定身份、允许查询状态、取消和取异常。自 Python 3.11 起，`asyncio.wait()` 不再接受裸 coroutine，必须显式建 Task。

### 4.4 gather：保序汇总

`await asyncio.gather(*aws)` 并发等待，结果列表严格按输入顺序，不按完成顺序。默认情况下，第一个传播给调用者的异常不会自动取消其他 awaitable；它们可能继续运行，因此调用者必须明确生命周期。`return_exceptions=True` 把异常当作结果收集，适合“尽量完成所有项”，但容易误把失败当成功，必须逐项分类。

若 `gather()` 自身被取消，未完成子任务会被取消。现代“任一失败则取消兄弟”语义更适合 `TaskGroup`；但 TaskGroup 不直接产生保序结果列表，可保存 Task 后在组出口读取。

### 4.5 as_completed：按完成顺序消费

`asyncio.as_completed(aws, timeout=...)` 让调用者逐个等待最先完成项，适合流式展示、降低首个结果延迟。超时表示在期限内尚未全部完成；仍须取消并等待自己创建的 pending tasks。Python 3.13 增强了异步迭代和原 Task 身份关联；面向 3.11 编写时不要依赖这些新行为。

### 4.6 wait：细粒度状态控制

`await asyncio.wait(tasks, return_when=...)` 返回两个集合：`done` 与 `pending`。模式包括：

- `ALL_COMPLETED`：等全部结束，类似汇合点，但不自动提取结果。
- `FIRST_EXCEPTION`：任一任务以异常结束时返回；若无异常则等同全部完成。
- `FIRST_COMPLETED`：任一成功、异常或取消即返回，适合竞速或滚动补充工作。

`wait(..., timeout=...)` 到时**不会抛 `TimeoutError`，也不会取消 pending**。这与 `wait_for()`、`asyncio.timeout()` 是关键差异。必须遍历 done 调用 `result()` 取得异常，并对 pending 选择继续、取消或转交其他所有者。

## 关键API

| API | 返回/行为 | 适用场景 |
|---|---|---|
| `aiohttp.ClientSession` | 可复用连接池 | 应用级 HTTP 客户端生命周期 |
| `aiohttp.ClientTimeout` | HTTP 阶段与总超时 | 网络层预算 |
| `aiohttp.TCPConnector(limit=...)` | 限制连接池总连接数 | 保护本机和远端连接资源 |
| `asyncio.Semaphore(n)` | 限制进入业务临界区的任务数 | 请求/重试/解析整体限流 |
| `asyncio.gather(*aws)` | 输入顺序的结果列表 | 全量、保序汇总 |
| `asyncio.as_completed(aws)` | 完成顺序的 awaitable 流 | 尽早处理结果 |
| `asyncio.wait(tasks, ...)` | `(done, pending)` 集合 | 自定义竞速、异常和超时策略 |
| `asyncio.TaskGroup` | 结构化失败传播 | 同一批必须共同成败 |

## 完整可运行原创示例

先安装 `aiohttp`：`python -m pip install aiohttp`。示例复用一个 Session，连接池上限为 4、业务并发上限为 2，并为 HTTP 阶段与整个批次分别设限；无论成功、超时或取消都能关闭响应、任务和连接池。

```python
import asyncio
from dataclasses import dataclass

import aiohttp


@dataclass(frozen=True)
class Page:
    url: str
    status: int
    size: int


async def fetch(
    session: aiohttp.ClientSession,
    limiter: asyncio.Semaphore,
    url: str,
) -> Page:
    async with limiter:
        async with session.get(url, allow_redirects=True) as response:
            response.raise_for_status()
            body = await response.read()
            return Page(str(response.url), response.status, len(body))


async def main() -> None:
    urls = [
        "https://example.com/",
        "https://www.python.org/",
        "https://docs.python.org/3/library/asyncio.html",
    ]
    timeout = aiohttp.ClientTimeout(total=5.0, connect=2.0, sock_read=3.0)
    connector = aiohttp.TCPConnector(limit=4, limit_per_host=2)
    limiter = asyncio.Semaphore(2)

    async with aiohttp.ClientSession(
        timeout=timeout,
        connector=connector,
        headers={"User-Agent": "asyncio-reading-notes/1.0"},
    ) as session:
        tasks = [
            asyncio.create_task(fetch(session, limiter, url), name=url)
            for url in urls
        ]
        try:
            async with asyncio.timeout(8.0):
                for completed in asyncio.as_completed(tasks):
                    try:
                        page = await completed
                        print(page)
                    except (aiohttp.ClientError, asyncio.TimeoutError) as exc:
                        print(f"请求失败: {exc!r}")
        finally:
            for task in tasks:
                if not task.done():
                    task.cancel()
            await asyncio.gather(*tasks, return_exceptions=True)


if __name__ == "__main__":
    asyncio.run(main())
```

示例依赖公网与目标站点可达；网络失败属于预期输入，代码会分类打印并完成清理。真实爬虫还应遵循 robots、服务条款和速率要求。

## 执行流程/时序说明

```text
main       建 Session/Connector -> 建 3 个 Task -> 进入 8s 批次期限
限流器     允许前 2 个 fetch；第 3 个在 Semaphore 排队，不占 HTTP 连接
请求任务   DNS/连接/发送/等响应均在 await 处让出事件循环
消费端     as_completed 每获得一个完成项就立即打印
限流器     一个请求退出上下文后，第 3 个进入
finally    取消未完成任务 -> gather 等取消清理 -> 退出 Session 关闭连接池
```

完成顺序取决于 DNS、连接复用、服务器和响应体大小。`as_completed` 不保证输入顺序。Semaphore 限的是整个 `fetch`；Connector 的 `limit_per_host` 另行约束同一主机 TCP 连接。

## 常见错误

- 每个 URL 新建 `ClientSession`，失去连接复用并产生未关闭连接警告。
- 只进入 `session.get()` 却不消费/释放响应体，连接无法及时回池。
- 一次创建几十万 Task；Semaphore 限制执行并不限制 Task 对象、输入列表和排队内存。
- 误以为 `gather()` 默认“一个失败就取消全部”；异常传播后其他任务可能仍运行。
- `gather(return_exceptions=True)` 后不检查元素类型，静默吞掉请求失败。
- `wait(timeout=...)` 后忘记处理 pending；该 API 不自动取消也不抛超时。
- 只设 total timeout，不区分连接和读取阶段，故障诊断困难；或只设 HTTP timeout，不限制重试后的总业务期限。
- 把连接池 limit 当作 API QPS 限流。连接并发数不等于单位时间请求数。
- 取消任务后不等待它们，响应上下文来不及释放资源。

## 现代Python补充

- 原书重点 API `gather()`、`as_completed()`、`wait()` 仍各有用途。`TaskGroup` 补充的是**结构化所有权与共同失败**，不是三者的全能替代品。
- `asyncio.timeout()` 比对整个 `gather()` 套 `wait_for()` 更便于覆盖重试、解析和后续 await；单请求仍应保留 aiohttp 的阶段 timeout。
- Python 3.11 起向 `asyncio.wait()` 传裸 coroutine 会报错，先使用 `create_task()`。这也让 pending 集合可被可靠取消和追踪。
- 大规模输入应采用固定 worker + `asyncio.Queue(maxsize=...)`，或分批创建任务，实现创建侧背压；Semaphore 只控制进入区段的数量。
- 可使用 `TraceConfig` 记录 DNS、排队、连接和响应时间，配合 task name、请求 ID 与指标定位尾延迟。

## 实践清单

- [ ] 一个清晰作用域复用一个 ClientSession，并在退出时关闭。
- [ ] 响应使用 `async with`，读取需要的 body，并限制最大响应体。
- [ ] 同时定义连接/读取 timeout 与端到端截止时间。
- [ ] Connector 限连接，Semaphore/令牌桶限业务并发或速率。
- [ ] 根据结果顺序需求选择 gather、as_completed 或 wait。
- [ ] 所有 pending 任务最终都被等待、取消并等待，或明确移交所有者。
- [ ] 重试仅针对幂等且可恢复错误，使用退避与随机抖动，并计入总期限。
- [ ] 大输入采用有界队列，而非一次性创建无限任务。
