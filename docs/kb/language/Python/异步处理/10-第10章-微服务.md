::: abstract 本章定位
微服务把本地函数调用变成了可能延迟、失败和重复的网络调用。异步并发能降低聚合延迟，也能更快制造级联故障。本章以 BFF 为载体，组合超时、重试、退避与 jitter、熔断、幂等和有界并发。
:::

## 本章目标/地图

- 理解 Backend for Frontend（BFF）的聚合职责与风险。
- 并发请求独立下游，并根据业务重要性降级。
- 设计 deadline、单次超时、有限重试及指数退避 + jitter。
- 用熔断器快速拒绝持续失败的依赖，并允许试探恢复。
- 通过幂等键约束重试副作用。
- 防止扇出、重试风暴和资源耗尽造成级联故障。

```text
client -> BFF
           |-- bulkhead/semaphore -> profile service
           |-- bulkhead/semaphore -> orders service
           `-- optional recommendation service

每个调用：总 deadline -> circuit breaker -> bounded concurrency
                              -> attempt timeout -> retryable?
                              -> exponential backoff + jitter
```

## 概念精讲

### BFF 与并发聚合

BFF 面向一种客户端体验组合多个领域服务，例如移动端首页同时需要用户、订单和推荐。独立调用并发启动可降低尾延迟，也减少客户端往返和协议复杂度。但 BFF 不应吞并所有领域逻辑，否则会成为新的单体和发布瓶颈。

聚合前要给依赖分类：用户身份等是必需数据，失败时整个请求失败；推荐等是可选数据，失败时返回空列表或缓存值。并发工具无法替代这种业务决策。

### 超时预算

超时不是单个魔法数字。入口请求有总 deadline，每次尝试有 attempt timeout，重试等待也消耗总预算。若 BFF 有 800 ms，不能给三个串行阶段各 800 ms。应从剩余预算推导下游 deadline，并给序列化和返回保留余量。

超时只停止等待方不够：下游最好接收 deadline/cancellation，HTTP client 还需阶段超时。否则调用方释放了 Task，下游仍消耗数据库和线程。

### 重试、指数退避和 jitter

重试适合短暂故障，例如连接重置、限流响应或短暂不可用；认证失败、参数错误等永久错误不应重试。指数退避让间隔随次数增长，jitter 加入随机性，避免所有实例同一时刻重试：

```text
cap = min(max_delay, base_delay * 2^attempt)
full jitter delay = random(0, cap)
```

限制次数只是第一步，还要限制总耗时和重试流量。尊重服务端 `Retry-After`，并为重试设置独立预算。

### 幂等

读取通常天然幂等；创建订单、扣款等写操作不是。客户端超时并不知道服务端是否已经提交，盲目重试可能产生重复副作用。常见做法是发送稳定的幂等键，服务端原子记录“键 -> 处理中/结果”，相同键返回同一结果。

幂等记录要定义作用域、参数一致性、TTL 和并发竞争语义。幂等不是简单缓存：同一键配不同请求体应拒绝，首次仍在处理中时也需明确响应。

### 熔断器

熔断器保护调用方免于反复等待已知故障依赖：

- **closed**：正常放行并统计失败。
- **open**：达到阈值后快速失败，给依赖恢复空间。
- **half-open**：冷却后只放少量探测；成功则 closed，失败则重新 open。

熔断器应按依赖/操作维度管理，并只统计代表依赖健康度的失败。用户 400 错误不应使服务熔断。分布式实例各有本地熔断状态通常足够，强行共享反而引入新依赖。

### 级联故障与有界并发

慢下游会占住 BFF 的 socket、Task、内存；等待请求越积越多，下游收到超时重试后更慢，最终扩散到其他服务。`asyncio` 能承载很多 Task，却不能创造无限的数据库连接和下游容量。

使用 semaphore/连接池形成 bulkhead（舱壁），给不同依赖隔离容量；队列也必须有上限，满时尽早拒绝或降级。再结合 deadline、熔断、负载削减和可观测性，才能控制级联。

## API

| API/模式 | 用途 | 关键点 |
|---|---|---|
| `asyncio.gather()` | 并发聚合独立结果 | 默认首个异常传播，其他 awaitable 不保证自动取消 |
| `asyncio.TaskGroup` | 结构化并发多个依赖 | 首个非取消失败会取消同组任务；异常按规则聚合或重抛 |
| `asyncio.timeout(seconds)` | 为一段异步操作设置 deadline | 超时转为 `TimeoutError`，取消需可传播 |
| `asyncio.Semaphore(n)` | 限制进入依赖的并发量 | 容量应对应真实下游承载力 |
| `asyncio.sleep(delay)` | 非阻塞退避 | delay 应计入总 deadline |
| `random.uniform(0, cap)` | full jitter | 测试时注入固定随机种子或 delay 函数 |
| 幂等键 | 让重复写请求返回同一结果 | 服务端需原子去重并校验参数 |
| circuit breaker | 失败达阈值后快速拒绝 | closed/open/half-open 状态机 |

## 完整原创可运行示例

以下纯标准库程序模拟 BFF。它对 profile 和 orders 并发聚合；orders 前两次出现瞬态错误，重试采用指数退避 + full jitter；所有下游调用经过 semaphore。熔断器可复用到连续失败场景；写接口则用幂等键去重。

```python
import asyncio
import random
import time
from collections.abc import Awaitable, Callable
from dataclasses import dataclass, field
from enum import Enum, auto
from typing import TypeVar


T = TypeVar("T")


class TransientError(Exception):
    pass


class CircuitOpen(Exception):
    pass


class State(Enum):
    CLOSED = auto()
    OPEN = auto()
    HALF_OPEN = auto()


@dataclass
class CircuitBreaker:
    threshold: int = 3
    recovery_seconds: float = 0.5
    state: State = State.CLOSED
    failures: int = 0
    opened_at: float = 0.0
    probe_in_flight: bool = False
    lock: asyncio.Lock = field(default_factory=asyncio.Lock)

    async def before_call(self) -> bool:
        async with self.lock:
            if self.state is State.OPEN:
                if time.monotonic() - self.opened_at < self.recovery_seconds:
                    raise CircuitOpen("dependency circuit is open")
                self.state = State.HALF_OPEN
            if self.state is State.HALF_OPEN:
                if self.probe_in_flight:
                    raise CircuitOpen("recovery probe is already running")
                self.probe_in_flight = True
                return True
            return False

    async def abandon_probe(self) -> None:
        async with self.lock:
            self.probe_in_flight = False

    async def record_success(self) -> None:
        async with self.lock:
            self.state = State.CLOSED
            self.failures = 0
            self.probe_in_flight = False

    async def record_failure(self) -> None:
        async with self.lock:
            self.probe_in_flight = False
            self.failures += 1
            if self.state is State.HALF_OPEN or self.failures >= self.threshold:
                self.state = State.OPEN
                self.opened_at = time.monotonic()


async def resilient_call(
    operation: Callable[[], Awaitable[T]],
    *,
    breaker: CircuitBreaker,
    bulkhead: asyncio.Semaphore,
    attempts: int = 3,
    attempt_timeout: float = 0.2,
) -> T:
    last_error: Exception | None = None
    for attempt in range(attempts):
        is_probe = await breaker.before_call()
        outcome_recorded = False
        try:
            async with bulkhead:
                async with asyncio.timeout(attempt_timeout):
                    result = await operation()
        except (TransientError, TimeoutError) as error:
            last_error = error
            await breaker.record_failure()
            outcome_recorded = True
            if attempt + 1 == attempts:
                break
            cap = min(0.2, 0.03 * (2**attempt))
            await asyncio.sleep(random.uniform(0, cap))
        except Exception:
            # 永久性错误直接传播，不污染依赖健康度，也不重试。
            raise
        else:
            await breaker.record_success()
            outcome_recorded = True
            return result
        finally:
            # 永久错误或调用者取消也不能把 half-open 探测位永久占住。
            if is_probe and not outcome_recorded:
                await breaker.abandon_probe()
    assert last_error is not None
    raise last_error


attempts_by_user: dict[str, int] = {}
idempotent_results: dict[str, dict[str, str]] = {}
idempotent_in_flight: dict[str, tuple[str, asyncio.Future[dict[str, str]]]] = {}
idempotency_lock = asyncio.Lock()


async def profile_service(user_id: str) -> dict[str, str]:
    await asyncio.sleep(0.05)
    return {"id": user_id, "name": "Ada"}


async def orders_service(user_id: str) -> list[str]:
    await asyncio.sleep(0.04)
    count = attempts_by_user.get(user_id, 0) + 1
    attempts_by_user[user_id] = count
    if count < 3:
        raise TransientError(f"orders temporary failure #{count}")
    return ["order-7", "order-9"]


async def create_payment(idempotency_key: str, amount: str) -> dict[str, str]:
    async with idempotency_lock:
        previous = idempotent_results.get(idempotency_key)
        if previous is not None:
            if previous["amount"] != amount:
                raise ValueError("idempotency key reused with different payload")
            return previous

        pending = idempotent_in_flight.get(idempotency_key)
        if pending is not None:
            pending_amount, future = pending
            if pending_amount != amount:
                raise ValueError("idempotency key reused with different payload")
            owner = False
        else:
            future = asyncio.get_running_loop().create_future()
            idempotent_in_flight[idempotency_key] = (amount, future)
            owner = True

    if not owner:
        return await asyncio.shield(future)

    try:
        await asyncio.sleep(0.03)
        result = {"payment_id": "pay-101", "amount": amount}
        async with idempotency_lock:
            idempotent_results[idempotency_key] = result
            if not future.done():
                future.set_result(result)
        return result
    except BaseException as error:
        async with idempotency_lock:
            if not future.done():
                future.set_exception(error)
        raise
    finally:
        async with idempotency_lock:
            idempotent_in_flight.pop(idempotency_key, None)


async def bff_home(user_id: str) -> dict[str, object]:
    bulkhead = asyncio.Semaphore(4)
    profile_breaker = CircuitBreaker()
    orders_breaker = CircuitBreaker()

    async with asyncio.timeout(0.8):  # 包括尝试、退避与聚合的总预算
        profile, orders = await asyncio.gather(
            resilient_call(
                lambda: profile_service(user_id),
                breaker=profile_breaker,
                bulkhead=bulkhead,
            ),
            resilient_call(
                lambda: orders_service(user_id),
                breaker=orders_breaker,
                bulkhead=bulkhead,
            ),
        )
    return {"profile": profile, "orders": orders}


async def main() -> None:
    random.seed(7)  # 仅为了让演示输出时序可复现
    print(await bff_home("42"))
    first = await create_payment("checkout-42-v1", "19.99")
    repeated = await create_payment("checkout-42-v1", "19.99")
    print("same payment:", first == repeated, repeated)


if __name__ == "__main__":
    asyncio.run(main())
```

运行：

```bash
python chapter10_resilient_bff.py
```

::: warning 示例边界
示例用锁和共享 Future 处理单事件循环中的并发重复请求，但内存状态仍不能承受多实例或重启。生产系统应在持久存储中以唯一约束/事务原子登记幂等键、请求摘要和处理中/完成状态。熔断器也应按应用生命周期复用，而不是像演示的 `bff_home()` 一样每请求新建。
:::

## 执行流程

1. BFF 建立 800 ms 总预算，同时启动 profile 和 orders 调用。
2. 每次调用先检查熔断器，再竞争容量为 4 的 semaphore。
3. profile 首次成功；orders 前两次抛 `TransientError`。
4. orders 失败被记录，随后按指数上限和 full jitter 非阻塞等待。
5. 第三次 orders 成功，熔断器清零失败计数，聚合返回两个结果。
6. payment 首次以幂等键创建结果；第二次相同键和参数直接得到同一逻辑结果。
7. 若连续失败达到阈值，熔断器进入 open；冷却后只允许一个 half-open 探测。

真实 BFF 中 breaker 和 bulkhead 都应按“下游依赖/操作类别”长期复用。若每请求创建，熔断器看不到跨请求失败，semaphore 也不能限制全局并发。

## 错误陷阱

- **所有异常都重试**：参数、权限和业务拒绝不会自行恢复。只重试明确的瞬态错误。
- **无 jitter 的固定退避**：大量实例同步重试形成惊群。使用 full/equal/decorrelated jitter 策略之一。
- **只限制重试次数，不设总 deadline**：每次超时加退避后响应仍可能极慢。统一预算。
- **重试非幂等写操作**：超时后重复扣款或下单。使用稳定幂等键和服务端原子去重。
- **每请求创建熔断器**：状态无法跨请求积累，等于没有熔断。按依赖长期持有。
- **把所有错误计入熔断**：客户端 4xx 导致健康依赖被错误隔离。只统计健康相关失败。
- **half-open 放行全部流量**：恢复中的服务再次被洪峰击倒。仅允许少量探测。
- **创建无限 Task 再在函数内部 semaphore**：任务对象和排队内存仍无限。入口队列也要有界并及早拒绝。
- **所有依赖共用一个 semaphore**：慢推荐服务耗尽槽位，阻塞关键用户服务。按依赖做 bulkhead 隔离。
- **降级掩盖关键数据错误**：对必需依赖返回“空数据”可能产生错误业务决策。先分类必需/可选。
- **忽略取消传播**：调用方已超时，下游仍运行并继续占资源。客户端、服务端和数据库层都应感知 deadline。
- **重试层叠**：网关、BFF、服务和数据库各重试 3 次，最坏调用数乘法增长。指定单一重试责任层。

## 现代Python补充

### Python 3.11+

- `asyncio.timeout()` 是表达总 deadline 的核心工具。它通过取消当前 Task 实现，因此依赖代码不应吞掉 `CancelledError`。
- `TaskGroup` 适合“任一必需依赖失败即取消同组”的聚合；`gather(return_exceptions=True)` 更适合逐项收集后按必需/可选规则降级。
- `ExceptionGroup` 与 `except*` 可分别处理并发产生的超时和领域异常，但不要因此丢失每个依赖的标签、耗时与尝试次数。
- `asyncio.Semaphore` 只限制单进程 loop 内并发。多实例总容量还需连接池、队列、服务端限流和部署副本策略共同约束。
- `ContextVar` 可传播 trace ID、deadline 和幂等键；跨 HTTP 时仍要显式写入受信任的 header，并防止外部伪造内部身份信息。

可观测性是韧性机制的一部分：至少记录调用结果、延迟分位数、in-flight 数、排队时间、重试原因、熔断状态和降级比例。只有错误率没有基数和延迟，无法判断熔断阈值是否合理。

## 实践清单

- [ ] BFF 只承载客户端聚合/适配，领域规则留在领域服务。
- [ ] 将依赖标为必需或可选，并定义明确降级结果。
- [ ] 入口 deadline 向下游传播，各尝试与退避共享该预算。
- [ ] 只重试瞬态、可安全重试的操作，并加入随机 jitter。
- [ ] 避免多层重复重试，评估最坏放大倍数。
- [ ] 写操作使用幂等键，服务端以原子存储校验键和请求参数。
- [ ] 熔断器按依赖复用，限制 half-open 探测并正确分类失败。
- [ ] 为每个依赖设置独立 bulkhead、连接池和有界入口队列。
- [ ] 对过载尽早拒绝或降级，不让无限 Task 留在内存等待。
- [ ] 演练慢响应、部分失败、进程重启、网络分区和恢复洪峰。
- [ ] 监控尾延迟、重试率、熔断状态、并发量与降级率。
