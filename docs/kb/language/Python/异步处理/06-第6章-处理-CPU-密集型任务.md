::: abstract 本章定位
`asyncio` 擅长让等待重叠，却不会自动加速占满 CPU 的 Python 代码。本章讨论如何把计算拆给多个进程，同时让事件循环继续服务 I/O。笔记按原书第 6 章的主题重组，不复述原文。
:::

## 本章目标/地图

- 区分 I/O 密集型与 CPU 密集型工作，解释 CPU 代码为何会阻塞事件循环。
- 掌握 `multiprocessing.Process`、进程池与 `ProcessPoolExecutor` 的取舍。
- 用 `loop.run_in_executor()` 把进程池结果接回协程世界。
- 用 MapReduce 理解“可并行分片 + 汇总”的计算结构。
- 识别 pickling、进程启动、共享状态、锁以及多进程多事件循环的边界。

```text
CPU 工作进入协程
    |
    +-- 很短：直接计算
    |
    +-- 可切成独立分片：ProcessPoolExecutor -> Map -> Reduce
    |
    +-- 独立长期进程：multiprocessing.Process
    |
    +-- 每个进程还要做异步 I/O：每进程各自创建一个 event loop
```

## 概念精讲

### 事件循环不是计算调度器

事件循环通常运行在一个线程中。协程只有在 `await` 一个尚未完成的操作时才交还控制权；纯 Python 循环不会因为写在 `async def` 中就自动让步。一次 500 ms 的计算意味着同一 loop 上的定时器、socket 回调和其他任务至少被拖延 500 ms。

线程池适合阻塞 I/O，但在常规 CPython 中，两个执行 Python 字节码的线程受 GIL 约束，未必能并行利用多个核心。多个进程有各自的解释器和 GIL，因而是本章处理纯 Python CPU 计算的主要工具。代价是启动、序列化和进程间通信。

### `Process` 与进程池

`multiprocessing.Process` 给予生命周期、进程函数和 IPC 的直接控制，适合少量长期 worker。大量短任务若逐个创建进程，启动成本会淹没收益。`ProcessPoolExecutor` 保留固定 worker，并提供与 `asyncio` 易于衔接的 `Future` 接口，适合请求式计算。

进程池不是“越大越快”。通常从可用 CPU 数附近开始测量；容器 CPU 配额、内存带宽、数据复制量都会改变最佳值。计算片段过小也不值得跨进程。

### MapReduce

MapReduce 把问题分成两层：

1. **Map**：每个输入分片独立转换为局部结果。
2. **Reduce**：将局部结果合并成最终结果。

能否高效并行，关键不是 API，而是 Map 阶段是否独立、数据是否足够粗粒度，以及 Reduce 是否成为新瓶颈。词频、日志统计、分块校验和都适合这种结构；每一步依赖上一步的递推则不适合直接 Map。

### Pickling 是进程边界

传给 worker 的可调用对象、参数和返回值需要经过 pickle。模块顶层函数、基本容器和简单数据类通常可用；lambda、嵌套函数、打开的 socket、事件循环、协程对象和锁通常不能直接传递。即使对象可 pickle，大对象的复制成本也可能很高。

因此应传“计算需要的最小数据”，并让 worker 返回紧凑结果。进程入口必须受 `if __name__ == "__main__":` 保护，尤其在采用 `spawn` 的系统上，否则子进程导入模块时可能递归创建进程。

### 共享状态、锁和消息传递

进程默认不共享普通 Python 内存。`multiprocessing.Value`、`Array`、共享内存或 `Manager` 可以共享数据；复合的“读-改-写”仍需 `multiprocessing.Lock` 保护。Manager 代理方便但每次访问都可能跨进程通信，不应把它当普通字典高频修改。

优先选择 worker 返回局部值、父进程汇总的消息传递模式。共享锁应只保护很短的同步代码，绝不能在持有进程锁时等待网络或执行大计算。

### 多进程、多事件循环

事件循环不能在进程之间共享。若每个进程都承担异步 I/O，应让各进程在自己的入口里调用 `asyncio.run()`，各自创建 loop。不要把 loop、Task 或 Future 作为进程参数；父子进程间用 pipe、queue、socket 等 IPC 交换可序列化消息。

## API

| API | 用途 | 关键点 |
|---|---|---|
| `multiprocessing.Process(target=..., args=...)` | 创建独立进程 | 显式 `start()`、`join()`；入口需可导入 |
| `multiprocessing.Lock()` | 保护进程间共享临界区 | 不同于 `asyncio.Lock`，会阻塞调用线程 |
| `multiprocessing.Value/Array` | 小型共享值或数组 | 复合更新仍要考虑原子性 |
| `concurrent.futures.ProcessPoolExecutor` | 复用多个 worker 进程 | 支持 context manager，退出时回收进程 |
| `loop.run_in_executor(executor, func, *args)` | 将阻塞调用提交给 executor | 返回可 `await` 的 asyncio Future |
| `asyncio.get_running_loop()` | 获取当前运行中的 loop | 应在协程或回调内部调用 |
| `asyncio.run(coro)` | 创建、运行并关闭一个 loop | 可作为每个子进程的异步入口 |

`run_in_executor()` 只接收位置参数。需要关键字参数时可用 `functools.partial()` 包装。将 executor 传为 `None` 会使用默认**线程池**，并不会自动改用进程池。

## 完整原创可运行示例

下面的程序用进程池统计若干文本分片中的单词频率。Map 在多个进程中执行；一个心跳协程同时证明主事件循环没有被计算长期占住；Reduce 留在父进程完成。

```python
import asyncio
import os
from collections import Counter
from concurrent.futures import ProcessPoolExecutor


def count_words(chunk: str) -> dict[str, int]:
    """进程 worker 必须是模块顶层函数，返回值也必须可 pickle。"""
    # 重复计算只是为了让示例明显表现出 CPU 工作；业务代码应做真实计算。
    words = chunk.lower().split()
    checksum = 0
    for number in range(900_000):
        checksum = (checksum + number * number) % 97
    result = Counter(words)
    result[f"worker-{os.getpid()}-checksum-{checksum}"] += 0
    return dict(result)


def reduce_counts(parts: list[dict[str, int]]) -> Counter[str]:
    total: Counter[str] = Counter()
    for part in parts:
        total.update(part)
    return total


async def heartbeat(stop: asyncio.Event) -> None:
    while not stop.is_set():
        print("event loop is responsive")
        try:
            await asyncio.wait_for(stop.wait(), timeout=0.2)
        except TimeoutError:
            pass


async def main() -> None:
    chunks = [
        "asyncio handles waiting while processes handle computation",
        "process pools allow computation to use several CPU cores",
        "map creates local results and reduce combines results",
        "small computation may cost less without a process pool",
    ]
    stop = asyncio.Event()
    pulse = asyncio.create_task(heartbeat(stop))
    loop = asyncio.get_running_loop()

    try:
        workers = min(4, os.cpu_count() or 1)
        with ProcessPoolExecutor(max_workers=workers) as pool:
            pending = [
                loop.run_in_executor(pool, count_words, chunk)
                for chunk in chunks
            ]
            mapped = await asyncio.gather(*pending)
        print("top words:", reduce_counts(mapped).most_common(8))
    finally:
        stop.set()
        await pulse


if __name__ == "__main__":
    asyncio.run(main())
```

运行：

```bash
python chapter06_map_reduce.py
```

## 执行流程

1. 主进程由 `asyncio.run()` 创建唯一的主事件循环。
2. 心跳 Task 每 200 ms 让出控制权并打印状态。
3. `ProcessPoolExecutor` 启动最多 4 个 worker 进程。
4. 每个 `run_in_executor()` 将顶层函数和一个字符串分片序列化给 worker。
5. worker 独立计算并把字典结果序列化回主进程。
6. `asyncio.gather()` 在所有 Map Future 完成后返回结果列表。
7. 父进程执行轻量 Reduce，随后关闭进程池并停止心跳。

这个例子中 `with ProcessPoolExecutor(...)` 的退出会同步等待 worker。若进程池是应用级长期资源，应在应用关闭阶段统一 `shutdown()`，不要每个请求创建一次。

## 错误陷阱

- **把 CPU 循环直接放进协程**：没有 `await` 的计算会冻结 loop。应拆分并提交进程池。
- **误用默认 executor**：`run_in_executor(None, ...)` 是线程池；纯 Python CPU 工作通常不能借此扩展多核。
- **遗漏 `__main__` 保护**：在 `spawn` 下会递归导入并创建子进程。
- **提交 lambda 或闭包**：pickle 常无法定位这类函数。使用模块顶层函数。
- **任务粒度太小**：进程启动和序列化比计算更贵。应批处理并基准测试。
- **传递巨大对象**：复制占用时间和内存。传路径、共享内存描述符或压缩后的必要字段。
- **以为取消 Future 会终止计算**：worker 中已经开始的函数通常仍会运行；需要可协作的进程间取消协议，或终止进程。
- **用 `asyncio.Lock` 保护多进程数据**：它只协调同一个事件循环里的 Task，不是进程锁。
- **锁中执行 await/慢计算**：会放大竞争甚至死锁。临界区只做最小状态变更。
- **fork 后复用现成 loop**：文件描述符和内部状态可能不安全。子进程重新 `asyncio.run()`。

## 现代Python补充

### Python 3.11+

- `asyncio.TaskGroup` 提供结构化并发，但它管理的是 Task 生命周期，不会把 CPU 计算变成并行；仍需进程池。
- `asyncio.timeout()` 可以限制“等待计算结果”的时间，但超时不保证杀死已在 worker 中运行的函数。
- `ExceptionGroup` 能汇集 TaskGroup 中多个失败。进程 worker 的异常会通过 Future 重新抛出，应在聚合层区分输入错误与进程崩溃。
- `asyncio.Runner` 适合需要在同一线程中多次运行顶层异步调用的场景；它仍不允许多个 loop 同时运行在同一线程。
- 在现代 Python 中应优先 `get_running_loop()`，避免依赖旧式隐式 loop 获取行为。

进程启动方式具有平台差异。macOS 和 Windows 常使用 `spawn`，Linux 的默认及版本演进有所不同。不要依赖 fork 复制的隐式全局状态；显式创建资源、保持入口可导入，代码更可移植。

## 实践清单

- [ ] 用 loop 延迟、CPU 利用率和耗时确认瓶颈确实是 CPU。
- [ ] 确认工作可拆成互不依赖、粒度足够大的分片。
- [ ] worker 使用模块顶层函数，输入和输出可 pickle。
- [ ] 进程池按应用生命周期复用，并设置合理 worker 数。
- [ ] 大数据传输前评估序列化和内存复制成本。
- [ ] 优先返回局部结果再汇总，减少共享可变状态。
- [ ] 必须共享时使用进程级同步原语，并缩短锁持有时间。
- [ ] 为超时、worker 异常、进程池损坏和应用关闭设计处理路径。
- [ ] 每个需要 asyncio 的子进程自己创建并关闭事件循环。
- [ ] 在目标操作系统和部署 CPU 配额下做基准测试。
