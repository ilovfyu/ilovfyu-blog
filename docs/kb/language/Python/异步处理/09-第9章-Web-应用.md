::: abstract 本章定位
Web 框架把 socket、HTTP 解析和请求生命周期包装起来，但不会消除并发边界。本章以 `aiohttp` 为主线，比较 ASGI/WSGI，并说明 Starlette 与 Django async 视图中何时仍会阻塞事件循环。
:::

## 本章目标/地图

- 使用 `aiohttp.web` 构建异步 HTTP 服务，并正确管理 `ClientSession`。
- 理解 WSGI 的同步调用模型与 ASGI 的异步消息模型。
- 认识 Starlette 的 ASGI 原生接口和 Django 的 async 支持范围。
- 在请求处理中并发执行独立 I/O，同时设置超时和清理资源。
- 识别 ORM、模板、SDK、CPU 计算等阻塞边界，选择异步 API 或线程隔离。

```text
HTTP client
    -> server/protocol
    -> middleware
    -> async handler
         |-- await async dependency
         |-- await aiohttp ClientSession request
         `-- await asyncio.to_thread(legacy blocking call)
    -> response
```

## 概念精讲

### `aiohttp` 的两面

`aiohttp` 同时提供异步 HTTP client 和 server。服务端以 `Application` 保存路由、middleware 和生命周期资源；handler 接收 `Request` 并返回 `Response`。客户端应复用 `ClientSession`，以复用连接池和 DNS/TLS 成本，不能每个请求新建一个 session。

读取响应体也属于异步工作。`async with session.get(...) as response` 确保响应释放回连接池；应检查状态码，并为连接、读取和总耗时设置 timeout。

### 请求级并发

页面经常依赖互不相关的数据源。若先 await 用户服务再 await 推荐服务，总耗时接近两者之和；并发启动可接近较慢者耗时。但并发必须有边界：一次请求生成 N 个下游调用，乘以并发请求数后可能压垮连接池和下游。本章只建立 Web 层原则，完整韧性治理留到第 10 章。

### WSGI 与 ASGI

WSGI 以同步可调用对象处理 HTTP 请求，接口核心是 `environ` 和 `start_response`。它成熟且生态广，但规范本身不表达 WebSocket，也不以 `await` 表达长连接与异步 I/O。通过线程运行 WSGI 并不等于应用内部成为异步。

ASGI 以 `scope`、`receive`、`send` 三元组定义异步应用，除 HTTP 外还能表达 WebSocket 和 lifespan。一次 ASGI 调用可在等待 I/O 时让出 loop。ASGI 是服务器和应用的协议，不等于“所有被调用代码都非阻塞”。

### Starlette

Starlette 是轻量 ASGI 工具包，路由、中间件、请求响应、WebSocket 与 lifespan 都围绕 ASGI 构建。`async def` endpoint 直接在 event loop 执行；同步 `def` endpoint 通常由框架在线程池执行。不要通过把阻塞函数包一层 `async def` 来欺骗框架，那反而会让它进入 loop。

### Django async

Django 可运行于 ASGI 并支持 async view、async middleware 及逐步扩展的异步 ORM 接口。同步 middleware 会迫使适配边界切换执行模式；仍只有同步 API 的组件，应通过 Django 提供的 sync/async 适配工具隔离，并遵守数据库连接的线程敏感性。

在 async view 中直接调用同步 ORM 或其他 async-unsafe 组件可能阻塞，或被 Django 主动拒绝。是否可异步必须按当前 Django 版本逐 API 核对，而不能从函数名称猜测。

### 阻塞边界

以下代码即使位于 async handler 中也可能阻塞：同步 ORM、`requests`、文件操作、模板中的慢同步函数、密码哈希、图片处理、巨大 JSON 编解码。处理原则：

- 有成熟异步 API：直接 `await`。
- 阻塞 I/O 且无法替换：有界线程池 / `to_thread()`。
- 纯 Python CPU 工作：进程池或外部任务系统。
- 长任务：接受请求后排队，返回任务 ID，不占住 Web worker。

## API

| API | 用途 | 关键点 |
|---|---|---|
| `web.Application()` | aiohttp 服务端应用容器 | 注册路由、middleware、cleanup context |
| `web.get/post(path, handler)` | 定义路由 | handler 返回 `StreamResponse` 子类 |
| `web.json_response(data, status=...)` | 生成 JSON 响应 | 大对象编码也可能占 CPU |
| `aiohttp.ClientSession` | 客户端连接池与请求入口 | 按应用生命周期复用并关闭 |
| `aiohttp.ClientTimeout` | 客户端超时配置 | 区分 total/connect/read 等阶段 |
| `response.raise_for_status()` | 将非成功状态转为异常 | 业务可按状态码细分策略 |
| `web.AppRunner` / `web.TCPSite` | 以编程方式启动服务 | 适合集成测试和多站点 |
| ASGI `app(scope, receive, send)` | 异步服务协议入口 | server 驱动消息收发 |
| `asgiref.sync.sync_to_async` | Django/ASGI 同步边界适配 | 线程敏感资源需正确配置 |

## 完整原创可运行示例

下面只依赖 `aiohttp`。同一个进程启动两个本地下游接口和一个聚合页面；聚合 handler 并发请求两个接口，同时把传统阻塞审计函数放到线程中。无需外部网络。

```python
import asyncio
import time
from collections.abc import AsyncIterator

from aiohttp import ClientSession, ClientTimeout, web


SESSION_KEY = web.AppKey("session", ClientSession)


async def session_context(app: web.Application) -> AsyncIterator[None]:
    timeout = ClientTimeout(total=1.0, connect=0.3)
    async with ClientSession(timeout=timeout) as session:
        app[SESSION_KEY] = session
        yield


async def user_api(request: web.Request) -> web.Response:
    await asyncio.sleep(0.12)
    return web.json_response({"id": request.match_info["user_id"], "name": "Ada"})


async def notices_api(request: web.Request) -> web.Response:
    await asyncio.sleep(0.18)
    return web.json_response({"unread": 3})


async def fetch_json(session: ClientSession, url: str) -> dict:
    async with session.get(url) as response:
        response.raise_for_status()
        return await response.json()


def blocking_audit(user_id: str) -> str:
    time.sleep(0.05)  # 模拟旧同步 SDK 或文件审计
    return f"audit:{user_id}"


async def dashboard(request: web.Request) -> web.Response:
    user_id = request.match_info["user_id"]
    base = f"{request.scheme}://{request.host}"
    session = request.app[SESSION_KEY]

    try:
        async with asyncio.timeout(0.8):
            user, notices, audit = await asyncio.gather(
                fetch_json(session, f"{base}/internal/users/{user_id}"),
                fetch_json(session, f"{base}/internal/notices"),
                asyncio.to_thread(blocking_audit, user_id),
            )
    except TimeoutError:
        raise web.HTTPGatewayTimeout(text="dependency timeout")
    return web.json_response({"user": user, "notices": notices, "audit": audit})


async def main() -> None:
    app = web.Application()
    app.cleanup_ctx.append(session_context)
    app.add_routes(
        [
            web.get("/internal/users/{user_id}", user_api),
            web.get("/internal/notices", notices_api),
            web.get("/dashboard/{user_id}", dashboard),
        ]
    )

    runner = web.AppRunner(app)
    await runner.setup()
    site = web.TCPSite(runner, "127.0.0.1", 0)
    await site.start()
    port = site._server.sockets[0].getsockname()[1]

    try:
        async with ClientSession() as client:
            async with client.get(f"http://127.0.0.1:{port}/dashboard/42") as response:
                print(response.status, await response.json())
    finally:
        await runner.cleanup()


if __name__ == "__main__":
    asyncio.run(main())
```

安装并运行：

```bash
python -m pip install aiohttp
python chapter09_web_app.py
```

## 执行流程

1. `AppRunner` 启动 aiohttp 应用，系统选择随机空闲端口。
2. cleanup context 创建一个应用级 `ClientSession`，所有 handler 共享连接池。
3. 演示 client 请求 `/dashboard/42`。
4. dashboard 同时启动用户接口、通知接口和线程中的同步审计。
5. 两个内部 HTTP 请求在等待时都把控制权交回 loop，因此延迟重叠。
6. 外层 `asyncio.timeout()` 给整个依赖聚合设置 800 ms 预算。
7. 聚合成功后返回 JSON；失败则转换成网关超时。
8. `runner.cleanup()` 停止站点并运行 cleanup context，关闭 session 与连接池。

示例用私有属性 `_server` 只为自动化演示取随机端口；生产启动通常交给 `web.run_app()` 或部署服务器，不应依赖该私有属性。

## 错误陷阱

- **每个请求创建 `ClientSession`**：失去连接池，增加 socket/TLS 开销。按应用生命周期复用。
- **忘记释放 response**：连接不能及时回池。使用 `async with` 或显式读取/释放。
- **async handler 调用 `requests`/同步 ORM**：阻塞整个 worker loop。换异步客户端或线程隔离。
- **把 CPU 重活交给 `to_thread()`**：纯 Python 计算受 GIL 限制，还会挤占阻塞 I/O 线程。用进程/任务系统。
- **无超时等待下游**：请求和连接池槽位永久占用。设置阶段超时和整体 deadline。
- **盲目 `gather()` 大量调用**：单请求扇出乘以流量造成下游洪峰。添加 semaphore/连接池限制。
- **认为 ASGI 自动异步化同步代码**：ASGI 只定义调用协议，阻塞函数仍阻塞。
- **WSGI/ASGI 适配层过多**：频繁跨线程或执行模式切换增加复杂性与开销。保持中间件栈一致。
- **Django async view 直接碰 async-unsafe API**：可能阻塞或触发保护错误。按版本使用异步 ORM或 `sync_to_async`。
- **把长后台任务留在请求 Task**：客户端断开、进程重启会令任务失控。使用可靠任务队列。

## 现代Python补充

### Python 3.11+

- `asyncio.timeout()` 支持围绕一组依赖设置可读的总预算；嵌套阶段预算时要确保总和不超过请求 deadline。
- `TaskGroup` 适合结构化启动多个依赖调用。一个子任务失败时会取消同组任务并以 `ExceptionGroup` 汇报，语义不同于 `gather(return_exceptions=True)`。
- `asyncio.to_thread()` 传播 `ContextVar`，有利于把 trace/request ID 带入同步边界；日志库仍需配置读取该 ContextVar。
- ASGI lifespan 是初始化和关闭连接池、客户端与缓存的自然位置；Starlette 推荐 lifespan context，而不是在 import 时创建异步资源。
- Django 的 async 能力持续演进。应以部署版本文档为准，特别检查事务、持久数据库连接、中间件和 ORM 方法是否支持异步。

Web 服务还要让 server 的 keep-alive、最大请求体、连接数和优雅关闭配置与应用超时对齐。应用超时不是唯一防线，反向代理与下游客户端也应有一致但逐层收紧的预算。

## 实践清单

- [ ] 明确部署接口是 ASGI 还是 WSGI，并保持中间件执行模式一致。
- [ ] ClientSession、数据库池等资源按应用生命周期创建与关闭。
- [ ] 每个外部调用设置连接、读取和总超时。
- [ ] 仅并发真正独立的依赖，并限制每请求和全局扇出。
- [ ] 清点 handler 内同步 ORM、SDK、文件 I/O 和 CPU 重活。
- [ ] 线程边界遵守库的线程安全与连接亲和要求。
- [ ] 对客户端断开、Task 取消和应用优雅关闭进行测试。
- [ ] 状态码区分输入错误、下游失败、超时和内部错误。
- [ ] 日志与 trace 使用 ContextVar 传递关联 ID。
- [ ] Starlette/Django 行为以实际锁定版本的官方文档为准。
