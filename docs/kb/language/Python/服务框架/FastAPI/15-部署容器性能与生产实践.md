> 基线：FastAPI 0.141.1（latest 2026-07-29），Python 3.10+，Pydantic v2。代理细节见 [中间件 CORS 与反向代理](/kb/language/Python/服务框架/FastAPI/11-中间件-CORS-与反向代理/)，测试门禁见 [测试与调试](/kb/language/Python/服务框架/FastAPI/13-测试与调试/)，API 契约见 [OpenAPI 文档与客户端生成](/kb/language/Python/服务框架/FastAPI/14-OpenAPI-文档与客户端生成/)。

## 1. dev、run 与 Uvicorn

`fastapi dev main.py` 面向本地开发：自动 reload、监听本机、详细日志，不用于生产。`fastapi run main.py` 面向生产，底层运行 Uvicorn；FastAPI CLI 能从文件发现 `app`。也可直接：

```bash
uvicorn main:app --host 0.0.0.0 --port 8000
fastapi run main.py --host 0.0.0.0 --port 8000
```

`--reload` 与 `--workers` 互斥。生产不要 reload。单机非编排场景可 `fastapi run main.py --workers 4`；worker 是独立进程，内存、连接池、缓存、WebSocket 连接和定时任务均不共享。worker 数不是固定的 `2*CPU+1` 公式，应按 CPU/内存、阻塞比例和压测确定。每进程都加载大模型会倍增内存。

同步 `def` 路由由线程池运行；`async def` 中必须避免阻塞 I/O。CPU 密集工作会阻塞 event loop，移到进程池/任务队列或专用服务。增加 worker 只能缓解，不能修复无界资源和慢查询。

## 2. 最小生产应用

```python
# app/main.py
import logging
from contextlib import asynccontextmanager

from fastapi import FastAPI, Response, status

log = logging.getLogger("app")


@asynccontextmanager
async def lifespan(app: FastAPI):
    # 此处创建每 worker 独立的数据库/HTTP 连接池，并设置显式超时。
    app.state.ready = True
    log.info("application_started")
    try:
        yield
    finally:
        app.state.ready = False
        # 按依赖顺序停止消费、等待在途任务、关闭连接池。
        log.info("application_stopped")


app = FastAPI(lifespan=lifespan, docs_url=None, redoc_url=None)


@app.get("/live", include_in_schema=False)
def live() -> dict[str, str]:
    # 只判断进程/event loop 活着，不访问下游。
    return {"status": "alive"}


@app.get("/ready", include_in_schema=False)
def ready(response: Response) -> dict[str, str]:
    if not app.state.ready:
        response.status_code = status.HTTP_503_SERVICE_UNAVAILABLE
        return {"status": "not_ready"}
    return {"status": "ready"}


@app.get("/items/{item_id}")
def item(item_id: int) -> dict[str, int]:
    return {"item_id": item_id}
```

startup 不应让每个副本同时执行数据库迁移；Kubernetes 用 Job/init container，其他平台用独立 release step，并确保迁移兼容滚动发布。readiness 可检查关键本地初始化；若每次都深查所有下游，短暂数据库抖动会同时摘掉全部实例，放大故障。

## 3. 容器：一容器一服务主进程

生产通常基于官方 Python slim 镜像自行构建，不使用已弃用的 `tiangolo/uvicorn-gunicorn-fastapi` 镜像。示例三个文件是一个完整最小项目：

```text
.
├── app/main.py
├── requirements.txt
└── Dockerfile
```

```text
# requirements.txt，实际项目应由 lock 文件导出并包含所有传递依赖哈希
fastapi[standard]==0.141.1
```

```dockerfile
FROM python:3.12-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1 \
    PIP_NO_CACHE_DIR=1

WORKDIR /code
RUN addgroup --system app && adduser --system --ingroup app app
COPY requirements.txt .
RUN python -m pip install --upgrade pip && python -m pip install -r requirements.txt
COPY --chown=app:app app ./app
USER app
EXPOSE 8000
CMD ["fastapi", "run", "app/main.py", "--host", "0.0.0.0", "--port", "8000"]
```

必须使用 JSON exec form `CMD`，让 FastAPI 成为 PID 1 并直接收到 SIGTERM，lifespan 才能优雅关闭。先复制依赖清单利用构建缓存；加 `.dockerignore` 排除 `.git`、测试缓存、密钥。用固定基础镜像 digest、漏洞扫描、多阶段构建/无编译工具运行层、只读根文件系统、非 root 用户和最小 Linux capabilities。秘密通过平台 secret 注入，绝不 `COPY` 进镜像或写 ENV 层。

“一进程原则”指每容器通常一个应用主进程，让编排器负责副本、重启、资源限制和滚动更新，并非容器技术禁止子进程。Kubernetes/ECS/Nomad：通常一个 Uvicorn worker 每容器，多副本横向扩展。单机 Docker Compose 缺少成熟副本负载均衡时，一个容器 `--workers N` 可能更简单。不要同时按容器和内部 worker 双重过度扩容。

## 4. HTTPS、反向代理与网络

通常由云负载均衡器、Ingress、Traefik 或 Nginx 终止 TLS，应用容器走受控内网 HTTP。入口负责证书自动续期、TLS 版本/cipher、HTTP/2/3、HSTS；应用端口不暴露公网。

只有可信代理可传入时启用：

```bash
fastapi run app/main.py --proxy-headers --forwarded-allow-ips="10.0.0.10"
```

不要为省事在公网监听时信任 `*`。代理应设置 `X-Forwarded-For/Proto/Host`，WebSocket 转发 Upgrade，SSE 禁止 buffering 并增加 idle timeout。外部有剥离路径前缀时设置 `--root-path /api/v1`。限制请求体、header 数量/大小、连接和每 IP 速率通常在边缘执行，应用再做用户级配额。

## 5. 优雅关闭与滚动发布

典型流程：编排器发 SIGTERM；实例 readiness 变失败并从负载均衡摘除；留出传播时间；Uvicorn 停止接新请求并等待在途请求；lifespan finally 关闭消费者和连接池；超出 termination grace 后 SIGKILL。

长 SSE/WebSocket/大上传可能超过宽限期。发布前定义最大连接年龄和应用级“server restarting”通知，客户端指数退避重连。后台 `BackgroundTasks` 不具备持久可靠性，进程退出会丢失；重要任务进入外部队列并用幂等 consumer。Kubernetes 的 `terminationGracePeriodSeconds` 必须大于 server graceful timeout + preStop/摘流延迟。容器命令不能用 shell form，否则信号可能停在 shell。

## 6. 健康检查

- liveness：进程是否卡死，失败会重启；必须廉价，避免依赖数据库。
- readiness：是否能接新流量；启动、排空或关键资源不可用时 503。
- startup probe：慢启动服务在初始化完成前不被 liveness 误杀。

Docker 可由外部编排器请求 `/live`；镜像不一定需要安装 curl。Kubernetes 分开设置 initial delay、period、timeout、failure threshold。探针不要写日志 INFO 造成噪声，也不要公开内部版本和依赖详情。

## 7. 日志、指标与 tracing

日志输出 stdout/stderr，由平台采集，不写容器本地滚动文件。生产推荐结构化 JSON，至少含 timestamp、level、service、environment、request_id/trace_id、method、route template、status、duration；不要用原始 path 作为指标 label，避免 `/users/{id}` 产生高基数。脱敏 Authorization、Cookie、密码、token、个人信息和请求体。

核心 RED 指标：请求 Rate、Error、Duration；再看 event-loop lag、在途请求、worker 重启、CPU/RSS、连接池等待、DB/外部服务延迟、队列深度、WebSocket/SSE 连接数。直方图 bucket 应匹配 SLO。Prometheus 多 worker 模式需要正确的 multiprocess 方案，不能简单把每进程内存指标当全局。

OpenTelemetry 在入口提取/创建 trace context，HTTP/DB/消息调用传播上下文；采样率和尾采样兼顾成本与错误可见性。不要为每个流式 chunk 建 span。日志、指标、trace 使用同一 service/version/deployment 标识。可观测中间件与 `BaseHTTPMiddleware` 边界见 [中间件 CORS 与反向代理](/kb/language/Python/服务框架/FastAPI/11-中间件-CORS-与反向代理/)。

## 8. 性能实践

先定义延迟 SLO 和真实工作负载，再用固定环境压测，关注 p50/p95/p99、错误率、吞吐和资源，不追逐 hello-world benchmark。

- 使用 Pydantic response model/返回类型，FastAPI 可走高效序列化；避免无必要的 `jsonable_encoder` 和手工 `JSONResponse`。
- 所有出站 HTTP、DB 都设置连接、读取、写入、池等待超时；连接池上限按每 worker 乘总 worker 计算，不能压垮数据库。
- 消除 N+1、加索引、分页设上限；大响应使用 JSON Lines/流，但注意慢客户端 backpressure。
- 缓存只缓存可安全共享的数据，key 包含租户/权限/locale，设置 TTL 和失效策略，防缓存击穿。
- `async` 提升 I/O 并发而非单请求 CPU 速度；阻塞库用同步路由/线程，CPU 重任务用队列。
- GZip/Brotli 通常在边缘完成；小响应不压缩，SSE 不压缩。静态文件交给 CDN/object storage。
- 设置 worker/container CPU 与内存 requests/limits，压测后水平扩缩；CPU throttling 会直接推高尾延迟。

## 9. 安全清单

- 精确 CORS、TrustedHost；浏览器 Cookie 使用 `Secure`、`HttpOnly`、合适 `SameSite`，状态变更请求防 CSRF。
- 全链路 TLS；可信代理白名单；管理/docs/metrics 端点认证或网络隔离。
- 标准认证授权并默认拒绝；对象级权限不可只验证“已登录”。密钥短期化、轮换、最小权限。
- 请求体、上传、消息、查询复杂度、分页、连接、速率均设上限；压缩包防 zip bomb。
- 严格 Pydantic 输入模型 `extra="forbid"` 用在需要拒绝未知字段的边界；输出 response model 防字段泄露。
- 不把用户路径直接交给 FileResponse；防 SQL/命令/模板注入和 SSRF；URL 回调尤其限制内网地址。
- 依赖与镜像做 SCA/CVE 扫描，生成 SBOM、签名镜像；运行时非 root、只读文件系统、最小权限。
- 统一安全响应头由边缘或应用设置；错误不泄漏 traceback；审计高风险操作且保护审计日志。

## 10. 版本锁定与发布

`fastapi==0.141.1` 只锁直接依赖还不够，Starlette、Pydantic、Uvicorn/httpx 的变化也可能影响行为。使用 `uv.lock`、Poetry lock 或带 hashes 的 requirements 锁定**完整解析结果**；应用和测试安装同一个 lock。基础镜像固定 Python minor，严格环境可固定 digest。

升级流程：机器人开 PR；阅读 FastAPI/Starlette/Pydantic/Uvicorn release notes；运行单元、OpenAPI diff、集成和真实服务器冒烟测试；灰度/canary；监控错误与 p99 后扩量；保留可回滚镜像。不要在镜像构建中无约束 `pip install --upgrade` 获取“当时最新”。数据库 schema 使用向后兼容的 expand/migrate/contract，避免旧新副本滚动期间互不兼容。

生产发布清单：

1. 镜像可复现、扫描通过、非 root、无秘密，SBOM 和版本标签齐全。
2. migrations 独立且向后兼容；readiness/liveness/startup probe 验证通过。
3. TLS、proxy headers、root_path、Host/CORS、请求上限和限流经过入口实测。
4. graceful timeout、编排器宽限期、WebSocket/SSE 重连和可靠任务策略匹配。
5. 日志脱敏，指标与 trace 可关联，SLO 告警和 runbook 已配置。
6. OpenAPI breaking-change 与 SDK 检查通过，回滚步骤已演练。

## 11. 常见故障

- 容器立即退出：主进程结束、导入路径错误或未监听 `0.0.0.0`；看容器日志和 exit code。
- 反复重启但无应用异常：liveness 太严格、OOMKilled、CPU limit 或启动时间超过探针阈值。
- 只在多 worker 出错：使用了进程内全局状态、重复 scheduler、总连接池超额或文件锁假设错误。
- HTTPS 重定向循环/回调 URL 是 http：转发头未设置或 Uvicorn 不信任代理来源。
- 停止总被 SIGKILL：shell form 吞信号、长连接未排空、shutdown 清理无超时或 grace 太短。
- p99 高但平均正常：检查池等待、event-loop lag、GC/大对象、CPU throttling、慢查询与下游重试放大。
