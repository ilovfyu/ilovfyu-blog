> 基线：FastAPI 0.141.1、Python 3.10+、Pydantic v2、`Annotated`。

FastAPI 基于 ASGI、Starlette 和 AnyIO。高并发来自等待 I/O 时让出事件循环，不意味着一段 Python 代码能自动并行，也不意味着把所有函数改成 `async def` 就会变快。

## 1. `async def` 与 `def`

```python
import asyncio
import time

from fastapi import FastAPI

app = FastAPI()


@app.get("/async-io")
async def async_io() -> dict[str, str]:
    await asyncio.sleep(0.1)  # 代表支持 await 的 HTTP/DB 客户端
    return {"mode": "non-blocking"}


@app.get("/sync-io")
def sync_io() -> dict[str, str]:
    time.sleep(0.1)  # 普通 def 路径操作在线程池执行，不堵事件循环
    return {"mode": "thread-pool"}
```

选择规则：

- 第三方库提供可等待 API，就使用 `async def` 并 `await`。
- 库只有阻塞 API，优先普通 `def` 路径操作/依赖，让 FastAPI 在线程池执行。
- 不要在 `async def` 内直接调用 `time.sleep()`、`requests.get()`、同步数据库驱动或大文件同步 I/O，它们会冻结该 worker 的事件循环。
- 必须从 async 代码调用短小阻塞函数时，可用 `await anyio.to_thread.run_sync(fn)`；线程池容量有限，不能把它当无限队列。
- 普通工具函数不会因 FastAPI 自动进入线程池；只有由 FastAPI 调用的同步路径操作和依赖会被调度。`async def` 中直接调用普通函数仍在事件循环线程运行。

并发（任务交错）、并行（多个 CPU 同时执行）与 worker（独立进程）是不同概念。

## 2. CPU-bound 与多 worker

图片编码、大模型推理、压缩和大量纯 Python 计算属于 CPU-bound。线程通常受 GIL 限制，而且会与请求争用资源。小任务可使用进程池；重任务应投递到 Celery、Dramatiq、RQ 等外部作业系统，由独立 worker 执行。

Uvicorn 多 worker 利用多核并隔离故障：

```bash
uvicorn main:app --host 0.0.0.0 --port 8000 --workers 4
```

每个 worker 都是独立进程：全局字典、缓存、锁、连接池互不共享；总数据库连接数约为“每 worker 池大小 × worker 数”。容器编排中常由平台水平扩展，worker 数要结合 CPU、内存、连接限制和压测决定，不能机械采用某个公式。`--reload` 只用于开发，不能与生产 worker 策略混用。

## 3. `BackgroundTasks` 的完整示例与边界

```python
from pathlib import Path
from fastapi import BackgroundTasks, Depends, FastAPI, status
from pydantic import BaseModel, EmailStr

app = FastAPI()
LOG_FILE = Path("notifications.log")


class Message(BaseModel):
    email: EmailStr
    body: str


def write_notification(email: str, body: str) -> None:
    with LOG_FILE.open("a", encoding="utf-8") as file:
        file.write(f"to={email} body={body}\n")


def audit_tasks(tasks: BackgroundTasks) -> BackgroundTasks:
    # 同一个 BackgroundTasks 实例可由依赖与路径操作共同追加任务。
    tasks.add_task(write_notification, "audit@example.com", "request accepted")
    return tasks


@app.post(
    "/messages",
    status_code=status.HTTP_202_ACCEPTED,
    dependencies=[Depends(audit_tasks)],
)
def send_message(
    message: Message,
    tasks: BackgroundTasks,
) -> dict[str, str]:
    tasks.add_task(write_notification, message.email, message.body)
    return {"status": "accepted"}
```

安装 `email-validator`（或 `pydantic[email]`）后运行：

```bash
pip install "fastapi==0.141.1" "uvicorn[standard]" "pydantic[email]"
uvicorn main:app --reload
```

任务在响应发送后、**同一 Web 进程**执行，不是持久队列：进程崩溃或部署重启会丢任务；没有内建重试、去重、结果查询、跨机器调度或强交付保证。任务过慢仍占用该进程的线程/事件循环资源，异常也无法再改写已发送响应。

适合：短小、失败可容忍的日志、通知触发。支付、订单、视频处理、长耗时邮件、必须重试的任务应使用外部队列，并采用持久化 job、幂等键和 outbox 等模式解决“数据库提交成功但消息未投递”的原子性问题。不要把请求 Session、上传文件句柄等即将 teardown 的资源传给后台任务；只传 ID 和不可变数据，让任务自己获取资源。

## 4. lifespan 与资源池

应用级资源应在进程启动时创建、停机时释放。推荐 `lifespan` + `asynccontextmanager`：

```python
from contextlib import asynccontextmanager
from typing import AsyncIterator, TypedDict

import httpx
from fastapi import FastAPI, Request


class State(TypedDict):
    http: httpx.AsyncClient


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[State]:
    client = httpx.AsyncClient(timeout=httpx.Timeout(5.0))
    try:
        # yield 前：启动；yield 的 state 会复制到 request.state。
        yield {"http": client}
    finally:
        # yield 后：停止，即使服务异常退出流程也尽量清理。
        await client.aclose()


app = FastAPI(lifespan=lifespan)


@app.get("/github")
async def github(request: Request) -> dict[str, int]:
    response = await request.state.http.get("https://api.github.com")
    return {"status_code": response.status_code}
```

HTTP client、数据库 engine/连接池、模型和 producer 适合应用级生命周期；数据库 Session、事务、用户上下文适合请求依赖。池应复用，不能每请求创建 engine/client；但 Session 不可跨请求共享。

每个 worker 会各执行一次 lifespan，因此大型模型内存和连接池都会按 worker 复制。启动失败应让进程失败而不是带着半初始化资源提供服务；关闭设置合理 grace period，先停止接流量再清理。

## 5. 旧式 events 与挂载应用

旧 API：

```python
@app.on_event("startup")
async def startup() -> None:
    ...


@app.on_event("shutdown")
async def shutdown() -> None:
    ...
```

它仍可能出现在旧项目，但推荐 lifespan，因为获取与释放写在一个上下文中，不易漏掉对称清理。提供 `lifespan` 后，不应再期待同一 app 的 `startup`/`shutdown` handlers 同时执行；迁移时统一到 lifespan。

挂载的子应用拥有独立 ASGI 边界。主应用 lifespan 不会自动等价于每个 mount 子应用都完成其生命周期约定；部署前应对所用 Starlette/FastAPI 版本做启动与测试验证，必要时由顶层 lifespan 明确管理共享资源。

## 6. 取消、超时与资源上限

- 所有外部 I/O 都设置连接、读取和总超时；超时后正确释放响应和连接。
- 客户端断开可能触发取消。不要无条件捕获 `BaseException`；清理放在 `finally`，关键提交需设计幂等和一致性，而非简单屏蔽取消。
- 用 semaphore 限制昂贵下游调用并发，用队列提供背压；无限 `asyncio.create_task()` 会造成内存和下游雪崩。
- 不要创建“无人持有”的 task。需跨请求存活的任务使用 lifespan 管理的 task group 或外部队列，并在停机时取消/等待。
- 流式响应会延长请求资源生存时间；请求级 `yield` 清理时机见 [依赖注入系统](/kb/language/Python/服务框架/FastAPI/06-依赖注入系统/)。

## 7. 测试与生产观测

使用 `with TestClient(app) as client:`，上下文会运行 lifespan；异步测试使用 `httpx.AsyncClient` 配合 ASGI transport，并显式使用 lifespan manager。测试后台任务成功和失败分支，不要只断言 202。对超时、取消、池耗尽、worker 终止和优雅关停做集成测试。

生产记录请求延迟、事件循环延迟、线程池等待、活跃任务、队列积压、连接池占用和下游超时。为每个请求传递 correlation ID，但避免将用户敏感数据写入日志。数据库 async 边界见 [SQL 数据库与事务](/kb/language/Python/服务框架/FastAPI/08-SQL-数据库与事务/)，Router 与配置见 [大型应用配置与工程结构](/kb/language/Python/服务框架/FastAPI/10-大型应用配置与工程结构/)。
